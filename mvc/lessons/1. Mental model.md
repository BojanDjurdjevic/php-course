# 1. MVC Mental Model — Šta MVC zapravo rešava

## 1. Problem pre MVC-a

Zamisli PHP fajl:

```php
<?php

session_start();

$pdo = new PDO(...);

if (!isset($_SESSION['user_id'])) {
    header('Location: login.php');
    exit;
}

$id = (int) ($_GET['id'] ?? 0);

$stmt = $pdo->prepare(
    'SELECT * FROM bookings WHERE id = :id'
);

$stmt->execute([
    'id' => $id,
]);

$booking = $stmt->fetch();

if (!$booking) {
    http_response_code(404);
    echo 'Booking not found';
    exit;
}

if (
    $booking['user_id']
    !== $_SESSION['user_id']
) {
    http_response_code(403);
    exit;
}

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    // validate CSRF
    // check state
    // update booking
    // update inventory
    // send email
}

?>

<h1>
    <?= htmlspecialchars(
        $booking['reference']
    ) ?>
</h1>
```

Ovaj fajl možda potpuno radi.

Ali u njemu imamo:

```text
HTTP handling
session
authentication
authorization
SQL
business logic
HTML
redirects
error handling
```

sve na jednom mestu.

Problem nije:

```text
"PHP ne dozvoljava ovakav kod."
```

Problem je:

```text
svaka promena utiče na sve
```

---

## 2. Kako aplikacija raste

Za malu skriptu:

```text
login.php
booking.php
cancel.php
```

možda deluje sasvim razumno.

Ali onda dođu:

```text
admin booking pregled
API
email notifications
PDF voucher
availability
refund
permissions
tests
```

I ista business pravila počnu da se pojavljuju na više mesta.

Na primer:

```text
Može li booking da se otkaže?
```

odjednom proverava:

```text
cancel.php
admin-cancel.php
Booking API
mobile API
```

Ako logiku promeniš na jednom mestu, a zaboraviš drugo:

```text
bug
```

MVC pokušava da smanji ovu vrstu haosa razdvajanjem odgovornosti.

# 3. Osnovna MVC ideja

MVC znači:

```text
Model
View
Controller
```

Najjednostavnije:

```text
Controller
→ prima zahtev i koordinira

Model
→ predstavlja application/domain state i logiku

View
→ prikazuje rezultat
```

Mentalno:

```text
USER
↓
REQUEST
↓
CONTROLLER
↓
MODEL
↓
CONTROLLER
↓
VIEW
↓
RESPONSE
↓
USER
```

Ovo je osnovna slika.

Ali u realnoj PHP aplikaciji architecture će imati više slojeva.

---

# 4. Controller — koordinator

Controller ne treba da bude:

```text
mesto gde živi cela aplikacija
```

Njegov posao je uglavnom:

```text
primi HTTP request
↓
izvuci ono što mu treba
↓
pozovi odgovarajući application use case
↓
pretvori rezultat u HTTP response
```

Na primer:

```php
public function show(
    int $id
): Response {
    $booking =
        $this->bookingService
            ->getForUser(
                $id,
                $this->auth->id()
            );

    return $this->view->render(
        'bookings/show',
        [
            'booking' => $booking,
        ]
    );
}
```

Controller zna:

```text
koji use case treba da pozove
koji response treba da vrati
```

Ali ne treba da zna:

```text
SQL
PDO
kako se računa cena
kako inventory radi
kako se hashira password
```

---

# 5. Controller nije business layer

Loše:

```php
public function cancel(
    int $id
): Response {
    $booking =
        $this->repository->findById($id);

    if (
        $booking->status === 'confirmed'
        && $booking->checkIn > new DateTime()
        && $booking->userId === $this->auth->id()
    ) {
        // update booking
        // restore inventory
        // email guest
    }

    return ...;
}
```

Ovde Controller zna previše.

Bolje:

```php
public function cancel(
    int $id
): Response {
    $this->bookingService->cancel(
        $id,
        $this->auth->user()
    );

    return Response::redirect(
        '/bookings'
    );
}
```

Controller kaže:

```text
"otkaži booking"
```

Service/domain zna:

```text
"šta cancellation znači"
```

---

# 6. View — presentation layer

View odgovara na pitanje:

> Kako rezultat prikazujemo user-u?

Na primer:

```php
<h1>
    <?= e($booking->reference()) ?>
</h1>

<p>
    <?= e($booking->status()->value) ?>
</p>
```

View treba da zna:

```text
HTML
presentation
formatiranje
```

Ali ne treba da radi:

```php
$pdo->query(...);
```

niti:

```php
$bookingService->cancel(...);
```

View ne menja application state.

---

# 7. View nije samo HTML fajl

U klasičnoj server-rendered aplikaciji:

```text
View
→ PHP/HTML template
```

Ali šire gledano presentation layer može vratiti:

```text
HTML
JSON
XML
PDF
```

Ako imamo API:

```text
Controller
↓
application/service
↓
JSON Response
```

tu nema tradicionalnog HTML View fajla.

Zato MVC mentalni model nije:

```text
svaki Controller mora imati .php view
```

nego:

```text
presentation je odvojena
od application/business logike
```

---

# 8. Model — najzbunjujući deo MVC-a

Najčešća početnička definicija je:

```text
Model = tabela iz baze
```

ili:

```text
Model = klasa koja radi SQL
```

To je previše usko.

Originalna MVC ideja pod Model-om podrazumeva ono što predstavlja:

```text
application state
business concepts
business behavior
```

Na primer u MiniStay:

```text
User
Room
Booking
Inventory
Price
```

plus pravila koja određuju njihovo ponašanje.

---

# 9. Model nije isto što i Repository

Repository:

```php
interface BookingRepository
{
    public function findById(
        int $id
    ): ?Booking;

    public function save(
        Booking $booking
    ): void;
}
```

Repository odgovara na pitanje:

```text
Kako pronalazimo i čuvamo Booking?
```

Booking model/entity odgovara na pitanje:

```text
Šta Booking jeste?
Kako se ponaša?
Koja pravila ima?
```

To nisu iste odgovornosti.

---

# 10. Model nije isto što i PDO

Ovo:

```php
final class BookingModel
{
    public function __construct(
        private PDO $pdo
    ) {}

    public function cancel(
        int $id
    ): void {
        $this->pdo->prepare(...);
    }
}
```

može biti funkcionalno.

Ali naziv:

```text
Model
```

ne znači automatski:

```text
"mesto gde guramo sve database stvari"
```

U našoj arhitekturi ćemo jasnije razdvajati:

```text
Entity / Model
→ domain state

Repository
→ persistence

Service
→ application use case
```

---

# 11. Zašto Laravel može da zbuni

U Laravel-u imamo:

```php
class Booking extends Model
{
}
```

Eloquent `Model` predstavlja:

```text
database-backed entity
+
query capabilities
+
persistence behavior
```

Dakle Laravel koristi pojam `Model` na specifičan način.

To nije potpuno isto kao teorijska definicija:

```text
M iz MVC-a
```

Laravel Model je jedan deo šire:

```text
model/application/domain strane
```

architecture.

---

# 12. MVC nije samo tri foldera

Ako napraviš:

```text
controllers/
models/
views/
```

to još ne znači da imaš dobar MVC.

Možeš imati:

```text
BookingController.php
→ 800 linija

BookingModel.php
→ 1200 linija SQL + business logike

booking.php
→ još business logike
```

Folderi su samo organizacija.

MVC je pre svega:

```text
separation of responsibilities
```

---

# 13. Separation of Concerns

Glavna ideja:

```text
svaki deo sistema
treba da ima jasan razlog za promenu
```

Na primer:

Ako promenimo HTML:

```text
View
```

Ako promenimo routing:

```text
Router
```

Ako promenimo cancellation business rule:

```text
Service / Domain
```

Ako promenimo SQL:

```text
Repository
```

Ako promenimo HTTP redirect:

```text
Controller / Response
```

To je ogromna prednost.

---

# 14. MVC smanjuje coupling

Ako Controller direktno radi:

```php
$pdo = new PDO(...);

$stmt = $pdo->prepare(...);
```

Controller je vezan za:

```text
PDO
SQL
database schema
```

Ako umesto toga koristi:

```php
$this->bookingService->cancel(...);
```

Controller zna mnogo manje.

To smanjuje:

```text
coupling
```

i olakšava:

```text
testiranje
promene
refactoring
```

---

# 15. MVC poboljšava testability

Ako business rule stoji u Controller-u koji zavisi od:

```text
$_POST
$_SESSION
header()
exit()
PDO
```

testiranje je teško.

Ako imamo:

```php
$service->cancel(
    $bookingId,
    $user
);
```

možemo testirati use case bez browser-a.

Na primer:

```text
given:
booking confirmed

when:
cancel()

then:
status cancelled
inventory restored
```

MVC i slojevita architecture omogućavaju da business logika bude odvojena od HTTP-a.

# 16. MVC ne znači da svaki sloj sme da komunicira sa svakim

Loša mapa:

```text
View
↔ Controller
↔ Repository
↔ View
↔ PDO
↔ Service
↔ Controller
```

Sve priča sa svime.

Bolja zavisnost:

```text
Controller
↓
Service
↓
Repository
↓
Database
```

i za output:

```text
Controller
↓
View
↓
HTML
```

Granice treba da budu predvidive.

# 17. Realna aplikacija je veća od MVC trougla

Naš Vanilla PHP projekat će zapravo izgledati približno:

```text
              Request
                 ↓
              Router
                 ↓
            Middleware
                 ↓
            Controller
              ↙   ↘
         Service   View
            ↓        ↓
       Repository   HTML
            ↓
         Database
```

Uz:

```text
DTO
Validation
Authentication
Authorization
Error handling
Storage
```

Dakle:

```text
MVC
```

je osnova.

Ali moderna aplikacija često koristi dodatne patterns da razdvoji odgovornosti još jasnije.

# 18. Gde je onda "Model" u ovoj slici?

U našoj arhitekturi širi Model side izgleda otprilike:

```text
Service
↓
Domain/Entities
↓
Repositories
↓
Database
```

Drugim rečima:

```text
M
```

nije nužno samo jedna klasa ili jedan folder.

To je šira application/domain strana koja predstavlja podatke, pravila i ponašanje sistema.

# 21. Overengineering

Važan princip:

```text
separation
≠ maksimalan broj klasa
```

Ne treba za svaki:

```text
echo
if
array
```

praviti poseban Service.

Dobar design pita:

```text
Da li postoji stvarna odgovornost
koja zaslužuje svoju granicu?
```

Na primer:

```text
Booking cancellation
```

ima dovoljno business pravila da Service ima smisla.

Ali:

```text
formatiranje naslova stranice
```

verovatno ne zahteva `PageTitleService`.

---

# 22. Thin Controller ne znači anoreksičan Controller

Čućeš:

```text
Fat Model, Skinny Controller
```

ili:

```text
Controllers should be thin.
```

Ideja je dobra:

```text
business logic ne treba živeti u Controller-u
```

Ali ne treba opsesivno pokušavati da Controller ima:

```text
2 linije
```

Controller sme da radi HTTP orchestration:

```text
read input
invoke validator/request object
authorize
call service
select response
```

To jeste njegova odgovornost.

---

# 23. MVC vs Layered Architecture

Često kažemo:

```text
MVC aplikacija
```

ali ono što gradimo je kombinacija:

```text
MVC
+
Layered Architecture
+
Repository
+
Service Layer
+
Dependency Injection
+
Middleware
```

To nije kontradikcija.

MVC rešava prvenstveno separation između:

```text
input/control
application/model
presentation
```

Dodatni patterns rešavaju detaljnije granice unutar aplikacije.

# 24. MVC i Laravel

Laravel request flow pojednostavljeno:

```text
Request
↓
public/index.php
↓
Kernel / application bootstrap
↓
Middleware
↓
Router
↓
Controller
↓
Service / Model / Repository
↓
View ili JSON Response
↓
Browser
```

Laravel ti već daje:

```text
Router
Request
Response
Middleware
Container
Validation
Auth
Views
Exception handling
```

Zato Laravel projekat izgleda mnogo čistije nego prvi Vanilla PHP projekat.

Framework nije izmislio te probleme.

Framework ti daje gotove implementations za architecture problems koje ćemo sada napraviti ručno.

---

# 25. Zašto učimo MVC bez frameworka

Cilj nije:

```text
da napravimo Laravel od nule
```

To bi bilo besmisleno.

Cilj je da razumeš šta se dešava kada napišeš:

```php
Route::get(
    '/bookings/{booking}',
    [BookingController::class, 'show']
);
```

Framework iza toga rešava mnogo stvari:

```text
request
routing
parameters
controller resolution
dependency injection
response handling
exceptions
```

Kada razumeš Vanilla verziju:

```text
Laravel više nije magija
```

# Najvažnije za zapamtiti

MVC znači:

```text
Model
View
Controller
```

ali njegova glavna vrednost nije naziv foldera.

Glavna vrednost je:

```text
SEPARATION OF CONCERNS
```

Controller:

```text
prima HTTP input
koordinira use case
vraća response
```

View:

```text
prikazuje rezultat
```

Model side:

```text
predstavlja application/domain
state + behavior
```

U realnoj aplikaciji Model stranu često razlažemo na:

```text
Entities
Services
Repositories
```

Controller ne treba da zna:

```text
SQL
PDO
business details
```

View ne treba da:

```text
radi SQL
menja state
```

Repository:

```text
persistence
```

nije isto što i:

```text
domain model
```

Service:

```text
use case / application orchestration
```

nije isto što i Controller.

MVC:

```text
nije tri foldera
```

nego:

```text
jasne granice odgovornosti
```

Realna Vanilla aplikacija:

```text
Request
↓
Router
↓
Middleware
↓
Controller
↓
Service
↓
Repository
↓
Database
```

a output:

```text
Service result
↓
Controller
↓
View / Response
↓
Browser
```

I najvažnija rečenica:

> **MVC ne postoji da bi kod izgledao „enterprise“, već da bi HTTP, business logika, persistence i presentation mogli da se menjaju bez toga da svaki put rasturimo ostatak aplikacije.**
