# 2. Front Controller & Application Entry Point

## 1. Klasičan "više PHP fajlova" pristup

Početni PHP projekat često izgleda ovako:

```text
public/
├── index.php
├── login.php
├── register.php
├── bookings.php
├── booking.php
├── cancel-booking.php
├── profile.php
└── logout.php
```

Browser direktno poziva konkretan PHP fajl:

```text
GET /login.php
GET /bookings.php
POST /cancel-booking.php
```

Svaki fajl je zaseban entry point.

Na primer:

```php
<?php

session_start();

require '../db.php';

if (!isset($_SESSION['user_id'])) {
    header('Location: login.php');
    exit;
}

$id = (int) ($_POST['id'] ?? 0);

// validation
// authorization
// SQL
// business logic
// redirect
```

Ovo može sasvim dobro da radi za malu aplikaciju.

Problem počinje kada aplikacija raste.

---

## 2. Problem sa mnogo entry point-a

Ako imamo:

```text
login.php
register.php
bookings.php
cancel-booking.php
profile.php
```

svaki fajl možda mora da ponovi:

```text
autoload
.env
session_start()
database connection
error handling
security config
authentication setup
```

Vrlo brzo dobiješ:

```text
50 PHP fajlova
↓
50 potencijalno različitih bootstrap flow-ova
```

Jedan developer doda:

```php
session_regenerate_id(true);
```

na jedno mesto.

Drugi zaboravi na drugom.

Jedan endpoint ima CSRF.

Drugi nema.

Jedan koristi novi error handler.

Drugi i dalje prikazuje raw exception.

To je arhitektonski problem.

---

# 3. Front Controller pattern

Umesto mnogo entry point-a:

```text
login.php
register.php
bookings.php
...
```

imamo jedan:

```text
public/index.php
```

Sve request-e prvo prima:

```text
index.php
```

Mentalno:

```text
Browser
↓
Web Server
↓
public/index.php
↓
Application
↓
Router
↓
Controller
```

To je:

```text
Front Controller Pattern
```

---

# 4. "Front" ne znači frontend

Važna terminologija.

Front Controller nije:

```text
JavaScript frontend
Vue
React
HTML
```

"Front" znači:

```text
ispred ostatka backend aplikacije
```

On stoji kao zajednička ulazna tačka ispred:

```text
router-a
controller-a
service-a
repository-ja
```

Dakle:

```text
FRONT CONTROLLER
→ prvi application-level entry point
```

---

# 5. Kako request dolazi do `index.php`

Pretpostavimo user otvori:

```text
GET /bookings/42
```

Na filesystem-u ne postoji:

```text
public/bookings/42
```

Web server je konfigurisan tako da request koji nije stvarna static datoteka prosledi na:

```text
public/index.php
```

Dakle:

```text
GET /bookings/42
↓
web server rewrite
↓
public/index.php
```

PHP zatim može da vidi originalni URI:

```php
$_SERVER['REQUEST_URI'];
```

na primer:

```text
/bookings/42
```

Router odlučuje šta sa tim request-om.

---

# 6. Apache rewrite mentalni model

Kod Apache-a često imamo `.htaccess`.

Konceptualno:

```apache
RewriteEngine On

RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d

RewriteRule ^ index.php [QSA,L]
```

Ideja:

```text
Ako request NIJE stvarni fajl
i NIJE stvarni direktorijum
↓
pošalji ga na index.php
```

Zato:

```text
/assets/app.css
```

može i dalje biti stvarna static datoteka.

Ali:

```text
/bookings/42
```

ide kroz aplikaciju.

---

# 7. Nginx mentalni model

Kod Nginx-a ista ideja može izgledati kao:

```nginx
try_files $uri $uri/ /index.php?$query_string;
```

Opet:

```text
stvarni file?
→ serviraj

stvarni directory?
→ koristi

inače
→ index.php
```

Nije bitno da sada pamtiš web-server sintaksu.

Bitna je arhitektura:

```text
dynamic application routes
→ jedan PHP entry point
```

---

# 8. Zašto je ovo bolje za routing

Sada možemo imati lepe URL-ove:

```text
GET  /bookings
GET  /bookings/42
POST /bookings
POST /bookings/42/cancel
```

umesto:

```text
GET  /bookings.php
GET  /booking.php?id=42
POST /create-booking.php
POST /cancel-booking.php?id=42
```

Router dobija:

```text
HTTP method
+
URI
```

i bira Controller.

Na primer:

```text
GET + /bookings
→ BookingController::index

GET + /bookings/42
→ BookingController::show

POST + /bookings
→ BookingController::store
```

---

# 9. Front Controller centralizuje bootstrap

Najveća prednost nije samo lepši URL.

Svi request-i prolaze kroz isti početak:

```php
<?php

require_once dirname(__DIR__)
    . '/vendor/autoload.php';

Dotenv\Dotenv::createImmutable(
    dirname(__DIR__)
)->load();

$session->start();

set_exception_handler(...);

$router = ...;

$response = $router->dispatch(...);

$response->send();
```

Sada imamo jedno mesto za:

```text
autoload
config
session
error handlers
DI wiring
router startup
```

# 10. Jedan application lifecycle

Sa Front Controller-om svaki request ima isti osnovni lifecycle:

```text
REQUEST
↓
index.php
↓
bootstrap
↓
router
↓
middleware
↓
controller
↓
service
↓
repository
↓
response
```

To daje predvidivost.

Predvidivost je ogromna arhitektonska prednost.

# 11. Front Controller i Security

Pošto svi dynamic request-i prolaze kroz:

```text
├── .env
```


Ne:

Ovo je veoma važno.

# 13. Zašto `/public` postoji

Browser treba direktno da vidi samo stvari koje stvarno jesu javne.

Na primer:

```text
public/index.php
public/assets/app.css
public/assets/app.js
public/images/logo.png
```

Ne treba direktno da vidi:

```text
.env
vendor/
app/
config/
storage/
views/
composer.json
```

Dakle:

```text
public/
```

je istovremeno:

```text
architectural boundary
+
security boundary
```

---

# 14. Loš document root

Ako web server root pokazuje na:

```text
/project
```

umesto:

```text
/project/public
```

onda pogrešna server konfiguracija potencijalno može učiniti dostupnim:

```text
/.env
/composer.json
/storage/...
/config/...
```

Možda web server trenutno ne servira neke od tih fajlova.

Ali nema razloga da ih uopšte stavimo unutar javnog namespace-a.

Bolje:

```text
default architecture
→ private by location
```

---

# 15. Public-by-design vs private-by-design

Loš model:

```text
ceo projekat je public
↓
onda pokušavamo da blokiramo
.env
storage
vendor
config
```

Bolji:

```text
sve je private
↓
samo public/ je exposed
```

To je praktično:

```text
fail closed
```

na filesystem nivou.

---

# 16. `index.php` treba da bude mali

Front Controller ne znači:

```text
sada ćemo celu aplikaciju napisati u index.php
```

To bi nas vratilo na početak.

Loše:

```php
<?php

// load env
// connect PDO
// inspect URI
// validate forms
// SQL
// business logic
// render 15 pages
```

Front Controller treba da bude:

```text
entry point
```

ne:

```text
application itself
```

---

# 17. Dobar `index.php`

Konceptualno:

```php
<?php

declare(strict_types=1);

require_once dirname(__DIR__)
    . '/vendor/autoload.php';

$app = require dirname(__DIR__)
    . '/bootstrap/app.php';

$response = $app->handle();

$response->send();
```

Veoma malo koda.

Zašto?

Jer `index.php` samo kaže:

```text
pokreni aplikaciju
↓
obradi request
↓
pošalji response
```

# 18. Bootstrap file

Možemo imati:

```text
bootstrap/app.php
```

koji radi:

```text
load configuration
create PDO
create repositories
create services
create controllers
configure router
return application
```

Tako:

```text
public/index.php
```

ostaje čist.

Kasnije ćemo Bootstrap detaljno obraditi u sledećoj lekciji.

---

# 19. Front Controller nije Router

Ovo je važna razlika.

`index.php`:

```text
prima svaki request
```

Router:

```text
odlučuje koji handler ga obrađuje
```

Dakle:

```text
Front Controller
↓
Router
↓
Controller
```

Ne:

```text
Front Controller = Router = Controller
```

Mogu tehnički biti spojeni u maloj aplikaciji.

Ali konceptualno su različite odgovornosti.

---

# 20. Front Controller nije Controller iz MVC-a

Još jedna česta zabuna.

Imamo:

```text
Front Controller Pattern
```

i:

```text
MVC Controller
```

To nisu ista stvar.

Front Controller:

```text
jedna globalna ulazna tačka
```

MVC Controller:

```text
handler određenog use case-a / resource-a
```

Na primer:

```text
public/index.php
↓
Router
↓
BookingController::show()
```

`index.php` je Front Controller.

`BookingController` je MVC Controller.

```text
↓
```

# 23. Front Controller i error handling

Ako sve ide kroz isti entry point:

```text
Unhandled Throwable
↓
Global Exception Handler
↓
safe 500 response
```

Mnogo je lakše nego imati:

```text

→ jedan error style

→ drugi

admin.php
→ raw stack trace
```

Centralizacija daje konzistentno ponašanje.

# 24. Front Controller i dependency injection

Jedan application startup omogućava da jednom napravimo:

```php
$pdo =
    new PDO(...);

$users =
    new PdoUserRepository($pdo);

$bookings =
    new PdoBookingRepository($pdo);

$bookingService =
    new BookingService(
        $bookings
    );

$bookingController =
    new BookingController(
        $bookingService
    );
```

Router zatim dobija već konfigurisane handler-e.

Ne moramo u svakom `.php` fajlu ponovo da pravimo ceo object graph.

# 25. Front Controller i testiranje

Ako business endpoints nisu fizički zasebni PHP scriptovi:


```text

```

```text

```

```text

```

Manje smo vezani za:

```text

```

# 26. Front Controller i REST-ish routing

Front Controller omogućava da URI predstavlja resource:

```text
/bookings
/bookings/42
/rooms/5
/users/17
```

a HTTP method predstavlja action/context:

```text
GET
POST
PUT
PATCH
DELETE
```

Na primer:

```text
GET /bookings/42
→ show

PATCH /bookings/42
→ update

DELETE /bookings/42
→ delete
```

Za klasične HTML forme često koristimo praktičnije POST action rute, npr.:

```text
POST /bookings/42/cancel
```

Nije cilj da budemo REST fanatični.

Poenta je da routing postane jasan i centralan.

# Najvažnije za zapamtiti

Front Controller znači:

```text
svi dynamic application request-i
↓
jedan entry point
↓
public/index.php
```

To omogućava centralizaciju:

```text
bootstrap
config
sessions
error handling
routing
security
DI
```

Front Controller:

```text
≠ MVC Controller
```

Front Controller:

```text
global application entry point
```

MVC Controller:

```text
obrađuje određeni use case/request
```

Router:

```text
odlučuje koji Controller pozivamo
```

`public/` treba da bude:

```text
jedini web-accessible root
```

Private:

```text
.env
src/
vendor/
storage/
config/
```

Public:

```text
index.php
CSS
JS
images
ostali stvarno javni assets
```

Dobar architecture:

```text
PRIVATE BY DEFAULT
↓
public/ eksplicitno izložen
```

Static resource:

```text
/assets/app.css
→ web server direktno
```

Dynamic request:

```text
/bookings/42
→ index.php
→ Router
→ Controller
```

Front Controller ne treba da sadrži celu aplikaciju.

Treba da bude mali:

```text
BOOT
↓
HANDLE
↓
SEND
```

Centralni mentalni model:

```text
INTERNET
↓
PUBLIC/
↓
INDEX.PHP
↓
APPLICATION
↓
ROUTER
↓
CONTROLLER
```

Ako samo jednu rečenicu zapamtiš:

> **Front Controller pretvara PHP aplikaciju iz kolekcije nezavisnih skripti u jedan sistem sa jedinstvenim request lifecycle-om.**
