# 8. Views & View Renderer

## 1. Šta je View

View odgovara na pitanje:

> Kako rezultat aplikacije prikazujemo korisniku?

U server-rendered PHP aplikaciji View je najčešće:

```text
PHP + HTML template
```

Na primer:

```php
<h1>
    <?= e($booking->reference()) ?>
</h1>

<p>
    Status:
    <?= e($booking->status()->value) ?>
</p>
```

View zna:

```text
presentation
markup
formatiranje
```

Ne treba da zna:

```text
SQL
PDO
business transakcije
authorization policy implementation
```

---

# 2. View nije samo HTML

Čist HTML ne može da prikaže dinamičke podatke.

Zato PHP template može sadržati:

```php
<?php foreach ($bookings as $booking): ?>

    <article>
        <?= e($booking->reference()) ?>
    </article>

<?php endforeach; ?>
```

To je potpuno normalno.

View sme da ima:

```text
if
foreach
formatiranje
conditional rendering
```

jer su to presentation concerns.

---

# 3. Presentation logic vs business logic

Ovo je ključna granica.

View sme:

```php
<?php if ($booking->canBeShownAsCancelled()): ?>
    <span>Cancelled</span>
<?php endif; ?>
```

ako metoda samo daje presentation-friendly informaciju.

Ali View ne treba da radi:

```php
<?php

if (
    $booking->status() === 'confirmed'
    && $booking->checkIn() > new DateTimeImmutable()
) {
    $booking->cancel();
}

?>
```

To menja business state.

Dakle:

```text
presentation decision
→ View

business decision
→ Service / Domain
```

---

# 4. View ne treba da priča sa bazom

Loše:

```php
<?php

$stmt = $pdo->query(
    'SELECT * FROM bookings'
);

$bookings = $stmt->fetchAll();

?>
```

Zašto je loše?

Jer View sada zna:

```text
PDO
SQL
database schema
```

i više nije samo presentation layer.

Bolje:

```text
Controller
↓
Service / Repository
↓
data
↓
View
```

---

# 5. View ne treba da poziva Repository

Loše:

```php
<?php

$bookings =
    $bookingRepository
        ->findForUser(
            $user->id()
        );

?>
```

Onda View sam odlučuje:

```text
koje podatke da učita
kako da ih učita
```

To krši separation.

Controller treba da pripremi data:

```php
return Response::html(
    $this->view->render(
        'bookings/index',
        [
            'bookings' => $bookings,
        ]
    )
);
```

View samo koristi ono što dobije.

---

# 6. View data

Controller može poslati:

```php
[
    'bookings' => $bookings,
    'user' => $user,
    'flash' => $flash,
]
```

View Renderer zatim učini te vrednosti dostupnim template-u.

Na primer:

```php
$view->render(
    'bookings/index',
    [
        'bookings' => $bookings,
    ]
);
```

U template-u:

```php
<?php foreach ($bookings as $booking): ?>
    ...
<?php endforeach; ?>
```

---

# 7. `extract()`

Jednostavan View Renderer može koristiti:

```php
extract(
    $data,
    EXTR_SKIP
);
```

Ako imamo:

```php
[
    'bookings' => $bookings,
    'title' => 'My Bookings'
]
```

u template-u dobijamo:

```php
$bookings
$title
```

To je praktično.

---

# 8. Zašto `EXTR_SKIP`

Ako postoji lokalna promenljiva:

```php
$viewPath
```

ne želimo da je data array slučajno pregazi.

Zato:

```php
extract(
    $data,
    EXTR_SKIP
);
```

znači:

```text
ako varijabla već postoji
→ ne overwrite-uj
```

To je bezbednije.

---

# 9. Minimalni View Renderer

Možemo imati:

```php
final class ViewRenderer
{
    public function __construct(
        private string $basePath
    ) {}

    public function render(
        string $view,
        array $data = []
    ): string {
        $path =
            $this->basePath
            . '/'
            . $view
            . '.php';

        extract(
            $data,
            EXTR_SKIP
        );

        ob_start();

        require $path;

        return ob_get_clean();
    }
}
```

Tok:

```text
view name
+
data
↓
template
↓
HTML string
```

---

# 10. Output buffering

Ako template radi:

```php
<h1>Hello</h1>
```

to bi inače odmah išlo na output.

Sa:

```php
ob_start();
```

PHP privremeno hvata output u buffer.

Zatim:

```php
$html =
    ob_get_clean();
```

dobijamo string.

Dakle:

```text
template output
↓
buffer
↓
HTML string
↓
Response
```

# 11. Zašto je to korisno

Controller može:

```php
$html =
    $this->view->render(
        'rooms/index',
        [
            'rooms' => $rooms,
        ]
    );

return Response::html(
    $html
);
```

View više ne šalje response direktno.

On samo:

```text

```

Response ga šalje.

---

# 12. View ne treba da radi `header()`

Loše:

```php
<?php

header(
    'Location: /login'
);

exit;

?>
```

View ne treba da odlučuje navigation flow.

To pripada:

```text
Controller / Response
```

View prikazuje rezultat.

Ne upravlja request lifecycle-om.

---

# 13. View ne treba da radi redirect

Isto:

```text
View
→ presentation

Controller
→ redirect
```

Ako View otkrije:

```text

```

to ne znači da treba da radi redirect.

Controller ili application layer treba već da zna šta to znači.

# 16. Jednostavan layout flow

Prvo renderujemo page:

```php
$content =
    $this->renderFile(
        'bookings/index',
        $data
    );
```

zatim:

```php
return $this->renderFile(
    'layouts/app',
    [
        'content' => $content,
        'title' => $title,
    ]
);
```

Layout:

```php
<!DOCTYPE html>
<html>
<head>
    <title>
        <?= e($title) ?>
    </title>
</head>

<body>

    <main>
        <?= $content ?>
    </main>

</body>
</html>
```

Ovde `$content` je već naš trusted rendered template output.

---

# 17. Zašto ne escape-ujemo ceo `$content`

Ako uradimo:

```php
<?= e($content) ?>
```

HTML:

```html
<h1>Bookings</h1>
```

postao bi tekst:

```text
<h1>Bookings</h1>
```

Zato treba razlikovati:

```text
untrusted data
vs
already-rendered HTML fragment
```

Layout renderuje HTML content namerno kao HTML.

Ali individualne user-controlled vrednosti unutar tog content-a moraju već biti pravilno escaped.

# 18. Partial

Partial je mali reusable presentation fragment.

Na primer:

```text
views/
└── partials/
    ├── flash.php
    └── booking-card.php
```

Ako više stranica koristi isti booking card:

```php
<?php require ... ?>
```

može biti razumno.

# 19. Partial nije mini Controller

Loše:

```php
<?php

$booking =
    $bookingRepository
        ->findById($id);

?>
```

u partial-u.

Partial treba da dobije:

```text

```

Na primer:

```php

    'partials/booking-card',

        'booking' => $booking,
    ]

```

# 20. View helper

Možemo imati funkciju:

```php
function e(
    mixed $value
): string {
    return htmlspecialchars(
        (string) $value,
        ENT_QUOTES,
        'UTF-8'
    );
}
```

Pa u View-u:

```php
<?= e($user->name()) ?>
```

To poboljšava čitljivost.

---

# 21. Escaping pripada output-u

Iz Security modula:

```text
escape late
```

Tačka na kojoj user data ide u HTML je upravo:

```text
View
```

Zato View ima važnu security odgovornost:

```text
context-aware output escaping
```

---

# 22. HTML text context

Za:

```php
<h1>
    <?= e($booking->reference()) ?>
</h1>
```

koristimo HTML escaping.

Ako reference sadrži:

```text
<script>alert(1)</script>
```

browser dobija tekst.

Ne executable HTML.

---

# 23. Attribute context

Na primer:

```php
<input
    value="<?= e($user->name()) ?>"
>
```

`ENT_QUOTES` je važan jer vrednost ulazi u quoted HTML attribute.

Opet:

```text
data
↓
escape for actual output context
```

---

# 24. URL context

Pretpostavimo:

```php
<a href="<?= e($url) ?>">
```

Samo HTML escaping nije cela priča.

Ako `$url` može biti user-controlled:

```text
javascript:...
```

treba prvo imati URL policy/validation.

Dakle:

```text
validate allowed URL semantics
+
escape for HTML attribute
```

---

# 25. JavaScript context

Ovo:

```php
<script>
const name =
    '<?= e($user->name()) ?>';
</script>
```

nije idealan način.

HTML escaping nije JavaScript escaping.

Bolje:

```php
<script>
const user =
    <?= json_encode(
        $data,
        JSON_HEX_TAG
        | JSON_HEX_AMP
        | JSON_HEX_APOS
        | JSON_HEX_QUOT
    ) ?>;
</script>
```

ili još bolje izbegavati unnecessary inline JS data.

Kontekst je bitan.

---

# 26. Database data nije automatski trusted

Ako user ime dolazi iz DB:

```php
$user->name()
```

to ne znači:

```text
safe HTML
```

DB možda sadrži input koji je user ranije uneo.

Zato i dalje:

```php
<?= e($user->name()) ?>
```

Security mentalni model:

```text
stored
≠ trusted
```

---

# 27. Raw HTML

Ponekad imamo legitimno trusted HTML:

```text
rich-text CMS content
```

Ali tada sadržaj mora biti:

```text
trusted
ili
propisno sanitized
```

Raw output treba biti eksplicitan i redak.

Na primer:

```php
<?= $trustedHtml ?>
```

treba odmah da privuče pažnju na code review-u.


# 29. View sme da ima `foreach`

Na primer:

# 30. View sme da formatira podatke


ili:

# 31. Ali formatiranje može zaslužiti helper

Ako svuda pišemo:

```php

    $price,

    ',',

```

možemo napraviti:

```php

```

Ne business logic.

# 32. View ne treba da računa cenu

Ovo:

```php
<?php

$total =
    $room->price()
    * $booking->nights();

?>
```

može delovati bezazleno.

Ali ako je total business vrednost:

```text
View ne treba ponovo da je računa
```

Service/domain treba da je već izračunao.

```php

    $booking->total()
) ?>
```

# 33. View ne treba da odlučuje authorization

Loše:

```php
<?php

if (
    $booking->userId()

}

?>
```

# 34. Hiding button nije authorization

# 40. Ne prosleđuj secret u View bez potrebe

Ako View dobije:

```text
DB password
API secret
session token
```

to je već design smell.

Presentation layer treba samo ono što realno mora da prikaže ili koristi.

Least privilege važi i ovde.

---

# 41. View Renderer treba da spreči arbitrary path

Ako Controller može da uradi:

```php
$view->render(
    $request->query('view')
);
```

attacker možda pokuša:

```text
../../config/secret
```

Zato View name treba da dolazi iz:

```text
application-controlled mapping
```

ne arbitrary user input-a.

---

# 42. View name kao logical key

Dobro:

```php
$view->render(
    'bookings/show',
    [...]
);
```

Renderer ga mapira na:

```text

```

Client ne šalje filesystem path.

To je isti principle koji smo imali kod filesystem security-ja.

# 43. `realpath()` i View Renderer

Ako Renderer podržava dinamičke names, može dodatno proveriti canonical path.

Ali najbolji design je:

```text

→ application-controlled logical identifier
```

Tada ne moramo da rešavamo arbitrary filesystem navigation svaki put.

Architecture je security control.

# 50. View i N+1 problem

Zamisli View:

```php
<?php foreach ($bookings as $booking): ?>

    <?= e(
        $booking
            ->guest()
            ->name()
    ) ?>

<?php endforeach; ?>
```

Ako `guest()` svaki put radi DB query:

```text
100 bookings
→ 100 dodatnih queries
```

View možda nije direktno napisao SQL, ali data model design može izazvati N+1.

Zato Controller/service/query layer treba da pripremi potrebne podatke efikasno.

View ne treba da pokreće skriveni persistence work.

# 57. View Renderer i exception safety

Ako template baci exception tokom:

```php
require $path;
```

treba paziti na output buffer.

Na primer:

```php
ob_start();

try {
    require $path;

    return ob_get_clean();
} catch (Throwable $e) {
    ob_end_clean();

    throw $e;
}
```

Inače buffer može ostati otvoren.

To je implementation detail Renderer-a.

---

# 58. View Renderer skeleton

Malo ozbiljnija verzija:

```php
final class ViewRenderer
{
    public function __construct(
        private string $basePath
    ) {}

    public function render(
        string $view,
        array $data = []
    ): string {
        $path =
            $this->basePath
            . '/'
            . $view
            . '.php';

        if (!is_file($path)) {
            throw new ViewNotFoundException(
                $view
            );
        }

        extract(
            $data,
            EXTR_SKIP
        );

        ob_start();

        try {
            require $path;

            return ob_get_clean();
        } catch (Throwable $e) {
            ob_end_clean();

            throw $e;
        }
    }
}
```

Dovoljno jasno za naš Vanilla MVC.

```php
            ->getForUser(
                $this->auth->user(),
                $request->route('id')
            );

    return Response::html(
        $this->view->render(
            'bookings/show',
            [
                'booking' =>
                    $booking,

                'canCancel' =>
                    $this->policy
                        ->canCancel(
                            $this->auth->user(),
                            $booking
                        ),
            ]
        )
    );
}
```

# Najvažnije za zapamtiti

View odgovara na:

```text
Kako prikazujemo rezultat?
```

View sme da:

```text
renderuje HTML
koristi if
koristi foreach
formatira datume/cene
prikazuje validation errors
prikazuje flash messages
sakrije/prikaže dugmad
escape-uje output
```

View ne treba da:

```text
radi SQL
koristi Repository
menja business state
pokreće transakcije
šalje business email
radi redirect
implementira authorization
```

View Renderer:

```text
view name
+
data
↓
PHP template
↓
HTML string
```

Output buffering omogućava da template output pretvorimo u string pre nego što ga stavimo u Response.

Layout:

```text
shared page shell
```

Partial:

```text
reusable presentation fragment
```

Najvažnija security odgovornost View-a:

```text
CONTEXT-AWARE OUTPUT ESCAPING
```

DB data:

```text
≠ trusted HTML
```

Hiding button:

```text
≠ authorization
```

View data treba da bude:

```text
explicit
minimal
namerno prosleđena
```

Dobar flow:

```text
CONTROLLER
↓
DATA
↓
VIEW
↓
HTML
↓
RESPONSE
```

Ako samo jednu rečenicu zapamtiš:

> **View sme da odlučuje kako nešto izgleda i da li se prikazuje, ali ne sme da odlučuje da li se business operacija izvršava niti kako se podaci čuvaju.**
