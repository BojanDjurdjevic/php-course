# 5. Request Object — Od superglobals do HTTP abstraction-a

## 1. Problem sa direktnim korišćenjem superglobal-a

U čistom PHP-u lako završimo sa kodom poput:

```php
$id = $_GET['id'] ?? null;

$email = $_POST['email'] ?? null;

$method = $_SERVER['REQUEST_METHOD'];

$token = $_SERVER['HTTP_X_CSRF_TOKEN']
    ?? null;

$file = $_FILES['photo']
    ?? null;
```

Ovo radi.

Ali sada Controller direktno zavisi od:

```text
$_GET
$_POST
$_SERVER
$_COOKIE
$_FILES
```

Drugim rečima:

```text
Controller
↓
PHP global runtime
```

To stvara nekoliko problema:

```text
teže testiranje
razbacano parsing ponašanje
ponavljanje
nejasne granice
teže menjanje HTTP infrastrukture
```

---

# 2. Request Object

Umesto da svaki Controller direktno razgovara sa superglobal-ima, možemo imati:

```php
$request = Request::capture();
```

Sada:

```php
$request->method();

$request->path();

$request->query('status');

$request->input('email');

$request->header('Accept');

$request->cookie('session');

$request->file('photo');
```

Mentalno:

```text
PHP SUPERGLOBALS
↓
REQUEST OBJECT
↓
APPLICATION
```

Request postaje HTTP abstraction boundary.

---

# 3. Request nije samo `$_POST`

Request predstavlja ceo HTTP request.

Može sadržati:

```text
method
URI
path
query parameters
request body
headers
cookies
uploaded files
route parameters
server metadata
```

Dakle:

```text
Request
≠ POST data
```

Request predstavlja:

```text
HTTP REQUEST AS AN OBJECT
```

---

# 4. Request lifecycle

Front Controller:

```php
$request = Request::capture();
```

Router:

```php
$response =
    $router->dispatch($request);
```

Controller:

```php
public function store(
    Request $request
): Response {
    ...
}
```

Tok:

```text
PHP runtime
↓
Request
↓
Router
↓
Controller
```

Od tog trenutka Controller više ne mora direktno da zna odakle PHP uzima HTTP podatke.

---

# 5. `capture()` kao boundary

Jednostavan primer:

```php
final class Request
{
    public static function capture(): self
    {
        return new self(
            server: $_SERVER,
            query: $_GET,
            body: $_POST,
            cookies: $_COOKIE,
            files: $_FILES
        );
    }
}
```

Ovo je trenutak kada:

```text
global mutable state
```

pretvaramo u:

```text
explicit object dependency
```

To je architectural improvement samo po sebi.

---

# 6. Constructor

Možemo imati:

```php
final class Request
{
    public function __construct(
        private array $server,
        private array $query,
        private array $body,
        private array $cookies,
        private array $files,
        private array $routeParams = []
    ) {}
}
```

Sada Request može biti napravljen i bez stvarnog browser request-a.

Na primer u testu:

```php
$request = new Request(
    server: [
        'REQUEST_METHOD' => 'POST',
        'REQUEST_URI' => '/login',
    ],
    query: [],
    body: [
        'email' => 'test@example.com',
        'password' => 'secret',
    ],
    cookies: [],
    files: []
);
```

To je mnogo lakše testirati nego menjati:

```php
$_POST
$_SERVER
```

globalno.

---

# 7. Method

Request može imati:

```php
public function method(): string
{
    return strtoupper(
        $this->server['REQUEST_METHOD']
        ?? 'GET'
    );
}
```

Poziv:

```php
$request->method();
```

vrati:

```text
GET
POST
PATCH
DELETE
```

Router koristi:

```text
method + path
```

za matching.

---

# 8. Method nije application validation

Request može normalizovati:

```text
post
→ POST
```

ali ne treba da odlučuje:

```text
da li BookingController sme da prihvati POST
```

To radi Router.

Dakle:

```text
Request
→ predstavlja method

Router
→ odlučuje šta method znači za route
```

---

# 9. URI vs Path

`REQUEST_URI` može biti:

```text
/bookings/42?include=guest
```

Ali Router želi:

```text
/bookings/42
```

Zato:

```php
public function path(): string
{
    return parse_url(
        $this->server['REQUEST_URI']
            ?? '/',
        PHP_URL_PATH
    ) ?: '/';
}
```

Sada:

```php
$request->path();
```

daje:

```text
/bookings/42
```

---

# 10. Query parameters

Za:

```text
GET /bookings?status=confirmed&page=2
```

PHP daje:

```php
$_GET = [
    'status' => 'confirmed',
    'page' => '2',
];
```

Request:

```php
public function query(
    string $key,
    mixed $default = null
): mixed {
    return $this->query[$key]
        ?? $default;
}
```

Controller:

```php
$status =
    $request->query('status');

$page =
    $request->query('page', 1);
```

---

# 11. Query data je i dalje untrusted

Ovo:

```php
$request->query('page');
```

ne znači:

```text
page je integer
```

PHP HTTP input je često string.

Na primer:

```text
?page=2
```

može dati:

```php
'2'
```

A attacker može poslati:

```text
?page=banana
```

Dakle:

```text
Request retrieval
≠ validation
```

---

# 12. Body data

Kod običnog HTML form POST-a:

```php
$request->input('email');
```

može čitati iz:

```php
$this->body
```

Na primer:

```php
public function input(
    string $key,
    mixed $default = null
): mixed {
    return $this->body[$key]
        ?? $default;
}
```

Ali ovo je samo najjednostavnija verzija.

---

# 13. `input()` i query mixing

Neki framework-i imaju `input()` koji može kombinovati više sources.

Na primer:

```text
query
+
body
```

Ali za edukativnu arhitekturu je često bolje da budemo eksplicitni:

```php
$request->query('page');

$request->input('email');
```

Zašto?

Jer odmah znamo:

```text
odakle podatak dolazi
```

Eksplicitnost nam ovde pomaže više nego convenience.

---

# 14. JSON body

Ako API šalje:

```http
Content-Type: application/json
```

`$_POST` neće nužno sadržati JSON body kao form data.

Moramo pročitati raw body:

```php
$raw = file_get_contents(
    'php://input'
);
```

zatim:

```php
$data = json_decode(
    $raw,
    true,
    512,
    JSON_THROW_ON_ERROR
);
```

Request abstraction može ovo centralizovati.

---

# 15. Content-Type određuje parsing strategiju

Request može pogledati:

```text
Content-Type
```

Na primer:

```text
application/x-www-form-urlencoded
multipart/form-data
application/json
```

i odlučiti kako da interpretira body.

Mentalno:

```text
RAW HTTP BODY
↓
Content-Type
↓
Parser
↓
structured request body
```

To je HTTP concern.

Zato ima smisla da bude u Request infrastrukturi.

---

# 16. Ali Request ne radi business validation

Request sme da uradi:

```text
JSON parsing
```

i prijavi:

```text
malformed JSON
```

Ali ne treba da odlučuje:

```text
check_out mora biti posle check_in
```

To je application validation.

Razlika:

```text
PARSING
→ mogu li da razumem request format?

VALIDATION
→ da li su podaci dozvoljeni?
```

---

# 17. Malformed JSON

Ako body nije validan JSON:

```json
{
    "email":
```

to je parsing failure.

Možemo baciti:

```php
InvalidJsonException
```

ili odgovarajući HTTP exception.

To nije isto što i:

```text
email nije validna email adresa
```

Prvo je:

```text
transport/representation problem
```

Drugo:

```text
validation problem
```

---

# 18. Headers

HTTP headers u PHP-u često završavaju kroz:

```text
$_SERVER
```

na primer:

```text
HTTP_ACCEPT
HTTP_AUTHORIZATION
HTTP_X_CSRF_TOKEN
```

Request može dati:

```php
$request->header(
    'Accept'
);
```

umesto da Controller zna PHP server naming pravila.

---

# 19. Header normalization

Možemo interno pretvoriti:

```text
X-CSRF-TOKEN
x-csrf-token
X-Csrf-Token
```

u isti canonical key.

Na primer:

```text
lowercase
```

Request abstraction skriva te detalje.

Controller samo kaže:

```php
$request->header(
    'X-CSRF-TOKEN'
);
```

---

# 20. Header nije trusted samo zato što je header

Ovo je veoma važno.

Attacker može slati:

```http
X-Role: admin
```

ili:

```http
X-User-Id: 1
```

Dakle:

```text
HEADER
≠ trusted server fact
```

Headers su takođe:

```text
untrusted request input
```

osim kada imamo posebno definisan trusted infrastructure context, npr. trusted reverse proxy.

---

# 21. Authorization header

Request može dati:

```php
$request->header(
    'Authorization'
);
```

Ali ne treba:

```text
logovati ceo header
```

jer može sadržati:

```text
Bearer token
Basic credentials
API key
```

Request abstraction može čak pomoći centralnom redaction-u.

---

# 22. Cookies

Request može imati:

```php
public function cookie(
    string $key,
    mixed $default = null
): mixed {
    return $this->cookies[$key]
        ?? $default;
}
```

Poziv:

```php
$request->cookie(
    'remember_me'
);
```

Ali cookie:

```text
dolazi od client-a
```

i dalje nije trusted.

Čak ni signed/validated cookie ne treba tretirati bez njegove odgovarajuće verifikacije.

---

# 23. Session nije isto što i Request cookie

Browser šalje session cookie kroz request.

Ali application obično ne želi da Controller radi:

```php
$request->cookie(
    'PHPSESSID'
);
```

Session infrastructure treba da:

```text
pročita session cookie
↓
resolve server-side session
↓
da aplikaciji Session abstraction
```

Dakle:

```text
Request
→ raw HTTP cookie

Session
→ server-side session state
```

Različite abstraction-e.

---

# 24. Uploaded files

Request može dati:

```php
$file =
    $request->file('photo');
```

umesto:

```php
$_FILES['photo'];
```

Ali treba imati jasan file object ili strukturu.

Na primer:

```php
final readonly class UploadedFile
{
    public function __construct(
        public string $originalName,
        public string $tempPath,
        public int $error,
        public int $size,
        public ?string $clientMime
    ) {}
}
```

Request parser može pretvoriti:

```text
$_FILES
↓
UploadedFile objects
```

---

# 25. UploadedFile nije valid file

Čak i ako imamo:

```php
UploadedFile $file
```

to ne znači:

```text
MIME validan
size dozvoljen
upload uspešan
image stvarna
```

Object samo bolje predstavlja:

```text
ono što je HTTP upload doneo
```

Security validacija ostaje u upload/use-case sloju.

---

# 26. Route parameters

Router pronađe:

```text
GET /bookings/{id}
```

za:

```text
GET /bookings/42
```

i izvuče:

```php
[
    'id' => '42'
]
```

Možemo ih dodati Request-u.

Na primer:

```php
$request =
    $request->withRouteParams(
        [
            'id' => '42'
        ]
    );
```

Controller:

```php
$id =
    $request->route('id');
```

---

# 27. Immutable Request

Lep design je da Request bude immutable.

Umesto:

```php
$request->setRouteParam(
    'id',
    42
);
```

koristimo:

```php
$request =
    $request->withRouteParams(
        $params
    );
```

Metoda pravi novu instancu:

```php
public function withRouteParams(
    array $params
): self {
    return new self(
        server: $this->server,
        query: $this->query,
        body: $this->body,
        cookies: $this->cookies,
        files: $this->files,
        routeParams: $params
    );
}
```

Prednost:

```text
Request state se ne menja nasumično
dok prolazi kroz aplikaciju
```

---

# 28. Route param vs query param

Controller:

```php
$id =
    $request->route('id');

$status =
    $request->query('status');
```

Odmah se vidi razlika:

```text
/bookings/{id}
→ resource identity

?status=confirmed
→ filter/query concern
```

To daje čitljiviji kod.

---

# 29. Server metadata

Request može imati:

```php
$request->server(
    'REMOTE_ADDR'
);
```

ili bolje specijalizovano:

```php
$request->ip();
```

Ali tu dolazi problem proxy-ja.

`REMOTE_ADDR` možda predstavlja:

```text
reverse proxy
```

ne krajnjeg client-a.

Zato real client IP resolution mora imati jasnu trusted proxy politiku.

---

# 30. Request ne sme slepo verovati `X-Forwarded-For`

Attacker može direktno poslati:

```http
X-Forwarded-For: 1.2.3.4
```

Ako naš server bez razlike veruje tom header-u:

```text
attacker bira svoj "IP"
```

To može pokvariti:

```text
rate limiting
logging
security decisions
```

Zato:

```text
forwarded headers
→ trusted samo od trusted proxy-ja
```

---

# 31. `isMethod()`

Request može ponuditi:

```php
public function isMethod(
    string $method
): bool {
    return $this->method()
        === strtoupper($method);
}
```

Poziv:

```php
$request->isMethod('POST');
```

Ali Router već treba da odluči route method.

Controller retko treba da radi:

```php
if ($request->isMethod('POST')) {
    ...
}
```

ako imamo dobar routing.

To je upravo poenta architecture-a.

---

# 32. Loš Controller bez Router discipline

Ako imaš:

```php
public function booking(
    Request $request
): Response {
    if ($request->isMethod('GET')) {
        // show
    }

    if ($request->isMethod('POST')) {
        // store
    }

    if ($request->isMethod('DELETE')) {
        // delete
    }
}
```

Controller ponovo postaje mini-router.

Bolje:

```text
GET /bookings/{id}
→ show()

POST /bookings
→ store()

POST /bookings/{id}/cancel
→ cancel()
```

Router rešava method dispatch.

---

# 33. Request object treba da bude relativno "glup"

Dobar Request zna:

```text
HTTP facts
```

Na primer:

```text
method
path
query
body
headers
cookies
files
route params
```

Ne treba da zna:

```text
da li booking može biti otkazan
da li user ima pravo na hotel
kako se računa total
```

To nisu HTTP concerns.

---

# 34. `Request` vs `FormRequest` / Request DTO

Važno razdvajanje.

Generički HTTP Request:

```text
"Šta je browser poslao?"
```

Use-case specific request/DTO:

```text
"Koje validirane podatke CreateBooking use case prihvata?"
```

Na primer:

```php
Request
```

sadrži:

```text
room_id="12"
guests="2"
check_in="2027-06-10"
check_out="2027-06-15"
```

Nakon validation/mapping:

```php
CreateBookingData
```

sadrži:

```php
roomId: 12
guests: 2
checkIn: DateTimeImmutable
checkOut: DateTimeImmutable
```

Ogromna razlika.

---

# 35. HTTP Request nije DTO

Nemoj prosleđivati generički Request duboko u Service:

```php
$bookingService->create(
    $request
);
```

Zašto?

Sada Service zavisi od:

```text
HTTP abstraction
```

i može nasumično čitati:

```text
query
headers
cookies
```

Bolje:

```php
$data =
    CreateBookingRequest::from(
        $request
    );

$bookingService->create(
    $currentUser,
    $data
);
```

Service dobija use-case data.

Ne HTTP request.

---

# 36. Controller kao boundary mapper

Controller može raditi:

```text
HTTP Request
↓
specific Request Validator / DTO
↓
Service
```

Na primer:

```php
public function store(
    Request $request
): Response {
    $data =
        $this->createBookingRequest
            ->validate($request);

    $booking =
        $this->bookingService
            ->create(
                $this->auth->user(),
                $data
            );

    return Response::redirect(
        '/bookings/'
        . $booking->id(),
        303
    );
}
```

Controller prevodi:

```text
HTTP world
→ application world
```

To je njegova prava odgovornost.

---

# 37. Request validation može imati poseban object

Na primer:

```php
final class CreateBookingRequest
{
    public function validate(
        Request $request
    ): CreateBookingData {
        ...
    }
}
```

On zna:

```text
room_id required integer
guests required 1–5
check_in valid date
check_out valid date
```

I vraća:

```php
CreateBookingData
```

To je mnogo preciznije nego da Service stalno radi:

```php
$request->input(...)
```

---

# 38. `all()` metoda

Framework-i često imaju:

```php
$request->all();
```

Možemo je imati i mi.

Ali treba biti oprezan.

Ako uradimo:

```php
$user->update(
    $request->all()
);
```

vraćamo se na:

```text
mass assignment
```

problem.

Request može omogućiti `all()` radi convenience-a.

Ali application treba da:

```text
explicitly choose allowed fields
```

---

# 39. `only()`

Možemo imati:

```php
$data =
    $request->only([
        'name',
        'city',
    ]);
```

To je bolji pattern nego:

```php
$request->all();
```

Ali i dalje:

```text
only()
≠ validation
```

Samo ograničava fields.

---

# 40. `has()` vs value semantics

Request može imati:

```php
$request->has('guests');
```

ali treba definisati šta znači:

```text
key exists?
value is not null?
value is not empty?
```

Nemoj mešati:

```text
presence
```

sa:

```text
validity
```

Na primer:

```text
guests=0
```

field jeste prisutan.

Možda nije validan.

---

# 41. `filled()`

Framework-like helper:

```php
$request->filled('name');
```

može značiti:

```text
key postoji
i nije prazan
```

To može biti praktično.

Ali opet:

```text
filled
≠ valid
```

`abc` je filled.

Možda nije validan email.

---

# 42. Normalization

Da li Request treba automatski da radi:

```php
trim(...)
```

na svakom string-u?

Ne nužno.

Zašto?

Jer:

```text
"  text  "
```

nekad može imati značenje.

Bolji princip:

```text
generic Request
→ minimalna HTTP normalization

use-case request
→ semantic normalization
```

Na primer email:

```php
$email = strtolower(
    trim(
        $request->input('email')
    )
);
```

pripada auth/registration request policy-ju.

---

# 43. Request ne treba da "sanitize everything"

Loš design:

```php
foreach ($body as $key => $value) {
    $body[$key] =
        htmlspecialchars($value);
}
```

Zašto?

Jer smo upravo pomešali:

```text
input parsing
```

sa:

```text
HTML output escaping
```

Ako kasnije podatak ide u:

```text
database
JSON
email
URL
```

HTML escaping je pogrešan context.

Security lekcija:

```text
escape late
for the actual output context
```

i ovde ponovo važi.

---

# 44. Request object ne pravi podatke "safe"

Ovo je jedna od najvažnijih rečenica lekcije.

Ako uradimo:

```php
$email =
    $request->input('email');
```

to je i dalje:

```text
untrusted email input
```

Request abstraction daje:

```text
structure
convenience
testability
```

Ne daje automatski:

```text
trust
validation
authorization
escaping
```

---

# 45. Input source collision

Pretpostavimo:

```text
POST /bookings?id=10
```

body:

```text
id=20
```

Ako imamo magični:

```php
$request->get('id');
```

šta treba da vrati?

```text
10?
20?
route ID?
```

Zato eksplicitni API:

```php
$request->route('id');

$request->query('id');

$request->input('id');
```

može biti mnogo jasniji.

---

# 46. Route param često ima najveći semantic priority

Za:

```text
POST /bookings/42/cancel
```

resource ID treba da dolazi iz:

```text
route param
```

Ne iz:

```text
body user-provided id
```

Loše:

```php
$id =
    $request->input('id');
```

Bolje:

```php
$id =
    $request->route('id');
```

jer route određuje resource nad kojim operacija radi.

# 47. Content negotiation

Request može čitati:

```http
Accept: application/json
```

i dati:

```php
$request->expectsJson();
```

To može pomoći Controller/global handler-u da odluči:

```text
HTML error page
vs
JSON error response
```

Ali za MiniStay ne moramo napraviti kompleksan content negotiation engine.

Bitno je razumeti koncept.

# 48. AJAX nije poseban security trust level

Request može imati header:

```text
X-Requested-With
```

ili browser JavaScript request.

Ali:

```text
AJAX
≠ trusted
```

Request napravljen Axios-om nije sigurniji od request-a napravljenog curl-om.

Security se ne zasniva na:

```text
"došlo je iz mog frontend-a"
```

nego na:

```text
auth
authorization
CSRF
validation
```

$request->ip();

ali implementation mora znati:

# 57. MiniStay Request skeleton

Konceptualno:

```php
final class Request
{
    public function __construct(
        private array $server,
        private array $query,
        private array $body,
        private array $cookies,
        private array $files,
        private array $routeParams = []
    ) {}

    public static function capture(): self
    {
        return new self(
            server: $_SERVER,
            query: $_GET,
            body: $_POST,
            cookies: $_COOKIE,
            files: $_FILES
        );
    }

    public function method(): string
    {
        return strtoupper(
            $this->server[
                'REQUEST_METHOD'
            ] ?? 'GET'
        );
    }

    public function path(): string
    {
        return parse_url(
            $this->server[
                'REQUEST_URI'
            ] ?? '/',
            PHP_URL_PATH
        ) ?: '/';
    }

    public function query(
        string $key,
        mixed $default = null
    ): mixed {
        return $this->query[$key]
            ?? $default;
    }

    public function input(
        string $key,
        mixed $default = null
    ): mixed {
        return $this->body[$key]
            ?? $default;
    }

    public function route(
        string $key,
        mixed $default = null
    ): mixed {
        return $this->routeParams[$key]
            ?? $default;
    }
}
```

Ovo još nije savršen production HTTP component.

Ali odlično pokazuje architecture.

# 60. Najvažnija arhitektonska granica

Request object predstavlja:

```text
HTTP world
```

Service layer treba da predstavlja:

```text
application world
```

Controller je translator između njih.

Mentalno:

```text
HTTP
↓
Request
↓
Controller
↓
DTO
↓
Service
```

Ne:

```text
HTTP Request
↓
Service
↓
Repository
↓
svuda request->input(...)
```

To bi proširilo HTTP coupling kroz celu aplikaciju.

# Najvažnije za zapamtiti

Request object:

```text
predstavlja HTTP request
kao objekat
```

On centralizuje:

```text
method
path
query
body
headers
cookies
files
route params
```

Umesto:

```php
$_GET
$_POST
$_SERVER
$_COOKIE
$_FILES
```

razbacanih kroz Controller-e.

Ali:

```text
Request
≠ validation
≠ authentication
≠ authorization
≠ sanitization
≠ escaping
```

Request data je i dalje:

```text
UNTRUSTED
```

Parsing:

```text
"Da li mogu da razumem ovaj HTTP body?"
```

Validation:

```text
"Da li je ova vrednost dozvoljena?"
```

To nisu iste stvari.

Route:

```php
$request->route('id');
```

Query:

```php
$request->query('status');
```

Body:

```php
$request->input('email');
```

Treba ih razlikovati.

HTTP Request:

```text
generic transport object
```

Use-case DTO:

```text
validated application data
```

Ne prosleđuj generički Request duboko u Service bez dobrog razloga.

Bolji flow:

```text
HTTP REQUEST
↓
REQUEST OBJECT
↓
CONTROLLER
↓
VALIDATION / DTO
↓
SERVICE
```

Request object treba da bude relativno glup:

```text
zna HTTP
ne zna Booking business
```

I najvažnija rečenica:

> **Request object ne čini input bezbednim — on samo pretvara globalni PHP HTTP state u jasnu, testabilnu i kontrolisanu granicu prema ostatku aplikacije.**
