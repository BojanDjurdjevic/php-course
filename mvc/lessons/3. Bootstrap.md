# 3. Bootstrap & Application Wiring

## 1. Šta je bootstrap

U kontekstu naše Vanilla PHP aplikacije, bootstrap je deo koji:

```text id="sgp9bv"
priprema aplikaciju
pre nego što obrada konkretnog request-a počne
```

Na primer:

```text id="fm5j7x"
autoload
config
environment
session
error handling
PDO
repositories
services
controllers
router
middleware
```

Mentalno:

```text id="5mrf15"
public/index.php
↓
BOOTSTRAP
↓
configured application
↓
handle request
```

Bootstrap odgovara na pitanje:

> Šta aplikaciji treba da bi uopšte mogla da radi?

---

## 2. Bootstrap nije isto što i request handling

Važna granica.

Bootstrap:

```text id="v3lley"
napravi BookingRepository
napravi BookingService
napravi BookingController
registruj route
```

Request handling:

```text id="j0knv1"
GET /bookings/42
↓
router match
↓
BookingController::show(42)
```

Dakle:

```text id="mml0dj"
BOOTSTRAP
→ sastavlja sistem

REQUEST HANDLING
→ koristi sastavljen sistem
```

Ovo su dve različite faze.

---

# 3. Primer bez jasnog bootstrap-a

Loše organizovan `index.php`:

```php id="1s78we"
<?php

require '../vendor/autoload.php';

Dotenv\Dotenv::createImmutable(
    dirname(__DIR__)
)->load();

$pdo = new PDO(
    $_ENV['DB_DSN'],
    $_ENV['DB_USER'],
    $_ENV['DB_PASS']
);

$users =
    new PdoUserRepository($pdo);

$bookings =
    new PdoBookingRepository($pdo);

$auth =
    new AuthService($users);

$bookingService =
    new BookingService(
        $bookings
    );

$bookingController =
    new BookingController(
        $bookingService
    );

// routing logic
// URI parsing
// method checks
// controller calls
// response sending
```

Ovo nije katastrofa za mali projekat.

Ali kako aplikacija raste, `index.php` počinje da radi previše.

---

# 4. Bolja podela

`public/index.php`:

```php id="bkshx8"
<?php

declare(strict_types=1);

require_once dirname(__DIR__)
    . '/vendor/autoload.php';

$app = require dirname(__DIR__)
    . '/bootstrap/app.php';

$response = $app->handle();

$response->send();
```

A:

```text id="zshq5g"
bootstrap/app.php
```

priprema aplikaciju.

Sada je `index.php` skoro samo:

```text id="c93ww8"
LOAD
↓
BOOT
↓
HANDLE
↓
SEND
```

---

# 5. Šta bootstrap tipično radi

Možemo ga zamisliti u fazama:

```text id="fvkj3b"
1. Load environment/config

2. Configure runtime

3. Create infrastructure

4. Create repositories

5. Create services

6. Create controllers

7. Configure middleware

8. Register routes

9. Return application/router
```

Ovo je veoma dobar mentalni redosled.

---

# 6. Load environment

Na početku:

```php id="8blgzx"
Dotenv\Dotenv::createImmutable(
    dirname(__DIR__)
)->load();
```

Sada možemo čitati:

```php id="osdkmw"
$_ENV['APP_ENV'];
$_ENV['DB_HOST'];
$_ENV['DB_NAME'];
```

Ali bootstrap ne treba da prosleđuje:

```text id="yewc4u"
ceo $_ENV
```

svakoj klasi.

Bolje je napraviti konkretne config vrednosti/objekte.

---

# 7. Config je bolji od globalnog `$_ENV`

Loše:

```php id="tuzsky"
final class Database
{
    public function connect(): PDO
    {
        return new PDO(
            $_ENV['DB_DSN'],
            $_ENV['DB_USER'],
            $_ENV['DB_PASS']
        );
    }
}
```

Sada `Database` zavisi od globalnog environment-a.

Bolje:

```php id="fc6l56"
final readonly class DatabaseConfig
{
    public function __construct(
        public string $dsn,
        public string $user,
        public string $password
    ) {}
}
```

Bootstrap:

```php id="t5ep5m"
$dbConfig =
    new DatabaseConfig(
        $_ENV['DB_DSN'],
        $_ENV['DB_USER'],
        $_ENV['DB_PASS']
    );
```

Pa:

```php id="3yvs9x"
$database =
    new Database($dbConfig);
```

Sada je dependency eksplicitna.

---

# 8. Configure runtime

Bootstrap može podesiti:

```text id="gl82rw"
error reporting
session configuration
timezone
encoding
logging
```

Na primer:

```php id="g8mgo4"
error_reporting(E_ALL);

ini_set(
    'display_errors',
    $_ENV['APP_ENV'] === 'production'
        ? '0'
        : '1'
);

ini_set(
    'log_errors',
    '1'
);
```

Ovo je application startup concern.

Ne treba Controller da odlučuje:

```text id="wyldv4"
da li display_errors treba biti uključen
```

---

# 9. Session setup

Bootstrap može napraviti:

```php id="yr5tx1"
$session = new Session(
    new SessionConfig(...)
);

$session->start();
```

Ili jednostavnije:

```php id="5fpheq"
$session = new Session();

$session->start();
```

Bitno je:

```text id="qogzyb"
session infrastructure
→ jednom centralno
```

Ne:

```text id="xnlp3z"
session_start()
u svakom Controller-u
```

---

# 10. Global error handlers

Bootstrap je prirodno mesto za:

```php id="k5j21q"
set_exception_handler(...);
set_error_handler(...);
register_shutdown_function(...);
```

Zašto?

Jer želimo da budu aktivni:

```text id="1694iq"
pre nego što application code
počne ozbiljno da obrađuje request
```

Ako ih postaviš tek u Controller-u:

```text id="u5u91v"
bootstrap/router failure
```

možda neće biti pravilno obrađen.

# 11. Infrastructure creation

Sledeće pravimo infrastructure dependencies.

Na primer:

```php id="dtaw8d"
$pdo = $database->connect();
```

Onda:

```php id="zn568y"
$logger = new Logger(...);

$mailer = new SmtpMailer(...);

$storage = new LocalStorage(...);
```

Infrastructure znači:

```text id="gz5tt5"
database
filesystem
email
external services
cache
```

To su konkretne tehničke implementations.

# 12. Repositories

Na infrastructure-u gradimo repositories:

```php id="ud35gn"
$userRepository =
    new PdoUserRepository($pdo);

$bookingRepository =
    new PdoBookingRepository($pdo);

$roomRepository =
    new PdoRoomRepository($pdo);

$inventoryRepository =
    new PdoInventoryRepository($pdo);
```

Ovde se vidi dependency direction:

```text id="f1f3ra"
PDO
↓
PdoRepository
```

Repository zavisi od PDO.

Service ne mora.

---

# 13. Services

Zatim sastavljamo application services:

```php id="x15k43"
$authService =
    new AuthService(
        $userRepository,
        $session
    );

$bookingService =
    new BookingService(
        $bookingRepository,
        $inventoryRepository
    );
```

Service dobija ono što mu treba kroz constructor.

Ne radi:

```php id="uh48dn"
new PdoBookingRepository(...)
```

unutar sebe.

To je veoma važna granica.

---

# 14. Controllers

Sledeće:

```php id="uvcfhm"
$bookingController =
    new BookingController(
        $bookingService,
        $authService,
        $view
    );
```

Controller dobija svoje dependencies.

Ne treba sam da ih pravi.

Loše:

```php id="q8mpmo"
final class BookingController
{
    public function __construct()
    {
        $pdo = new PDO(...);

        $this->service =
            new BookingService(
                new PdoBookingRepository(
                    $pdo
                )
            );
    }
}
```

Zašto je loše?

Jer Controller sada odlučuje:

```text id="1b04q1"
koju repository implementaciju koristimo
kako se pravi PDO
kako se gradi service
```

To nije njegova odgovornost.

---

# 15. Composition Root

Mesto gde sastavljamo object graph zovemo:

```text id="lv8nyj"
Composition Root
```

To je mesto gde je `new` potpuno očekivan.

Na primer:

```php id="v9y0yq"
$pdo = new PDO(...);

$repository =
    new PdoBookingRepository($pdo);

$service =
    new BookingService(
        $repository
    );

$controller =
    new BookingController(
        $service
    );
```

Mentalno:

```text id="bljln8"
Composition Root
→ zna konkretne implementations
```

Ostatak aplikacije uglavnom radi sa već dobijenim dependencies.

---

# 16. Gde sme `new`?

Važno: `new` nije loš.

Problem nije:

```text id="w55poe"
"nikad ne koristi new"
```

Problem je:

```text id="4vy8fp"
gde odlučuješ kako se dependency pravi
```

Dobro:

```text id="w4motf"
bootstrap/app.php
→ new PDO
→ new Repository
→ new Service
→ new Controller
```

Sumnjivo:

```text id="rwi05u"
BookingController
→ new PDO
```

ili:

```text id="h3g5j7"
BookingService
→ new PdoBookingRepository
```

Jer tada high-level klasa sama bira low-level implementation.

# 18. Application wiring

`wiring` znači:

```text id="jt2uht"
povezivanje objekata i njihovih zavisnosti
```

Na primer:

```php id="0g86uk"
$controller =
    new BookingController(
        bookingService:
            $bookingService,
        auth:
            $authService,
        view:
            $view
    );
```

To nije business logic.

To je:

```text id="c3mlqg"
application configuration
```

---

# 19. Router registration pripada wiring-u

Kad imamo Controller:

```php id="d2xxma"
$bookingController =
    new BookingController(...);
```

registrujemo:

```php id="6oc07t"
$router->get(
    '/bookings',
    [$bookingController, 'index']
);

$router->get(
    '/bookings/{id}',
    [$bookingController, 'show']
);

$router->post(
    '/bookings',
    [$bookingController, 'store']
);
```

Bootstrap zna:

```text id="d96wu9"
koji route
→ koji handler
```

Ali sam Controller ne zna:

```text id="aypvyl"
na kom URL-u je registrovan
```

To je dobro razdvajanje.

---

# 20. Controller ne treba da zna route registration

Loše:

```php id="yld2ky"
final class BookingController

    public function route(): string
    {
        return '/bookings';
    }
}
```

nije nužno uvek pogrešno, ali vezuje Controller za routing konfiguraciju.

Bolji mentalni model:

```text id="0xrgcm"

→ zna route

Controller
→ zna action
```

# 24. Container — gde se uklapa

Kasnije framework može imati:

```text id="0t37wg"
Dependency Injection Container
```

koji automatski zna:

```text id="8d7jre"
BookingController
needs BookingService

BookingService
needs BookingRepository
```

Laravel Service Container upravo to radi.

Umesto:

```php id="vs4cvc"
$repository =
    new PdoBookingRepository($pdo);

$service =
    new BookingService($repository);

    new BookingController($service);
```

framework može resolve-ovati dependency graph.

Ali mentalno se i dalje dešava isto:

```text id="nryidc"

↓

↓
build object graph
```

# 25. Zašto prvo ručno wiring

Ako odmah koristimo container:


može delovati kao magija.

Ručno wiring pokazuje:

```text id="sg3ta2"

```

Zato u Vanilla PHP kursu prvo želimo eksplicitno:

# 26. Bootstrap vs Service Locator

Loš pattern:

```php id="6l1zdi"
final class Container
{
    public static function get(
        string $name
    ): mixed {
        ...
    }
}
```

pa svuda:

```php id="k6gkrz"
$repo =
    Container::get(
        'booking_repository'
    );
```

Sada dependencies više nisu eksplicitne.

BookingService izgleda kao da nema dependencies:

```php id="b5u8cx"
new BookingService();
```

ali unutra secretly uzima repository.

To otežava:

```text id="wq0w8z"
razumevanje
testiranje
refactoring
```

To je Service Locator stil.

Constructor injection je jasniji.

# 27. Constructor Injection

Dobar:

```php id="hv7jxj"

{
    public function __construct(
        private BookingRepository
            $bookings,
        private InventoryRepository
            $inventory
    ) {}
}
```

Odmah vidimo:

```text id="y5zu8d"
BookingService zahteva:
- BookingRepository
- InventoryRepository
```

Bootstrap mora da mu ih obezbedi.

Dependency contract je eksplicitan.

# 33. Application object

Možemo imati jednostavan:

```php id="9a2feq"
final class Application
{
    public function __construct(
        private Router $router
    ) {}

    public function handle(
        Request $request
    ): Response {
        return $this->router
            ->dispatch($request);
    }
}
```

Bootstrap:

```php id="ku5nvx"
return new Application(
    $router
);
```

Front Controller:

```php id="ytmf1c"
$app = require ...;

$request =
    Request::capture();

$response =
    $app->handle($request);

$response->send();
```

Sada je lifecycle vrlo jasan.

---

# 34. Šta se pravi jednom po PHP request-u?

U klasičnom PHP-FPM modelu svaki HTTP request izvršava application bootstrap za taj request.

Mentalno:

```text id="n2kz7e"
HTTP request A
→ bootstrap
→ handle
→ finish

HTTP request B
→ bootstrap
→ handle
→ finish
```

To nije isto kao long-running Node process koji drži isti application graph zauvek.

Važno kada razmišljaš o:

```text id="mgw014"
static state
singletons
request-scoped data
```

Laravel i drugi framework-i mogu imati dodatne optimizacije i long-running runtime modele, ali klasični PHP lifecycle je request-oriented.

# 36. Sharing dependencies

Možemo imati:

# 37. Transaction boundary i shared PDO

Pretpostavimo BookingService koristi:

```text id="3xqp5t"
BookingRepository
InventoryRepository
```

Ako oba koriste isti PDO connection:

```text id="mhjjcc"
PDO
├── BookingRepository
└── InventoryRepository
```

onda:

```php id="b8zwzt"
$pdo->beginTransaction();
```

može pokriti operacije oba repository-ja.

Ako svaki repository sam napravi svoj PDO:

```text id="rpaj94"
BookingRepository
→ PDO A

→ PDO B
```

jedna DB transaction više ne obuhvata automatski oba.

Ovo je odličan primer zašto wiring nije samo kozmetika.

Bootstrap pravi:

```text id="qedtlc"

```

Ne treba da:

```text id="fanlh4"

```

# 39. MiniStay bootstrap — konceptualna verzija

Na kraju bi mogao izgledati približno:

```php id="7b7qzx"
<?php

declare(strict_types=1);

use App\Application;
use App\Database\Database;
use App\Http\Router;

Dotenv\Dotenv::createImmutable(
    dirname(__DIR__)
)->load();

// Runtime config
$session = new Session(...);
$session->start();

$logger = new Logger(...);

register_error_handlers(
    $logger
);

// Infrastructure
$database =
    new Database(...);

$pdo =
    $database->connect();

$view =
    new ViewRenderer(
        dirname(__DIR__)
        . '/views'
    );

// Repositories
$users =
    new PdoUserRepository($pdo);

$rooms =
    new PdoRoomRepository($pdo);

$bookings =
    new PdoBookingRepository($pdo);

$inventory =
    new PdoInventoryRepository($pdo);

// Services
$auth =
    new AuthService(
        $users,
        $session
    );

$bookingService =
    new BookingService(
        $bookings,
        $inventory
    );

// Controllers
$bookingController =
    new BookingController(
        $bookingService,
        $auth,
        $view
    );

// Router
$router =
    new Router();

$router->get(
    '/bookings',
    [$bookingController, 'index']
);

$router->post(
    '/bookings',
    [$bookingController, 'store']
);

return new Application(
    $router
);
```

Ne mora finalna verzija izgledati baš tako.

Ali architecture mentalno već postoji.

# 40. Laravel paralela

U Laravel-u ne pišeš ručno:

```php id="gc4svp"
new BookingService(
    new PdoBookingRepository(...)
);
```

na svakom mestu.

Service Container može da resolve-uje dependencies.

Service Provider može definisati binding:

```php id="5dvlda"
$this->app->bind(
    BookingRepository::class,
    EloquentBookingRepository::class
);
```

Controller:

```php id="66bdvc"
public function __construct(
    BookingService $service
) {
    $this->service = $service;
}
```

Laravel container vidi:

```text id="brblkt"
BookingController
needs BookingService
↓
BookingService
needs BookingRepository
↓
binding says
EloquentBookingRepository
```

i sastavlja graph.

To je framework automatizacija istog procesa koji mi ručno radimo u bootstrap-u.

```text id="j3j675"
manual composition root

container automation
```

Container nije nešto konceptualno potpuno drugo.

On automatizuje:

```text id="g1pjv8"
object construction
dependency resolution
lifecycle management
bindings
```

# 42. Bootstrap vs Laravel Service Provider

U našoj Vanilla aplikaciji:

```text id="j7c95x"
bootstrap/app.php
```

će verovatno imati većinu wiring-a.

Laravel razlaže startup/configuration kroz:

```text id="frfrtu"
bootstrap
service container
service providers
configuration
route files
```

ali princip je isti:

```text id="x6zqrn"
application mora negde
da odluči koje implementations koristi
i kako ih povezuje
```

# Najvažnije za zapamtiti

Bootstrap:

```text id="1nczua"
priprema aplikaciju
```

Request handling:

```text id="k2omxu"
koristi pripremljenu aplikaciju
```

Bootstrap tipično radi:

```text id="18pvbl"
config
runtime setup
session
error handlers
PDO
repositories
services
controllers
middleware
routes
```

`public/index.php` treba da ostane mali:

```text id="1w1uxa"
BOOT
↓
HANDLE
↓
SEND
```

Mesto gde sastavljamo dependency graph zove se:

```text id="nw6mmp"
Composition Root
```

Tu je normalno videti:

```php id="nqx814"
new PDO(...)
new PdoRepository(...)
new Service(...)
new Controller(...)
```

Controller ne treba da radi:

```php id="14967y"
new PDO(...)
```

Service ne treba da radi:

```php id="jj9n10"
new PdoRepository(...)
```

Dependencies su bolje:

```text id="t0gxg3"
eksplicitno injectovane
```

Constructor injection:

```php id="hru1w3"
__construct(
    BookingRepository $bookings
)
```

odmah pokazuje šta klasi treba.

Wiring:

```text id="zyl6x5"
povezuje implementations
```

Business logic:

```text id="l078hn"
odlučuje ponašanje aplikacije
```

To nisu ista stvar.

Veoma važna mapa:

```text id="dlke6t"
PDO
↓
Repository
↓
Service
↓
Controller
↓
Router
```

Bootstrap gradi mapu.

Request je koristi.

Shared PDO može biti važan zbog:

```text id="7xfnxu"
jedne transaction boundary
preko više repositories
```

Laravel Service Container:

```text id="ht9tdk"
automatizuje object wiring
koje mi ovde radimo ručno
```

Ako samo jednu rečenicu zapamtiš:

> **Bootstrap ne izvršava use case — bootstrap sastavlja objekte koji će use case kasnije izvršiti.**
