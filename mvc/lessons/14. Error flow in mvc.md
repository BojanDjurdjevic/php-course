# 14. Error Flow kroz MVC

## 1. Greška može nastati u bilo kom sloju

U jednom request-u problem može nastati u:

```text
Router-u
Controller-u
Service-u
Entity-ju
Repository-ju
PDO-u
View-u
Middleware-u
```

Na primer:

```text
GET /bookings/999
```

može završiti kao 404 zato što:

```text
route ne postoji
```

ili zato što:

```text
route postoji,
ali Booking #999 ne postoji
```

Isti finalni HTTP status.

Potpuno drugačiji uzrok.

---

# 2. Error flow nije samo "catch exception"

Prava pitanja su:

```text
Gde je problem nastao?

Ko razume njegovu semantiku?

Ko sme da ga prevede?

Ko treba da ga loguje?

Ko odlučuje HTTP status?

Šta sme user da vidi?
```

To je error architecture.

---

# 3. Osnovni success flow

Normalan request:

```text
Request
↓
Router
↓
Middleware
↓
Controller
↓
Service
↓
Repository
↓
Database

↑
Result
↑
Service
↑
Controller
↑
Response
↑
Middleware
↑
Browser
```

Kod failure-a umesto normalnog return-a možemo dobiti:

```text
Throwable
```

koji propagira naviše.

---

# 4. Exception propagation kroz slojeve

Pretpostavimo Repository baci:

```php
throw new PersistenceException(
    'Could not load booking.',
    previous: $e
);
```

Ako Service nema razlog da ga hvata:

```text
Repository
↓ throws
Service
↓ propagates
Controller
↓ propagates
Middleware
↓ propagates
Error Handler
```

Ne moramo imati:

```php
try {
    ...
} catch (...) {
    throw ...;
}
```

u svakom sloju.

To bi bilo samo noise.

---

# 5. Pravilo: catch samo kada znaš šta ćeš uraditi

Dobro pitanje:

> Da li ovaj sloj može smisleno da obradi exception?

Ako ne:

```text
ne hvataj ga
```

Neka propagira.

Hvataj kada želiš da:

```text
recovery

translate exception

add meaningful context

rollback transaction

map to Response

perform guaranteed cleanup
```

---

# 6. Routing 404

Request:

```text
GET /flying-elephants
```

Router proveri routes:

```text
nema match-a
```

Ovo nije nužno exception.

Router može jednostavno vratiti:

```php
return Response::html(
    $view->render(
        'errors/404'
    ),
    404
);
```

ili baciti:

```php
throw new RouteNotFoundException();
```

pa centralni error layer pravi Response.

Oba design-a su moguća.

---

# 7. Routing 404 vs Resource 404

### Routing 404

```text
GET /abcxyz
```

nema route-a.

### Resource 404

```text
GET /bookings/999
```

route postoji:

```text
GET /bookings/{id}
```

ali:

```text
Booking #999 ne postoji
```

U oba slučaja client može dobiti:

```text
404 Not Found
```

Ali architecture mora razlikovati razlog.

---

# 8. Resource not found

Service može:

```php
$booking =
    $this->bookings
        ->findById($id);

if ($booking === null) {
    throw new BookingNotFoundException(
        $id
    );
}
```

Service govori application jezikom:

```text
Booking ne postoji
```

Ne:

```text
HTTP 404
```

---

# 9. Domain/Application exception nije HTTP exception

`BookingNotFoundException` zna:

```text
Booking nije pronađen
```

Ne mora da zna:

```text
status 404
HTML error page
JSON response
```

HTTP layer kasnije odlučuje:

```text
BookingNotFoundException
→ 404
```

To održava Service reusable.

---

# 10. Controller ne mora svaki put da catch-uje NotFound

Loše ponavljanje:

```php
try {
    $booking =
        $service->find($id);
} catch (
    BookingNotFoundException $e
) {
    return Response::html(
        'Not found',
        404
    );
}
```

u svakom Controller-u.

Ako je mapping uvek isti:

```text
BookingNotFoundException
→ 404
```

centralni error handler je bolje mesto.

---

# 11. Kada Controller ipak sme da catch-uje expected exception

Na primer booking cancellation:

```php
try {
    $this->bookingService
        ->cancel(
            $user,
            $id
        );
} catch (
    BookingCannotBeCancelledException $e
) {
    $this->session->flash(
        'error',
        'Booking cannot be cancelled.'
    );

    return Response::redirect(
        '/bookings/' . $id,
        303
    );
}
```

Ovo ima smisla jer Controller bira:

```text
specific presentation/navigation flow
```

To nije generički 500 handling.

---

# 12. Expected vs Unexpected failure

Expected failure:

```text
resource not found
validation failure
not authorized
booking unavailable
booking cannot be cancelled
duplicate email
```

Unexpected failure:

```text
PDO server unavailable
TypeError
undefined invariant bug
template file missing
programming error
```

Error architecture treba da ih tretira različito.

---

# 13. Validation errors

Validation failure može biti predstavljena kao:

```php
throw new ValidationException(
    $errors
);
```

ili kao explicit result.

Za web flow:

```text
ValidationException
↓
flash errors
↓
303 redirect
```

Za API:

```text
ValidationException
↓
422 JSON
```

Dakle:

```text
same application failure
→ different HTTP representation
```

---

# 14. Authorization failure

Policy može baciti:

```php
throw new AuthorizationException();
```

HTTP mapping:

```text
403 Forbidden
```

ili, ako želimo da sakrijemo existence resource-a:

```text
404
```

To je HTTP/security presentation odluka.

---

# 15. Authentication failure

Ako middleware vidi:

```text
nema authenticated user-a
```

web može:

```text
303 → /login
```

API može:

```text
401 Unauthorized
```

Isti security fact.

Druga HTTP presentation politika.

---

# 16. Business conflict

Na primer:

```php
throw new RoomUnavailableException();
```

To nije:

```text
500
```

To je očekivani business failure.

HTTP representation može biti:

```text
409 Conflict
```

ili:

```text
422
```

ili u server-rendered app-u:

```text
flash + redirect
```

Bitno:

```text
ne tretirati expected domain failure
kao server crash
```

---

# 17. Repository-level failure

Repository može naići na:

```php
PDOException
```

Na primer:

```text
connection refused
deadlock
unique constraint
invalid SQL
```

Nisu svi isti.

Repository/application layer treba da razlikuje:

```text
known persistence condition
vs
unexpected infrastructure failure
```

---

# 18. Known DB constraint

Registration:

```text
UNIQUE(email)
```

PDO baci constraint violation.

Repository može prevesti:

```text
PDOException
↓
EmailAlreadyRegisteredException
```

To je korisna translation jer DB detalj postaje application semantics.

---

# 19. Unknown PDO failure

Na primer:

```text
database unavailable
```

Ako nemamo meaningful recovery:

```text
PDOException
```

ili `PersistenceException` propagira do global error handler-a.

Finalno:

```text
500 Internal Server Error
```

Client ne treba da vidi:

```text
SQLSTATE
DSN
SQL query
file path
stack trace
```

---

# 20. Exception chaining

Ako Repository radi:

```php
try {
    ...
} catch (PDOException $e) {
    throw new PersistenceException(
        'Could not save booking.',
        previous: $e
    );
}
```

dobijamo:

```text
application context
+
original technical cause
```

Logging može videti chain.

User ne mora.

---

# 21. Transaction failure

Service:

```php
$this->pdo
    ->beginTransaction();

try {
    // operations

    $this->pdo
        ->commit();
} catch (Throwable $e) {
    if (
        $this->pdo
            ->inTransaction()
    ) {
        $this->pdo
            ->rollBack();
    }

    throw $e;
}
```

Ovde Service hvata exception sa vrlo dobrim razlogom:

```text
mora rollback
```

Ali nakon rollback-a:

```text
rethrow
```

ako ga ne zna dalje obraditi.

---

# 22. Catch radi cleanup-a

Ovo je dobar primer:

```text
catch
→ cleanup
→ rethrow
```

Ne zato da "pojemo" exception.

Nego da održimo transaction invariant.

---

# 23. `finally` i cleanup

Ako imamo resource cleanup:

```php
try {
    ...
} finally {
    $resource->close();
}
```

`finally` radi bez obzira da li je:

```text
success
ili
exception
```

Ali za PDO transaction obično moraš znati:

```text
da li commit ili rollback
```

pa `catch` često ima veću ulogu.

---

# 24. Deadlock

DB može prijaviti deadlock.

To je infrastructure/concurrency failure.

U nekim sistemima možemo:

```text
retry transaction
```

ograničen broj puta.

Ali retry treba da bude nameran.

Ne:

```text
catch Throwable
→ retry 100 puta
```

---

# 25. Retry samo za retryable failures

Primeri koji možda jesu retryable:

```text
deadlock
temporary network failure
transient external service failure
```

Primeri koji nisu:

```text
validation error
authorization failure
invalid SQL syntax
programming bug
```

Error type treba da vodi ponašanje.

---

# 26. Entity exception

Booking:

```php
public function cancel(): void
{
    if (!$this->canCancel()) {
        throw new BookingCannotBeCancelledException();
    }

    ...
}
```

Entity govori business jezikom.

Ne zna:

```text
flash
redirect
status code
```

To je dobra domain granica.

---

# 27. View failure

View Renderer može baciti:

```php
ViewNotFoundException
```

ako developer napiše:

```php
$view->render(
    'bookings/shwo'
);
```

To je uglavnom:

```text
programming/configuration error
```

ne user 404.

Finalni response:

```text
500
```

Ne:

```text
404
```

samo zato što "file nije pronađen".

HTTP semantics zavise od application meaning-a, ne od low-level exception wording-a.

---

# 28. Ovo je veoma važna nijansa

```text
BookingNotFoundException
→ 404

ViewNotFoundException
→ 500
```

Iako oba sadrže ideju:

```text
not found
```

semantika je potpuno različita.

Zato ne mapiramo exception na HTTP samo po nazivu/string poruci.

---

# 29. Invalid route parameter

Request:

```text
GET /bookings/abc
```

Ako route ima numeric constraint:

```text
nema match-a
→ routing 404
```

Ako route matchuje bilo koji segment:

```text
{id} = abc
```

pa validator kaže:

```text
invalid ID format
```

možemo vratiti:

```text
404
```

ili `400`, zavisno od routing policy-ja.

Najvažnije je:

```text
consistent behavior
```

---

# 30. 400 Bad Request

`400` ima smisla kada HTTP request ne možemo smisleno obraditi zbog malformed request-a.

Na primer:

```text
malformed JSON
invalid required transport syntax
```

Ne mora svaka validation greška biti 400.

---

# 31. 422

Za syntactically valid request sa semantički nevalidnim input-om često:

```text
422 Unprocessable Content
```

Na primer:

```text
email invalid
check_out before check_in
```

posebno u API-ju.

Server-rendered HTML može koristiti drugačiji flow.

---

# 32. 409 Conflict

Na primer:

```text
room više nije dostupna
version conflict
duplicate state transition
```

može imati smisla kao:

```text
409 Conflict
```

Ali status mapping nije business layer responsibility.

---

# 33. 500

`500 Internal Server Error` znači:

```text
server nije uspeo da obradi request
zbog neočekivanog problema
```

Ne znači:

```text
"uhvatili smo exception"
```

Expected domain failure obično nije 500.

# 34. Global exception handler

Možemo imati:

```php
final class ExceptionHandler
{
    public function toResponse(
        Throwable $e,
        Request $request
    ): Response {
        ...
    }
}
```

Njegov posao:

```text
Throwable
+
HTTP context
↓
safe Response
```

---

# 35. Exception mapping

Na primer:

```php
return match (true) {
    $e instanceof BookingNotFoundException
        => $this->notFound(),

    $e instanceof AuthorizationException
        => $this->forbidden(),

    $e instanceof ValidationException
        => $this->validation(
            $e
        ),

    default
        => $this->internalServerError(
            $e
        ),
};
```

To je centralna HTTP translation granica.

Loše:

```php

```

Jer exception message može sadržati:

```text

internal class names

sensitive details
```

User-facing message treba da bude:

```text

```


Log:

Razdvajamo:

# 38. Development response

# 39. Error handler i logging

Global handler može:

```php
$this->logger->error(
    'Unhandled exception',
    [
        'exception' => $e,
        'request_id' =>
            $request->attribute(
                'request_id'
            ),
    ]
);
```

Ali ne treba logovati:

```text
password
session ID
CSRF token
Authorization header
reset token
```

---

# 40. Log once

Ako Repository loguje:

```text
PDO error
```

Service opet loguje:

```text
Service failed
```

Controller opet:

```text
Controller failed
```

Global handler opet:

```text
Unhandled exception
```

dobijamo četiri skoro ista log entry-ja.

To je noise.

Bolje:

```text
log tamo gde postoji meaningful context
ili centralno finalno
```

Ne automatski na svakom catch-u.

---

# 41. Exception translation bez duplog logovanja

Repository može:

```php
catch (PDOException $e) {
    throw new PersistenceException(
        'Could not save booking.',
        previous: $e
    );
}
```

bez logovanja.

Global handler loguje finalni chain jednom.

To je često mnogo čistije.

---

# 42. Error handling middleware

Možemo imati outer middleware:

```php
final class ErrorHandlingMiddleware
    implements Middleware
{
    public function __construct(
        private ExceptionHandler
            $handler
    ) {}

    public function process(
        Request $request,
        callable $next
    ): Response {
        try {
            return $next(
                $request
            );
        } catch (Throwable $e) {
            return $this->handler
                ->toResponse(
                    $e,
                    $request
                );
        }
    }
}
```

Sada ceo application pipeline garantuje:

```text
Request
→ Response
```

čak i kada unutra nastane exception.

---

# 43. Zašto Error middleware treba da bude spolja

Stack:

```text
ErrorHandler
↓
Logging
↓
Auth
↓
CSRF
↓
Controller
```

Ako bilo šta unutra pukne:

```text
ErrorHandler
```

ga može uhvatiti.

Ako je ErrorHandler unutra iza nekog middleware-a koji sam pukne:

```text
taj exception mu nikad ne stigne
```

Zato je često outermost ili skoro outermost.

---

# 44. Logging vs Error middleware order

Dve opcije.

### Error spolja

```text
Error
↓
Logging
↓
Application
```

Ako Logging pukne, Error ga hvata.

### Logging spolja

```text
Logging
↓
Error
↓
Application
```

Logging može videti finalni 500 Response.

Oba imaju tradeoff.

Možemo čak razdvojiti:

```text
request logging
exception logging
```

Nema jednog univerzalnog stack-a.

---

# 45. PHP-level global handler

I pored middleware-a možemo imati:

```php
set_exception_handler(...);
```

kao poslednju zaštitu.

Zašto?

Exception može nastati:

```text
pre middleware pipeline-a
tokom bootstrapa
tokom Router setup-a
```

Tada application error middleware možda još nije aktivan.

---

# 46. Dva nivoa zaštite

Mentalno:

```text
PHP global exception handler
→ last-resort safety net

Application Error Middleware
→ normal MVC exception-to-response flow
```

To nije nepotrebno dupliranje ako roles ostanu jasne.

# 47. Bootstrap failure

Na primer:

```text
.env invalid

DB config missing

container wiring bug
```

može nastati pre nego što imamo kompletan:

```text
Application
Router
Middleware
```

Zato Front Controller/bootstrap treba imati minimalnu final safety strategiju.

---

# 48. Fatal errors

PHP `Error` takođe implementira:

```text
Throwable
```

na primer:

```text
TypeError
ArgumentCountError
```

Global exception/error architecture treba da razmišlja u terminima:

```php
Throwable
```

ne samo:

```php
Exception
```

---

# 49. Error handler ne znači da treba nastaviti posle programming bug-a

Ako imamo:

```text
TypeError
```

ne treba:

```text
"catch pa nastavi kao da je sve u redu"
```

Obično:

```text
log
500 response
terminate request normally
```

Programmer bug nije recoverable business condition.

---

# 50. Middleware unwind kod exception-a

Normalno:

```text
A before
↓
B before
↓
Controller
↓
B after
↓
A after
```

Ako Controller baci exception i niko unutra ga ne uhvati:

```text
A before
↓
B before
↓
Controller throws
↑
B interrupted
↑
A interrupted
```

Kod posle `$next()` se neće izvršiti osim ako koristimo:

```text
catch
ili
finally
```

---

# 51. `finally` middleware

Timing:

```php
$start =
    hrtime(true);

try {
    return $next(
        $request
    );
} finally {
    $duration =
        hrtime(true)
        - $start;

    $this->metrics
        ->record($duration);
}
```

Metrics se beleži i kada request fail-uje.

---

# 52. Middleware koji želi finalni Response

Ako ErrorHandlingMiddleware pretvori exception u 500 Response, middleware spolja može i dalje dobiti:

```text
normalan Response object
```

Na primer:

```text
Logging
↓
ErrorHandler
↓
Controller throws
↓
ErrorHandler returns 500
↓
Logging sees status=500
```

To je elegantan pipeline design.

# 58. Concurrency conflict flow

Optimistic locking:

```text
UPDATE ... WHERE version = expected
↓
affected rows = 0
↓
ConcurrentModificationException
```

Service može:

```text
retry
```

ako je bezbedno.

Ili propagirati:

```text
ConflictException
```

HTTP:

```text
409
```

To je odličan primer translation kroz slojeve.

# 59. Pessimistic locking failure

Ako transaction:

```text

```

i dobije timeout/deadlock:

```text

```

Repository/infrastructure prepoznaje tehnički failure.

Service može imati retry policy.

Ako nema:

```text
500 / 503
```

zavisno od vrste problema i application policy-ja.

# 60. `503 Service Unavailable`

Ako zavisni sistem privremeno nije dostupan:

```text
DB maintenance

```

nekad `503` preciznije opisuje situaciju nego `500`.

Ali nemoj automatski mapirati svaki DB exception na 503.

Treba razumeti uzrok.

# 75. Error flow i idempotency


# 84. Error mapping table

Mentalno:

| Failure | Layer gde nastaje | HTTP rezultat |
|---|---|---|
| Route ne postoji | Router | 404 |
| Booking ne postoji | Service/application | 404 |
| Invalid form input | Validator | 422 ili flash + 303 |
| Nije authenticated | Middleware | 401 ili login redirect |

| Programming bug | bilo gde | 500 |
| Missing internal View | View Renderer | 500 |

Ovo je vrlo koristan mentalni pregled.

# 85. MiniStay centralni ExceptionHandler

Konceptualno:

```php
final class ExceptionHandler
{
    public function __construct(
        private ViewRenderer $view,
        private Logger $logger,
        private bool $debug
    ) {}

    public function toResponse(
        Throwable $e,
        Request $request
    ): Response {
        if (
            $e instanceof
            BookingNotFoundException
        ) {
            return $this->errorPage(
                404,
                'Booking not found.'
            );
        }

        if (
            $e instanceof
            AuthorizationException
        ) {
            return $this->errorPage(
                403,
                'Forbidden.'
            );
        }

        $this->logger->error(
            'Unhandled exception',
            [
                'exception' => $e,
            ]
        );

        return $this->errorPage(
            500,
            $this->debug
                ? $e->getMessage()
                : 'Internal Server Error'
        );
    }
}
```

Final implementation možemo dodatno poboljšati.

# Najvažnije za zapamtiti

Exception može nastati bilo gde:

```text
Router
Controller
Service
Entity
Repository
PDO
View
Middleware
```

Ali ne treba svaki sloj da ga catch-uje.

Pravilo:

```text
CATCH
samo ako možeš da:

recover

translate

add useful context

rollback/cleanup

map to Response
```

Inače:

```text
propagate
```

Routing 404:

```text
route ne postoji
```

Resource 404:

```text
route postoji
resource ne postoji
```

Isti status.

Druga semantika.

Domain/Application exceptions:

```text
ne treba da znaju HTTP status
```

Na primer:

```text
BookingNotFoundException
→ HTTP layer mapira u 404
```

Repository:

```text
null
```

može značiti:

```text
normalno nije pronađeno
```

Ali:

```text
PDOException
```

nije isto što i null.

Transaction Service catch:

```text
rollback
↓
rethrow
```

je dobar catch jer sloj zna šta mora da očisti.

Expected failure:

```text
validation
authorization
business conflict
not found
```

uglavnom nije 500.

Unexpected failure:

```text
programming bug
DB outage
internal rendering failure
```

uglavnom završava kao:

```text
500
```

Production user ne treba da vidi:

```text
stack trace
SQL
filesystem path
secrets
raw internal exception
```

Log i user response imaju različitu publiku.

Error middleware:

```text
try
↓
$next($request)
↓
catch Throwable
↓
ExceptionHandler
↓
Response
```

može centralizovati MVC exception mapping.

PHP global exception handler ostaje:

```text
last-resort safety net
```

posebno za failure pre middleware pipeline-a.

Ključna error mapa:

```text
LOW LEVEL FAILURE
↓
optional translation
↓
APPLICATION SEMANTICS
↓
HTTP ERROR MAPPING
↓
SAFE RESPONSE
```

I najvažnija rečenica:

> **Dobar error flow ne znači da hvataš exception što ranije — znači da ga puštaš do najbližeg sloja koji zaista razume šta sa njim treba uraditi.**
