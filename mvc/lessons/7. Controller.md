# 7. Controllers — Šta Controller sme, a šta ne sme

## 1. Controller je HTTP koordinator

Najkraća dobra definicija:

> Controller prima HTTP request, koordinira odgovarajući use case i vraća HTTP response.

Mentalno:

```text
Request
↓
Controller
↓
Application / Service
↓
Controller
↓
Response
```

Controller je granica između:

```text
HTTP sveta
```

i:

```text
application sveta
```

---

# 2. Controller ne treba da bude "glavni mozak"

Loš Controller:

```php
public function store(
    Request $request
): Response {
    $roomId =
        (int) $request->input(
            'room_id'
        );

    $checkIn =
        new DateTimeImmutable(
            $request->input(
                'check_in'
            )
        );

    $checkOut =
        new DateTimeImmutable(
            $request->input(
                'check_out'
            )
        );

    $stmt =
        $this->pdo->prepare(
            'SELECT *
             FROM rooms
             WHERE id = :id'
        );

    $stmt->execute([
        'id' => $roomId,
    ]);

    $room = $stmt->fetch();

    // availability
    // calculate nights
    // calculate total
    // transaction
    // insert booking
    // update inventory
    // send email

    return Response::redirect(
        '/bookings',
        303
    );
}
```

Ovo je praktično stari proceduralni `booking.php`, samo upakovan u class.

MVC nije rešen samo zato što smo napisali:

```php
class BookingController
```

---

# 3. Šta Controller treba da radi

Dobar Controller obično radi nekoliko stvari:

```text
1. Primi Request

2. Uzme route/input podatke

3. Pozove validation/request mapper

4. Uzme current user-a

5. Pozove authorization ako treba

6. Pozove application service/use case

7. Pretvori rezultat u Response
```

Na primer:

```php
public function store(
    Request $request
): Response {
    $data =
        $this->createBookingRequest
            ->validate($request);

    $user =
        $this->auth->user();

    $booking =
        $this->bookingService
            ->create(
                $user,
                $data
            );

    return Response::redirect(
        '/bookings/'
        . $booking->id(),
        303
    );
}
```

Controller ovde koordinira.

Ne implementira booking sistem.

---

# 4. Thin Controller

Često ćeš čuti:

```text
Keep controllers thin.
```

To ne znači:

```text
Controller mora imati 2 linije
```

Znači:

```text
business logic
ne treba da živi u Controller-u
```

Controller sme da ima:

```text
HTTP orchestration
```

To je njegova prava odgovornost.

---

# 5. Controller sme da čita HTTP podatke

Na primer:

```php
$id =
    $request->route('id');

$status =
    $request->query(
        'status'
    );
```

To je potpuno normalno.

Controller je HTTP sloj.

Ne mora svaki:

```php
$request->route(...)
```

odmah da bude izbačen u neku novu klasu.

Overengineering nije cilj.

---

# 6. Controller sme da bira Response

Na primer:

```php
return Response::redirect(
    '/login',
    303
);
```

ili:

```php
return Response::html(
    $html
);
```

ili:

```php
return Response::json(
    $data,
    201
);
```

To jeste Controller concern.

Zašto?

Jer Controller prevodi application result u:

```text
HTTP representation
```

---

# 7. Controller sme da bira View

Na primer:

```php
return Response::html(
    $this->view->render(
        'bookings/index',
        [
            'bookings' =>
                $bookings,
        ]
    )
);
```

To je presentation orchestration.

Controller zna:

```text
koji view treba prikazati
```

View zna:

```text
kako HTML izgleda
```

---

# 8. Controller ne treba da piše SQL

Loše:

```php
$stmt =
    $this->pdo->prepare(
        'SELECT * FROM bookings
         WHERE user_id = :user_id'
    );
```

Controller sada zna:

```text
database schema
SQL
PDO
```

Bolje:

```php
$bookings =
    $this->bookingService
        ->listForUser(
            $user
        );
```

ili u jednostavnijem read use case-u:

```php
$bookings =
    $this->bookingRepository
        ->findForUser(
            $user->id()
        );
```

zavisno od architecture-a.

---

# 9. Da li Controller sme direktno da koristi Repository?

Odgovor nije:

```text
nikada
```

Za veoma jednostavan read-only use case:

```text
GET /rooms
```

može biti sasvim razumno:

```php
$rooms =
    $this->rooms
        ->findAvailable();
```

ako nema business orchestration-a.

Ali čim use case uključuje:

```text
business rules
više repositories
transaction
side effects
```

Service layer obično ima više smisla.

Dakle:

```text
Controller → Repository
```

nije automatski greška.

Ali:

```text
Controller → Repository + business logic
```

često jeste znak da Service nedostaje.

---

# 10. Controller ne treba da računa business pravila

Loše:

```php
$nights =
    $checkIn->diff(
        $checkOut
    )->days;

$total =
    $nights
    * $room->pricePerNight();

if ($user->isVip()) {
    $total *= 0.9;
}
```

Ako je ovo business pricing rule, ne pripada Controller-u.

Zašto?

Jer ista cena možda treba u:

```text
web booking
API booking
admin booking
quote preview
invoice
```

Ako je logika u Controller-u:

```text
dupliciraćemo je
```

---

# 11. Business logic ide u odgovarajući application/domain sloj

Na primer:

```php
$quote =
    $this->bookingService
        ->quote(
            $user,
            $data
        );
```

ili:

```php
$total =
    $pricingService
        ->calculate(...);
```

Controller ne mora da zna:

```text
kako pricing formula radi
```

Samo da je pozove.

---

# 12. Controller ne treba da upravlja transakcijom ako je use case kompleksan

Loše:

```php
$this->pdo->beginTransaction();

try {
    $this->bookingRepository
        ->create(...);

    $this->inventoryRepository
        ->decrease(...);

    $this->pdo->commit();
} catch (Throwable $e) {
    $this->pdo->rollBack();

    throw $e;
}
```

u Controller-u.

Zašto?

Transaction boundary je deo:

```text
application use case-a
```

Ne HTTP presentation-a.

Bolje:

```php
$booking =
    $this->bookingService
        ->create(
            $user,
            $data
        );
```

A Service upravlja transakcijom.

---

# 13. Controller ne treba da šalje email direktno kao business side effect

Loše:

```php
$this->mailer->send(
    ...
);
```

direktno posle booking insert-a u Controller-u, ako je email deo booking use case-a.

Zašto?

Jer sada:

```text
booking creation
```

zavisi od:

```text
koji Controller ga je pokrenuo
```

Ako sutra booking napravi:

```text
API
admin command
queue
```

email može biti zaboravljen.

Ako je notification deo use case-a:

```text
Service / event / application layer
```

je bolja lokacija.

---

# 14. Controller i Validation

Controller može raditi:

```php
$data =
    $this->requestValidator
        ->validate($request);
```

To je dobra orchestration odgovornost.

Ali nije idealno da Controller sadrži 80 linija:

```php
if (!is_string(...)) ...
if (!filter_var(...)) ...
if (...) ...
```

za kompleksan form.

Za male input-e:

```text
2–3 jednostavna polja
```

može biti sasvim prihvatljivo.

Za veće use case-ove:

```text
FormRequest / Validator / DTO mapper
```

je čistije.

---

# 15. Validation vs business rule

Controller/request validation:

```text
room_id mora biti integer

guests mora biti 1–5

check_in mora biti validan datum
```

Service/domain:

```text
room postoji

room prima toliko gostiju

room je dostupan

booking period je dozvoljen
```

Vrlo važna razlika:

```text
INPUT SHAPE
vs
BUSINESS VALIDITY
```

---

# 16. Controller i Authorization

Controller može eksplicitno pozvati policy:

```php
$this->bookingPolicy
    ->cancel(
        $user,
        $booking
    );
```

ili:

```php
if (
    !$this->bookingPolicy
        ->canCancel(
            $user,
            $booking
        )
) {
    throw new AuthorizationException();
}
```

To je normalno.

Controller koordinira:

```text
current user
+
resource
+
action
```

Ali sama policy logika ne treba da bude 30 `if`-ova u Controller-u.

---

# 17. Authorization može biti middleware ili policy

Za opštu proveru:

```text
mora biti logged in
```

middleware je odličan.

Za object-level proveru:

```text
da li ovaj user sme baš booking 42
```

Policy ili scoped service/repository ima više smisla.

Controller povezuje te delove.

---

# 18. Controller ne treba da veruje `user_id` iz request-a

Loše:

```php
$userId =
    $request->input(
        'user_id'
    );
```

pa:

```php
$service->create(
    $userId,
    $data
);
```

Bolje:

```php
$user =
    $this->auth->user();
```

Client kaže:

```text
šta želi
```

Server zna:

```text
ko je user
```

---

# 19. Controller i route param

Za:

```text
POST /bookings/42/cancel
```

Controller može:

```php
$id =
    (int) $request->route(
        'id'
    );
```

Ali treba paziti:

```text
(int) "abc"
→ 0
```

To može sakriti invalid input.

Bolje je da route constraint ili validator proveri da ID stvarno predstavlja dozvoljeni integer format.

---

# 20. Primitive casting nije validation

Ovo:

```php
$id =
    (int) $request->route(
        'id'
    );
```

nije isto kao:

```text
validated integer ID
```

Jer:

```text
abc
→ 0

12abc
→ 12
```

zavisno od konverzije/context-a.

Bolje:

```text
validate first
then convert
```

---

# 21. Controller ne treba da zna persistence details

Loše:

```php
if (
    $e->getCode() === '23000'
) {
    ...
}
```

na deset mesta u Controller-ima.

Database constraint detalji treba da budu prevedeni u:

```text
application/persistence exception
```

bliže repository/service granici.

Na primer:

```text
DuplicateEmailException
```

Controller zatim može da ga mapira u:

```text
validation-like response
```

bez znanja o SQLSTATE-u.

---

# 22. Controller i exceptions

Controller ne treba da hvata:

```php
catch (Throwable $e)
```

samo da bi vratio:

```text
Something went wrong
```

na svakom action-u.

To pripada global exception handler-u.

Ali Controller može uhvatiti:

```text
očekivanu use-case grešku
```

ako želi specifičan HTTP flow.

Na primer:

```php
try {
    $this->bookingService
        ->cancel(
            $bookingId,
            $user
        );
} catch (
    BookingCannotBeCancelledException $e
) {
    $this->session->flash(
        'error',
        $e->getMessage()
    );

    return Response::redirect(
        '/bookings/' . $bookingId,
        303
    );
}
```

To može biti opravdano jer Controller bira presentation behavior.

---

# 23. Expected vs unexpected failure

Expected:

```text
validation failed
resource unavailable
booking cannot be cancelled
```

Unexpected:

```text
PDO connection crash
TypeError
programming bug
unhandled runtime failure
```

Controller može mapirati expected failure.

Unexpected failure ide:

```text
global handler
```

---

# 24. Controller ne treba da loguje svaki exception ručno

Loše:

```php
try {
    ...
} catch (Throwable $e) {
    $this->logger->error(...);

    throw $e;
}
```

u svakom Controller-u.

Ako samo rethrow-uje:

```text
centralni global handler
```

može jednom logovati unexpected failure.

Controller loguje samo ako ima:

```text
specifičan business/security event
```

koji stvarno pripada njegovom flow-u.

# 29. Resource Controller vs Single-action Controller

Oba mogu biti dobra.

Resource style:

```text
BookingController
├── index
├── show
├── store
└── cancel
```

Single-action:

```text
ListBookingsController
ShowBookingController
CreateBookingController
CancelBookingController
```

Tradeoff:

```text
manje klasa
vs
manje odgovornosti po klasi
```

Za naš projekat ćemo verovatno koristiti pragmatični resource-style.

# 32. Controller i AuthService

Da li Controller sme da koristi:

```php
$this->auth->user()
```

Da.

Current authenticated identity je deo HTTP/application boundary-a.

Ali Controller ne treba da implementira:

```text

remember me logic
```

To pripada auth infrastrukturi/service-u.

# 33. Controller i Session flash

Za server-rendered web:

```php
$this->session->flash(
    'success',
    'Booking created.'
);
```

u Controller-u može biti sasvim razumno.

Zašto?

Flash message je:

```text
presentation/navigation concern
```

Na primer:

```php
$this->session->flash(
    'success',
    'Booking cancelled.'

    '/bookings',
    303
);
```

To je web flow.

# 34. Ali Service ne treba da pravi flash message

```php
$bookingService->cancel(...);

$session->flash(
    'success',
    'Booking cancelled.'
);
```

unutar Service-a.

Zašto?

Jer API use case možda uopšte nema session/flash concept.

Service treba da kaže:

```text
operation succeeded
```

```text
kako to user-u predstavljamo
```

```php
$viewData = [
```

```text
Presenter
```

# 40. Defense in depth ipak postoji

To ne znači:

```text
Controller nikad ne proverava ništa
jer middleware postoji
```

Na primer object-level authorization:

```text

```

i dalje mora biti proverena.

Middleware može reći:

```text
authenticated
```

```text
authorized for this resource
```

Različite odgovornosti.

# 41. Controller should not own business state

Ne želiš:

```php
private array $bookings = [];
```

u Controller-u kao application state.

Controller je handler.

Business state pripada:

```text
domain model
repository/database
session gde je session state
```

Controller ne treba da postane pseudo-database.

```text
header
redirect
route
cookie
```

verovatno pripada:

```text
HTTP layer-u
```

Ako ne zna ništa od toga i opisuje business action:

```text
BookingService
```

granica je verovatno dobra.

---

# 50. Treći mentalni test: "Zašto bi se ovaj kod promenio?"

Controller treba da se menja kada promenimo:

```text
HTTP flow
route input
redirect
view
presentation behavior
```

Service treba da se menja kada promenimo:

```text
business use case
```

Repository:

```text
persistence
```

View:

```text
presentation markup
```

Ako Controller mora da se menja svaki put kada se promeni SQL schema:

```text
coupling je verovatno previsok
```

---

# 51. Controller nije nužno potpuno bez logike

Controller sme da ima branching koji je:

```text
HTTP/presentation orchestration
```

Na primer:

```php
if ($request->expectsJson()) {
    return Response::json(
        $data
    );
}

return Response::html(
    $this->view->render(
        'bookings/show',
        $data
    )
);
```

To jeste presentation decision.

Problem nije svaki `if`.

Problem je:

```text
koju odgovornost taj if predstavlja?
```

---

# 52. Ne seli svaki `if` u Service

Loš anti-pattern je:

```text
Controller ima if
→ mora u Service
```

Netačno.

Na primer:

```php
if ($request->query('sort') === 'newest') {
    ...
}
```

može biti request mapping concern.

Ili:

```php
if ($request->expectsJson()) {
    ...
}
```

je response concern.

Važno je semantičko vlasništvo logike.

---

# 53. Controller i status code mapping

Controller/global HTTP layer može mapirati:

```text
BookingNotFoundException
→ 404

AuthorizationException
→ 403

ValidationException
→ 422
```

Service ne treba da kaže:

```php
throw new Http404Exception();
```

ako želi da ostane nezavisan od HTTP-a.

Bolje:

```php
throw new BookingNotFoundException();
```

pa HTTP layer odluči:

```text
404
```

---

# 54. Domain exception nije HTTP exception

Na primer:

```php
BookingCannotBeCancelledException
```

znači:

```text
business operation nije dozvoljena
```

HTTP presentation može biti:

```text
409 Conflict
```

ili:

```text
422
```

ili:

```text
flash + redirect
```

zavisno od surface-a.

Zato domain exception ne treba da bude previše vezan za status code.

---

# 55. Controller i logging security event-a

Ponekad Controller/middleware može logovati:

```text
authorization denied
```

ali idealno centralizovano.

Ne logujemo:

```text
password
CSRF token
session ID
```

Controller ne treba da pravi custom insecure logging samo zato što ima pristup Request-u.

---

# 56. Controller i duplicated logic

Ako dva Controller-a imaju:

```php
$email =
    strtolower(
        trim(
            $request->input(
                'email'
            )
        )
    );
```

to možda još nije problem.

Ako šest Controller-a imaju isti:

```text
complex normalization + validation
```

onda ima smisla izdvojiti:

```text
request object / mapper / validator
```

Refactor kada postoji stvarna odgovornost i ponavljanje.

Ne unapred iz straha.

```php
final class AppController
```

# 60. Complete Controller boundary

Možemo nacrtati:

```text
                ROUTER
                  ↓
             CONTROLLER
          ┌───────┼────────┐
          ↓       ↓        ↓
      Request   Auth    Validator
          \       |       /
           \      |      /
            ↓     ↓     ↓
               DTO
                ↓
              POLICY
                ↓
              SERVICE
                ↓
              RESULT
                ↓
          CONTROLLER
          ┌─────┴─────┐
          ↓           ↓
        VIEW       REDIRECT/JSON
          \           /
           \         /
            RESPONSE
```

Controller je orchestration centar HTTP request-a.

Ne business centar aplikacije.

# Laravel paralela

Laravel Controller:

```php
public function store(
    StoreBookingRequest $request,
    BookingService $service
) {
    $booking =
        $service->create(
            auth()->user(),
            BookingData::from(
                $request->validated()
            )
        );

    return redirect()
        ->route(
            'bookings.show',
            $booking
        );
}
```

Ovo je dobar thin Controller.

Laravel već može da obezbedi:

```text
routing
dependency injection
FormRequest validation
auth
policies
responses
redirects
```

Ali osnovni design princip ostaje isti:

```text
Controller
→ koordinira

Service/domain
→ izvršava business use case
```

# Najvažnije za zapamtiti

Controller sme da:

```text
prima Request

čita route/query/body input

pozove validator/request mapper

uzme current user-a

pozove authorization

pozove Service

izabere View

postavi flash message

vrati Response
```

Controller uglavnom ne treba da:

```text
piše SQL

pravi PDO

računa business pricing

upravlja kompleksnom transakcijom

implementira inventory logiku

hashira passwords

šalje business email kao deo use case-a

generiše veliki HTML

hvata svaki Throwable

radi global middleware posao
```

Thin Controller znači:

```text
malo business logike
```

ne:

```text
maksimalno dve linije koda
```

Ključna podela:

```text
ROUTER
→ Ko obrađuje request?

CONTROLLER
→ Kako HTTP request postaje use case?

SERVICE
→ Šta use case radi?

REPOSITORY
→ Kako čuvamo/čitamo podatke?

VIEW
→ Kako rezultat prikazujemo?
```

Dobar Controller često se čita kao scenario:

```text
validate
↓
identify user
↓
authorize
↓
execute use case
↓
respond
```

I najvažnija rečenica:

> **Controller treba da zna dovoljno o HTTP-u da orkestrira request, ali ne dovoljno o business i persistence detaljima da postane mesto gde aplikacija stvarno "živi".**
