# 3. Regenerate ID - session fix

## Lekcija 3 — `session_regenerate_id()` i session fixation

Sad dolazimo do razloga zašto regenerišemo session ID nakon login-a.
Zamisli anonymous user-a:

PHPSESSID=AAA

Session trenutno nema authenticated identity:

```php
$_SESSION = [
    'cart' => [...]
];
```

User zatim uspešno unese email/password.
Najnaivnije bi bilo samo:

```php
$_SESSION['user_id'] = 15;
```

i nastaviti da koristiš:

PHPSESSID=AAA

Problem je ako je napadač nekako uspeo da navede žrtvu da koristi session ID koji napadač već zna.
To je osnova session fixation napada.
Mentalno:

```text
Attacker zna session ID AAA
↓
victim koristi session AAA
↓
victim se loginuje
↓
```

server u istoj session AAA postavi:

```text
user_id = 15
↓
attacker i dalje zna AAA
```

Odjednom ID koji je ranije predstavljao anonymous session predstavlja authenticated session.
To ne želimo.

---

## Rešenje: promeni ID na authentication boundary-ju

Nakon uspešnog login-a:

```php
session_regenerate_id(true);

$_SESSION['user_id'] = $user['id'];
```

ili često:

```php
session_regenerate_id(true);

$_SESSION['user_id'] = $user['id'];
$_SESSION['role'] = $user['role'];
```

Ideja:

pre login:

PHPSESSID=AAA

```text
successful authentication
↓
session_regenerate_id()
```

posle login:

PHPSESSID=BBB

Session state nastavlja da postoji, ali dobija novi ID koji napadač nije unapred znao.

---

## Šta znači argument true?

```php
session_regenerate_id(true);
```

true znači da PHP treba da obriše staru server-side session data povezanu sa starim ID-em.
Grubo:

```text
AAA → invalidiraj / ukloni staru session
BBB → nastavi sa novom session
```

To je tipičan izbor nakon login-a.
Bez argumenta ili sa:

```php
session_regenerate_id(false);
```

stara session data može ostati sačuvana neko vreme.
Za naš login flow ćemo koristiti:

```php
session_regenerate_id(true);
```

---

## Kada regenerisati?

Najvažniji trenutak:

```text
anonymous
↓
SUCCESSFUL LOGIN
↓
regenerate
↓
authenticated
```

Takođe ima smisla pri promenama security privilegija, na primer:

```text
user → admin
```

ili drugim privilege-boundary situacijama.
Ne treba regenerisati ID na svakom request-u bez razmišljanja.

---

## Authentication pre session mutation-a

Flow treba da bude:

```text
POST email/password
↓
validate input
↓
find user
↓
password_verify()
↓
SUCCESS?
    NE → login error
    DA
↓
session_regenerate_id(true)
↓
```

```php
$_SESSION['user_id'] = ...
```

Ne:

```php
$_SESSION['user_id'] = $userId;

// pa tek onda:
password_verify(...)
```

Authenticated identity upisujemo tek kada smo dokazali identitet.

---

## Session fixation vs session hijacking

Ovo ćemo još posebno raditi, ali odmah razdvoji:

```text
SESSION FIXATION
→ napadač unapred zna/fiksira ID
→ žrtva se loginuje koristeći taj isti ID
```

```text
SESSION HIJACKING
→ napadač ukrade već postojeći validan authenticated session ID
```

Kod fixation-a je ključ:

ID nije promenjen nakon login-a

Kod hijacking-a je ključ:

credential/session ID je procureo ili ukraden

`session_regenerate_id()` je posebno važna odbrana od fixation-a.

## Pitanje 3

Imamo ovaj login kod:

```php
session_start();

if (password_verify($password, $user['password_hash'])) {
    $_SESSION['user_id'] = $user['id'];
    header('Location: /dashboard.php');
    exit;
}
```

---

## Šta mu nedostaje sa security stanovišta?

Objasni:

1. gde bi ubacio `session_regenerate_id(true)`,
2. zašto,
3. i koja je razlika između session fixation i session hijacking.

---

nedostje naravno `session_regenerate_id(true)` i ja bih ga ovde ubacio kao prvu liniju
if uslov bloka čim proverimo identitet, pa onda upis user_id u sesiju, jer regenerisanjem se gube podaci stare sesije.

A sve ovo bih uradio kao zaštitu tj session fixation, u slučaju da je napadač zna session ID usera,
nakon logina bi mogao da ga koristi i da se predstavi kao auth user, međutim kada promenimo session id on više nema pristup.

ovo je bilo session fixation, a hijacking je druga stvar i odnosi se na scenario kada napadač presretne cookie i ukrade podatke.

`session_regenerate_id(true)` ne briše trenutne session podatke koje želiš da zadržiš.

## Ono generiše novi session ID i, sa true, uklanja staru server-side session instancu povezanu

sa prethodnim ID-em. Zato možeš sasvim normalno imati:

```php
$_SESSION['cart'] = [...];

session_regenerate_id(true);

$_SESSION['user_id'] = $user['id'];
```

cart ne mora da nestane samo zato što si regenerisao ID.
I da, mesto si izabrao dobro:

```php
if (password_verify($password, $user['password_hash'])) {
    session_regenerate_id(true);

    $_SESSION['user_id'] = $user['id'];

    header('Location: /dashboard.php');
    exit;
}
```

Kod session fixation scenarija preciznije je reći: napadač unapred zna
ili uspe da nametne/fiksira session ID koji žrtva koristi pre login-a.
Ako aplikacija posle uspešnog login-a zadrži isti ID, napadač može pokušati
da koristi taj isti ID kao authenticated session.
Kod session hijacking-a napadač ne mora ništa unapred da fiksira.
On ukrade već postojeći validan authenticated session ID,
recimo preko XSS-a, nesigurnog transporta ili drugog curenja.

Dakle:

```text
fixation
→ attacker zna/fiksira ID PRE login-a
→ victim se loginuje sa istim ID-em
```

```text
hijacking
→ attacker ukrade već VALIDAN authenticated session ID
```
