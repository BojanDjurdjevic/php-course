# 12. Questions

## Pitanje 1

Šta se tačno dešava kada pozovemo:

```php
session_start();
```

u request-u?
Objasni svojim rečima:

- šta PHP proverava u request-u,
- kako koristi session cookie / session ID,
- kada se kreira nova session,
- i kako na kraju nastaje `$_SESSION`.

---

PHP prvo pogleda da li request već nosi session ID (PHPSESSID=...)

Ako nosi -> pokušava da pronađe sesiju pod tim ID-en

A ako ne nosi -> kreira novu sesiju sa novim ID-em i učitava podatke i `$_SESSION`.

Zatim šalje browseru session cookie koji će browser automatski slati pri svakom requestu.

---

Tačno — 9.7/10.
Jedina mala nijansa: kada request nosi session ID, PHP ne „veruje“ nužno automatski tom ID-u. Sa:

session.use_strict_mode = 1

ako ID nije validna postojeća session, PHP neće samo prihvatiti proizvoljan ID nego će napraviti novu session.
I da, kod nove session:

```text
nema postojećih podataka
→ $_SESSION kreće kao prazan server-side state
```

A browser dobija session cookie sa session ID-em koji će zatim slati u sledećim request-ovima.

PITANJE 2

Koja je tačna razlika između:

```text
session
cookie
```

i zašto kažemo da:

PHPSESSID

nije isto što i:

```php
$_SESSION['user_id']
```

?

---

Ono što ljudi često mešaju jeste upravo cookies i session, što su dva odvojena pojma.

Sesija je server side state i podaci se čuvaju na serveru i u zavisnosti
opet od konfiguracije koristiće se filesystem, db, redis ...

Cookie iako se može setovati na serveru, ipak služi za komunikaciju između klijenta i servera,
čuva se u browser-u i može biti user controlled.

Session ID je nasumični identifikator sesije dok je `$_SESSION['user_id']` podatak
unutar sesije i ovo su 2 različita koncepta:

Session ID možemo gledati kao ključ a session storage kao server-side state.

---

Odlično — 10/10.
Posebno je dobro što si rekao:

```text
session ID = ključ
session storage = server-side state
```

To je verovatno najčistiji mentalni model.
I još jedna dobra nijansa iz tvog odgovora: cookie jeste client-side storage i zato je generalno untrusted input,
dok session state nije direktno user-controlled na isti način.

PITANJE 3

Objasni:

```php
session_regenerate_id(true);
```

---

## Kada ga koristimo, zašto ga koristimo i šta tačno znači argument true?

I usput razdvoji:

```text
session fixation
session hijacking
```

u po jednoj-dve rečenice.

---

Prvo da razjasnimo:

session fixation -> napadač je fiksirao / nametnuo session ID

hijacking -> napadač je ukrao session ID i podatke i predstavlja se kao validni korisnik.

```php
session_regenerate_id(true);
```

Koristimo svaki put posle  login-a (ili bilo koje radnje gde dolazi do podizanja nivoa:

guest -> user, user -> admin i sl). Zašto? Zato što ukoliko bi neko došao do session ID-a,
nakon login-a php regeneriše ID tj pravi novi ID za istu sesiju i napadač koji sada ima
stari ID ne može više pristupiti podacima.

Argument true znači da PHP treba da obriše staru server-side session data, povezanu sa starim ID.

---

Odlično — 9.8/10.
Jedina mala preciznost: kod session hijacking-a napadač ne mora da ukrade „session podatke“; dovoljno je da ukrade validan authenticated session ID, jer taj ID praktično služi kao credential za pristup toj session.
Tvoj opis regeneracije je dobar:

pre login:

session ID = AAA

```text
successful login / privilege elevation
↓
session_regenerate_id(true)
```

posle:

session ID = BBB

Trenutni session podaci se nastavljaju pod novim ID-em, a true znači da se stari server-side session state vezan za AAA uklanja, tako da stari ID više ne treba da ostane upotrebljiv.
I da — koristiš ga upravo na security boundary-ju:

```text
guest → authenticated user
user → viši privilege nivo
```

ne nasumično na svakom request-u.

PITANJE 4

Objasni čemu služe ova tri atributa session cookie-ja:

```text
HttpOnly
Secure
SameSite
```

I koje bi vrednosti tipično stavio za klasičnu production PHP aplikaciju preko HTTPS-a?

---

HttpOnly -> cookie nije vidljiv JS-u i JS ne mže da mu pristupi preko document.cookie.
U produkciji naravno true kao vrednost.

Secure -> Znači da će se koristiti samo preko secure veze HTTPS - postavio bih u produkciji true (u lokalu false).

SameSite -> kontroliš cross site slanje i pomaže u zaštiti od CSRF-a, u produkciji bih stavio Lax.

---

Tačno — 10/10.

Mentalna mapa ti je sada baš čista:

```text
HttpOnly → JS ne čita cookie
Secure   → cookie samo preko HTTPS
SameSite → kontroliše cross-site slanje / CSRF defense-in-depth
```

Za klasičnu production PHP aplikaciju preko HTTPS-a:

```php
[
    'secure' => true,
    'httponly' => true,
    'samesite' => 'Lax',
]
```

je vrlo razuman default.
Samo sitna nijansa za SameSite: Lax nije „samo same-site“,
nego dopušta neke bezbednije top-level cross-site navigacije,
dok blokira dosta rizičnih cross-site scenarija.

PITANJE 5

Koja je razlika između:

```php
unset($_SESSION['user_id']);

$_SESSION = [];

session_destroy();
```

i zašto kompletan logout obično uključuje i brisanje session cookie-ja iz browsera, a ne samo `session_destroy()`?

---

Ovde unset - briše samo jedan element iz session data, konkretno user_id i iako se to kao čini dovoljno da user ne bude ulogovan
ipak bolje je obrisati sve podatke sesije = [], zatim brisanje svih cookie pa i session cookie iz browser-a,
jer iako smo obrisali sesiju, browser može slati cookie na server,
a tek onda uraditi `session_destroy()` koji isključuje server-side session state povezan sa trenutnim ID-em.

---

Vrlo dobro — 9.5/10.
Jedina važna korekcija: ne brišemo nužno sve cookie-je, nego one koji učestvuju u authentication/session mehanizmu.
Dakle:

```text
unset($_SESSION['user_id'])
→ briše samo jedan session podatak
```

```text
$_SESSION = []
→ prazni sve session podatke u trenutnom request-u
```

```text
brisanje session cookie-ja
→ browser više ne šalje stari session ID
```

```text
session_destroy()
→ briše server-side session data vezanu za trenutni session ID
```

Ako imamo i remember_me cookie, onda pri punom logout-u treba revoke-ovati i njega. Ali recimo theme=dark nema razloga da brišemo.
I još jedna nijansa: `session_destroy()` ne prazni automatski trenutni `$_SESSION` array, zato ima smisla prethodno:

```php
$_SESSION = [];
```

PITANJE 6

Objasni razliku između:

```text
session cookie lifetime
session.gc_maxlifetime
application idle timeout
```

i zašto za pravilo:

„Izloguj korisnika nakon 30 minuta neaktivnosti“

ne bismo koristili samo session.gc_maxlifetime.

---

session cookie lifetime -> trajanje session cookie u browseru, koji nije isti kao server side session trajanje.

session.gc_maxlifetime -> trajanje sesije na serveru, postavljeno nesto pout 24 min koji kada prodju,
session podaci postaju kandidat za garbage collection.
VAŽNO: Ovo nije garantovano trajanje sesije, to je samo prag, nakon kog server-side podaci mogu se smatrati zastarelim.

application idle timeout -> ono sto mi sami postavljamo kroz aplikaciju.

Ovo poslednje bih i koristio ako bih zeleo da pouzdano izlogujem usera nakon 30 min. Jer se na
session.gc_maxlifetime
Ne mozemo osloniti.

---

Odlično — 10/10. Ovo je već odgovor za intervju bez bitne korekcije.
Najvažnije si jasno razdvojio:

```text
session cookie lifetime
→ browser-side životni vek cookie-ja
```

```text
session.gc_maxlifetime
→ server-side GC prag
→ nije garantovani auth timeout
```

```text
application idle timeout
→ naše eksplicitno security pravilo
```

I upravo zato za 30 minuta neaktivnosti radimo nešto tipa:

    isset($_SESSION['last_activity']) &&

## Zašto može nastati problem sa paralelnim request-ovima kada oba koriste istu PHP session?

I čemu služi:

```php
session_write_close();
```

u scenariju gde session pročitaš odmah na početku request-a,
a zatim imaš neku sporu operaciju koja traje 10–15 sekundi?

---

Ako bi klijent tokom izvršavanja jednog requesta od 15ak sekundi, odmah poslao drugi request,
onda bi taj drugi request čekao da se prvi izvrši, što nije sjajno za UI.

To je zato što php po defaultu zaključava sesiju da ne bi došlo do condition trace-a.

Zato kada ma potrebe se koristi `session_write_close()`; kako bi se oslobodila sesija od zaključavanja ali moramo znati
i to da posledice mogu biti da se upisuje u sesiju od strane 2 requesta i da jedan pregazi drugi, zato koristimo pažljivo.

---

Vrlo dobro — 9.4/10.
Jedina korekcija je termin: nije „condition trace“, nego race condition. Još preciznije, problem koji PHP session locking pokušava da spreči može biti lost update između paralelnih request-ova.
Ovo si dobro objasnio:

```text
Request A
→ session_start()
→ drži lock
→ radi 15 sekundi
```

```text
Request B
→ session_start()
→ čeka lock
```

A:

```php
session_write_close();
```

radi dve stvari:

1. upiše trenutne session izmene
2. zatvori session i oslobodi lock

Pa je dobar obrazac:

```php
session_start();

$userId = $_SESSION['user_id'];

session_write_close();

generateHugePdf();
```

Tu je bitna nijansa: ako si završio sa session-om pre `session_write_close()`, onda nema problema. Problem nastaje ako posle zatvaranja nastaviš da računaš da možeš normalno menjati:

```php
$_SESSION['foo'] = 'bar';
```

i očekuješ da će se to automatski persistovati.

Šta je flash message, zašto je prirodno vezan za session i PRG flow, i zašto je ovaj pattern dobar:

```php
$_SESSION['_flash']['success'] = 'Hotel created.';

header('Location: hotels.php', true, 303);
exit;
```

pa u sledećem request-u:

```php
$message = $_SESSION['_flash']['success'] ?? null;

unset($_SESSION['_flash']['success']);
```

?

---

Flash message su kratke poruke, zapisi u sesiju, koji nam služe da obavestimo korisnika o
uspehu / neuspehu radnje i postavljamo ih da traju jedan request.

Zato je ovaj kod dobar, jer on pita ako je upisan _flash u sesiju daj mi ga a zatim
unset-uj - obriši, kasnije ću ispisati varijablu jedanput,
a onda pri sledećem requestu je varijabla već null i ne prikazuje se ništa.

---

Tačno — 9.8/10.
Suština ti je potpuno dobra:

```text
request 1
→ upiše flash u session
→ redirect
```

```text
request 2
→ pročita flash
→ unset
```

```text
request 3
→ poruke više nema
```

```text
Zato je flash prirodan za PRG (POST → Redirect → GET): treba da preživi tačno
```

jedan redirect između dva request-a, a session je idealno mesto za taj kratkotrajni server-side state.
Samo mala preciznost: nije baš _flash ono što PHP „zna“ kao posebno
ime — to je samo naša konvencija. Mi sami odlučujemo da podatak postaje
flash time što ga posle čitanja brišemo.

## Zašto je ovaj kod nesiguran?

```php
setcookie('user_id', '15', [
    'expires' => time() + 86400 * 30,
    'path' => '/',
]);

if (isset($_COOKIE['user_id'])) {
    $_SESSION['user_id'] = (int) $_COOKIE['user_id'];
}
```

I kako bi konceptualno trebalo da radi bezbedniji remember me mehanizam?

---

Kod je potpuno nesiguran jer cookie moze biti user controlled.
I sta ako korisnik promeni user_id na 1?

Zato ke bolje napraviti random secret rememberme token a idealno
i da bude hashovan pa da se on poredi prilikom slanja cookie

---

Tačno — 9.5/10.
Najvažnije si pogodio: user_id u običnom cookie-ju ne sme biti dokaz identiteta, jer je cookie client-side i user-controlled.
Bezbedniji mentalni model je:

browser:

remember_token = RANDOM_SECRET

server/DB:

hash tog tokena

Na sledećem request-u:

```text
cookie token
↓
server izračuna hash
↓
proveri da li postoji validan zapis
↓
```

ako postoji:

```text
    kreira novu authenticated session
    postavi novi session ID
    upiše $_SESSION['user_id']
```

Dakle remember cookie ne kaže:

"Ja sam user 15."

nego:

"Evo jakog credential-a koji server može da proveri."

I još jedna dobra praksa: token treba da bude dovoljno jak, npr:

```php
$token = bin2hex(random_bytes(32));
```

PITANJE 10

Objasni zašto ovo:

```php
setcookie('theme', 'dark');

var_dump($_COOKIE['theme'] ?? null);
```

ne mora odmah da ispiše:

dark

u istom request-u.
I kako se cookie zaista briše iz browsera — da li je dovoljno:

```php
unset($_COOKIE['theme']);
```

?

---

Prvo: neće ispisati jer se cookie prvo šalje ka browser-u a zatim
pri sledećem requestu browser šalje nazad cookie
a PHP popunjava superglobal `$_COOKIE` i tek onda nam je dostupno.

Drugo: nije dovoljno unset, nego bi trebalo uraditi
`setcookie('theme', '', [ expires => -3600])`; dakle, postaviti expiration u minus tj u prošlost.

---

Tačno — 9.6/10.
Prvi deo je potpuno precizan:

```text
setcookie()
→ response šalje Set-Cookie browseru
→ browser ga čuva
→ sledeći request ga vraća
→ PHP tada puni $_COOKIE
```

Kod brisanja samo mala korekcija: ne bih stavio:

```php
'expires' => -3600
```

nego:

```php
'expires' => time() - 3600
```

Dakle expiration timestamp mora biti u prošlosti.
I još važnije: cookie treba obrisati sa istim relevantnim scope parametrima sa kojima je napravljen, naročito path i po potrebi domain.
Na primer:

```php
setcookie('theme', '', [
    'expires' => time() - 3600,
    'path' => '/',
]);
```

`unset($_COOKIE['theme'])` samo menja PHP array u trenutnom request-u; browser cookie ostaje.

## Pitanje 11

Objasni zašto je ovaj login flow ispravan:

```php
$user = findUserByEmail($email);

if (
    $user !== null &&
    password_verify($password, $user['password_hash'])
) {
    session_regenerate_id(true);

    $_SESSION['user_id'] = (int) $user['id'];

    header('Location: member_area.php', true, 303);
    exit;
}
```

Posebno me zanima:

1. zašto ne radimo `password_hash()` nad submitted passwordom pri svakom login-u,
2. zašto u session radije stavljamo user_id nego ceo `$user`,
3. i zašto `session_regenerate_id(true)` ide tek posle uspešnog `password_verify()`.

---

Kod je ispravan iz ugla sesije jer pre svega radi regenarete session ID-a što smanjuje rizik od napada,
a zatim u sesiju upisuje user_id na pravilan način.&#x20;

pasword_hash ne radimo nad submitted pasword iz prostog razloga što se lozinka hashuje pri registraciji
i onda se poslati input poredi kroz verify, jer ako bismo radili hash nad inputom,
on je svaki put salted i mogao bi biti drugačiji od upisanog u bazu.

---

## 2. Ne stavljamo ceo objekat `$user` jer u njemu može biti password i drugi podaci kritični za izlaganje,

user_id sasvim dovoljan, ako još šta treba, bolje izdvojiti posebno, npr `$user['name']`

---

## 3. Zato što je korisnik tek posle uspešnog verify praktično ulogovan, nema smisla raditi pre.

---

Odlično — 10/10.
Sve tri stvari si objasnio kako treba.
Kod passworda si posebno dobro uhvatio poentu:

```text
register/change password
→ password_hash()
→ stored hash
```

```text
login
→ submitted plain password
+ stored hash
→ password_verify()
```

Ne pravimo novi hash radi poređenja jer bi zbog salta mogao izgledati drugačije i za isti password.
Za session payload takođe tačno: minimalni identitet je bolji izbor.

```php
$_SESSION['user_id'] = (int) $user['id'];
```

je čistije i bezbednije nego da guraš ceo `$user`, posebno ako taj array sadrži password_hash, remember token ili druge interne podatke.
I treća tačka je potpuno tačna: `session_regenerate_id(true)` ima smisla tek kada smo potvrdili identitet. Pre toga je session još anonymous.

## Kako bi ga proširio da uvedeš 30 minuta idle timeout-a?

Ne treba savršen kod, može pseudo-code, ali objasni tačan flow sa:

```php
$_SESSION['last_activity']
time()
```

```text
session cleanup
redirect
```

i reci šta se dešava kada user napravi validan request pre isteka 30 minuta.

---

Naš idle bi otprilike izgledao ovako:

```php
$now = time() // uzimamo sadašnji trenutak

$maxIdle = 1800 // Postavimo max limit na 30 min

if(isset($_SESSION['last_activity') && $now - $_SESSION['last_activity'] > $maxIdle) // Proveravamo da li imamo aktivnu sesiju u kojoj je upisana poslednja aktivnost i da li je sada - poslednja aktivnost duže od postavljenog limita

{
 $_SESSION = [];
 session_destroy(); // ako jeste brišemo podatke sesije i gasimo sesiju

 header('Location: /login.php'); // redirktujemo na login page
 exit;
}

// A ako je manje vreme od 30min od poslednje aktivnosti:
$_SESSION['last_activity'] = $now // upisujemo sadašnje vreme kao poslednju aktivnost.
```

---

Odlično — 9.7/10. Flow ti je potpuno ispravan.
Pseudo-code mentalno radi ovo:

```text
now = current time
maxIdle = 1800
```

```text
ako postoji last_activity
i prošlo je više od 1800 sekundi
    ↓
    očisti auth/session state
    ↓
    uništi session
    ↓
    redirect login
    ↓
    exit
```

```text
inače
    ↓
    last_activity = now
```

Ovo je tačno:

```php
$now - $_SESSION['last_activity'] > $maxIdle
```

jer računaš koliko je sekundi prošlo od poslednje aktivnosti.
Jedina sintaksna sitnica ti je ovde:

```php
isset($_SESSION['last_activity')
```

treba:

```php
isset($_SESSION['last_activity'])
```

ali pošto si pisao pseudo-code, to uopšte ne računam kao konceptualnu grešku.
I još jedna production nijansa: ako želiš potpuno gašenje session-a, možeš obrisati i session cookie kao kod logout-a. Ali za samo objašnjenje idle-timeout logike, ovo što si napisao je sasvim dovoljno.
Posebno je važan poslednji deo:

```php
$_SESSION['last_activity'] = $now;
```

Ako user pravi validne request-ove svakih, recimo, 10 minuta:

```text
09:00 → last_activity = 09:00
09:10 → last_activity = 09:10
09:20 → last_activity = 09:20
09:40 → last_activity = 09:40
```

nikada nije bilo 30 minuta neaktivnosti, pa ostaje prijavljen.
