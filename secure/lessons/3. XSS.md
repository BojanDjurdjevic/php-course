# 3. XSS & Context-Aware Output Escaping — Part 1

## 1. Šta je XSS

XSS znači:

```text
Cross-Site Scripting
```

Suština:

> Napadač uspe da ubaci sadržaj koji browser drugog korisnika protumači kao executable JavaScript ili aktivni HTML.

Primer:

```php
$comment = $_POST['comment'];

echo $comment;
```

Ako attacker pošalje:

```html
<script>
    alert('XSS');
</script>
```

browser može izvršiti script.

Problem nije samo što je user uneo "čudan tekst".

Problem je što smo:

```text
untrusted data
↓
ubacili direktno u executable browser context
```

---

## 2. XSS se izvršava u browser-u žrtve

Ovo je važan mentalni model.

Kod SQL injection-a napadamo:

```text
database query
```

Kod XSS-a:

```text
server može sasvim normalno da radi
↓
ali vraća attacker-controlled sadržaj
↓
browser žrtve ga izvršava
```

Napadač želi da njegov input postane:

```text
code
```

umesto:

```text
data
```

Security cilj je:

> Untrusted data mora ostati data.

---

## 3. Šta XSS može da uradi

Ako attacker izvršava JavaScript u origin-u naše aplikacije, potencijalno može:

```text
čitati podatke dostupne stranici
menjati DOM
slati request-e u ime user-a
čitati non-HttpOnly storage
krasti CSRF token iz DOM-a
preusmeravati user-a
prikazati lažni login form
praviti actions kao trenutni user
```

Važna nijansa:

Ako session cookie ima:

```text
HttpOnly
```

JavaScript ne može direktno da ga pročita.

Ali XSS i dalje može biti veoma ozbiljan jer browser automatski šalje cookie uz same-origin request-e.

Dakle:

```text
HttpOnly
→ pomaže

HttpOnly
≠ rešava XSS
```

---

## 4. Stored XSS

Stored XSS znači:

```text
attacker payload
↓
sačuvan u sistemu
↓
kasnije prikazan drugom user-u
↓
browser ga izvrši
```

Primer:

Attacker unese ime:

```html
<script>
    fetch('/admin')
</script>
```

Mi ga sačuvamo u database.

Kasnije admin otvori user listu:

```php
echo $user->name;
```

Payload se izvrši u browser-u admina.

Tok:

```text
Input
↓
Database
↓
Output
↓
XSS
```

Zato:

```text
data from DB
≠ trusted
```

---

## 5. Reflected XSS

Reflected XSS nije trajno sačuvan.

Primer:

URL:

```text
/search?q=<script>alert(1)</script>
```

Kod:

```php
$query = $_GET['q'] ?? '';

echo "Results for: {$query}";
```

Server vrati input nazad u response.

Ako attacker uspe da user klikne maliciozni link, browser može izvršiti payload.

Tok:

```text
malicious URL
↓
request
↓
server reflects value
↓
browser executes
```

---

## 6. DOM-based XSS

XSS ne mora uvek nastati iz PHP output-a.

Na primer frontend JS:

```js
const name =
    new URLSearchParams(location.search)
        .get('name');

document.getElementById('result')
    .innerHTML = name;
```

Ako `name` sadrži attacker-controlled HTML:

```text
browser-side source
↓
innerHTML sink
↓
DOM XSS
```

Dakle XSS zaštita nije samo backend tema.

Frontend sink-ovi poput:

```text
innerHTML
outerHTML
insertAdjacentHTML
document.write
```

zahtevaju poseban oprez.

---

## 7. Glavna zaštita za plain text output: escaping

Ako želimo user input da prikažemo kao običan tekst u HTML-u:

```php
echo htmlspecialchars(
    $value,
    ENT_QUOTES,
    'UTF-8'
);
```

Na primer:

```php
$value = '<script>alert(1)</script>';
```

Browser će dobiti nešto poput:

```html
&lt;script&gt;alert(1)&lt;/script&gt;
```

i prikazati:

```text
<script>alert(1)</script>
```

kao tekst.

Ne kao executable HTML.

---

## 8. Šta `htmlspecialchars()` radi

Pretvara karaktere koji imaju posebno značenje u HTML-u.

Na primer:

```text
<
>
&
"
'
```

u njihove HTML-safe reprezentacije.

Zato attacker input više ne može lako da "izađe" iz tekstualnog context-a i formira novi tag ili attribute.

Mentalno:

```text
dangerous HTML syntax
↓
encoded representation
↓
browser vidi text
```

---

## 9. `ENT_QUOTES`

Koristimo:

```php
ENT_QUOTES
```

jer želimo encoding i:

```text
double quotes
single quotes
```

To je posebno bitno kada vrednost završi u HTML attribute-u.

Na primer:

```php
<input
    value="<?= htmlspecialchars(
        $name,
        ENT_QUOTES,
        'UTF-8'
    ) ?>"
>
```

Bez quote escaping-a attacker može pokušati da zatvori attribute i ubaci novi.

---

## 10. UTF-8

Dobro je eksplicitno koristiti:

```php
'UTF-8'
```

Na primer:

```php
htmlspecialchars(
    $value,
    ENT_QUOTES,
    'UTF-8'
);
```

Jer escaping mora pravilno razumeti encoding input-a.

U modernoj PHP aplikaciji:

```text
UTF-8 svuda
```

je dobar default.

---

## 11. Escaping treba raditi na output-u

Loš mentalni model:

```php
$name = htmlspecialchars(
    $_POST['name']
);
```

pa sačuvamo escaped string u database.

Zašto je to loše?

Jer sada stored vrednost više nije originalna semantic value.

Možda kasnije treba:

```text
JSON
email
PDF
API
plain text
HTML
```

Ako smo već HTML-escape-ovali vrednost pri unosu:

```text
data je vezana za jedan output context
```

Bolje:

```text
input
↓
validate / normalize
↓
store semantic value
↓
escape when rendering HTML
```

---

## 12. Escape late

Dobro pravilo:

```text
validate early
escape late
```

Primer:

```php
$name = trim(
    $_POST['name'] ?? ''
);
```

validiramo:

```php
if ($name === '') {
    // error
}
```

sačuvamo:

```text
Bojan <Developer>
```

u database kao normalan tekst.

Kasnije HTML:

```php
<?= htmlspecialchars(
    $user->name,
    ENT_QUOTES,
    'UTF-8'
) ?>
```

JSON:

```php
json_encode($user->name);
```

Email plain text:

```text
koristi originalni semantic string
```

Svaki output dobija odgovarajući encoding.

---

## 13. Stored value nije "safe" samo zato što je iz database

Primer:

```php
$user = $users->findById($id);

echo $user->bio;
```

Ovo nije sigurno samo zato što:

```text
bio je došao iz MySQL-a
```

Database je samo storage.

Možda je attacker ranije sačuvao:

```html
<img src=x onerror=alert(1)>
```

Zato:

```text
DB data
→ i dalje untrusted za HTML output
```

---

## 14. Escaping vs sanitization

Sanitization:

```php
$value = strip_tags($value);
```

menja podatak.

Escaping:

```php
echo htmlspecialchars(
    $value,
    ENT_QUOTES,
    'UTF-8'
);
```

menja samo HTML representation.

Ako user napiše:

```text
5 < 10
```

želimo da čuvamo:

```text
5 < 10
```

ne:

```text
5  10
```

Na output-u ga escape-ujemo i browser lepo prikaže:

```text
5 < 10
```

To je razlog zašto escaping često daje bolji model za plain text input.

---

## 15. Context-aware escaping

Ovo je najvažniji deo lekcije.

Ne postoji jedno escaping pravilo za:

```text
svaki output
```

Moramo znati gde vrednost ide.

Na primer:

```text
HTML body
HTML attribute
URL
JavaScript
CSS
JSON
```

svaki context ima svoja pravila.

Zato kažemo:

```text
context-aware output escaping
```

---

## 16. HTML text context

Primer:

```html
<p>
    <?= htmlspecialchars(
        $comment,
        ENT_QUOTES,
        'UTF-8'
    ) ?>
</p>
```

Ovo je:

```text
HTML text context
```

i `htmlspecialchars()` je odgovarajuća zaštita.

---

## 17. HTML attribute context

Primer:

```html
<input
    value="<?= htmlspecialchars(
        $name,
        ENT_QUOTES,
        'UTF-8'
    ) ?>"
>
```

Ovde takođe moramo escape-ovati quotes.

Zato:

```php
ENT_QUOTES
```

ima smisla.

Ali postoji važna stvar:

> Čak i pravilno HTML-escaped vrednost nije automatski bezbedna ako sam attribute ima aktivnu semantiku.

Na primer:

```html
<a href="<?= htmlspecialchars(
    $url,
    ENT_QUOTES,
    'UTF-8'
) ?>">
```

Ako `$url` bude:

```text
javascript:alert(1)
```

HTML escaping nije rešio problem.

String nije "pobegao" iz attribute-a.

Ali sam URL scheme može biti opasan.

Tu nam treba i:

```text
URL validation / allowlist
```

---

## 18. Escaping nije isto što i validation

Primer:

```php
$url = 'javascript:alert(1)';
```

Možemo bezbedno escape-ovati quotes:

```php
htmlspecialchars(
    $url,
    ENT_QUOTES,
    'UTF-8'
);
```

ali vrednost i dalje može semantički biti:

```text
nedozvoljen URL
```

Dakle:

```text
Escaping
→ sprečava syntax breakout

Validation
→ odlučuje da li je sama vrednost dozvoljena
```

Oba mogu biti potrebna.

---

## 19. URL context

Ako user može da dostavi URL:

```php
$website = $_POST['website'];
```

želimo proveriti dozvoljene scheme-ove.

Na primer:

```php
$url = filter_var(
    $website,
    FILTER_VALIDATE_URL
);

if ($url === false) {
    // invalid
}
```

zatim dodatno možemo proveriti scheme:

```php
$scheme = parse_url(
    $url,
    PHP_URL_SCHEME
);

if (!in_array(
    strtolower((string) $scheme),
    ['http', 'https'],
    true
)) {
    // reject
}
```

Pa kada ubacujemo u HTML:

```php
htmlspecialchars(
    $url,
    ENT_QUOTES,
    'UTF-8'
);
```

Dakle:

```text
URL validation
+
HTML attribute escaping
```

---

## 20. Nemoj direktno ubacivati user input u JavaScript source

Loše:

```php
<script>
    const name = '<?= $name ?>';
</script>
```

Ako `$name` sadrži:

```text
'; alert(1); //
```

možemo razbiti JavaScript string context.

Čak ni HTML escaping nije pravi mentalni model za JavaScript string.

Bolje:

```php
<script>
    const name = <?= json_encode(
        $name,
        JSON_HEX_TAG |
        JSON_HEX_AMP |
        JSON_HEX_APOS |
        JSON_HEX_QUOT
    ) ?>;
</script>
```

Još bolje, kada je moguće:

```text
izbegni inline dynamic JavaScript
```

i prenesi podatke kroz bezbednije strukture/API.

# 3. XSS & Context-Aware Output Escaping — Part 2

## 21. `innerHTML` vs `textContent`

Frontend primer.

Rizično:

```js
element.innerHTML = userInput;
```

jer browser parsira input kao HTML.

Bezbednije za plain text:

```js
element.textContent = userInput;
```

Mentalno:

```text
innerHTML
→ "parsiraj ovo kao HTML"

textContent
→ "prikaži ovo kao tekst"
```

Ako ti HTML nije potreban:

```text
ne koristi HTML sink
```

To je često najbolja zaštita.

---

## 22. Blade escaping

Laravel Blade:

```blade
{{ $value }}
```

automatski escape-uje HTML output.

Konceptualno je slično:

```php
htmlspecialchars(
    $value,
    ENT_QUOTES,
    'UTF-8'
);
```

Zato:

```blade
{{ $user->name }}
```

je default koji želimo.

---

## 23. Blade raw output

Blade ima:

```blade
{!! $value !!}
```

što znači:

```text
renderuj bez escaping-a
```

To je opasno ako je `$value` attacker-controlled.

Ako user unese:

```html
<script>alert(1)</script>
```

raw output može napraviti XSS.

Mentalno:

```text
{{ }}
→ escaped

{!! !!}
→ trust me, render raw
```

Zato raw Blade output treba koristiti samo kada:

```text
zaista znaš da sadržaj sme biti trusted HTML
```

---

## 24. "Ali ja sam validirao input"

Validation sama ne rešava XSS.

Na primer:

```text
name max 100 chars
required
string
```

Input:

```html
<img src=x onerror=alert(1)>
```

može potpuno zadovoljiti:

```text
required|string|max:100
```

Dakle:

```text
valid input
≠ safe HTML output
```

Validation i output escaping rešavaju različite probleme.

---

## 25. "Ali koristim prepared statements"

Prepared statements rešavaju:

```text
SQL injection
```

ne:

```text
XSS
```

Na primer:

```php
$stmt->execute([
    'comment' => $comment,
]);
```

savršeno bezbedno ubaci XSS payload u database kao podatak.

Kasnije:

```php
echo $comment;
```

može napraviti stored XSS.

Dakle:

```text
Prepared statement
→ SQL boundary

htmlspecialchars
→ HTML output boundary
```

Različite zaštite za različite trust boundaries.

---

## 26. Rich text menja problem

Pretpostavimo da user-u dozvoljavamo:

```html
<strong>
<em>
<p>
<ul>
<li>
```

Ne možemo samo escape-ovati sve, jer onda HTML više neće raditi.

Ali ne možemo ni:

```php
echo $userHtml;
```

jer to omogućava XSS.

Treba nam:

```text
HTML sanitizer
+
strict allowlist
```

koji dozvoljava samo određene:

```text
tags
attributes
schemes
```

Na primer:

```text
strong
em
p
ul
li
```

ali ne:

```text
script
onerror
onclick
javascript:
iframe
```

Ovo je jedan od slučajeva gde sanitization zaista ima smisla.

---

## 27. `strip_tags()` nije ozbiljan rich HTML sanitizer

Možda deluje primamljivo:

```php
strip_tags(
    $html,
    '<p><strong><em>'
);
```

Ali ozbiljan HTML security nije samo pitanje:

```text
koji tagovi postoje?
```

nego i:

```text
koji attributes?
koji URL schemes?
kakav nesting?
kakva encoding ponašanja?
```

Za pravi rich-text HTML treba koristiti battle-tested sanitizer biblioteku, ne praviti sopstveni parser regexima.

---

## 28. Ne pokušavaj da XSS rešavaš regexom

Loše:

```php
$value = preg_replace(
    '/<script.*?>.*?<\/script>/i',
    '',
    $value
);
```

Zašto?

HTML je složen parser context.

Attacker ima mnogo drugih načina:

```html
<img onerror=...>
<svg ...>
<a href="javascript:...">
```

i razne encoding/parser trikove.

Mentalno:

```text
denylist + regex
→ beskrajna igra mačke i miša
```

Bolje:

```text
plain text → escape

rich HTML → parser-based allowlist sanitizer
```

---

## 29. Double escaping

Ako escape-ujemo pri unosu:

```php
$name = htmlspecialchars(
    $_POST['name'],
    ENT_QUOTES,
    'UTF-8'
);
```

pa kasnije ponovo:

```php
echo htmlspecialchars(
    $name,
    ENT_QUOTES,
    'UTF-8'
);
```

možemo dobiti:

```text
&amp;lt;
```

umesto:

```text
&lt;
```

i korisnik vidi HTML entities umesto originalnog teksta.

To je:

```text
double escaping
```

Još jedan razlog da:

```text
store semantic data
escape at output
```

---

## 30. Helper za HTML escaping

U Vanilla PHP aplikaciji možemo imati helper:

```php
function e(
    ?string $value
): string {
    return htmlspecialchars(
        $value ?? '',
        ENT_QUOTES,
        'UTF-8'
    );
}
```

View:

```php
<h1>
    <?= e($hotel->name()) ?>
</h1>
```

```php
<p>
    <?= e($hotel->description()) ?>
</p>
```

To smanjuje mogućnost da neko slučajno zaboravi escaping.

Laravel `e()` helper i Blade rade isti tip posla.

---

## 31. Escape by default

Dobar template mentalitet:

```text
default:
escape

exception:
raw HTML only when explicitly trusted
```

Ne obrnuto.

Loš sistem:

```text
sve raw
→ developer mora da se seti gde je opasno
```

Dobar sistem:

```text
sve escaped
→ developer mora eksplicitno da kaže
  "ovde stvarno želim raw HTML"
```

To je:

```text
secure by default
```

## 32. XSS i admin panel

Česta greška:

> Admin panel je interni, pa ne moramo toliko da escape-ujemo.

Upravo su admin stranice često veoma vredne mete.

Attacker unese maliciozni payload u:

```text
contact form
hotel name
support ticket
user profile
review
```

Admin kasnije otvori taj sadržaj.

Ako admin view radi:

```php
echo $message;
```

dobijamo stored XSS sa privilegovanim user-om.

Zato:

```text
internal/admin UI
≠ trusted input
```

## 33. XSS i API

JSON API sam po sebi ne renderuje HTML.

Na primer:

```json
{
    "name": "<script>alert(1)</script>"
}
```

JSON response ne znači automatski XSS.

Ali ako frontend kasnije uzme:

```js
data.name
```

i uradi:

```js
element.innerHTML = data.name;
```

onda XSS nastaje u browser-u.

Dakle:

```text
API data
↓
frontend sink
↓
XSS possible
```

Security zavisi i od mesta gde se podatak na kraju koristi.

## 34. Content Security Policy kao defense in depth

CSP može ograničiti šta browser sme da izvrši.

Na primer policy može ograničiti:

```text
script sources
inline scripts
iframes
external resources
```

To može značajno smanjiti posledice XSS-a.

Ali:

```text
CSP
≠ zamena za escaping
```

Mentalno:

```text
escaping
→ sprečava injection

CSP
→ dodatno ograničava izvršavanje
```

Defense in depth.

CSP ćemo ponovo dotaći u lekciji o security headers.

## 35. XSS checklist za Vanilla PHP view

Kad prikazuješ bilo šta dinamičko u view-u, pitaj:

```text
1. Ko kontroliše ovu vrednost?

2. U kom context-u je prikazujem?

3. Da li je plain text ili intentional HTML?

4. Da li koristim odgovarajući encoder?

5. Da li attribute zahteva i semantic validation?

6. Da li frontend kasnije koristi innerHTML?
```

Na primer:

```php
<a
    href="<?= e($hotel->website()) ?>"
>
    <?= e($hotel->name()) ?>
</a>
```

`name`:

```text
HTML text escaping
```

`website`:

```text
URL validation
+
HTML attribute escaping
```

Ista vrednost ne dobija automatski isti security tretman samo zato što je string.

```text
Validation

```

Svaki sloj rešava drugi problem.

# Najvažnije za zapamtiti

XSS nastaje kada:

```text
untrusted data
↓
browser ga protumači kao executable content
```

Najčešći oblici:

```text
Stored XSS
Reflected XSS
DOM-based XSS
```

Za plain HTML text koristi:

```php
htmlspecialchars(
    $value,
    ENT_QUOTES,
    'UTF-8'
);
```

Ali centralno pravilo nije samo:

```text
"koristi htmlspecialchars"
```

nego:

```text
ESCAPE FOR THE OUTPUT CONTEXT
```

HTML text:

```text
HTML escaping
```

HTML attribute:

```text
HTML escaping
+
po potrebi semantic validation
```

URL:

```text
URL validation
+
HTML attribute escaping
```

JavaScript:

```text
JS-safe serialization
ne običan string interpolation
```

SQL:

```text
prepared statements
```

Plain text input:

```text
store semantic value
↓
escape on output
```

Ne koristi:

```text
strip_tags()
regex
random replacements
```

kao univerzalnu XSS zaštitu.

Rich HTML zahteva:

```text
parser-based allowlist sanitizer
```

Database data nije automatski trusted.

Prepared statements ne sprečavaju XSS.

Validation ne sprečava XSS.

HttpOnly ne sprečava XSS.

CSP pomaže, ali je dodatni sloj.

I centralni mentalni model:

```text
INPUT
→ validate

STORAGE
→ čuvaj semantic data

OUTPUT
→ pitaj:
   "u kom context-u ovo izlazi?"

BROWSER
→ mora da vidi attacker data kao DATA,
  nikada kao CODE
```

Ako samo jednu rečenicu zapamtiš:

> **XSS se ne rešava "čišćenjem input-a", već time da untrusted data nikada ne dobije značenje executable koda u output context-u.**
