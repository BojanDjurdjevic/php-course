# 2. Validation, Normalization & Sanitization — Part 1

## 1. Tri pojma koja se često mešaju

Imamo:

```text
Validation
Normalization
Sanitization
```

i vrlo često još:

```text
Escaping
```

To nisu ista stvar.

Najkraće:

```text
Validation
→ Da li je vrednost dozvoljena?

Normalization
→ Kako je pretvaramo u naš standardni oblik?

Sanitization
→ Da li namerno uklanjamo/menjamo deo input-a?

Escaping
→ Kako vrednost bezbedno predstavljamo
  u konkretnom output context-u?
```

Ovo je osnovna mapa cele lekcije.

---

## 2. Validation

Validation odgovara na pitanje:

> Da li ova vrednost zadovoljava pravila našeg sistema?

Na primer email:

```php
if (!filter_var(
    $email,
    FILTER_VALIDATE_EMAIL
)) {
    throw new ValidationException();
}
```

Broj gostiju:

```php
if (
    !is_int($guests)
    || $guests < 1
    || $guests > 10
) {
    throw new ValidationException();
}
```

Status:

```php
$allowedStatuses = [
    'pending',
    'confirmed',
    'cancelled',
];

if (!in_array(
    $status,
    $allowedStatuses,
    true
)) {
    throw new ValidationException();
}
```

Mentalno:

```text
Input
↓
Da li odgovara contract-u?
├── DA → prihvati
└── NE → odbij
```

---

## 3. Validation ne pokušava da "popravi" arbitrary input

Ako očekujemo:

```text
status = pending|confirmed|cancelled
```

i dobijemo:

```text
status = super_admin
```

validation ne treba da pokušava da pogodi šta je user mislio.

Treba:

```text
reject
```

Isto:

```text
guests = 5000
```

ako je dozvoljeno:

```text
1–10
```

ne treba automatski pretvoriti u:

```text
10
```

osim ako je to eksplicitno business pravilo.

Security princip:

> Invalid input treba uglavnom odbiti, ne "popraviti" tako da tiho postane nešto drugo.

---

## 4. Validation može biti sintaktička i semantička

### Sintaktička validation

Pita:

```text
Da li vrednost ima pravilan oblik?
```

Na primer:

```php
filter_var(
    $email,
    FILTER_VALIDATE_EMAIL
);
```

ili:

```php
ctype_digit($id);
```

### Semantička validation

Pita:

```text
Da li vrednost ima smisla
u našem konkretnom use case-u?
```

Na primer:

```text
check_out > check_in
guests <= room capacity
booking date nije u prošlosti
status transition je dozvoljen
```

Vrednost može biti sintaktički validna, ali business-validacija može pasti.

Na primer:

```text
check_in = 2027-05-10
check_out = 2027-05-01
```

Oba su validni datumi.

Ali zajedno:

```text
nisu validan booking period
```

---

## 5. Type validation je posebno važna u PHP-u

HTTP request vrednosti često stižu kao stringovi.

Na primer:

```php
$_POST['guests'];
```

može biti:

```text
"4"
```

a ne pravi integer:

```text
4
```

Zato treba jasno odlučiti:

```text
šta input contract dozvoljava?
```

Na primer:

```php
$rawGuests = $_POST['guests'] ?? null;

$guests = filter_var(
    $rawGuests,
    FILTER_VALIDATE_INT,
    [
        'options' => [
            'min_range' => 1,
            'max_range' => 10,
        ],
    ]
);
```

Ako validation ne uspe:

```php
if ($guests === false) {
    // invalid input
}
```

Sada imamo:

```text
HTTP string
↓
validacija / konverzija
↓
domain-friendly integer
```

---

## 6. `isset()` nije validation

Ovo:

```php
if (isset($_POST['email'])) {
    ...
}
```

samo govori:

```text
ključ postoji i nije null
```

Ne govori:

```text
da li je string
da li je prazan
da li je validan email
da li je dozvoljene dužine
```

Isto:

```php
$email = $_POST['email'] ?? '';
```

nije validation.

To je samo default vrednost.

Validation tek sledi.

---

## 7. `empty()` može biti problematičan

PHP:

```php
empty($value)
```

smatra praznim više različitih vrednosti:

```text
''
'0'
0
0.0
null
false
[]
```

To nekad može biti zgodno.

Ali u validation kodu može sakriti razliku između:

```text
nije poslato
```

i:

```text
poslata je legitimna vrednost 0
```

Zato često želimo precizniji contract.

Na primer:

```php
if (
    !isset($_POST['quantity'])
    || $_POST['quantity'] === ''
) {
    ...
}
```

ili još bolje centralizovan validator.

---

## 8. Normalization

Normalization znači:

> Pretvori različite legitimne reprezentacije u jedan standardni oblik.

Primer email-a:

```php
$email = strtolower(
    trim($email)
);
```

User može poslati:

```text
  BOJAN@EXAMPLE.COM
```

a naš canonical oblik bude:

```text
bojan@example.com
```

To nije isto što i validation.

Normalization:

```text
menja reprezentaciju
```

Validation:

```text
odlučuje da li je vrednost prihvatljiva
```

---

## 9. Primer normalization-a

Na primer grad:

```php
$city = trim($city);
```

ili telefonski broj, ako naš domain to eksplicitno definiše:

```text
" 064 123 456 "
↓
normalization
↓
"064123456"
```

Ali moraš biti oprezan.

Normalization nije:

```text
nasumično menjaj input dok ne izgleda lepo
```

Mora biti deo jasnog application contract-a.

---

## 10. Redosled normalization vs validation

Ne postoji univerzalno pravilo da se baš svaka normalization mora desiti pre ili posle baš svake validation provere.

Zavisi šta normalizujemo.

Na primer:

```php
$email = trim($rawEmail);
$email = strtolower($email);
```

pa:

```php
filter_var(
    $email,
    FILTER_VALIDATE_EMAIL
);
```

ima smisla.

Jer whitespace i casing ne želimo da utiču na naš canonical email oblik.

Ali ako bismo radili agresivnu transformaciju koja menja semantiku input-a:

```text
invalid value
↓
pretvori je u nešto drugo
↓
validiraj novu vrednost
```

možemo slučajno prihvatiti ono što je trebalo odbiti.

Dobar princip:

```text
safe normalization
→ canonical representation

validation
→ da li canonical value sme da uđe u sistem
```

---

## 11. Canonicalization

Normalization se često povezuje sa pojmom:

```text
canonical form
```

To znači:

> Jedan standardni oblik iste logičke vrednosti.

Na primer:

```text
JOHN@EXAMPLE.COM
john@example.com
 John@example.com
```

ako naš sistem email tretira case-insensitive:

```text
john@example.com
```

postaje canonical representation.

To pomaže kod:

```text
comparison
UNIQUE checks
search
authentication
```

---

## 12. Normalization mora biti konzistentna

Loše:

Registration:

```php
$email = strtolower(
    trim($email)
);
```

Login:

```php
$email = trim($email);
```

Password reset:

```php
$email = $email;
```

Sada imamo tri različita pravila.

Bolje:

```text
email normalization policy
→ ista kroz celu aplikaciju
```

Na primer:

```php
final class EmailNormalizer
{
    public function normalize(
        string $email
    ): string {
        return strtolower(
            trim($email)
        );
    }
}
```

ili centralizovano u request/service sloju.

---

## 13. Sanitization

Sanitization je najčešće pogrešno shvaćen deo.

Sanitization znači:

> Namerno menjamo input tako što uklanjamo ili transformišemo delove koje ne želimo.

Na primer:

```php
$title = strip_tags($title);
```

Ako user pošalje:

```html
<b>Hello</b>
```

dobijemo:

```text
Hello
```

To je sanitization.

Promenili smo originalni podatak.

---

## 14. Sanitization nije automatska security zaštita

Ovo je veoma važno.

Mnogi početnički tutorijali imaju mentalitet:

```text
user input
↓
sanitize
↓
safe forever
```

To nije tačno.

Na primer:

```php
$comment = strip_tags(
    $_POST['comment']
);
```

ne znači:

```text
$comment je bezbedan
za svaki mogući context
```

Kasnije ga možda stavimo u:

```text
HTML attribute
JavaScript
URL
SQL
shell command
```

Svaki od tih context-a ima drugačija pravila.

Zato:

```text
sanitized
≠ universally safe
```

---

## 15. Zašto "sanitize input" kao univerzalni savet nije dovoljan

Pretpostavimo:

```text
O'Reilly
```

To je legitimno prezime.

Ako pokušamo da "sanitize-ujemo SQL":

```php
$name = str_replace(
    "'",
    '',
    $name
);
```

dobijemo:

```text
OReilly
```

Promenili smo legitiman podatak.

I još gore:

```text
nismo rešili SQL injection kako treba
```

Pravo SQL rešenje je:

```text
prepared statement
+
parameter binding
```

Dakle ne menjamo legitimate data da bismo "očistili SQL".

Koristimo zaštitu primerenu sink/context-u.

# 2. Validation, Normalization & Sanitization — Part 2

## 16. Escaping nije sanitization

Pretpostavimo:

```php
$name = '<b>Bojan</b>';
```

Ako uradimo:

```php
echo htmlspecialchars(
    $name,
    ENT_QUOTES,
    'UTF-8'
);
```

browser će prikazati:

```text
<b>Bojan</b>
```

kao tekst.

Nismo promenili originalnu stored vrednost.

Samo smo je bezbedno predstavili u HTML context-u.

To je:

```text
escaping
```

Mentalno:

```text
Sanitization
→ menja podatak

Escaping
→ menja representation za output context
```

Ovo je ogromna razlika.

---

## 17. Escape late

Dobar princip:

```text
validate early
normalize intentionally
escape late
```

Na primer:

```php
$name = trim($_POST['name'] ?? '');
```

validiramo:

```php
if ($name === '') {
    // validation error
}
```

sačuvamo semantic value:

```text
<script>alert(1)</script>
```

ako je takav tekst dozvoljen u tom polju.

A kada prikazujemo u HTML-u:

```php
<?= htmlspecialchars(
    $name,
    ENT_QUOTES,
    'UTF-8'
) ?>
```

Browser neće izvršiti script.

Zašto escape radimo na output-u?

Jer tada znamo:

```text
u kom context-u podatak izlazi
```

---

## 18. Različiti output context-i zahtevaju različita pravila

HTML text:

```html
<p>
    <?= htmlspecialchars(
        $value,
        ENT_QUOTES,
        'UTF-8'
    ) ?>
</p>
```

HTML attribute:

```html
<input
    value="<?= htmlspecialchars(
        $value,
        ENT_QUOTES,
        'UTF-8'
    ) ?>"
>
```

URL:

```text
zahteva URL encoding / validaciju URL komponenti
```

JavaScript:

```text
nije isto što i HTML escaping
```

SQL:

```text
prepared statements
```

Shell:

```text
posebna shell sigurnost,
a najbolje izbegavati user-controlled shell input
```

Zato ne postoji:

```php
makeSafeForEverything($value);
```

---

## 19. Store raw ili sanitized?

Odgovor:

```text
zavisi od domain-a
```

Ako polje treba da bude plain text komentar, često ima smisla sačuvati normalnu tekstualnu vrednost i escape-ovati je na output-u.

Ako imamo rich-text editor i dozvoljavamo samo:

```text
p
strong
em
ul
li
```

onda možda moramo imati pravi HTML sanitization pipeline koji dozvoljava samo određeni subset HTML-a.

Ali to je drugačiji problem.

Mentalno:

```text
plain text
→ store semantic text
→ escape on output

allowed rich HTML
→ sanitization policy
→ allowlist tags/attributes
→ still careful on output
```

---

## 20. Denylist sanitization je slaba strategija

Loše:

```php
$value = str_replace(
    '<script>',
    '',
    $value
);
```

Zašto?

Jer napadač može koristiti mnogo drugih formi.

Na primer:

```html
<img src=x onerror=alert(1)>
```

ili druge HTML/JS tehnike.

Dakle:

```text
ukloni jednu poznatu bad stvar
```

nije dobar security model.

Ako rich HTML nije potreban:

```text
tretiraj sadržaj kao text
+
escape output
```

Ako jeste potreban:

```text
allowlist sanitization
```

je mnogo bolji model.

---

## 21. Validation treba da bude allowlist-oriented

Status:

Loše:

```php
if ($status !== 'hacked') {
    ...
}
```

Bolje:

```php
$allowedStatuses = [
    'pending',
    'confirmed',
    'cancelled',
];

if (!in_array(
    $status,
    $allowedStatuses,
    true
)) {
    throw new ValidationException();
}
```

Isto važi za:

```text
sort column
order direction
role
currency
country code
booking status
file type
```

Mentalno:

```text
poznat mali skup
→ allowlist
```

---

## 22. Length validation je i correctness i security

Na primer:

```php
$name = trim($name);

if (
    mb_strlen($name) < 2
    || mb_strlen($name) > 100
) {
    // invalid
}
```

Zašto max length?

Zbog:

```text
database constraints
UI correctness
resource abuse
unexpected payloads
```

Isto važi za:

```text
comments
titles
search queries
JSON bodies
uploads
```

Unlimited input često nije dobar contract.

## 23. Numerical range validation

Ako očekujemo broj gostiju:

```php
$guests = filter_var(
    $rawGuests,
    FILTER_VALIDATE_INT,
    [
        'options' => [
            'min_range' => 1,
            'max_range' => 10,
        ],
    ]
);
```

nije dovoljno samo:

```php
is_numeric($rawGuests)
```

jer:

```text
-999
1000000
1.5
```

mogu biti numeric, ali ne i validni za use case.

Zato:

```text
type
+
range
```

## 24. Enum-like values

Za polje:

```text
role
```

nikada ne želimo:

```php
$role = $_POST['role'];
```

pa direktno:

```php
$user->setRole($role);
```

ako legalne vrednosti jesu:

```text
user
supplier
admin
```

Backend mora imati:

```php
$allowedRoles = [
    'user',
    'supplier',
    'admin',
];
```

Ali još važnije:

> Čak i validna role vrednost možda nije dozvoljena ovom user-u.

Na primer user pošalje:

```text
role=admin
```

To može biti:

```text
valid enum value
```

ali:

```text
unauthorized operation
```

Opet:

```text
validation
≠ authorization
```

---

## 25. Client-provided fields koje uopšte ne treba prihvatiti

Jedna od najboljih security tehnika je:

> Nemoj ni prihvatiti field koji client ne treba da kontroliše.

Na primer registration:

Client šalje:

```text
name
email
password
```

Ne treba da šalje:

```text
role
email_verified_at
status
auth_version
is_admin
```

Čak i ako frontend nema ta polja, napadač ih može ručno dodati.

Backend request mapping treba da kaže:

```text
ovo su jedina dozvoljena input polja
```

Mentalno:

```text
client payload
↓
pick allowed fields
↓
DTO / validated data
```

Ne:

```text
uzmi sve što je poslato
```

---

## 26. Mass assignment mentalni model

Loše:

```php
$user->fill($_POST);
```

ili u Vanilla PHP mentalitetu:

```php
foreach ($_POST as $key => $value) {
    $user->$key = $value;
}
```

Napadač može poslati:

```text
role=admin
status=active
email_verified_at=...
```

Bolje:

```php
$data = new UserRegisterData(
    name: $validated['name'],
    email: $validated['email'],
    password: $validated['password']
);
```

Explicit mapping je bezbedniji:

```text
request može sadržati 20 field-ova
↓
application uzima samo 3 dozvoljena
```

---

## 27. Unknown fields: ignore ili reject?

Postoje dva validna pristupa.

### Ignore

```text
poznata polja uzmi
ostala ignoriši
```

Jednostavno i često dovoljno.

### Reject

Ako payload sadrži neočekivano polje:

```text
validation error
```

Ovo može biti korisno kod strožih API contract-a.

Na primer:

```json
{
    "email": "a@example.com",
    "password": "...",
    "role": "admin"
}
```

Backend može eksplicitno reći:

```text
unknown field: role
```

Oba pristupa mogu biti validna.

Najgore je:

```text
slepo prihvati sve
```

---

## 28. Validation error nije 500

Ako user pošalje:

```text
guests = abc
```

to nije:

```text
server bug
```

To je client/application validation failure.

Dakle ne želimo:

```text
PDOException / RuntimeException
→ 500
```

nego kontrolisan odgovor.

U klasičnom web form flow-u:

```text
validation errors
↓
flash
↓
redirect back
```

U API-ju često:

```text
422 Unprocessable Content
```

ili odgovarajući client error contract.

Poenta:

```text
invalid input
≠ unexpected server failure
```

## 29. Validation treba da bude centralizovana koliko ima smisla

Ako u svakom Controller-u pišemo:

```php
if (...)
if (...)
if (...)
if (...)
```

dobijamo dupliranje.

Zato smo već imali:

```text
UserRegisterRequest
UserLoginRequest
Validator helper
DTO
```

Dobar tok:

```text
Request
↓
Validation / normalization
↓
DTO
↓
Service
```

Service tada dobija mnogo pouzdaniji object contract.

Na primer:

```php
final readonly class UserRegisterData
{
    public function __construct(
        public string $name,
        public string $email,
        public string $password
    ) {}
}
```

Service ne mora ponovo da pita:

```text
da li je email string?
da li postoji name?
```

ako je request boundary to već garantovao.

## 30. Ali business validation može ostati u Service-u

Request validator može proveriti:

```text
email format
password length
required fields
```

Ali Service možda proverava:

```text
email already exists
booking dates overlap
inventory available
user status allows operation
```

Zašto?

Jer to nisu samo input-format pravila.

To su:

```text
application / domain rules
```

Mentalno:

```text
Request validation
→ shape + format + basic constraints

Service/domain validation
→ business rules
```

# Laravel paralela

Laravel `FormRequest` lepo razdvaja input boundary:

```php
public function rules(): array
{
    return [
        'email' => [
            'required',
            'email',
            'max:255',
        ],

        'guests' => [
            'required',
            'integer',
            'between:1,10',
        ],
    ];
}
```

Posle:

```php
$validated = $request->validated();
```

dobijamo samo polja koja su prošla validation contract.

Ali Laravel validation i dalje nije zamena za authorization.

Na primer:

```php
'booking_id' => [
    'required',
    'integer',
]
```

ne dokazuje:

```text
booking pripada current user-u
```

To i dalje rešava:

```text
Policy
Gate
Service/domain logic
```

I Laravel Blade escaping:

```blade
{{ $value }}
```

je output escaping problem, a ne input validation problem.

Isti principi — samo više gotove infrastrukture.

# Najvažnije za zapamtiti

Četiri različita pojma:

```text
VALIDATION
→ Da li je vrednost dozvoljena?

NORMALIZATION
→ Koji canonical oblik koristimo?

SANITIZATION
→ Da li namerno menjamo/uklanjamo sadržaj?

ESCAPING
→ Kako vrednost bezbedno predstavljamo
  u konkretnom output context-u?
```

Dobar tok:

```text
Untrusted input
↓
pick allowed fields
↓
normalize namerno
↓
validate
↓
DTO / domain value
↓
business rules
↓
store / process
↓
escape za konkretan output context
```

Ne koristi sanitization kao univerzalni:

```text
"make safe"
```

mehanizam.

```text
sanitized
≠ safe everywhere
```

Ne menjaj legitiman input da bi rešio problem koji treba rešiti drugim mehanizmom.

SQL:

```text
prepared statements
```

HTML:

```text
context-aware escaping
```

Authorization:

```text
server-side permission check
```

Validation:

```text
allowlist + type + range + format
```

Normalizuj konzistentno.

Na primer:

```text
registration email
login email
password reset email
```

treba da koriste isti normalization policy.

Ne prihvataj client-controlled field ako client nema razlog da ga kontroliše.

Posebno:

```text
role
is_admin
status
email_verified_at
user_id kao dokaz identiteta
```

Explicit mapping:

```text
request
↓
validated allowed fields
↓
DTO
```

je mnogo bezbedniji od:

```text
mass assignment svega što je poslato
```

I najvažnija rečenica:

> **Validation odlučuje da li podatak sme u sistem; escaping odlučuje kako sme da izađe iz sistema.**
