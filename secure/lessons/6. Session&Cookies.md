# 6. Sessions & Cookie Security — Part 1

## 1. Session nije isto što i cookie

PHP session tipično radi ovako:

```text id="zj2j6u"
Browser
↓
session cookie
↓
PHPSESSID=abc123
↓
server
↓
session storage
↓
$_SESSION
```

Cookie obično ne sadrži:

```text id="p1x0v4"
user object
permissions
cart
flash messages
```

nego samo identifikator session-a.

Na serveru čuvamo stvarne podatke:

```php id="la8jq9"
$_SESSION['user_id'] = 17;
```

Mentalno:

```text id="bl9ziq"
cookie
→ ključ

server session
→ podatak
```

---

## 2. Zašto je session ID security-sensitive

Ako attacker dobije validan session ID:

```text id="nfnwvs"
PHPSESSID=abc123
```

server možda više ne može da razlikuje:

```text id="z6l5ha"
pravog user-a
od
attacker-a
```

Jer oba request-a nose isti session identifier.

Zato session ID praktično funkcioniše kao:

```text id="vbb4ku"
privremeni credential
```

Mentalno:

```text id="3vqtzz"
ko ima validan session ID
→ može potencijalno koristiti tu session
```

Zato ga ne logujemo, ne prikazujemo i ne šaljemo nepotrebno.

---

## 3. Session hijacking

Session hijacking znači:

```text id="6p4cvr"
attacker dobije već postojeći
validan session ID
```

Na primer:

```text id="v14qpt"
user se loginovao
↓
session ID = XYZ
↓
attacker nekako ukrade XYZ
↓
attacker koristi istu session
```

Attacker sada ne mora znati password.

On koristi:

```text id="f2nscx"
već authenticated session
```

---

## 4. Kako session može biti ukraden

Na primer kroz:

```text id="jq978r"
XSS
malware
insecure transport
logove
browser extension
server-side leak
session ID u URL-u
```

Ako cookie nema `HttpOnly`, XSS može potencijalno uraditi:

```js id="df0vzi"
document.cookie
```

Ako nema HTTPS/Secure:

```text id="m3dt5s"
session može biti izložena
na nezaštićenom transportu
```

Zato cookie flags imaju smisla kao defense in depth.

---

## 5. Session fixation

Session fixation je drugačiji problem.

Ovde attacker ne krade session ID posle login-a.

On pokušava da unapred nametne session ID koji žrtva kasnije koristi.

Mentalno:

```text id="ednuzf"
attacker zna session ID
↓
žrtva koristi taj ID
↓
žrtva se loginuje
↓
isti ID postaje authenticated
↓
attacker već zna ID
```

To je:

```text id="5us3mu"
session fixation
```

---

## 6. Fixation vs hijacking

Najkraće:

```text id="d34wt2"
FIXATION
→ attacker zna session ID PRE login-a
→ žrtva se autentifikuje na toj session

HIJACKING
→ attacker ukrade session ID POSLE login-a
```

Oba mogu dovesti do:

```text id="zyruwx"
session takeover
```

ali mehanizam nije isti.

---

## 7. `session_regenerate_id(true)`

Posle uspešnog login-a radimo:

```php id="bfg5lm"
session_regenerate_id(true);
```

Zašto?

Da prekinemo vezu sa pre-login session ID-em.

Mentalno:

```text id="wdic1u"
guest session ID
↓
login success
↓
generate NEW session ID
↓
authenticated session
```

Ako attacker zna stari ID:

```text id="mzkjfh"
više mu ne koristi
```

To je glavna zaštita od session fixation-a.

---

## 8. Zašto baš posle login-a

Login je security boundary transition:

```text id="r7ms5a"
anonymous
↓
authenticated
```

To je veliki privilege change.

Zato želimo:

```text id="czt997"
novi session ID
```

Slično može imati smisla i pri drugim velikim privilege promenama.

Na primer:

```text id="690mk7"
user
↓
admin impersonation / privilege elevation
```

---

## 9. Šta radi `true`

Kod:

```php id="v9w2q7"
session_regenerate_id(true);
```

`true` znači:

```text id="zfa21v"
obriši staru session storage entry
```

odnosno želimo da stari identifier više ne ostane validan.

U auth flow-u to je najčešće upravo ono što želimo.

## 10. Cookie flags

Za session cookie posebno su važni:

```text id="ejukzg"
Secure
HttpOnly
SameSite
```

Uz to imamo:

```text id="y20w9f"
Path
Domain
Lifetime
```

Svaki utiče na to:

```text id="8o1vwc"
kada
gde
i kako

```

---

## 11. `HttpOnly`

Cookie:

```text id="rfr70c"
HttpOnly
```

znači:

> Browser-side JavaScript ne bi trebalo da može direktno da pročita cookie.

Na primer:

```js id="ub66y9"
document.cookie
```

neće vratiti HttpOnly session cookie.

To smanjuje rizik krađe session ID-a kroz XSS.

Ali:

```text id="b2i0sd"
HttpOnly
≠ XSS protection
```

Ako attacker već izvršava JavaScript na našem origin-u, može i dalje slati authenticated requests u ime user-a.

---

## 12. `Secure`

Cookie sa:

```text id="crfhk5"
Secure
```

browser šalje samo preko HTTPS-a.

To sprečava slanje session cookie-ja preko običnog:

```text id="2v8k4a"
http://
```

u normalnom browser ponašanju.

Production princip:

```text id="ag99ap"
session cookie
→ Secure
→ HTTPS only
```

Bez HTTPS-a session security je ozbiljno oslabljen.

---

## 13. `SameSite`

Već smo ga videli kod CSRF-a.

Opcije:

```text id="591z7v"
Strict
Lax
None
```

Za session cookie često je dobar default:

```text id="oe6i6e"
SameSite=Lax
```

jer značajno ograničava cross-site slanje cookie-ja.

Ali:

```text id="u5inwc"
SameSite
≠ authorization
≠ XSS protection
≠ kompletna CSRF zaštita
```

---

## 14. Cookie setup pre `session_start()`

U PHP-u tipično:

```php id="jrjh1f"
session_set_cookie_params([
    'lifetime' => 0,
    'path' => '/',
    'secure' => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);

session_start();
```

Važno je da cookie parametre postavimo:

```text id="qtblke"
pre session_start()
```

jer se odnose na session cookie koji PHP kreira.

---

## 15. `session.use_strict_mode`

Dobra PHP session konfiguracija:

```php id="6lr6ny"
ini_set(
    'session.use_strict_mode',
    '1'
);
```

Ideja:

```text id="idk3bd"
PHP ne treba slepo prihvatati
arbitrary session ID koji client pošalje
ako ta session ne postoji
```

To dodatno smanjuje fixation-style probleme.

Mentalno:

```text id="a7pz0k"
client predlaže ID
≠ server ga automatski prihvata
```

## 16. Session wrapper

Dobar Vanilla PHP Session wrapper može centralizovati:

```text id="w1mkoc"
start
get
put
forget
flash
regenerate
destroy
```

Na primer:

```php id="b1382u"
final class Session
{
    public function start(): void
    {
        if (
            session_status()
            === PHP_SESSION_ACTIVE
        ) {
            return;
        }

        ini_set(
            'session.use_strict_mode',
            '1'
        );

        session_set_cookie_params([
            'lifetime' => 0,
            'path' => '/',
            'secure' => true,
            'httponly' => true,
            'samesite' => 'Lax',
        ]);

        session_start();
    }
}
```

Prednost:

```text id="mdol7v"
session security policy
→ jedno mesto
```

## 17. Session cookie ne treba da sadrži user ID kao auth dokaz

Loše:

```text id="j3wtsw"
cookie:
user_id=17
```

pa:

```php id="3h9lb9"
$userId = $_COOKIE['user_id'];
```

i tretiramo user-a kao authenticated.

Client može menjati cookie.

Bolje:

```text id="59rkf5"
cookie
→ opaque session ID

server
→ $_SESSION['user_id']
```

Identitet mora dolaziti iz trusted server-side state-a.

---

## 18. Session data i stale user state

Pretpostavimo:

```php id="3mcfbz"
$_SESSION['user_id'] = 17;
```

ali user 17 je kasnije:

```text id="17ug4k"
deleted
disabled
suspended
```

Session nije dokaz da user i dalje sme da koristi account.

Zato current-user loading treba da proveri:

```text id="wqrfbs"
user postoji?
user active?
account status validan?
```

Ako nije:

```php id="q9ix06"
$session->forget('user_id');
```

ili potpuno invalidira session, zavisno od politike.

---

## 19. Session authentication nije samo `isset(user_id)`

Loše:

```php id="29hati"
public function check(): bool
{
    return isset(
        $_SESSION['user_id']
    );
}
```

Bolje:

```text id="i4td7r"
session user_id postoji
↓
load user
↓
user postoji?
↓
status validan?
↓
auth state validan?
```

Tek onda:

```text id="7qo3o6"
authenticated = true
```

To je razlog zašto smo u Auth modulu pravili `user()` kao centralnu current-user metodu.

---

## 20. Session versioning

Možemo imati u users tabeli:

```text id="u2f36b"
auth_version
```

a u session-u:

```text id="1lj3rf"
user_id = 17
auth_version = 4
```

Pri current-user load-u:

```text id="t5js2l"
session.auth_version
vs
users.auth_version
```

Ako se ne poklapaju:

```text id="97iqpt"
session više nije validna
```

Ovo omogućava centralno invalidiranje postojećih sessions.

Na primer posle:

```text id="oytm65"
password reset-a
security event-a
logout all devices
```

povećamo:

```text id="dhnu0v"
users.auth_version
```

i stare sessions postaju nevažeće.

# 6. Sessions & Cookie Security — Part 2

## 21. Transparent password rehash i `auth_version`


Zato obično nema potrebe povećavati:

```text id="40641p"

```

S druge strane:

```text id="sz7ht7"

```

## 22. Session lifetime

Postoje najmanje dva korisna koncepta:

```text id="dzc7tu"
inactivity timeout
absolute lifetime
```

### Inactivity timeout

Ako user ništa ne radi:

```text id="xe9qtz"
30 minuta
↓
session expire
```

### Absolute lifetime

Čak i ako je aktivan:

```text id="y8ly6x"
session traje najviše npr. 12 sati
```

Zašto oba?

Jer session ne treba nužno da traje beskonačno samo zato što user povremeno pravi request.

---

## 23. Inactivity timeout

U session možemo čuvati:

```php id="w6xfmj"
$_SESSION['last_activity']
    = time();
```

Na svakom request-u:

```php id="s0i9oz"
$lastActivity =
    $_SESSION['last_activity']
    ?? null;

if (
    is_int($lastActivity)
    && time() - $lastActivity > 1800
) {
    // expire session
}
```

pa osvežimo:

```php id="8iaiw6"
$_SESSION['last_activity']
    = time();
```

Mentalno:

```text id="7il09z"
request
↓
koliko dugo je session bila neaktivna?
↓
predugo?
→ logout
```

---

## 24. Absolute lifetime

Možemo čuvati:

```php id="j8e1vd"
$_SESSION['authenticated_at']
    = time();
```

i proveravati:

```php id="8mki0w"
if (
    time()
    - $_SESSION['authenticated_at']
    > 43200
) {
    // re-authenticate
}
```

Na primer:

```text id="1hk6w5"
43200 sec
= 12 hours
```

Čak i aktivan user posle određenog vremena mora ponovo da se autentifikuje.

# Laravel paralela

Laravel session auth već apstrahuje veliki deo ovoga.

Kod login-a:

```php id="32qldg"
Auth::attempt($credentials);
```

a nakon uspešnog login-a tipični Laravel flow koristi session regeneration.

Manual primer:

```php id="093yli"
if (Auth::attempt($credentials)) {
    $request->session()
        ->regenerate();

    return redirect()
        ->intended('/dashboard');
}
```

Logout:

```php id="76sqmw"
Auth::logout();

$request->session()
    ->invalidate();

$request->session()
    ->regenerateToken();
```

Ovde vidiš tri ideje:

```text id="5rx19h"
logout auth identity
invalidate session
regenerate CSRF token
```

Framework ti daje infrastrukturu, ali mentalni model ostaje isti.

Centralni mentalni model:

```text id="hd7pqe"
SESSION ID
→ privremeni credential

LOGIN
→ privilege change
→ regenerate ID

REQUEST
→ validate current user state

COOKIE
→ Secure + HttpOnly + SameSite

LOGOUT
→ revoke + destroy + expire

LONG-TERM LOGIN
→ Remember Me credential,
  ne beskonačna session
```

> **Session security nije samo čuvanje `user_id` u `$_SESSION`; ona štiti ceo lifecycle credential-a koji browser i server koriste da bi dokazali da request pripada istoj authenticated session.**
