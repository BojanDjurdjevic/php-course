# 4. SQL Injection — Part 1

## 1. Šta je SQL injection

SQL injection nastaje kada attacker-controlled input uspe da promeni:

```text
značenje SQL query-ja
```

umesto da ostane samo:

```text
data
```

Primer lošeg koda:

```php
$email = $_GET['email'];

$sql = "
    SELECT *
    FROM users
    WHERE email = '{$email}'
";
```

Ako user pošalje nešto poput:

```text
' OR 1=1 --
```

SQL više nije samo:

```text
traži user-a po email-u
```

nego attacker pokušava da promeni samu logiku query-ja.

Centralni problem:

```text
DATA
↓
postala je deo SQL CODE-a
```

---

## 2. SQL injection je isti mentalni problem kao XSS

Kod XSS-a:

```text
untrusted data
↓
browser je protumači kao code
```

Kod SQL injection-a:

```text
untrusted data
↓
database je protumači kao SQL syntax
```

Zato je centralni security princip isti:

> Untrusted data mora ostati data.

Prepared statements upravo prave tu granicu.

---

## 3. Loša string concatenation

Loše:

```php
$sql = "
    SELECT *
    FROM users
    WHERE email = '" . $email . "'
";
```

ili:

```php
$sql = "
    SELECT *
    FROM users
    WHERE email = '{$email}'
";
```

Problem nije samo quote karakter.

Problem je:

```text
user input
↓
direktno učestvuje u formiranju SQL source code-a
```

Napadač pokušava da ubaci:

```text
quotes
operators
comments
subqueries
SQL keywords
```

i promeni query strukturu.

---

## 4. Prepared statement

Bezbedniji obrazac:

```php
$stmt = $pdo->prepare(
    'SELECT *
     FROM users
     WHERE email = :email'
);

$stmt->execute([
    'email' => $email,
]);
```

Ovde:

```text
SQL structure
→ definisana od developera

data
→ prosleđena odvojeno
```

Database driver sada može tretirati `$email` kao:

```text
VALUE
```

a ne SQL syntax.

---

## 5. Placeholder ne predstavlja SQL kod

Ovo:

```sql
WHERE email = :email
```

znači:

```text
ovde dolazi vrednost
```

Ne znači:

```text
ovde može doći bilo koji deo SQL-a
```

To je veoma važna razlika.

Placeholder je za:

```text
string
number
date
boolean-ish scalar
value
```

ne za:

```text
table name
column name
ORDER BY direction
SQL keyword
operator
```

---

## 6. Named i positional placeholders

Named:

```php
$stmt = $pdo->prepare(
    'SELECT *
     FROM bookings
     WHERE user_id = :user_id
       AND status = :status'
);

$stmt->execute([
    'user_id' => $userId,
    'status' => $status,
]);
```

Positional:

```php
$stmt = $pdo->prepare(
    'SELECT *
     FROM bookings
     WHERE user_id = ?
       AND status = ?'
);

$stmt->execute([
    $userId,
    $status,
]);
```

Oba pristupa mogu biti bezbedna.

Named placeholders su često čitljiviji kod većih query-ja.

---

## 7. `bindValue()` i tipovi

Možemo eksplicitno bind-ovati:

```php
$stmt->bindValue(
    ':user_id',
    $userId,
    PDO::PARAM_INT
);
```

i:

```php
$stmt->bindValue(
    ':status',
    $status,
    PDO::PARAM_STR
);
```

To pomaže da contract bude jasniji.

Ali security suština nije samo tip.

Najvažnije je:

```text
value je odvojena od SQL strukture
```

---

## 8. Prepared statement ne zamenjuje validation

Ako user pošalje:

```text
guests = -999
```

prepared statement će bezbedno sačuvati:

```text
-999
```

ako DB schema to dozvoli.

Dakle:

```text
prepared statement
→ sprečava SQL injection

validation
→ proverava da li je vrednost dozvoljena
```

Različiti problemi.

---

## 9. Prepared statement ne zamenjuje authorization

Primer:

```php
$stmt = $pdo->prepare(
    'DELETE FROM bookings
     WHERE id = :id'
);

$stmt->execute([
    'id' => $bookingId,
]);
```

Query može biti potpuno zaštićen od SQL injection-a.

Ali ako user može poslati:

```text
booking_id = tuđi booking
```

imamo authorization problem.

Dakle:

```text
SQL-safe
≠ authorized
```

Kasnije ćemo to detaljno raditi u IDOR lekciji.

---

## 10. Dynamic `ORDER BY` problem

Recimo da user bira sortiranje:

```text
?sort=price
```

Možda pokušamo:

```php
$stmt = $pdo->prepare(
    'SELECT *
     FROM hotels
     ORDER BY :sort'
);

$stmt->execute([
    'sort' => $sort,
]);
```

Ovo ne radi ono što želimo.

Zašto?

Jer placeholder predstavlja:

```text
value
```

a:

```text
price
```

u `ORDER BY price` nije value.

To je:

```text
SQL identifier
```

---

## 11. Zašto ne možemo bind-ovati column name

Database mora da parsira:

```sql
ORDER BY price
```

kao SQL strukturu.

Ako napišemo:

```sql
ORDER BY :column
```

driver ne može da kaže:

```text
ova value zapravo znači identifier
```

Isto važi za:

```text
table names
column names
ASC / DESC
operators
```

Zato tu prepared statement nije dovoljno rešenje.

---

## 12. Allowlist za dynamic column

Ako dozvoljavamo samo:

```text
price
name
created_at
```

onda:

```php
$allowedSorts = [
    'price',
    'name',
    'created_at',
];

$sort = $_GET['sort'] ?? 'created_at';

if (!in_array(
    $sort,
    $allowedSorts,
    true
)) {
    $sort = 'created_at';
}
```

Tek onda:

```php
$sql = "
    SELECT *
    FROM hotels
    ORDER BY {$sort}
";
```

Ovo je bezbedno zato što:

```text
user ne određuje arbitrary SQL text
```

nego bira između:

```text
tri unapred poznate vrednosti
```

---

## 13. Još bolji mapping

Umesto da directly koristimo client string kao SQL identifier:

```php
$allowedSorts = [
    'price' => 'price_per_night',
    'name' => 'name',
    'newest' => 'created_at',
];

$key = $_GET['sort'] ?? 'newest';

$column = $allowedSorts[$key]
    ?? $allowedSorts['newest'];
```

pa:

```php
$sql = "
    SELECT *
    FROM hotels
    ORDER BY {$column}
";
```

Ovo je još bolji mentalni model:

```text
client value
↓
application key
↓
trusted SQL fragment
```

Client nikada direktno ne šalje stvarno ime SQL kolone.

---

## 14. `ASC` / `DESC`

Isto važi za direction.

Loše:

```php
$direction = $_GET['direction'];

$sql = "
    SELECT *
    FROM hotels
    ORDER BY price {$direction}
";
```

Bolje:

```php
$direction = strtolower(
    $_GET['direction'] ?? 'asc'
);

if (!in_array(
    $direction,
    ['asc', 'desc'],
    true
)) {
    $direction = 'asc';
}
```

Sada je SQL fragment iz:

```text
strict allowlist
```

---

## 15. Dynamic filters su vrednosti

Za filtere poput:

```text
status
min_price
user_id
city
```

i dalje koristimo binding.

Na primer:

```php
$sql = "
    SELECT *
    FROM hotels
    WHERE city = :city
      AND price_per_night >= :min_price
";
```

pa:

```php
$stmt->execute([
    'city' => $city,
    'min_price' => $minPrice,
]);
```

Mentalno:

```text
dynamic VALUE
→ placeholder

dynamic SQL STRUCTURE
→ trusted mapping / allowlist
```

Ovo je jedna od najvažnijih stvari za zapamtiti.

# 4. SQL Injection — Part 2

## 16. Dynamic operators

Pretpostavimo da client bira:

```text
price filter mode
```

Na primer:

```text
greater
less
equal
```

Nemoj:

```php
$operator = $_GET['operator'];

$sql = "
    SELECT *
    FROM hotels
    WHERE price {$operator} :price
";
```

Umesto toga:

```php
$operators = [
    'greater' => '>',
    'less' => '<',
    'equal' => '=',
];

$key = $_GET['operator'] ?? 'equal';

$operator = $operators[$key]
    ?? '=';
```

Sada:

```text
client
→ bira application opciju

application
→ bira trusted SQL operator
```

---

## 17. Dynamic table name

Placeholder ne može rešiti:

```php
SELECT * FROM :table
```

Ako je table dynamic, mora biti iz trusted mapping-a.

Na primer:

```php
$tables = [
    'users' => 'users',
    'bookings' => 'bookings',
];

$key = $_GET['resource'] ?? '';

if (!isset($tables[$key])) {
    throw new InvalidArgumentException();
}

$table = $tables[$key];
```

pa:

```php
$sql = "
    SELECT *
    FROM {$table}
";
```

Ali u većini aplikacija dynamic table name iz client input-a je znak da arhitekturu treba dobro preispitati.

---

## 18. `IN (...)` lista

Problem:

```php
$ids = [1, 4, 7];
```

Ne možemo uraditi:

```sql
WHERE id IN (:ids)
```

i proslediti ceo array kao jednu vrednost.

Moramo napraviti placeholder za svaki element.

Na primer:

```php
$ids = [1, 4, 7];

$placeholders = implode(
    ', ',
    array_fill(
        0,
        count($ids),
        '?'
    )
);

$sql = "
    SELECT *
    FROM users
    WHERE id IN ({$placeholders})
";

$stmt = $pdo->prepare($sql);

$stmt->execute($ids);
```

Ovde:

```text
broj placeholder-a
→ generiše aplikacija

same vrednosti
→ bind-uju se
```

---

## 19. Empty `IN` lista

Ako:

```php
$ids = [];
```

dobijemo problematičan SQL poput:

```sql
WHERE id IN ()
```

Zato application treba da ima jasan contract.

Na primer:

```php
if ($ids === []) {
    return [];
}
```

Security i correctness se često preklapaju.

---

## 20. `LIKE` i wildcards

Prepared statement štiti SQL syntax:

```php
$stmt = $pdo->prepare(
    'SELECT *
     FROM hotels
     WHERE name LIKE :search'
);

$stmt->execute([
    'search' => '%' . $search . '%',
]);
```

Ali user može poslati:

```text
%
```

što semantički znači:

```text
match almost everything
```

To nije SQL injection.

To je:

```text
query semantics / search behavior
```

Ako `%` i `_` ne želiš da tretiraš kao wildcards, moraš ih posebno escape-ovati za `LIKE` semantics.

Dakle:

```text
SQL injection protection
≠ LIKE behavior control
```

---

## 21. Zašto manual escaping nije dovoljno

Loš mentalni model:

```php
$email = addslashes($email);
```

ili:

```php
$email = str_replace(
    "'",
    "''",
    $email
);
```

pa onda concatenation.

Zašto je to loše?

Jer moraš ručno pravilno rešiti:

```text
encoding
driver behavior
SQL mode
special characters
different DB systems
```

Prepared statements su mnogo pouzdaniji model.

Pravilo:

```text
values
→ bind

ne:
escape pa concatenate
```

---

## 22. `PDO::quote()` nije default security strategija

PDO ima:

```php
$pdo->quote($value);
```

Ali ako za normalne values već možeš da koristiš prepared statements:

```text
koristi prepared statements
```

`quote()` nije zamena za pravilno parameter binding dizajn.

Posebno ne treba graditi ceo repository oko:

```text
ručno quote-uj svaku vrednost
```

---

## 23. Search/filter query builder

Praktičan primer:

```php
$sql = "
    SELECT *
    FROM cars
    WHERE 1 = 1
";

$params = [];

if ($brand !== null) {
    $sql .= "
        AND brand = :brand
    ";

    $params['brand'] = $brand;
}

if ($minPrice !== null) {
    $sql .= "
        AND price >= :min_price
    ";

    $params['min_price'] = $minPrice;
}
```

Ovo je bezbedno jer:

```text
SQL structure
→ kontroliše application

values
→ idu kroz placeholders
```

Dynamic query ne znači automatski SQL injection.

Problem je samo ako dynamic deo dolazi direktno iz untrusted input-a kao SQL syntax.

## 24. Safe dynamic sort primer

Kompletno:

```php
$sortMap = [
    'price' => 'price',
    'name' => 'name',
    'newest' => 'created_at',
];

$orderMap = [
    'asc' => 'ASC',
    'desc' => 'DESC',
];

$sortKey = $_GET['sort']
    ?? 'newest';

$orderKey = strtolower(
    $_GET['order'] ?? 'desc'
);

$sortColumn = $sortMap[$sortKey]
    ?? $sortMap['newest'];

$orderDirection = $orderMap[$orderKey]
    ?? 'DESC';

$sql = "
    SELECT *
    FROM hotels
    WHERE city = :city
    ORDER BY {$sortColumn}
             {$orderDirection}
";

$stmt = $pdo->prepare($sql);

$stmt->execute([
    'city' => $city,
]);
```

Mentalno:

```text
city
→ value
→ bind

sort
→ application key
→ trusted column mapping

order
→ application key
→ trusted SQL keyword mapping
```

---

## 25. Second-order SQL injection mental model

Podatak može prvo biti bezbedno sačuvan u DB:

```text
attacker-controlled string
↓
prepared INSERT
↓
database
```

a kasnije developer uradi:

```php
$sql = "
    SELECT *
    FROM {$storedValue}
";
```

Sada je podatak koji je ranije bio:

```text
safe as a VALUE
```

upotrebljen kao:

```text
SQL STRUCTURE
```

Problem se pojavljuje tek kasnije.

To je važan mentalni model:

```text
data nije "safe forever"
```

Bezbednost zavisi od:

```text
novog context-a u kojem se koristi
```

Isto kao kod stored XSS-a.

---

## 26. ORM nije magični security štit

Laravel Eloquent:

```php
User::where(
    'email',
    $email
)->first();
```

tipično koristi parameter binding i bezbedan je za value.

Ali možeš napraviti problem sa raw SQL:

```php
User::whereRaw(
    "email = '{$email}'"
)->first();
```

Ili:

```php
DB::raw(...)
```

Ako untrusted data ubaciš direktno u raw expression.

Dakle:

```text
ORM
→ smanjuje rizik

ORM
≠ nemoguće napraviti SQL injection
```

---

## 27. Raw query discipline

Ako koristiš:

```php
DB::select(...)
```

ili PDO raw query, pravilo ostaje isto.

Dobro:

```php
DB::select(
    'SELECT *
     FROM users
     WHERE email = ?',
    [$email]
);
```

Loše:

```php
DB::select(
    "SELECT *
     FROM users
     WHERE email = '{$email}'"
);
```

Framework ne može da zaštiti code koji eksplicitno pravi unsafe SQL string.

---

## 28. Database permissions kao defense in depth

Application database user ne treba po default-u da ima:

```text
DROP DATABASE
CREATE USER
GRANT
SUPER privileges
```

ako mu to nije potrebno.

Princip:

```text
least privilege
```

Ako SQL injection ipak postoji, ograničene DB dozvole mogu smanjiti:

```text
blast radius
```

Ali:

```text
DB permissions
≠ zamena za prepared statements
```

To je defense in depth.

---

## 29. SQL injection checklist

Kad pišeš query, pitaj:

```text
1. Da li neki deo dolazi od user-a?

2. Da li je to VALUE ili SQL STRUCTURE?

3. VALUE?
   → placeholder/binding

4. STRUCTURE?
   → mogu li je potpuno izbeći?

5. Ako mora biti dynamic:
   → strict allowlist / trusted mapping

6. Da li sam odvojeno uradio validation?

7. Da li postoji authorization check?

8. Da li DB user ima minimalne potrebne privileges?
```

# Laravel paralela

Eloquent:

```php
User::where(
    'email',
    $email
)->first();
```

Query Builder:

```php
DB::table('users')
    ->where('email', $email)
    ->first();
```

oba normalno koriste binding za values.

Ali dynamic structure i dalje zahteva pažnju.

Na primer:

```php
$allowedSorts = [
    'name',
    'created_at',
];

if (!in_array(
    $sort,
    $allowedSorts,
    true
)) {
    $sort = 'created_at';
}

User::query()
    ->orderBy($sort)
    ->get();
```

Isto mentalno pravilo:

```text
value
→ framework binding

identifier / structure
→ developer-controlled allowlist
```

Kod:

```php
whereRaw()
orderByRaw()
selectRaw()
DB::raw()
```

treba tretirati kao:

```text
security-sensitive boundary
```

jer framework više ne može u potpunosti da pretpostavi šta je data, a šta SQL syntax.

# Najvažnije za zapamtiti

SQL injection nastaje kada:

```text
untrusted data
↓
postane SQL syntax
```

Centralno pravilo:

```text
VALUE
→ placeholder / binding

SQL STRUCTURE
→ trusted code / allowlist
```

Prepared statements štite:

```text
values
```

Ne mogu direktno bind-ovati:

```text
table name
column name
ASC / DESC
operator
SQL keyword
```

Za njih koristimo:

```text
strict allowlist
ili
trusted mapping
```

Primer:

```text
client:
sort=newest

application mapping:
newest → created_at
```

Ne:

```text
client text
→ direktno u SQL
```

Prepared statements ne rešavaju:

```text
validation
authorization
business rules
LIKE wildcard semantics
```

Manual escaping:

```text
addslashes
str_replace
random quote escaping
```

nije dobra zamena za parameter binding.

ORM pomaže, ali:

```text
raw SQL
→ i dalje zahteva isti security discipline
```

Database permissions daju:

```text
defense in depth
```

ali ne popravljaju injection bug.

Centralni mentalni model:

```text
QUERY
↓
koji delovi su SQL STRUCTURE?
→ developer / allowlist

koji delovi su DATA?
→ bind

VALIDATION
→ da li data ima smisla?

AUTHORIZATION
→ da li user sme da izvrši operaciju?

DATABASE PRIVILEGES
→ koliko štete kompromitovan query može da napravi?
```

Ako samo jednu rečenicu zapamtiš:

> **Prepared statements odvajaju SQL kod od podataka; kada nešto ne može biti bind-ovano jer je deo SQL strukture, ta struktura mora doći iz trusted allowlist-a, ne direktno od user-a.**
