# 10. Command Injection, SSRF & Dangerous PHP APIs — Part 1

## 1. Dangerous sink mentalni model

Do sada smo videli isti obrazac više puta.

SQL injection:

```text
untrusted input
↓
SQL interpreter
```

XSS:

```text
untrusted input
↓
browser HTML/JS parser
```

Path traversal:

```text
untrusted input
↓
filesystem path
```

Sada dodajemo:

```text
untrusted input
↓
OS shell
```

i:

```text
untrusted URL
↓
server pravi network request
```

Centralni pojam:

```text
SOURCE
→ mesto odakle dolazi untrusted data

SINK
→ mesto gde ta data dobija opasno značenje
```

Security često znači:

> Sprečiti da attacker-controlled data stigne do dangerous sink-a u obliku koji menja ponašanje sistema.

---

## 2. Command injection

PHP može pokretati operativne sistemske komande kroz funkcije poput:

```php
exec(...)
shell_exec(...)
system(...)
passthru(...)
```

Na primer:

```php
$file = $_GET['file'];

$output = shell_exec(
    "cat {$file}"
);
```

Problem:

```text
$file
→ nije samo podatak

$file
→ ulazi u shell command string
```

Attacker pokušava da doda shell syntax i promeni komandu.

To je:

```text
Command Injection
```

---

## 3. Zašto je shell posebno opasan

Shell razume mnogo više od običnog filename-a.

Na Unix-like sistemima postoje operatori poput:

```text
;
&&
||
|
>
>>
$
```

i drugi shell mehanizmi.

Zato ako radimo:

```php
shell_exec(
    "some-command " . $userInput
);
```

mi praktično kažemo:

```text
"interpretiraj attacker-controlled string
kao deo shell programa"
```

To je veoma opasna trust boundary.

---

## 4. Najbolja zaštita: ne koristi shell kada ne moraš

Ako želiš da pročitaš fajl:

Ne:

```php
shell_exec(
    "cat {$file}"
);
```

nego:

```php
file_get_contents($path);
```

Ako želiš da obrišeš fajl:

Ne:

```php
shell_exec(
    "rm {$file}"
);
```

nego:

```php
unlink($path);
```

Ako želiš da premestiš fajl:

Ne:

```php
shell_exec(
    "mv {$from} {$to}"
);
```

nego:

```php
rename(
    $from,
    $to
);
```

Security princip:

```text
ako PHP već ima direktan API
→ koristi PHP API

ne uvodi shell interpreter
bez potrebe
```

Time potpuno uklanjamo celu klasu shell injection problema.

---

## 5. Shell je interpreter

Mentalno je veoma slično SQL-u.

Loše:

```php
$sql =
    "SELECT * FROM users
     WHERE email = '{$email}'";
```

Loše:

```php
$command =
    "convert {$filename} output.jpg";
```

U oba slučaja:

```text
CODE
+
DATA
```

mešamo u jednom stringu.

Problem nije samo:

```text
"loš karakter"
```

Problem je što interpreter pokušava da razume ceo string kao program.

---

## 6. `escapeshellarg()`

Ako baš moramo da prosledimo data kao jedan shell argument, PHP ima:

```php
escapeshellarg($value);
```

Na primer:

```php
$safeFile =
    escapeshellarg($filename);

$command =
    "some-tool {$safeFile}";
```

Ideja:

```text
attacker-controlled string
↓
tretiraj kao jedan argument
```

umesto kao novu shell syntax strukturu.

Ali veoma važno:

> `escapeshellarg()` nije dozvola da arbitrary user input slobodno prosleđujemo shell-u.

Prvo pitanje i dalje treba da bude:

```text
Da li shell uopšte mora da se koristi?
```

---

## 7. `escapeshellcmd()` nije univerzalni lek

Postoji i:

```php
escapeshellcmd(...)
```

ali security dizajn ne treba da bude:

```text
napravi arbitrary shell string
↓
na kraju ga "očisti"
```

Bolji model:

```text
fixed command
+
strogo kontrolisani argumenti
+
allowlist gde je moguće
```

I još bolje:

```text
bez shell-a ako postoji library/API
```

---

## 8. Dynamic command name je mnogo opasniji

Recimo:

```php
$command = $_POST['command'];

shell_exec(
    $command
);
```

To je praktično:

```text
remote shell endpoint
```

Isto važi za nešto što deluje blaže:

```php
$tool = $_GET['tool'];

shell_exec(
    "{$tool} file.txt"
);
```

Ako `tool` mora biti dynamic, koristimo mapping:

```php
$tools = [
    'thumbnail' =>
        '/usr/bin/some-thumbnail-tool',

    'metadata' =>
        '/usr/bin/some-metadata-tool',
];
```

Client bira:

```text
thumbnail
```

Application bira:

```text
trusted executable
```

---

## 9. Allowlist za command options

Pretpostavimo CLI alat podržava:

```text
small
medium
large
```

Ne:

```php
$size = $_GET['size'];

$command =
    "tool --size={$size}";
```

nego:

```php
$sizes = [
    'small' => '640x480',
    'medium' => '1280x720',
    'large' => '1920x1080',
];

$key = $_GET['size'] ?? 'medium';

$size = $sizes[$key]
    ?? $sizes['medium'];
```

Sada application generiše trusted argument iz malog poznatog skupa.

Isti allowlist mentalni model kao kod:

```text
ORDER BY
file type
role
status
```

---

## 10. Command injection i file upload

Zamisli da smo uploadovali:

```text
holiday photo.jpg
```

a kasnije radimo:

```php
shell_exec(
    "image-tool "
    . $file->originalName()
);
```

Original filename je:

```text
untrusted metadata
```

Ne sme direktno ulaziti u shell command.

Bolje:

```text
server-generated storage path
+
fixed executable
+
kontrolisani arguments
```

Još bolje:

```text
image library/API
```

bez shell-a kada je moguće.

# 10. Command Injection, SSRF & Dangerous PHP APIs — Part 2

## 11. SSRF

SSRF znači:

```text
Server-Side Request Forgery
```

Problem nastaje kada attacker može da utiče na URL koji **server** posećuje.

Na primer:

```php
$url = $_POST['url'];

$content = file_get_contents(
    $url
);
```

ili preko HTTP client-a:

```php
$response =
    $http->get($url);
```

Na prvi pogled:

```text
server samo preuzima neki URL
```

Ali attacker sada praktično koristi naš server kao:

```text
network client / proxy
```

---

## 12. Zašto je SSRF opasan

Attacker-ov browser možda nema pristup:

```text
internal network-u
localhost servisima
cloud metadata endpoint-ima
private admin servisima
```

Ali naš backend možda ima.

Mentalno:

```text
Attacker
↓
public application
↓
SERVER
↓
internal network
```

Attacker pokušava da natera server da napravi request tamo gde attacker direktno ne može.

---

## 13. Primer SSRF-a

Aplikacija ima feature:

```text
"unesi URL slike"
```

Backend:

```php
$imageUrl =
    $_POST['image_url'];

$data =
    file_get_contents(
        $imageUrl
    );
```

Normalno:

```text
https://images.example.com/photo.jpg
```

Ali attacker pokuša URL ka:

```text
localhost
private IP
internal service
```

Ako server napravi request:

```text
attacker koristi server
da istražuje internu infrastrukturu
```

---

## 14. `FILTER_VALIDATE_URL` ne rešava SSRF

Ovo:

```php
filter_var(
    $url,
    FILTER_VALIDATE_URL
);
```

može potvrditi:

```text
string izgleda kao URL
```

Ali URL može biti potpuno sintaktički validan i ipak security-opasan.

Na primer:

```text
valid URL
→ internal destination
```

Dakle:

```text
URL VALIDATION
≠ SSRF PROTECTION
```

Ista lekcija kao ranije:

```text
valid
≠ authorized / safe
```

---

## 15. Najbezbednije: allowlist destination-a

Ako naš backend treba da komunicira samo sa:

```text
api.payment-provider.com
api.shipping-provider.com
```

onda nema razloga da dozvolimo arbitrary URL.

Možemo imati:

```php
$allowedHosts = [
    'api.payment-provider.com',
    'api.shipping-provider.com',
];
```

i proveravati destination prema jasnoj politici.

Još bolje:

```text
client uopšte ne šalje URL

client bira provider
↓
application bira URL
```

Na primer:

```php
$providers = [
    'payment' =>
        'https://api.payment-provider.com',

    'shipping' =>
        'https://api.shipping-provider.com',
];
```

---

## 16. User-provided webhook/callback URL

Neke aplikacije legitimno moraju da dozvole user-u URL.

Na primer:

```text
webhook endpoint
avatar URL
remote import
link preview
```

Tu security postaje složeniji.

Treba razmišljati o:

```text
allowed schemes
host resolution
private/internal addresses
redirects
timeouts
response size
protocol restrictions
```

Dakle arbitrary server-side URL fetching nije trivijalan feature.

---

## 17. Redirecti komplikuju SSRF

Možda proverimo prvi URL:

```text
https://safe.example
```

ali server dobije redirect ka:

```text
internal destination
```

Ako HTTP client automatski prati redirect:

```text
initial validation
→ više nije dovoljna
```

Zato ozbiljna SSRF zaštita mora razmišljati i o:

```text
redirect chain-u
```

ne samo početnom URL-u.

---

## 18. Timeout i response size

Čak i ako URL destination jeste dozvoljen, remote server može biti:

```text
veoma spor
```

ili vratiti:

```text
ogroman response
```

Zato outbound HTTP request treba da ima:

```text
connection timeout
request timeout
response/body size limit
```

Security nije samo:

```text
"da li je destination dozvoljen?"
```

nego i:

```text
"koliko resursa sme da potroši?"
```

---

## 19. SSRF i least privilege

Application server ne treba nepotrebno da ima pristup:

```text
svim internim servisima
svim mrežama
svim cloud endpoint-ima
```

Network-level ograničenja mogu smanjiti blast radius.

Defense in depth:

```text
application URL policy
+
network firewall / egress controls
+
service authentication
```

Ako SSRF bug ipak postoji, internal services ne bi trebalo automatski da veruju svakom request-u samo zato što dolazi iz interne mreže.

---

## 20. CORS ne štiti od SSRF-a

CORS je browser security mehanizam.

SSRF request pravi:

```text
server
```

Ne browser.

Zato CORS pravila internal servisa uglavnom neće zaustaviti backend HTTP client.

Mentalno:

```text
CORS
→ browser boundary

SSRF
→ server network boundary
```

Različiti problemi.

# 10. Command Injection, SSRF & Dangerous PHP APIs — Part 3

## 21. `unserialize()` i untrusted data

PHP ima:

```php
unserialize(...)
```

Ako serialized data dolazi od attacker-a:

```php
$data = unserialize(
    $_COOKIE['state']
);
```

to može biti veoma rizično.

Razlog:

```text
unserialize
→ ne pretvara samo string u obične scalar podatke

može rekonstruisati PHP objekte
```

A objekti mogu imati magic methods i application behavior.

Generalno pravilo:

> Ne koristi `unserialize()` nad untrusted data.

---

## 22. JSON je obično bolji za običan data transfer

Ako treba da prenesemo običnu strukturu:

```text
string
number
boolean
array
object-like data
```

često je prikladnije:

```php
json_encode(...)
json_decode(...)
```

Na primer:

```php
$data = json_decode(
    $input,
    true,
    512,
    JSON_THROW_ON_ERROR
);
```

JSON nije automatski:

```text
trusted
```

I dalje ga validiramo.

Ali nema isti PHP object deserialization model kao `unserialize()`.

---

## 23. `eval()` kao dangerous sink

PHP ima:

```php
eval($code);
```

Ako attacker na bilo koji način kontroliše `$code`:

```text
data
→ postaje PHP source code
```

To je ekstremno opasno.

U normalnoj web aplikaciji:

```text
eval()
```

skoro nikad ne treba da bude deo rešenja za user input.

Ako dizajn zahteva:

```text
"izvrši string kao PHP"
```

to je veliki security alarm.

---

## 24. Dynamic `include` / `require`

Iz prethodne lekcije:

```php
include $_GET['file'];
```

je dangerous sink.

Zašto?

Jer data sada utiče na:

```text
koji PHP code ulazi u execution flow
```

Isto važi za:

```php
require(...)
include_once(...)
require_once(...)
```

Application treba da kontroliše source-code paths.

---

## 25. Regular expression sa user-controlled pattern-om

Čak i nešto poput:

```php
preg_match(
    $userPattern,
    $largeText
);
```

može biti security/resource problem.

Kompleksan attacker-controlled regex može izazvati:

```text
veoma skupu obradu
```

u zavisnosti od pattern-a i engine behavior-a.

Dakle dangerous sink nije samo:

```text
"remote code execution"
```

Može biti i:

```text
resource exhaustion
```

Ako user ne mora da kontroliše regex:

```text
nemoj mu dati regex
```

nego application-defined search/filter opcije.

---

## 26. Dynamic class/function invocation

PHP dozvoljava:

```php
$function = $_POST['action'];

$function();
```

ili:

```php
$class = $_POST['class'];

$object = new $class();
```

Ovo može biti veoma opasno ako user može da bira arbitrary callable/class.

Bolje:

```php
$actions = [
    'cancel' =>
        fn () => $service->cancel(),

    'confirm' =>
        fn () => $service->confirm(),
];
```

Client bira:

```text
logical action
```

Application bira:

```text
trusted callable
```

Opet allowlist.

---

## 27. Dynamic method names

Isto:

```php
$method =
    $_POST['method'];

$service->$method();
```

može slučajno expose-ovati metode koje nikad nisu bile namenjene user-u.

Bolje:

```php
$handlers = [
    'cancel' => 'cancelBooking',
    'confirm' => 'confirmBooking',
];
```

ili još bolje:

```text
router/controller
→ eksplicitno mapiranje actions
```

Dobra MVC arhitektura smanjuje potrebu za ovakvom dinamikom.

---

## 28. Generalni dangerous sink checklist

Kada vidiš:

```text
exec
shell_exec
system
passthru
eval
include/require sa dynamic path-om
unserialize nad external input-om
file/network access sa arbitrary location
dynamic callable/class/method
```

pitaj:

```text
Ko kontroliše input?

Da li attacker može promeniti značenje operacije?

Da li ovaj interpreter/API uopšte mora da se koristi?

Mogu li koristiti fixed mapping?

Mogu li koristiti allowlist?

Mogu li potpuno ukloniti dangerous sink?
```

Najbezbedniji dangerous sink je često:

```text
sink koji uopšte ne postoji
```

---

## 29. Architecture beats sanitization

Loš security mindset:

```text
attacker input
↓
pusti ga do shell-a
↓
pokušaj da očistiš karaktere
```

Bolji:

```text
client:
operation = thumbnail

application:
operation mapping
↓
fixed image service

storage:
server-generated filename

execution:
library/API bez shell-a
```

Dakle:

```text
dobar architecture
→ smanjuje koliko sanitization-a uopšte treba
```

Isti princip smo videli kod:

```text
SQL identifiers
file paths
roles
views
```

---

## 30. Complete mental model

Za bilo koji security-sensitive API razmišljaj:

```text
SOURCE
↓
Ko kontroliše podatak?

VALIDATION
↓
Koje vrednosti smeju da postoje?

MAPPING
↓
Možemo li client value
pretvoriti u trusted application choice?

SINK
↓
SQL?
HTML?
Filesystem?
Shell?
Network?
PHP execution?
Deserializer?

BOUNDARY PROTECTION
↓
Koristi zaštitu specifičnu za taj sink
```

Ne postoji:

```php
sanitizeEverything($input);
```

koji rešava sve.

Različiti interpreteri imaju različita pravila.

# Laravel paralela

Laravel ti ne sprečava da napišeš:

```php
shell_exec(
    $request->input('command')
);
```

Framework tu ne može da te spase.

Isto:

```php
Http::get(
    $request->input('url')
);
```

može napraviti SSRF ako arbitrary URL nije dozvoljen use case.

I:

```php
unserialize(
    $request->input('payload')
);
```

ostaje opasno.

Laravel pomaže sa:

```text
routing
validation
authorization
HTTP client abstraction
filesystem abstraction
queues
```

ali dangerous sink policy i dalje pripada developer-u.

Na primer:

```php
$providers = [
    'weather' =>
        'https://api.weather.example',

    'currency' =>
        'https://api.currency.example',
];

$provider =
    $request->validated('provider');

$url = $providers[$provider];
```

je mnogo bezbedniji model nego:

```php
Http::get(
    $request->input('url')
);
```

# Najvažnije za zapamtiti

Command injection nastaje kada:

```text
untrusted data
↓
postane shell syntax
```

Najbolja zaštita:

```text
ne koristi shell
ako postoji direktan PHP/library API
```

Ako shell mora:

```text
fixed executable
+
strictly controlled arguments
+
allowlist
+
escapeshellarg gde je odgovarajuće
```

Ali:

```text
escapeshellarg()
≠ dozvola za arbitrary shell design
```

SSRF nastaje kada:

```text
attacker-controlled destination
↓
SERVER pravi request
```

Validan URL:

```text
≠ bezbedan URL
```

Najbolje:

```text
client bira logical provider
↓
application bira trusted destination
```

Ako arbitrary URL zaista mora biti podržan, razmišljaj o:

```text
scheme-u
host-u
private/internal destinations
redirectima
timeout-u
response size-u
network permissions
```

CORS:

```text
ne rešava SSRF
```

`unserialize()`:

```text
ne koristi nad untrusted data
```

Za običan data transfer:

```text
JSON
+
validation
```

je često bolji model.

Posebno oprezno sa:

```text
eval()
dynamic include/require
dynamic callable
dynamic class
dynamic method
```

Centralni princip:

```text
UNTRUSTED DATA
↓
nikada ne sme slučajno postati:

SQL CODE
HTML/JS CODE
SHELL CODE
PHP CODE
FILESYSTEM AUTHORITY
NETWORK AUTHORITY
```

I najvažnija rečenica:

> **Najbezbedniji način da zaštitiš dangerous sink često nije da "očistiš" user input, već da dizajniraš aplikaciju tako da user nikada ni ne kontroliše ono što sink izvršava.**
