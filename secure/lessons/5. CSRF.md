# 5. CSRF Protection — Part 1

## 1. Šta je CSRF

CSRF znači:

```text
Cross-Site Request Forgery
```

Suština napada:

> Attacker navede browser već authenticated korisnika da pošalje request našoj aplikaciji koji korisnik nije nameravao da izvrši.

Na primer user je ulogovan na:

```text
bank.example
```

i ima session cookie.

Zatim otvori attacker stranicu:

```text
evil.example
```

Attacker pokušava da pošalje:

```text
POST /transfer
```

Browser može automatski priložiti session cookie za naš sajt.

Server onda vidi:

```text
valid session
```

i može pomisliti:

```text
user je tražio transfer
```

ali zapravo nije.

---

## 2. Authentication sama ne rešava CSRF

Pretpostavimo:

```php
if (!$auth->check()) {
    throw new AuthenticationException();
}
```

To potvrđuje:

```text
request pripada browser-u
koji ima validnu session
```

Ali ne potvrđuje:

```text
da je user namerno poslao ovaj request
sa naše aplikacije
```

To je centralna razlika.

Mentalno:

```text
Authentication
→ Ko je session user?

CSRF protection
→ Da li je state-changing request
  zaista nastao kroz naš application flow?
```

---

## 3. Zašto cookie-based auth ima CSRF problem

Browser automatski šalje cookies prema njihovim pravilima.

Ako session cookie glasi:

```text
PHPSESSID=abc123
```

browser može uz odgovarajući request poslati:

```http
Cookie: PHPSESSID=abc123
```

bez toga da JavaScript attacker-a zna njegovu vrednost.

Zato attacker-u session ID često ni nije potreban.

Dovoljno je da natera browser žrtve da pošalje request.

Mentalno:

```text
attacker ne mora da UKRADE cookie

dovoljno je da browser
ISKORISTI cookie
```

---

## 4. Klasičan CSRF primer

Naša aplikacija ima:

```text
POST /profile/email
```

i prima:

```text
email
```

Attacker napravi stranicu:

```html
<form
    action="https://example.com/profile/email"
    method="POST"
>
    <input
        type="hidden"
        name="email"
        value="attacker@example.com"
    >
</form>

<script>
    document.forms[0].submit();
</script>
```

Ako žrtva:

```text
1. ima aktivnu session na example.com
2. otvori attacker stranicu
3. browser priloži session cookie
```

server može promeniti email.

Problem nije:

```text
authentication failure
```

nego:

```text
request authenticity failure
```

---

## 5. CSRF uglavnom štiti state-changing requests

Posebno:

```text
POST
PUT
PATCH
DELETE
```

odnosno operacije koje menjaju stanje:

```text
create
update
delete
cancel
logout
transfer
change password
change email
```

GET request bi po HTTP semantici trebalo da bude:

```text
safe
```

odnosno da ne menja server state.

Zato je loše:

```text
GET /booking/42/delete
```

Mnogo bolje:

```text
POST /booking/42/cancel
```

ili:

```text
DELETE /bookings/42
```

sa CSRF zaštitom.

---

## 6. GET ne treba da menja stanje

Ako imamo:

```html
<a href="/logout">
    Logout
</a>
```

i:

```text
GET /logout
```

neko može izazvati request preko:

```html
<img src="https://example.com/logout">
```

ili linka.

Zato state-changing operacije treba da zahtevaju odgovarajući HTTP method.

Na primer:

```text
POST /logout
```

uz CSRF token.

Mentalno:

```text
GET
→ read / safe

POST/PUT/PATCH/DELETE
→ state change
→ CSRF protection
```

---

## 7. Synchronizer Token Pattern

Najčešći session-based pristup:

```text
Session
↓
random CSRF token
↓
form dobije kopiju
↓
POST vrati token
↓
server poredi
```

Token mora biti:

```text
nepredvidiv
dovoljno nasumičan
vezan za session
```

Na primer:

```php
$_SESSION['csrf_token'] =
    bin2hex(
        random_bytes(32)
    );
```

Dobijamo 64 hex karaktera.

---

## 8. Zašto `random_bytes()`

Ne želimo:

```php
md5(time())
```

ili:

```php
rand()
```

ili:

```php
$userId . time()
```

jer token ne treba da bude predvidiv.

Koristimo:

```php
random_bytes(32)
```

jer je namenjen cryptographically secure random vrednostima.

Mentalno:

```text
CSRF token
→ secret-like unpredictable nonce
```

---

## 9. Token čuvamo server-side

Na primer:

```php
final class Csrf
{
    public function __construct(
        private Session $session
    ) {}

    public function token(): string
    {
        $token = $this->session->get(
            'csrf_token'
        );

        if (!is_string($token)) {
            $token = bin2hex(
                random_bytes(32)
            );

            $this->session->put(
                'csrf_token',
                $token
            );
        }

        return $token;
    }
}
```

Sada je token vezan za:

```text
ovu server-side session
```

---

## 10. Token u formi

View:

```php
<form method="POST" action="/booking/cancel">

    <input
        type="hidden"
        name="_token"
        value="<?= e($csrf->token()) ?>"
    >

    <button type="submit">
        Cancel booking
    </button>

</form>
```

Browser šalje:

```text
session cookie
+
_token
```

Server zatim proverava:

```text
da li request token
odgovara token-u u session
```

---

## 11. Zašto attacker ne može jednostavno da pogodi token

Attacker može pokušati da pošalje request sa svog sajta.

Browser žrtve može poslati session cookie.

Ali attacker ne zna:

```text
CSRF token iz session-a žrtve
```

Ako token ima dovoljnu entropy:

```text
praktično ga ne može pogoditi
```

Zato server zahteva dve stvari:

```text
valid session
+
valid CSRF token
```

Browser automatski šalje cookie.

Ali ne zna automatski da ubaci tajni token u attacker formu.

---

## 12. Validacija token-a

Na serveru:

```php
public function validate(
    ?string $token
): bool {
    $sessionToken =
        $this->session->get(
            'csrf_token'
        );

    if (
        !is_string($token)
        || !is_string($sessionToken)
    ) {
        return false;
    }

    return hash_equals(
        $sessionToken,
        $token
    );
}
```

Controller:

```php
if (!$csrf->validate(
    $_POST['_token'] ?? null
)) {
    http_response_code(403);

    exit;
}
```

Ili:

```php
throw new CsrfTokenMismatchException();
```

---

## 13. Zašto `hash_equals()`

Možemo tehnički napisati:

```php
$token === $sessionToken
```

ali za secret/token comparison preferiramo:

```php
hash_equals(
    $sessionToken,
    $token
);
```

Jer je dizajniran za timing-safe poređenje stringova.

Mentalno:

```text
secret comparison
→ hash_equals()
```

Isti princip smo već koristili kod auth tokena.

---

## 14. CSRF token nije auth token

CSRF token ne govori:

```text
ko je user
```

Session to već radi.

CSRF token govori:

```text
request je stigao kroz context
koji je imao pristup validnom token-u
vezanom za session
```

Dakle:

```text
Session
→ identity

CSRF token
→ request authenticity / intent protection
```

---

## 15. Jedan token po session-u ili po formi?

Postoje različiti dizajni.

Jednostavan Vanilla PHP pristup:

```text
jedan CSRF token
po session-u
```

Prednosti:

```text
jednostavan
stabilan
lako implementirati
```

Možemo imati i:

```text
token po formi
token po action-u
rotirajuće tokene
```

ali to povećava kompleksnost.

Za naš kurs:

```text
random token vezan za session
```

je dobar i sasvim ozbiljan default.

# 5. CSRF Protection — Part 2

## 16. Kada regenerisati CSRF token

Ne moraš nužno menjati token posle svakog request-a.

Ako token rotiraš preagresivno, možeš napraviti probleme sa:

```text
više otvorenih tabova
back button-om
paralelnim formama
```

Čest jednostavan model:

```text
token traje koliko i session
```

a nova session dobija novi token.

Možeš ga regenerisati i na važnim security događajima, ali lifecycle treba da bude konzistentan.

---

## 17. Session regeneration i CSRF

Posle login-a često radimo:

```php
session_regenerate_id(true);
```

To štiti od:

```text
session fixation
```

CSRF token može ostati ili biti regenerisan, zavisno od dizajna.

Security-sensitive aplikacija može odlučiti:

```text
login
↓
new session ID
+
new CSRF token
```

Važno je samo da server-side session i form token ostanu usklađeni.

---

## 18. CSRF validation treba da bude centralizovana

Loše:

```php
// Controller A
if (...) { ... }

// Controller B
if (...) { ... }

// Controller C
if (...) { ... }
```

Bolje:

```text
Middleware / request boundary
```

Na primer:

```php
final class VerifyCsrfToken
{
    public function __construct(
        private Csrf $csrf
    ) {}

    public function handle(
        Request $request,
        callable $next
    ): Response {
        if (
            in_array(
                $request->method(),
                ['POST', 'PUT', 'PATCH', 'DELETE'],
                true
            )
            && !$this->csrf->validate(
                $request->input('_token')
            )
        ) {
            throw new CsrfTokenMismatchException();
        }

        return $next($request);
    }
}
```

Mentalno:

```text
state-changing request
↓
CSRF middleware
↓
valid?
├── NE → reject
└── DA → Controller
```

---

## 19. CSRF i JSON/API requests

Kod AJAX request-a token možemo poslati kroz header.

Na primer:

```http
X-CSRF-TOKEN: abc123...
```

Frontend može token dobiti iz:

```text
meta tag-a
server-rendered bootstrap data
CSRF endpoint-a
```

Server zatim poredi header sa session tokenom.

Mentalno:

```text
HTML form
→ hidden _token

AJAX
→ header
```

Princip je isti.

---

## 20. SameSite cookie

Cookie može imati:

```text
SameSite=Lax
SameSite=Strict
SameSite=None
```

SameSite ograničava kada browser šalje cookie u cross-site context-u.

Na primer:

```php
session_set_cookie_params([
    'httponly' => true,
    'secure' => true,
    'samesite' => 'Lax',
]);
```

To može značajno smanjiti CSRF attack surface.

Ali:

```text
SameSite
≠ jedina CSRF zaštita
```

---

## 21. `SameSite=Strict`

Strict znači približno:

```text
cookie se vrlo restriktivno
ne šalje u cross-site context-u
```

To je jaka zaštita.

Ali može pokvariti UX u legitimnim flow-ovima.

Na primer user klikne link iz:

```text
email-a
external site-a
search engine-a
```

i možda ne dobije očekivanu authenticated session odmah.

Zato nije uvek praktičan default.

---

## 22. `SameSite=Lax`

Lax je čest kompromis.

Daje značajnu CSRF zaštitu za mnoge cross-site request scenarije, a zadržava praktičniji navigation behavior.

Za normalne session cookie-je često je dobar default.

Ali security architecture i dalje ne treba da kaže:

```text
imamo SameSite
→ CSRF token nam ne treba
```

Token daje dodatnu nezavisnu zaštitu.

To je:

```text
defense in depth
```

---

## 23. `SameSite=None`

Ako treba cookie u cross-site context-u:

```text
SameSite=None
```

moderni browser-i zahtevaju i:

```text
Secure
```

Takav cookie ima veći cross-site exposure.

Zato CSRF dizajn postaje još važniji.

---

## 24. Origin i Referer provera

Server može dodatno proveriti:

```text
Origin
```

ili:

```text
Referer
```

header.

Na primer očekujemo:

```text
Origin: https://example.com
```

Ovo može biti dodatna zaštita.

Ali ne želimo da cela CSRF zaštita zavisi samo od toga.

Razlozi uključuju:

```text
proxy behavior
privacy settings
header availability
deployment complexity
```

Dobar mentalni model:

```text
CSRF token
→ primarna application protection

SameSite
→ browser defense

Origin/Referer
→ dodatni signal
```

---

## 25. CORS nije CSRF zaštita

Ovo je veoma česta zabuna.

CORS kontroliše:

```text
da li JavaScript sa drugog origin-a
sme da ČITA response
```

Ali attacker često ne mora da pročita response da bi izvršio CSRF.

Ako samo želi:

```text
change email
cancel booking
logout
```

dovoljno mu je da request bude izvršen.

Dakle:

```text
CORS
≠ CSRF protection
```

CORS ćemo detaljnije raditi kasnije.

---

## 26. CSRF i login

Može postojati i:

```text
login CSRF
```

Attacker može pokušati da žrtvu uloguje na attacker-ov account.

Žrtva zatim možda unese:

```text
private podatke
payment information
orders
```

misleći da koristi svoj account.

Zato CSRF nije samo:

```text
"za authenticated POST request"
```

Security-sensitive auth flow-ovi takođe mogu zahtevati zaštitu.

---

## 27. CSRF i logout

Logout često izgleda bezazleno:

```text
GET /logout
```

ali attacker može forsirati logout.

Zato je bolji dizajn:

```text
POST /logout
+
CSRF token
```

Tvoj Auth modul je već išao u tom smeru.

---

## 28. CSRF i idempotency nisu isto

CSRF:

```text
Da li je request autentično pokrenut
iz očekivanog application context-a?
```

Idempotency:

```text
Šta se desi ako isti request
stigne dva puta?
```

Na primer payment:

```text
valid CSRF token
```

ne rešava:

```text
double submit
```

To zahteva poseban:

```text
idempotency / duplicate prevention
```

mehanizam.

Security problemi često imaju više nezavisnih dimenzija.

---

## 29. CSRF token ne rešava XSS

Ako attacker već ima XSS na našem origin-u, njegov JavaScript često može:

```text
pročitati CSRF token iz DOM-a
```

i poslati validan request.

Zato:

```text
CSRF token
≠ XSS protection
```

XSS je često moćniji problem jer attacker code već radi unutar trusted origin-a.

Opet defense in depth:

```text
XSS escaping
+
CSRF
+
HttpOnly
+
SameSite
+
authorization
```

---

## 30. CSRF ne zamenjuje authorization

User može imati potpuno validan CSRF token i pokušati:

```text
cancel tuđeg booking-a
```

Token samo potvrđuje:

```text
request pripada legitimnom session flow-u
```

Ne potvrđuje:

```text
user ima pravo nad resource-om
```

Dakle:

```text
CSRF
≠ authorization
```

Za booking:

```text
valid CSRF
+
authenticated user
+
ownership/policy check
```

svi su potrebni.

---

## 31. Failure response

Ako CSRF token nije validan, najčešće želimo:

```text
403 Forbidden
```

ili framework-specific:

```text
419 / session expired style response
```

zavisno od application contract-a.

U Vanilla PHP-u možeš imati:

```php
throw new CsrfTokenMismatchException();
```

a global handler ili middleware mapira u:

```text
403
```

Bitno:

```text
invalid CSRF
≠ 500
```

To nije server crash.

---

## 32. Nemoj logovati token

CSRF token je security-sensitive vrednost.

Ne radi:

```php
$logger->warning(
    'CSRF mismatch',
    [
        'expected' => $sessionToken,
        'received' => $requestToken,
    ]
);
```

Bolje:

```php
$logger->warning(
    'CSRF validation failed.',
    [
        'user_id' => $auth->id(),
        'request_id' => $requestId,
        'path' => $request->path(),
    ]
);
```

Logujemo događaj.

Ne secret/token vrednost.

---

## 33. Kompletan Vanilla PHP flow

Request:

```text
POST /bookings/42/cancel
```

Browser šalje:

```text
session cookie
+
_token
```

Middleware:

```text
method state-changing?
↓
DA
↓
session token postoji?
↓
request token postoji?
↓
hash_equals?
├── NE → reject 403
└── DA
    ↓
    Controller
```

Controller zatim još proverava:

```text
authenticated?
booking exists?
owner/admin?
booking cancellable?
```

CSRF je samo jedan sloj.

---

## 34. Laravel paralela

Laravel web middleware group već ima CSRF zaštitu.

Blade forma:

```blade
<form method="POST">
    @csrf

    ...
</form>
```

`@csrf` generiše hidden token field.

Konceptualno:

```html
<input
    type="hidden"
    name="_token"
    value="..."
>
```

Laravel zatim middleware proverava token pre Controller-a.

Za AJAX može koristiti:

```text
X-CSRF-TOKEN
```

header.

Dakle ono što ručno gradimo u Vanilla PHP-u:

```text
Session
↓
token
↓
hidden input/header
↓
middleware validation
↓
403/reject
```

Laravel već pruža kao infrastrukturu.

# Najvažnije za zapamtiti

CSRF znači:

```text
attacker
↓
koristi browser žrtve
↓
browser automatski šalje auth cookie
↓
server vidi authenticated request
↓
ali user ga nije namerno pokrenuo
```

Authentication sama nije dovoljna.

Cookie govori:

```text
koji session?
```

CSRF token daje dodatni dokaz:

```text
request je prošao kroz
legitiman application context
```

Tipičan token:

```php
bin2hex(
    random_bytes(32)
);
```

Čuvamo ga u session-u.

Form:

```text
_token
```

Server poredi:

```php
hash_equals(
    $sessionToken,
    $requestToken
);
```

CSRF posebno štitimo na:

```text
POST
PUT
PATCH
DELETE
```

GET ne treba da menja stanje.

Dobar flow:

```text
session cookie
+
CSRF token
+
authentication
+
authorization
+
business validation
```

SameSite:

```text
dodatna browser zaštita
```

ali nije jedina zaštita.

CORS:

```text
nije CSRF zaštita
```

CSRF token:

```text
ne rešava XSS
```

i:

```text
ne rešava authorization
```

Ne loguj token vrednosti.

Centralni mentalni model:

```text
SESSION
→ Ko je user?

CSRF
→ Da li je request legitiman
  u okviru te session?

AUTHORIZATION
→ Da li taj user sme
  baš ovu operaciju nad ovim resource-om?
```

Ako samo jednu rečenicu zapamtiš:

> **CSRF postoji zato što browser automatski šalje credentials; token dodaje dokaz koji attacker-ov cross-site request ne bi trebalo da poseduje.**
