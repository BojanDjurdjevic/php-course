# 8. Secure File Uploads — Part 1

## 1. Zašto su file upload-i posebno rizični

Kod običnog text input-a user šalje:

```text
string
number
date
```

Kod upload-a user šalje:

```text
ceo fajl
```

koji može biti:

```text
slika
PDF
HTML
JavaScript
PHP script
ogroman fajl
malformed fajl
polyglot fajl
malware
```

Zato upload predstavlja posebno veliku trust boundary.

Mentalno:

```text
Untrusted file
↓
validation
↓
type verification
↓
size limits
↓
safe filename
↓
safe storage
↓
controlled serving
```

---

## 2. HTML `accept` nije security

Frontend:

```html
<input
    type="file"
    name="photo"
    accept=".jpg,.jpeg,.png"
>
```

ovo je samo:

```text
browser UX hint
```

User i dalje može poslati:

```text
PHP file
HTML file
random binary data
```

direktno preko:

```text
curl
Postman
custom request
```

Dakle:

```text
accept=".jpg"
≠ backend validation
```

---

## 3. `$_FILES`

PHP upload tipično dolazi kroz:

```php
$_FILES['photo']
```

sa podacima poput:

```php
[
    'name' => 'image.jpg',
    'type' => 'image/jpeg',
    'tmp_name' => '/tmp/php123',
    'error' => UPLOAD_ERR_OK,
    'size' => 154321,
]
```

Važno:

```text
name
type
size
```

delimično dolaze iz client-controlled request context-a.

Posebno:

```text
$_FILES['photo']['type']
```

nije pouzdan security dokaz.

---

## 4. Prvo proveri upload error

Pre svega:

```php
$file = $_FILES['photo'] ?? null;

if ($file === null) {
    throw new ValidationException(
        'File is required.'
    );
}
```

zatim:

```php
if (
    $file['error']
    !== UPLOAD_ERR_OK
) {
    throw new UploadException();
}
```

PHP upload error može značiti:

```text
UPLOAD_ERR_INI_SIZE
UPLOAD_ERR_FORM_SIZE
UPLOAD_ERR_PARTIAL
UPLOAD_ERR_NO_FILE
UPLOAD_ERR_NO_TMP_DIR
UPLOAD_ERR_CANT_WRITE
UPLOAD_ERR_EXTENSION
```

Ne želimo pokušavati da obrađujemo upload koji već nije uspešno završen.

---

## 5. `UPLOAD_ERR_NO_FILE` nije isto što i server failure

Ako je file optional:

```text
UPLOAD_ERR_NO_FILE
```

može biti normalan application scenario.

Na primer:

```php
if (
    $file['error']
    === UPLOAD_ERR_NO_FILE
) {
    return null;
}
```

Ali:

```text
UPLOAD_ERR_CANT_WRITE
```

je druga vrsta problema.

To može predstavljati:

```text
filesystem/server failure
```

Dakle i upload errors treba semantički razlikovati.

---

## 6. Provera size-a

Nikad ne prihvataj unlimited upload.

Na primer:

```php
$maxBytes = 5 * 1024 * 1024;

if ($file['size'] > $maxBytes) {
    throw new ValidationException(
        'File is too large.'
    );
}
```

Zašto size limit?

Zbog:

```text
storage abuse
memory/resource pressure
DoS rizika
business pravila
```

Frontend:

```html
<input type="hidden" name="MAX_FILE_SIZE">
```

nije dovoljna zaštita.

Server-side limit je autoritet.

---

## 7. PHP server limits

PHP ima konfiguracije kao:

```text
upload_max_filesize
post_max_size
```

One ograničavaju request pre nego što application code uopšte dobije fajl.

To je:

```text
defense in depth
```

Na primer:

```text
web server / PHP limit
+
application-level limit
```

Ako application dozvoljava:

```text
5 MB
```

nema smisla da PHP dozvoli:

```text
2 GB
```

ako to aplikaciji nikad ne treba.

---

## 8. Original filename nije trusted

Client može poslati:

```text
../../shell.php
```

ili:

```text
invoice.php.jpg
```

ili:

```text
photo.jpg.php
```

ili veoma dugačak/neobičan filename.

Zato:

```php
$file['name']
```

ne treba koristiti direktno kao server filename.

Posebno ne:

```php
move_uploaded_file(
    $file['tmp_name'],
    '/uploads/' . $file['name']
);
```

---

## 9. Random server filename

Bolji model:

```php
$filename =
    bin2hex(
        random_bytes(16)
    );
```

pa dodamo extension koji smo **mi odredili na osnovu validated type-a**.

Na primer:

```text
8f1d6a...c9.jpg
```

Prednosti:

```text
nema path traversal-a
nema collision-a
nema attacker-controlled executable imena
nema oslanjanja na originalni filename
```

Originalno ime možemo eventualno čuvati kao metadata za prikaz.

Ne kao storage path.

---

## 10. Ekstenzija nije dokaz tipa

Fajl:

```text
shell.php.jpg
```

i dalje može sadržati PHP kod.

Ekstenzija:

```text
.jpg
```

govori samo kako se fajl zove.

Ne šta stvarno jeste.

Zato:

```text
extension
≠ trusted MIME/type verification
```

---

## 11. `$_FILES['type']` nije pouzdan

Client može poslati:

```text
Content-Type: image/jpeg
```

iako body nije JPEG.

Zato:

```php
$file['type']
```

koristimo najviše kao pomoćni podatak.

Ne kao security decision.

---

## 12. `finfo`

PHP može analizirati sadržaj fajla:

```php
$finfo = new finfo(
    FILEINFO_MIME_TYPE
);

$mime = $finfo->file(
    $file['tmp_name']
);
```

Na primer:

```text
image/jpeg
image/png
application/pdf
```

To je mnogo pouzdanije nego client-provided MIME.

Ali ni MIME detection nije magično savršena zaštita.

To je jedan sloj.

---

## 13. MIME allowlist

Ako dozvoljavamo samo slike:

```php
$allowed = [
    'image/jpeg' => 'jpg',
    'image/png' => 'png',
    'image/webp' => 'webp',
];
```

zatim:

```php
if (!isset($allowed[$mime])) {
    throw new ValidationException(
        'Unsupported file type.'
    );
}
```

Extension biramo iz trusted mapping-a:

```php
$extension = $allowed[$mime];
```

Ne iz originalnog filename-a.

---

## 14. Zašto mapping MIME → extension

Loše:

```php
$extension = pathinfo(
    $file['name'],
    PATHINFO_EXTENSION
);
```

Bolje:

```php
$extension = $allowed[$mime];
```

Mentalno:

```text
client filename
→ untrusted metadata

verified MIME
→ application mapping
→ trusted extension
```

Isti princip kao dynamic SQL allowlist.

---

## 15. Image validation može ići dalje od MIME-a

Ako očekujemo sliku, možemo pokušati da je stvarno parsiramo.

Na primer:

```php
$info = getimagesize(
    $file['tmp_name']
);

if ($info === false) {
    throw new ValidationException(
        'Invalid image.'
    );
}
```

Ovim dobijamo dodatni signal:

```text
fajl se ponaša kao image format
```

Ali ni to nije univerzalna malware analiza.

To je samo dodatna validacija.

---

## 16. Image dimensions

Možemo ograničiti:

```text
width
height
```

Na primer:

```php
[$width, $height] =
    getimagesize(
        $file['tmp_name']
    );

if (
    $width > 6000
    || $height > 6000
) {
    throw new ValidationException(
        'Image dimensions are too large.'
    );
}
```

Zašto?

Velike slike mogu izazvati:

```text
memory pressure
image processing DoS
storage problems
```

Posebno kada ih kasnije resize-ujemo.

---

## 17. Decompression bomb mentalni model

Fajl može biti relativno mali na disku, ali veoma skup za obradu.

Na primer velika compressed image može zahtevati mnogo memorije kada se decode-uje.

Dakle:

```text
file size
≠ jedini resource limit
```

Kod image processing-a gledamo i:

```text
dimensions
pixel count
processing limits
```

---

## 18. Temporary upload file

PHP čuva upload prvo u temporary location:

```php
$file['tmp_name']
```

To nije final storage.

Treba proveriti da stvarno dolazi iz PHP upload mehanizma:

```php
if (!is_uploaded_file(
    $file['tmp_name']
)) {
    throw new UploadException();
}
```

Ovo pomaže da ne tretiramo arbitrary local path kao legitiman HTTP upload.

---

## 19. `move_uploaded_file()`

Za final move koristimo:

```php
move_uploaded_file(
    $file['tmp_name'],
    $destination
);
```

Umesto generičkog:

```php
rename(...)
```

za upload flow.

Zašto?

`move_uploaded_file()` proverava da source zaista potiče iz PHP HTTP upload mehanizma.

Primer:

```php
if (!move_uploaded_file(
    $file['tmp_name'],
    $destination
)) {
    throw new UploadException(
        'Unable to store file.'
    );
}
```

---

## 20. Storage path ne treba da dolazi od user-a

Loše:

```php
$folder = $_POST['folder'];

$destination =
    '/uploads/' . $folder . '/' . $filename;
```

To otvara vrata:

```text
path traversal
arbitrary filesystem write
```

Storage root treba da definiše aplikacija:

```php
$uploadDir =
    dirname(__DIR__)
    . '/storage/uploads';
```

a user input nikada direktno ne određuje filesystem path.

# 8. Secure File Uploads — Part 2

## 21. Najbezbednije: storage van public web root-a

Ako fajl čuvamo direktno u:

```text
public/uploads
```

web server ga može direktno servirati.

Ako slučajno dozvolimo:

```text
shell.php
```

i server izvršava PHP u tom folderu, posledice mogu biti katastrofalne.

Bolji model:

```text
project/
├── public/
│   └── index.php
│
└── storage/
    └── uploads/
```

Fajl nije direktno dostupan kao:

```text
https://example.com/uploads/...
```

Aplikacija kontroliše kako se servira.

---

## 22. Zašto storage van `public/` pomaže

Ako upload sadrži:

```php
<?php
system($_GET['cmd']);
```

ali je sačuvan van public web root-a:

```text
storage/uploads/random.bin
```

web server ga normalno neće izvršavati preko URL-a.

To je ogromna zaštita.

Mentalno:

```text
uploaded file
→ data

ne:
uploaded file
→ server executable code
```

---

## 23. Ako moraš čuvati u public folder-u

Nekad hosting ili architecture zahtevaju:

```text
public/uploads
```

Tada moraš dodatno osigurati da:

```text
PHP execution bude disabled
```

u tom direktorijumu.

I dalje:

```text
strict MIME allowlist
random filename
no user-controlled extension
```

Ali generalni princip ostaje:

> Ako browser treba samo da preuzme/prikaže fajl, nema razloga da server sme da ga izvršava kao PHP.

---

## 24. Controlled file serving

Ako file čuvamo private:

```text
storage/uploads/...
```

download endpoint može:

```text
1. authenticate
2. authorize
3. resolve trusted path
4. set Content-Type
5. stream file
```

Na primer:

```php
$document =
    $documents->findById($id);

if ($document === null) {
    throw new NotFoundException();
}

$policy->authorizeView(
    $auth->user(),
    $document
);

readfile(
    $document->storagePath()
);
```

To sprečava file download IDOR.

---

## 25. Original filename može biti output XSS problem

Pretpostavimo originalno ime:

```text
"><script>alert(1)</script>.jpg
```

Ako ga kasnije prikažemo:

```php
echo $file->originalName();
```

možemo napraviti XSS.

Dakle čak i filename metadata mora biti:

```php
<?= e(
    $file->originalName()
) ?>
```

Opet:

```text
file metadata
≠ trusted
```

---

## 26. Content-Disposition filename

Ako file download koristi:

```http
Content-Disposition:
attachment; filename="..."
```

ne treba nekontrolisano ubaciti attacker filename.

Bolje koristiti:

```text
validated/safe filename
```

ili framework/helper koji pravilno encode-uje header vrednost.

Jer HTTP headers imaju svoj output context.

---

## 27. File permissions

Stored upload ne treba nepotrebno da bude:

```text
world-writable
executable
```

Princip:

```text
minimum required filesystem permissions
```

Na primer application process treba da može:

```text
write upload directory
read files
```

ali ne mora nužno da može:

```text
execute files
menja ostatak sistema
```

Least privilege opet važi.

---

## 28. Duplicate filenames

Ako koristimo originalna imena:

```text
photo.jpg
```

dva user-a mogu overwrite-ovati isti fajl.

Random filename:

```php
bin2hex(
    random_bytes(16)
)
```

praktično eliminiše collision problem.

Možemo još dodati database unique constraint na stored key ako je potrebno.

---

## 29. Ne koristi user ID kao jedinu "tajnost"

Na primer:

```text
/uploads/17/passport.pdf
```

nije access control.

Attacker može pogoditi:

```text
/uploads/18/passport.pdf
```

Authorization mora biti server-side.

Path obscurity nije zaštita.

---

## 30. File upload i IDOR

User A uploaduje:

```text
document id = 100
```

User B proba:

```text
GET /documents/100/download
```

Ako endpoint samo pronađe fajl po ID-u i pošalje ga:

```text
IDOR
```

Zato:

```text
upload security
+
download authorization
```

moraju biti deo istog lifecycle-a.

---

## 31. Delete file flow

Ako brišemo upload:

```text
DELETE /documents/42
```

moramo proveriti:

```text
authenticated?
authorized?
document exists?
storage path trusted?
```

Nikad:

```php
unlink(
    $_POST['path']
);
```

Jer client ne treba da kontroliše arbitrary filesystem path.

---

## 32. Ne čuvaj absolute path iz request-a

Loše:

```text
path=/var/www/app/storage/users/17/file.pdf
```

Bolje DB čuva application-controlled key:

```text
uploads/ab/cd/random-id.pdf
```

ili samo:

```text
random-id.pdf
```

a storage service zna root directory.

Mentalno:

```text
DB/user-facing identifier
→ logical storage key

filesystem root
→ server-controlled configuration
```

## 33. Antivirus / malware scanning

Za običnu malu aplikaciju možda nećeš odmah imati antivirus pipeline.

Ali za sisteme gde user uploaduje:

```text
documents
archives
office files
executables
```

može biti smisleno imati:

```text
malware scanning
quarantine
async scanning
```

Važno je razumeti:

```text
MIME valid
≠ malware-free
```

MIME samo govori format.

Ne sadržajnu bezbednost.

## 34. Re-encoding images

Jedna dodatna zaštita kod image-only sistema može biti:

```text
decode image
↓
re-encode image
↓
store new generated image
```

Na primer GD/Imagick učita JPEG i napravi novi JPEG.

Time se često uklanja veliki deo originalne file strukture/metadata.

Ali image processing library takođe mora biti bezbedno održavana i limitirana.

Dakle:

```text
re-encoding
→ defense in depth

ne:
re-encoding
→ apsolutna garancija
```

## 35. EXIF metadata

Slika može sadržati metadata poput:

```text
camera
GPS
timestamp
device info
```

Ako aplikacija redistribuira slike, ponekad je poželjno ukloniti metadata zbog privacy razloga.

Security nije samo:

```text
remote code execution
```

nego i:

```text
information disclosure
```

## 36. ZIP/archive upload-i su posebna kategorija

Ako uploadujemo ZIP i server ga raspakuje, pojavljuju se dodatni rizici:

```text
zip slip/path traversal
zip bombs
ogroman broj fajlova
nested archives
```

Nikad ne treba:

```text
extract archive blindly
```

u arbitrary filesystem directory.

Archive processing zahteva poseban security model.

## 38. Primer safe image upload flow-a

Konceptualno:

```php
$file = $_FILES['photo']
    ?? null;

if ($file === null) {
    throw new ValidationException();
}

if (
    $file['error']
    !== UPLOAD_ERR_OK
) {
    throw new UploadException();
}

if ($file['size'] > 5 * 1024 * 1024) {
    throw new ValidationException();
}

if (!is_uploaded_file(
    $file['tmp_name']
)) {
    throw new UploadException();
}

$finfo = new finfo(
    FILEINFO_MIME_TYPE
);

$mime = $finfo->file(
    $file['tmp_name']
);

$allowed = [
    'image/jpeg' => 'jpg',
    'image/png' => 'png',
    'image/webp' => 'webp',
];

if (!isset($allowed[$mime])) {
    throw new ValidationException();
}

if (
    getimagesize(
        $file['tmp_name']
    ) === false
) {
    throw new ValidationException();
}

$filename =
    bin2hex(
        random_bytes(16)
    )
    . '.'
    . $allowed[$mime];

$destination =
    $storageRoot
    . '/'
    . $filename;

if (!move_uploaded_file(
    $file['tmp_name'],
    $destination
)) {
    throw new UploadException();
}
```

Ovo nije jedina moguća implementacija.

Bitna je sekvenca zaštita.

## 39. Error handling i cleanup

Ako:

```text
file uspešno move-ujemo
```

a zatim DB insert metadata padne:

```text
orphan file
```

Ako prvo insertujemo DB pa file move padne:

```text
orphan DB row
```

Zato upload use case treba da razmišlja o consistency strategiji.

Na primer:

```text
store file
↓
insert metadata
↓
ako DB fail:
delete file
```

ili drugačiji workflow.

Filesystem i DB ne dele običnu atomic transaction.

Zato rollback mora biti application-level cleanup.

## 40. Complete upload mental model

Request:

```text
multipart/form-data
↓
PHP upload handling
↓
UPLOAD_ERR_OK?
↓
size valid?
↓
real HTTP upload?
↓
detect MIME from content
↓
allowed MIME?
↓
optional parser-specific validation
↓
generate random server filename
↓
trusted storage root
↓
move_uploaded_file()
↓
persist metadata
↓
authorized serving/download
```

Nigde u ovom toku:

```text
original filename
client MIME
HTML accept
```

nisu security authority.

# Najvažnije za zapamtiti

File upload je:

```text
untrusted binary input
```

Frontend:

```text
accept=".jpg"
```

je UX.

Ne security.

Ne veruj:

```text
original filename
client-provided MIME
extension
```

kao jedinom dokazu.

Proveri:

```text
UPLOAD_ERR
size
is_uploaded_file()
server-side MIME detection
format-specific validation
```

Za filename:

```text
random_bytes()
```

i application-controlled extension.

Bolje:

```text
verified MIME
↓
trusted mapping
↓
.jpg / .png / .webp
```

nego:

```text
original filename
↓
extension
```

Čuvaj upload:

```text
van public web root-a
```

kad god možeš.

Uploaded file treba da ostane:

```text
DATA
```

nikad:

```text
EXECUTABLE SERVER CODE
```

Download zahteva:

```text
authentication
+
authorization
```

Obscure path nije access control.

Nemoj da client kontroliše:

```text
filesystem path
storage directory
final filename
```

MIME-valid:

```text
≠ malware-free
```

DB i filesystem nisu jedna transaction.

Zato failure može zahtevati:

```text
application cleanup
```

Centralni mentalni model:

```text
CLIENT FILE
↓
NE VERUJ metadata

VERIFY
↓
error
size
type
format

CONTROL
↓
filename
path
permissions

STORE
↓
prefer private

SERVE
↓
authenticate + authorize
```

Ako samo jednu rečenicu zapamtiš:

> **Kod file upload-a client sme da pošalje sadržaj, ali server mora da odluči šta je taj sadržaj, kako se zove, gde se čuva i ko sme kasnije da mu pristupi.**
