## 11. Validation boundary

Controller/request layer dobije:

```text
untrusted input
```

i pretvara ga u:

```text
validated application data
```

Primer:

```text
POST /bookings
```

Client šalje:

```json
{
    "room_id": "12",
    "check_in": "2027-07-10",
    "check_out": "2027-07-15",
    "guests": "2",
    "user_id": "999",
    "status": "confirmed"
}
```

Application ne treba slepo da prihvati sve.

Request DTO uzima samo:

```text
room_id
check_in
check_out
guests
```

Ignoriše ili reject-uje:

```text
user_id
status
```

jer client ne sme da kontroliše te vrednosti.

## 14. Authorization pre action-a

Za postojeći resource:

```text
POST /bookings/42/cancel
```

tok:

```text
load booking
↓
exists?
↓
authorize current user
↓
business rule
↓
execute
```

Na primer:

```php
$booking =
    $bookings->findById($bookingId);

if ($booking === null) {
    throw new BookingNotFoundException();
}

if (
    !$bookingPolicy->cancel(
        $currentUser,
        $booking
    )
) {
    throw new AuthorizationException();
}
```

Tek tada:

```php
$bookingService->cancel(
    $booking
);
```

## 15. Authorization nije business validation

Policy kaže:

```text
WHO MAY TRY?
```

Service/domain kaže:

```text
IS IT VALID NOW?
```

Primer:

User jeste owner.

Dakle:

```text
authorization
→ PASS
```

Ali booking je već:

```text
completed
```

pa:

```text
business rule
→ FAIL
```

Mogući exception:

```php
BookingCannotBeCancelledException
```

Ne:

```text
403 Forbidden
```

jer user možda ima permission, ali operation više nije poslovno dozvoljen.

## 16. Service čuva invariant

Booking Service može raditi:

```text
begin transaction
↓
SELECT ... FOR UPDATE
↓
proveri current inventory
↓
proveri booking state
↓
update booking
↓
update inventory
↓
commit
```

Ako bilo šta pukne:

```text
rollback
```

Security i correctness se ovde spajaju.

Attacker može pokušati:

```text
parallel request
double cancel
double booking
```

Zato:

```text
concurrency safety
```

može biti security relevantna.

## 17. Repository security

Repository koristi:

```text
prepared statements
```

za values.

Na primer:

```php
$stmt = $pdo->prepare(
    'SELECT *
     FROM bookings
     WHERE id = :id'
);

$stmt->execute([
    'id' => $id,
]);
```

Ako SQL structure mora biti dynamic:

```text
ORDER BY
column
direction
```

koristimo:

```text
trusted application mapping
```

Ne arbitrary user string.

Mentalno:

```text
VALUES
→ bind

STRUCTURE
→ allowlist
```

## 18. Scoped queries mogu pomoći authorization-u

Za current-user booking:

```sql
SELECT *
FROM bookings
WHERE id = :booking_id
  AND user_id = :user_id
LIMIT 1
```

ili:

```php
$booking =
    $repository->findForUser(
        $bookingId,
        $auth->id()
    );
```

Time ownership postaje deo query scope-a.

Za kompleksnije politike i dalje možemo imati:

```text
Policy
```

Oba pristupa mogu sarađivati.

```text

→ MOŽE LI?

Repository
```

Ako samo jednu ideju zapamtiš:

> **Validan request nije automatski autorizovan, autorizovan request nije automatski business-validan, a business-validna operacija nije automatski concurrency-safe.**

# Security pitanja koja postavljaš za svaki feature

Kada praviš novi feature, prođi mentalno kroz:

```text
1. Ko kontroliše input?

2. Šta tačno dozvoljavam?

3. Da li treba normalization?

4. Da li postoji allowlist?

5. Ko je current user?

6. Da li sme ovu akciju?

7. Da li sme baš ovaj resource?

8. Da li client pokušava da kontroliše
   nešto što server treba da kontroliše?

9. Da li query koristi binding?

10. Da li postoji dynamic SQL structure?

11. Da li postoji filesystem/network/shell sink?

12. Da li state-changing request ima CSRF?

13. Da li endpoint može biti abused?

14. Da li concurrency može prekršiti invariant?

15. Šta user vidi kada nešto pukne?

16. Šta logujemo?

17. Da li log sadrži secret?

18. Kako se output escape-uje?

19. Koji production permissions su potrebni?

20. Kako invalidiramo credential ako procure?
```

Ako na ova pitanja imaš jasan odgovor, već razmišljaš mnogo bliže ozbiljnom backend developer-u nego developer-u koji samo pokušava:

```text
"da request proradi"
```

# Najvažnije za zapamtiti

Security nije:

```text
CSRF token
prepared statement
htmlspecialchars
Secure cookie
```

pojedinačno.

Security je sistem nezavisnih granica:

```text
TRANSPORT
→ HTTPS

INPUT
→ validation

IDENTITY
→ authentication

PERMISSION
→ authorization

INTENT
→ CSRF

ABUSE
→ rate limiting

DATABASE
→ binding + constraints

FILES
→ controlled storage

OUTPUT
→ context-aware escaping

BROWSER
→ security headers

PRODUCTION
→ secrets + permissions + dependencies

FAILURE
→ safe errors + secure logging
```

Jedan sloj ne zamenjuje drugi.

```text
Prepared statement
≠ authorization

CSRF
≠ XSS protection

CORS
≠ authentication

HTTPS
≠ secure application

Validation
≠ authorization

Authentication
≠ permission

UUID
≠ access control

.env
≠ secret management
```

Najvažniji security mentalni model celog modula:

```text
UNTRUSTED
↓
CROSSING A BOUNDARY
↓
ASK:
Who controls this?
What is allowed?
What authority does it carry?
Where is it going?
What happens if it is malicious?
↓
APPLY THE PROTECTION
FOR THAT SPECIFIC BOUNDARY
```

I konačno:

> **Nikada ne pokušavaj da napraviš podatak „bezbednim zauvek“. Bezbednost uvek zavisi od toga ko ga kontroliše, u kom context-u ga koristiš i koju privilegiju ta operacija ima.**
