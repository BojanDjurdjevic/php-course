# 5. Exception Chaining & Preserving Context — Part 1

## 1. Problem: novi exception može sakriti pravi uzrok

Pretpostavimo da repository dobije `PDOException`:

```php
try {
    $statement->execute();
} catch (\PDOException $e) {
    throw new RuntimeException(
        'Unable to create user.'
    );
}
```

Na prvi pogled ovo izgleda dobro.

Niži sloj je dobio:

```text
PDOException
```

a viši sloj sada dobija razumljiviji:

```text
RuntimeException
```

Ali napravili smo problem:

```text
originalni PDOException
→ izgubljen iz exception chain-a
```

Kasnije vidimo samo:

```text
Unable to create user.
```

a možda nam za debugging treba pravi uzrok:

```text
SQLSTATE[23000]
Duplicate entry
Connection refused
Foreign key violation
```

Zato želimo da novi exception sačuva originalni.

---

## 2. `previous` exception

PHP `Exception` constructor tipično podržava:

```php
new Exception(
    message: '...',
    code: 0,
    previous: $previousException
);
```

Na primer:

```php
try {
    $statement->execute();
} catch (\PDOException $e) {
    throw new RuntimeException(
        'Unable to create user.',
        0,
        $e
    );
}
```

Sada imamo:

```text
RuntimeException
│
└── previous
    └── PDOException
```

Viši sloj vidi smislen application-level problem:

```text
Unable to create user.
```

ali debugging infrastruktura i dalje može pronaći:

```text
originalni PDOException
```

preko:

```php
$exception->getPrevious();
```

## 3. Exception chaining

Ovaj obrazac zovemo:

```text
exception chaining
```

Primer:

```text
PDOException
↓
wrapped by
↓
UserPersistenceException
↓
wrapped by
↓
RegistrationException
```

Mentalno:

```text
high-level meaning
↓
RegistrationException

previous
↓
UserPersistenceException

previous
↓
PDOException

previous
↓
null
```

Na taj način svaki sloj može dodati svoje značenje, a da se originalni uzrok ne izgubi.

To je kao lanac uzroka:

```text
Registration failed

WHY?
↓
User could not be persisted

WHY?
↓
Database rejected INSERT
```

## 4. Wrapping vs rethrow

Važno je razlikovati:

### Rethrow

```php
catch (\PDOException $e) {
    throw $e;
}
```

To znači:

```text
isti exception
isti objekat
isti tip
isti originalni kontekst
```

### Wrapping

```php
catch (\PDOException $e) {
    throw new UserPersistenceException(
        'Unable to persist user.',
        0,
        $e
    );
}
```

To znači:

```text
pravimo novi exception
+
originalni ostaje kao previous
```

Mentalno:

```text
RETHROW
→ isti problem ide dalje

WRAP
→ isti uzrok dobija novo značenje
  za viši sloj
```

---

## 5. Kada wrapping ima smisla

Wrapping ima smisla kada prelazimo granicu između različitih nivoa apstrakcije.

Na primer:

```text
PDO
→ Repository
```

PDO govori jezikom:

```text
SQLSTATE
constraint
connection
driver
```

Repository / application želi jezik:

```text
duplicate email
user persistence failed
```

Primer:

```php
try {
    $statement->execute();
} catch (\PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            'Email already taken.',
            0,
            $e
        );
    }

    throw new UserPersistenceException(
        'Unable to create user.',
        0,
        $e
    );
}
```

Sada viši sloj ne mora da zna:

```text
MySQL
PDO
SQLSTATE
```

ali originalni infrastructure detalji nisu nestali.

---

## 6. Kada wrapping nema smisla

Loše:

```php
try {
    $service->execute();
} catch (\RuntimeException $e) {
    throw new RuntimeException(
        $e->getMessage(),
        0,
        $e
    );
}
```

Ovde nismo dodali nikakvo novo značenje.

Imamo samo:

```text
RuntimeException
↓
RuntimeException
```

bez korisne promene apstrakcije.

Još gore:

```text
ControllerException
↓
ServiceException
↓
RepositoryException
↓
RuntimeException
↓
PDOException
```

ako svaki sloj automatski wrap-uje sve što primi.

To stvara:

```text
exception lasagna
```

mnogo slojeva, malo dodatne vrednosti.

Pravilo:

> Wrap samo kada novi exception stvarno predstavlja smisleniji nivo apstrakcije ili dodaje koristan kontekst.

---

## 7. Custom exception sa `previous`

Na primer:

```php
final class UserPersistenceException
    extends \RuntimeException
{
}
```

Možemo ga koristiti:

```php
try {
    $statement->execute();
} catch (\PDOException $e) {
    throw new UserPersistenceException(
        'Unable to persist user.',
        0,
        $e
    );
}
```

Pošto `RuntimeException` već podržava standardni exception constructor, često ne moramo pisati sopstveni constructor.

Ali možemo, ako želimo bolji semantic API.

Na primer:

```php
final class DuplicateEmailException
    extends \DomainException
{
    public function __construct(
        string $email,
        ?\Throwable $previous = null
    ) {
        parent::__construct(
            "Email {$email} is already taken.",
            0,
            $previous
        );
    }
}
```

Onda:

```php
throw new DuplicateEmailException(
    $email,
    $e
);
```

To već veoma lepo izražava nameru.

---

## 8. `getPrevious()`

Ako imamo:

```php
try {
    ...
} catch (\PDOException $e) {
    throw new UserPersistenceException(
        'Unable to create user.',
        0,
        $e
    );
}
```

kasnije:

```php
catch (UserPersistenceException $e) {
    $previous = $e->getPrevious();
}
```

`$previous` može biti:

```text
PDOException
```

Ako nema previous exception-a:

```php
$e->getPrevious();
```

vraća:

```text
null
```

Možemo čak prolaziti kroz ceo chain:

```php
$current = $e;

while ($current !== null) {
    echo $current::class;
    echo $current->getMessage();

    $current = $current->getPrevious();
}
```

Mentalno:

```text
current exception
↓
previous
↓
previous
↓
previous
↓
null
```

---

## 9. Message nije isto što i debugging context

Pretpostavimo:

```php
throw new DuplicateEmailException(
    'Email already taken.',
    0,
    $pdoException
);
```

User-facing poruka može biti:

```text
Email already taken.
```

Ali debugging context može sadržati mnogo više:

```text
DuplicateEmailException
message
file
line
stack trace

previous:
PDOException
SQLSTATE
driver message
file
line
stack trace
```

To je veoma važno.

Ne treba pokušavati da sve debugging detalje naguramo u:

```php
$e->getMessage()
```

Exception objekat već nosi mnogo više konteksta.

Zato je dobar princip:

```text
message
→ smislen opis problema

exception chain
→ tehnički uzrok

stack trace
→ kako smo stigli do problema
```

# 5. Exception Chaining & Preserving Context — Part 2

## 10. Stack trace pripada mestu gde je exception nastao

Pretpostavimo:

```php
function repository(): void
{
    throw new RuntimeException(
        'Database problem.'
    );
}

function service(): void
{
    repository();
}

function controller(): void
{
    service();
}
```

Stack trace konceptualno pokazuje:

```text
controller()
↓
service()
↓
repository()
↓
throw
```

Možemo ga dobiti:

```php
$e->getTrace();
```

ili kao string:

```php
$e->getTraceAsString();
```

To je mnogo korisnije od poruke:

```text
Database problem.
```

jer nam govori:

```text
ko je pozvao šta
kojim redosledom
iz kog fajla
sa koje linije
```

Stack trace je zato jedan od glavnih debugging alata.

---

## 11. Rethrow i originalni stack trace

Ako imamo:

```php
catch (\Throwable $e) {
    throw $e;
}
```

bacamo isti exception objekat dalje.

Originalni exception i njegovo poreklo ostaju sačuvani.

Na primer:

```text
PDO
↓
throws
↓
Repository catch
↓
rollback / cleanup
↓
throw $e
↓
Service
↓
Global handler
```

Global handler i dalje može videti gde je exception originalno nastao.

To je još jedan razlog da ne pravimo nepotrebno novi exception ako ne menjamo značenje problema.

---

## 12. Wrapping menja spoljašnji exception, ali čuva uzrok

Primer:

```php
try {
    $this->pdo->query($sql);
} catch (\PDOException $e) {
    throw new UserPersistenceException(
        'Unable to load user.',
        0,
        $e
    );
}
```

Global handler dobija:

```text
UserPersistenceException
```

To je spoljašnji exception.

Ali:

```php
$e->getPrevious();
```

daje:

```text
PDOException
```

Zato imamo dva nivoa informacije:

```text
WHAT FAILED AT APPLICATION LEVEL?
→ Unable to load user

WHY DID IT REALLY FAIL?
→ PDOException / database cause
```

To je odlična separacija.

## 13. Primer: duplicate email race condition

Ovo je savršen primer za exception chaining.

Repository:

```php
public function create(
    string $name,
    string $email,
    string $passwordHash
): User {
    try {
        $stmt = $this->pdo->prepare(
            'INSERT INTO users
             (name, email, password_hash)
             VALUES
             (:name, :email, :password_hash)'
        );

        $stmt->execute([
            'name' => $name,
            'email' => $email,
            'password_hash' => $passwordHash,
        ]);
    } catch (\PDOException $e) {
        if ($this->isDuplicateEmail($e)) {
            throw new DuplicateEmailException(
                'Email already taken.',
                0,
                $e
            );
        }

        throw $e;
    }

    return $this->findById(
        (int) $this->pdo->lastInsertId()
    );
}
```

Application vidi:

```text
DuplicateEmailException
```

ali debugging i dalje može pronaći:

```text
PDOException
↓
SQLSTATE
↓
driver information
```

Tako dobijamo oba sveta:

```text
clean architecture
+
full technical context
```

## 14. Nemoj user-u prikazivati exception chain

Veoma važno:

Exception chain je za:

```text
developer-a
logove
debugging
monitoring
```

ne za krajnjeg korisnika.

Loše:

```php
echo $e->getMessage();
echo $e->getTraceAsString();
```

u production-u.

Time možemo otkriti:

```text
filesystem paths
class names
SQL
database details
server structure
secret-like context
```

Korisnik treba da dobije kontrolisanu poruku:

```text
Something went wrong.
```

ili za očekivani problem:

```text
Email is already taken.
```

Dok log može sadržati:

```text
exception class
message
stack trace
previous exception chain
request/context identifiers
```

Security ćemo dublje raditi u sledećem modulu, ali ova granica je veoma važna.

## 15. Logovanje exception chain-a

Dobar logger često ume da primi sam exception:

```php
$logger->error(
    'Registration failed.',
    [
        'exception' => $e,
    ]
);
```

Umesto da ručno radiš:

```php
$logger->error(
    $e->getMessage()
);
```

Zašto?

Jer sam exception nosi:

```text
class
message
file
line
trace
previous
```

Logging infrastruktura može iz njega izvući daleko više.

Mentalno:

```text
ne loguj samo string
↓
loguj exception kao strukturiran context
```

## 16. Dodavanje context-a bez uništavanja uzroka

Pretpostavimo da znamo:

```text
user_id = 17
booking_id = 500
```

Ako repository padne, možda želimo dodatni kontekst.

Možemo logovati:

```php
$logger->error(
    'Booking cancellation failed.',
    [
        'user_id' => $userId,
        'booking_id' => $bookingId,
        'exception' => $e,
    ]
);
```

To je često bolje nego praviti novi exception samo da ubacimo ID u message.

Na primer, nije uvek potrebno:

```php
throw new RuntimeException(
    "Booking {$bookingId} failed for user {$userId}",
    0,
    $e
);
```

ako samo želimo debugging metadata.

Dakle:

```text
new semantic meaning
→ wrapping može imati smisla

samo additional diagnostics
→ često logging context
```

To je važna razlika.

---

## 17. Ne loguj isti exception na svakom sloju

Loš tok:

```text
Repository
→ log

Service
→ log

Controller
→ log

Global Handler
→ log
```

Rezultat:

```text
isti failure
→ 4 log entry-ja
```

To otežava debugging i pravi šum.

Bolje je definisati:

```text
jedan glavni logging boundary
```

često:

```text
Global Exception Handler
```

Lokalni sloj loguje samo kada ima specifičan razlog, na primer:

```text
retry failure
security event
external API context
special operational metadata
```

Ako lokalni sloj samo:

```php
catch (\Throwable $e) {
    $logger->error($e->getMessage());
    throw $e;
}
```

a global handler će ga svakako logovati, verovatno samo pravi duplikat.

## 18. Kako razmišljati o exception chain-u

Najkorisniji mentalni model:

```text
spoljašnji exception
→ govori VIŠEM sloju šta se dogodilo

previous exception
→ govori ZAŠTO se dogodilo

stack trace
→ govori KAKO smo stigli do mesta gde je problem nastao
```

Primer:

```text
DuplicateEmailException
→ registration ne može da nastavi

previous:
PDOException
→ database je prijavila UNIQUE violation

stack trace:
Controller
→ RegistrationService
→ PdoUserRepository
→ PDO
```

To je kompletna priča.

# Najvažnije za zapamtiti

Ako napravimo novi exception bez `previous`:

```php
throw new RuntimeException(
    'Operation failed.'
);
```

možemo izgubiti vezu sa originalnim uzrokom.

Ako menjamo nivo apstrakcije:

```php
throw new UserPersistenceException(
    'Unable to persist user.',
    0,
    $e
);
```

čuvamo:

```text
new application meaning
+
originalni technical cause
```

To je:

```text
exception chaining
```

`getPrevious()`:

```php
$e->getPrevious();
```

vraća prethodni exception ili:

```text
null
```

Rethrow:

```php
throw $e;
```

koristi isti exception.

Wrapping:

```php
throw new SomeException(
    'Higher-level meaning',
    0,
    $e
);
```

pravi novi exception i čuva originalni kao `previous`.

Wrap samo kada:

```text
novi sloj dobija smislenije značenje
```

Nemoj wrap-ovati exception samo zato što možeš.

Dobro:

```text
PDOException
↓
DuplicateEmailException
```

jer prevodimo infrastructure problem u application problem.

Loše:

```text
RuntimeException
↓
RuntimeException
↓
RuntimeException
```

bez novog značenja.

Exception chain nije user-facing sadržaj.

Production korisnik dobija:

```text
kontrolisanu poruku
```

dok logovi mogu dobiti:

```text
exception class
message
stack trace
previous chain
diagnostic context
```

Centralni mentalni model:

```text
outer exception
→ ŠTA je problem za ovaj sloj?

previous exception
→ ZAŠTO se problem desio?

stack trace
→ KAKO smo stigli do problema?
```
