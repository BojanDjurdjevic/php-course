# 2\. PHP Error Types \& `Throwable` Hierarchy

## 1\. Zašto je `Throwable` centralni pojam

U modernom PHP-u najvažniji zajednički tip za ozbiljne runtime probleme je:

``` php
Throwable
```

Mentalna hijerarhija izgleda ovako:

``` text
Throwable
├── Error
└── Exception
```

To znači:

``` php
catch (\Throwable $e)
```

može uhvatiti i:

``` text
Error
```

i:

``` text
Exception
```

To je veoma važna razlika u odnosu na starije PHP verzije i stariji mentalni model gde se mnogo runtime problema nije moglo tretirati kao objekti kroz isti exception sistem.

---

## 2\. `Throwable` je interface

`Throwable` nije obična base class.

To je interface koji implementiraju dve glavne grane:

``` text
Throwable
├── Error
└── Exception
```

Praktično:

``` php
try {
    // nešto
} catch (\Throwable $e) {
    // može dobiti Error ili Exception
}
```

Ali ne treba iz toga zaključiti:

> Onda ću svuda koristiti `catch (Throwable)`.

To bi bilo pogrešno.

`Throwable` je veoma širok tip.

Koristan je uglavnom:

``` text
na global boundary-ju
u rollback catch-u
u logging infrastrukturi
```

a ne kao default catch svuda po aplikaciji.

---

## 3\. `Exception` grana

`Exception` predstavlja klasičnu exception granu.

Osnova:

``` php
class Exception implements Throwable
```

Mnoge built-in exception klase nasleđuju `Exception`.

Na primer:

``` text
Exception
├── RuntimeException
├── LogicException
├── DomainException
├── InvalidArgumentException
└── ...
```

Takođe brojne biblioteke i framework-i imaju svoje exception klase koje indirektno završavaju pod `Exception`.

Na primer:

``` php
throw new RuntimeException(
    'Unable to read configuration file.'
);
```

ili:

``` php
throw new DomainException(
    'Booking cannot be cancelled.'
);
```

---

## 4\. `Error` grana

`Error` je druga glavna grana `Throwable` hijerarhije.

Mentalno:

``` text
Throwable
└── Error
```

Pod `Error` spadaju brojni problemi koje PHP runtime sam detektuje.

Na primer:

``` text
TypeError
ValueError
ArgumentCountError
ArithmeticError
DivisionByZeroError
AssertionError
```

i drugi.

Primer:

``` php
function greet(string $name): void
{
    echo "Hello {$name}";
}

greet([]);
```

PHP može baciti:

``` text
TypeError
```

jer array nije validan argument za očekivani `string`.

To je `Error`, ali je istovremeno i `Throwable`.

Zato:

``` php
try {
    greet([]);
} catch (\Throwable $e) {
    echo $e::class;
}
```

može uhvatiti `TypeError`.

---

## 5\. `TypeError`

`TypeError` je jedna od najvažnijih PHP runtime error klasa.

Nastaje kada je vrednost pogrešnog tipa.

Na primer:

``` php
function calculateTotal(
    int $quantity,
    float $price
): float {
    return $quantity * $price;
}

calculateTotal('five', 10.5);
```

U odgovarajućem strict typing kontekstu ovo može dati:

``` text
TypeError
```

Drugi primer:

``` php
function findUser(int $id): User
{
    return null;
}
```

Ako metoda garantuje:

``` php
: User
```

a vrati:

``` php
null
```

PHP može baciti `TypeError`.

Mentalno:

``` text
Type contract violated
→ TypeError
```

U većini aplikacija ovo je obično:

``` text
programming bug
```

a ne očekivani business problem.

---

## 6\. `ValueError`

`ValueError` je drugačiji od `TypeError`.

Tip može biti potpuno ispravan, ali konkretna vrednost nije dozvoljena.

Na primer:

``` php
array_rand([], 1);
```

ili određene built-in PHP funkcije kada prime vrednost koja je tipom validna, ali semantički neprihvatljiva.

Mentalno:

``` text
TypeError
→ pogrešan tip

ValueError
→ pravi tip, pogrešna vrednost
```

Primer konceptualno:

``` text
string ✅
ali prazna / nedozvoljena vrednost ❌
```

Važno je, međutim, ne mešati built-in `ValueError` sa našom business validation logikom.

Na primer:

``` text
password prekratak
```

ne znači automatski da treba baciti PHP `ValueError`.

To može biti sasvim druga application validation odluka.

---

## 7\. `ArgumentCountError`

Ako metoda ili funkcija zahteva argumente koje ne prosledimo pravilno, PHP može baciti:

``` text
ArgumentCountError
```

Na primer:

``` php
function createUser(
    string $name,
    string $email
): void {
}

createUser('Bojan');
```

Nedostaje:

``` text
$email
```

Rezultat može biti:

``` text
ArgumentCountError
```

I to je opet:

``` text
Error
→ Throwable
```

Tipično:

``` text
programming bug
```

---

## 8\. `DivisionByZeroError`

Primer:

``` php
$result = intdiv(10, 0);
```

može proizvesti:

``` text
DivisionByZeroError
```

To je runtime problem koji PHP detektuje.

U business aplikaciji možda nikad ne želiš da do ovoga dođeš.

Bolje je često unapred proveriti business input:

``` php
if ($count === 0) {
    // business/application handling
}
```

nego se oslanjati na:

``` text
DivisionByZeroError
```

kao normalan control flow.

---

## 9\. `LogicException`

Sada prelazimo na `Exception` granu.

`LogicException` obično signalizira:

> Program je u stanju u kom se ova operacija ne bi smela pozvati.

Primer:

``` php
final class Booking
{
    private bool $cancelled = false;

    public function cancel(): void
    {
        if ($this->cancelled) {
            throw new LogicException(
                'Booking is already cancelled.'
            );
        }

        $this->cancelled = true;
    }
}
```

Mentalno:

``` text
LogicException
→ poziv nema smisla u trenutnom programskom stanju
```

Često ukazuje na programming/design problem.

Ali u praksi granica nije uvek savršeno čista.

---

## 10\. `RuntimeException`

`RuntimeException` obično koristimo za problem koji nastane tokom izvršavanja i nije nužno mogao biti poznat unapred iz samog koda.

Na primer:

``` php
$content = file_get_contents(
    '/path/to/config.json'
);

if ($content === false) {
    throw new RuntimeException(
        'Unable to read config file.'
    );
}
```

Mentalno:

``` text
RuntimeException
→ operacija je bila legitimna
→ ali runtime uslovi su sprečili uspeh
```

Na primer:

``` text
file unavailable
external service unavailable
runtime resource problem
```

---

## 11\. `DomainException`

`DomainException` je veoma zanimljiva za application code.

Može izraziti:

> Tip i osnovni argument jesu validni, ali vrednost nije dozvoljena pravilima domena.

Na primer:

``` php
if (!$booking->canBeCancelled()) {
    throw new DomainException(
        'Booking can no longer be cancelled.'
    );
}
```

Ili možemo napraviti sopstvenu klasu:

``` php
final class BookingCannotBeCancelled
    extends DomainException
{
}
```

To je mnogo semantičkije.

Mentalno:

``` text
DomainException
→ business/domain rule violated
```

Ali ne treba svaki business problem automatski bazirati baš na `DomainException`.

Custom exceptions ćemo detaljno raditi kasnije.

---

## 12\. `InvalidArgumentException`

`InvalidArgumentException` se koristi kada pozivalac metode prosledi argument koji nije prihvatljiv prema contract-u metode.

Na primer:

``` php
function changeStatus(string $status): void
{
    $allowed = [
        'active',
        'disabled',
        'suspended',
    ];

    if (!in_array($status, $allowed, true)) {
        throw new InvalidArgumentException(
            'Invalid user status.'
        );
    }
}
```

Mentalno:

``` text
InvalidArgumentException
→ caller je prosledio argument koji metoda ne prihvata
```

Ali opet:

``` text
HTTP validation
≠ nužno InvalidArgumentException
```

Ako korisnik u formi unese loš email, to je često validation error koji rešavamo na drugom nivou.

---

## 13\. `PDOException`

`PDOException` je veoma važan za backend PHP.

Ako PDO operacija padne:

``` php
$statement->execute();
```

može biti bačen:

``` text
PDOException
```

Na primer:

``` text
database unavailable
constraint violation
SQL problem
connection error
```

Važno:

``` text
PDOException
```

je infrastructure-level problem.

Viši slojevi često ne treba da znaju za konkretni PDO detalj.

Na primer:

``` text
PdoUserRepository
↓
PDOException:
duplicate unique key
↓
mapiranje
↓
DuplicateEmailException
```

To je mnogo čistije nego da Controller proverava:

``` text
SQLSTATE
MySQL error code
```

---

## 14\. `Exception` vs `Error` — praktična razlika

Najjednostavniji mentalni model:

``` text
Exception
→ često application/library signal
```

dok:

``` text
Error
→ često PHP runtime/programming problem
```

Ali ovo nije apsolutno pravilo.

Ne treba donositi odluku samo na osnovu toga:

``` text
Error = uvek fatalno
Exception = uvek očekivano
```

To nije dovoljno precizno.

Na primer:

``` text
PDOException
```

može biti potpuno neočekivan infrastructure failure.

A:

``` text
TypeError
```

možemo tehnički uhvatiti, ali to često ne znači da treba da ga lokalno obrađujemo.

---

## 15\. Zašto ne treba svuda `catch (Throwable)`

Pogledaj:

``` php
try {
    $service->register($data);
} catch (\Throwable $e) {
    return false;
}
```

Ovim hvataš:

``` text
DuplicateEmailException
PDOException
TypeError
ArgumentCountError
ValueError
Error
```

i sve pretvaraš u:

``` text
false
```

Time brišeš veoma važne razlike između problema.

Još gore:

``` text
TypeError
```

koji možda predstavlja čist bug sada izgleda kao običan expected failure.

Zato:

``` php
catch (\Throwable $e)
```

ima smisla uglavnom kada:

``` text
moramo rollback-ovati
moramo logovati
nalazimo se na global boundary-ju
```

Na primer:

``` php
$this->pdo->beginTransaction();

try {
    $service->doWork();

    $this->pdo->commit();
} catch (\Throwable $e) {
    $this->pdo->rollBack();

    throw $e;
}
```

Ovde ne pokušavamo da odlučimo da je svaki problem isti.

Samo garantujemo:

``` text
ako bilo šta ozbiljno prekine transaction
→ rollback
→ originalni problem nastavlja dalje
```

To je odlična upotreba `Throwable`.

---

## 16\. Catch specifičnog tipa

Mnogo preciznije:

``` php
try {
    $registration->register(
        $name,
        $email,
        $password
    );
} catch (DuplicateEmailException $e) {
    // znaš tačno šta se dogodilo
}
```

Ovde catch ima smisla jer sloj zna kako da reaguje.

Možda:

``` text
DuplicateEmailException
↓
422 / validation error
↓
"Email is already taken."
```

Ali:

``` text
PDOException
```

ne treba nužno uhvatiti na istom mestu.

Može da ode dalje do global handler-a.

---

## 17\. Može li `catch (Exception)` uhvatiti `TypeError`?

Ne.

Ovo:

``` php
catch (\Exception $e)
```

hvata samo:

``` text
Exception branch
```

Ne hvata:

``` text
Error branch
```

Dakle:

``` text
TypeError
```

neće biti uhvaćen.

Za oba treba:

``` php
catch (\Throwable $e)
```

Mentalno:

``` text
Throwable
├── Error
│   └── TypeError
│
└── Exception
    └── RuntimeException
```

Ako uhvatiš:

``` php
catch (\Exception $e)
```

hvataš samo donju `Exception` granu.

---

## 18\. Može li `catch (Error)` uhvatiti `Exception`?

Takođe ne.

``` php
catch (\Error $e)
```

hvata samo `Error` granu.

Na primer:

``` text
TypeError ✅
ValueError ✅
ArgumentCountError ✅

RuntimeException ❌
DomainException ❌
PDOException ❌
```

Zato je hijerarhija važna.

---

## 19\. Stack trace i exception objekat

Kada dobiješ:

``` php
catch (\Throwable $e)
```

`$e` nosi mnogo više od message-a.

Na primer:

``` php
$e->getMessage();
$e->getCode();
$e->getFile();
$e->getLine();
$e->getTrace();
$e->getTraceAsString();
$e->getPrevious();
```

To znači da exception nije samo:

``` text
"nešto je puklo"
```

nego nosi kontekst o mestu i toku poziva.

Na primer:

``` text
Controller
↓
Service
↓
Repository
↓
PDO
↓
exception
```

stack trace može pokazati ceo put kojim je program stigao do problema.

To je jedan od najvažnijih alata za debugging.

---

## 20\. Šta treba znati napamet

Ne treba memorisati svaku PHP exception klasu.

Za backend intervju je mnogo važnije da znaš ovu mapu:

``` text
Throwable
├── Error
│   ├── TypeError
│   ├── ValueError
│   ├── ArgumentCountError
│   └── DivisionByZeroError
│
└── Exception
    ├── RuntimeException
    ├── LogicException
    │   ├── DomainException
    │   └── InvalidArgumentException
    └── PDOException
```

Napomena:

Hijerarhija built-in exception klasa ima više detalja od ove pojednostavljene mape, ali ovo je praktična mapa koju treba da razumeš.

Mnogo važnije od pamćenja stabla je da znaš:

``` text
šta znači tip problema
ko treba da ga catch-uje
da li je expected ili unexpected
da li ga treba mapirati
da li ga treba pustiti global handler-u
```

# Laravel paralela

Laravel može naići na:

``` text
TypeError
PDOException
ModelNotFoundException
AuthorizationException
ValidationException
```

Sve one na kraju prolaze kroz framework exception lifecycle.

Framework zatim može odlučiti:

``` text
logovati?
↓
renderovati?
↓
koji HTTP status?
↓
JSON ili HTML response?
```

Vanilla PHP ćemo uskoro napraviti isto:

``` text
Throwable
↓
Global Exception Handler
↓
classify
↓
log
↓
HTTP response
```

Kada to jednom napraviš ručno, Laravelov exception handling postaje mnogo transparentniji.

# Najvažnije za zapamtiti

Osnovna hijerarhija:

``` text
Throwable
├── Error
└── Exception
```

`Throwable` može predstavljati obe grane.

``` php
catch (\Throwable $e)
```

hvata:

``` text
Error
+
Exception
```

dok:

``` php
catch (\Exception $e)
```

ne hvata `TypeError` i ostale `Error` klase.

Najvažniji primeri:

``` text
TypeError
→ pogrešan tip
```

``` text
ValueError
→ tip je prihvatljiv, ali vrednost nije
```

``` text
ArgumentCountError
→ pogrešan broj argumenata
```

``` text
RuntimeException
→ runtime problem tokom legitimne operacije
```

``` text
LogicException
→ operacija nema smisla u trenutnom programskom stanju
```

``` text
DomainException
→ domain/business pravilo nije zadovoljeno
```

``` text
InvalidArgumentException
→ caller je prosledio neprihvatljiv argument
```

``` text
PDOException
→ PDO/database infrastructure problem
```

Nemoj koristiti:

``` php
catch (\Throwable $e)
```

svuda samo zato što hvata sve.

Najčešće ga koristiš:

``` text
na global boundary-ju
za rollback
za centralno logovanje
```

dok lokalno treba hvatati što specifičniji tip samo kada taj sloj stvarno zna šta sa njim treba uraditi.

Centralni mentalni model:

``` text
specific catch
→ "znam šta je ovaj problem i znam kako da reagujem"

Throwable catch
→ "moram garantovati cleanup/logging/global handling čak i ako je problem veoma širok"
```
