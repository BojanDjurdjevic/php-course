# 3. `throw`, `try`, `catch` & `finally`

## 1. Osnovni exception lifecycle

Najjednostavniji tok izgleda ovako:

```php
try {
    // kod koji može baciti exception
} catch (\RuntimeException $e) {
    // obrada problema
}
```

Mentalno:

```text
try
↓
normalan kod
↓
nešto baci exception
↓
PHP traži odgovarajući catch
↓
catch izvršava handling
```

Ako exception nije bačen:

```text
try
↓
kod se izvrši do kraja
↓
catch se preskače
↓
nastavlja se dalje
```

Ako exception jeste bačen:

```text
try
↓
throw
↓
ostatak try bloka se prekida
↓
PHP traži matching catch
```

To je najvažniji početni model.

---

## 2. `throw` prekida normalan tok

Primer:

```php
function registerUser(string $email): void
{
    if ($email === 'taken@example.com') {
        throw new DomainException(
            'Email already taken.'
        );
    }

    echo 'User created';
}
```

Poziv:

```php
registerUser('taken@example.com');
```

Tok:

```text
if uslov
↓
throw
↓
funkcija se odmah prekida
↓
echo se NE izvršava
```

Dakle:

```php
throw new DomainException(
    'Email already taken.'
);
```

nije kao:

```php
return false;
```

Kod `return`:

```text
metoda vraća normalnu vrednost
```

Kod `throw`:

```text
normalan tok je prekinut
```

---

## 3. Exception se propagira naviše

Pogledaj:

```php
function repository(): void
{
    throw new RuntimeException(
        'Database unavailable.'
    );
}

function service(): void
{
    repository();

    echo 'Service finished';
}

function controller(): void
{
    service();

    echo 'Controller finished';
}
```

Pozovemo:

```php
controller();
```

Tok:

```text
controller()
↓
service()
↓
repository()
↓
throw RuntimeException
↑
repository() se prekida
↑
service() se prekida
↑
controller() se prekida
```

Ni ovo:

```php
echo 'Service finished';
```

ni ovo:

```php
echo 'Controller finished';
```

se neće izvršiti.

Exception putuje naviše sve dok:

```text
ne pronađe odgovarajući catch
```

ili dok ne stigne do vrha aplikacije.

---

## 4. `try` ne znači "ovde rešavam problem"

Ovo je važna nijansa.

`try` samo kaže:

> U ovom bloku može nastati problem koji želim da posmatram kroz exception handling.

Na primer:

```php
try {
    $service->register($data);
}
```

To samo po sebi ništa ne rešava.

Tek `catch` određuje šta radimo sa konkretnim exception-om.

Na primer:

```php
try {
    $service->register($data);
} catch (DuplicateEmailException $e) {
    // sada konkretno obrađujemo duplicate email
}
```

---

## 5. `catch` mora odgovarati tipu exception-a

Ako bacimo:

```php
throw new DomainException(
    'Invalid operation.'
);
```

onda:

```php
catch (\DomainException $e)
```

će ga uhvatiti.

Ali i:

```php
catch (\LogicException $e)
```

može ga uhvatiti, jer `DomainException` nasleđuje `LogicException`.

I:

```php
catch (\Exception $e)
```

može ga uhvatiti.

I:

```php
catch (\Throwable $e)
```

može ga uhvatiti.

Mentalno:

```text
DomainException
↓
LogicException
↓
Exception
↓
Throwable
```

Što je `catch` viši u hijerarhiji:

```text
to je širi
```

---

## 6. Šta ako nijedan `catch` ne odgovara?

Primer:

```php
try {
    throw new TypeError(
        'Wrong type.'
    );
} catch (\Exception $e) {
    echo 'Caught';
}
```

`TypeError` ne pripada `Exception` grani.

Zato ovaj `catch` neće reagovati.

Tok:

```text
TypeError
↓
catch(Exception) ne odgovara
↓
exception nastavlja dalje
```

Ako nema višeg handler-a:

```text
request završava uncaught Throwable-om
```

Zato je bitno razumeti hijerarhiju.

---

## 7. `catch` blok može da završi problem

Primer:

```php
try {
    $registration->register(
        $name,
        $email,
        $password
    );
} catch (DuplicateEmailException $e) {
    $errors['email'] = 'Email already taken.';
}
```

Ovde smo odlučili:

```text
DuplicateEmailException
↓
poznat expected problem
↓
pretvaramo ga u validation-style error
↓
exception više ne propagira
```

Dakle `catch` je problem "potrošio".

Posle `catch` bloka tok može normalno da se nastavi.

---

## 8. `catch` ne mora da završi problem

Možemo:

```php
try {
    $service->doSomething();
} catch (\RuntimeException $e) {
    error_log($e->getMessage());

    throw $e;
}
```

Ovde:

```text
catch
↓
uradi lokalni side effect
↓
throw isti exception dalje
```

To se zove:

```text
rethrow
```

Dakle `catch` ne znači automatski:

> problem je potpuno obrađen.

Može značiti:

> uradio sam ono što pripada ovom sloju, sada problem ide dalje.

Detaljno ćemo rethrow obrađivati u sledećoj lekciji.

---

## 9. Više `catch` blokova

Možemo imati:

```php
try {
    $service->execute();
} catch (DuplicateEmailException $e) {
    // duplicate email
} catch (DomainException $e) {
    // drugi domain problem
} catch (\Throwable $e) {
    // fallback
}
```

PHP ide redom i koristi prvi `catch` koji odgovara exception tipu.

Zato redosled mora ići:

```text
specifičniji
↓
širi
↓
najširi
```

Na primer:

```php
catch (DuplicateEmailException $e)
catch (DomainException $e)
catch (\Throwable $e)
```

a ne obrnuto.

Detaljno ćemo catch order raditi u sledećoj lekciji.

---

## 10. `finally` blok

`finally` se izvršava bez obzira na to da li je exception bačen ili nije.

Primer:

```php
try {
    echo 'TRY';
} catch (\Throwable $e) {
    echo 'CATCH';
} finally {
    echo 'FINALLY';
}
```

Ako nema exception-a:

```text
TRY
FINALLY
```

Ako ima exception-a koji je uhvaćen:

```text
TRY
CATCH
FINALLY
```

Dakle:

```text
finally
→ izvršava se i na success i na failure putanji
```

---

## 11. Kada `finally` ima smisla

Najčešći mentalni model:

```text
cleanup koji mora da se desi
bez obzira na ishod
```

Na primer:

```php
$file = fopen(
    '/tmp/data.txt',
    'r'
);

try {
    // rad sa fajlom
} finally {
    if (is_resource($file)) {
        fclose($file);
    }
}
```

Bez obzira da li:

```text
operacija uspe
ili
exception prekine tok
```

resource se zatvara.

Isto može važiti za:

```text
lock release
temporary resource cleanup
external resource release
```

---

## 12. `finally` nije automatski potreban uz transaction

Početnici često napišu:

```php
$this->pdo->beginTransaction();

try {
    $service->doWork();

    $this->pdo->commit();
} catch (\Throwable $e) {
    $this->pdo->rollBack();

    throw $e;
} finally {
    // nešto
}
```

Ali ako nema konkretnog cleanup-a:

```text
finally je nepotreban
```

Transaction se normalno rešava:

```text
success
→ commit

failure
→ rollback
```

Nema pravila:

> Svaki try/catch treba finally.

Ne treba.

---

## 13. `finally` i `return`

Ovo je veoma važna nijansa.

Primer:

```php
function test(): string
{
    try {
        return 'TRY';
    } finally {
        echo 'FINALLY';
    }
}
```

Rezultat:

```text
FINALLY
```

se izvrši pre nego što funkcija zaista završi.

A return value ostaje:

```text
TRY
```

Dakle:

```text
return je pripremljen
↓
finally se izvrši
↓
funkcija se završi
```

---

## 14. Zašto je `return` unutar `finally` loša ideja

Pogledaj:

```php
function test(): string
{
    try {
        return 'TRY';
    } finally {
        return 'FINALLY';
    }
}
```

`finally` može pregaziti prethodni `return`.

Još gore:

```php
try {
    throw new RuntimeException(
        'Database failed.'
    );
} finally {
    return false;
}
```

Ovim možemo praktično sakriti exception.

To je veoma opasno.

Mentalno:

```text
exception nastao
↓
finally return
↓
exception više ne propagira kako očekujemo
```

Zato je dobra praksa:

> Nemoj koristiti `return` u `finally` bloku.

`finally` je namenjen cleanup-u, ne kontroli business flow-a.

---

## 15. `finally` i rethrow

Primer:

```php
try {
    throw new RuntimeException(
        'Something failed.'
    );
} catch (\RuntimeException $e) {
    echo 'Logging';

    throw $e;
} finally {
    echo 'Cleanup';
}
```

Tok:

```text
throw
↓
catch
↓
log
↓
rethrow
↓
finally
↓
exception nastavlja dalje
```

Dakle čak i ako catch ponovo baci exception:

```text
finally će se izvršiti pre propagacije dalje
```

To je veoma korisno za cleanup.

---

## 16. Exception prekida samo trenutni normalni put

Primer:

```php
try {
    echo 'A';

    throw new RuntimeException();

    echo 'B';
} catch (\RuntimeException $e) {
    echo 'C';
}

echo 'D';
```

Output:

```text
A
C
D
```

`B` se ne izvršava jer je posle `throw`.

Ali nakon što catch obradi exception:

```text
tok se nastavlja iza try/catch strukture
```

Zato dobijamo `D`.

Mentalno:

```text
A
↓
throw
↓
preskoči B
↓
catch C
↓
nastavi
↓
D
```

---

## 17. Exception iz `catch` bloka

I sam `catch` može baciti novi exception.

Primer:

```php
try {
    throw new PDOException(
        'Duplicate key'
    );
} catch (\PDOException $e) {
    throw new DuplicateEmailException();
}
```

Tok:

```text
PDOException
↓
catch
↓
novi DuplicateEmailException
↓
propagacija dalje
```

Ovo je osnova exception mapping-a.

Repository može reći:

```text
PDO language
↓
application language
```

Na primer:

```text
PDOException
↓
DuplicateEmailException
```

Kasnije ćemo videti kako da pri tome sačuvamo originalni exception kao `previous`.

---

## 18. Ne treba svaki `throw` okružiti `try/catch`

Primer:

```php
final class RegistrationService
{
    public function register(
        string $email
    ): void {
        if ($this->users->findByEmail($email)) {
            throw new DuplicateEmailException();
        }
    }
}
```

Ne treba odmah:

```php
try {
    throw new DuplicateEmailException();
} catch (DuplicateEmailException $e) {
    throw $e;
}
```

To nema nikakvu vrednost.

Ako trenutni sloj nema šta korisno da uradi:

```text
ne catch-uj
```

Pusti da viši sloj odluči.

---

## 19. Loš obrazac: catch pa ništa

Najgori primer:

```php
try {
    $repository->save($user);
} catch (\Throwable $e) {
}
```

Time smo:

```text
uhvatili problem
↓
sakrili problem
↓
nastavili kao da je sve dobro
```

To može izazvati ozbiljne bugove.

Na primer:

```text
save nije uspeo
↓
controller misli da jeste
↓
prikaže "Success"
```

Ovo se zove:

```text
swallowing the exception
```

i treba ga izbegavati.

---

## 20. Loš obrazac: catch samo da vrati `false`

Primer:

```php
try {
    $service->createBooking();
} catch (\Throwable $e) {
    return false;
}
```

Problem:

```text
NoAvailabilityException
PDOException
TypeError
bug
```

sve postaje:

```text
false
```

Izgubili smo značenje.

Bolje:

```php
try {
    $service->createBooking();
} catch (NoAvailabilityException $e) {
    // expected business handling
}
```

a ostalo pustiti dalje.

---

## 21. `try` blok treba da bude što uži koliko ima smisla

Pogledaj:

```php
try {
    $email = trim($_POST['email']);

    $request = new RegisterRequest(...);

    $service->register(...);

    $session->flash(...);

    header(...);

    exit;
} catch (DuplicateEmailException $e) {
    ...
}
```

Ovo je širok try blok.

Problem:

```text
mnogo različitih stvari može baciti exception
```

Bolje je često ograničiti try na deo za koji zaista očekujemo konkretni exception:

```php
try {
    $service->register(
        $name,
        $email,
        $password
    );
} catch (DuplicateEmailException $e) {
    ...
}
```

Mentalno:

```text
narrow try
→ jasnije šta zapravo očekujemo da fail-uje
```

## 22. Primer sa `PasswordResetService`

Već smo imali:

```php
$this->pdo->beginTransaction();

try {
    $this->users->updatePasswordHash(
        $userId,
        $hash
    );

    $this->resetTokens->deleteForUser(
        $userId
    );

    $this->rememberTokens->deleteForUser(
        $userId
    );

    $this->pdo->commit();
} catch (\Throwable $e) {
    if ($this->pdo->inTransaction()) {
        $this->pdo->rollBack();
    }

    throw $e;
}
```

Ovde široki:

```php
catch (\Throwable $e)
```

ima smisla.

Zašto?

Ne tvrdimo:

> svi problemi su isti.

Nego:

> šta god da prekine atomic use case, transaction mora biti rollback-ovana.

Dakle catch ima jednu preciznu odgovornost:

```text
cleanup DB state
```

onda:

```php
throw $e;
```

i pravi handling ostavljamo višem sloju.

## 23. Primer sa Controller-om

Pretpostavimo:

```php
try {
    $registration->register(
        $name,
        $email,
        $password
    );

    return $response->redirect('/login');

} catch (DuplicateEmailException $e) {
    $session->flashSet(
        'errors',
        ['email' => 'Email already taken.']
    );

    return $response->redirect('/register');
}
```

Ovde Controller zna kako da mapira:

```text
DuplicateEmailException
↓
HTTP/UI behavior
```

To ima smisla.

Ali ako nastane:

```text
PDO connection failure
```

Controller možda ne zna šta s tim.

Zato ga ne catch-ujemo ovde.

On može otići:

```text
global handler
↓
log
↓
500 response
```

---

## 24. Kada koristiti `finally`

Najbolje pitanje je:

> Postoji li nešto što mora da se uradi bez obzira da li je operacija uspela ili nije?

Ako da:

```text
finally može imati smisla
```

Primeri:

```text
zatvaranje resource-a
release lock-a
cleanup temporary state-a
restore neke lokalne postavke
```

Ako ne:

```text
nemoj dodavati finally samo zato što postoji
```

---

## 25. Kada ne koristiti `finally`

Ne koristi ga samo da:

```text
loguje success
vrati rezultat
menja business state
maskira exception
```

Posebno izbegavaj:

```php
finally {
    return false;
}
```

ili:

```php
finally {
    throw new RuntimeException(
        'Something else'
    );
}
```

ako time slučajno uništavaš originalni problem.

`finally` treba prvenstveno da bude:

```text
deterministic cleanup
```

# Laravel paralela

U Laravelu često napišemo:

```php
try {
    DB::transaction(function () {
        // work
    });
} catch (SomeException $e) {
    ...
}
```

ili čak samo:

```php
DB::transaction(function () {
    // work
});
```

Framework tada radi:

```text
begin transaction
↓
callback
↓
success → commit
failure → rollback
↓
rethrow
```

Dakle isti mentalni model koji smo upravo ručno napravili:

```text
try
catch
rollback
rethrow
```

Laravel samo skriva boilerplate.

Isto važi za exception propagation kroz Controller, middleware i global exception handler.

# Najvažnije za zapamtiti

`throw`:

```text
prekida normalan tok
i šalje problem naviše
```

`try`:

```text
označava blok u kojem pratimo exception lifecycle
```

`catch`:

```text
obrađuje određeni tip problema
ako trenutni sloj zna šta treba da uradi
```

`finally`:

```text
izvršava se bez obzira na success ili failure
i najčešće služi cleanup-u
```

Exception propagation:

```text
Repository
↓
throw
↑
Service
↑
Controller
↑
Global Handler
```

dok ga neko ne catch-uje.

Najvažnije pravilo:

```text
Ne catch-uj exception samo zato što možeš.
Catch-uj ga kada ovaj sloj ima jasnu odgovornost.
```

Dobar lokalni catch:

```php
catch (DuplicateEmailException $e)
```

kada znamo kako da problem pretvorimo u application response.

Dobar široki catch:

```php
catch (\Throwable $e)
```

kod transaction rollback-a:

```text
rollback
↓
rethrow
```

Loš obrazac:

```php
catch (\Throwable $e) {
}
```

jer guta problem.

`finally` koristi kada postoji:

```text
cleanup koji mora da se desi
bez obzira na rezultat
```

i izbegavaj:

```php
return
```

unutar `finally`, jer može da pregazi return ili sakrije exception.

Centralni mentalni model lekcije:

```text
throw
→ problem nastaje

catch
→ neko zna šta sa problemom

rethrow
→ ovaj sloj je uradio svoj deo,
  ali problem nije završen

finally
→ cleanup bez obzira na ishod
```
