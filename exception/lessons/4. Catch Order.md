# 4. Catch Order, Multi-Catch & Rethrowing

## 1. Zašto je redosled `catch` blokova važan

Kada imamo više `catch` blokova, PHP ih proverava redom.

Na primer:

```php
try {
    $service->execute();
} catch (DuplicateEmailException $e) {
    // vrlo specifičan problem
} catch (DomainException $e) {
    // širi domain problem
} catch (\Throwable $e) {
    // najširi fallback
}
```

Mentalno:

```text
exception je bačen
↓
PHP gleda prvi catch
↓
odgovara tipu?
├── DA → izvršava ga i završava pretragu
└── NE → ide na sledeći catch
```

Zato redosled mora biti:

```text
specifičniji tip
↓
širi parent tip
↓
najširi fallback
```

---

## 2. PHP bira prvi matching `catch`

Pretpostavimo:

```php
final class DuplicateEmailException
    extends DomainException
{
}
```

i:

```php
throw new DuplicateEmailException();
```

Ako imamo:

```php
try {
    ...
} catch (DuplicateEmailException $e) {
    echo 'Duplicate';
} catch (DomainException $e) {
    echo 'Domain';
}
```

rezultat je:

```text
Duplicate
```

Zašto?

Jer PHP vidi:

```text
DuplicateEmailException
→ tačno odgovara prvom catch-u
```

i više ne proverava sledeće.

---

## 3. Šta ako stavimo širi `catch` prvi?

Pogledaj:

```php
try {
    ...
} catch (DomainException $e) {
    echo 'Domain';
} catch (DuplicateEmailException $e) {
    echo 'Duplicate';
}
```

`DuplicateEmailException` jeste i:

```text
DuplicateEmailException
↓
DomainException
```

pa prvi catch već odgovara.

Zato specifični catch ispod njega praktično gubi smisao.

Mentalno:

```text
parent catch prvi
↓
pokupi child exception
↓
child catch nikada ne dobije šansu
```

Zato:

```text
specific first
general later
```

---

## 4. Primer sa `Throwable`

Ovo je loš redosled:

```php
try {
    $service->execute();
} catch (\Throwable $e) {
    // sve
} catch (DomainException $e) {
    // nikad neće imati smisla
}
```

Jer:

```text
DomainException
→ Exception
→ Throwable
```

Prvi catch već hvata sve.

Zato `Throwable` gotovo uvek ide poslednji ako imamo više catch blokova:

```php
try {
    ...
} catch (DuplicateEmailException $e) {
    ...
} catch (DomainException $e) {
    ...
} catch (\Throwable $e) {
    ...
}
```

---

## 5. `catch` hijerarhija mora pratiti class hijerarhiju

Ako imamo:

```text
Throwable
└── Exception
    └── LogicException
        └── DomainException
            └── DuplicateEmailException
```

onda catch redosled treba da prati obrnut smer:

```text
DuplicateEmailException
↓
DomainException
↓
LogicException
↓
Exception
↓
Throwable
```

Drugim rečima:

> Što je tip konkretniji, treba da bude više.

---

## 6. Kada imati više `catch` blokova

Više catch blokova ima smisla kada za različite probleme želimo različito ponašanje.

Na primer:

```php
try {
    $bookingService->cancel($bookingId);
} catch (BookingNotFoundException $e) {
    return $response->notFound();
} catch (BookingCannotBeCancelledException $e) {
    return $response->conflict(
        'Booking can no longer be cancelled.'
    );
} catch (\Throwable $e) {
    throw $e;
}
```

Ovde:

```text
not found
→ 404

cannot cancel
→ 409

unexpected
→ dalje
```

Dakle catch blokovi predstavljaju različite application odluke.

---

## 7. Multi-catch sintaksa

Ako više različitih exception tipova želimo obraditi potpuno isto, možemo koristiti:

```php
catch (
    FirstException | SecondException $e
) {
    // ista obrada
}
```

Na primer:

```php
try {
    $service->execute();
} catch (
    FileNotFoundException |
    ConfigNotFoundException $e
) {
    return $response->notFound();
}
```

To je:

```text
multi-catch
```

Koristan je kada:

```text
različiti exception tipovi
↓
isti handling
```

---

## 8. Kada je multi-catch bolji od dva `catch` bloka

Ovo:

```php
catch (FileNotFoundException $e) {
    return false;
}

catch (ConfigNotFoundException $e) {
    return false;
}
```

duplira ponašanje.

Čistije:

```php
catch (
    FileNotFoundException |
    ConfigNotFoundException $e
) {
    return false;
}
```

Ako se handling razlikuje:

```text
nemoj ih spajati
```

Multi-catch ne treba koristiti samo da kod izgleda kraće.

Treba ga koristiti kada exception tipovi zaista dele istu reakciju.

---

## 9. Parent tip često već rešava potrebu za multi-catch

Pretpostavimo:

```php
final class FileNotFoundException
    extends ResourceNotFoundException
{
}

final class ConfigNotFoundException
    extends ResourceNotFoundException
{
}
```

Ako oba treba obraditi isto, možda je dovoljno:

```php
catch (ResourceNotFoundException $e) {
    ...
}
```

umesto:

```php
catch (
    FileNotFoundException |
    ConfigNotFoundException $e
) {
    ...
}
```

Dakle pitanje je:

```text
imaju li ovi exception-i zajednički semantički parent?
```

Ako da, često je parent elegantniji.

---

## 10. `throw $e` — rethrow

Najjednostavniji rethrow:

```php
try {
    $service->execute();
} catch (\Throwable $e) {
    throw $e;
}
```

Ovim:

```text
uhvatiš exception
↓
odmah ga ponovo baciš
```

Ako ne radiš ništa drugo:

```php
catch (\Throwable $e) {
    throw $e;
}
```

je potpuno redundantno.

Bolje je samo:

```php
$service->execute();
```

i pustiti propagation prirodno.

---

## 11. Kada `throw $e` ima smisla

Ima smisla kada catch blok mora prvo nešto da uradi.

Na primer:

```php
try {
    $this->pdo->beginTransaction();

    $service->execute();

    $this->pdo->commit();
} catch (\Throwable $e) {
    if ($this->pdo->inTransaction()) {
        $this->pdo->rollBack();
    }

    throw $e;
}
```

Ovde catch ima stvarnu odgovornost:

```text
rollback
```

a zatim:

```text
rethrow
```

jer ne želi da konačno obradi problem.

---

## 12. Logovanje pa rethrow

Primer:

```php
try {
    $service->execute();
} catch (\RuntimeException $e) {
    $logger->error(
        $e->getMessage()
    );

    throw $e;
}
```

Ovo može imati smisla ako baš taj sloj treba da loguje.

Ali postoji važna opasnost:

```text
isti exception može biti logovan više puta
```

na primer:

```text
Repository logs
↓
Service logs
↓
Controller logs
↓
Global handler logs
```

Rezultat:

```text
4 ista log zapisa
```

Zato obično treba imati jasan logging boundary.

Često:

```text
global handler
→ centralno logovanje
```

a lokalni slojevi loguju samo kada imaju dodatni kontekst koji viši sloj nema.

---

## 13. Rethrow istog exception-a čuva njegov identitet

Ako uradimo:

```php
catch (\Throwable $e) {
    throw $e;
}
```

bacamo isti exception objekat dalje.

To znači da zadržavamo:

```text
class
message
code
original file
original line
stack trace
```

Mentalno:

```text
original exception
↓
catch
↓
isti objekat
↓
throw dalje
```

To je važno za debugging.

---

## 14. Razlika između rethrow i wrapping-a

Rethrow:

```php
catch (\PDOException $e) {
    throw $e;
}
```

znači:

```text
isti problem
isti tip
isti objekat
```

Wrapping:

```php
catch (\PDOException $e) {
    throw new DuplicateEmailException(
        'Email already taken.',
        0,
        $e
    );
}
```

znači:

```text
original problem
↓
preveden u novi application problem
↓
originalni exception sačuvan kao previous
```

To ćemo detaljnije raditi u sledećoj lekciji.

---

## 15. `throw new ...` bez `previous` može izgubiti važan kontekst

Pogledaj:

```php
try {
    $this->pdo->prepare(...)->execute();
} catch (\PDOException $e) {
    throw new RuntimeException(
        'Database failed.'
    );
}
```

Sada imamo novi exception, ali originalni:

```text
PDOException
```

više nije povezan sa njim.

Bolje:

```php
throw new RuntimeException(
    'Database failed.',
    0,
    $e
);
```

Tada možemo kasnije:

```php
$e->getPrevious();
```

i videti pravi uzrok.

Ovo je exception chaining.

Detaljno u Lekciji 5.

---

## 16. Mapping exception-a

Jedan od najvažnijih obrazaca je:

```text
low-level exception
↓
mapiranje
↓
higher-level exception
```

Primer:

```php
try {
    $this->users->create(
        $name,
        $email,
        $hash
    );
} catch (\PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            'Email already taken.',
            0,
            $e
        );
    }

    throw $e;
}
```

Ovde repository kaže:

```text
ako znam da PDO exception predstavlja duplicate email
→ prevedi ga

ako ne znam
→ ne izmišljaj
→ pusti ga dalje
```

To je veoma zdrav obrazac.

---

## 17. Ne mapiraj svaki exception u isti custom exception

Loše:

```php
try {
    $statement->execute();
} catch (\PDOException $e) {
    throw new DuplicateEmailException();
}
```

Problem:

PDOException može značiti:

```text
duplicate email
database down
invalid SQL
foreign key violation
connection failure
```

Ako sve pretvorimo u:

```text
DuplicateEmailException
```

lažemo ostatak aplikacije.

Bolje:

```text
prepoznaj samo konkretan poznat slučaj
```

a ostalo:

```php
throw $e;
```

---

## 18. `catch` na pravom sloju

Repository može imati smisla da catch-uje:

```text
PDOException
```

ako želi da ga mapira u persistence/application exception.

Service može imati smisla da catch-uje:

```text
domain/application exception
```

ako mora da uradi rollback ili orkestraciju.

Controller može imati smisla da catch-uje:

```text
known application exception
```

ako zna kako da ga pretvori u HTTP/UI response.

Global handler može uhvatiti:

```text
Throwable
```

kao poslednju granicu.

Mentalno:

```text
Repository
→ infrastructure meaning

Service
→ use-case meaning

Controller
→ HTTP meaning

Global handler
→ fallback
```

---

## 19. Primer kompletnog propagation-a

Pretpostavimo registration race condition.

Repository:

```php
try {
    $statement->execute();
} catch (\PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            'Email already taken.',
            0,
            $e
        );
    }

    throw $e;
}
```

Service:

```php
public function register(...): User
{
    return $this->users->create(...);
}
```

Ne catch-uje ništa jer nema dodatnu odgovornost.

Controller:

```php
try {
    $user = $registration->register(...);
} catch (DuplicateEmailException $e) {
    $session->flashSet(
        'errors',
        ['email' => 'Email already taken.']
    );

    return $response->redirect('/register');
}
```

Ako nastane pravi DB failure:

```text
PDOException
↓
Repository ga ne mapira
↓
Service
↓
Controller
↓
Global Handler
↓
500
```

Ovo je veoma čist lifecycle.

---

## 20. Catch-order primer sa auth aplikacijom

Pretpostavimo:

```php
try {
    $registration->register(...);
} catch (DuplicateEmailException $e) {
    // email error
} catch (DomainException $e) {
    // neki drugi domain problem
} catch (\Throwable $e) {
    // fallback
}
```

Ako se baci:

```text
DuplicateEmailException
```

ide prvi catch.

Ako se baci:

```text
SomeOtherDomainException
```

ide drugi.

Ako se baci:

```text
TypeError
PDOException
Error
```

ide poslednji `Throwable`.

Ali u realnoj aplikaciji poslednji `Throwable` catch često ne bi bio u Controller-u, nego u global handler-u.

## 21. Specifičan catch ne mora da poznaje sve child klase

Ako imaš:

```php
abstract class AuthenticationException
    extends RuntimeException
{
}
```

i:

```php
final class InvalidCredentialsException
    extends AuthenticationException
{
}

final class SuspendedAccountException
    extends AuthenticationException
{
}
```

možeš:

```php
catch (AuthenticationException $e) {
    ...
}
```

ako oba problema imaju isti handling.

To je odličan primer dobre exception hijerarhije.

Ali ako jedan treba:

```text
401
```

a drugi:

```text
403
```

onda možda želiš specifične catch blokove.

---

## 22. Multi-catch i zajednički variable tip

Kod:

```php
catch (
    FirstException |
    SecondException $e
) {
    ...
}
```

`$e` može biti instanca bilo kog navedenog tipa.

Zato unutar catch-a treba koristiti samo ono što oba exception tipa zajednički garantuju.

Na primer:

```php
$e->getMessage();
```

je sigurno jer oba nasleđuju `Throwable`.

Ali metoda specifična samo za jedan exception:

```php
$e->duplicateField();
```

nije sigurna ako drugi tip nema tu metodu.

To je još jedan razlog da ne spajamo tipove samo zbog kraćeg koda.

---

## 23. Kada rethrow nije potreban

Loše:

```php
try {
    $service->execute();
} catch (DomainException $e) {
    throw $e;
}
```

Ako nema:

```text
logging
cleanup
mapping
additional context
```

onda je catch potpuno nepotreban.

Bolje:

```php
$service->execute();
```

Pusti propagation.

Manje koda, manje šuma.

---

## 24. Kada catch treba da transformiše problem

Primer iz booking sistema:

Repository dobije:

```text
database deadlock
```

Možda ga ne želiš mapirati.

Ali ako dobije:

```text
unique booking conflict
```

i znaš da to predstavlja:

```text
room already reserved
```

možda mapiraš u:

```php
throw new BookingConflictException(
    previous: $e
);
```

Sada viši sloj razume:

```text
business/application meaning
```

umesto database detalja.

To je jedna od najvažnijih svrha custom exception-a.

---

## 25. Pravilo za catch odluku

Za svaki catch pitaj:

```text
1. Znam li tačno šta ovaj exception znači?

2. Imam li nešto korisno da uradim?

3. Da li treba da završim problem ovde?

4. Ili samo radim cleanup/mapping pa ga šaljem dalje?
```

Ako je odgovor na sve praktično:

```text
ne
```

onda:

```text
nemoj catch-ovati
```

# Laravel paralela

Laravel često ima svoje specifične exception tipove:

```text
ModelNotFoundException
ValidationException
AuthorizationException
AuthenticationException
QueryException
```

Framework može da ih mapira u različite HTTP responses.

Mentalno:

```text
specific exception
↓
framework handler
↓
specific response
```

Na primer:

```text
ModelNotFoundException
→ 404

AuthorizationException
→ 403
```

To je isti koncept koji ručno gradimo:

```text
specific type
↓
specific handling
```

Laravel samo već ima dosta exception mapping-a unapred.

# Najvažnije za zapamtiti

PHP proverava `catch` blokove redom.

Zato ide:

```text
specifičniji
↓
širi
↓
najširi
```

Primer:

```php
catch (DuplicateEmailException $e)
catch (DomainException $e)
catch (\Throwable $e)
```

Nikad obrnuto ako očekujemo da specifični catch dobije šansu.

Multi-catch:

```php
catch (A | B $e)
```

koristi kada:

```text
različiti exception tipovi
→ zahtevaju potpuno isti handling
```

Ako imaju zajednički semantički parent, često je još čistije:

```php
catch (CommonParentException $e)
```

Rethrow:

```php
throw $e;
```

ima smisla kada catch prvo radi nešto korisno:

```text
rollback
logging
cleanup
```

a zatim pušta originalni problem dalje.

Redundantno:

```php
catch (\Throwable $e) {
    throw $e;
}
```

ako ništa drugo ne radiš.

Mapping:

```text
low-level exception
↓
higher-level meaningful exception
```

Primer:

```text
PDOException
↓
DuplicateEmailException
```

ali mapiraj samo kada stvarno znaš šta low-level problem znači.

Ne pretvaraj sve DB greške u isti application exception.

Centralni mentalni model:

```text
specific catch
→ specifična reakcija

multi-catch
→ različiti tipovi, ista reakcija

rethrow
→ ovaj sloj je uradio svoj deo,
  ali problem nastavlja dalje

mapping
→ prevodimo problem
  iz jezika nižeg sloja
  u jezik višeg sloja
```
