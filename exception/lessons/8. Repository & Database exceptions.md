# 8. Repository & Database Exceptions — Part 1

## 1. Gde database exception nastaje

U PDO repository-ju tipičan tok izgleda:

```php
$stmt = $this->pdo->prepare(
    'INSERT INTO users
     (name, email, password_hash)
     VALUES
     (:name, :email, :password_hash)'
);

$stmt->execute([
    'name' => $name,
    'email' => $email,
    'password_hash' => $passwordHash,
]);
```

Ako database odbije operaciju, uz:

```php
PDO::ATTR_ERRMODE
    => PDO::ERRMODE_EXCEPTION
```

PDO baca:

```php
PDOException
```

Mentalno:

```text
Repository
↓
PDO
↓
Database
↓
problem
↓
PDOException
↑
Repository
```

Repository je zato prvo mesto u našoj aplikaciji koje vidi concrete database failure.

---

## 2. `PDOException` može značiti mnogo različitih stvari

Veoma je važno da ne razmišljamo:

```text
PDOException
→ database je offline
```

`PDOException` može nastati zbog:

```text
duplicate UNIQUE vrednosti
foreign key violation
invalid SQL
missing table
missing column
connection failure
deadlock
lock timeout
data too long
NOT NULL violation
```

Dakle isti PHP exception tip može predstavljati potpuno različite probleme.

Zato ovo nije dovoljno:

```php
catch (PDOException $e) {
    throw new DuplicateEmailException();
}
```

jer možda email uopšte nije problem.

---

## 3. Expected database failure vs unexpected database failure

Ovo je veoma korisna podela.

### Expected

Database je odbila operaciju zbog invariant-a koji aplikacija poznaje.

Na primer:

```text
UNIQUE(email)
```

ili:

```text
booking slot već zauzet
```

ili:

```text
foreign key više ne postoji
```

Takvu grešku ponekad možemo smisleno mapirati u application exception.

### Unexpected

Na primer:

```text
database server unavailable
SQL syntax error
table missing
programming bug u query-ju
```

To uglavnom ne želimo pretvarati u:

```text
Email already taken.
```

nego pustiti prema global handler-u:

```text
log
+
500
```

---

## 4. Database constraint je deo zaštite invariant-a

Seti se registration race condition-a:

```text
Request A
→ findByEmail()
→ nema

Request B
→ findByEmail()
→ nema
```

Oba zatim pokušavaju:

```text
INSERT same email
```

Application pre-check ne može garantovati da se stanje neće promeniti između:

```text
SELECT
i
INSERT
```

Zato imamo:

```sql
UNIQUE(email)
```

Database garantuje invariant:

```text
email mora ostati jedinstven
```

Repository onda mora znati da database može legitimno odgovoriti:

```text
duplicate key
```

čak i ako je application check prethodno prošao.

---

## 5. `PDOException::getCode()` i SQLSTATE

Kod database exception-a često ćemo videti SQLSTATE.

Na primer:

```php
catch (PDOException $e) {
    $sqlState = $e->getCode();
}
```

Može izgledati kao:

```text
23000
```

SQLSTATE je standardizovana kategorija database greške.

Na primer:

```text
23...
→ integrity constraint violation
```

Ali tu postoji važna zamka.

SQLSTATE:

```text
23000
```

ne znači nužno samo:

```text
duplicate email
```

Može predstavljati različite integrity constraint probleme.

Zato samo:

```php
if ($e->getCode() === '23000') {
    throw new DuplicateEmailException();
}
```

može biti preširoko.

---

## 6. Driver-specific error code

PDO exception može sadržati dodatne informacije kroz:

```php
$e->errorInfo
```

tipično u obliku:

```text
[
    SQLSTATE,
    driver-specific code,
    driver-specific message
]
```

Kod MySQL-a, na primer:

```text
1062
```

predstavlja duplicate entry / duplicate key.

Tako možemo imati:

```php
catch (PDOException $e) {
    $driverCode = $e->errorInfo[1] ?? null;

    if ($driverCode === 1062) {
        // duplicate key
    }

    throw $e;
}
```

Ali ni ovo još nije automatski dovoljno da kažemo:

```text
duplicate EMAIL
```

jer tabela može imati više UNIQUE constraint-a.

Na primer:

```text
UNIQUE(email)
UNIQUE(username)
```

`1062` samo kaže:

```text
neki UNIQUE constraint je prekršen
```

---

## 7. Kako mapirati duplicate email bez laganja

Pretpostavimo da `users` tabela ima samo jedan relevantan UNIQUE constraint:

```sql
UNIQUE KEY uq_users_email (email)
```

Repository može imati helper:

```php
private function isDuplicateEmail(
    PDOException $e
): bool {
    $driverCode = $e->errorInfo[1] ?? null;

    return $driverCode === 1062
        && str_contains(
            $e->getMessage(),
            'uq_users_email'
        );
}
```

pa:

```php
try {
    $stmt->execute(...);
} catch (PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            previous: $e
        );
    }

    throw $e;
}
```

Ovde repository ne kaže:

```text
svaki duplicate key
→ duplicate email
```

nego:

```text
prepoznajem baš constraint
koji predstavlja email invariant
```

To je mnogo bezbednije mapiranje.

---

## 8. Zašto imenovanje constraint-a pomaže

Umesto da database sama napravi neko generičko ime:

```text
users_email_unique
```

ili driver-specific naziv, korisno je imati eksplicitna imena:

```sql
CONSTRAINT uq_users_email
UNIQUE (email)
```

ili kod composite unique constraint-a:

```sql
CONSTRAINT uq_booking_room_date
UNIQUE (room_id, booking_date)
```

Tada exception mapping može biti razumljiviji.

Mentalno:

```text
constraint name
→ database invariant ima ime
```

To olakšava:

```text
debugging
mapping
migration maintenance
```

---

## 9. Foreign key violation

Pretpostavimo:

```text
bookings.user_id
→ FOREIGN KEY
→ users.id
```

Ako pokušamo da kreiramo booking za user-a koji više ne postoji, database može odbiti INSERT.

Kod MySQL-a tipični driver-specific kodovi uključuju:

```text
1452
→ child row cannot be added/updated
   because parent row does not exist
```

i:

```text
1451
→ parent row cannot be deleted/updated
   because child rows still reference it
```

Repository može videti:

```text
PDOException
```

ali pitanje je:

> Da li ovo treba mapirati?

Zavisi od značenja.

Ako je to expected concurrent scenario:

```text
user je obrisan između lookup-a i INSERT-a
```

možda application exception ima smisla.

Ako FK violation znači:

```text
naš kod je prekršio invariant koji nikada nije smeo
```

onda je to možda programming/infrastructure problem koji ne treba skrivati kao expected business failure.

---

## 10. Ne pretvaraj programming bug u business exception

Pretpostavimo:

```php
$stmt = $this->pdo->prepare(
    'INSERT INTO users
     (full_name, email)
     VALUES
     (:name, :email)'
);
```

ali kolona:

```text
full_name
```

uopšte ne postoji.

Database baci `PDOException`.

Loše:

```php
catch (PDOException $e) {
    throw new RegistrationFailedException();
}
```

ako time pokušavamo da ga tretiramo kao normalan expected registration failure.

Ovo je verovatno:

```text
programming / deployment problem
```

i treba:

```text
propagirati
↓
global handler
↓
logovati detaljno
↓
500
```

Važno pravilo:

> Nemoj koristiti custom application exception da slučajno sakriješ bug.

# 8. Repository & Database Exceptions — Part 2

## 11. Repository treba da prevodi samo ono što razume

Dobar obrazac:

```php
try {
    $stmt->execute($params);
} catch (PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            previous: $e
        );
    }

    throw $e;
}
```

Mentalno:

```text
poznati DB failure
→ mapiraj

nepoznati DB failure
→ ne izmišljaj
→ rethrow
```

Repository nije dužan da svaki `PDOException` pretvori u neki custom exception.

To je jedna od najvažnijih stvari ove lekcije.

---

## 12. Repository-specific wrapper

Nekad želimo da infrastructure detalj uopšte ne curi iz repository sloja.

Možemo imati:

```php
final class UserPersistenceException
    extends RuntimeException
{
}
```

i:

```php
try {
    $stmt->execute($params);
} catch (PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            previous: $e
        );
    }

    throw new UserPersistenceException(
        'Unable to persist user.',
        0,
        $e
    );
}
```

Sada viši sloj vidi:

```text
DuplicateEmailException
ili
UserPersistenceException
```

a ne direktno PDO.

To može biti dobro ako želimo jaku infrastructure boundary separaciju.

Ali nije obavezno za svaku manju aplikaciju.

Važnije je da razumemo šta time dobijamo:

```text
viši sloj
→ manje vezan za PDO
```

---

## 13. Kada ne treba praviti repository wrapper

Ako napišemo u svakoj metodi:

```php
catch (PDOException $e) {
    throw new UserPersistenceException(
        'Database operation failed.',
        0,
        $e
    );
}
```

možda dobijemo mnogo boilerplate-a bez stvarne vrednosti.

Ako global handler sasvim lepo ume da loguje:

```text
PDOException
```

i Service/Controller ne treba da ga razlikuju, možemo ga pustiti dalje.

Dakle:

```text
wrapper
→ koristan kada menja nivo apstrakcije

wrapper
→ nepotreban ako samo menja ime
```

---

## 14. Deadlock nije isto što i duplicate constraint

U concurrent aplikacijama database može prijaviti:

```text
deadlock
```

Na MySQL-u je tipični driver code:

```text
1213
```

To znači otprilike:

```text
dve transaction čekaju jedna drugu
↓
database izabere jednu da prekine
```

Ovo nije:

```text
business validation error
```

nego:

```text
concurrency/runtime database failure
```

U nekim sistemima možemo implementirati retry.

Na primer mentalno:

```text
deadlock
↓
rollback
↓
retry transaction
```

Ali retry policy pripada use-case / transaction sloju, ne nužno repository-ju.

Repository može prepoznati failure.

Service odlučuje:

```text
da li ceo use case može bezbedno da se ponovi
```

---

## 15. Lock wait timeout

Slično:

```text
MySQL driver code 1205
→ lock wait timeout
```

To znači da transaction predugo čeka lock.

Opet:

```text
nije isto što i invalid user input
```

i ne treba pretvarati u:

```text
"Booking unavailable"
```

osim ako application semantics zaista opravdava takvo mapiranje.

Češće:

```text
rollback
log
eventualno retry
```

zavisno od use case-a.

---

## 16. Repository i transaction boundary nisu isto

Repository radi:

```text
jednu persistence operaciju
```

Service može orkestrirati:

```text
više repository operacija
kao jedan atomic use case
```

Na primer:

```text
PasswordResetService
↓
UserRepository::updatePasswordHash()
ResetTokenRepository::deleteForUser()
RememberTokenRepository::deleteForUser()
```

Ako drugi repository baci `PDOException`:

```text
Service
→ rollback cele transaction
```

Zato transaction boundary ne treba automatski stavljati u:

```text
svaki repository method
```

Inače:

```text
repository A commit
↓
repository B fail
```

i izgubili smo atomicity.

---

## 17. Isti PDO connection je važan

Ako transaction otvorimo:

```php
$this->pdo->beginTransaction();
```

a repositories koriste drugi PDO objekat / drugi connection:

```text
transaction na connection A
```

ne kontroliše nužno query-je izvršene kroz:

```text
connection B
```

Zato kod use case-a koji zahteva atomic transaction želimo:

```text
PasswordResetService
↓
PDO A
↓
UserRepository → PDO A
ResetTokenRepository → PDO A
RememberTokenRepository → PDO A
```

Mentalno:

```text
jedan transaction
→ jedan isti database connection
```

Ovo si već koristio u prethodnim modulima.

---

## 18. `findById(): ?User` i database exception nisu ista stvar

Ovo je veoma važna distinkcija.

```php
public function findById(int $id): ?User
```

može vratiti:

```text
null
```

ako query uspešno kaže:

```text
nema reda sa tim ID-em
```

To nije `PDOException`.

Tok:

```text
SELECT uspeo
↓
0 rows
↓
null
```

Nasuprot:

```text
database connection pukne
↓
query nije uspešno izvršen
↓
PDOException
```

Dakle:

```text
not found
≠
database failure
```

To treba jasno razlikovati.

---

## 19. Database exception message nije za korisnika

Loše:

```php
catch (PDOException $e) {
    echo $e->getMessage();
}
```

Production user može dobiti nešto poput:

```text
SQLSTATE...
table name
constraint name
column name
query details
server paths
```

To je i loš UX i potencijalni security leak.

Bolje:

```text
PDOException
↓
log / exception chain
```

dok korisnik dobija:

```text
Something went wrong.
```

ili ako smo sigurno mapirali expected condition:

```text
Email already taken.
```

## 20. Kompletan repository mentalni model

Primer:

```php
public function create(
    string $name,
    string $email,
    string $passwordHash
): User {
    try {
        $stmt = $this->pdo->prepare(
            'INSERT INTO users
             (name, email, password_hash)
             VALUES
             (:name, :email, :password_hash)'
        );

        $stmt->execute([
            'name' => $name,
            'email' => $email,
            'password_hash' => $passwordHash,
        ]);

    } catch (PDOException $e) {
        if ($this->isDuplicateEmail($e)) {
            throw new DuplicateEmailException(
                $email,
                $e
            );
        }

        throw $e;
    }

    return $this->findById(
        (int) $this->pdo->lastInsertId()
    );
}
```

Mentalno:

```text
Database operation
↓
success?
├── DA
│   ↓
│   return domain/application data
│
└── NE
    ↓
    PDOException
    ↓
    poznat invariant failure?
    ├── DA → mapiraj
    └── NE → propagiraj
```

To je praktično srž database exception handling-a.

# Najvažnije za zapamtiti

`PDOException` može značiti mnogo stvari:

```text
duplicate constraint
foreign key violation
deadlock
timeout
connection failure
invalid SQL
programming bug
```

Zato:

```text
PDOException
≠ automatski business exception
```

Repository mapira samo ono što stvarno razume.

Dobro:

```text
poznat UNIQUE email constraint
↓
DuplicateEmailException
```

Loše:

```text
svaki PDOException
↓
DuplicateEmailException
```

SQLSTATE daje kategoriju problema, dok driver-specific code može dati precizniji database detalj.

Kod MySQL-a često ćemo sresti:

```text
1062
→ duplicate key

1451 / 1452
→ foreign key constraint problems

1213
→ deadlock

1205
→ lock wait timeout
```

Ali i driver code mora biti tumačen u kontekstu query-ja i constraint-a.

`findById()` koji vraća:

```text
null
```

znači:

```text
query je uspeo,
ali record ne postoji
```

To nije isto što i:

```text
PDOException
```

Transaction boundary tipično pripada Service-u kada jedan use case obuhvata više repository operacija.

Za atomic transaction:

```text
svi repository-ji
→ isti PDO connection
```

Database exception detalji nisu user-facing sadržaj.

Centralni mentalni model:

```text
Database
↓
PDOException
↓
Repository pita:

"Da li tačno znam šta ovaj failure znači?"

├── DA
│   ↓
│   mapiraj u smislen application exception
│
└── NE
    ↓
    propagiraj dalje
    ↓
    global handler / logging
```
