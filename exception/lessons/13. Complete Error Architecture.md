# 13. Complete Vanilla PHP Error Architecture — Part 1

Do sada smo pojedinačno učili:

```text

rethrow
```


```text

↓
```

## 2. Bootstrap je mesto gde podižemo error infrastrukturu

Pre nego što aplikacija krene da obrađuje request, želimo da postavimo globalna pravila.

Na primer:

```php
<?php

require_once __DIR__ . '/../vendor/autoload.php';

error_reporting(E_ALL);

$isDevelopment =
    ($_ENV['APP_ENV'] ?? 'production')
    === 'development';

ini_set(
    'display_errors',
    $isDevelopment ? '1' : '0'
);

ini_set(
    'log_errors',
    '1'
);
```

Zatim registrujemo:

```text
error handler
exception handler
shutdown handler
```

Mentalno:

```text
bootstrap
↓
error policy
↓
application execution
```

Ako infrastrukturu registrujemo rano, gotovo ceo application lifecycle prolazi kroz ista pravila.

## 3. PHP error handler

Traditional PHP runtime errors možemo normalizovati u exception sistem:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        if (!(error_reporting() & $severity)) {
            return false;
        }

        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    }
);
```

Mentalno:

```text
E_WARNING / E_NOTICE / ...
↓
set_error_handler()
↓
ErrorException
↓
normalan Throwable pipeline
```

Time smanjujemo broj različitih failure mehanizama koje application code mora da razume.

## 4. Global exception handler

Unhandled `Throwable` ide u centralni handler.

Bolje od ogromnog closure-a je posebna klasa:

```php
final class ExceptionHandler
{
    public function __construct(
        private Logger $logger,
        private bool $debug
    ) {}

    public function handle(
        Throwable $e
    ): void {
        $this->report($e);
        $this->render($e);
    }
}
```

Bootstrap:

```php
$handler = new ExceptionHandler(
    $logger,
    $isDevelopment
);

set_exception_handler(
    [$handler, 'handle']
);
```

Sada imamo jasno:

```text
Throwable
↓
ExceptionHandler
↓
report
+
render
```

## 5. `report()` i `render()` treba razdvojiti

`report()` odgovara na pitanje:

> Šta treba zabeležiti?

Na primer:

```php
private function report(
    Throwable $e
): void {
    $this->logger->error(
        'Unhandled exception.',
        [
            'exception' => $e,
        ]
    );
}
```

`render()` odgovara:

> Šta klijent treba da dobije?

Na primer:

```php
private function render(
    Throwable $e
): void {
    http_response_code(500);

    echo 'Something went wrong.';
}
```

Mentalno:

```text
REPORT
→ developer / operations

RENDER
→ HTTP client
```

Te dve stvari ne treba mešati.

## 6. Expected i unexpected exceptions

Global handler može da razlikuje poznate application failure-e.

Na primer:

```php
private function render(
    Throwable $e
): void {
    if ($e instanceof NotFoundException) {
        http_response_code(404);

        require __DIR__
            . '/../../views/errors/404.php';

        return;
    }

    if ($e instanceof AuthorizationException) {
        http_response_code(403);

        require __DIR__
            . '/../../views/errors/403.php';

        return;
    }

    http_response_code(500);

    require __DIR__
        . '/../../views/errors/500.php';
}
```

Mentalno:

```text
poznat application problem
→ poznat HTTP response

nepoznat problem
→ 500
```

Ali ne treba svaki expected problem automatski slati global handler-u.

Ako Controller ima bolji lokalni kontekst, lokalni catch može biti bolji.

## 7. Repository boundary

Repository radi sa infrastructure detaljima:

```text
PDO
SQL
rows
constraints
mapping
```

Na primer:

```php
final class PdoUserRepository
    implements UserRepository
{
    public function create(
        string $name,
        string $email,
        string $passwordHash
    ): User {
        try {
            $stmt = $this->pdo->prepare(
                'INSERT INTO users
                 (name, email, password_hash)
                 VALUES
                 (:name, :email, :password_hash)'
            );

            $stmt->execute([
                'name' => $name,
                'email' => $email,
                'password_hash'
                    => $passwordHash,
            ]);

        } catch (PDOException $e) {
            if ($this->isDuplicateEmail($e)) {
                throw new DuplicateEmailException(
                    $email,
                    $e
                );
            }

            throw $e;
        }

        return $this->findById(
            (int) $this->pdo->lastInsertId()
        );
    }
}
```

Repository ovde:

```text
razume DB failure
↓
prepoznaje konkretan invariant
↓
prevodi ga u application exception
```

Ali ne pretvara svaki `PDOException` u nešto drugo bez razloga.

## 9. Service boundary

Service poseduje use case.

Na primer:

```text
PasswordResetService
```

zna da reset znači:

```text
update password
+
delete reset token
+
delete remember tokens
```

Zato prirodno poseduje transaction boundary:

```php
$this->pdo->beginTransaction();

try {
    $this->users->updatePasswordHash(
        $userId,
        $hash
    );

    $this->resetTokens->deleteForUser(
        $userId
    );

    $this->rememberTokens->deleteForUser(
        $userId
    );

    $this->pdo->commit();

} catch (Throwable $e) {
    if ($this->pdo->inTransaction()) {
        $this->pdo->rollBack();
    }

    throw $e;
}
```

Service ovde ne tvrdi:

```text
znam konačni odgovor user-u
```

nego:

```text
znam da use case mora ostati atomic
```

Zato:

```text
catch
→ rollback
→ rethrow
```

ima smisla.

Loše:

```php
public function reset(...): Response

    try {
        ...
    } catch (PDOException $e) {
        return new Response(
            'Something went wrong.',
```

Sada service zna za:

```text
HTTP

status code
presentation
```

```text

→ application result ili exception

```

Separation:

```text

→ Šta use case znači?

HTTP layer
→ Kako to izgleda klijentu?
```

## 11. Controller boundary

Controller je HTTP/application boundary.

Na primer:

```php
try {
    $registration->register(
        $name,

        '/register'
```

```text

↓

↓

↓
gde redirect
```

## 13. Middleware i exceptions

Middleware može:

```text
prekinuti request
```

pre Controller-a.

Na primer:

```php
final class AuthMiddleware
{
    public function handle(
        Request $request,
        callable $next
    ): Response {
        if ($this->auth->guest()) {
            throw new AuthenticationException();
        }

        return $next($request);
    }
}
```

Ili može direktno vratiti redirect/401, u zavisnosti od dizajna.

Ako middleware baci exception:

```text
Middleware
↓
Throwable
↑
Global Handler
```

## 21. Shutdown fallback

Pored normalnog Throwable pipeline-a imamo:

```php
register_shutdown_function(
    function (): void {
        $error = error_get_last();

        if ($error === null) {
            return;
        }

        $fatalTypes = [
            E_ERROR,
            E_PARSE,
            E_CORE_ERROR,
            E_COMPILE_ERROR,
        ];

        if (!in_array(
            $error['type'],
            $fatalTypes,
            true
        )) {
            return;
        }

        error_log(
            sprintf(
                'Fatal PHP error: %s in %s:%d',
                $error['message'],
                $error['file'],
                $error['line']
            )
        );

        if (!headers_sent()) {
            http_response_code(500);
        }
    }
);
```

To je:

```text
last-resort diagnostics
```

ne:

```text
normal business recovery
```

# Najvažnije za zapamtiti

Kompletan error lifecycle:

```text
Request
↓
Middleware
↓
Controller
↓
Service
↓
Repository
↓
Infrastructure
```

Ako nastane problem:

```text
Infrastructure
↑
Repository
↑
Service
↑
Controller
↑
Global Handler
```

svaki sloj catch-uje samo kada ima konkretnu odgovornost.

Repository:

```text
infrastructure failure
→ eventualno semantic mapping
```

Service:

```text
use-case orchestration
transaction
rollback
cleanup
```

Controller:

```text
expected application problem
→ HTTP/UI response
```

Global handler:

```text
unhandled Throwable
→ report
→ render
```

Error handler:

```text
traditional PHP error
→ ErrorException
→ Throwable pipeline
```

Shutdown handler:

```text
fatal fallback
→ minimal diagnostics
```

Development:

```text
detaljan visibility
```

Production:

```text
display_errors = Off
log_errors = On
safe public response
```

Exception chaining:

```text
outer exception
→ šta problem znači ovom sloju

previous
→ pravi uzrok

stack trace
→ kako smo stigli do problema
```

Logging:

```text
koristan context
+
exception object
-
secrets
```

Najvažnije pravilo celog modula:

> **Exception treba da propagira sve dok ne stigne do sloja koji ima konkretnu odgovornost za taj problem.**

I još važnije:

```text
catch ne znači:
"ne želim da vidim grešku"

catch znači:
"ovaj sloj zna šta konkretno treba
da uradi zbog ovog failure-a"
```

Finalna mentalna mapa:

```text
EXPECTED FAILURE
→ specific exception
→ specific handling

UNEXPECTED FAILURE
→ propagation
→ global handler
→ log + safe response

TRANSACTION FAILURE
→ rollback
→ rethrow
→ final handling

PROGRAMMING BUG
→ ne maskirati
→ log
→ fix root cause

FATAL PHP FAILURE
→ shutdown fallback
→ diagnostics
```
