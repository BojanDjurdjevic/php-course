# 1. Errors, Exceptions & Bugs — Mental Model

## 1. Zašto je error handling poseban deo aplikacije

Kada aplikacija radi idealnim putem, tok izgleda jednostavno:

```text
Request
↓
Controller
↓
Service
↓
Repository
↓
Database
↓
Response
```

Na primer:

```php
$user = $users->findByEmail($email);

$auth->login($user);

return $response;
```

Ali realna aplikacija skoro nikada nema samo happy path.

Može se desiti:

```text
database connection failed

user ne postoji

email je već zauzet

fajl ne može da se pročita

API ne odgovara

argument je pogrešnog tipa

programer je pozvao nepostojeću metodu

SQL constraint je prekršen

booking više nije dostupan

password reset token je istekao
```

Error handling je način na koji aplikacija odgovara na pitanje:

> Šta radimo kada normalan tok više ne može da se nastavi?

To ne znači samo:

```php
try {
    ...
} catch (...) {
    ...
}
```

Error handling uključuje:

```text
prepoznavanje problema
↓
klasifikaciju problema
↓
odluku gde se problem obrađuje
↓
logovanje
↓
eventualni rollback
↓
pretvaranje problema u smislen HTTP response
```

---

## 2. Četiri pojma koja treba razdvojiti

Najkorisnije je da razlikujemo:

```text
Bug
Error
Exception
Failure
```

Ovi pojmovi se u svakodnevnom govoru često koriste kao sinonimi, ali nisu potpuno ista stvar.

---

## 3. Bug — greška u programu

**Bug** je greška u našem kodu ili logici.

Na primer:

```php
$total = $price - $quantity;
```

a trebalo je:

```php
$total = $price * $quantity;
```

PHP neće nužno prijaviti nikakav problem.

Kod je sintaksno validan.

Program može završiti request bez ijednog exception-a.

Ali rezultat je pogrešan.

To je bug.

Još jedan primer:

```php
if ($user->isAdmin()) {
    return $booking->delete();
}
```

Ako smo slučajno obrnuli authorization pravilo:

```php
if (!$user->isAdmin()) {
    return $booking->delete();
}
```

PHP će sasvim normalno izvršiti kod.

Ali imamo ozbiljan bug.

Dakle:

```text
Bug
→ program radi drugačije nego što je trebalo
```

Bug ne mora automatski proizvesti PHP error ili exception.

---

## 4. Error — problem koji PHP runtime detektuje

PHP može sam detektovati određene probleme tokom izvršavanja.

Na primer:

```php
function divide(int $a, int $b): float
{
    return $a / $b;
}

divide(10, 0);
```

Ili:

```php
$user->methodThatDoesNotExist();
```

Ili:

```php
function greet(string $name): void
{
}

greet([]);
```

To nisu business problemi.

PHP runtime kaže:

> Ovaj kod ne može pravilno da nastavi izvršavanje.

U modernom PHP-u mnogi ozbiljni runtime problemi predstavljeni su objektima koji nasleđuju:

```php
Error
```

na primer:

```text
TypeError
ArgumentCountError
ValueError
DivisionByZeroError
```

Detaljnu `Throwable` hijerarhiju ćemo obrađivati u sledećoj lekciji.

Za sada je dovoljno:

```text
Error
→ runtime/programming problem koji PHP detektuje
```

---

## 5. Exception — problem koji aplikacija može eksplicitno predstaviti

Exception je objekat kojim možemo reći:

> Normalan tok ove operacije ne može da se nastavi.

Na primer:

```php
if ($user === null) {
    throw new RuntimeException('User not found.');
}
```

Ili mnogo smislenije:

```php
if ($users->findByEmail($email) !== null) {
    throw new DuplicateEmailException();
}
```

Ovde PHP nije sam odlučio da postoji problem.

**Mi smo odlučili da je određeno stanje exceptional za konkretni use case.**

Na primer:

```text
RegistrationService::register()
```

treba da registruje novog korisnika.

Ako email već postoji:

```text
normalan uspešan tok više nije moguć
```

pa možemo baciti:

```php
throw new DuplicateEmailException();
```

Exception nam omogućava da prekinemo trenutni tok i prenesemo informaciju o problemu višem sloju.

---

## 6. Exception nije isto što i bug

Ovo je veoma važna razlika.

Pogledaj:

```php
throw new DuplicateEmailException();
```

To ne mora značiti da aplikacija ima bug.

Može biti potpuno očekivana situacija:

```text
User pokušava registraciju
↓
email već postoji
↓
registration ne može da se završi
```

Sistem radi tačno kako je dizajniran.

Dakle:

```text
Expected exceptional condition
≠
Bug
```

Primeri očekivanih situacija:

```text
duplicate email
booking više nije dostupan
reset token je istekao
user nema permission
fajl koji je tražen ne postoji
payment je odbijen
```

Sa druge strane:

```php
$user->nonExistingMethod();
```

je verovatno programming bug.

Mentalno:

```text
Exception
→ mehanizam prenosa problema

Bug
→ greška u našem programu
```

Exception može predstavljati business problem, infrastructure problem ili čak bug.

---

## 7. Failure — operacija nije uspela

`Failure` možemo posmatrati kao širi koncept.

Na primer:

```text
Password reset nije uspeo.
```

Zašto?

Možda:

```text
token expired
```

ili:

```text
database unavailable
```

ili:

```text
programming bug
```

Sva tri rezultiraju:

```text
password reset failed
```

Dakle:

```text
Failure
→ rezultat: operacija nije uspešno završena
```

Uzrok failure-a može biti različit.

Na primer:

```text
FAILURE:
booking nije kreiran

CAUSE:
inventory više nije dostupan
```

ili:

```text
FAILURE:
booking nije kreiran

CAUSE:
database connection failed
```

ili:

```text
FAILURE:
booking nije kreiran

CAUSE:
bug u kodu
```

To će kasnije biti važno jer ne treba svaki failure prikazati korisniku istom porukom.

---

## 8. Expected vs unexpected problems

Jedna od najkorisnijih podela je:

```text
Expected problem
vs
Unexpected problem
```

### Expected

Aplikacija zna da se ovo može dogoditi.

Na primer:

```text
email already taken
invalid credentials
booking sold out
password reset token expired
user not authorized
```

To su situacije koje često možemo pretvoriti u kontrolisani response:

```text
409 Conflict
422 Unprocessable Content
401 Unauthorized
403 Forbidden
404 Not Found
```

zavisno od konteksta.

Na primer:

```php
throw new DuplicateEmailException();
```

može završiti kao:

```text
409 Conflict
```

ili validation-style response.

### Unexpected

Nešto što nismo očekivali u normalnom poslovnom toku:

```text
PDO driver problem
filesystem unavailable
TypeError
undefined method
programming invariant violated
```

Takva situacija često završi kao:

```text
500 Internal Server Error
```

uz logovanje detalja.

Korisniku ne želimo poslati:

```text
PDOException:
SQLSTATE[HY000] ...
```

nego nešto poput:

```text
Something went wrong.
```

dok pravi detalji idu u log.

## 9. Error handling nije isto što i skrivanje grešaka

Početnici često rade:

```php
try {
    $service->doSomething();
} catch (\Throwable $e) {
    return false;
}
```

Ovo izgleda kao error handling.

Ali često je zapravo:

```text
error swallowing
```

Problem je nestao iz toka, ali više niko ne zna:

```text
šta se dogodilo
gde se dogodilo
zašto se dogodilo
```

Još gore:

```php
try {
    $repository->save($user);
} catch (\Throwable $e) {
}
```

Aplikacija nastavlja kao da je sve u redu.

To može napraviti mnogo veći problem od originalnog exception-a.

Dobro error handling pitanje nije:

> Kako da sprečim exception?

nego:

> Koji sloj ima dovoljno konteksta da pravilno odluči šta treba uraditi sa ovim exception-om?

Ponekad odgovor glasi:

```text
nemoj ga catch-ovati ovde
```

Pusti ga višem sloju.

To ćemo veoma detaljno raditi kasnije.

## 10. Mentalni model propagation-a

Pretpostavimo:

```text
Controller
↓
Service
↓
Repository
↓
PDO
```

Repository izvrši:

```php
$statement->execute();
```

i database baci exception.

Ako repository ne uradi `catch`:

```text
PDO
throws
↓
Repository
↓
Service
↓
Controller
↓
global handler
```

Exception se **propagira naviše kroz call stack**.

Na primer:

```php
function repository(): void
{
    throw new RuntimeException('Database problem');
}

function service(): void
{
    repository();
}

function controller(): void
{
    service();
}

controller();
```

Tok:

```text
controller()
↓
service()
↓
repository()
↓
THROW
↑
repository se prekida
↑
service se prekida
↑
controller se prekida
↑
dok neko ne catch-uje exception
```

Ovo je centralni mentalni model exception sistema.

`throw` kaže:

> Ovde više ne mogu normalno da nastavim.

`catch` kaže:

> Ja imam dovoljno konteksta da nešto uradim sa ovim problemom.

## 11. `return false` vs exception

Ovo je jedna od tema koju ćemo često sretati.

Možemo napisati:

```php
if (!$user) {
    return false;
}
```

ili:

```php
if (!$user) {
    throw new UserNotFoundException();
}
```

Nijedno nije automatski bolje.

Zavisi od contract-a metode.

Na primer:

```php
public function attempt(
    string $email,
    string $password
): bool
```

ima prirodan contract:

```text
true
→ login uspeo

false
→ credentials nisu prihvaćeni
```

Tu `false` može imati smisla.

Ali:

```php
public function createBooking(...): Booking
```

ako rezervaciju nije moguće napraviti jer nema inventory-ja, vraćanje:

```php
false
```

može biti mnogo manje informativno od:

```php
throw new NoAvailabilityException();
```

Exception može preneti semantičko značenje problema.

Mentalno:

```text
return
→ normalan rezultat metode

throw
→ normalan tok metode je prekinut
```

Granica nije uvek potpuno crno-bela, ali ovo je dobar početni model.

## 12. Primer iz tvoje auth arhitekture

Već smo zapravo koristili error-handling ideje u prethodnom modulu.

Registration:

```php
$user = $users->findByEmail($email);

if ($user !== null) {
    throw new DuplicateEmailException();
}
```

Repository zatim radi:

```php
$users->create(...);
```

Ali može nastati race condition:

```text
Request A → email ne postoji
Request B → email ne postoji

A → INSERT ✅
B → INSERT ❌ UNIQUE constraint
```

Concrete PDO repository može dobiti:

```text
PDOException
```

a zatim problem prevesti u:

```text
DuplicateEmailException
```

Mentalno:

```text
Database language
↓
PDOException / constraint violation

Repository
↓
mapiranje

Application language
↓
DuplicateEmailException
```

To je veoma važan obrazac.

Viši slojevi više ne moraju da znaju:

```text
SQLSTATE
MySQL error code
PDO detalje
```

nego razumeju:

```text
duplicate email
```

## 13. Laravel paralela

Kada Laravel aplikacija baci:

```php
throw new SomeException();
```

framework ima centralni exception handling lifecycle.

U Laravelu često izgleda kao da:

```text
exception
↓
nekako automatski postane HTTP response
```

Ali ispod konceptualno postoji isti tok:

```text
Controller
↓
Service
↓
Repository / framework component
↓
throw
↑
propagation
↑
global exception handler
↓
log
↓
HTTP response
```

Laravel samo već ima veliki deo infrastrukture.

Kada kasnije napravimo naš Vanilla PHP global handler, videćeš veoma jasno šta framework radi za nas.

# Najvažnije za zapamtiti

```text
Bug
→ greška u našem programu ili logici
```

```text
Error
→ runtime/programming problem koji PHP detektuje
```

```text
Exception
→ objekat/mehanizam kojim prekidamo normalan tok i prenosimo problem višem sloju
```

```text
Failure
→ operacija nije uspešno završena
```

Exception ne znači automatski bug.

Na primer:

```text
DuplicateEmailException
ExpiredResetTokenException
NoAvailabilityException
```

mogu predstavljati potpuno očekivane application situacije.

Najvažnija podela:

```text
Expected problem
→ često kontrolisan application response

Unexpected problem
→ obično log + generic 500 response
```

Exception se propagira kroz call stack:

```text
Repository
throws
↑
Service
↑
Controller
↑
Global Handler
```

dok ga neki sloj ne `catch`-uje.

Ne treba catch-ovati exception samo zato što možemo.

Pravo pitanje je:

> Da li ovaj sloj ima dovoljno konteksta da pravilno obradi problem?

Ako nema:

```text
pusti exception dalje
```

I najvažniji mentalni model cele lekcije:

```text
throw
→ "ne mogu normalno da nastavim"

catch
→ "ja znam šta treba da uradim sa ovim problemom"
```
