# 12. Logging & Practical Debugging Workflow — Part 1

## 1. Error handling i debugging nisu isto

Error handling odgovara na pitanje:

> Šta aplikacija treba da uradi kada nešto pođe po zlu?

Debugging odgovara na pitanje:

> Zašto je pošlo po zlu?

Na primer:

```text
PDOException
↓
Global Handler
↓
500 response
```

je error handling.

Ali developer zatim mora da utvrdi:

```text
Koji query?
Koji request?
Koji user?
Koja linija?
Koji input?
Koji prethodni exception?
```

To je debugging.

Mentalno:

```text
ERROR HANDLING
→ kontroliše failure

DEBUGGING
→ pronalazi uzrok failure-a
```

---

## 2. Logging je istorija onoga što se dogodilo

Bez logova imamo samo:

```text
"User kaže da nije radilo."
```

Sa logovima možemo imati:

```text
2026-11-09 10:15:03
Booking creation failed

user_id: 17
hotel_id: 4
room_id: 8
check_in: 2026-12-10
check_out: 2026-12-15
exception: PDOException
```

Logging nam daje:

```text
vreme
context
event
failure
```

To je posebno važno za probleme koje ne možemo lako reprodukovati lokalno.

---

## 3. Log message bez context-a često nije dovoljan

Loše:

```php
error_log(
    'Booking failed.'
);
```

To nam ne govori:

```text
koji booking?
koji user?
koji request?
zašto?
```

Bolje:

```php
$logger->error(
    'Booking creation failed.',
    [
        'user_id' => $userId,
        'hotel_id' => $hotelId,
        'room_id' => $roomId,
        'check_in' => $checkIn,
        'check_out' => $checkOut,
        'exception' => $e,
    ]
);
```

Mentalno:

```text
message
→ šta se dogodilo

context
→ pod kojim uslovima se dogodilo
```

---

## 4. Log levels

Ozbiljniji logger-i koriste nivoe.

Najčešći:

```text
debug
info
notice
warning
error
critical
alert
emergency
```

Ne moraš svaku nijansu koristiti svakodnevno.

Za praktičan backend rad dovoljno je prvo dobro razumeti:

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

Mentalno:

```text
debug
→ detalji za development/debugging

info
→ normalan značajan događaj

warning
→ nešto neobično, ali aplikacija nastavlja

error
→ operacija nije uspela

critical
→ ozbiljan failure sistema
```

---

## 5. `debug`

Primer:

```php
$logger->debug(
    'Remember Me token lookup.',
    [
        'selector' => $selector,
    ]
);
```

Koristi se za detalje koji pomažu tokom razvoja ili istrage problema.

Ali production log ne treba zatrpati:

```text
svakom promenljivom
svakim query-jem
svakim method call-om
```

Previše logova može biti skoro jednako loše kao premalo logova.

Dobar `debug` log treba da ima svrhu.

---

## 6. `info`

`info` označava normalan, značajan događaj.

Na primer:

```php
$logger->info(
    'User registered.',
    [
        'user_id' => $user->id(),
    ]
);
```

ili:

```php
$logger->info(
    'Password reset completed.',
    [
        'user_id' => $userId,
    ]
);
```

To nisu failures.

To su događaji koje možda želimo da pratimo.

Ali opet:

```text
ne loguj baš svaki normalan method call
```

Logging treba da ostane signal, ne buka.

---

## 7. `warning`

Warning predstavlja:

```text
nešto nije idealno
ali sistem još funkcioniše
```

Na primer:

```php
$logger->warning(
    'Remember Me token mismatch.',
    [
        'selector' => $selector,
    ]
);
```

ili:

```php
$logger->warning(
    'External API response was slow.',
    [
        'duration_ms' => $duration,
    ]
);
```

Warning je dobar za situacije koje možda ukazuju na budući problem ili security anomaly.

---

## 8. `error`

Error:

```text
konkretna operacija nije uspela
```

Na primer:

```php
$logger->error(
    'Password reset transaction failed.',
    [
        'user_id' => $userId,
        'exception' => $e,
    ]
);
```

Ili:

```php
$logger->error(
    'Unable to persist booking.',
    [
        'booking_id' => $bookingId,
        'exception' => $e,
    ]
);
```

Ovo je tipičan nivo za unhandled application/infrastructure failure.

---

## 9. `critical`

Critical je za ozbiljnije probleme koji ugrožavaju rad sistema.

Na primer:

```text
database potpuno nedostupna
payment provider nedostupan za sve request-e
filesystem storage nije dostupan
critical configuration missing
```

Primer:

```php
$logger->critical(
    'Database connection failed.',
    [
        'exception' => $e,
    ]
);
```

Ne treba svaki običan exception označiti kao `critical`.

Inače nivo gubi značenje.

---

## 10. Log exception kao objekat, ne samo message

Loše:

```php
$logger->error(
    $e->getMessage()
);
```

Bolje:

```php
$logger->error(
    'Unhandled exception.',
    [
        'exception' => $e,
    ]
);
```

Zašto?

Exception objekat nosi:

```text
class
message
file
line
stack trace
previous exception
```

Dok:

```php
$e->getMessage()
```

daje samo jedan deo priče.

Mentalno:

```text
string message
→ simptom

exception object
→ simptom + poreklo + trag
```

# 12. Logging & Practical Debugging Workflow — Part 2

## 11. Request ID / Correlation ID

U production-u mnogo request-a može istovremeno proizvoditi logove.

Na primer:

```text
10:15:03 booking started
10:15:03 login success
10:15:03 SQL failed
10:15:03 email sent
```

Kako znamo šta pripada istom request-u?

Možemo generisati:

```text
request_id
```

na početku request-a.

Na primer:

```php
$requestId = bin2hex(
    random_bytes(8)
);
```

pa ga dodavati u log context:

```php
$logger->error(
    'Booking failed.',
    [
        'request_id' => $requestId,
        'user_id' => $userId,
        'exception' => $e,
    ]
);
```

Sada možemo povezati sve događaje:

```text
request_id = abc123
```

Mentalno:

```text
jedan HTTP request
→ jedan correlation/request ID
→ svi logovi mogu da se povežu
```

---

## 12. Šta NE treba logovati

Ovo je veoma važno.

Ne logujemo:

```text
plain password
password hash
reset token
remember-me validator
session ID
CSRF token
API secret
private key
authorization header
full credit card data
```

Na primer, nikada:

```php
$logger->debug(
    'Login attempt.',
    [
        'email' => $email,
        'password' => $password,
    ]
);
```

Password nije debugging podatak.

To je credential.

Isto važi za:

```text
session ID
remember token
password reset token
```

jer njihova krađa može dati pristup nalogu.

Mentalno:

```text
logovi su često dugotrajni
+
više ljudi/sistema može imati pristup
↓
secrets ne smeju u log
```

---

## 13. PII i minimalni context

Ni podatke koji nisu credentials ne treba logovati bez razloga.

Na primer:

```text
ime
email
telefon
adresa
IP
```

mogu biti lični podaci.

Često je dovoljno:

```php
[
    'user_id' => 17,
]
```

umesto:

```php
[
    'name' => '...',
    'email' => '...',
    'phone' => '...',
    'address' => '...',
]
```

Princip:

> Loguj minimum informacija koje su potrebne da se problem dijagnostikuje.

Security/privacy deo ćemo još dublje obrađivati u sledećem modulu.

---

## 14. Stack trace čitaj odozdo ka uzroku i kroz call chain

Kada vidiš stack trace, nemoj se uplašiti količine teksta.

Traži:

```text
exception class
message
original file
original line
```

zatim prati:

```text
ko je pozvao problematičnu metodu?
ko je pozvao njega?
kako je request stigao do tog mesta?
```

Na primer:

```text
PDOException
at PdoBookingRepository.php:84

#0 PDOStatement->execute()
#1 PdoBookingRepository->create()
#2 BookingService->book()
#3 BookingController->store()
#4 Router->dispatch()
```

Mentalno:

```text
symptom
↓
repository
↓
service
↓
controller
↓
request
```

Stack trace je mapa puta do failure-a.

---

## 15. Prvo reprodukuj problem

Jedan od najvažnijih debugging principa:

> Ne menjaj kod nasumično pre nego što razumeš kako da ponoviš problem.

Ako bug glasi:

```text
"Booking ponekad ne može da se kreira."
```

prvo utvrdi:

```text
Koji hotel?
Koja soba?
Koji datumi?
Koji user?
Da li se dešava samo pri concurrency?
Da li se dešava lokalno?
Da li postoji specifičan log?
```

Tek onda:

```text
reproduce
↓
observe
↓
form hypothesis
↓
test hypothesis
```

Ne:

```text
guess
↓
change code
↓
hope
```

---

## 16. Minimal reproduction

Ako veliki use case ima problem, pokušaj da ga svedeš na najmanji primer.

Na primer:

```text
BookingService
+ 8 repository metoda
+ email
+ notification
+ inventory
```

možda je previše.

Ako sumnjaš na query:

```php
$stmt = $pdo->prepare(...);
$stmt->execute(...);
```

testiraj upravo taj deo sa minimalnim inputom.

Mentalno:

```text
veliki problem
↓
izoluj najmanji failure
↓
lakše vidi uzrok
```

Ovo je posebno korisno kod:

```text
SQL
transactions
date calculations
type problems
```

---

## 17. `var_dump()` je alat, ne strategija

`var_dump()` je koristan:

```php
var_dump($user);
var_dump($booking);
var_dump($result);
```

kada želiš brzo da vidiš:

```text
tip
vrednost
strukturu
```

Ali ako debugging izgleda ovako:

```php
var_dump('A');
var_dump('B');
var_dump('C');
var_dump('D');
die();
```

po celoj aplikaciji, brzo postaje haotično.

Koristi ga za:

```text
brzu lokalnu proveru
```

ne kao trajnu observability strategiju.

Posle debugging-a:

```text
ukloni privremene dump-ove
```

---

## 18. `die()` / `exit()` debugging

Početnički debugging često izgleda:

```php
var_dump($data);
die();
```

To može biti sasvim korisno lokalno.

Ali problem je:

```text
prekida ceo lifecycle
```

pa ne vidiš:

```text
šta bi se desilo kasnije
da li bi transaction rollback-ovao
da li bi middleware završio
da li bi response bio pravilno napravljen
```

Koristi ga ciljano.

Ako debugging zahteva praćenje celog flow-a, logger ili breakpoint je često bolji.

---

## 19. Xdebug mentalni model

Debugger poput Xdebug-a omogućava da:

```text
zaustaviš execution
↓
pogledaš promenljive
↓
ideš liniju po liniju
↓
uđeš u pozvanu metodu
↓
izađeš iz metode
↓
pratiš call stack
```

To znači da umesto:

```php
var_dump($x);
var_dump($y);
var_dump($z);
```

možeš postaviti breakpoint i direktno videti stanje programa.

Najvažniji koncepti:

```text
breakpoint
step over
step into
step out
watch variables
call stack
```

Ne moraš odmah postati Xdebug ekspert.

Bitno je razumeti da je debugger:

```text
interaktivni pogled u runtime state
```

---

## 20. Sistematičan debugging workflow

Dobar workflow može izgledati:

```text
1. Precizno definiši simptom

2. Reprodukuj problem

3. Pronađi relevantan log / exception

4. Pročitaj exception class + message

5. Pogledaj file + line

6. Pročitaj stack trace

7. Proveri relevantan input/state

8. Napravi hipotezu

9. Testiraj samo jednu hipotezu

10. Ispravi root cause

11. Ponovi originalni scenario

12. Dodaj test ako bug može da se vrati
```

Na primer:

```text
"Password reset vraća 500"
↓
reproduce
↓
log kaže PDOException
↓
PasswordResetService line 74
↓
ResetTokenRepository::deleteForUser()
↓
SQL koristi pogrešno ime kolone
↓
fix
↓
ponovi
↓
test
```

Ovo je debugging.

Ne:

```text
"verovatno session"
↓
promeni session
↓
nije
↓
promeni controller
↓
nije
↓
promeni repository
```

# Najvažnije za zapamtiti

Error handling:

```text
šta aplikacija radi sa failure-om
```

Debugging:

```text
kako developer pronalazi uzrok failure-a
```

Logging treba da sadrži:

```text
jasan message
+
koristan context
+
exception object kada postoji
```

Najvažniji nivoi:

```text
DEBUG
→ detalji

INFO
→ normalan značajan događaj

WARNING
→ neobično stanje

ERROR
→ operacija nije uspela

CRITICAL
→ ozbiljan sistemski problem
```

Ne loguj secrets:

```text
password
password hash
session ID
CSRF token
reset token
remember validator
API secret
```

Koristi minimum potrebnog context-a.

Request/correlation ID pomaže da povežeš sve logove jednog request-a:

```text
request_id
→ jedna request priča
```

Stack trace čitaj kao:

```text
gde je puklo?
↓
ko je to pozvao?
↓
kako je request stigao tamo?
```

Najvažniji debugging princip:

```text
prvo reprodukuj
onda menjaj
```

Dobar workflow:

```text
symptom
↓
reproduce
↓
observe
↓
trace
↓
hypothesis
↓
test
↓
fix root cause
↓
verify
↓
regression test
```

`var_dump()` i `die()` su korisni lokalni alati, ali nisu zamena za:

```text
logging
stack trace
debugger
tests
```

Centralni mentalni model lekcije:

```text
Log
→ ostavlja trag

Stack trace
→ pokazuje put

Debugger
→ pokazuje trenutno stanje

Test
→ sprečava da se isti bug vrati
```
