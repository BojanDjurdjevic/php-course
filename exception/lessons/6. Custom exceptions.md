# 6. Custom Exceptions — Part 1

## 1. Zašto pravimo custom exceptions

Možemo svuda pisati:

```php
throw new RuntimeException(
    'Something went wrong.'
);
```

ili:

```php
throw new DomainException(
    'Invalid operation.'
);
```

Ali time gubimo značenje.

Pogledaj razliku:

```php
throw new DomainException(
    'Email already taken.'
);
```

i:

```php
throw new DuplicateEmailException();
```

Drugi oblik odmah govori:

```text
šta se tačno dogodilo
```

bez čitanja message-a.

Custom exception nam daje:

```text
semantiku
čitljivost
precizniji catch
lakše mapiranje
bolje testove
```

---

## 2. Exception class je deo jezika aplikacije

Ako imamo:

```php
final class DuplicateEmailException
    extends DomainException
{
}
```

onda kod:

```php
throw new DuplicateEmailException();
```

govori:

```text
registration ne može da nastavi
jer email već postoji
```

To je mnogo jače od:

```php
throw new RuntimeException(
    'Problem with email.'
);
```

Mentalno:

```text
custom exception
→ imenovani failure scenario
```

Dobar naziv exception-a često opisuje ceo problem bez dodatnog komentara.

---

## 3. Minimalna custom exception klasa

Najjednostavnije:

```php
final class DuplicateEmailException
    extends DomainException
{
}
```

To je sasvim validna klasa.

Dobijamo sve standardne metode:

```php
$e->getMessage();
$e->getCode();
$e->getFile();
$e->getLine();
$e->getPrevious();
$e->getTraceAsString();
```

jer ih nasleđujemo iz standardne exception hijerarhije.

Ne moramo automatski pisati sopstveni constructor.

---

## 4. Kada dodati sopstveni constructor

Ako želimo konzistentan message:

```php
final class DuplicateEmailException
    extends DomainException
{
    public function __construct(
        string $email,
        ?Throwable $previous = null
    ) {
        parent::__construct(
            "Email {$email} is already taken.",
            0,
            $previous
        );
    }
}
```

Onda kod postaje:

```php
throw new DuplicateEmailException(
    $email,
    $pdoException
);
```

Prednost:

```text
caller ne mora svaki put da smišlja message
```

i exception svuda ima isti format.

Ali treba paziti da u message ne ubacujemo sensitive podatke koje ne želimo logovati ili prikazivati.

---

## 5. `DomainException` vs `RuntimeException`

Najkorisniji mentalni model:

```text
DomainException
→ business/domain pravilo nije zadovoljeno
```

```text
RuntimeException
→ legitimna operacija nije uspela zbog runtime/infrastructure okolnosti
```

Primer:

```php
throw new BookingCannotBeCancelledException();
```

može prirodno da nasleđuje:

```php
DomainException
```

jer je problem:

```text
booking više nije u stanju koje dozvoljava cancellation
```

Sa druge strane:

```php
throw new UserPersistenceException();
```

češće pripada:

```php
RuntimeException
```

jer:

```text
operacija je bila legitimna
ali persistence nije uspela
```

---

## 6. Primer domain exception-a

```php
final class BookingCannotBeCancelledException
    extends DomainException
{
}
```

Service:

```php
if (!$booking->canBeCancelled()) {
    throw new BookingCannotBeCancelledException();
}
```

Viši sloj može precizno:

```php
catch (BookingCannotBeCancelledException $e) {
    return $response->conflict(
        'Booking can no longer be cancelled.'
    );
}
```

To je mnogo bolje nego:

```php
catch (DomainException $e)
```

ako imamo različite domain probleme sa različitim responses.

---

## 7. Primer infrastructure/application exception-a

```php
final class UserPersistenceException
    extends RuntimeException
{
}
```

Repository:

```php
try {
    $statement->execute();
} catch (PDOException $e) {
    throw new UserPersistenceException(
        'Unable to persist user.',
        0,
        $e
    );
}
```

Mentalno:

```text
PDOException
→ infrastructure detalj

UserPersistenceException
→ application-level meaning
```

Viši sloj ne mora znati za PDO.

---

## 8. Custom exception ne mora značiti user-facing error

Ovo je veoma važno.

Ako imamo:

```php
UserPersistenceException
```

to ne znači da korisniku treba prikazati:

```text
Unable to persist user.
```

Exception class služi internom sistemu.

User-facing response može biti:

```text
Something went wrong.
```

dok logovi sadrže:

```text
UserPersistenceException
previous PDOException
stack trace
```

Dakle:

```text
internal exception semantics
≠
public error message
```

---

## 9. Kada custom exception ima smisla

Custom exception je posebno koristan kada:

```text
isti failure scenario
→ pojavljuje se na više mesta
```

ili:

```text
želiš specifičan catch
```

ili:

```text
želiš mapiranje na HTTP response
```

ili:

```text
želiš da sakriješ infrastructure detalje
```

Na primer:

```text
DuplicateEmailException
BookingNotFoundException
BookingCannotBeCancelledException
InvalidResetTokenException
RememberTokenExpiredException
UserPersistenceException
```

sve imaju jasno značenje.

---

## 10. Kada custom exception nema smisla

Nemoj praviti novu klasu za svaki mogući problem.

Na primer:

```text
UserNameTooShortException
UserNameTooLongException
UserNameContainsSpaceException
UserNameContainsNumberException
```

ako je sve to zapravo obična input validation logika.

Isto tako:

```php
final class SomethingWentWrongException
    extends RuntimeException
{
}
```

ne dodaje skoro nikakvu vrednost.

Pravilo:

> Custom exception treba da predstavlja smislen failure scenario, ne samo novi naziv za generički problem.

# 6. Custom Exceptions — Part 2

## 11. Exception hijerarhija

Možemo napraviti sopstvenu hijerarhiju.

Na primer:

```php
abstract class AuthenticationException
    extends RuntimeException
{
}
```

pa:

```php
final class InvalidCredentialsException
    extends AuthenticationException
{
}
```

```php
final class SuspendedAccountException
    extends AuthenticationException
{
}
```

```php
final class UnverifiedEmailException
    extends AuthenticationException
{
}
```

Sada možemo:

```php
catch (InvalidCredentialsException $e) {
    ...
}
```

ili šire:

```php
catch (AuthenticationException $e) {
    ...
}
```

u zavisnosti od potrebe.

---

## 12. Dobra hijerarhija prati semantiku

Ne treba praviti hijerarhiju samo radi nasleđivanja.

Loše:

```text
AppException
└── ServiceException
    └── AuthServiceException
        └── LoginServiceException
```

ako ti parent klase ništa semantički ne znače.

Bolje:

```text
AuthenticationException
├── InvalidCredentialsException
├── SuspendedAccountException
└── UnverifiedEmailException
```

jer parent govori:

```text
ovo su authentication failures
```

Hijerarhija treba da podrži smislen catch.

---

## 13. Marker base exception

Nekad ima smisla imati:

```php
abstract class DomainException
    extends \DomainException
{
}
```

ili:

```php
interface ApplicationException
{
}
```

ali treba biti oprezan da ne komplikujemo sistem bez potrebe.

Na primer:

```php
interface PublicException
{
}
```

može označavati exception-e koje global handler sme da mapira u kontrolisan public response.

Ali za manju Vanilla PHP aplikaciju često je dovoljno koristiti postojeće base klase plus nekoliko smislenih custom exception-a.

---

## 14. Exception class vs error code

Možemo imati:

```php
throw new DomainException(
    'Email already taken.',
    1001
);
```

ali onda svi moraju znati:

```text
1001 = duplicate email
```

To je manje čitljivo od:

```php
throw new DuplicateEmailException();
```

Class-based handling:

```php
catch (DuplicateEmailException $e)
```

je obično mnogo jasniji od:

```php
if ($e->getCode() === 1001)
```

Exception code ima svoje mesto, ali ne treba ga koristiti kao zamenu za dobru exception semantiku.

---

## 15. Exception class vs return result

Nije svaki failure automatski exception.

Na primer:

```php
public function attempt(
    string $email,
    string $password
): bool
```

može normalno koristiti:

```text
true
false
```

jer invalid credentials mogu biti deo očekivanog contract-a.

Ali:

```php
public function createBooking(...): Booking
```

ako booking više nije dostupan, može smislenije:

```php
throw new NoAvailabilityException();
```

Dakle pitamo:

```text
da li je failure deo normalnog return contract-a?
```

Ako jeste, return value može biti dovoljan.

Ako prekida očekivani use case na semantički značajan način, custom exception često ima više smisla.

---

## 16. Custom exception i HTTP status nisu ista stvar

Na primer:

```php
DuplicateEmailException
```

nije inherentno:

```text
422
```

ili:

```text
409
```

Exception opisuje application problem.

HTTP sloj odlučuje kako se taj problem mapira.

Na primer:

```text
DuplicateEmailException
↓
Web form
→ validation-style 422

API create resource
→ 409 Conflict
```

Dakle:

```text
exception
→ application semantics

HTTP status
→ transport semantics
```

Ova separacija je veoma važna.

---

## 17. Custom exception ne treba da zna za redirect

Loše:

```php
final class DuplicateEmailException
    extends DomainException
{
    public function redirectTo(): string
    {
        return '/register';
    }
}
```

Time domain/application exception zna za HTTP/UI.

Bolje:

```text
DuplicateEmailException
→ samo opisuje problem
```

Controller ili global handler odlučuje:

```text
redirect?
JSON?
HTTP status?
flash message?
```

To čuva separation of concerns.

---

## 18. Primer dobre registracione arhitekture

Repository:

```php
try {
    $statement->execute();
} catch (PDOException $e) {
    if ($this->isDuplicateEmail($e)) {
        throw new DuplicateEmailException(
            $email,
            $e
        );
    }

    throw new UserPersistenceException(
        'Unable to create user.',
        0,
        $e
    );
}
```

Service:

```php
public function register(...): User
{
    return $this->users->create(...);
}
```

Controller:

```php
try {
    $user = $this->registration->register(...);
} catch (DuplicateEmailException $e) {
    // expected application response
}
```

Global handler:

```text
UserPersistenceException
→ log
→ 500
```

Mentalno:

```text
Repository
→ prevodi infrastructure meaning

Service
→ orkestrira use case

Controller
→ prevodi application meaning u HTTP/UI

Global handler
→ fallback
```

---

## 19. Testiranje custom exception-a

Custom exception klase čine testove preciznijim.

Na primer:

```php
$this->expectException(
    DuplicateEmailException::class
);
```

pa:

```php
$service->register(
    'Bojan',
    'taken@example.com',
    'password'
);
```

To je mnogo jače nego testirati:

```php
$this->expectException(
    RuntimeException::class
);
```

jer sada test potvrđuje:

```text
tačan failure scenario
```

a ne samo da je "nešto puklo".

---

## 20. Kako birati custom exception

Najbolje pitanje je:

> Da li ovaj problem ima posebno značenje koje viši sloj treba da razlikuje?

Ako da:

```text
custom exception ima smisla
```

Ako ne:

```text
generički parent exception može biti dovoljan
```

Primeri gde ima smisla:

```text
DuplicateEmailException
BookingNotFoundException
BookingConflictException
InvalidResetTokenException
SuspendedAccountException
```

Primeri gde možda nema:

```text
SomethingBadException
GenericServiceException
OperationFailedException
```

ako ne dodaju ništa.

# Najvažnije za zapamtiti

Custom exception služi da:

```text
problem dobije ime
```

Primer:

```php
throw new DuplicateEmailException();
```

je mnogo semantičkiji od:

```php
throw new RuntimeException(
    'Problem.'
);
```

Najčešći izbor parent klase:

```text
DomainException
→ business/domain rule violated
```

```text
RuntimeException
→ runtime/infrastructure/application operation failed
```

Custom exception ne znači automatski:

```text
prikaži njegov message user-u
```

Internal exception:

```text
developer / application semantics
```

User-facing response:

```text
HTTP/UI odluka
```

Dobra exception hijerarhija:

```text
prati semantiku
i omogućava smislen catch
```

Na primer:

```text
AuthenticationException
├── InvalidCredentialsException
├── SuspendedAccountException
└── UnverifiedEmailException
```

Nemoj praviti custom exception za svaki sitni validation problem.

Nemoj koristiti exception code kao zamenu za dobro ime klase kada class-based handling bolje izražava nameru.

Exception nije HTTP response.

```text
exception
→ šta se dogodilo u aplikaciji

controller/global handler
→ kako to izgleda preko HTTP-a
```

Najvažniji mentalni model:

```text
custom exception
→ imenovani failure scenario

parent exception
→ grupa srodnih failure scenario-a

catch
→ reakcija na smislen application problem
```
