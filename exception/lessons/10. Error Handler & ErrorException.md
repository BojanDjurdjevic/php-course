# 10. PHP Error Handler & `ErrorException` — Part 1

## 1. `set_exception_handler()` nije cela priča

U prethodnoj lekciji napravili smo:

```php
set_exception_handler(
    function (\Throwable $e): void {
        // log
        // response
    }
);
```

To rešava neobrađene:

```text
Exception
+
Error
```

koji implementiraju:

```text
Throwable
```

Ali PHP ima i tradicionalni error sistem:

```text
warning
notice
deprecated
user warning
user notice
...
```

Na primer:

```php
$content = file_get_contents(
    '/file/that/does/not/exist.txt'
);
```

`file_get_contents()` tradicionalno može proizvesti:

```text
E_WARNING
```

To nije automatski isto što i:

```php
throw new RuntimeException();
```

Dakle imamo dve paralelne stvari:

```text
Throwable system
→ Exception / Error

traditional PHP error system
→ warning / notice / deprecated...
```

`set_error_handler()` nam omogućava da kontrolišemo ovaj drugi svet.

---

## 2. Šta je PHP error level

PHP tradicionalne greške imaju različite severity nivoe.

Česti primeri:

```text
E_WARNING
E_NOTICE
E_DEPRECATED
E_USER_WARNING
E_USER_NOTICE
E_USER_DEPRECATED
```

Postoje i ozbiljniji nivoi poput:

```text
E_ERROR
E_PARSE
E_CORE_ERROR
E_COMPILE_ERROR
```

ali važno je odmah znati:

> `set_error_handler()` ne može pouzdano preuzeti sve moguće PHP failure kategorije.

Posebno fatalne, startup, parsing i compile-time probleme ne treba zamišljati kao obične runtime warnings koje ćemo jednostavno pretvoriti u exception.

Za njih ćemo u sledećoj lekciji govoriti o:

```text
shutdown handling
PHP configuration
server logs
```

Za sada:

```text
set_error_handler()
→ runtime PHP errors koje user-defined handler može presresti
```

---

## 3. `set_error_handler()`

Osnovna sintaksa:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        // handling

        return true;
    }
);
```

PHP našem handler-u daje:

```text
severity
→ koji tip greške

message
→ opis

file
→ gde je nastala

line
→ na kojoj liniji
```

Na primer:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        echo "PHP problem: {$message}";

        return true;
    }
);
```

Mentalno:

```text
PHP runtime warning
↓
registered error handler
↓
naša odluka šta dalje
```

---

## 4. Drugi argument određuje koje nivoe želimo

Možemo registrovati handler za određene error levele:

```php
set_error_handler(
    $handler,
    E_WARNING | E_NOTICE
);
```

Mentalno:

```text
E_WARNING
OR
E_NOTICE
```

Bitwise `|` ovde kombinuje error masks.

Možemo koristiti i:

```php
E_ALL
```

ako želimo širok handler.

Na primer:

```php
set_error_handler(
    $handler,
    E_ALL
);
```

Ali:

```text
E_ALL
```

ne znači:

> sada magično možemo obraditi baš svaki mogući PHP fatal problem.

Samo određuje koje error kategorije želimo proslediti handler-u među onima koje handler uopšte može da preuzme.

---

## 5. Šta znači `return true`

Primer:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        error_log($message);

        return true;
    }
);
```

`true` konceptualno znači:

```text
"Obradio sam ovu grešku."
```

PHP tada ne treba da nastavi sa svojim normalnim/default error handling-om za taj slučaj.

Mentalno:

```text
PHP warning
↓
custom handler
↓
return true
↓
problem smatramo obrađenim
```

Ali ovo ima opasnost.

Ako samo:

```php
return true;
```

a ne uradimo ništa smisleno, možda smo upravo sakrili problem.

---

## 6. `return false` delegira PHP-u

Možemo napisati:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        if ($severity === E_DEPRECATED) {
            return false;
        }

        // naš handling

        return true;
    }
);
```

`false` znači približno:

```text
"Ja ovu grešku neću obraditi;
neka PHP nastavi sa standardnim handler-om."
```

Dakle:

```text
return true
→ handled here

return false
→ delegate/default PHP handling
```

Ovo je veoma korisno kada ne želimo da custom handler preuzme baš sve kategorije.

---

## 7. Zašto uopšte pretvarati PHP error u exception

Pretpostavimo:

```php
$content = file_get_contents(
    '/missing/config.json'
);
```

Dobijemo warning.

Problem je što naša application arhitektura već mnogo bolje razume:

```text
Throwable
↓
catch
↓
global handler
↓
logging
↓
response
```

Bilo bi lepo kada bismo warning mogli pretvoriti u nešto što ulazi u isti pipeline.

Tu dolazi:

```php
ErrorException
```

Mentalno:

```text
PHP warning
↓
set_error_handler()
↓
ErrorException
↓
Throwable pipeline
```

To je most između dva sistema.

---

## 8. `ErrorException`

`ErrorException` je standardna PHP exception klasa.

Možemo:

```php
throw new ErrorException(
    $message,
    0,
    $severity,
    $file,
    $line
);
```

Važno je da joj prosledimo:

```text
message
severity
file
line
```

jer tako zadržavamo originalni error context.

Primer handler-a:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): never {
        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    }
);
```

Sada tradicionalni PHP warning možemo dobiti kao:

```text
ErrorException
```

koji pripada `Throwable` svetu.

---

## 9. Kompletan tok warning → global handler

Bootstrap:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): never {
        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    }
);

set_exception_handler(
    function (\Throwable $e): void {
        error_log(
            $e->__toString()
        );

        http_response_code(500);

        echo 'Something went wrong.';
    }
);
```

Aplikacija:

```php
file_get_contents(
    '/missing/file.txt'
);
```

Mentalno:

```text
file_get_contents()
↓
E_WARNING
↓
set_error_handler()
↓
throw ErrorException
↓
nije lokalno catch-ovan
↓
set_exception_handler()
↓
log
↓
500
```

Sada imamo jedan mnogo konzistentniji error pipeline.

---

## 10. Zašto je ovo moćno

Bez konverzije:

```text
warning
→ jedan PHP mehanizam

exception
→ drugi PHP mehanizam
```

Sa konverzijom:

```text
warning
↓
ErrorException
↓
Throwable
```

dobijamo mogućnost da koristimo već poznate obrasce:

```text
try/catch
exception propagation
global handler
logging
stack trace
```

Drugim rečima:

```text
traditional PHP error
→ normalizujemo u exception architecture
```

Ali ovo ne znači da treba potpuno bez razmišljanja svaku PHP poruku pretvoriti u fatalan application exception.

To je sledeća važna nijansa.

# 10. PHP Error Handler & `ErrorException` — Part 2

## 11. Ne treba svaki error level tretirati isto

Pretpostavimo da registrujemo:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): never {
        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    },
    E_ALL
);
```

Sada i:

```text
warning
notice
deprecated
```

mogu potencijalno promeniti application flow.

To može biti korisno u development-u jer:

```text
problem koji bismo možda ignorisali
→ postaje veoma vidljiv
```

Ali u velikoj aplikaciji ili third-party biblioteci može biti previše agresivno.

Na primer:

```text
E_DEPRECATED
```

često znači:

> Ovaj API će u budućnosti biti problematičan.

Ne nužno:

> Ovaj request odmah mora da završi kao 500.

Zato error policy treba biti namerna odluka.

---

## 12. Provera `error_reporting()`

Čest robustan obrazac je:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        if (!(error_reporting() & $severity)) {
            return false;
        }

        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    }
);
```

Ovim proveravamo:

```text
da li je konkretni severity trenutno uključen
u aktivni error_reporting policy
```

Ako nije:

```php
return false;
```

Ako jeste:

```text
pretvori ga u ErrorException
```

Mentalno:

```text
PHP error
↓
da li policy želi da ga tretira?
├── NE → default/delegation
└── DA → ErrorException
```

---

## 13. `ErrorException::getSeverity()`

Pošto smo originalni severity prosledili:

```php
new ErrorException(
    $message,
    0,
    $severity,
    $file,
    $line
);
```

kasnije možemo dobiti:

```php
$e->getSeverity();
```

Na primer:

```php
catch (ErrorException $e) {
    if ($e->getSeverity() === E_WARNING) {
        // warning-specific handling
    }
}
```

Dakle nismo izgubili informaciju da je originalno bilo:

```text
E_WARNING
```

iako sada imamo:

```text
ErrorException
```

---

## 14. Warning nije uvek bug

Na primer:

```php
file_get_contents(
    '/optional/cache/file.txt'
);
```

Ako fajl ne postoji, to možda predstavlja:

```text
expected cache miss
```

U tom slučaju možda nije najbolji dizajn da pustimo PHP da proizvede warning pa da ga globalno pretvorimo u 500.

Bolje je koristiti API i application logiku koja eksplicitno tretira očekivani scenario.

Mentalno:

```text
expected application state
→ handle explicitly

unexpected PHP warning
→ error handler / ErrorException
```

Drugim rečima:

> Nemoj koristiti globalni error handler kao zamenu za normalnu business logiku.

---

## 15. Primer: file operation

Lošiji pristup:

```php
try {
    $content = file_get_contents(
        $path
    );
} catch (ErrorException $e) {
    return null;
}
```

ako je missing file normalna situacija koju smo mogli proveriti kroz jasniji application contract.

Možemo imati:

```php
if (!is_file($path)) {
    return null;
}
```

pa onda:

```php
$content = file_get_contents($path);
```

A ako `file_get_contents()` ipak neočekivano padne zbog permissions ili drugog runtime problema:

```text
ErrorException
→ propagation
```

To razdvaja:

```text
expected absence
od
unexpected IO failure
```

---

## 16. `trigger_error()`

Možemo i sami proizvesti traditional PHP error:

```php
trigger_error(
    'Legacy configuration detected.',
    E_USER_WARNING
);
```

Tipični user-level tipovi:

```text
E_USER_NOTICE
E_USER_WARNING
E_USER_DEPRECATED
E_USER_ERROR
```

Ako imamo custom error handler, i oni mogu proći kroz njega.

Mentalno:

```text
our code
↓
trigger_error()
↓
PHP error system
↓
set_error_handler()
```

U modernom OOP application code-u često je semantički jasnije koristiti exception kada želimo prekinuti use case.

Ali `trigger_error()` i dalje postoji i može biti koristan za:

```text
library warnings
deprecation notices
legacy integrations
```

---

## 17. `ErrorException` nije isto što i `Error`

Ovo je važno zbog imena.

Imamo:

```text
Throwable
├── Error
└── Exception
    └── ErrorException
```

Dakle:

```php
ErrorException
```

uprkos nazivu pripada:

```text
Exception branch
```

a ne:

```text
Error branch
```

Mentalno:

```text
TypeError
→ Error

ErrorException
→ Exception
```

`ErrorException` koristimo kao wrapper za traditional PHP error.

---

## 18. Global error handler vs local `try/catch`

Ako globalno pretvaramo warning u `ErrorException`:

```php
set_error_handler(...);
```

i znamo da određena operacija može dati takav failure, možemo lokalno:

```php
try {
    $content = file_get_contents(
        $path
    );
} catch (ErrorException $e) {
    // samo ako ovde stvarno znamo kako da reagujemo
}
```

Ako ne znamo:

```text
ne catch-ujemo
↓
global exception handler
```

Dakle ista lekcija kao ranije:

> Samo zato što smo error pretvorili u exception ne znači da ga moramo lokalno catch-ovati.

---

## 19. Šta `set_error_handler()` ne rešava

Ne treba imati mentalni model:

```text
set_error_handler(E_ALL)
→ uhvatiće apsolutno sve PHP probleme
```

Neće.

Postoje kategorije problema koje se dešavaju:

```text
pre nego što runtime handler može normalno da reaguje
ili
na nivou koji user-defined error handler ne može standardno preuzeti
```

Na primer ozbiljni:

```text
parse
compile
startup
fatal
```

scenariji zahtevaju drugačiji pristup.

Zato ćemo imati:

```text
set_error_handler()
+
set_exception_handler()
+
register_shutdown_function()
+
PHP/server logging
```

kao različite slojeve.

## 20. Kompletna Vanilla PHP error infrastruktura do sada

Bootstrap konceptualno postaje:

```php
require_once __DIR__
    . '/../vendor/autoload.php';

set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        if (!(error_reporting() & $severity)) {
            return false;
        }

        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    }
);

set_exception_handler(
    function (\Throwable $e): void {
        error_log(
            $e->__toString()
        );

        http_response_code(500);

        echo 'Something went wrong.';
    }
);

$app->run();
```

Mentalna mapa:

```text
PHP warning / notice
↓
set_error_handler()
↓
ErrorException
↓
Throwable pipeline
↓
local catch?
├── DA → local handling
└── NE
    ↓
    set_exception_handler()
    ↓
    log + response
```

To je već veoma ozbiljna Vanilla PHP error architecture.

# Najvažnije za zapamtiti

`set_exception_handler()` i `set_error_handler()` rešavaju različite ulaze.

```text
set_exception_handler()
→ unhandled Throwable
```

```text
set_error_handler()
→ tradicionalni PHP error levels
  koje user handler može da presretne
```

Traditional PHP error može biti:

```text
E_WARNING
E_NOTICE
E_DEPRECATED
E_USER_WARNING
...
```

Možemo ga pretvoriti u:

```php
ErrorException
```

i time dobiti:

```text
PHP error
↓
ErrorException
↓
Throwable architecture
```

Tipičan obrazac:

```php
set_error_handler(
    function (
        int $severity,
        string $message,
        string $file,
        int $line
    ): bool {
        if (!(error_reporting() & $severity)) {
            return false;
        }

        throw new ErrorException(
            $message,
            0,
            $severity,
            $file,
            $line
        );
    }
);
```

`return true` znači:

```text
custom handler je obradio problem
```

`return false`:

```text
prepusti standardnom PHP handling-u
```

`ErrorException` nije `Error`.

Hijerarhija:

```text
Throwable
├── Error
│   └── TypeError
│
└── Exception
    └── ErrorException
```

Ne pretvaraj slepo svaki warning/deprecation u request-fatal exception bez razmišljanja o policy-ju.

Expected application situacije treba rešavati kroz jasan application flow, a ne oslanjanjem na PHP warning kao business control flow.

I najvažnije:

```text
set_error_handler()
nije poslednja zaštita od svih PHP problema
```

Zato sledeći sloj arhitekture postaje:

```text
fatal/startup/compile problems
↓
shutdown handling
+
PHP configuration
+
server logs
```
