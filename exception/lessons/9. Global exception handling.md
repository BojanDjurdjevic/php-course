# 9. Global Exception Handling — Part 1

## 1. Zašto nam treba global exception handler

Do sada smo imali mentalni model:

```text
Repository
↓
Service
↓
Controller
```

Ako negde nastane exception:

```text
Repository
↑
Service
↑
Controller
```

i nijedan sloj ga ne `catch`-uje, exception nastavlja da se propagira.

Bez centralnog handler-a završavamo sa:

```text
Uncaught PDOException...
Stack trace...
```

ili sličnim PHP output-om.

To nije ono što želimo u ozbiljnoj aplikaciji.

Treba nam poslednja granica:

```text
Request
↓
Middleware
↓
Controller
↓
Service
↓
Repository
↓
Throwable
↑
↑
↑
Global Exception Handler
↓
log
↓
safe HTTP response
```

Global handler kaže:

> Ako niko konkretniji nije znao šta da uradi sa problemom, ja garantujem da request neće završiti nekontrolisano.

---

## 2. `set_exception_handler()`

PHP nam daje:

```php
set_exception_handler(
    callable $callback
);
```

Na primer:

```php
set_exception_handler(
    function (\Throwable $e): void {
        http_response_code(500);

        echo 'Something went wrong.';
    }
);
```

Sada ako se desi:

```php
throw new RuntimeException(
    'Database unavailable.'
);
```

a niko ga pre toga ne catch-uje, PHP poziva naš handler.

Mentalno:

```text
Unhandled Throwable
↓
set_exception_handler callback
↓
final handling
```

---

## 3. Handler treba registrovati rano u bootstrap-u

Global handler nema mnogo koristi ako ga registrujemo tek pred kraj aplikacije.

Tipičan bootstrap:

```php
<?php

require_once __DIR__ . '/../vendor/autoload.php';

set_exception_handler(
    function (\Throwable $e): void {
        // final handling
    }
);

$session->start();

$router->dispatch();
```

Želimo ga registrovati pre glavnog application flow-a.

Mentalno:

```text
bootstrap
↓
register handlers
↓
initialize app
↓
dispatch request
```

Tako najveći deo runtime lifecycle-a već ima centralnu zaštitu.

---

## 4. Global handler prima `Throwable`

Najčešće želimo:

```php
function handleException(
    \Throwable $e
): void {
}
```

Zašto ne samo:

```php
\Exception
```

?

Jer:

```text
Throwable
├── Error
└── Exception
```

Global boundary treba da vidi i:

```text
PDOException
RuntimeException
DomainException
```

i:

```text
TypeError
ValueError
ArgumentCountError
```

ako su ostali neobrađeni.

Zato je upravo global handler jedno od mesta gde je:

```php
\Throwable
```

prirodan tip.

---

## 5. Global handler nije zamena za lokalni handling

Pogrešan zaključak bi bio:

> Ako imamo global handler, više nam ne trebaju `try/catch` blokovi.

Ne.

Na primer:

```text
DuplicateEmailException
```

Controller možda zna:

```text
flash error
↓
redirect /register
```

To je bolji handling nego da exception ode globalnom handler-u.

Ili Service zna:

```text
Throwable
↓
rollback transaction
↓
rethrow
```

Global handler ne može naknadno vratiti već delimično izvršenu transaction ako je transaction boundary bio niže i nije pravilno obrađen.

Dakle:

```text
local catch
→ specifična odgovornost

global handler
→ poslednja zaštitna mreža
```

---

## 6. Prva odgovornost: stabilan HTTP response

Minimalni production handler:

```php
set_exception_handler(
    function (\Throwable $e): void {
        http_response_code(500);

        echo 'Internal Server Error';
    }
);
```

Bez njega korisnik bi mogao dobiti:

```text
Fatal error...
Stack trace...
/var/www/app/src/...
SQLSTATE...
```

Sa handler-om:

```text
HTTP/1.1 500 Internal Server Error

Something went wrong.
```

To je kontrolisan response.

Važno:

```text
unexpected internal failure
→ 500
```

je dobar fallback.

---

## 7. Druga odgovornost: logovanje

Ako korisniku kažemo samo:

```text
Something went wrong.
```

developer ipak mora znati šta se zapravo dogodilo.

Zato global handler tipično loguje:

```php
set_exception_handler(
    function (\Throwable $e): void {
        error_log(
            $e->__toString()
        );

        http_response_code(500);

        echo 'Something went wrong.';
    }
);
```

`__toString()` za exception obično uključuje mnogo korisnog context-a:

```text
exception class
message
stack trace
```

Za ozbiljniju aplikaciju koristili bismo logger umesto direktnog:

```php
error_log()
```

ali mentalni model je isti.

---

## 8. User-facing poruka i log nisu isto

Ovo je jedna od najvažnijih granica.

User:

```text
Something went wrong.
```

Log:

```text
PDOException
SQLSTATE...
file
line
stack trace
previous exception
```

Nikada ne želimo princip:

```php
echo $e->getMessage();
```

za svaki production exception.

Jer message može sadržati:

```text
SQL
table names
filesystem paths
driver details
internal class names
```

Mentalno:

```text
public response
→ minimum necessary information

internal log
→ maximum useful diagnostic information
```

---

## 9. Development i production nisu isti

U development okruženju želimo detalje.

Na primer:

```php
if ($environment === 'development') {
    echo '<pre>';
    echo htmlspecialchars(
        $e->__toString(),
        ENT_QUOTES,
        'UTF-8'
    );
    echo '</pre>';

    return;
}
```

To može pomoći da odmah vidimo:

```text
exception class
message
file
line
trace
```

Ali u production-u:

```php
http_response_code(500);

echo 'Something went wrong.';
```

Dakle:

```text
DEVELOPMENT
→ visibility

PRODUCTION
→ confidentiality + safe UX
```

Framework-i upravo ovo rade za nas kroz environment/debug konfiguraciju.

---

## 10. `display_errors` nije isto što i logging

PHP ima konfiguracije poput:

```ini
display_errors = On
log_errors = On
```

To nisu ista stvar.

`display_errors` znači:

```text
prikaži PHP grešku/output klijentu
```

`log_errors` znači:

```text
upiši tehnički problem u log
```

U development-u često:

```text
display_errors = On
log_errors = On
```

U production-u tipično želimo:

```text
display_errors = Off
log_errors = On
```

Drugim rečima:

```text
korisnik ne vidi internals
developer/operations ipak imaju dijagnostiku
```

Global handler radi zajedno sa ovim principom, ne protiv njega.

# 9. Global Exception Handling — Part 2

## 11. Da li global handler uvek mora vratiti 500?

Ne nužno.

Možemo centralno mapirati poznate exception tipove.

Na primer:

```php
set_exception_handler(
    function (\Throwable $e): void {
        if ($e instanceof NotFoundException) {
            http_response_code(404);

            echo 'Not Found';

            return;
        }

        if ($e instanceof AuthorizationException) {
            http_response_code(403);

            echo 'Forbidden';

            return;
        }

        error_log($e->__toString());

        http_response_code(500);

        echo 'Something went wrong.';
    }
);
```

Mentalno:

```text
known exception
→ known HTTP mapping

unknown exception
→ 500 fallback
```

To je već početak framework-like exception architecture.

---

## 12. Expected exceptions mogu biti mapirani centralno

Pretpostavimo da imamo:

```php
abstract class NotFoundException
    extends RuntimeException
{
}
```

i:

```php
final class BookingNotFoundException
    extends NotFoundException
{
}
```

```php
final class UserNotFoundException
    extends NotFoundException
{
}
```

Global handler može imati:

```php
if ($e instanceof NotFoundException) {
    http_response_code(404);

    require __DIR__
        . '/../views/errors/404.php';

    return;
}
```

Sada Controllers više ne moraju svaki put:

```php
try {
    ...
} catch (BookingNotFoundException $e) {
    return 404;
}
```

ako svi not-found failure-i imaju isto HTTP ponašanje.

To smanjuje dupliranje.

---

## 13. Ali ne treba sve exception-e centralizovati

Pretpostavimo registration formu.

`DuplicateEmailException` možda treba:

```text
flash validation error
↓
redirect nazad na register
↓
očuvaj form input
```

To je specifično za taj UI flow.

Global handler nema nužno dovoljno context-a da zna:

```text
gde redirect?
koji form field?
šta sa old input?
```

Zato takav problem možda i dalje pripada Controller-u.

Mentalno:

```text
globalno mapiranje
→ kada reakcija važi široko kroz aplikaciju

lokalni catch
→ kada reakcija zavisi od konkretnog use case-a/UI-a
```

---

## 14. Global handler može postati posebna klasa

Umesto closure-a:

```php
set_exception_handler(
    function (\Throwable $e): void {
        ...
    }
);
```

možemo imati:

```php
final class ExceptionHandler
{
    public function handle(
        \Throwable $e
    ): void {
        // classify
        // report
        // render
    }
}
```

Bootstrap:

```php
$handler = new ExceptionHandler();

set_exception_handler(
    [$handler, 'handle']
);
```

To je već mnogo urednije.

Handler sada može imati dependencies:

```php
final class ExceptionHandler
{
    public function __construct(
        private Logger $logger,
        private string $environment
    ) {}
}
```

Ovo je vrlo blizu načinu na koji framework organizuje istu odgovornost.

---

## 15. `report` i `render` su dve različite odgovornosti

Dobra mentalna podela global handler-a:

```text
REPORT
→ šta ćemo zabeležiti?

RENDER
→ šta ćemo poslati klijentu?
```

Na primer:

```php
public function handle(
    \Throwable $e
): void {
    $this->report($e);

    $this->render($e);
}
```

`report()`:

```php
private function report(
    \Throwable $e
): void {
    $this->logger->error(
        'Unhandled exception',
        [
            'exception' => $e,
        ]
    );
}
```

`render()`:

```php
private function render(
    \Throwable $e
): void {
    http_response_code(500);

    require __DIR__
        . '/../../views/errors/500.php';
}
```

Ta separacija kasnije mnogo pomaže.

---

## 16. Ne mora svaki expected exception biti logovan kao ERROR

Pretpostavimo:

```text
BookingNotFoundException
```

i korisnik je samo otvorio URL koji ne postoji.

To možda nije:

```text
ERROR
```

u operativnom smislu.

Ako svaki 404 logujemo kao ozbiljan error:

```text
log postaje pun normalnih request situacija
```

Nasuprot:

```text
PDOException
TypeError
unexpected RuntimeException
```

jesu mnogo relevantniji za error logging.

Zato će kasnije logging imati nivoe poput:

```text
debug
info
warning
error
critical
```

Global handler ne mora sve `Throwable` instance tretirati identično.

---

## 17. Handler ne sme sam napraviti novi haos

Ako unutar global handler-a napišemo komplikovanu logiku koja sama može lako da baci exception:

```php
public function handle(
    \Throwable $e
): void {
    $user = $this->users->findById(...);

    $this->mailer->send(...);

    $this->templates->render(...);
}
```

možemo napraviti problem:

```text
originalni exception
↓
global handler
↓
handler ponovo fail-uje
```

Zato global handler treba da bude relativno robustan.

Posebno fallback path treba biti jednostavan:

```text
log koliko možemo
↓
set status
↓
minimalan safe response
```

Ne želimo da failure handling zavisi od deset drugih sistema koji možda upravo ne rade.

---

## 18. Šta global handler ne može da popravi

Global handler nije vremenska mašina.

Ako je pre exception-a već urađeno:

```text
INSERT booking ✅
SEND email ✅
UPDATE inventory ❌
```

global handler ne može automatski znati kako da vrati sistem u prethodno stanje.

Atomicity se rešava ranije:

```text
Service transaction boundary
```

Global handler samo vidi krajnji failure.

Zato:

```text
transaction integrity
→ Service

final error handling
→ Global Handler
```

To su različite odgovornosti.

---

## 19. Ograničenje: handler mora već biti registrovan

Ako problem nastane pre:

```php
set_exception_handler(...)
```

naš handler ga naravno ne može obraditi.

Takođe postoje greške koje nastanu toliko rano u procesu učitavanja/parsiranja da application-level handler još nije ni stigao da se registruje.

Zato global handler jeste:

```text
poslednja granica aplikacije
```

ali nije apsolutna zaštita od svega što PHP/runtime može ikada da uradi.

Za još niži nivo problema koristićemo:

```text
PHP configuration
error logging
shutdown handling
web server logs
```

što dolazi u narednim lekcijama.

---

## 20. Kompletan Vanilla PHP model

Bootstrap:

```php
<?php

require_once __DIR__
    . '/../vendor/autoload.php';

$logger = new Logger(...);

$handler = new ExceptionHandler(
    $logger,
    $_ENV['APP_ENV']
);

set_exception_handler(
    [$handler, 'handle']
);

$session->start();

$router->dispatch();
```

Handler konceptualno:

```php
final class ExceptionHandler
{
    public function __construct(
        private Logger $logger,
        private string $environment
    ) {}

    public function handle(
        \Throwable $e
    ): void {
        $this->report($e);

        $this->render($e);
    }

    private function report(
        \Throwable $e
    ): void {
        $this->logger->error(
            'Unhandled exception',
            [
                'exception' => $e,
            ]
        );
    }

    private function render(
        \Throwable $e
    ): void {
        if ($e instanceof NotFoundException) {
            http_response_code(404);

            require __DIR__
                . '/../../views/errors/404.php';

            return;
        }

        if ($this->environment === 'development') {
            http_response_code(500);

            echo '<pre>';
            echo htmlspecialchars(
                $e->__toString(),
                ENT_QUOTES,
                'UTF-8'
            );
            echo '</pre>';

            return;
        }

        http_response_code(500);

        require __DIR__
            . '/../../views/errors/500.php';
    }
}
```

Mentalni tok:

```text
Request
↓
Controller
↓
Service
↓
Repository
↓
unexpected Throwable
↑
↑
↑
Global Exception Handler
↓
report
↓
classify
↓
render
↓
HTTP response
```

# Laravel paralela

Kada Laravel dobije unhandled exception, framework već ima centralni exception lifecycle.

Konceptualno:

```text
Throwable
↓
Laravel exception handling infrastructure
↓
report
↓
render
↓
HTTP Response
```

Zato kada se dogodi:

```text
ModelNotFoundException
```

framework može napraviti:

```text
404
```

a kada se dogodi neočekivani:

```text
TypeError
PDO failure
```

može završiti:

```text
500
+
logging
```

U development/debug režimu vidiš detaljan exception ekran.

U production-u korisnik dobija bezbedniji odgovor.

Dakle Laravel nije izmislio drugi princip.

On je već izgradio infrastrukturu koju mi sada ručno pravimo.

# Najvažnije za zapamtiti

Global exception handler je:

```text
poslednja application boundary
za neobrađeni Throwable
```

Registrujemo ga pomoću:

```php
set_exception_handler(
    callable $handler
);
```

Najčešće prima:

```php
\Throwable
```

jer globalna granica treba da obuhvati:

```text
Exception
+
Error
```

Njegove glavne odgovornosti su:

```text
report
→ log / monitoring

render
→ bezbedan HTTP response
```

Development:

```text
više tehničkih detalja
```

Production:

```text
detalji u log
generičan/siguran response korisniku
```

Ne radi:

```php
echo $e->getMessage();
```

automatski u production-u.

Known application exception može centralno postati:

```text
NotFoundException → 404
AuthorizationException → 403
```

dok unknown problem ide:

```text
500
```

Ali lokalni catch i dalje ima smisla kada konkretni sloj zna više.

Na primer:

```text
DuplicateEmailException
→ Controller zna kako da vrati form error
```

Global handler ne zamenjuje:

```text
transaction rollback
business recovery
repository mapping
```

On je final fallback.

Najvažniji mentalni model:

```text
LOCAL HANDLING
→ "znam kako ovaj konkretni problem treba rešiti"

GLOBAL HANDLING
→ "niko ga nije rešio;
   ja garantujem logging
   i kontrolisan finalni response"
```
