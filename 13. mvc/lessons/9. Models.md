# 9. Models — Entity, Data Model i zašto je termin „Model“ zbunjujući

## 1. Najčešća početnička definicija

Vrlo često ćeš videti:

```text
MVC

Model
→ database

View
→ HTML

Controller
→ sve između
```

Ovo je korisno kao prvi crtež.

Ali je previše pojednostavljeno.

Posebno je problematično ovo:

```text
Model = database
```

Jer Model u MVC smislu nije samo:

```text
SQL
tabela
PDO
database row
```

---

# 2. Šta "Model" znači šire

Model predstavlja:

```text
application state
+
business concepts
+
business behavior
```

Na primer u MiniStay aplikaciji:

```text
Booking
Room
User
Inventory
Price
Reservation period
```

To su stvari iz problema koji aplikacija rešava.

Dakle:

```text
MODEL SIDE
→ ono što aplikacija zna
  i kako se ponaša
```

Ne samo način na koji je to snimljeno u MySQL.

---

# 3. Database je persistence

Database odgovara na pitanje:

> Gde i kako trajno čuvamo podatke?

Na primer:

```text
bookings table
rooms table
users table
inventory table
```

To je:

```text
persistence concern
```

Ali Booking kao business koncept postoji i bez MySQL-a.

Možemo ga držati:

```text
u memoriji
u PostgreSQL
u MySQL
u JSON fajlu
u test double-u
```

i dalje je:

```text
Booking
```

---

# 4. Entity

Entity je objekat koji predstavlja business stvar sa identitetom.

Na primer:

```php
final class Booking
{
    public function __construct(
        private int $id,
        private int $userId,
        private int $roomId,
        private BookingStatus $status
    ) {}
}
```

Booking ID `42` predstavlja isti booking kroz vreme čak i ako mu se:

```text
status promeni
datum promeni
guest podatak promeni
```

Identitet ostaje:

```text
Booking #42
```

Zato kažemo da je Booking:

```text
Entity
```

---

# 5. Entity nije samo bag of properties

Najanemičnija verzija:

```php
final class Booking
{
    public int $id;
    public string $status;
    public float $total;
}
```

ovo može predstavljati data object.

Ali pravi domain entity može imati ponašanje:

```php
public function cancel(): void
{
    if (
        $this->status
        !== BookingStatus::CONFIRMED
    ) {
        throw new BookingCannotBeCancelledException();
    }

    $this->status =
        BookingStatus::CANCELLED;
}
```

Sada Booking ne samo da:

```text
ima state
```

nego i:

```text
čuva pravilo sopstvenog ponašanja
```

---

# 6. Entity čuva lokalne invariants

Na primer:

```php
public function cancel(): void
{
    if ($this->isCancelled()) {
        throw new BookingAlreadyCancelledException();
    }

    $this->status =
        BookingStatus::CANCELLED;
}
```

Entity može zaštititi pravilo:

```text
Booking ne može biti cancelled dva puta
```

To je business invariant.

---

# 7. Ali Entity ne mora da zna sve

Booking entity ne mora nužno da zna:

```text
SQL
PDO
mailer
filesystem
HTTP request
current session
```

Na primer ovo je loše:

```php
public function cancel(): void
{
    $pdo = new PDO(...);

    $pdo->exec(...);

    mail(...);
}
```

Entity sada radi:

```text
domain
+
persistence
+
infrastructure
```

previše odgovornosti.

# 8. Database row

Pretpostavimo DB vrati:

```php
[
    'id' => '42',

    'room_id' => '3',
    'status' => 'confirmed'

```

To je:

```text

```


# 9. Hydration

Proces:

```text
DB row
↓
object
```

često zovemo:

```text
hydration
```

Na primer:

```php
return new Booking(
    id: (int) $row['id'],
    userId: (int) $row['user_id'],
    roomId: (int) $row['room_id'],
    status: BookingStatus::from(
        $row['status']
    )
);
```

Repository zna kako persistence representation postaje domain object.

# 10. Dehydration / persistence mapping

Suprotno:

```text
Booking object
↓
database values
```

na primer:

```php
$stmt->execute([
    'status' =>
        $booking->status()->value,

    'id' =>
        $booking->id(),

```

Opet:

```text
Repository responsibility
```

# 11. Repository nije Entity

Repository:

```php
interface BookingRepository
{
    public function findById(
        int $id
    ): ?Booking;

    public function save(
        Booking $booking
    ): void;
}
```

Repository odgovara na:

```text
Kako pronaći Booking?
Kako sačuvati Booking?
```

Booking odgovara na:

```text
Šta Booking jeste?
Kako se ponaša?
```

To su odvojene stvari.

---

# 12. Repository može skrivati persistence tehnologiju

Service:

```php
$booking =
    $this->bookings
        ->findById($id);
```

ne mora da zna da li implementacija koristi:

```text
PDO
MySQL
PostgreSQL
in-memory array
API
```

To je vrednost Repository abstraction-a.

# 13. DTO

DTO znači:

```text
Data Transfer Object
```

DTO služi da prenese strukturirane podatke između granica/slojeva.

Na primer:

```php
final readonly class CreateBookingData
{
    public function __construct(
        public int $roomId,
        public DateTimeImmutable $checkIn,
        public DateTimeImmutable $checkOut,
        public int $guests
    ) {}
}
```

Ovo nije Booking entity.

Zašto?

Jer još nemamo:

```text
booking ID
status
persisted identity
booking lifecycle
```

Ovo samo predstavlja:

```text
podatke potrebne za create use case
```

---

# 14. DTO nema business identity

Ako imamo:

```php
new CreateBookingData(
    roomId: 3,
    checkIn: ...,
    checkOut: ...,
    guests: 2
);
```

to nije:

```text
Booking #42
```

To je:

```text
zahtev/paket podataka
za kreiranje booking-a
```

Zato:

```text
DTO
≠ Entity
```

---

# 15. DTO često treba da bude immutable

Na primer:

```php
final readonly class CreateBookingData
```

jer DTO često predstavlja:

```text
validated snapshot input-a
```

Ne želimo da se nasumično menja dok prolazi kroz Service.

---

# 16. Entity može biti mutable

Booking može menjati state:

```php
$booking->cancel();
```

jer je to njegov lifecycle.

Dakle:

```text
DTO
→ često immutable transfer data

Entity
→ može menjati business state
```

---

# 17. Value Object

Pored Entity i DTO imamo i:

```text
Value Object
```

Na primer:

```php
final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency
    ) {}
}
```

Value Object nema business identity.

Dve vrednosti:

```text
100 EUR
100 EUR
```

su semantički iste.

Za razliku od:

```text
Booking #42
Booking #43
```

koji nisu isti čak i ako imaju identične podatke.

---

# 18. Entity vs Value Object

Mentalno:

```text
ENTITY
→ identitet je važan

VALUE OBJECT
→ vrednost je važna
```

Primer:

```text
User #7
Booking #42
Room #3
```

su Entities.

```text
Money(100, EUR)
DateRange(...)
EmailAddress(...)
```

mogu biti Value Objects.

# 23. Database schema ne treba automatski da diktira OOP model

Ako imamo:

```text

```

to ne znači da domain mora imati:

```php

```

```php

```

```php
enum BookingStatus: string
{
    case Pending = 'pending';
    case Confirmed = 'confirmed';
    case Cancelled = 'cancelled';
}
```

Database representation:

```text
string
```

```text
enum
```

Repository ih mapira.

# 25. Active Record

Sada dolazimo do Laravel-a.

Active Record pattern kombinuje:

```text
object state
+
persistence behavior
```

Na primer konceptualno:

```php
$booking =
    Booking::find(42);

$booking->status =
    'cancelled';

$booking->save();
```

Booking object zna kako da:

```text
učita sebe

```

To je:

```text
Active Record
```

```php

```

```text

```

To je praktičan framework pattern.

# 29. Anemic Domain Model


# 30. Da li je anemic model uvek loš?

Ne.

Za jednostavan CRUD:

```text

simple settings

```

bogat domain model može biti nepotreban.

Ako nema mnogo business ponašanja:

```text
data-centric model
```

je sasvim dovoljan.

Problem je kada kompleksan domain ima pravila, ali ih razbacamo svuda jer Entity nema nikakvo ponašanje.

# 31. Rich Domain Model

Bogata Entity može imati:

```php
$booking->cancel();

$booking->confirm();

$booking->changeDates(...);
```

i čuvati svoja pravila.

Na primer:

```php
public function cancel(
    DateTimeImmutable $now
): void {
    if (!$this->status->canCancel()) {
        throw new BookingCannotBeCancelledException();
    }

    if ($this->checkIn <= $now) {
        throw new BookingCannotBeCancelledException();
    }

    $this->status =
        BookingStatus::Cancelled;
}
```

To je:

```text
behavior close to state
```

```text

```

```text

```

```text

```

```text

```

ima više smisla.

# 34. Primer cancellation use case-a

Service:

```php
public function cancel(
    User $user,
    int $bookingId
): void {
    $booking =
        $this->bookings
            ->findById($bookingId);

    if ($booking === null) {
        throw new BookingNotFoundException();
    }

    $this->policy
        ->assertCanCancel(
            $user,
            $booking
        );

    $booking->cancel();

    $this->inventory
        ->restoreFor(
            $booking
        );

    $this->bookings
        ->save(
            $booking
        );
}
```

Ovde:

```text
Booking
→ štiti svoj state

Service
→ koordinira use case
```

# 46. Constructor invariant

Na primer:

```php

{
    public function __construct(
        public DateTimeImmutable $from,
        public DateTimeImmutable $to

            throw new InvalidArgumentException(
                'End must be after start.'

        }
    }
}
```

Ako object postoji:

```text

```

To je moćan pattern.

# 50. Laravel Eloquent primer

Laravel:

```php
final class Booking extends Model
{
    protected $casts = [
        'check_in' => 'date',
        'check_out' => 'date',
    ];
}
```

Ovaj class može:

```text
predstavljati DB record
query-ovati
persistovati
definisati relationships
castovati values
```

Može imati i business behavior:

```php
public function cancel(): void
{
    if ($this->status !== 'confirmed') {
        throw new DomainException();
    }

    $this->status = 'cancelled';
}
```

To nije nužno loše.

Ali možda ne treba da ima:

```php
sendVoucherEmail()
generatePdf()
chargeStripe()
```

sve u istoj klasi.

---

# 51. Eloquent relationship je persistence-aware

Na primer:

```php
$booking->user
```

odgovara relationship-u.

To je veoma praktično.

Ali znači da Eloquent Model nije persistence-ignorant domain entity.

On zna ORM.

To je tradeoff koji Laravel namerno pravi radi produktivnosti.

# 52. Repository sa Eloquent-om — da ili ne?

Možeš imati:

```php

```

iznad Eloquent-a.

Ali ne moraš automatski.

Ako repository samo radi:


bez ikakve dodatne vrednosti, možda je samo nepotrebna abstrakcija.

Repository ima više smisla kada želiš:

```text
stabilan domain contract

persistence boundary
test replacement
više persistence implementations
```

# 57. Booking example

Entity:

```php
final class Booking
{
    public function __construct(
        private int $id,
        private int $userId,
        private int $roomId,
        private BookingStatus $status,
        private DateTimeImmutable $checkIn,
        private DateTimeImmutable $checkOut
    ) {}

    public function cancel(): void
    {
        if (
            $this->status
            !== BookingStatus::Confirmed
        ) {
            throw new BookingCannotBeCancelledException();
        }

        $this->status =
            BookingStatus::Cancelled;
    }

    public function id(): int
    {
        return $this->id;
    }

    public function status(): BookingStatus
    {
        return $this->status;
    }
}
```

Repository:

```php
interface BookingRepository
{
    public function findById(
        int $id
    ): ?Booking;

    public function save(
        Booking $booking
    ): void;
}
```

Service:

```php
final class BookingService
{
    public function __construct(
        private BookingRepository
            $bookings
    ) {}

    public function cancel(
        int $id
    ): void {
        $booking =
            $this->bookings
                ->findById($id);

        if ($booking === null) {
            throw new BookingNotFoundException();
        }

        $booking->cancel();

        $this->bookings
            ->save($booking);
    }
}
```

Tri različite odgovornosti.

# 59. Complete terminology map

```text
MVC MODEL
→ široka business/application strana

ENTITY
→ object sa business identitetom

VALUE OBJECT
→ object definisan vrednošću

DTO
→ prenosi strukturirane podatke

REPOSITORY
→ persistence abstraction

DATABASE ROW
→ persistence representation

SERVICE
→ koordinira use case

ELOQUENT MODEL
→ Active Record-style ORM object
```

Ovo nisu sinonimi.

# 60. Najvažniji mentalni test

Ako vidiš klasu, pitaj:

### Da li predstavlja business stvar sa identitetom?

```text
Entity
```

### Da li predstavlja vrednost bez identiteta?

```text
Value Object
```

### Da li samo prenosi podatke između granica?

```text
DTO
```

### Da li učitava/čuva Entities?

```text
Repository
```

### Da li koordinira use case?

```text
Service
```

### Da li predstavlja/persistuje DB record kroz ORM?

```text
Active Record / Eloquent Model
```

Termin:

```text
Model
```

sam po sebi nije dovoljno precizan.

# Najvažnije za zapamtiti

Najveća greška:

```text
Model = tabela
```

Model u širem MVC smislu predstavlja:

```text
state
business concepts
business behavior
```

Entity:

```text
ima identitet
```

Na primer:

```text
Booking #42
```

Value Object:

```text
definisan vrednošću
```

Na primer:

```text
Money(100 EUR)
```

DTO:

```text
prenosi podatke
```

Na primer:

```text
CreateBookingData
```

Repository:

```text
učitava i čuva domain/application objekte
```

Database row:

```text
persistence representation
```

nije isto što i Entity.

Hydration:

```text
DB row
↓
Entity
```

Service:

```text
koordinira use case
```

Entity:

```text
čuva lokalna business pravila
```

kada to ima smisla.

Laravel Eloquent Model:

```text
Active Record-style ORM object
```

i nije cela `M` komponenta MVC-a.

Ne treba svaki projekat da ima:

```text
Entity
Record
DTO
ViewModel
Repository
Factory
Mapper
```

za svaku tabelu.

Svaka abstraction treba da rešava stvaran problem.

Centralna mapa:

```text
HTTP
↓
Controller
↓
DTO
↓
Service
↓
Entity / Value Objects
↓
Repository
↓
Database
```

I najvažnija rečenica:

> **Model nije "klasa koja priča sa bazom" — Model je način na koji aplikacija predstavlja svoj problem, dok je baza samo jedan način da taj state sačuva.**
