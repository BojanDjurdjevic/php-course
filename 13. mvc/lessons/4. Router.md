# 4. Router — Route Matching & Dispatch

## 1. Šta Router radi

Router odgovara na pitanje:

> Koji deo aplikacije treba da obradi ovaj HTTP request?

Request ima bar dve ključne informacije:

```text id="a8uk5s"
HTTP method
+
URI path
```

Na primer:

```text id="9m1zqg"
GET /bookings
```

ili:

```text id="0k0h4p"
POST /bookings
```

ili:

```text id="c5d9xq"
GET /bookings/42
```

Router poredi request sa registrovanim route-ovima i bira odgovarajući handler.

---

# 2. Najjednostavniji route

Možemo registrovati:

```php id="06f3ty"
$router->get(
    '/bookings',
    [$bookingController, 'index']
);
```

Ovo možemo čitati kao:

```text id="vh7ghp"
Ako stigne:

GET /bookings

pozovi:

BookingController::index()
```

Router čuva mapping:

```text id="fmaosf"
GET + /bookings
→ handler
```

---

# 3. Method je deo route identiteta

Ovo:

```text id="gnszmd"
GET /bookings
```

i:

```text id="p8j7ui"
POST /bookings
```

nisu isti route.

Možemo imati:

```php id="esrmm1"
$router->get(
    '/bookings',
    [$controller, 'index']
);

$router->post(
    '/bookings',
    [$controller, 'store']
);
```

Isti URI.

Različit HTTP method.

Zato router ne radi samo:

```text id="xoqh0h"
URI → handler
```

nego:

```text id="5ksscp"
METHOD + URI
→ handler
```

---

# 4. Zašto je ovo bitno

Na primer:

```text id="d5k5f2"
GET /bookings
```

znači:

```text id="vfus7s"
prikaži listu
```

Dok:

```text id="mhh7ap"
POST /bookings
```

znači:

```text id="90hs6a"
kreiraj novi booking
```

Jedan resource.

Različite operacije.

HTTP method nosi semantiku.

---

# 5. Router ne treba da sadrži business logic

Loše:

```php id="97qic3"
$router->post(
    '/bookings',
    function () use ($pdo) {
        // validate
        // SQL
        // booking logic
        // inventory
        // email
    }
);
```

Za malu aplikaciju closure route može biti praktičan.

Ali u našem MVC modelu Router treba uglavnom da odlučuje:

```text id="qsgg9y"
ko obrađuje request
```

Ne:

```text id="5zfp5g"
šta booking creation znači
```

Bolje:

```php id="q04w0a"
$router->post(
    '/bookings',
    [$bookingController, 'store']
);
```

# 7. Dynamic route

Često nam treba:

```text id="ldoqs6"
/bookings/42
```

Ali ne želimo registrovati:

```text id="w2lyab"
/bookings/1
/bookings/2
/bookings/3
...
```

Zato koristimo route parameter:

```text id="mjjw07"

```

```php id="lfyo6n"

    '/bookings/{id}',
    [$bookingController, 'show']

```

Sada:

```text id="bvvs0l"
GET /bookings/42
```

matchuje:

```text id="n6gbzc"
/bookings/{id}
```

i dobijamo:

```text id="bpngnd"

```

# 8. Route parameter nije isto što i query parameter

Ovo:

```text id="h2lh28"
/bookings/42
```

ima:

```text id="ng7pjh"

```

Dok:

```text id="rvahyk"
/bookings?id=42
```


To su dve različite stvari.

```text id="c1q4r5"

?status=confirmed
→ optional query/filter state
```

# 9. Primer kombinacije


```text id="v7mtdc"
include = guest
```

Router uglavnom rešava:

```text id="onq3e4"

```

Request object kasnije čita:


# 10. Kako dynamic matching može da radi

Pretpostavimo route:

```text id="4euwob"
/bookings/{id}
```

Router može interno pretvoriti pattern u nešto poput:

```regex id="8v0j0o"
^/bookings/([^/]+)$
```

Request:

```text id="yow8kc"
/bookings/42
```

matchuje.

Capture group daje:

```text id="hw8btf"
42
```

koji mapiramo na:

```text id="1we5fi"
id
```

# 11. Route pattern nije validation

Ovo je veoma bitno.

Ako route:

```text id="58n5k9"
/bookings/{id}
```

uhvati:

```text id="5u8j5e"
/bookings/abc
```

to ne znači da je:

```text id="8p7sui"
abc
```

validan booking ID.

Router kaže samo:

```text id="0ez0wa"
path shape se poklapa
```

Validation mora dalje da kaže:

```text id="7qn6r6"
id mora biti pozitivan integer
```

Dakle:

```text id="9rbpf3"
ROUTE MATCH
≠ INPUT VALIDATION
```

---

# 12. Route constraints

Možemo imati routing constraint:

```text id="95833g"
/bookings/{id:\d+}
```

ili drugačiji API, zavisno od Router implementacije.

To znači:

```text id="a9m6bv"
id segment
mora izgledati kao digits
```

Sada:

```text id="mzf6e8"
/bookings/42
→ match

/bookings/abc
→ no match
```

To može biti korisno.

Ali opet:

```text id="yp6xmi"
\d+
```

nije kompletna business validation.

Na primer:

```text id="8it6vu"
0
99999999999999999
```

možda i dalje nisu prihvatljivi application IDs.

---

# 13. Static vs dynamic route priority

Pretpostavimo:

```text id="4lwphr"
/bookings/create
/bookings/{id}
```

Request:

```text id="4n79pi"
/bookings/create
```

Ako Router prvo proveri:

```text id="cxatnv"
/bookings/{id}
```

možda dobije:

```text id="fd4y29"
id = create
```

umesto static route-a.

Zato Router treba da ima jasnu matching strategiju.

Čest princip:

```text id="bzllst"
static routes
pre dynamic routes
```

ili specificity-based matching.

---

# 14. Route order može biti važan

Jednostavan Router može samo proveravati routes redom:

```php id="3adwbw"
foreach ($routes as $route) {
    if ($route->matches($request)) {
        return $route;
    }
}
```

Tada registration order postaje bitan.

Na primer:

```php id="3gms62"
$router->get(
    '/bookings/create',
    ...
);

$router->get(
    '/bookings/{id}',
    ...
);
```

je sigurnije nego obrnuto kod naivnog Router-a.

Ozbiljniji Router može sam računati specificity.

# 15. Dispatch

Kada Router pronađe route, treba da:

```text id="x4g20a"
pozove njegov handler
```

To je:

```text id="b89y7c"
dispatch
```

Mentalno:

```text id="nuak09"
Request
↓
match route
↓
extract params
↓
invoke handler
↓
Response
```

---

# 16. Jednostavan `dispatch()`

Konceptualno:

```php id="7r9mtf"
public function dispatch(
    Request $request
): Response {
    foreach ($this->routes as $route) {
        if ($route->matches($request)) {
            return $route->run($request);
        }
    }

    return Response::notFound();
}
```

Ovo je srž Router-a.

Sve ostalo su dodatne mogućnosti.

---

# 17. Handler

Handler može biti:

```php id="9zqanx"
[$bookingController, 'show']
```

To je PHP callable.

Router može pozvati:

```php id="10e1um"
$response = call_user_func(
    $handler,
    $request,
    $params
);
```

Ili eksplicitnije:

```php id="zngt9h"
[$object, $method] = $handler;

$response =
    $object->$method(
        $request,
        $params
    );
```

# 18. Route params treba da stignu do Controller-a

# 41. Jednostavan Router skeleton

Na primer:

```php id="65551u"
final class Router
{
    private array $routes = [];

    public function get(
        string $path,
        callable|array $handler
    ): void {
        $this->add(
            'GET',
            $path,
            $handler
        );
    }

    public function post(
        string $path,
        callable|array $handler
    ): void {
        $this->add(
            'POST',
            $path,
            $handler
        );
    }

    private function add(
        string $method,
        string $path,
        callable|array $handler
    ): void {
        $this->routes[] =
            new Route(
                $method,
                $path,
                $handler
            );
    }
}
```

Ovo je registration deo.

---

# 42. Dispatch skeleton

Zatim:

```php id="phxncg"
public function dispatch(
    Request $request
): Response {
    foreach ($this->routes as $route) {
        if (
            !$route->matchesPath(
                $request->path()
            )
        ) {
            continue;
        }

        if (
            $route->method
            !== $request->method()
        ) {
            continue;
        }

        return $route->dispatch(
            $request
        );
    }

    return Response::notFound();
}
```

Ovo još ne razlikuje idealno:

```text id="lk16hk"
404
vs
405
```

ali pokazuje osnovnu ideju.

---

# 43. Precizniji dispatch mentalni model

Bolji tok:

```text id="g1rw6d"
$allowedMethods = [];

foreach routes:
    path match?
    ├── NE → continue
    └── DA
        ↓
        method match?
        ├── NE
        │   → remember allowed method
        │
        └── DA
            → dispatch handler

posle loop-a:

allowedMethods not empty?
→ 405

otherwise
→ 404
```

Tako Router razlikuje dve vrste failure-a.

Bitno je da ne pravimo višestruki nasumični decoding kroz različite slojeve.

Security lekcija nam je već pokazala zašto canonicalization mora biti dosledna.

# Najvažnije za zapamtiti

Router rešava:

```text id="wx5w05"
METHOD + PATH
→ HANDLER
```

Na primer:

```text id="v4wr1h"
GET /bookings
→ index

POST /bookings
→ store
```

Static route:

```text id="2c59qe"
/bookings
```

Dynamic route:

```text id="g0c9rr"
/bookings/{id}
```

Route parameter:

```text id="cd5zhs"
/bookings/42
→ id = 42
```

Query parameter:

```text id="ah4kc8"
/bookings?status=confirmed
→ status = confirmed
```

To nisu iste stvari.

Route matching:

```text id="k1snnq"
≠ validation
```

`{id}` može matchovati string ako nema constraint.

`dispatch()` znači:

```text id="3nqsje"
find matching route
↓
extract params
↓
invoke handler
↓
return Response
```

404:

```text id="o0xk2j"
nema matching route/path
```

405:

```text id="n6fykr"
path postoji
ali method nije dozvoljen
```

I zapamti dve vrste 404:

```text id="knopuf"
Routing 404
→ route ne postoji

Resource 404
→ route postoji,
  resource ne postoji
```

Router:

```text id="sh6zqz"
ne radi business logic
ne radi authorization
ne radi domain validation
```

On odgovara samo na:

```text id="6ghd2b"
Ko treba da obradi ovaj request?
```

Named routes pomažu da ne hard-code-ujemo URL-ove.

Route groups pomažu sa:

```text id="jn35w5"
prefix
middleware
naming
```

Kompletan mentalni model:

```text id="f0cck8"
REQUEST
↓
METHOD + PATH
↓
ROUTER
↓
MATCH
↓
PARAMS
↓
MIDDLEWARE
↓
HANDLER
↓
RESPONSE
```

Ako samo jednu rečenicu zapamtiš:

> **Router ne odlučuje šta business akcija znači — Router samo prevodi HTTP method i URI u handler koji zna šta dalje treba da se desi.**
