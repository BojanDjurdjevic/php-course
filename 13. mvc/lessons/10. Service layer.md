# 10. Service Layer & Use Cases

## 1. Zašto Service Layer postoji

Controller ne treba da nosi business logiku.

Repository ne treba da zna application flow.

Entity ne treba da koordinira deset drugih sistema.

Zato često uvodimo:

```text id="u5qnw9"
Service Layer
```

Njegov posao je da koordinira konkretan application use case.

Na primer:

```text id="9u1bvq"
Create booking
Cancel booking
Register user
Reset password
Generate voucher
```

Mentalno:

```text id="8442xf"
Controller
↓
Service
↓
Entities / Repositories / Infrastructure
```

---

# 2. Service odgovara na pitanje "šta use case radi?"

Na primer:

```text id="z4oyc2"
POST /bookings
```

Controller pita:

```text id="h7cnhy"
"Pokreni create booking use case."
```

Service zatim može da:

```text id="09tcy6"

učita Room

izračuna cenu

otvori transaction

kreira Booking

sačuva Booking

promeni inventory

commit
```

Controller ne treba da zna sve te korake.

# 3. Service nije samo "mesto gde prebacimo kod"

Loš refactor:

Controller:

```php id="qglkan"

    ->create($request);
```

```php id="i3a2we"

    Request $request

```

Sada samo imamo:


Ne novi miscellaneous folder.

# 8. Service vs Entity behavior

Pretpostavimo Booking ima:

```php id="kzl5ai"
public function cancel(): void
{
    if (
        $this->status
        !== BookingStatus::Confirmed
    ) {
        throw new BookingCannotBeCancelledException();
    }

    $this->status =
        BookingStatus::Cancelled;
}
```

Service ne mora ponovo da piše:

```php id="234hw5"
if (
    $booking->status()
    !== BookingStatus::Confirmed
) {
    ...
}
```

Bolje:

```php id="ny7gsd"
$booking->cancel();
```

Entity čuva svoje lokalno pravilo.

Service koordinira širu operaciju.

# 9. Service orchestration

Cancellation use case može izgledati:

```php id="gihp45"
public function cancel(
    User $user,
    int $bookingId
): void {
    $booking =
        $this->bookings
            ->findById(
                $bookingId
            );

    if ($booking === null) {
        throw new BookingNotFoundException();
    }

    $this->policy
        ->assertCanCancel(
            $user,
            $booking
        );

    $booking->cancel();

    $this->inventory
        ->restoreFor(
            $booking
        );

    $this->bookings
        ->save(
            $booking
        );
}
```

Ovde Service:

```text id="yktiyb"
učitava

autorizuje

poziva domain behavior

koordinira inventory

persistuje
```

To je pravi use-case orchestration.

# 12. Service i transaction boundary

Service layer je često odlično mesto za transaction boundary.

Na primer:

```php id="6zxyuz"
$this->pdo
    ->beginTransaction();

try {
    // create booking
    // update inventory

    $this->pdo
        ->commit();

    return $booking;
} catch (Throwable $e) {
    $this->pdo
        ->rollBack();

    throw $e;
}
```

Zašto?

Jer transaction treba da obuhvati:

```text id="ipxvtj"
ceo business use case
```

ne samo jednu repository metodu.

# 13. Repository-level transaction može biti preuska

Pretpostavimo:

```text id="u3y6o2"
BookingRepository::create()
```

sam otvori i zatvori transaction.

Zatim:

```text id="s5hll9"
InventoryRepository::decrease()
```

ima drugu transaction.

Ako druga operacija pukne:

```text id="589f9x"
Booking je već sačuvan
Inventory nije promenjen
```

Invariant je razbijen.

Zato transaction boundary često pripada višem sloju koji vidi celu operaciju.

# 14. Shared PDO i Service transaction

Ako repositories dele isti PDO:

```text id="bt2h65"
PDO
├── BookingRepository
└── InventoryRepository
```

Service može:

```php id="yqkjgc"
$this->pdo
    ->beginTransaction();
```

i onda obe repository operacije pripadaju istoj transaction.

To je konkretan razlog zašto smo u Bootstrap lekciji pričali o shared dependency wiring-u.

# Najvažnije za zapamtiti

Service Layer postoji da:

```text id="s64gct"
koordinira application use case
```

Controller:

```text id="op5gtx"
HTTP orchestration
```

Service:

```text id="05f5s5"
business/application orchestration
```

Entity:

```text id="4ip7wm"
lokalni state + business invariants
```

Repository:

```text id="jj9qp7"
persistence
```

Domain Service:

```text id="ak29te"
business pravilo koje ne pripada
prirodno jednom Entity-ju
```

Service ne treba da zna:

```text id="41q3bb"
Request
Response
redirect
HTML
route
flash message
```

Bolje:

```text id="hz0mzs"
HTTP Request
↓
Controller
↓
DTO
↓
Service
```

Service ima posebno smisla kada use case uključuje:

```text id="5gl31e"
više repositories

transactions

business invariants

side effects

domain coordination

authorization/business policies
```

Ne pravi Service koji samo radi:

```php id="2bj32r"
return $repository->findAll();
```

ako ne dodaje nikakvu vrednost.

Transaction boundary često pripada Service-u zato što Service vidi:

```text id="ezt2vv"
ceo use case
```

Ne samo jednu SQL operaciju.

Veoma važna razlika:

```text id="ok6qlr"
Service Container
≠
Service Layer

Service Provider
≠
Application Service
```

Use-case oriented API je često bolji:

```php id="2k92fg"
cancel(...)
```

od:

```php id="as665d"
updateStatus(
    'cancelled'
)
```

jer izražava business nameru i štiti transitions.

Centralni mentalni model:

```text id="556x8p"
CONTROLLER
→ Šta user traži preko HTTP-a?

SERVICE
→ Kako izvršavamo taj use case?

ENTITY
→ Koja pravila čuvaju svoj state?

REPOSITORY
→ Kako podatke učitavamo i čuvamo?
```

Ako samo jednu rečenicu zapamtiš:

> **Service ima smisla kada predstavlja stvarni application use case; ako samo preimenuje jednu repository metodu, verovatno još nema razlog da postoji.**
