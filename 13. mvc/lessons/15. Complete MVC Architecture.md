# 15. Complete Vanilla PHP MVC Architecture

## 1. Šta smo zapravo izgradili

Na početku MVC modula imali smo jednostavan problem:

```text
PHP aplikacija lako postane:

request
+ session
+ validation
+ SQL
+ business logic
+ HTML
+ redirect
+ error handling

u istom fajlu
```

MVC i prateći architectural patterns razdvajaju te odgovornosti.

Naša finalna slika više nije samo:

```text
Model
View
Controller
```

nego:

```text
Front Controller
↓
Bootstrap / Composition Root
↓
Request
↓
Router
↓
Middleware
↓
Controller
↓
DTO / Validator
↓
Service
↓
Entity / Domain
↓
Repository
↓
Database

zatim nazad:

Database
↑
Repository
↑
Service
↑
Controller
↑
View
↑
Response
↑
Middleware
↑
Browser
```

To je praktična moderna Vanilla PHP MVC arhitektura.

---

# 2. MVC nije folder structure

Možemo napraviti:

```text
Controllers/
Models/
Views/
```

i i dalje imati lošu arhitekturu.

Na primer:

```php
final class BookingController
{
    public function store()
    {
        // $_POST
        // SQL
        // pricing
        // transaction
        // email
        // HTML
    }
}
```

Folder se zove `Controllers`.

Ali separation nije stvarno postignut.

MVC je pre svega:

```text
SEPARATION OF RESPONSIBILITIES
```

a folderi samo pomažu da ga izrazimo.

# 4. `public/` — web boundary

Web server document root:

```text
/project/public
```

Browser direktno može da vidi:

```text
public/index.php
public/assets/...
```

Ne:

```text
.env
src/
vendor/
config/
storage/
views/
```

To daje:

```text
private by default
```

architecture.

---

# 5. `public/index.php` — Front Controller

Treba da ostane veoma mali.

Na primer:

```php
<?php

declare(strict_types=1);

require_once dirname(__DIR__)
    . '/vendor/autoload.php';

$app = require dirname(__DIR__)
    . '/bootstrap/app.php';

$request =
    Request::capture();

$response =
    $app->handle(
        $request
    );

$response->send();
```

Mentalno:

```text
BOOT
↓
CAPTURE REQUEST
↓
HANDLE
↓
SEND RESPONSE
```

Ne:

```text
SQL
business logic
HTML
```

---

# 6. `bootstrap/app.php` — Composition Root

Bootstrap sastavlja application graph.

Na primer:

```php
$pdo = $database->connect();

$users =
    new PdoUserRepository(
        $pdo
    );

$rooms =
    new PdoRoomRepository(
        $pdo
    );

$bookings =
    new PdoBookingRepository(
        $pdo
    );

$inventory =
    new PdoInventoryRepository(
        $pdo
    );

$auth =
    new AuthService(
        $users,
        $session
    );

$bookingService =
    new BookingService(
        $pdo,
        $rooms,
        $bookings,
        $inventory
    );

$bookingController =
    new BookingController(
        $bookingService,
        $auth,
        $view,
        $session
    );
```

Bootstrap zna concrete implementations.

Application classes ne moraju.

---

# 7. Bootstrap ne izvršava use case

Bootstrap:

```text
creates objects
configures objects
connects objects
registers routes
```

Ne:

```text
creates booking
logs user in
calculates price
```

Centralno pravilo:

> Bootstrap sastavlja sistem; request koristi sastavljen sistem.

---

# 8. Request Object

Front Controller pretvara:

```text
$_SERVER
$_GET
$_POST
$_COOKIE
$_FILES
```

u:

```php
Request
```

Na primer:

```php
$request->method();

$request->path();

$request->query('status');

$request->input('email');

$request->header('Accept');

$request->route('id');
```

Request:

```text
predstavlja HTTP input
```

ali ga ne čini trusted.

---

# 9. Request je boundary object

Tok:

```text
raw PHP globals
↓
Request
↓
Application
```

Od tog trenutka ostatak HTTP sloja ne mora direktno da koristi:

```php
$_POST
$_SERVER
```

svuda po kodu.

To smanjuje global coupling.

---

# 10. Router

Router rešava:

```text
METHOD + PATH
→ HANDLER
```

Na primer:

```text
GET /rooms
→ RoomController::index

GET /rooms/{id}
→ RoomController::show

POST /bookings
→ BookingController::store
```

Router ne radi:

```text
pricing
authorization business pravila
SQL
```

On samo dispatchuje.

---

# 11. Route parameters

Route:

```text
GET /bookings/{id}
```

Request:

```text
GET /bookings/42
```

Router izvlači:

```text
id = 42
```

i prosleđuje dalje.

To nije isto što i:

```text
?status=confirmed
```

Route param određuje path structure.

Query param je dodatni request input.

---

# 12. Router failures

Ako path ne postoji:

```text
404
```

Ako path postoji ali method nije dozvoljen:

```text
405
```

Mentalno:

```text
PATH MATCH?
├── ne → 404
└── da
    ↓
METHOD MATCH?
├── ne → 405
└── da → dispatch
```

---

# 13. Middleware

Pre Controller-a možemo imati:

```text
logging
auth
CSRF
rate limiting
```

Posle Controller-a:

```text
security headers
timing
response logging
```

Tok:

```text
A before
↓
B before
↓
Controller
↓
B after
↓
A after
```

To je onion pipeline.

---

# 14. Middleware short-circuit

Na primer:

```text
Request
↓
AuthMiddleware
↓
user not logged in
↓
303 /login
```

Controller se nikad ne poziva.

Isto:

```text
invalid CSRF
→ 403

rate limit
→ 429
```

Middleware filtrira request lifecycle.

---

# 15. Middleware ne sme da preuzme business use case

Ovo nije middleware posao:

```text
check room availability
calculate total price
restore inventory
cancel booking
```

To pripada application/domain sloju.

Middleware:

```text
around the use case
```

Service:

```text
the use case itself
```

---

# 16. Controller

Controller je:

```text
HTTP coordinator
```

Tipičan flow:

```text
Request
↓
extract/map input
↓
validate
↓
identify user
↓
authorize
↓
call Service
↓
choose View/Redirect/JSON
↓
Response
```

---

# 17. Controller ne treba da radi SQL

Loše:

```php
$stmt =
    $this->pdo->prepare(...);
```

u Controller-u.

Bolje:

```php
$booking =
    $this->bookingService
        ->create(...);
```

Controller ne treba da zna persistence detalje.

---

# 18. Controller ne treba da radi business calculation

Loše:

```php
$total =
    $room->price()
    * $nights;
```

ako je to business pricing logic.

Bolje:

```php
$booking =
    $service->create(
        $user,
        $data
    );
```

Pricing se rešava ispod Controller-a.

---

# 19. Thin Controller ne znači "2 linije"

Controller sme da:

```text
čita request
pozove validator
pozove auth/policy
pozove service
flashuje message
vrati response
```

Thin znači:

```text
malo business/persistence logike
```

ne:

```text
veštački minimalan broj linija
```

---

# 20. DTO / Request Data

Generički HTTP Request:

```text
room_id = "12"
guests = "2"
check_in = "2027-06-10"
```

nakon validation/mapping-a postaje:

```php
new CreateBookingData(
    roomId: 12,
    guests: 2,
    checkIn:
        new DateTimeImmutable(
            '2027-06-10'
        ),
    checkOut:
        ...
);
```

Time prelazimo iz:

```text
HTTP data
```

u:

```text
application data
```

# 21. Service ne treba da prima HTTP Request

Loše:

```php
$service->create(
    $request
);
```

Bolje:

```php
$service->create(
    $user,
    $data
);
```

Service tada ne zna:

```text
POST
headers
cookies
query string
```

Može se koristiti iz:

```text
web
API

test
```

# 22. Validation granica

Input validation:

```text
room_id je integer
email je validnog formata
date se može parsirati
```

Business validation:

```text

room je slobodna
booking može da se otkaže
```

Prvo pripada request/validation sloju.

Drugo Service/domain sloju.

Service predstavlja:

```text
application use case
```

Na primer:

```text

```

Service koordinira:

```text

```

# 24. Kada Service ima smisla

Ako use case ima:

```text
više Repository-ja
business rules
transaction

```

Service ima jasnu vrednost.

Na primer booking creation.

# 25. Kada Service možda nema smisla

Ako:

```text
GET /rooms
```

samo učita listu soba:

```php
$rooms =
    $this->rooms
        ->findPublic();
```

ne mora obavezno postojati:

```php
RoomService::findPublic()
```

koji samo prosleđuje isti poziv.

Ne pravimo abstraction bez odgovornosti.

# 26. Entity / Model

Entity predstavlja business stvar sa identitetom.

Na primer:

```php
Booking #42
```

Može imati state:

```text
status
dates
user
room
```

i ponašanje:

```php
$booking->cancel();
```

Entity može štititi lokalni invariant.

---

# 27. Entity nije Repository

Entity kaže:

```text
šta Booking jeste
i kako se ponaša
```

Repository kaže:

```text
kako ga učitavamo i čuvamo
```

Nemoj ih mešati.

---

# 28. MVC Model nije samo DB Model

Šira "M" strana može uključivati:

```text
Entities
Value Objects
Services
Repositories
business rules
```

Laravelov:

```php
class Booking extends Model
```

je Eloquent/Active Record pojam.

Nije cela teorijska MVC Model strana.

---

# 29. Repository

Repository predstavlja:

```text
persistence boundary
```

Service govori:

```php
$booking =
    $this->bookings
        ->findById($id);
```

Repository rešava:

```text
SQL
prepared statements
fetch
hydration
mapping
```

---

# 30. Repository vraća application representation

Bolje:

```php
findById(): ?Booking
```

nego:

```php
findById(): array
```

ako ostatak aplikacije koristi Booking Entity.

Time DB column names ne cure dalje.

---

# 31. Hydration

Repository radi:

```text
DB row
↓
Booking
```

Na primer:

```php
new Booking(
    id:
        (int) $row['id'],

    status:
        BookingStatus::from(
            $row['status']
        )
);
```

Repository je translator između:

```text
persistence representation
```

i:

```text
application representation
```

# 32. Shared PDO

Composition Root:

```php
$pdo =
    $database->connect();

    new PdoBookingRepository(
        $pdo
    );

    new PdoInventoryRepository(
        $pdo
    );
```

Oba koriste istu connection.

To omogućava:

```text

```

# 33. Transaction boundary

Booking creation:

```text
begin
↓
lock inventory
↓
check
↓
create booking
↓
decrease inventory
↓
commit
```

Ako bilo šta pukne:

```text
rollback
```

Transaction boundary treba da prati:

```text
business use case
```

ne nasumičnu pojedinačnu repository metodu.

---

# 34. Concurrency

Availability check:

```text
check
↓
insert
```

nije dovoljan ako paralelni request-i mogu proći istovremeno.

Zato Service + Repository mogu zajedno implementirati:

```text
transaction
+
SELECT ... FOR UPDATE
```

ili optimistic strategy.

MVC layering ne zamenjuje concurrency correctness.

```php

```

ne pravi:

```php

```

sam.

Dependency dobija spolja.

To je DI.

# 41. Output escaping

View je mesto gde:

```text
untrusted data
↓
HTML context
```

Zato:

```php

```

a `e()` koristi:

```php
htmlspecialchars(
    $value,
    ENT_QUOTES,
    'UTF-8'
);
```

Escape:

```text
late
for the actual output context
```

```text

```

# Najvažnije za zapamtiti

MVC nije:

```text
3 foldera
```

MVC je separation između:

```text
input coordination
business/application state
presentation
```

U realnoj aplikaciji to proširujemo sa:

```text
Front Controller
Router
Request/Response
Middleware
Service Layer
Repository
Dependency Injection
Error Handling
```

Centralni request flow:

```text
BROWSER
↓
FRONT CONTROLLER
↓
REQUEST
↓
ROUTER
↓
MIDDLEWARE
↓
CONTROLLER
↓
DTO
↓
SERVICE
↓
ENTITY / REPOSITORY
↓
DATABASE
```

Povratak:

```text
RESULT
↓
CONTROLLER
↓
VIEW / JSON / REDIRECT
↓
RESPONSE
↓
MIDDLEWARE
↓
BROWSER
```

Controller:

```text
HTTP orchestration
```

Service:

```text
use-case orchestration
```

Entity:

```text
business state + local invariants
```

Repository:

```text
persistence boundary
```

View:

```text
presentation
```

Middleware:

```text
cross-cutting request/response concerns
```

Bootstrap:

```text
composition
```

Request:

```text
HTTP input representation
```

Response:

```text
HTTP output representation
```

Error Handler:

```text
failure → safe HTTP result
```

Ne mora svaki use case koristiti svaki sloj.

Architecture treba da bude:

```text
onoliko složena
koliko problem zahteva
```

Najvažnije je:

```text
odgovornost na pravom mestu
```

Ne broj klasa.

Ako framework sutra nestane, i dalje treba da znaš:

```text
ko prima request

ko dispatchuje

ko validira

ko autorizuje

ko izvršava business use case

ko radi SQL

ko renderuje

ko vraća response

ko hvata failure
```

I centralna rečenica celog MVC modula:

> **Dobra MVC arhitektura nije ona sa najviše slojeva, već ona u kojoj za svaki komad koda možeš jasno da objasniš zašto živi baš tu i ko je odgovoran za ono što se dešava pre i posle njega.**
