# 12. Dependency Injection & Composition Root u MVC aplikaciji

## 1. Problem skrivene zavisnosti

Zamisli Controller:

```php id="kpwqqc"
final class BookingController
{
    public function store(
        Request $request
    ): Response {
        $pdo = new PDO(...);

        $repository =
            new PdoBookingRepository(
                $pdo
            );

        $service =
            new BookingService(
                $repository
            );

        // ...
    }
}
```

Na prvi pogled radi.

Ali Controller sada odlučuje:

```text id="wv3zl7"
koji PDO koristi

koji Repository koristi

kako se Repository pravi

koji Service koristi
```

Drugim rečima:

```text id="5xm0kb"
BookingController
→ zna konstrukciju svog sveta
```

To nije njegova odgovornost.

---

# 2. Dependency

Dependency je objekat ili servis koji druga klasa treba da bi radila.

Na primer:

```php id="4rpt4z"
final class BookingService
{
    public function __construct(
        private BookingRepository
            $bookings
    ) {}
}
```

`BookingRepository` je:

```text id="8yu5q0"
dependency BookingService-a
```

BookingService ne može potpuno da radi bez njega.

---

# 3. Dependency Injection

Dependency Injection znači:

> Klasa ne pravi sama svoje dependencies, već ih dobija spolja.

Umesto:

```php id="cf5y0g"
$this->repository =
    new PdoBookingRepository(
        new PDO(...)
    );
```

dobijamo:

```php id="nv2lks"
public function __construct(
    BookingRepository $bookings
) {
    $this->bookings =
        $bookings;
}
```

Dependency je:

```text id="yyw90i"
INJECTED
```

spolja.

---

# 4. Constructor Injection

Najčešći i najjasniji oblik:

```php id="m7jkev"
final class BookingService
{
    public function __construct(
        private BookingRepository
            $bookings,
        private InventoryRepository
            $inventory
    ) {}
}
```

Odmah vidimo:

```text id="x8tvfo"
BookingService zahteva:

BookingRepository
InventoryRepository
```

Nema skrivene dependency magije.

---

# 5. Zašto je constructor injection dobar

Constructor signature je praktično:

```text id="20r7r2"
dependency contract
```

Čitajući:

```php id="il2t1t"
new BookingService(
    $bookings,
    $inventory
);
```

odmah znaš šta Service treba.

To pomaže:

```text id="fbm07c"
čitljivosti
testiranju
refactoring-u
static analysis-u
```

# 6. Dependency Injection nije isto što i Dependency Injection Container

Veoma važna razlika.

Ovo:

```php id="4o7j3w"
$service =
    new BookingService(
        $repository
    );
```

je već:

```text id="x4y9gw"

```

Ne treba ti container da bi koristio DI.

Container samo:

```text id="sy5w0b"
automatizuje construction/resolution
```

# 7. Manual DI

Na primer:

```php id="kj41hb"
$pdo =
    new PDO(...);

$repository =
    new PdoBookingRepository(
        $pdo

    new PdoInventoryRepository(

    new BookingService(
```

I vrlo transparentan.

# 10. Composition Root zna concrete implementations

Na primer:

```php id="eg92nl"

    new PdoBookingRepository(
        $pdo
    );
```

Composition Root zna:

```text id="q2db4v"
BookingRepository

```

Ali BookingService ne mora.

On zna samo:

```php id="pvrhn4"
BookingRepository
```

# 11. High-level vs low-level

BookingService je više:

```text id="yanl0o"
high-level application policy
```

PdoBookingRepository je:

```text id="xg6t1m"
low-level persistence implementation
```

Ako BookingService direktno radi:

```php id="b2kgpl"
new PdoBookingRepository(...)
```

high-level code zavisi od:

```text id="i4r9pv"
concrete low-level detail
```

To povećava coupling.

---

# 12. Dependency Inversion Principle

DIP kaže, pojednostavljeno:

```text id="z8cv3w"
high-level modules
ne treba da zavise od
low-level concrete details

oba treba da zavise od abstractions
```

Kod nas:

```text id="xp29at"
BookingService
↓
BookingRepository interface
↑
PdoBookingRepository
```

Service ne zavisi direktno od PDO implementation-a.

---

# 13. DIP nije isto što i DI

Još jedna važna razlika.

DIP:

```text id="13s0lz"
design principle
```

DI:

```text id="qb5p1y"
mechanism za prosleđivanje dependencies
```

Možeš koristiti DI bez interface-a:

```php id="3kx3tr"
public function __construct(
    PdoBookingRepository $repo
) {}
```

To je DI.

Ali nije naročito snažna primena DIP-a jer i dalje zavisiš od concrete implementation-a.

# 14. Interface kao abstraction

Na primer:

```php id="e2k6cr"
interface BookingRepository
{
    public function findById(
        int $id
    ): ?Booking;
}
```

Concrete:

```php id="tcb4ja"
final class PdoBookingRepository
    implements BookingRepository
{
    ...
}
```

Service:

```php id="dlbxrc"
final class BookingService
{
    public function __construct(
        private BookingRepository
            $bookings
    ) {}
}
```

Bootstrap:

```php id="kqg908"
$repo =
    new PdoBookingRepository(
        $pdo
    );

$service =
    new BookingService(
        $repo
    );
```

To je ceo princip u praksi.

# 17. Concrete dependency može biti sasvim u redu

Na primer:

```php id="20y0ro"

    private ViewRenderer $view

```

Ako imamo jednu jednostavnu ViewRenderer implementation i nema potrebe za zamenom:

```text id="bfxpcx"
interface možda ne dodaje vrednost
```

Ne pravimo ceremony bez razloga.

---

# 18. Constructor Injection vs Setter Injection

Constructor injection:

```php id="qdbayk"
public function __construct(
    BookingRepository $repo
) {}
```

Setter injection:

```php id="0zcd5d"
public function setRepository(
    BookingRepository $repo
): void {
    $this->repo = $repo;
}
```

Constructor je obično bolji za:

```text id="kr2rsm"
obavezne dependencies
```

jer object ne može postojati u invalid stanju.

---

# 19. Problem setter injection-a

Možeš napraviti:

```php id="q0fpyl"
$service =
    new BookingService();

$service->create(...);
```

pre nego što pozoveš:

```php id="23he4i"
$service->setRepository(...);
```

Sada object postoji, ali nije spreman.

Constructor injection garantuje:

```text id="7j0drf"
ako object postoji
→ required dependencies postoje
```

---

# 20. Method Injection

Ponekad dependency treba samo jednoj metodi:

```php id="cy2mav"
public function sendVoucher(
    Booking $booking,
    Mailer $mailer
): void {
    ...
}
```

To je:

```text id="ay0prf"
method injection
```

Može imati smisla u specifičnim slučajevima.

Ali za stabilne dependencies klase constructor injection je obično jasniji.

---

# 21. Service Locator

Lošiji pattern:

```php id="g8u6vy"
final class BookingService
{
    public function create(): void
    {
        $repo =
            Container::get(
                BookingRepository::class
            );
    }
}
```

Dependency ne vidiš u constructor-u.

Klasa izgleda:

```php id="fokmgm"
bez dependencies
```

ali zapravo tajno zavisi od globalnog Container-a.

To je:

```text id="o0leq2"
Service Locator
```

---

# 22. Zašto Service Locator otežava razumevanje

Da bi znao šta BookingService koristi, moraš:

```text id="pc1ymm"
čitati method body

tražiti Container::get

razumeti global container state
```

Kod constructor injection-a:

```php id="0cq5zl"
__construct(
    BookingRepository $bookings,
    InventoryRepository $inventory
)
```

odmah vidiš contract.

---

# 23. Hidden dependencies su problem

Primer:

```php id="mbk7y6"
final class BookingService
{
    public function create()
    {
        $logger =
            GlobalContainer::logger();

        $repo =
            GlobalContainer::bookings();
    }
}
```

Tests sada zavise od:

```text id="4051c1"
global mutable state
```

Redosled testova može postati problem.

Dependency Injection smanjuje taj coupling.

---

# 24. Static helper kao hidden dependency

Na primer:

```php id="mlnmmy"
Mailer::send(...)
```

može biti praktično.

Ali ako je to facade/static gateway ka globalnom service-u, dependency nije vidljiva u class signature-u.

To nije nužno uvek loše.

Ali treba razumeti tradeoff.

---

# 25. Laravel Facades

Laravel:

```php id="77vspz"
Mail::to(...)->send(...);

Cache::get(...);

DB::transaction(...);
```

izgleda kao static call.

Ali Facades su framework proxy ka service container bindings.

I dalje postoji service ispod.

Convenience je velika.

Ali dependency je manje očigledna nego constructor injection.

# 32. DI Container

Container održava mapu:

```text id="e8i53q"

→ implementation
```

i/ili zna kako da:

```text id="0smxxb"

```

Na primer:

```text id="wh95wx"

needs BookingRepository

BookingRepository

PdoBookingRepository
needs PDO
```

Container prati graph i pravi objekte.

```php id="gxrz7w"
    new BookingService(
```

# 34. Autowiring

# 37. Instance binding

# 38. Transient / bind lifecycle

Ako container svaki put kada neko traži:

```text id="9dbn64"
SomeService
```

napravi novu instancu:

```text id="m9tt4o"
resolve A
→ new SomeService

resolve B
→ new SomeService
```

to je transient-like behavior.

Laravel `bind()` tipično daje novu instancu po resolution-u.

---

# 39. Singleton lifecycle

Ako container napravi jednu instancu i ponovo je koristi:

```text id="v0skyn"
first resolve
→ new Service

next resolves
→ same Service
```

to je singleton-like lifecycle.

U Laravel-u:

```php id="hvkzq2"
$this->app->singleton(...)
```

---

# 40. Singleton ne znači nužno "zauvek"

U klasičnom PHP-FPM request-u container/application uglavnom postoji tokom tog request-a.

Dakle singleton često praktično znači:

```text id="5081i5"
jedna instanca
u okviru application lifecycle-a/request-a
```

Kod long-running runtime-a semantics postaju još važnije.

---

# 41. Scoped lifecycle

Kod long-running worker/runtime modela može postojati:

```text id="zvbkht"
scoped
```

značenje:

```text id="cykktj"
jedna instanca po request/job lifecycle-u
```

To sprečava leakage state-a između requests.

Laravel ima scoped bindings upravo za takve scenario-e.

---

# 42. Lifecycle je važan za stateful services

Ako Service sadrži:

```php id="4kreb2"

```

i bude singleton u long-running procesu, može nastati:

```text id="neol5a"
state leakage
između requests
```

Zato je bolje da service dependencies budu:

```text id="pm7hgj"
stateless
```

koliko je praktično.

I da lifecycle bude nameran.

# 84. Zašto je ovo važno za Laravel intervju

Ako te pitaju:

> Šta radi Service Container?

Dobar odgovor nije samo:

```text id="sred3l"
"Dependency Injection."
```

Bolje:

> Laravel Service Container resolve-uje object dependencies, može automatski da autowire-uje concrete classes, a za interfaces definišemo bindings. Tako application code može da zavisi od abstractions, dok container/composition configuration bira concrete implementations i njihov lifecycle.

To pokazuje da razumeš mehanizam.

# 85. Service Provider vs Container


# Najvažnije za zapamtiti

Dependency je:

```text id="07cdz5"
objekat/service
koji druga klasa treba
da bi radila
```

Dependency Injection:

```text id="737xqz"
dependency se daje spolja
```

umesto:

```text id="obw14h"
klasa sama pravi dependency
```

Constructor injection:

```php id="gdnke9"
__construct(
    BookingRepository $bookings
)
```

čini dependency:

```text id="0sflww"
eksplicitnom
obaveznom
testabilnom
```

DI:

```text id="isf3s9"
≠ DI Container
```

Možeš imati potpuno dobar DI sa običnim:

```php id="qg2mgd"
new BookingService(
    $repository
);
```

Composition Root:

```text id="e7iv76"
mesto gde gradimo object graph
```

Tu je normalno imati:

```text id="f18k0b"
new PDO
new Repository
new Service
new Controller
```

DIP:

```text id="byjn8w"
high-level code
zavisi od abstractions
ne concrete low-level details
```

Na primer:

```text id="ijtt93"
BookingService
↓
BookingRepository
↑
PdoBookingRepository
```

Service Locator:

```text id="3qad7i"
sakriva dependencies
iza globalnog Container::get()
```

i često je lošiji od constructor injection-a.

Container:

```text id="dq5875"
automatizuje object construction
dependency resolution
bindings
lifecycles
```

Autowiring:

```text id="14au0f"
container čita constructor types
i automatski resolve-uje graph
```

Interface zahteva:

```text id="p8hcsf"
binding
```

jer container ne može sam znati koju implementation želiš.

Laravel:

```text id="hquoo2"
Service Container
→ resolves dependencies

Service Provider
→ registers/configures bindings
```

`bind`:

```text id="h7xb10"
nova instanca po resolution-u
```

`singleton`:

```text id="d4ih5d"
shared instance
```

`scoped`:

```text id="4f2y7d"
shared unutar scope-a
reset između scope-ova
```

Najvažnija architectural ideja:

```text id="p9bnfu"
Application classes
→ koriste dependencies

Composition Root
→ odlučuje koje concrete dependencies postoje
```

I najvažnija rečenica:

> **Dependency Injection nije magija kojom framework pravi objekte — to je princip da klasa koristi ono što joj je dato, dok se odluka o tome kako se te zavisnosti konstruišu drži na spoljašnjoj composition granici aplikacije.**
