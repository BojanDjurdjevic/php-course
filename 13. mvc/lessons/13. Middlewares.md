# 13. Middleware Pipeline

## 1. Šta middleware rešava

Zamisli da svaki Controller počinje ovako:

```php
if (!$this->auth->check()) {
    return Response::redirect(
        '/login',
        303
    );
}

if (!$this->csrf->isValid(
    $request->input('_token')
)) {
    return Response::html(
        'Forbidden',
        403
    );
}

$start = hrtime(true);

// controller logic

$duration =
    hrtime(true) - $start;
```

Ako imamo 20 Controller-a, vrlo brzo ćemo imati:

```text
auth check
CSRF check
logging
timing
security headers
rate limiting
```

ponovljene svuda.

To su:

```text
cross-cutting concerns
```

odnosno concerns koji presecaju veliki deo aplikacije.

Tu middleware ima smisla.

---

# 2. Osnovni mentalni model

Middleware stoji između:

```text
Request
```

i:

```text
Controller
```

Ali zanimljiv deo je da može raditi i:

```text
pre Controller-a
```

i:

```text
posle Controller-a
```

Mentalno:

```text
Request
↓
Middleware
↓
Controller
↓
Middleware
↓
Response
```

To je više od običnog:

```text
"filter pre Controller-a"
```

---

# 3. Najjednostavniji middleware contract

Možemo zamisliti:

```php
interface Middleware
{
    public function process(
        Request $request,
        callable $next
    ): Response;
}
```

Middleware dobija:

```text
Request
+
$next
```

`$next` predstavlja:

```text
sledeći korak pipeline-a
```

---

# 4. Najvažnija linija

Tipičan middleware:

```php
$response =
    $next($request);
```

Ova linija znači:

> Prosledi request dalje kroz pipeline i sačekaj da dobiješ Response nazad.

To je srce middleware mehanizma.

---

# 5. Pre i posle `$next`

Na primer:

```php
public function process(
    Request $request,
    callable $next
): Response {
    // BEFORE

    $response =
        $next($request);

    // AFTER

    return $response;
}
```

Sve iznad:

```php
$next($request)
```

dešava se pre Controller-a.

Sve ispod njega:

```text
posle Controller-a
dok Response ide nazad
```

---

# 6. Onion model

Pretpostavimo middleware:

```text
A
B
C
```

i Controller.

Tok nije:

```text
A
B
C
Controller
A
B
C
```

```text

↓
B before
↓
C before
↓

↓
```

To je:


# 7. Funkcijski mentalni model

Možemo zamisliti:

```text
A(
    B(
        C(
            Controller
        )
    )
)
```

Svaki middleware:

```text
obavija sledeći sloj
```

Zato se response vraća obrnutim redosledom.

# 8. Primer sa logging-om

```php
final class RequestLoggingMiddleware
    implements Middleware
{
    public function __construct(
        private Logger $logger
    ) {}

    public function process(
        Request $request,
        callable $next
    ): Response {
        $this->logger->info(
            'Request started',
            [
                'method' =>
                    $request->method(),

                'path' =>
                    $request->path(),
            ]
        );

        $response =
            $next($request);

        $this->logger->info(
            'Request completed',
            [
                'status' =>
                    $response->status(),
            ]
        );

        return $response;
    }
}
```

Middleware vidi:

```text
request pre Controller-a
```

i:

```text
response posle Controller-a
```

---

# 9. Timing middleware

Vrlo sličan tvom Laravel middleware zadatku:

```php
final class TimingMiddleware
    implements Middleware
{
    public function process(
        Request $request,
        callable $next
    ): Response {
        $start =
            hrtime(true);

        $response =
            $next($request);

        $elapsedNs =
            hrtime(true) - $start;

        $elapsedMs =
            $elapsedNs / 1_000_000;

        return $response
            ->withHeader(
                'X-App-Time-Ms',
                number_format(
                    $elapsedMs,
                    2,
                    '.',
                    ''
                )
            );
    }
}
```

Tok:

```text
start timer
↓
rest of application
↓
Response
↓
calculate duration
↓
add header
```

---

# 10. Zašto Response object čini ovo mogućim

Da Controller radi:

```php
echo $html;
exit;
```

Timing middleware nikad ne bi dobio priliku da:

```text
doda header posle Controller-a
```

Ali zato što Controller:

```php
return $response;
```

middleware može da ga obradi.

Dakle prethodna Response lekcija direktno omogućava middleware architecture.

---

# 11. Short-circuit middleware

Middleware ne mora da pozove `$next`.

Na primer authentication:

```php
if (!$this->auth->check()) {
    return Response::redirect(
        '/login',
        303
    );
}

return $next($request);
```

Ako user nije authenticated:

```text
Request
↓
AuthMiddleware
↓
Redirect Response
```

Controller se uopšte ne izvrši.

To zovemo:

```text
short-circuit
```

pipeline-a.

---

# 12. Auth middleware

Na primer:

```php
final class AuthenticateMiddleware
    implements Middleware
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function process(
        Request $request,
        callable $next
    ): Response {
        if (
            !$this->auth->check()
        ) {
            return Response::redirect(
                '/login',
                303
            );
        }

        return $next(
            $request
        );
    }
}
```

Sada ne moramo na svakoj protected route:

```php
if (!$auth->check()) ...
```

---

# 13. Middleware ne znači da Authorization nestaje

Auth middleware može proveriti:

```text
da li je user logged in
```

Ali ne zna nužno:

```text
da li user 17 sme Booking #42
```

To je:

```text
object-level authorization
```

koji može ostati u:

```text
Policy
Service
Controller orchestration
```

Dakle:

```text
Authentication middleware
≠ kompletna authorization zaštita
```

# 14. CSRF middleware

Za state-changing web routes:

```text
POST
PUT
PATCH
DELETE
```

možemo imati:

```php
final class CsrfMiddleware
    implements Middleware
{
    public function __construct(
        private Csrf $csrf
    ) {}

    public function process(
        Request $request,
        callable $next
    ): Response {
        if (
            $this->isSafeMethod(
                $request->method()
            )
        ) {
            return $next(
                $request
            );
        }

        $token =
            $request->input(
                '_token'
            )
            ?? $request->header(
                'X-CSRF-TOKEN'
            );

        if (
            !$this->csrf
                ->isValid($token)
        ) {
            return Response::html(
                'Forbidden',
                403
            );
        }

        return $next(
            $request
        );
    }
}
```

Centralizovana zaštita.

---

# 15. Safe methods

Tipično:

```text
GET
HEAD
OPTIONS
```

ne menjaju state i ne zahtevaju CSRF token.

State-changing:

```text
POST
PUT
PATCH
DELETE
```

zahtevaju CSRF kada koristimo cookie/session authentication.

Ali tačna middleware politika zavisi od aplikacije.

```text
↓

↓
```

# 31. Kako napraviti pipeline

Pretpostavimo imamo final handler:

```php
$handler =
    fn (Request $request): Response
        => $controller->store(
            $request
        );
```

Middleware:

```php
$middlewares = [
    $logging,
    $auth,
    $csrf,
];
```

Treba ih povezati u nested callable chain.

---

# 32. Jednostavan pipeline builder

Možemo konceptualno:

```php
$next =
    fn (Request $request): Response
        => $controller->store(
            $request
        );

foreach (
    array_reverse(
        $middlewares
    )
    as $middleware
) {
    $previous = $next;

    $next =
        fn (Request $request): Response
            => $middleware->process(
                $request,
                $previous
            );
}

$response =
    $next($request);
```

Ovo je middleware pipeline.

---

# 33. Zašto `array_reverse`

Ako middleware lista glasi:

```text
A
B
C
```

želimo execution:

```text
A(
    B(
        C(
            Controller
        )
    )
)
```

Zato chain gradimo od unutra ka spolja:

```text
Controller
↓
C wraps
↓
B wraps
↓
A wraps
```

Pa koristimo reverse tokom composition-a.

---

# 34. Pipeline class

Možemo imati:

```php
final class MiddlewarePipeline
{
    /**
     * @param list<Middleware> $middleware
     */
    public function handle(
        Request $request,
        array $middleware,
        callable $destination
    ): Response {
        $next = $destination;

        foreach (
            array_reverse(
                $middleware
            ) as $item
        ) {
            $previous = $next;

            $next =
                fn (
                    Request $request
                ): Response =>
                    $item->process(
                        $request,
                        $previous
                    );
        }

        return $next(
            $request
        );
    }
}
```

Jasno i dovoljno za edukativni Router.

# 40. Current user u Request-u?

Neki framework-i dozvoljavaju:

```php

```

što je praktično.

Auth middleware može resolve-ovati user-a.

Ali možeš i imati poseban:

# 41. Middleware i exceptions

Šta ako Controller baci exception?

Ako middleware radi:

```php
$response =
    $next($request);
```

exception prekida normalni flow.

Možemo imati spoljašnji error handling middleware:

```php
try {
    return $next($request);
} catch (Throwable $e) {
    return $this->handler
        ->toResponse(
            $e,
            $request
        );
}
```

To je veoma moćan pattern.

---

# 42. Error middleware kao outermost boundary

Stack:

```text
ErrorHandler
↓
Logging
↓
Auth
↓
Controller
```

Ako bilo šta unutra baci exception:

```text
ErrorHandler
```

ga hvata i pretvara u:

```text
Response
```

To daje elegantan:

```text
Request in
→ Response out
```

contract čak i kada nešto pukne.

---

# 43. Middleware ili global `set_exception_handler()`?

Oba modela postoje.

`set_exception_handler()`:

```text
PHP-level final safety net
```

Error middleware:

```text
application pipeline-level exception mapping
```

Možemo imati oba:

```text
middleware
→ normal application exception conversion

global PHP handler
→ ultimate fallback
```

Ne moramo MiniStay učiniti previše sofisticiranim, ali koncept je važan.

---

# 44. `finally` u middleware-u

Ako želimo da nešto uradimo čak i kada exception prođe:

```php
$start = hrtime(true);

try {
    return $next(
        $request
    );
} finally {
    $elapsed =
        hrtime(true)
        - $start;

    // metrics
}
```

Ovo je korisno za:

```text
timing
cleanup
metrics
```

jer `finally` radi i na exception flow-u.

---

# 45. Logging middleware i exception

Ako napišemo samo:

```php
$response =
    $next($request);

$this->logger->info(...);

return $response;
```

`after` log se neće izvršiti ako `$next()` baci exception.

Ako želimo log i failure-a:

```php
try {
    $response =
        $next($request);

    $this->logger->info(
        'Completed'
    );

    return $response;
} catch (Throwable $e) {
    $this->logger->error(
        'Failed'
    );

    throw $e;
}
```

ili logging centralizujemo drugačije.

# 50. Middleware i redirects

```text

→ 303 /login
```

```text

```

# 51. `401` vs `403`

Authentication middleware:

```text
ne znamo ko si / nisi authenticated
→ 401
```

za API.

Authorization:

```text
znamo ko si, ali nemaš pravo
→ 403
```

Za browser app može biti:

```text
unauthenticated
→ redirect login
```

umesto čistog 401 page-a.

# 52. Middleware state

Middleware bi idealno trebalo da bude:

```text
stateless
```

osim svojih injected dependencies.

Loše je da instance akumuliraju:

```text
current request user
temporary request data
counter specifičan za request
```

u properties koje mogu procuriti kod long-running runtime-a.

Request-specific state neka bude lokalna promenljiva ili scoped object.

```text

↓

↓

↓
pošalje u pipeline
```

Pipeline:

```text
ne zna routing syntax
```

```text
middleware chain

```

# 65. Destination

Finalni destination pipeline-a je obično:

```text
Controller action
```

Na primer:

```php
$destination =
    fn (
        Request $request
    ): Response =>
        $controller->store(
            $request
        );
```

Pipeline ne mora da zna šta je Controller.

Samo callable:

```text
Request → Response
```

# 66. Middleware contract je takođe `Request → Response`

Svaki middleware conceptualno uzima:

```text

+
next(Request → Response)
```

i sam vraća:

```text
Response
```

Zato se composability tako lepo dobija.

# 67. Matematički mentalni model

```text

```

```text

→
(Request → Response)
```

> Middleware uzima handler i vraća novi handler koji ga obavija.

Ne moraš ovo pamtiti formalno, ali lepo objašnjava zašto pipeline funkcioniše.

# Najvažnije za zapamtiti

Middleware rešava:

```text
cross-cutting request/response concerns
```

kao što su:

```text
authentication
CSRF
logging
timing
rate limiting
CORS
security headers
maintenance mode
```

Osnovni contract:

```php
process(
    Request $request,
    callable $next
): Response
```

Najvažnija linija:

```php
$response =
    $next($request);
```

Iznad `$next`:

```text
BEFORE Controller
```

Ispod `$next`:

```text
AFTER Controller
```

Execution order:

```text
A before
↓
B before
↓
Controller
↓
B after
↓
A after
```

Middleware može:

```text
short-circuit
```

i vratiti Response bez pozivanja `$next`.

Na primer:

```text
unauthenticated
→ redirect / 401

invalid CSRF
→ 403

rate limit exceeded
→ 429
```

Middleware:

```text
nije mesto za business logic
```

Availability, pricing i inventory pripadaju Service/domain sloju.

Authentication:

```text
odličan middleware concern
```

Object-level authorization:

```text
često Policy/Service concern
```

Order middleware-a je važan.

Spoljašnji middleware i dalje vidi Response koji je napravio unutrašnji short-circuit.

Response object omogućava middleware-u da:

```text
menja headers
loguje status
meri vreme
```

nakon Controller-a.

Pipeline se izvršava:

```text
PRE nego što Response::send()
pošalje output
```

Laravelov:

```php
$next($request)
```

nije magija.

To je samo sledeći callable u nested request pipeline-u.

Centralni mentalni model:

```text
REQUEST
↓
MIDDLEWARE BEFORE
↓
CONTROLLER / USE CASE
↓
MIDDLEWARE AFTER
↓
RESPONSE
```

Ako samo jednu rečenicu zapamtiš:

> **Middleware ne izvršava business use case — on obavija request lifecycle i odlučuje šta mora da se desi pre i posle use case-a, ili da li request uopšte sme da stigne do njega.**
