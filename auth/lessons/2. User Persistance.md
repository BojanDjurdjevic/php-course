# Lekcija 2/15 — User persistence: users tabela, User objekat i repository

Cilj ove lekcije je da precizno razdvojimo:
šta čuvamo u bazi
šta predstavlja User objekat
šta radi UserRepository
šta ne treba gurati u auth/session sloj

Najvažniji mentalni model:
Authentication ne postoji bez nekog trajnog izvora identiteta korisnika.

U našem slučaju to je najčešće:
users tabela
↓
UserRepository
↓
User objekat

1. Minimalna users tabela
Za klasičan email/password auth, minimalno nam treba nešto poput:
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

Za auth sistem su suštinski:
id
email
password_hash

Ostalo zavisi od aplikacije.

Na primer kasnije možeš imati:
name
email_verified_at
status
role
updated_at

ali nije potrebno da odmah zatrpamo tabelu.
2. Zašto email mora biti UNIQUE?
Ako login radi preko email-a:
email + password

onda email treba da identifikuje najviše jednog korisnika.

Ne želiš:
user #12 → test@example.com
user #47 → test@example.com

pa onda:
findByEmail('test@example.com')

vrati dve osobe.

Zato:
email VARCHAR(255) NOT NULL UNIQUE

nije samo validation pravilo.

To je i database invariant.

Čak i ako aplikacija proverava:
if ($users->existsByEmail($email)) {
    // reject
}

baza i dalje treba da ima UNIQUE.

Zašto?

Zbog konkurentnih request-ova.

Dva registration request-a mogu skoro istovremeno proveriti:
email ne postoji ✅

i oba pokušati insert.

Database unique constraint je poslednja zaštita.

To se lepo povezuje sa concurrency pričom koju smo radili ranije.
3. Zašto password_hash, a ne password?
Namerno bih kolonu nazvao:
password_hash

jer ona ne sadrži password.

To odmah čini model jasnijim.

Ne:
password VARCHAR(255)

ako unutra zapravo čuvaš hash.

Bolje:
password_hash VARCHAR(255)

Mentalno:
plain password
→ postoji samo tokom registration/login request-a

password hash
→ trajno čuvamo u bazi

Detaljno hashiranje dolazi u sledećoj lekciji.
4. Zašto VARCHAR(255) za hash?
Ne želiš da hardcode-uješ strukturu trenutnog hash algoritma.

PHP može koristiti različite algoritme i format hash-a može evoluirati.

Zato je praktično:
password_hash VARCHAR(255)

umesto:
CHAR(60)

samo zato što neki današnji bcrypt hash ima određenu dužinu.

Poenta:
Baza treba da čuva hash bez nepotrebnog vezivanja za jedan konkretan algoritam.

5. User ID je bolji session identifier od email-a
Posle login-a mogli bismo da uradimo:
$_SESSION['email'] = $user->email();

ali je obično bolje:
$_SESSION['user_id'] = $user->id();

Zašto?

Email može da se promeni.

ID tipično ostaje stabilan.

Dakle:
email
→ credential/login identifier

id
→ stabilni internal identity

To je važna razlika.
6. User objekat
Recimo:
final class User
{
    public function __construct(
        private int $id,
        private string $email,
        private string $passwordHash
    ) {}

    public function id(): int
    {
        return $this->id;
    }

    public function email(): string
    {
        return $this->email;
    }

    public function passwordHash(): string
    {
        return $this->passwordHash;
    }
}

Ovaj objekat predstavlja:
jednog korisnika iz našeg sistema

Ne predstavlja:
HTTP request
session
SQL query
login form

To su druge odgovornosti.
7. Da li User treba da zna password?
Tu treba biti precizan.

User objekat može legitimno imati:
passwordHash

jer je to deo persisted user state-a.

Ali ne treba da nosi:
plain password

nakon što nam više nije potreban.

Dakle:
$user->passwordHash()

može imati smisla.

Ali nešto poput:
$user->password()

koje vraća originalni plain password — ne.
8. User objekat nije isto što i login DTO
Login request može doneti:
email
plain password

To može biti:
final readonly class LoginData
{
    public function __construct(
        public string $email,
        public string $password
    ) {}
}

A User ima:
id
email
passwordHash

Dakle:
LoginData
→ ono što korisnik pokušava da dokaže

User
→ persisted identity/state

Nemoj ih mešati.
9. Repository mental model
Seti se OOP modula:
Repository je persistence boundary.

Dakle nešto poput:
interface UserRepository
{
    public function findById(int $id): ?User;

    public function findByEmail(string $email): ?User;

    public function save(User $user): void;
}

AuthService ne treba da zna:
SELECT
PDO
table name
fetch mode
SQL syntax

On samo kaže:
$user = $users->findByEmail($email);

A repository zna kako to da uradi.
10. findByEmail() je auth-critical metoda
Login flow će najčešće imati:
$user = $users->findByEmail($email);

pa:
nije pronađen
→ login fail

pronađen
→ proveri password

Dakle repository je deo login procesa, ali repository ne treba da odlučuje da li je login uspešan.

To je bitna granica.

Loše:
$users->login($email, $password);

ako UserRepository sada radi:
SQL
password verification
session

To više nije repository.
11. Ko treba da proverava password?
Ne repository.

Repository treba da vrati podatke:
$user = $users->findByEmail($email);

A auth/application sloj zatim:
password_verify(
    $plainPassword,
    $user->passwordHash()
);

Mentalno:
UserRepository
→ pronađi user-a

AuthService
→ odluči da li credentials dokazuju identitet

To je SRP.
12. PDO implementacija
Minimalno:
final class PdoUserRepository implements UserRepository
{
    public function __construct(
        private PDO $pdo
    ) {}

    public function findByEmail(string $email): ?User
    {
        $stmt = $this->pdo->prepare(
            'SELECT id, email, password_hash
             FROM users
             WHERE email = :email
             LIMIT 1'
        );

        $stmt->execute([
            'email' => $email
        ]);

        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if ($row === false) {
            return null;
        }

        return new User(
            (int) $row['id'],
            $row['email'],
            $row['password_hash']
        );
    }
}

Ovde repository radi tačno ono što očekujemo:
SQL row
↓
mapiranje
↓
User objekat

13. Zašto ?User?
Jer email možda ne postoji.

Zato:
public function findByEmail(string $email): ?User

znači:
User
ili
null

To lepo tera caller-a da razmisli:
$user = $users->findByEmail($email);

if ($user === null) {
    // login failed
}

Bolje nego da repository baca exception samo zato što user nije pronađen.

"Not found" je ovde normalan business outcome.
14. findById() će nam trebati posle login-a
Zašto?

Seti se:
$_SESSION['user_id'] = 17;

Sledeći request:
user_id = 17
↓
UserRepository::findById(17)
↓
User object

Dakle dve veoma važne repository metode su:
findByEmail()

za login,

i:
findById()

za current user resolution.
15. Registration persistence
Kod registracije ćemo imati nešto poput:
validated input
↓
password hash
↓
new user
↓
save()

Ali tu postoji jedna praktična odluka:

Ako id generiše baza:
AUTO_INCREMENT

onda pre INSERT-a novi User možda još nema ID.

Možeš zato imati različite modele.

Na primer DTO:
final readonly class NewUserData
{
    public function __construct(
        public string $email,
        public string $passwordHash
    ) {}
}

pa repository:
public function create(NewUserData $data): User;

ili User sa nullable ID.

Oba pristupa postoje.

Za naš auth kurs nećemo komplikovati više nego što treba.
16. Repository API može biti use-case friendly
Umesto generičkog:
save(User $user)

možemo imati:
public function create(
    string $email,
    string $passwordHash
): User;

ili DTO.

Bitnije je da granica bude jasna nego da slepo jurimo jednu "ispravnu" repository formu.

Za auth flow nama trebaju funkcionalno:
findByEmail
findById
create

To je dovoljno.
17. Email normalizacija
Praktična tema: šta ako korisnik unese:
 Bojan@Example.com

a u bazi imaš:
bojan@example.com

Pre persistence/login flow-a često želiš bar:
$email = trim($email);

A pitanje case normalization-a treba rešavati konzistentno.

Čest praktičan pristup:
$email = mb_strtolower(trim($email));

pa čuvati i pretraživati normalizovano.

Bitno je:
Nemoj na registration-u normalizovati na jedan način, a na login-u na drugi.

To kasnije daje "user postoji ali ne mogu da se ulogujem" probleme.
18. Database collation takođe utiče
MySQL poređenje email-a može zavisiti od collation-a.

Neke collations su case-insensitive.

Dakle čak i ako:
Bojan@example.com
bojan@example.com

SQL može da ih tretira kao isto.

Ali nemoj da ti cela application politika zavisi od "valjda collation to rešava".

Bolje:
application normalization
+
UNIQUE constraint

da bude namerno i predvidivo.
19. Da li role ide u users tabelu?
Može.

Na primer:
role VARCHAR(50) NOT NULL DEFAULT 'user'

Ali to već ulazi više u authorization.

Za authentication je dovoljno da znaš:
user postoji
credentials odgovaraju
user identity je potvrđen

Da li je:
admin
supplier
customer

postaje važno kasnije kada odlučuješ šta sme.

Naravno, u realnoj aplikaciji User entity može nositi i role.
20. Account status
Možemo imati:
status VARCHAR(20) NOT NULL DEFAULT 'active'

ili:
active
disabled
suspended

Tada login flow možda kaže:
credentials valid ✅
account active ❌
→ login denied

Ovo je lepo da razumeš:
Validan password ne mora automatski značiti da korisnik sme da dobije authenticated session.

To ćemo više povezati u Lekciji 14.
21. Soft delete korisnika?
Ako koristiš:
deleted_at

onda repository mora da odluči da li:
findByEmail()

vraća soft-deleted user-a.

Za auth sistem obično želiš:
deleted user
→ ne može login

To je opet application/business pravilo koje repository/query treba da podrži.
22. Session ne zamenjuje bazu
Još jednom važna granica:

Loše:
$_SESSION['user'] = [
    'id' => 17,
    'email' => '...',
    'role' => 'admin',
    'status' => 'active',
    ...
];

pa onda više nikad ne pitaš bazu.

Zašto?

User može biti:
disabled
role changed
email changed
deleted

dok je session još živ.

Zato ćemo kasnije koristiti:
session
→ identity reference

repository/database
→ current truth

23. Laravel paralela
Laravelov:
User::where('email', $email)->first()

ili auth provider ispod haube radi istu fundamentalnu stvar:
credential identifier
↓
persistence lookup
↓
User model

A posle session ima user identifier i framework može da učita user-a za sledeći request.

Laravel ti samo automatizuje:
repository/provider
session
current-user resolution

Mi sada pravimo mentalni model ručno.
24. Naš minimalni auth persistence sloj
Za sada možemo zamisliti:
src/
├── Models/
│   └── User.php
├── Contracts/
│   └── UserRepository.php
└── Repositories/
    └── PdoUserRepository.php

UserRepository:
interface UserRepository
{
    public function findById(int $id): ?User;

    public function findByEmail(string $email): ?User;
}

Kasnije dodamo create/update po potrebi.
Najvažnije za zapamtiti
Minimalni user persistence:
users
├── id
├── email UNIQUE
├── password_hash
└── created_at

Ključne razlike:
plain password
→ privremeni credential

password_hash
→ trajno se čuva u bazi

email
→ login identifier / credential identifier

id
→ stabilni internal user identity

Arhitektura:
User
→ persisted user state

UserRepository
→ persistence boundary

AuthService
→ proverava credentials i odlučuje da li login uspeva

Repository treba da radi:
findByEmail()
findById()
create/save()

ali ne:
password verification
session login
authorization

I najvažniji tok:
LOGIN
email
↓
UserRepository::findByEmail()
↓
User
↓
password verification

NEXT REQUEST
session user_id
↓
UserRepository::findById()
↓
current User

I database pravilo:
application validation
+
UNIQUE(email)

jer baza mora da štiti invariant čak i kod concurrent request-ova.
