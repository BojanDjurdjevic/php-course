# 6. Session as Authstate

## Module 10 — Authentication bez frameworka

### Lekcija 6/15 — Sessions kao auth state

Cilj ove lekcije je da potpuno razjasnimo šta PHP session
zapravo jeste i kako njome održavamo authenticated state između više HTTP request-ova.

Najvažniji mentalni model:

HTTP je stateless, a session nam omogućava da više različitih request-ova povežemo sa istim korisnikom.

---

## 1. Zašto nam session uopšte treba?

Korisnik pošalje:

```http
POST /login
```

Mi proverimo credentials i utvrdimo:

ovo je user #17

Ali login request se završi.

Sledeći request:

```http
GET /dashboard
```

sam po sebi nema pojma šta se dogodilo u prethodnom request-u.

HTTP nema ugrađeno:

"ovaj browser je malopre uspešno loginovan"

Zato nam treba state koji preživi više request-ova.

Kod klasičnog PHP authentication-a to je:

session

---

## 2. `session_start()`

Da bi PHP učitao ili napravio session, pozivamo:

```php
session_start();
```

To konceptualno znači:

```text
da li browser šalje poznati session ID?
↓
DA
→ pronađi postojeću session
```

```text
NE
→ napravi novu session
```

Nakon toga dobijaš:

```php
$_SESSION
```

koji se ponaša kao associative array.

Na primer:

```php
$_SESSION['user_id'] = 17;
```

---

## 3. Gde se session podaci zapravo nalaze?

Ovo je veoma važna stvar:

Browser tipično ne čuva ceo `$_SESSION`.

Browser dobija session cookie sa identifier-om, recimo konceptualno:

PHPSESSID=abc123xyz

Dok server čuva podatke povezane sa tim ID-em:

```text
abc123xyz
→ user_id = 17
```

Dakle:

```text
BROWSER
→ session ID
```

```text
SERVER
→ session data
```

Ne:

```text
browser cookie
→ ceo user/session sadržaj
```

---

## 4. Kompletan login tok sa session-om

Login:

```text
POST /login
↓
password_verify() ✅
↓
session_regenerate_id(true)
↓
$_SESSION['user_id'] = 17
↓
response browseru
↓
browser čuva session cookie
```

Sledeći request:

```text
GET /dashboard
↓
browser šalje session cookie
↓
PHP vidi session ID
↓
session_start()
↓
učitava session data
↓
$_SESSION['user_id'] === 17
```

I sada znamo ko je authenticated user.

---

## 5. Session cookie nije authentication dokaz sam po sebi

Važna nijansa:

Cookie sadrži session identifier.

On praktično služi kao ključ:

```text
session ID
↓
server-side session data
↓
authenticated identity
```

Ako attacker dobije validan session ID authenticated korisnika, može potencijalno preuzeti tu session.

Zato session ID mora da se tretira kao secret.

Mentalno:

```text
password
→ secret credential za login
```

```text
session ID
→ secret credential za već uspostavljenu session
```

Zato session security postaje veoma važna tema.

To detaljnije radimo u sledećoj lekciji.

---

## 6. Šta čuvamo u session-u?

Za minimalan auth:

```php
$_SESSION['user_id'] = $user->id();
```

To je često dovoljno.

Možemo eventualno imati još nešto poput:

```php
$_SESSION['authenticated_at'] = time();
```

ali ne treba praviti session kao zamenu za bazu.

Najzdraviji model:

```text
session
→ identity reference
```

```text
database
→ current user data
```

---

## 7. Zašto ne čuvamo ceo User?

Recimo:

```php
$_SESSION['user'] = [
    'id' => 17,
    'email' => 'bojan@example.com',
    'role' => 'admin',
    'status' => 'active'
];
```

Problem:

User može kasnije u bazi postati:

```text
role = customer
status = disabled
```

a session i dalje kaže:

```text
admin
active
```

To je stale state.

Zato:

```php
$_SESSION['user_id'] = 17;
```

pa:

```text
user_id
↓
repository
↓
fresh User
```

mnogo je zdravije.

---

## 8. Session nije isto što i cookie

Ovo moraš precizno razlikovati.

### Cookie

Podatak koji browser čuva i šalje serveru.

Na primer:

PHPSESSID=abc123

### Session

Server-side state povezan sa tim session identifier-om.

Dakle:

```text
cookie
→ nosi session identifier
```

```text
session
→ nosi server-side state
```

Naravno, PHP može koristiti drugačiji session storage, ali mentalni model ostaje isti.

---

## 9. `$_SESSION` radi tek nakon `session_start()`

Ako samo napišeš:

```php
$_SESSION['user_id'] = 17;
```

bez pravilnog session lifecycle-a, nemaš pouzdan session sistem.

Tipično rano u request lifecycle-u:

```php
session_start();
```

pa tek onda:

```php
$_SESSION['user_id'];
```

U ozbiljnijoj arhitekturi ne mora svaki controller ručno da zove `session_start()`.

Možeš ga centralizovati u bootstrap-u ili Session wrapper-u.

## 10. Session u Front Controller arhitekturi

Naš public/index.php može konceptualno imati:

```php
<?php
```

require `__DIR__` . '/../vendor/autoload.php';

```php
session_start();


// router...
```

Tada svaki request koji ulazi kroz front controller ima aktivnu session.

Mentalno:

```text
HTTP request
↓
public/index.php
↓
Composer autoload
↓
session_start()
↓
router
↓
controller
```

To je mnogo bolje nego da svaki controller posebno radi:

```php
session_start();
```

## 11. Session wrapper

Još čistije:

```php
final class Session
{
    public function start(): void
    {
        if (session_status() !== PHP_SESSION_ACTIVE) {
            session_start();
        }
    }

    public function put(string $key, mixed $value): void
    {
        $_SESSION[$key] = $value;
    }

    public function get(
        string $key,
        mixed $default = null
    ): mixed {
        return $_SESSION[$key] ?? $default;
    }

    public function forget(string $key): void
    {
        unset($_SESSION[$key]);
    }
}
```

Sada AuthService ne mora direktno da manipuliše superglobalom.

Na primer:

```php
$this->session->put(
    'user_id',
    $user->id()
);
```

To daje:

```text
AuthService
→ zavisi od Session abstraction/wrapper
```

```text
Session
→ zna za $_SESSION
```

---

## 12. Zašto je wrapper koristan?

Bez njega:

```php
$_SESSION['user_id'] = ...
```

se može pojaviti svuda:

```text
AuthService
Controller
Middleware
Helper
View
```

i brzo izgubiš kontrolu.

Sa wrapper-om:

```text
jedno mesto
→ session API
```

Dobijaš:

```text
lakše testiranje
jasniju odgovornost
manje direktnog oslanjanja na superglobals
```

Isti princip kao sa Request klasom.

---

## 13. Kako znamo da li je user authenticated?

Najjednostavnije:

```php
$userId = $_SESSION['user_id'] ?? null;
```

Ako:

user_id postoji

to je signal da session tvrdi da imamo authenticated identity.

Ali još ne mora da znači da user zaista postoji.

Zato:

```text
session user_id
↓
repository lookup
↓
User ili null
```

Tek tada dobijaš validnog current user-a.

---

## 14. Šta ako session ima user_id koji više ne postoji?

Na primer:

```php
$_SESSION['user_id'] = 17
```

ali user #17 je obrisan.

Sledeći request:

```php
findById(17)
```

```text
→ null
```

Tada auth sistem treba da tretira session kao nevalidnu:

```text
nema validnog user-a
→ guest
```

i verovatno ukloni stale user_id.

To ćemo detaljnije u Lekciji 9.

---

## 15. Šta ako user postoji ali je disabled?

Isto važna nijansa.

Session kaže:

user_id = 17

Repository vrati user-a, ali:

status = disabled

Auth sistem može reći:

```text
session postoji
ali account više nije eligible
→ logout / guest
```

Dakle:

```text
session user_id
≠ bezuslovna istina da je user validno authenticated zauvek
```

Database ostaje source of truth.

---

## 16. Session lifetime

Session ne mora trajati zauvek.

Postoje najmanje dva povezana pojma:

```text
cookie lifetime
server-side session lifetime
```

Ako browser izgubi/izbriše session cookie:

više ne zna session ID

Ako server ukloni session data:

ID više nema validno stanje

U oba slučaja authenticated state prestaje da bude dostupan.

Detalje o lifetime/cookie opcijama radimo više u sledećoj lekciji.

---

## 17. Session cookie tipično nema user ID

Ne treba praviti:

cookie:

user_id=17

i onda verovati:

```php
$currentUserId = $_COOKIE['user_id'];
```

jer browser kontroliše taj cookie i mogao bi jednostavno promeniti:

```text
17 → 1
```

i pokušati da postane admin.

Sa session modelom browser šalje opaque session ID:

abc123xyz

a server odlučuje šta ta session predstavlja.

To je fundamentalna razlika.

---

## 18. Session ID treba da bude nepredvidiv

Ne želiš:

```text
user 1 → session 1
user 2 → session 2
```

ili:

session = `md5(user_id)`

PHP session mehanizam generiše session identifikatore umesto da ih ti ručno praviš.

Auth sistem ne treba da izmišlja svoj session ID generator bez ozbiljnog razloga.

---

## 19. Session se čuva između request-ova, ne između korisnika

Svaki browser/client tipično ima svoj session identifier.

Na primer:

```text
Browser A
→ session AAA
→ user #17
```

```text
Browser B
→ session BBB
→ user #42
```

Server na osnovu cookie-ja zna koju session da učita.

Zato `$_SESSION` nije jedan globalni array za sve korisnike.

To je per-session state.

---

## 20. Dva browsera, isti user

Isti user može biti loginovan:

```text
Chrome
→ session A
```

```text
Phone
→ session B
```

oba mogu sadržati:

user_id = 17

Dakle:

```text
user
≠ session
```

Jedan user može imati više aktivnih sessions.

Ovo kasnije postaje bitno ako želiš:

```text
logout all devices
session management
device list
```

ali za naš minimalni auth dovoljno je razumeti razliku.

---

## 21. Session i concurrent requests

Browser može istovremeno poslati više request-ova.

PHP session storage može imati locking ponašanje dok je session otvorena, zavisno od handler-a.

To znači da long-running request može blokirati drugi request iste session.

Za naš auth kurs nećemo duboko ulaziti u session locking, ali vredi znati:

Session nije samo array; iza nje postoji storage/lifecycle mehanizam.

U ozbiljnijim aplikacijama ponekad se session rano pročita i zatvori kada više nije potrebna.

---

## 22. Session storage nije nužno fajl

PHP može čuvati session u različitim storage backend-ima.

Na primer:

```text
filesystem
Redis
database
custom handler
```

Application code i dalje može koristiti:

```php
$_SESSION
```

dok storage implementation može biti drugačija.

To je slično:

```text
Session API
→ abstraction
```

```text
filesystem/Redis
→ implementation
```

---

## 23. Redis i sessions

Pošto si radio osnove Redis-a, ovo je dobra paralela.

Na jednom serveru file-based session može biti sasvim dovoljna.

Ali ako imaš više app servera:

```text
Server A
Server B
Server C
```

a session fajl postoji samo na Server A, request koji ode na B možda ne vidi isti state.

Zato shared session storage kao Redis može imati smisla:

```text
Browser
↓
Load balancer
├── Server A
├── Server B
└── Server C
       ↓
     Redis
```

Svi serveri vide isti session state.

To je infrastruktura, ne menja auth mentalni model.

## 24. Session-based auth vs token auth

Za sada radimo:

session-based authentication

Mentalno:

```text
browser
→ session cookie
→ server-side session
```

Kod token-based auth-a često imaš:

```text
client
→ bearer token
→ server validates token
```

To je drugačiji model.

Nemoj ih mešati.

Laravel Sanctum si koristio i tamo si video da različiti auth scenariji mogu koristiti cookies/session ili API tokens.

Za ovaj modul ostajemo fokusirani na classic web session auth.

## 25. Session state treba biti mali

Ne želiš:

```php
$_SESSION['all_bookings'] = [...500 bookings...];
$_SESSION['hotels'] = [...];
$_SESSION['user'] = [...100 fields...];
```

Session nije cache za celu aplikaciju.

Za authentication:

```php
$_SESSION['user_id'] = 17;
```

je često sasvim dovoljno.

Manje state-a znači:

```text
manje stale podataka
manje storage overhead-a
jednostavniji auth lifecycle
```

## 26. Flash data je druga session upotreba

Session nije samo za auth.

Može se koristiti i za:

```text
flash messages
old form input
CSRF token
```

Na primer:

```php
$_SESSION['flash']['success']
    = 'Registration successful.';
```

Ali to su druge vrste session state-a.

Nemoj mešati:

auth identity

sa:

temporary UI state

iako tehnički žive u istoj session.

## 28. Login kroz Session wrapper

Na primer:

```php
public function login(User $user): void
{
    session_regenerate_id(true);

    $this->session->put(
        'user_id',
        $user->id()
    );
}
```

A check:

```php
public function check(): bool
{
    return $this->session->get('user_id') !== null;
}
```

Kasnije ćemo ovo poboljšati jer user_id može biti stale, ali mentalno je dobar početak.

---

## 29. Logout kroz Session wrapper

Minimalno:

```php
$this->session->forget('user_id');
```

Tada session može i dalje postojati za druge stvari:

```text
flash
cart
CSRF
```

ali više ne predstavlja authenticated user-a.

Potpuni session destruction je posebna odluka koju ćemo raditi u Lekciji 11.

## 30. Laravel paralela

Kada Laravel radi:

```php
auth()->login($user);
```

ili:

```php
Auth::attempt(...)
```

framework ispod održava auth identity kroz configured guard/session mehanizam.

A kada na sledećem request-u napišeš:

```php
auth()->user();
```

framework rekonstruše current user-a iz persisted auth state-a.

Mi sada ručno razumemo:

```text
cookie
↓
session ID
↓
server-side session
↓
user identifier
↓
user provider/repository
↓
current User
```

To je stvarna osnova.
