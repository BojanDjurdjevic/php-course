# 12. Remember Me — Part 1

## Module 10 — Authentication bez frameworka

### Lekcija 12/15 — Persistent authentication

Obična session authentication traje dok postoji validna session.

Ali korisnik često očekuje opciju:

```text
☑ Remember me
```

što praktično znači:

> Ako mi obična session nestane, pokušaj da me ponovo prepoznaš na ovom browser-u bez ponovnog unosa password-a.

Najvažniji mentalni model:

```text
SESSION AUTH
→ kratkotrajniji authenticated state

REMEMBER ME
→ dugotrajniji persistent credential
→ može ponovo uspostaviti session
```

Remember-me cookie zato **ne treba da bude sama session**.

On treba da omogući kreiranje nove authenticated session.

---

## 1. Šta Remember Me zapravo radi?

Pretpostavimo user se loginuje danas.

Session:

```text
session ABC
→ user #17
```

Kasnije:

```text
browser zatvoren
session istekla / nestala
```

Bez Remember Me:

```text
GET /dashboard
↓
nema session user_id
↓
guest
↓
login ponovo
```

Sa Remember Me:

```text
GET /dashboard
↓
nema authenticated session
↓
browser šalje remember-me cookie
↓
server proverava persistent token
↓
user prepoznat
↓
kreira se nova authenticated session
```

Dakle Remember Me:

```text
ne održava nužno staru session
```

nego:

```text
može da obnovi authentication
```

---

## 2. Šta nikada ne treba čuvati u Remember Me cookie-ju?

Nikada:

```text
email=bojan@example.com
password=Secret123
```

ili:

```text
user_id=17
password_hash=$2y$...
```

Cookie kontroliše client.

Sve što pošalješ u cookie:

```text
browser može da vidi
browser može da pošalje
attacker može pokušati da ukrade
```

Zato Remember Me mora koristiti:

```text
cryptographically random token
```

Ne password.

---

## 3. Zašto običan `user_id` cookie nije dovoljan?

Katastrofalan model:

```php
setcookie('remember_user', '17');
```

pa:

```php
$userId = $_COOKIE['remember_user'];

$auth->login(
    $users->findById($userId)
);
```

Attacker može jednostavno promeniti:

```text
17 → 1
```

i pokušati da se predstavi kao drugi user.

Dakle cookie mora sadržati nešto što attacker ne može pogoditi:

```text
random secret token
```

---

## 4. Remember-me token je credential

Ako browser ima validan Remember Me token, server može da ga koristi da ponovo authenticate-uje user-a.

Zato:

```text
Remember Me token
→ credential
```

Praktično je sličan:

```text
password-u
session ID-u
password-reset tokenu
```

jer possession tog tokena daje određenu moć.

Zato ga treba tretirati kao secret.

---

## 5. Osnovni random token model

Mogli bismo generisati:

```php
$token = bin2hex(
    random_bytes(32)
);
```

`random_bytes()` daje cryptographically secure random bytes.

Na primer:

```text
8f4bd72c...
```

Mentalno:

```text
random_bytes()
↓
unpredictable secret
↓
remember-me credential
```

Ne koristi:

```php
rand();
mt_rand();
uniqid();
```

za security tokene.

---

## 6. Zašto `random_bytes()`?

Remember token mora biti praktično nemoguće pogoditi brute force-om.

Želimo:

```text
visoku entropiju
+
kriptografski siguran generator
```

PHP već daje:

```php
random_bytes()
```

Zato ne treba sam da praviš random generator.

Na primer:

```php
$token = bin2hex(
    random_bytes(32)
);
```

32 random bytes daju veoma veliki prostor mogućih tokena.

`bin2hex()` samo pretvara binary bytes u string koji je lak za cookie/DB rad.

---

## 7. Da li token čuvamo plaintext u bazi?

Bolje ne.

Zamisli database leak.

Ako tabela sadrži:

```text
user_id = 17
token = abcSecretToken123
```

attacker može taj token odmah staviti u svoj browser.

To je slično krađi session ID-a.

Zato je zdraviji pattern:

```text
browser
→ plaintext token

database
→ token hash
```

Isti princip kao:

```text
password
→ browser/user zna secret

database
→ čuva verifier/hash
```

---

## 8. Token hashing

Za random token ne moramo koristiti sporo password hashing kao:

```php
password_hash()
```

Jer token već ima ogromnu random entropiju.

Možemo koristiti:

```php
$tokenHash = hash(
    'sha256',
    $token
);
```

Ovde je SHA-256 sasvim druga priča nego kod password-a.

Password:

```text
ljudi biraju
→ mala/predvidiva entropija
→ treba spor password hashing
```

Random token:

```text
random_bytes()
→ ogromna entropija
→ brz cryptographic hash je dovoljan verifier
```

Dakle:

```text
password → password_hash()

random token → SHA-256 hash može biti sasvim prikladan
```

---

## 9. Problem: kako pronaći token u bazi ako čuvamo samo hash?

Mogli bismo dobiti cookie token:

```text
abc123...
```

izračunati:

```php
$hash = hash('sha256', $token);
```

pa tražiti:

```sql
SELECT *
FROM remember_tokens
WHERE token_hash = :hash
```

To može raditi.

Ali postoji i veoma praktičan pattern:

```text
selector + validator
```

koji lepo odvaja:

```text
lookup deo
+
secret verification deo
```

To ćemo koristiti u našem mentalnom modelu.

---

## 10. Selector + Validator model

Remember credential podelimo na dva dela:

```text
selector
validator
```

### Selector

```text
nije glavni secret
služi za pronalaženje DB reda
```

### Validator

```text
secret random token
dokazuje possession
```

Cookie može izgledati:

```text
selector:validator
```

Baza:

```text
selector
validator_hash
user_id
expires_at
```

Mentalno:

```text
cookie selector
↓
pronađi DB row
↓
cookie validator
↓
hash validator
↓
uporedi sa stored validator_hash
```

To daje vrlo čist persistent authentication flow.

## 11. Primer `remember_tokens` tabele

Na primer:

```sql
CREATE TABLE remember_tokens (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    selector VARCHAR(64) NOT NULL UNIQUE,
    validator_hash CHAR(64) NOT NULL,
    expires_at DATETIME NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);
```

Ovde:

```text
selector
→ lookup key

validator_hash
→ secret verifier

user_id
→ kome token pripada

expires_at
→ do kada važi
```

---

## 12. Generisanje selector-a i validator-a

Na primer:

```php
$selector = bin2hex(
    random_bytes(9)
);

$validator = bin2hex(
    random_bytes(32)
);
```

Zatim:

```php
$validatorHash = hash(
    'sha256',
    $validator
);
```

U bazu:

```text
selector
validator_hash
user_id
expires_at
```

U browser cookie:

```text
selector:validator
```

Važno:

```text
plaintext validator
→ browser

validator hash
→ database
```

---

## 13. Zašto selector možemo čuvati plaintext?

Selector nije dovoljan da authenticate-uje user-a.

Ako attacker zna samo:

```text
selector
```

još nema:

```text
validator
```

koji je secret.

Selector služi kao indeks:

```text
"Koji DB row treba proveriti?"
```

Validator odgovara:

```text
"Da li client poseduje pravi secret?"
```

To je sličan princip:

```text
username/email
→ identifikator

password
→ secret
```

---

## 14. Kreiranje Remember Me tokena posle login-a

Pretpostavimo:

```php
$auth->attempt(
    $email,
    $password
);
```

uspe.

Ako je user označio:

```text
remember_me = true
```

onda kreiramo persistent credential.

Flow:

```text
credentials valid
↓
normal session login
↓
Remember Me checked?
↓
DA
↓
generate selector + validator
↓
store validator hash in DB
↓
send selector:validator cookie
```

Remember Me se kreira **tek nakon uspešne authentication**.

---

## 15. Cookie konfiguracija

Remember Me cookie treba da bude zaštićen slično session cookie-ju.

Na primer konceptualno:

```php
setcookie(
    'remember_me',
    $selector . ':' . $validator,
    [
        'expires' => time() + 60 * 60 * 24 * 30,
        'path' => '/',
        'secure' => true,
        'httponly' => true,
        'samesite' => 'Lax',
    ]
);
```

Dakle:

```text
Secure
→ HTTPS only

HttpOnly
→ JS ne čita cookie

SameSite
→ ograničava cross-site slanje

Expires
→ persistent cookie
```

Za razliku od običnog session cookie-ja, Remember Me namerno ima duži lifetime.

---

## 16. Expiry mora postojati i u bazi

Nije dovoljno da browser cookie kaže:

```text
expires za 30 dana
```

Server takođe treba da ima:

```text
expires_at
```

Zašto?

Client-side expiry nije nešto čemu server slepo veruje.

Server pri validaciji proverava:

```text
da li token postoji?
da li validator odgovara?
da li expires_at još važi?
```

Dakle:

```text
browser expiry
+
server expiry
```

---

## 17. Automatski login kada nema session-a

Na početku request-a:

```text
ima authenticated session?
├── DA → normalno nastavi
└── NE → postoji remember cookie?
```

Ako cookie postoji:

```text
parse selector + validator
↓
lookup selector
↓
token postoji?
↓
nije expired?
↓
validator hash odgovara?
↓
load User
↓
User active?
↓
login(User)
```

Tako Remember Me ponovo uspostavlja normalnu session.

---

## 18. Verifikacija validatora

Recimo iz cookie-ja dobiješ:

```php
$validator;
```

Iz baze:

```php
$storedHash = $rememberToken->validatorHash();
```

Izračunaš:

```php
$providedHash = hash(
    'sha256',
    $validator
);
```

Za sigurnu proveru:

```php
if (!hash_equals(
    $storedHash,
    $providedHash
)) {
    // invalid remember token
}
```

`hash_equals()` radi timing-safe string comparison.

Za security-sensitive hash/token comparison je bolji izbor od običnog:

```php
===
```

---

## 19. Zašto `hash_equals()`?

Običan string comparison može u nekim implementacijama završiti ranije čim pronađe razliku.

To teoretski može otkriti male timing informacije.

`hash_equals()` je napravljen za poređenje security-sensitive stringova.

Mentalno:

```text
stored verifier
+
calculated verifier
↓
hash_equals()
↓
valid / invalid
```

Za naš Remember Me token:

```php
hash_equals(
    $storedValidatorHash,
    hash('sha256', $validator)
);
```

je lep pattern.

---

## 20. Ne loginuj user-a samo zato što selector postoji

Katastrofalna greška:

```php
$token = $tokens->findBySelector(
    $selector
);

$auth->login(
    $users->findById($token->userId())
);
```

Ovde validator nikada nije proveravan.

Selector nije credential.

Ispravno:

```text
selector pronađe row
↓
validator dokaže possession
↓
tek onda authentication
```

Dakle dva koraka imaju različite uloge:

```text
selector
→ lookup

validator
→ proof
```

## 21. Rotacija Remember Me tokena

Ako persistent token važi 30 dana i isti validator koristimo svakog dana, ukradeni token može biti koristan dugo.

Zdraviji pattern je:

```text
successful remember-me authentication
↓
invalidate old validator
↓
generate new validator
↓
update hash u bazi
↓
replace browser cookie
```

To se zove token rotation.

Mentalno:

```text
old persistent credential
↓
successful use
↓
new persistent credential
```

Slično session ID rotation principu.

---

## 22. Šta ako validator ne odgovara?

Ako selector postoji u bazi:

```text
selector validan
```

ali validator ne odgovara:

```text
validator invalidan
```

to može značiti:

```text
cookie corrupt
stari token
attacker pokušava token
token je već rotiran
```

Bezbedan odgovor:

```text
ne authenticate user-a
```

i često:

```text
obriši Remember Me cookie
```

U strožim sistemima možeš invalidirati i DB token jer mismatch može biti security signal.

---

## 23. Multiple devices

User može izabrati Remember Me na:

```text
Laptop
Phone
Tablet
```

Ne želiš nužno jedan jedini token:

```text
users.remember_token
```

koji svaki novi login pregazi.

Posebna tabela omogućava:

```text
user #17
├── token A → laptop
├── token B → phone
└── token C → tablet
```

Zato je:

```text
remember_tokens
```

kao zasebna tabela fleksibilniji dizajn.

---

## 24. Logout mora invalidirati Remember Me token

Pretpostavimo logout uradi samo:

```php
$this->session->forget('user_id');
```

ali browser i dalje ima:

```text
remember_me=selector:validator
```

Sledeći request:

```text
nema session
↓
Remember Me validan
↓
AuthService loginuje user-a ponovo
```

Korisnik bi izgledao kao da se "ne može izlogovati".

Zato logout sa Remember Me sistemom mora:

```text
invalidate DB token
↓
delete remember cookie
↓
remove session auth
```

---

## 25. Brisanje Remember Me cookie-ja

Na primer:

```php
setcookie(
    'remember_me',
    '',
    [
        'expires' => time() - 3600,
        'path' => '/',
        'secure' => true,
        'httponly' => true,
        'samesite' => 'Lax',
    ]
);
```

Ali pre toga treba iz cookie-ja uzeti selector i invalidirati corresponding DB token.

Mentalno:

```text
logout
↓
read selector
↓
DELETE / revoke token in DB
↓
expire cookie
↓
remove session identity
```

Tada persistent credential više ne postoji ni client-side ni server-side.

---

## 26. Remember Me nije zamena za session

Ovo je centralno.

Ne želimo da svaki request zauvek radi:

```text
remember cookie
↓
DB token lookup
↓
authenticate
```

ako već imamo normalnu authenticated session.

Bolji model:

```text
Remember Me
→ fallback kada normalna session ne postoji
```

Flow:

```text
Request
↓
session authenticated?
├── DA
│   → koristi normalnu session
│
└── NE
    ↓
    remember token postoji?
    ├── NE → guest
    └── DA
        ↓
        validate token
        ↓
        create normal session
```

Dakle Remember Me **obnavlja session**, a onda session nastavlja normalan auth lifecycle.

---

## 27. Gde Remember Me pripada arhitektonski?

Ne želimo AuthService od 1500 linija.

Možemo imati:

```text
AuthService
→ session authentication

RememberTokenRepository
→ token persistence

RememberMeService
→ persistent authentication lifecycle
```

Na primer:

```php
final class RememberMeService
{
    public function __construct(
        private RememberTokenRepository $tokens,
        private UserRepository $users,
        private AuthService $auth
    ) {}
}
```

Odgovornosti:

```text
RememberMeService
→ issue token
→ restore authentication
→ revoke token

RememberTokenRepository
→ DB

AuthService
→ login(User)
```

To lepo sprečava da AuthService postane God Object.
