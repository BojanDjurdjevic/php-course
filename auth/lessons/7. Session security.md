# 7. Session security

## Module 10 — Authentication bez frameworka

### Lekcija 7/15 — Session security: fixation, regeneration i cookie flags

Ovo je jedna od ključnih auth lekcija, jer od ovog trenutka session ID praktično postaje credential.

Najvažniji mentalni model:

Nakon uspešnog login-a ne smemo samo da upišemo user_id u postojeću session. Treba da rotiramo session ID i da session cookie bude dovoljno zaštićen.

---

## 1. Zašto je session ID toliko osetljiv?

Posle login-a imamo otprilike:

Browser:

PHPSESSID=abc123

Server:

```text
abc123
→ user_id = 17
```

Ako attacker dobije:

abc123

njemu često više ne treba password.

Server može da vidi isti session ID i zaključi:

authenticated user = 17

Dakle:

```text
password
→ credential za kreiranje authenticated session
```

```text
session ID
→ credential za korišćenje već postojeće authenticated session
```

Zbog toga session cookie tretiramo kao secret.

---

## 2. Session fixation

Session fixation znači da attacker pokušava da natera žrtvu da koristi session ID koji attacker već zna.

Pojednostavljen scenario:

Attacker zna session ID:

```text
ABC
↓
žrtva nekako počne da koristi ABC
↓
žrtva se loginuje
↓
aplikacija NE promeni session ID
↓
ABC sada predstavlja authenticated user-a
↓
attacker već zna ABC
```

Napadač nije morao da ukrade novi session ID.

On je unapred znao session koji je kasnije postao authenticated.

To je session fixation.

---

## 3. Rešenje: `session_regenerate_id()`

Nakon uspešne authentication:

```php
session_regenerate_id(true);
```

pa onda authenticated state.

Na primer:

```php
if (!password_verify(
    $password,
    $user->passwordHash()
)) {
    return false;
}

session_regenerate_id(true);

$_SESSION['user_id'] = $user->id();
```

Mentalno:

```text
guest session
ABC
↓
credentials valid
↓
regenerate
↓
authenticated session
XYZ
```

Attacker koji je znao:

ABC

više nema novi authenticated identifier:

XYZ

---

## 4. Zašto baš na login-u?

Zato što se menja security privilege level.

Pre:

guest

Posle:

authenticated user

To je odličan trenutak za session ID rotation.

Isti princip ima smisla i kada dođe do ozbiljne promene privilegije, recimo:

```text
normal user
↓
privileged/admin context
```

Centralna ideja:

Kada session dobije značajno više privilegija, rotacija ID-a smanjuje rizik da prethodno poznat identifier nastavi da važi.

---

## 5. Šta znači true?

```php
session_regenerate_id(true);
```

true govori PHP-u da ukloni staru session podatkovnu strukturu nakon regeneracije.

Za naš mentalni model:

```text
old session ID
→ više ne želimo da predstavlja isti state
```

```text
new session ID
→ nastavlja session lifecycle
```

Za tipičan jednostavan login ovo je razuman pristup.

---

## 6. Redosled login-a

Dobar tok:

```text
find user
↓
password_verify()
↓
account checks
↓
optional password rehash
↓
session_regenerate_id(true)
↓
store user_id
```

Na primer:

```php
if (!$this->credentialsAreValid($user, $password)) {
    return false;
}

session_regenerate_id(true);

$this->session->put(
    'user_id',
    $user->id()
);
```

Ne regenerišemo svaki put kad korisnik samo pogreši password.

Security boundary je:

```text
guest → authenticated
```

---

## 7. Session hijacking vs fixation

Ovo treba razlikovati.

### Session fixation

```text
Attacker unapred zna session ID i pokušava da ga zadrži kroz login.
poznat ID
↓
žrtva se loginuje
↓
isti ID ostaje
```

### Session hijacking

Attacker ukrade već authenticated session ID.

Na primer:

```text
authenticated user
↓
session ID procuri
↓
attacker ga koristi
```

Dakle:

```text
fixation
→ attacker zna ID pre authentication
```

```text
hijacking
→ attacker dobije authenticated ID
```

`session_regenerate_id()` je posebno važan protiv fixation-a.

Cookie zaštite i HTTPS pomažu protiv krađe/hijacking-a.

---

## 8. Session cookie flags

Za browser session cookie posebno su važna tri atributa:

```text
Secure
HttpOnly
SameSite
```

Svaki rešava drugačiji problem.

---

## 9. HttpOnly

Cookie:

HttpOnly

znači da browser-side JavaScript ne može normalno da mu pristupa kroz:

document.cookie

To pomaže ako postoji XSS ranjivost.

Bez HttpOnly, malicious JS bi potencijalno mogao da pročita session cookie.

Mentalno:

```text
HttpOnly
→ JavaScript ne može čitati session cookie
```

Ali veoma važno:

HttpOnly ne rešava XSS.

Ako attacker može izvršavati JS na tvojoj stranici, i dalje može praviti štetu u kontekstu korisnika.

HttpOnly samo otežava direktnu krađu cookie-ja kroz JS.

---

## 10. Secure

Cookie sa:

Secure

browser šalje samo preko HTTPS veze.

Mentalno:

```text
Secure
→ session cookie samo preko HTTPS
```

Na production web aplikaciji:

HTTPS + Secure cookie

treba da bude standard.

Bez HTTPS-a, zaštita session-a je fundamentalno slabija.

---

## 11. SameSite

SameSite reguliše u kojim cross-site situacijama browser šalje cookie.

Najčešće vrednosti:

```text
Strict
Lax
None
```

Pojednostavljeno:

```text
Strict
→ najrestriktivnije cross-site slanje
```

```text
Lax
→ balans usability/security za mnoge klasične web app scenarije
```

```text
None
→ dozvoljava cross-site cookie scenario,
   uz Secure zahtev u modernim browserima
```

SameSite pomaže protiv određenih CSRF scenarija.

Ali:

SameSite nije razlog da zaboraviš CSRF zaštitu.

CSRF detaljno ostavljamo za Security modul.

---

## 12. Tipična session cookie konfiguracija

Pre `session_start()` možemo podesiti cookie parametre.

Na primer:

```text
session_set_cookie_params([
    'httponly' => true,
    'secure' => true,
    'samesite' => 'Lax',
]);
```

```php
session_start();
```

Na production HTTPS serveru ovo ima smisla.

Važno:

```text
cookie settings
↓
pre session_start()
```

jer session cookie lifecycle tada još nije započet.

---

## 13. Lokalni development i Secure

Ako lokalno radiš preko običnog:

http://localhost

i postaviš:

```php
'secure' => true
```

browser možda neće slati cookie preko ne-HTTPS konekcije.

Zato environment može uticati na konfiguraciju.

Konceptualno:

```php
'secure' => $isProductionHttps
```

Ali production pravilo ostaje:

```text
session auth
→ HTTPS
→ Secure cookie
```

---

## 14. session.use_strict_mode

PHP ima session konfiguraciju:

```ini
session.use_strict_mode = 1
```

Mentalna ideja:

PHP ne treba olako da prihvata proizvoljan session ID koji client pošalje ako server nema odgovarajuću validnu session.

Ovo dodatno pomaže protiv fixation scenarija.

Za auth sistem je zdrav izbor imati strict session handling.

Ne moraš ga podešavati u svakom fajlu; često ide u PHP/server konfiguraciju.

---

## 15. Cookie name

Default PHP session cookie često je:

PHPSESSID

Možeš promeniti naziv:

```php
session_name('app_session');
```

ali važno:

Promena imena cookie-ja nije security mehanizam sama po sebi.

Ako session sistem nije bezbedan, nazvati cookie:

super_secret_cookie

ne rešava problem.

Security through obscurity nije osnova zaštite.

---

## 16. Session ID ne sme ići kroz URL

Ne želiš:

/account?session_id=abc123

ili:

/profile/PHPSESSID/abc123

Zašto?

URL može završiti u:

```text
browser history
logs
analytics
referrer headers
screenshots
```

Session identifier treba da ide kroz cookie, ne kroz URL.

---

## 17. Ne loguj session ID

Iz istog razloga ne želiš:

```text
logger()->debug(
    'Session: ' . session_id()
);
```

u normalnim application logovima.

Ako log procuri:

```text
session identifier
→ potencijalno authenticated access
```

Dakle:

```text
password
session ID
remember-me token
reset token
```

svi pripadaju porodici secrets.

---

## 18. Session regeneration nije logout

Ovo:

```php
session_regenerate_id(true);
```

ne znači:

logout

Naprotiv, authenticated state može ostati:

```php
$_SESSION['user_id'] = 17;
```

Samo je identifier promenjen.

Dakle:

```text
regenerate
→ promeni session ID
```

```text
logout
→ ukloni authenticated state
```

Dve različite stvari.

---

## 19. Nemoj regenerisati ID nasumično u svakom redu koda

Session rotation je korisna, ali ne znači:

```php
session_regenerate_id(true);
session_regenerate_id(true);
session_regenerate_id(true);
```

na svakom pozivu.

Treba da postoji razlog.

Najvažniji za nas:

```text
successful login
→ regenerate
```

Kasnije možeš imati periodičnu rotation politiku u ozbiljnijim sistemima,
ali to nije potrebno za minimalni auth sistem.

---

## 20. Session lifetime nije dovoljna zaštita sama po sebi

Možeš reći:

session traje samo 20 minuta

ali ako attacker ukrade validan session ID tokom tih 20 minuta, i dalje ima problem.

Dakle security je slojevita:

```text
HTTPS
+
Secure
+
HttpOnly
+
SameSite
+
session regeneration
+
reasonable expiry
+
CSRF/XSS protection
```

Ne postoji jedan magični flag.

---

## 21. Idle timeout vs absolute timeout

Napredniji auth može imati dva koncepta.

### Idle timeout

```text
nije bilo aktivnosti 30 min
→ session više nije authenticated
```

### Absolute timeout

```text
bez obzira na aktivnost,
posle npr. X sati/dana
→ traži novi login
```

Ovo je posebno važno kod osetljivijih aplikacija.

Za naš minimalni projekat dovoljno je da znaš koncept.

---

## 22. Ručni idle timeout

Možeš konceptualno čuvati:

```php
$_SESSION['last_activity'] = time();
```

Pa na request-u:

```php
if (
    time() - $_SESSION['last_activity']
    > $maxIdleSeconds
) {
    // invalidate auth state
}
```

Onda osvežiš:

```php
$_SESSION['last_activity'] = time();
```

Ali ovo je već application-level session policy.

Nemoj mešati sa samim PHP session storage lifetime-om.

---

## 23. IP address binding?

Ponekad ljudi pokušavaju:

session belongs to IP 1.2.3.4

pa ako IP promeni:

logout

To zvuči sigurno, ali može napraviti probleme.

Korisnikov IP može legitimno da se menja:

```text
mobile network
VPN
corporate proxy
ISP
```

Zato rigidno vezivanje session-a za IP nije univerzalno dobro rešenje.

Može biti signal za risk analysis, ali nije nešto što ćemo koristiti kao osnovnu auth zaštitu.

---

## 24. User-Agent binding?

Slično:

zapamti User-Agent

i proveravaj ga.

Može pomoći kao signal, ali nije jak authentication dokaz i može se spoof-ovati.

Dakle:

```text
IP/User-Agent
→ eventualni dodatni signal
```

```text
session ID security
→ osnovna zaštita
```

## 25. Login implementation

Naš AuthService sada može izgledati konceptualno:

```php
public function attempt(
    string $email,
    string $password
): bool {
    $user = $this->users->findByEmail(
        mb_strtolower(trim($email))
    );

    if ($user === null) {
        return false;
    }

    if (!password_verify(
        $password,
        $user->passwordHash()
    )) {
        return false;
    }

    if (!$user->isActive()) {
        return false;
    }

    session_regenerate_id(true);

    $this->session->put(
        'user_id',
        $user->id()
    );

    return true;
}
```

To sada već ima dobar security skeleton.

```text
session_set_cookie_params([
    'httponly' => true,
```

```php

```

Pa ostatak aplikacije koristi već bezbednije podešenu session infrastrukturu.

## 27. Session wrapper i regeneration

Možemo čak sakriti PHP detalj:

```php
final class Session
{
    public function regenerate(): void
    {
        session_regenerate_id(true);
    }

    public function put(
        string $key,
        mixed $value
    ): void {
        $_SESSION[$key] = $value;
    }
}
```

Pa AuthService:

```php
$this->session->regenerate();

$this->session->put(
    'user_id',
    $user->id()
);
```

To povećava testabilnost i čisti auth service.

## 28. Laravel paralela

U Laravel login kodu često vidiš nešto poput:

```php
if (Auth::attempt($credentials)) {
    $request->session()->regenerate();

    return redirect()->intended('dashboard');
}
```

Sada znaš zašto postoji:

```php
$request->session()->regenerate();
```

Nije ritual.

To je zaštita oko promene:

```text
guest
→ authenticated
```

Framework samo skriva PHP session detalje.

## 29. Session security ne rešava password security

Ne mešaj slojeve.

Možeš imati savršeno:

```text
Secure
HttpOnly
SameSite
regeneration
```

ali ako password čuvaš u plaintext-u:

auth je i dalje katastrofalno loš

I obrnuto:

Savršeno hashiranje password-a ne rešava ukradeni authenticated session ID.

Dakle:

```text
password security
→ štiti credentials
```

```text
session security
→ štiti authenticated state
```

Oba su potrebna.

```text

↓
find user
↓

↓
account check
↓

↓

```

To je pravi session-based login lifecycle.
