# 10. Protected Routes and Middleware — Part 1

## Module 10 — Authentication bez frameworka

### Lekcija 10/15 — Protected routes i middleware mental model

Do sada možemo da pitamo:

```php
$auth->check();
$auth->guest();
$auth->user();
```

Ali ako svaki controller ručno proverava authentication:

```php
if ($auth->guest()) {
    header('Location: /login');
    exit;
}
```

ubrzo ćemo isti kod imati na deset mesta.

Tu ulazi **middleware**.

Najvažniji mentalni model:

```text
Request
↓
Middleware
↓
Controller
```

Middleware odlučuje:

> Da li request uopšte sme da stigne do sledećeg sloja?

---

## 1. Šta znači protected route?

Protected route je ruta kojoj ne može pristupiti guest.

Na primer:

```text
/dashboard
/profile
/bookings
/account
```

Želimo:

```text
authenticated user
→ dozvoli request

guest
→ redirect /login
```

Na primer:

```text
GET /dashboard
↓
auth middleware
↓
authenticated?
├── DA → DashboardController
└── NE → redirect /login
```

---

## 2. Problem ručnih provera u Controller-u

Bez middleware-a:

```php
final class DashboardController
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function index(): void
    {
        if ($this->auth->guest()) {
            header('Location: /login');
            exit;
        }

        // dashboard
    }
}
```

Zatim isto radi:

```text
ProfileController
BookingController
AccountController
SupplierController
```

Dobijamo:

```text
isti kod
isti redirect
ista auth provera
na više mesta
```

To je signal da postoji cross-cutting concern koji treba izdvojiti.

---

## 3. Šta je middleware?

Middleware je sloj koji stoji između:

```text
HTTP request-a
```

i:

```text
controller/action-a
```

i može da odluči:

```text
nastavi dalje
ili
prekini request
```

Mentalno:

```text
Request
↓
Middleware
↓
Middleware
↓
Controller
↓
Response
```

Middleware može da radi:

```text
authentication
CSRF
rate limiting
logging
CORS
request transformation
```

Ali u ovom modulu fokusiramo se na authentication middleware.

---

## 4. Auth middleware

Želimo nešto konceptualno poput:

```php
final class AuthMiddleware
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function handle(callable $next): mixed
    {
        if ($this->auth->guest()) {
            // redirect /login
        }

        return $next();
    }
}
```

Mentalni flow:

```text
Request
↓
AuthMiddleware
↓
auth->guest() ?
├── true  → prekini
└── false → next()
             ↓
          Controller
```

---

## 5. Šta predstavlja `$next`?

`$next` predstavlja:

> Sledeći korak u request pipeline-u.

To može biti:

```text
sledeći middleware
```

ili, ako više nema middleware-a:

```text
controller
```

Na primer:

```php
return $next();
```

znači:

```text
"Moja provera je završena.
Pusti request dalje."
```

Ako middleware **ne pozove `$next`**, pipeline se tu završava.

---

## 6. Middleware kao lanac

Pretpostavimo ruta ima:

```text
AuthMiddleware
CsrfMiddleware
Controller
```

Flow:

```text
Request
↓
AuthMiddleware
↓
next()
↓
CsrfMiddleware
↓
next()
↓
Controller
```

Ako `AuthMiddleware` odbije request:

```text
Request
↓
AuthMiddleware
↓
redirect
```

`CsrfMiddleware` i Controller se uopšte ne izvršavaju.

Zato middleware pravi pipeline.

---

## 7. Protected route bez Laravel magije

U Laravelu si navikao na nešto poput:

```php
Route::get('/dashboard', ...)
    ->middleware('auth');
```

Ispod toga mentalno postoji:

```text
route matched
↓
auth middleware resolved
↓
current user checked
↓
controller allowed / blocked
```

Mi sada pravimo isti princip ručno.

---

## 8. Minimalni `AuthMiddleware`

Na primer:

```php
final class AuthMiddleware
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function handle(
        callable $next
    ): mixed {
        if ($this->auth->guest()) {
            header('Location: /login');
            exit;
        }

        return $next();
    }
}
```

Ovo je veoma jednostavno, ali već rešava glavni problem.

Controller više ne mora da zna:

```text
da li ruta zahteva login
```

To je rešeno pre njega.

---

## 9. Controller posle auth middleware-a

Sada controller može biti:

```php
final class DashboardController
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function index(): void
    {
        $user = $this->auth->user();

        // render dashboard
    }
}
```

Više nema:

```php
if ($this->auth->guest()) {
    ...
}
```

jer contract rute kaže:

> Ako je Controller pozvan, auth middleware je već pustio authenticated user-a dalje.

To znatno pojednostavljuje Controller kod.

## 10. Guest middleware

Postoji i suprotan problem.

Neke rute želimo samo za goste:

```text
/login
/register
```

Ako je user već authenticated, nema mnogo smisla da ponovo vidi login formu.

Zato možemo imati:

```text
GuestMiddleware
```

Flow:

```text
GET /login
↓
GuestMiddleware
↓
authenticated?
├── DA → redirect /dashboard
└── NE → LoginController
```

---

## 11. Minimalni `GuestMiddleware`

Na primer:

```php
final class GuestMiddleware
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function handle(
        callable $next
    ): mixed {
        if ($this->auth->check()) {
            header('Location: /dashboard');
            exit;
        }

        return $next();
    }
}
```

Dakle:

```text
AuthMiddleware
→ zahteva authenticated user-a

GuestMiddleware
→ zahteva unauthenticated user-a
```

---

## 12. `auth` i `guest` nisu authorization

Ovo je veoma važno.

`AuthMiddleware` proverava:

```text
da li user postoji i authenticated je
```

Ne proverava:

```text
da li je admin
da li je supplier
da li poseduje booking
da li sme refund
```

Dakle:

```text
auth middleware
→ authentication

role/policy middleware
→ authorization
```

Ne mešamo ih.

---

## 13. Primer: supplier ruta

Recimo BookYourHotel ima:

```text
/supplier/hotels
```

`AuthMiddleware` može da proveri:

```text
user logged in?
```

Ali to nije dovoljno.

Jer authenticated customer ne mora imati supplier pristup.

Mentalno:

```text
Request
↓
AuthMiddleware
↓
authenticated ✅
↓
SupplierAuthorization
↓
supplier? ✅
↓
Controller
```

Dakle authentication je prvi filter.

Authorization dolazi posle.

---

## 14. Middleware redosled je bitan

Pretpostavimo imamo:

```text
AuthMiddleware
AdminMiddleware
```

Logičan redosled:

```text
Request
↓
AuthMiddleware
↓
AdminMiddleware
↓
Controller
```

Zašto?

Jer `AdminMiddleware` treba da radi sa već utvrđenim current user-em.

Nema smisla prvo pitati:

```text
"Da li je admin?"
```

ako još ne znamo da li uopšte imamo authenticated user-a.

---

## 15. `401` vs `403`

Ovo je korisna HTTP razlika.

### `401 Unauthorized`

U praksi znači:

```text
authentication nedostaje ili nije validna
```

Drugim rečima:

> Ne znamo ko si / nisi authenticated.

### `403 Forbidden`

Znači:

```text
znamo ko si,
ali nemaš dozvolu
```

Mentalno:

```text
401
→ authentication problem

403
→ authorization problem
```

Naziv `401 Unauthorized` je malo istorijski nezgodan jer praktično govori o authentication-u.

---

## 16. Web aplikacija vs API response

Kod klasične web aplikacije guest koji otvori:

```text
/dashboard
```

često dobije:

```text
redirect /login
```

Kod JSON API-ja često ne želiš redirect.

Želiš:

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json
```

sa nečim poput:

```json
{
    "message": "Unauthenticated."
}
```

Dakle middleware behavior može zavisiti od application surface-a.

---

## 17. Middleware ne treba da prikazuje Login formu

`AuthMiddleware` ne treba da radi:

```php
include 'login-form.php';
```

Bolje:

```text
AuthMiddleware
→ odluči da request nije dozvoljen
→ redirect / response

LoginController
→ prikazuje login formu
```

Middleware treba da ostane fokusiran.

---

## 18. Redirect na originalnu stranicu

Dobar UX:

```text
user otvori:
/bookings/17

nije authenticated
↓
redirect /login
↓
login uspe
↓
vrati /bookings/17
```

Da bismo to uradili, možemo sačuvati intended URL:

```php
$this->session->put(
    'intended_url',
    '/bookings/17'
);
```

Posle login-a:

```text
intended URL postoji?
↓
DA → redirect tamo
NE → default dashboard
```

Laravel ima isti koncept kroz:

```php
redirect()->intended(...)
```

---

## 19. Intended URL mora biti kontrolisan

Ne želimo slepo:

```text
?redirect=https://evil.example
```

pa posle login-a:

```text
redirect na bilo koji user-provided URL
```

To može napraviti **open redirect** problem.

Zdrav model:

```text
intended destination
→ lokalna/internal ruta
→ validirana pre redirect-a
```

Detaljniji security deo ostaje za Module 12.

Bitno je da ne tretiramo redirect destination kao potpuno pouzdan input.

## 20. Kako Router može da zna koji middleware koristi?

Možemo zamisliti route definiciju:

```php
$router->get(
    '/dashboard',
    [DashboardController::class, 'index'],
    [AuthMiddleware::class]
);
```

Ili konceptualno:

```php
$router->middleware('auth')->get(
    '/dashboard',
    ...
);
```

Router treba da zna:

```text
ruta
controller
middleware lista
```

pa da napravi pipeline pre poziva controller-a.

---

## 21. Alias za middleware

Umesto da route svuda zna:

```php
AuthMiddleware::class
```

možemo imati registry:

```php
$middleware = [
    'auth' => AuthMiddleware::class,
    'guest' => GuestMiddleware::class,
];
```

Pa ruta:

```text
/dashboard → auth
/login     → guest
/register  → guest
```

To je veoma slično framework pristupu.

Alias je samo:

```text
kratko ime
→ konkretna middleware klasa
```

---

## 22. Middleware contract

Možemo napraviti interface:

```php
interface Middleware
{
    public function handle(
        callable $next
    ): mixed;
}
```

Onda:

```php
final class AuthMiddleware
    implements Middleware
{
    // ...
}
```

i:

```php
final class GuestMiddleware
    implements Middleware
{
    // ...
}
```

Router sada može sve middleware klase tretirati polimorfno.

To je lep spoj sa OOP modulom:

```text
Interface
↓
više implementacija
↓
Router ne zavisi od konkretne klase
```

---

## 23. Pipeline mental model

Ako imamo:

```text
Middleware A
Middleware B
Middleware C
Controller
```

pipeline možemo zamisliti kao:

```text
A(
    B(
        C(
            Controller
        )
    )
)
```

Svaki middleware dobija sledeći korak:

```php
$next();
```

i odlučuje:

```text
pozovi next
ili
vrati svoj response
```

To je middleware pattern u svojoj suštini.

---

## 24. Middleware može da prekine pipeline

Na primer:

```php
public function handle(
    callable $next
): mixed {
    if ($this->auth->guest()) {
        return new RedirectResponse('/login');
    }

    return $next();
}
```

Guest slučaj:

```text
Request
↓
AuthMiddleware
↓
RedirectResponse

STOP
```

Authenticated slučaj:

```text
Request
↓
AuthMiddleware
↓
next()
↓
Controller
```

Middleware zato nije samo "funkcija koja se izvrši pre Controller-a".

On kontroliše da li se nastavak pipeline-a uopšte izvršava.

---

## 25. Bolje Response objekat nego `header()` svuda

Za minimalistički PHP kod možemo koristiti:

```php
header('Location: /login');
exit;
```

Ali arhitektonski čistije je imati:

```php
return new RedirectResponse('/login');
```

ili:

```php
return Response::redirect('/login');
```

Zašto?

Jer:

```text
middleware
→ vraća response

controller
→ vraća response

router/kernel
→ šalje response
```

To daje jedinstven HTTP flow.

Ovo ćemo još bolje videti u MVC modulu.

---

## 26. Auth middleware koristi `AuthService`, ne Session direktno

Lošije:

```php
if (!isset($_SESSION['user_id'])) {
    // redirect
}
```

Zašto?

Jer middleware sada ponavlja auth logiku i zaobilazi:

```text
stale user handling
disabled user handling
current user resolution
```

Bolje:

```php
if ($this->auth->guest()) {
    // reject
}
```

Dakle:

```text
Middleware
→ pita AuthService

AuthService
→ zna kako authentication stvarno funkcioniše
```

To je encapsulation.

---

## 27. Kompletan request flow

Za protected route:

```text
GET /dashboard
↓
Router
↓
route matched
↓
AuthMiddleware
↓
AuthService::check()
↓
session user_id
↓
UserRepository::findById()
↓
User
↓
middleware calls next()
↓
DashboardController
↓
Response
```

Za guest-a:

```text
GET /dashboard
↓
Router
↓
AuthMiddleware
↓
AuthService::check() = false
↓
redirect /login

Controller se NE izvršava
```

Za login route:

```text
GET /login
↓
GuestMiddleware
↓
AuthService::guest()
├── true  → LoginController
└── false → redirect /dashboard
```

To je kompletan authentication middleware mental model.

---

## 28. Laravel paralela

Laravel:

```php
Route::middleware('auth')->group(function () {
    Route::get('/dashboard', ...);
});
```

mentalno radi:

```text
Route matched
↓
auth middleware
↓
guard/current user resolution
↓
authenticated?
├── DA → controller
└── NE → unauthenticated response
```

A:

```php
Route::middleware('guest')->group(function () {
    Route::get('/login', ...);
});
```

radi suprotnu proveru.

Sada znaš šta stoji iza tih vrlo kratkih framework deklaracija.

## Najvažnije za zapamtiti

Protected route:

```text
route kojoj je potreban authenticated user
```

Middleware:

```text
Request
↓
Middleware
↓
Controller
```

i može:

```text
pozvati next()
ili
prekinuti pipeline
```

`AuthMiddleware`:

```text
guest
→ redirect / login response

authenticated
→ next()
```

`GuestMiddleware`:

```text
authenticated
→ redirect / dashboard

guest
→ next()
```

Najvažnija granica:

```text
auth middleware
→ authentication

authorization/policy
→ permissions
```

HTTP mental model:

```text
401
→ nisi authenticated

403
→ authenticated si,
  ali nemaš dozvolu
```

Controller više ne treba da ponavlja:

```php
if ($auth->guest()) {
    ...
}
```

jer protected-route contract rešava middleware.

Arhitektonski:

```text
Router
↓
Middleware pipeline
↓
AuthService
↓
Controller
↓
Response
```

Middleware treba da koristi:

```php
$auth->check();
$auth->guest();
```

a ne direktno:

```php
$_SESSION
```

jer je AuthService centralni source authentication log

I suština $next obrasca:

middleware dozvoljava request
↓
next()

middleware odbija request
↓
ne poziva next()
