# 14. Email Verification and Account State — Part 1

## Module 10 — Authentication bez frameworka

### Lekcija 14/15 — Email verification i account state

Do sada smo uglavnom razmišljali:

```text
credentials valid?
↓
DA
↓
login
```

Ali realna aplikacija često ima dodatna pravila.

User može:

```text
postojati u bazi
imati tačan password
ali ipak ne sme da koristi sve funkcije sistema
```

Na primer:

```text
email nije potvrđen
account je disabled
account je suspended
```

Najvažniji mentalni model:

```text
Identity
→ ko je user

Credential verification
→ da li je dokazao identitet

Account state
→ da li account trenutno sme da se koristi

Authorization
→ šta sme da radi
```

To su različite stvari.

---

## 1. Validan password nije ceo login policy

Pretpostavimo:

```text
email postoji ✅
password_verify() ✅
```

To znači:

```text
credentials su validni
```

Ali možda:

```text
email_verified_at = NULL
```

ili:

```text
status = disabled
```

Dakle:

```text
valid credentials
≠ automatski pun pristup aplikaciji
```

Authentication flow može imati dodatnu eligibility proveru.

---

## 2. Email verification nije isto što i authentication

Email verification odgovara na pitanje:

> Da li korisnik kontroliše email adresu koju je naveo?

Password authentication odgovara:

> Da li korisnik poseduje validne login credentials?

To nisu ista pitanja.

User može:

```text
znati password
ali nikada nije otvorio verification email
```

Dakle:

```text
password verified
→ identity credential valid

email verified
→ ownership/control email kanala potvrđen
```

---

## 3. Zašto uopšte verifikujemo email?

Email često koristimo za:

```text
password reset
security notifications
booking confirmations
account recovery
important communication
```

Ako email nije stvaran ili nije pod kontrolom user-a:

```text
password reset flow može otići pogrešnoj osobi
notifications ne stižu
user može registrovati tuđu adresu
```

Zato verification daje dodatnu sigurnost da je email stvarno dostupan tom korisniku.

---

## 4. `email_verified_at`

Vrlo praktičan model:

```sql
email_verified_at DATETIME NULL
```

Ako je:

```text
NULL
```

email nije verifikovan.

Ako ima datum:

```text
2026-10-27 15:30:00
```

email je potvrđen.

Zašto timestamp umesto običnog boolean-a?

Jer dobijamo i informaciju:

```text
da li je verified?
+
kada je verified?
```

Dakle:

```text
NULL
→ unverified

DATETIME
→ verified
```

---

## 5. `isEmailVerified()`

User objekat može imati:

```php
public function isEmailVerified(): bool
{
    return $this->emailVerifiedAt !== null;
}
```

Mentalno:

```text
User
→ poznaje svoj persisted state
```

Auth/service sloj onda može pitati:

```php
if (!$user->isEmailVerified()) {
    // application policy
}
```

Ne mora svaki deo aplikacije direktno proveravati:

```php
$user->emailVerifiedAt() !== null
```

Metoda čini nameru jasnijom.

---

## 6. Kada šaljemo verification email?

Najčešće:

```text
registration
↓
User created
↓
generate verification token
↓
send email
```

Dakle registration može biti uspešan:

```text
account postoji
```

ali account je:

```text
unverified
```

dok user ne klikne verification link.

To je važna razlika:

```text
registration completed
≠ email verification completed
```

---

## 7. Verification token mora biti random

Kao i kod Password Reset-a:

```php
$token = bin2hex(
    random_bytes(32)
);
```

Ne želimo predvidiv token kao:

```text
user_id
email
timestamp
md5(user_id)
```

jer verification link treba da dokaže possession secreta koji je poslat na email.

Mentalno:

```text
random high-entropy token
↓
email
↓
user presents token
↓
server verifies
```

---

## 8. Token hash u bazi

I ovde možemo čuvati:

```php
$tokenHash = hash(
    'sha256',
    $token
);
```

Browser/email dobija:

```text
plaintext token
```

Database čuva:

```text
token hash
```

Dakle:

```text
email verification token
→ random credential
→ isti verifier princip kao reset token
```

Ne moramo čuvati plaintext verification token u bazi.

---

## 9. Minimalna verification tabela

Na primer:

```sql
CREATE TABLE email_verification_tokens (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    token_hash CHAR(64) NOT NULL UNIQUE,
    expires_at DATETIME NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);
```

Ovde imamo:

```text
user_id
→ kome token pripada

token_hash
→ verifier

expires_at
→ validity window
```

Sličnost sa password reset tokenima je namerna.

---

## 10. Verification link

Email može sadržati:

```text
https://example.com/verify-email?token=PLAINTEXT_TOKEN
```

Kada user klikne:

```text
GET /verify-email?token=...
↓
server hashira token
↓
pronalazi verification record
↓
proverava expiry
↓
mark email verified
↓
invalidate token
```

Verification je jedna od retkih situacija gde GET često dovodi do state change-a u praksi.

Arhitektonski čistiji sistem može koristiti intermediate page + POST confirmation, ali mnogi sistemi direktno verifikuju preko signed/tokenized GET linka.

Najvažnije je da token bude:

```text
jak
privremen
single-use
```

---

## 11. Verification token treba da istekne

Ne želimo:

```text
verification token važi zauvek
```

Server treba da proveri:

```text
expires_at > now
```

Ako je istekao:

```text
verification rejected
```

User može dobiti opciju:

```text
Resend verification email
```

što kreira novi token.

---

## 12. Verification token treba da bude single-use

Kada verification uspe:

```text
mark email verified
↓
DELETE verification token
```

Nema potrebe da isti token nastavi da važi.

Na primer:

```text
valid token
↓
email_verified_at = NOW()
↓
token invalidated
```

Ako user ponovo klikne isti link:

```text
token više nije validan
```

Account je već verified i nema potrebe za ponovnom security operacijom.

---

## 13. Resend verification

Ako token istekne ili email nikada nije stigao, user može tražiti novi.

Flow:

```text
POST /email/verification-notification
↓
user authenticated?
↓
email already verified?
├── DA → ništa ne treba
└── NE
    ↓
    invalidate old token
    ↓
    create new token
    ↓
    send email
```

Ovaj endpoint treba rate limiting jer bi inače mogao biti korišćen za spam.

---

## 14. Šta ako user promeni email?

Ako verified user promeni:

```text
old@example.com
↓
new@example.com
```

ne treba automatski pretpostaviti da je novi email verified.

Tipičan flow:

```text
change email
↓
email_verified_at = NULL
↓
send new verification email
↓
user verifies new address
```

Jer verification pripada konkretnoj email adresi.

Dakle:

```text
verified user
≠ svaki budući email automatski verified
```

---

## 15. Account status

Pored verification state-a, možemo imati:

```text
active
disabled
suspended
```

Na primer:

```sql
status VARCHAR(20) NOT NULL DEFAULT 'active'
```

I User:

```php
public function isActive(): bool
{
    return $this->status === 'active';
}
```

Account status predstavlja:

```text
da li account trenutno sme normalno da se koristi
```

To je odvojeno od password-a i email verification-a.

---

## 16. `active`, `disabled`, `suspended`

Primer semantike:

```text
active
→ normalan account

disabled
→ account administrativno ugašen

suspended
→ privremeno blokiran
```

Tačna značenja zavise od aplikacije.

Bitno je da status bude:

```text
business/application state
```

a ne samo proizvoljan string bez definisanog ponašanja.

---

## 17. Enum za account status

Umesto magic stringova možemo koristiti enum:

```php
enum AccountStatus: string
{
    case Active = 'active';
    case Disabled = 'disabled';
    case Suspended = 'suspended';
}
```

User:

```php
public function isActive(): bool
{
    return $this->status === AccountStatus::Active;
}
```

To je lep nastavak OOP lekcije o enum-ima.

Dobijamo:

```text
closed set of valid states
+
type safety
+
jasniji domain model
```

---

## 18. Credentials valid, ali status nije active

Login flow:

```text
find user
↓
password_verify() ✅
↓
status?
```

Ako je:

```text
disabled
```

onda:

```text
login rejected
```

Dakle:

```text
password correctness
→ credential validity

account status
→ login eligibility
```

To su dve različite provere.

---

## 19. Gde proveravati account status?

Najprirodnije u authentication use case-u.

Na primer:

```php
if (!$user->isActive()) {
    return false;
}
```

pre:

```php
$this->login($user);
```

Ali status treba proveravati i kod current-user resolution-a.

Zašto?

Jer user može biti disabled dok je već loginovan.

Dakle:

```text
login time
→ proveri status

future requests
→ current user resolver ponovo vidi current status
```

---

## 20. Disabled user sa postojećom session

Scenario:

```text
10:00
user loginovan

10:30
admin ga disabled

10:31
user šalje novi request
```

Ako session samo kaže:

```text
user_id = 17
```

a AuthService učita fresh User-a:

```text
status = disabled
```

može odmah:

```text
invalidate auth state
→ guest
```

To je još jedan razlog zašto nismo čuvali stale:

```text
role
status
ceo User
```

u session-u.

## 21. Da li unverified user sme da se loginuje?

Ovo je application policy odluka.

Imamo dve česte strategije.

### Strategija A — nema login-a dok email nije verified

```text
credentials valid
↓
email unverified
↓
login rejected
```

### Strategija B — login dozvoljen, ali pristup ograničen

```text
credentials valid
↓
authenticated
↓
email unverified
↓
samo ograničene rute dostupne
```

Drugi model je često bolji UX jer user može da uđe i vidi:

```text
Please verify your email
Resend verification
Logout
```

Dakle verification nije nužno isto što i authentication eligibility.

---

## 22. Verified middleware

Ako dozvolimo login pre verification-a, možemo imati poseban middleware:

```text
AuthMiddleware
↓
VerifiedMiddleware
↓
Controller
```

Na primer:

```php
final class VerifiedMiddleware
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function handle(
        callable $next
    ): mixed {
        $user = $this->auth->user();

        if ($user === null) {
            // unauthenticated
        }

        if (!$user->isEmailVerified()) {
            // redirect verification notice
        }

        return $next();
    }
}
```

Sada imamo jasne nivoe:

```text
auth
→ user mora biti logged in

verified
→ user mora imati verified email
```

---

## 23. Authenticated ≠ Verified ≠ Authorized

Ovo je veoma važna trostruka razlika.

```text
Authenticated
→ Znamo ko si

Verified
→ Potvrdio si email/recovery kanal

Authorized
→ Imaš pravo na ovu akciju
```

Primer:

```text
User #17
authenticated ✅
email verified ✅
admin permission ❌
```

I dalje ne sme pristupiti admin panelu.

---

## 24. Account eligibility kao poseban koncept

Možemo mentalno imati:

```text
credential valid?
↓
account eligible?
↓
authenticated state
```

Eligibility može uključivati:

```text
status active?
email verification required?
account locked?
tenant active?
```

Ne mora sve biti hardcoded u `password_verify()` flow.

To je zaseban application policy sloj.

---

## 25. VerificationService

Da AuthService ne naraste previše, email verification možemo izdvojiti:

```php
final class EmailVerificationService
{
    public function __construct(
        private UserRepository $users,
        private VerificationTokenRepository $tokens
    ) {}
}
```

Use case metode mogu biti:

```php
issue(User $user): void;

verify(string $token): bool;

resend(User $user): void;
```

Odgovornosti:

```text
EmailVerificationService
→ verification orchestration

VerificationTokenRepository
→ token persistence

UserRepository
→ mark verified
```

AuthService ostaje fokusiran na authentication.
