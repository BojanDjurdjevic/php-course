# Lekcija 3/15 — Password hashing: password_hash(), password_verify(), password_needs_rehash()

Ovo je jedna od najvažnijih lekcija celog auth modula.

Najkraće:
Password se ne čuva, ne enkriptuje i ne poredi direktno. Čuva se samo njegov hash, a pri login-u proveravamo da li uneti password odgovara tom hash-u.

Mentalno:
REGISTRATION

plain password
↓
password_hash()
↓
password hash
↓
database

A login:
plain password iz login forme
+
hash iz baze
↓
password_verify()
↓
true / false

1. Hashing nije encryption
Ovo moraš jasno da razlikuješ.

Encryption je zamišljen kao:
plaintext
↓ encrypt(key)
ciphertext
↓ decrypt(key)
plaintext

Dakle postoji način da dobiješ original nazad ako imaš odgovarajući key.

Password hashing:
password
↓ hash
hash value

nema operaciju:
hash
↓
vrati originalni password

To je jednosmerna transformacija.

Zato za password želimo:
hashing ✅
encryption ❌
plaintext ❌

Ako aplikacija može da korisniku kaže:
Tvoj password je secret123

onda ga negde čuvaš u obliku koji može da se vrati i to je loš auth dizajn.
2. Registration
Pretpostavimo korisnik pošalje:
$password = 'Secret123!';

Ne radimo:
$userRepository->create(
    $email,
    $password
);

nego:
$passwordHash = password_hash(
    $password,
    PASSWORD_DEFAULT
);

pa u bazu ide:
$userRepository->create(
    $email,
    $passwordHash
);

Dakle:
request
↓
plain password
↓
hash
↓
database

Plain password treba da postoji samo onoliko dugo koliko je potrebno da završiš taj request.
3. password_hash()
Osnovno:
$hash = password_hash(
    $password,
    PASSWORD_DEFAULT
);

PASSWORD_DEFAULT znači:
Koristi PHP-ov preporučeni default password hashing algoritam.

To je često najbolji default izbor jer ne vezuješ aplikaciju za jedan algoritam zauvek.

Ne treba da hardcode-uješ mentalitet:
"Ja ću zauvek koristiti baš ovaj algoritam."

PHP može kroz buduće verzije promeniti šta smatra dobrim default-om.

Zato smo u prethodnoj lekciji rekli:
password_hash VARCHAR(255)

da imamo dovoljno prostora ako se format hash-a promeni.
4. Hash nije isti svaki put
Ovo je veoma važno.

Ako uradiš:
$hash1 = password_hash(
    'Secret123!',
    PASSWORD_DEFAULT
);

$hash2 = password_hash(
    'Secret123!',
    PASSWORD_DEFAULT
);

vrlo verovatno:
$hash1 !== $hash2;

iako je password isti.

Zašto?

Zato što password hashing koristi salt.

Mentalno:
isti password
+
različit random salt
↓
različit hash

To je namerno i poželjno.
5. Šta je salt?
Salt je random vrednost koja se kombinuje sa password-om pre/dok se hashira.

Bez salt-a:
password123
→ uvek isti hash

što bi omogućilo mnogo lakše prepoznavanje korisnika sa istim password-om i efikasnije korišćenje unapred izračunatih tabela.

Sa salt-om:
User A:
password123 + salt A
→ hash A

User B:
password123 + salt B
→ hash B

Isti password, različiti hash-evi.

Najvažnije:
Kada koristiš PHP password_hash(), ne praviš salt ručno.

PHP ga generiše i čuva potrebne informacije unutar samog hash string-a.

Ne radi:
$salt = 'moja_super_tajna_salt';
$password .= $salt;

To nije potrebno i lako možeš da pogrešiš.
6. Hash sadrži metadata
Password hash koji dobiješ nije samo neka slučajna gomila karaktera.

On u sebi tipično nosi informacije potrebne da PHP kasnije proveri password, kao što su:
algoritam
parametri/cost
salt
hash rezultat

Zato ti pri login-u ne treba posebna kolona:
password_salt

ako koristiš PHP password API na standardan način.

Dovoljno je:
password_hash

7. Login — password_verify()
Recimo iz baze dobiješ:
$user->passwordHash();

a iz forme:
$password;

Provera:
$isValid = password_verify(
    $password,
    $user->passwordHash()
);

Ako:
$isValid === true

password odgovara hash-u.

Ako:
false

ne odgovara.

Ne radi:
password_hash($password, PASSWORD_DEFAULT)
    === $user->passwordHash();

Zašto?

Jer će novi hash koristiti novi salt i gotovo sigurno biti drugačiji string.

Dakle:
REGISTER
→ password_hash()

LOGIN
→ password_verify()

To je osnovni par koji moraš znati napamet.
8. Tipičan login flow
$user = $users->findByEmail($email);

if ($user === null) {
    // login failed
}

if (!password_verify(
    $password,
    $user->passwordHash()
)) {
    // login failed
}

// credentials valid

Tek posle uspešne verifikacije ide:
$_SESSION['user_id'] = $user->id();

Dakle:
find user
↓
verify password
↓
tek onda establish auth state

Ne obrnuto.
9. Zašto se hash ne poredi sa ===?
Zbog salt-a.

Ako imaš:
$password = 'Secret123!';

i napraviš novi hash:
$newHash = password_hash(
    $password,
    PASSWORD_DEFAULT
);

taj hash neće biti identičan stored hash-u.

Zato:
$newHash === $storedHash

nije validna password provera.

Ispravno:
password_verify(
    $password,
    $storedHash
);

10. password_needs_rehash()
Ovo je elegantan deo PHP password API-ja.

Zamisli:
- korisnik se registrovao pre tri godine
- password hash je napravljen sa starijim parametrima
- danas želiš jači hashing setup
Ne moraš:
Svima odmah resetujte password.

Kada se user uspešno loginuje, već imaš njegov plain password u tom request-u.

Tada možeš proveriti:
if (password_needs_rehash(
    $user->passwordHash(),
    PASSWORD_DEFAULT
)) {
    $newHash = password_hash(
        $password,
        PASSWORD_DEFAULT
    );

    // update hash u bazi
}

Mentalno:
user login
↓
password_verify() ✅
↓
da li hash koristi zastarele parametre?
↓
password_needs_rehash()
↓
ako da:
napravi novi hash
↓
sačuvaj novi hash

To omogućava postepeni upgrade hash-eva bez forsiranja svih korisnika odjednom.
11. Rehash samo posle uspešnog verify-a
Nikada:
password_needs_rehash
↓
rehash user input

pre nego što znaš da je password validan.

Prvo:
password_verify(...)

tek ako je:
true

onda:
password_needs_rehash(...)

jer tek tada znaš da plain password pripada tom korisniku.
12. Primer login metode
Recimo:
public function login(
    string $email,
    string $password
): bool {
    $user = $this->users->findByEmail($email);

    if ($user === null) {
        return false;
    }

    if (!password_verify(
        $password,
        $user->passwordHash()
    )) {
        return false;
    }

    if (password_needs_rehash(
        $user->passwordHash(),
        PASSWORD_DEFAULT
    )) {
        $newHash = password_hash(
            $password,
            PASSWORD_DEFAULT
        );

        $this->users->updatePasswordHash(
            $user->id(),
            $newHash
        );
    }

    $_SESSION['user_id'] = $user->id();

    return true;
}

Još ćemo kasnije ovo arhitektonski popraviti i odvojiti session handling, ali kao mentalni flow je veoma dobar.
13. Hash treba da bude spor
Ovo zvuči kontraintuitivno.

Kod većine stvari želiš:
brže = bolje

Kod password hash-a želiš da bude:
dovoljno spor da je legitimnom login-u prihvatljivo,
ali napadaču skup za milione pokušaja.

Ako je hashing ekstremno brz, attacker može probati ogroman broj password kandidata u kratkom vremenu.

Zato password hashing algoritmi imaju work factor / cost.

Dakle:
password hashing
≠ običan brz hash

14. Zašto ne SHA-256?
Početnik često pomisli:
hash('sha256', $password);

Ali general-purpose hash funkcije poput SHA-256 su dizajnirane da budu veoma brze.

To je dobro za:
checksums
integrity
fingerprints

ali loše za password storage jer napadač takođe može da ih računa veoma brzo.

Zato koristi:
password_hash()

a ne ručno:
md5()
sha1()
hash('sha256', ...)

za password storage.
15. Zašto MD5/SHA1 nisu prihvatljivi za passwords
Dva problema:
MD5 / SHA1
→ stari/problematični algoritmi
→ veoma brzi

Čak ni:
hash('sha256', $password);

nije dovoljno samo zato što je SHA-256 kriptografski hash.

Password hashing zahteva algoritam dizajniran baš za passwords i visok computational cost.

Zato:
password_hash()

postoji.
16. PASSWORD_DEFAULT vs eksplicitni algoritam
Možeš eksplicitno birati podržane password algoritme, ali za većinu application code-a:
PASSWORD_DEFAULT

je odličan izbor.

Prednost:
PHP bira preporučeni default

a ti možeš koristiti:
password_needs_rehash()

kada se default/parametri kasnije promene.

Ako imaš specifične infrastrukturne zahteve, možeš birati konkretan algoritam i options, ali to nije potrebno za osnovni auth sistem.
17. Cost/options
Password hashing algoritmi mogu imati tuning parametre.

Na primer konceptualno:
password_hash(
    $password,
    PASSWORD_DEFAULT,
    [
        // algorithm-specific options
    ]
);

Veći cost može značiti:
teže attackeru ✅
sporiji login/register ⚠️
veći CPU/memory cost ⚠️

Zato:
Najveći mogući broj nije automatski najbolji.

Treba balansirati security i infrastrukturu.

Za naš kurs ćemo uglavnom koristiti:
password_hash(
    $password,
    PASSWORD_DEFAULT
);

bez ručnog fine-tuning-a.
18. Password validation i hashing nisu ista stvar
Pre hashiranja možda imaš registration validation:
required
min length
max length
confirmation

To je:
password policy / validation

A:
password_hash()

je:
secure storage transformation

Dakle:
validation
≠ hashing

Možeš savršeno hashirati katastrofalno slab password:
123

Hashing ga bezbedno skladišti, ali password policy je i dalje loš.
19. Sanitization password-a — veoma oprezno
Password obično ne želiš da "čistiš" na način koji menja sadržaj.

Na primer:
$password = trim($password);

može biti problematično ako korisnik namerno ima space kao deo password-a.

Još gore:
htmlspecialchars($password);

ili neke transformacije:
lowercase
strip tags
remove special chars

mogu promeniti credential.

Password treba tretirati kao opaque secret string.

Validiraš pravila, ali ga ne menjaš nasumično.

Ovo je važna razlika u odnosu na neke druge input-e.
20. Password confirmation nije password security mehanizam
Kod registration-a možeš imati:
password
password_confirmation

i proveriti:
$password === $confirmation

To samo sprečava korisnika da napravi typo pri registraciji.

Ne povećava hashing security.

Nakon toga:
password_hash($password, ...)

i confirmation se nigde ne čuva.
21. Šta ako hash leak-uje?
Ako baza procure, attacker može dobiti:
email
password_hash

Hash nije isto što i password, ali to ne znači:
Nema nikakvog rizika.

Napadač može offline pokušavati kandidat passwords i koristiti password verification algoritam protiv hash-a.

Zato želimo:
jak password
+
dobar password hashing algoritam
+
odgovarajući work factor
+
unique salt

Hashing smanjuje štetu, ne čini password matematički nemogućim za crack.
22. Zašto je password reuse problem
Ako korisnik koristi isti password na:
tvoj sajt
email
banku
drugi servis

i negde drugde password procure, attacker može probati te credentials kod tebe.

To je credential stuffing.

Tvoj password_hash() ne rešava činjenicu da korisnik ponavlja password drugde.

Zato auth security nije samo:
hashiraj password i gotovo

Kasniji security modul će proširiti sliku.
23. Greške pri login-u
Ako email ne postoji:
Invalid email

a ako password nije dobar:
Wrong password

time potencijalno otkrivaš:
da li account postoji

Često se koristi generička poruka:
Invalid credentials.

za oba slučaja.

To je više security/usability tema i vratićemo joj se kod login flow-a.

Ali važno:
interno
→ znaš razlog

prema korisniku
→ ne moraš otkrivati detalj

24. Password hash ne treba logovati
Nemoj logovati:
plain password ❌
password hash ❌ ako nije neophodno

Plain password posebno nikada ne treba završiti u:
logs
exception traces
debug dumps
analytics

Ako tokom development-a uradiš:
var_dump($_POST);

a forma ima password — upravo si ga možda izbacio u debug output.

Dakle password je secret kroz ceo lifecycle.
25. Laravel paralela
Laravel ti daje helper/facade sloj oko iste ideje.

Na primer mentalno:
Hash::make($password)
→ secure hash

Hash::check($password, $hash)
→ verify

Ali ispod je ista fundamentalna ideja koju sada radiš u čistom PHP-u:
registration
→ hash

→ verify

algorithm/cost evolution
→ rehash

Framework ne menja kriptografsku osnovu.

↓

To je kompletan mentalni model.
Najvažnije za zapamtiti
Osnovni par:
password_hash(
    $password,
    PASSWORD_DEFAULT
);

za registration/storage.
password_verify(
    $password,
    $storedHash
);

za login verification.

Nikada:
plaintext password u bazi ❌
reversible encryption za password ❌
md5/sha1/sha256 ručno za password storage ❌
nov hash === stored hash ❌
manual salt uz password_hash() ❌

Mentalno:
HASHING
→ one-way

ENCRYPTION
→ reversible sa key-em

Salt:
isti password
→ različiti hash-evi

PHP password API
→ salt rešava automatski

Rehash:
password_verify() ✅
↓
password_needs_rehash()
↓
password_hash() ponovo
↓
update stored hash

REGISTER

→ hash
→ database
