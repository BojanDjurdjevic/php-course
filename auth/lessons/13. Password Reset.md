# 13. Password Reset — Part 1

## Module 10 — Authentication bez frameworka

### Lekcija 13/15 — Password reset flow

Password reset je poseban authentication-related use case.

Najvažniji mentalni model:

> Ako user zaboravi password, ne vraćamo mu stari password. Dajemo mu vremenski ograničenu mogućnost da postavi **novi password**.

Flow:

```text
forgot password request
↓
generate random reset token
↓
store token verifier/hash
↓
send reset link
↓
user presents token
↓
verify token + expiry
↓
accept new password
↓
hash new password
↓
update user
↓
invalidate reset token
```

---

## 1. Zašto ne možemo poslati stari password?

Ako je password sistem pravilno napravljen, baza čuva:

```text
password_hash
```

a ne:

```text
plain password
```

Dakle aplikacija ne zna:

```text
"Koji je korisnikov originalni password?"
```

i to je dobro.

Ne želimo flow:

```text
Forgot password
↓
email:
"Tvoj password je Secret123"
```

Ako to možemo da uradimo, password storage je već loše dizajniran.

Ispravan model:

```text
forgot password
→ reset password
```

ne:

```text
forgot password
→ recover old password
```

---

## 2. Password reset je dokaz kontrole nad recovery kanalom

Najčešći recovery kanal je email.

User kaže:

```text
Želim reset za:
bojan@example.com
```

Server generiše secret token i šalje link na taj email.

Time se ne dokazuje stari password.

Dokazuje se:

> Osoba koja koristi reset link trenutno kontroliše recovery email account.

Zato je security email naloga veoma važan deo ukupne account security priče.

---

## 3. Forgot Password request

Tipičan endpoint:

```text
POST /forgot-password
```

Input:

```text
email
```

Flow:

```text
validate email format
↓
normalize email
↓
find user
↓
ako postoji:
    generate reset token
    persist token hash
    send email
↓
return generic response
```

Važno:

```text
POST
```

jer request može dovesti do server-side promene:

```text
kreiranje reset tokena
slanje email-a
```

---

## 4. Ne otkrivaj da li email postoji

Loš response:

```text
No account exists with this email.
```

u jednom slučaju, a:

```text
Reset email sent.
```

u drugom.

Time attacker može proveravati:

```text
ko ima account na našem sistemu?
```

Bolji outward response:

```text
If an account exists for this email,
we have sent password reset instructions.
```

Dakle:

```text
user exists
ili
user does not exist
↓
isti javni response
```

To smanjuje account enumeration.

---

## 5. Interno ipak razlikujemo slučajeve

Externally možemo vratiti istu poruku.

Interno:

```text
user found
→ create token

user missing
→ ne kreiraj token
```

Dakle:

```text
public behavior
→ isti

internal behavior
→ različit
```

Nema smisla kreirati token za nepostojećeg user-a.

Ali nema potrebe ni otkriti client-u šta se desilo.

---

## 6. Reset token mora biti random secret

Koristimo isti osnovni princip kao kod Remember Me tokena:

```php
$token = bin2hex(
    random_bytes(32)
);
```

Ne koristimo:

```php
rand();
mt_rand();
uniqid();
```

jer reset token mora biti praktično nemoguće pogoditi.

Mentalno:

```text
random_bytes()
↓
high-entropy secret
↓
password reset credential
```

Ako attacker poseduje validan reset token, može potencijalno promeniti password user-a.

Zato je token veoma osetljiv.

---

## 7. Reset token je privremeni credential

Reset token treba tretirati slično kao:

```text
password
session ID
remember-me validator
```

jer possession tokena daje security-sensitive mogućnost.

Konkretno:

```text
reset token
→ dozvoljava postavljanje novog password-a
```

Zato:

```text
ne loguj token
ne čuvaj plaintext u DB
ograniči lifetime
učini ga single-use
```

---

## 8. Ne čuvamo reset token plaintext u bazi

Lošije:

```text
password_reset_tokens

user_id = 17
token = verySecretToken
```

Ako baza procuri, attacker odmah dobija validne reset tokene.

Bolje:

```text
browser/email
→ plaintext token

database
→ token hash
```

Na primer:

```php
$tokenHash = hash(
    'sha256',
    $token
);
```

U bazu ide:

```text
token_hash
```

a plaintext token ide samo u reset link.

---

## 9. Zašto SHA-256 ovde ima smisla?

Ista logika kao kod Remember Me.

Password:

```text
human-generated
→ često mala/predvidiva entropija
→ treba password_hash()
```

Reset token:

```text
random_bytes(32)
→ velika random entropija
→ brz cryptographic hash je sasvim prikladan verifier
```

Zato:

```php
hash('sha256', $token);
```

može biti potpuno odgovarajuće za random reset token.

Ne treba koristiti `password_hash()` za svaki random token samo zato što je security-sensitive.

---

## 10. Minimalna password reset tabela

Na primer:

```sql
CREATE TABLE password_reset_tokens (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT UNSIGNED NOT NULL,
    token_hash CHAR(64) NOT NULL UNIQUE,
    expires_at DATETIME NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);
```

Mentalno:

```text
user_id
→ kome reset pripada

token_hash
→ verifier

expires_at
→ do kada token važi

created_at
→ kada je izdat
```

U jednostavnijem sistemu možeš vezati reset i za email, ali `user_id` daje jasnu relational vezu.

# 13. Password Reset — Part 2

## Module 10 — Authentication bez frameworka

### Lekcija 13/15 — Password reset flow

---

## 11. Expiry je obavezan

Reset token ne treba da važi:

```text
zauvek
```

nego relativno kratko.

Na primer:

```text
15 min
30 min
60 min
```

zavisno od application policy-ja.

Server proverava:

```text
expires_at > current time?
```

Ako ne:

```text
token expired
→ reset rejected
```

Poenta:

> Što token duže živi, duže postoji mogućnost njegove zloupotrebe ako procure.

---

## 12. Reset link

Email može sadržati link konceptualno:

```text
https://example.com/reset-password?token=PLAINTEXT_TOKEN
```

Ili:

```text
/reset-password/{token}
```

Plaintext token mora stići do browser-a jer ga server kasnije treba proveriti.

Ali treba paziti da token ne završi nepotrebno u:

```text
logs
analytics
third-party trackers
Referrer
screenshots
```

Zato reset stranice treba tretirati kao security-sensitive surface.

---

## 13. GET prikazuje formu, POST menja password

Dobar HTTP flow:

```text
GET /reset-password?token=...
→ prikaži formu
```

User unese:

```text
new_password
new_password_confirmation
```

Zatim:

```text
POST /reset-password
→ validiraj token
→ validiraj novi password
→ update password
```

Dakle:

```text
GET
→ prikaz

POST
→ state change
```

To čuva jasnu HTTP semantiku.

---

## 14. Reset formi i dalje treba token

POST request mora nekako nositi reset credential.

Na primer hidden field:

```html
<input
    type="hidden"
    name="token"
    value="..."
>
```

Ili drugi bezbedan način prenosa.

Server ne treba da kaže:

```text
"Pošto je browser otvorio reset stranicu,
verovatno je sve u redu."
```

Svaki state-changing reset request mora ponovo dokazati possession validnog tokena.

---

## 15. Verifikacija reset tokena

Server primi:

```php
$token;
```

Izračuna:

```php
$tokenHash = hash(
    'sha256',
    $token
);
```

Zatim:

```text
find reset record by token_hash
```

Ako ne postoji:

```text
invalid token
```

Ako postoji:

```text
proveri expiry
proveri da li je već iskorišćen / invalidiran
```

Tek onda možeš omogućiti promenu password-a.

---

## 16. Single-use token

Reset token treba da bude:

```text
one-time / single-use
```

Ako user jednom uspešno promeni password:

```text
token više ne sme da radi
```

Dakle:

```text
valid token
↓
password changed
↓
DELETE token
```

ili:

```text
mark used/revoked
```

Minimalno je sasvim dovoljno:

```sql
DELETE FROM password_reset_tokens
WHERE id = :id;
```

nakon uspešnog reset-a.

---

## 17. Zašto single-use?

Ako reset token ostane validan nakon uspešne promene password-a:

```text
attacker kasnije pronađe stari email/link
↓
ponovo koristi isti token
↓
ponovo menja password
```

To je ozbiljan problem.

Zato:

```text
successful reset
→ token invalidation odmah
```

mora biti deo istog use case-a.

---

## 18. Novi password prolazi registration-like validation

Kod password reset-a korisnik bira **novi password**.

Tu ponovo ima smisla primeniti password policy:

```text
required
minimalna dužina
confirmation
eventualna additional policy
```

Za razliku od login-a, ovde ne proveravamo postojeći password format.

Mi kreiramo novi credential.

Zato:

```text
login validation
≠ reset password validation
```

Reset je po tom pitanju sličniji registraciji.

---

## 19. Novi password hashiramo pre persistence

Nikada:

```sql
UPDATE users
SET password_hash = :plainPassword
```

nego:

```php
$newHash = password_hash(
    $newPassword,
    PASSWORD_DEFAULT
);
```

pa:

```php
$users->updatePasswordHash(
    $userId,
    $newHash
);
```

Flow:

```text
new plain password
↓
validation
↓
password_hash()
↓
database
```

Isti password storage princip kao kod registration-a.

---

## 20. Password reset treba da bude atomic use case

Imamo dve povezane promene:

```text
1. update user password hash
2. invalidate reset token
```

Ne želimo scenario:

```text
password update uspe
↓
token deletion fail
↓
token ostane validan
```

Zato ima smisla koristiti transaction:

```text
BEGIN
↓
UPDATE users password_hash
↓
DELETE reset token
↓
COMMIT
```

Ako nešto padne:

```text
ROLLBACK
```

Service je prirodno mesto za transaction boundary.

## 21. Šta sa postojećim Remember Me tokenima?

Ako user resetuje password, postoji dobra šansa da je reset pokrenut zato što:

```text
zaboravio password
ili
sumnja na compromise
```

Zato ima smisla razmotriti:

```text
password reset
→ revoke persistent Remember Me tokens
```

Jer attacker možda već poseduje jedan od njih.

Dakle reset može da invalidira:

```text
password reset token
+
remember-me tokens
```

To je dobra security politika.

---

## 22. Šta sa postojećim sessions?

Isto pitanje:

```text
da li sessions na drugim uređajima ostaju validne?
```

Za security-sensitive sistem često je razumno:

```text
password reset
→ invalidate other authenticated sessions
```

Ali kao što smo videli u Logout lekciji, klasični PHP session sistem ne daje automatski jednostavan:

```text
logout all devices
```

Za to treba dodatna session tracking/auth-version infrastruktura.

Dakle princip:

```text
reset password
→ razmotri globalnu auth invalidaciju
```

Implementacija zavisi od arhitekture.

---

## 23. Da li reset treba automatski da loginuje user-a?

Dve validne politike.

### Opcija A

```text
reset password
↓
redirect /login
↓
user loginuje sa novim password-om
```

### Opcija B

```text
reset password
↓
AuthService::login(User)
↓
user odmah authenticated
```

Oba pristupa postoje.

Security-sensitive aplikacija može preferirati novi login.

UX-oriented aplikacija može auto-loginovati nakon uspešno potvrđenog reset tokena.

To je product/security policy odluka.

---

## 24. Reset request može generisati više tokena

Šta ako user klikne:

```text
Forgot password
```

tri puta?

Možemo imati:

```text
token A
token B
token C
```

ili politiku:

```text
novi request
→ invalidate previous reset tokens
→ create only one active token
```

Druga opcija je često jednostavnija.

Na primer:

```text
DELETE existing tokens for user
↓
INSERT new token
```

Tada važi samo poslednji reset email.

---

## 25. Rate limiting reset endpoint-a

Attacker može pokušavati:

```text
POST /forgot-password
10000 puta
```

što može:

```text
spamovati korisnika emailovima
opterećivati mail servis
trošiti resurse
```

Zato password-reset request endpoint treba rate limiting.

Detaljno throttling ostaje u Security modulu, ali auth mentalni model treba da zna:

```text
forgot-password endpoint
→ abuse-sensitive
```

---

## 26. PasswordResetService

Da AuthService ne postane God Object, password reset možemo izdvojiti:

```php
final class PasswordResetService
{
    public function __construct(
        private UserRepository $users,
        private PasswordResetTokenRepository $tokens,
        private PDO $pdo
    ) {}
}
```

Može imati use case metode konceptualno:

```php
requestReset(string $email): void;

resetPassword(
    string $token,
    string $newPassword
): bool;
```

Odgovornosti:

```text
PasswordResetService
→ reset orchestration

PasswordResetTokenRepository
→ token persistence

UserRepository
→ user persistence
```

---

## 27. Kompletan Password Reset flow

### Request reset

```text
POST /forgot-password
↓
validate + normalize email
↓
find User
↓
public response ostaje generički
↓
ako User postoji:
    invalidate old reset tokens
    ↓
    generate random token
    ↓
    hash token
    ↓
    store hash + expiry
    ↓
    send plaintext token in reset link
```

### Perform reset

```text
POST /reset-password
↓
receive token + new password
↓
hash token
↓
find reset record
↓
check expiry
↓
validate new password
↓
BEGIN
↓
hash new password
↓
update User password hash
↓
invalidate reset token
↓
optionally revoke remember tokens
↓
COMMIT
↓
login or redirect to login
```

## 28. Laravel paralela

Laravel password reset sistemi abstrahuju isti mentalni model:

```text
password broker
↓
token generation/storage
↓
notification/email
↓
token verification
↓
password update
```

Kada framework radi veliki deo ovoga za tebe, suština se ne menja:

```text
random single-use token
+
expiry
+
new password hash
+
token invalidation
```

Framework samo sakriva infrastructure details.

## Najvažnije za zapamtiti

Password reset nije:

```text
vrati stari password ❌
```

nego:

```text
dozvoli bezbedno postavljanje novog password-a
```

Osnovni tok:

```text
forgot password
↓
random reset token
↓
store token hash
↓
send plaintext token
↓
verify token
↓
check expiry
↓
validate new password
↓
password_hash()
↓
update user
↓
invalidate token
```

Reset token:

```text
→ secret
→ temporary credential
→ high entropy
→ single-use
→ short-lived
```

Generacija:

```php
$token = bin2hex(
    random_bytes(32)
);
```

Persistence:

```php
$tokenHash = hash(
    'sha256',
    $token
);
```

Database čuva:

```text
token_hash
user_id
expires_at
```

Ne čuva:

```text
plaintext token
```

Public forgot-password response:

```text
user exists
ili
user missing
↓
ista generička poruka
```

Successful reset treba da bude atomic:

```text
BEGIN
↓
update password hash
↓
invalidate reset token
↓
COMMIT
```

Posle reset-a treba razmotriti invalidaciju:

```text
remember-me tokens
other sessions
```

posebno ako postoji mogućnost account compromise-a.

Arhitektonski:

```text
PasswordResetService
→ orchestration

PasswordResetTokenRepository
→ reset token persistence

UserRepository
→ user persistence
```

I centralna security razlika:

```text
Password
→ human-generated secret
→ password_hash()

Reset token
→ cryptographically random secret
→ SHA-256 verifier može biti dovoljan
```
