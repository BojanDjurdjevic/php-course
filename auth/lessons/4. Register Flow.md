# 4. Register Flow

## Module 10 — Authentication bez frameworka

### Lekcija 4/15 — Registration flow: input → validation → unique email → hash → persistence

Cilj ove lekcije je da sastavimo ceo registration use case od HTTP input-a do upisa korisnika u bazu.

Najvažniji mentalni model:

```text
Request
↓
validate input
↓
normalize email
↓
check business constraints
↓
hash password
↓
persist user
↓
return result / redirect
```

---

## 1. Registration nije samo INSERT

Početnički registration često izgleda ovako:

```sql
INSERT INTO users (email, password)
VALUES (...)
```

Ali pravi flow ima više odgovornosti:

```text
input validation
email normalization
unique email
password policy
password hashing
persistence
error handling
redirect/result
```

Dakle:

Registration je application use case, ne SQL query.

---

## 2. Šta dolazi iz request-a?

Recimo forma šalje:

```text
email
password
password_confirmation
```

Na primer:

```php
$email = $_POST['email'] ?? null;
$password = $_POST['password'] ?? null;
$confirmation = $_POST['password_confirmation'] ?? null;
```

Ali Controller ne bi trebalo odmah da radi:

```php
$users->create(...);
```

Prvo moramo potvrditi da su podaci validni.

---

## 3. Validation

Registration validation može uključivati:

```text
email
→ required
→ valid email format
```

```text
password
→ required
→ minimalna dužina
→ eventualna dodatna pravila
```

```text
password_confirmation
→ mora odgovarati password-u
```

Na primer:

```php
if (!is_string($email) || trim($email) === '') {
    $errors['email'] = 'Email is required.';
}

if (
    is_string($email)
    && filter_var($email, FILTER_VALIDATE_EMAIL) === false
) {
    $errors['email'] = 'Invalid email.';
}
```

Password:

```php
if (!is_string($password) || strlen($password) < 8) {
    $errors['password'] = 'Password must contain at least 8 characters.';
}
```

Confirmation:

```php
if ($password !== $confirmation) {
    $errors['password_confirmation'] = 'Passwords do not match.';
}
```

Za sada je bitan flow, ne savršena password policy.

---

## 4. Validation vs business rule

Ovo je važna razlika.

Ovo:

```text
email nije validnog formata
password je prekratak
confirmation se ne poklapa
```

je input validation.

Ali:

email već postoji u sistemu

nije samo format validation.

To je pravilo koje zavisi od application state-a / baze.

Mentalno:

```text
"Da li izgleda kao email?"
→ validation
```

```text
"Da li već postoji user sa tim email-om?"
→ business/persistence-backed rule
```

Laravel ti ovo često spoji u isti FormRequest kroz unique, ali ispod haube su različite vrste provere.

---

## 5. Email normalization pre lookup-a

Pre nego što proverimo da li email postoji, želimo konzistentnu vrednost:

```php
$email = mb_strtolower(trim($email));
```

Recimo input:

Bojan@Example.com

postaje:

bojan@example.com

Onda isti oblik koristimo za:

```text
unique lookup
persistence
login lookup
```

Ključno:

Registration i login moraju koristiti istu normalization politiku.

---

## 6. Provera postojećeg korisnika

Možemo:

```php
$existing = $users->findByEmail($email);

if ($existing !== null) {
    // registration rejected
}
```

Ili repository može imati:

```php
public function existsByEmail(string $email): bool;
```

Na primer:

```php
if ($users->existsByEmail($email)) {
    throw new RegistrationException(
        'An account with this email already exists.'
    );
}
```

Oba pristupa su validna.

---

## 7. Ali application check nije dovoljan

Seti se prethodne lekcije:

```sql
email VARCHAR(255) NOT NULL UNIQUE
```

Zašto nam trebaju oba?

Application check:

daje lep user-facing error

Database constraint:

garantuje invariant čak i kod race condition-a

Primer:

Request A:

email postoji? NE

Request B:

email postoji? NE

```text
A INSERT
B INSERT
```

Bez UNIQUE constraint-a možeš dobiti duplikat.

Sa constraint-om:

```text
jedan INSERT uspe
drugi fail
```

Dakle:

```text
application check
+
database constraint
```

je pravi model.

---

## 8. Password se hashira tek posle validacije

Ne moraš da radiš skupu hash operaciju ako je registration već nevalidan.

Dakle:

```text
validate
↓
business checks
↓
tek onda hash
```

Na primer:

```php
$passwordHash = password_hash(
    $password,
    PASSWORD_DEFAULT
);
```

U bazu ide:

password_hash

nikad plain password.

---

## 9. DTO za registration

Možemo imati:

```php
final readonly class RegisterUserData
{
    public function __construct(
        public string $email,
        public string $password
    ) {}
}
```

Ali tu postoji jedna zanimljiva odluka:

Da li DTO treba da nosi:

plain password

ili:

passwordHash

Zavisi od sloja.

Na primer:

```text
HTTP/Form layer
→ RegisterUserData(email, plain password)
```

```text
RegistrationService
→ hashira password
```

```text
Repository
→ dobija hash
```

To mi je čistiji model jer hashing pripada auth/application flow-u, ne Controller-u.

---

## 10. RegistrationService

Možemo imati:

```php
final class RegistrationService
{
    public function __construct(
        private UserRepository $users
    ) {}

    public function register(
        RegisterUserData $data
    ): User {
        // ...
    }
}
```

Flow unutra:

```text
normalize
↓
check existing user
↓
hash
↓
create
↓
return User
```

Na primer:

```php
public function register(RegisterUserData $data): User
{
    $email = mb_strtolower(trim($data->email));

    if ($this->users->findByEmail($email) !== null) {
        throw new RuntimeException(
            'Email is already registered.'
        );
    }

    $passwordHash = password_hash(
        $data->password,
        PASSWORD_DEFAULT
    );

    return $this->users->create(
        $email,
        $passwordHash
    );
}
```

---

## 11. Da li repository treba da hashira password?

Ja bih rekao: ne.

Loše:

```php
public function create(
    string $email,
    string $plainPassword
): User {
    $hash = password_hash(...);

    // INSERT
}
```

Zašto?

Jer repository tada više nije samo persistence boundary.

On sada zna i password security policy.

Bolje:

```text
RegistrationService
→ hashiranje
```

```text
UserRepository
→ persistence
```

Dakle:

```php
$hash = password_hash(...);

$users->create($email, $hash);
```

---

## 12. Controller treba da ostane tanak

Na primer:

```php
final class RegistrationController
{
    public function __construct(
        private RegistrationService $service
    ) {}

    public function store(RegisterRequest $request): void
    {
        $data = $request->validated();

        $user = $this->service->register($data);

        // redirect / response
    }
}
```

Controller ne treba da radi:

```text
SQL
password_hash
unique lookup
business orchestration
```

Njegov posao je:

HTTP boundary

To se lepo nastavlja na OOP modul.

## 13. Gde validation pripada?

Možemo imati:

RegisterRequest

koji validira HTTP input.

Na primer:

```php
final class RegisterRequest
{
    public function validated(): RegisterUserData
    {
        // required/email/password/confirmation validation
        // return DTO
    }
}
```

Flow:

```text
Request
↓
RegisterRequest
↓
RegisterUserData
↓
RegistrationService
↓
UserRepository
```

To je vrlo Laravel-like, ali potpuno Vanilla PHP.

## 14. Email uniqueness nije dovoljno proveravati samo u Request-u

Mogao bi da uradiš:

```text
RegisterRequest
→ proveri DB unique
```

ali tada Request sloj mora da zna repository/database.

Nije uvek pogrešno, ali ja bih za našu arhitekturu više voleo:

```text
RegisterRequest
→ format/input validation
```

```text
RegistrationService
→ business rule: email mora biti slobodan
```

Jer service treba da štiti pravilo bez obzira odakle je pozvan:

```text
web controller
CLI
API
test
```

Dakle business invariant ostaje u use case-u.

---

## 15. Šta repository može da radi pri `create()`?

Na primer:

```php
public function create(
    string $email,
    string $passwordHash
): User
{
    $stmt = $this->pdo->prepare(
        'INSERT INTO users (email, password_hash)
         VALUES (:email, :password_hash)'
    );

    $stmt->execute([
        'email' => $email,
        'password_hash' => $passwordHash
    ]);

    $id = (int) $this->pdo->lastInsertId();

    return new User(
        $id,
        $email,
        $passwordHash
    );
}
```

Repository:

```text
INSERT
lastInsertId
mapping
```

Service:

```text
registration rules
hashing
orchestration
```

Čista podela.

---

## 16. Šta ako INSERT padne zbog UNIQUE constraint-a?

Ovo je važna realna situacija.

Čak i ako si pre toga proverio:

```php
findByEmail()
```

može se desiti race condition.

Zato database INSERT može baciti PDOException.

Treba razlikovati:

duplicate email

od:

```text
database server down
syntax error
disk issue
```

U ozbiljnijem kodu možeš prepoznati unique violation i pretvoriti ga u application-friendly registration error.

Ne želiš korisniku pokazati:

SQLSTATE[23000]...

Ali detaljniju exception strategiju radimo u Modulu 11.

Za sada mentalno:

DB constraint može biti poslednja linija odbrane

---

## 17. Da li automatski loginujemo user-a posle registration-a?

To je product/application odluka.

Opcija A:

```text
register
↓
redirect /login
```

Opcija B:

```text
register
↓
automatically authenticate
↓
redirect /dashboard
```

Oba su validna.

Ako account zahteva email verification, možda želiš:

```text
register
↓
send verification
↓
limited/unverified state
```

To ćemo kasnije.

Poenta:

Registration i login su odvojeni use case-ovi čak i ako ih odlučiš povezati.

---

## 18. Registration response ne treba da sadrži password hash

Ako vraćaš:

```php
$user
```

prema API/controller sloju, nemoj automatski serialize-ovati sve property-je.

Ne želiš response:

```json
{
    "id": 17,
    "email": "bojan@example.com",
    "password_hash": "$2y$..."
}
```

Password hash nije nešto što frontend treba.

Čak i hash tretiramo kao sensitive credential data.

---

## 19. Confirmation se ne čuva

Input:

```text
password
password_confirmation
```

nakon validacije:

```php
$password === $confirmation
```

password_confirmation završava svoju svrhu.

Ne ide u:

```text
DTO posle validation-a, ako nije potrebno
database
session
logs
```

To je samo form-level verification input.

---

## 20. Registration i transaction?

Za minimalan registration sa jednim:

INSERT users

transaction ti često nije posebno potrebna.

Ali recimo registration radi:

```text
INSERT user
INSERT profile
INSERT default settings
INSERT audit entry
```

i želiš all-or-nothing.

Tada service može imati transaction boundary:

```text
BEGIN
↓
create user
create profile
create settings
↓
COMMIT
```

Ako nešto padne:

ROLLBACK

To je ista arhitektura koju smo već radili kod bookings.

---

## 21. Slanje welcome email-a

Ako nakon registracije radiš:

```text
create user
↓
send email
```

oprez sa transakcijom.

Ne želiš nužno:

```text
DB transaction otvorena
↓
čekaj external SMTP/API
```

To može dugo trajati.

Bolje mentalno:

```text
persist user
↓
commit
↓
queue/send notification
```

U Laravelu bi ti ovo već bilo poznato kroz queued notifications i afterCommit.

Isti princip važi bez frameworka.

---

## 22. Password policy ne treba preterano komplikovati

Nemoj praviti pravilo:

```text
minimum 8
1 uppercase
1 lowercase
1 digit
1 symbol
1 emoji
1 hijeroglif 😄
```

samo zato što izgleda "secure".

Bitnije su:

```text
razumna minimalna dužina
dozvoliti duže passwords/passphrases
dobar password hashing
rate limiting
MFA gde ima smisla
```

Duboki security policy ostaje za Module 12.

## 24. Laravel paralela

Laravel često sažme ovo u:

```php
$request->validate(...);

$user = User::create([
    'email' => $request->email,
    'password' => Hash::make($request->password),
]);
```

A framework/package može dodatno automatski loginovati user-a.

Ali ispod toga i dalje postoji:

```text
HTTP validation
↓
normalization/business checks
↓
hash
↓
persistence
↓
optional auth state
```

Mi sada samo eksplicitno vidimo svaki korak.

## Najvažnije za zapamtiti

Registration nije:

```text
forma → INSERT
```

nego:

```text
input
↓
validation
↓
normalize
↓
business rules
↓
password hash
↓
persistence
↓
response
```

Razdvoji:

```text
format validation
→ email format, required, password length
```

```text
business rule
→ email već postoji?
```

```text
database invariant
→ UNIQUE(email)
```

Password:

```text
plain password
→ samo privremeno
```

```text
password_hash()
→ pre persistence
```

```text
DB
→ čuva samo hash
```

Arhitektura:

```text
RegisterRequest
→ input validation
```

```text
RegistrationService
→ registration use case + hash + uniqueness
```

```text
UserRepository
→ SQL/persistence
```

```text
Controller
→ HTTP response/redirect
```

I posebno:

```text
application uniqueness check
+
database UNIQUE constraint
```

jer samo application check nije dovoljan protiv concurrent request-ova.
