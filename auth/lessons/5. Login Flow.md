# Lekcija 5/15 — Login flow: lookup → verify → establish auth state

Najvažniji mentalni model:
Login ne proverava samo da li user postoji — login mora da potvrdi da su credentials validni, 
pa tek onda uspostavi authenticated state.

Flow:
POST /login
↓
validate input
↓
normalize email
↓
find user by email
↓
verify password
↓
optional account checks
↓
regenerate session ID
↓
store user_id in session
↓
redirect / result

1. Login input
Tipično:
email
password

Na HTTP sloju proveravaš bar:
email
→ required
→ valid email format

password
→ required
→ string

Za login nema smisla ponovo primenjivati celu registration password policy.

Ako je user nekada napravio password od 8 karaktera, a ti sada policy promeniš na 12, ne želiš da mu login request kaže:
Password must contain at least 12 characters.

Login treba da proveri:
Da li ovaj credential odgovara postojećem account-u?

Dakle:
registration validation
≠
login validation

2. Normalize email isto kao na registration-u
Ako smo registration radili:
$email = mb_strtolower(trim($email));

isto radimo pre login lookup-a.

Ne:
register:
Bojan@Example.com → bojan@example.com

login:
traži bukvalno Bojan@Example.com

nego jedna konzistentna politika:
normalize
↓
findByEmail()

3. Find user
Repository:
$user = $this->users->findByEmail($email);

Rezultat:
User
ili
null

Ako je:
$user === null

credentials nisu validni.

Ali vrlo bitno:
Ne moramo korisniku reći da je baš email problem.

O tome malo kasnije.
4. Password verification
Ako user postoji:
if (!password_verify(
    $password,
    $user->passwordHash()
)) {
    // login failed
}

Dakle:
findByEmail()
↓
User
↓
password_verify()

Nikada:
$password === $user->passwordHash()

i nikada:
password_hash($password, PASSWORD_DEFAULT)
    === $user->passwordHash()

To smo zaključali u prethodnoj lekciji.
5. Tek uspešan verify znači valid credentials
Ako:
user postoji ✅
password odgovara ✅

tek tada možemo reći:
credentials valid

Ali čak ni tada ne znači automatski da će user dobiti session.

Možemo imati dodatna pravila:
account disabled?
account suspended?
email verification required?

Dakle:
valid credentials
≠ uvek valid login

6. Account status check
Recimo User ima:
active
disabled
suspended

Flow:
find user
↓
verify password
↓
check status
↓
establish auth state

Ako je:
status = disabled

onda:
password correct ✅
login allowed ❌

To je važna razlika između:
credential validation

i:
login eligibility

7. Generička error poruka
Loš model:
Email does not exist.

pa drugi slučaj:
Password is incorrect.

Time napadaču daješ informaciju:
koji email account postoji

To se zove user/account enumeration.

Bezbedniji outward response:
Invalid credentials.

za oba slučaja.

Interno možeš znati:
user not found
password mismatch

ali externally:
Invalid credentials.

8. Internal reason vs public message
Ovo je dobar dizajn:
interno:
USER_NOT_FOUND

ili:
PASSWORD_MISMATCH

ali korisniku:
Invalid credentials.

Zašto?

Jer logika i UX/security poruka nisu ista stvar.
9. Session se ne postavlja prerano
Loše:
$_SESSION['user_id'] = $user->id();

if (!password_verify(...)) {
    return false;
}

Jer si auth state postavio pre potvrde credentials.

Ispravno:
find user
↓
verify password
↓
account checks
↓
tek onda session

Authentication state je rezultat uspešnog login-a, ne deo pokušaja login-a.
10. Session fixation
Ovo je veoma važna auth security tema.

Ako korisnik uspešno pređe iz:
guest

u:
authenticated

treba promeniti session ID.

PHP:
session_regenerate_id(true);

Mentalno:
pre login:
session ABC

login uspešan
↓
regenerate

posle login:
session XYZ

Zašto?

Da attacker ne bi unapred znao/fiksirao session identifier koji će kasnije postati authenticated.

Detaljno session security radimo u Lekciji 7, ali login flow mora već sada da ima ovaj korak.
11. Tek onda čuvamo identity
Na primer:
session_regenerate_id(true);

$_SESSION['user_id'] = $user->id();

I to je dovoljno za minimalan auth state.

Ne treba:
$_SESSION['password'] = $password;

Nikada.

Ne treba ni:
$_SESSION['password_hash'] = $user->passwordHash();

Session treba identity reference, ne credentials.
12. Minimalna login metoda
Konceptualno:
public function login(
    string $email,
    string $password
): bool {
    $email = mb_strtolower(trim($email));

    $user = $this->users->findByEmail($email);

    if ($user === null) {
        return false;
    }

    if (!password_verify(
        $password,
        $user->passwordHash()
    )) {
        return false;
    }

    session_regenerate_id(true);

    $_SESSION['user_id'] = $user->id();

    return true;
}

Ovo je već funkcionalan minimalni login mental model.
13. Gde ide password_needs_rehash()?
Posle uspešnog verify-a:
if (password_needs_rehash(
    $user->passwordHash(),
    PASSWORD_DEFAULT
)) {
    $newHash = password_hash(
        $password,
        PASSWORD_DEFAULT
    );

    $this->users->updatePasswordHash(
        $user->id(),
        $newHash
    );
}

Dakle:
verify ✅
↓
optional rehash
↓
session

Možeš rehash raditi neposredno pre uspostavljanja session-a.
14. AuthService vs LoginController
Controller:
final class LoginController
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function store(LoginRequest $request): void
    {
        $data = $request->validated();

        if (!$this->auth->attempt(
            $data->email,
            $data->password
        )) {
            // return validation/auth error
        }

        // redirect
    }
}

Service:
normalize
lookup
verify
rehash
session auth state

Controller:
HTTP input/output
redirect/error response

To je dobra granica.
15. attempt() je često bolji naziv od login()
Zašto?

Jer:
attempt(...)

jasno govori:
pokušaj da potvrdiš credentials i uspostaviš auth state.

Povratna vrednost:
true
false

je prirodna.

Na primer Laravel:
Auth::attempt(...)

isti mentalni model.

Možeš imati i:
login(User $user)

kao posebnu internu metodu koja samo uspostavlja session za već potvrđenog user-a.

To je čak vrlo čista podela:
attempt(credentials)
→ verify

login(user)
→ establish auth state

16. Lepo razdvajanje attempt() i login()
Na primer:
public function attempt(
    string $email,
    string $password
): bool {
    $user = $this->users->findByEmail($email);

    if ($user === null) {
        return false;
    }

    if (!password_verify(
        $password,
        $user->passwordHash()
    )) {
        return false;
    }

    $this->login($user);

    return true;
}

A:
public function login(User $user): void
{
    session_regenerate_id(true);

    $_SESSION['user_id'] = $user->id();
}

Sada odgovornosti izgledaju još jasnije:
attempt()
→ credentials

login()
→ auth state

17. Zašto login(User $user) može biti koristan?
Jer user može postati authenticated i iz drugih flow-ova.

Na primer:
registration
↓
automatski login

ili:
remember-me token
↓
restore user
↓
login(user)

Tada ne želiš da svaki put ponavljaš:
password verification

jer user možda nije došao kroz password credentials.

Dakle centralna metoda za auth state može imati smisla.
18. Ne čuvaj ceo User objekat u session-u
Posle uspeha:
$_SESSION['user_id'] = $user->id();

je mnogo zdravije od:
$_SESSION['user'] = serialize($user);

Razlozi:
stale data
serialization problemi
class changes
nepotrebno session opterećenje
source of truth problem

U sledećim request-ovima:
user_id
↓
repository
↓
fresh User

19. Timing razlika — mali security detalj
Ako user ne postoji:
return false;

odmah.

Ako postoji:
password_verify()

radi skuplju hash proveru.

Teoretski može postojati timing razlika između:
unknown email
known email + wrong password

koja može pomoći enumeration napadu.

Napredniji sistemi ponekad rade dummy password verification čak i kada user ne postoji, da bi response time bio sličniji.

Na primer konceptualno:
if ($user === null) {
    password_verify(
        $password,
        $dummyHash
    );

    return false;
}

Ne moramo ovo implementirati u našem minimalnom projektu, ali dobro je da znaš da postoji.
20. Rate limiting nije isto što i login logic
Čak i savršen:
password_verify()

ne sprečava attacker-a da proba:
100,000 passwords

preko login endpoint-a.

Zato realan login ima i:
rate limiting
lockout/throttling
monitoring

Ali to ćemo dublje u Module 12 Security.

Za sada:
credential correctness
≠ brute-force protection

21. Login success response
Kod web aplikacije tipično:
success
↓
redirect /dashboard

Kod API-ja:
success
↓
response / token / session cookie

Kod našeg session auth modela:
session cookie

je već deo PHP session mehanizma.

Ne vraćamo password, hash ili credentials.
22. Redirect safety
Posle login-a možda želiš:
redirect back to originally requested page

na primer:
user tried /account
↓
sent to /login
↓
successful login
↓
return /account

Ali redirect destination ne treba slepo uzeti iz user input-a bez validacije, jer to može dovesti do open redirect problema.

To je više Security module tema, ali vredi znati.
23. Login nije persistence operation nad User-om
Osim eventualnog:
password rehash
last_login_at

login nije:
"save User"

Njegova glavna svrha je:
confirm credentials
+
establish auth state

Dakle repository je lookup dependency, session je state dependency.
