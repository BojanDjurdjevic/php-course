# 9. Current User Loading — Part 1

## Module 10 — Authentication bez frameworka

### Lekcija 9/15 — Current user loading

Do sada session može da sadrži:

```php
$_SESSION['user_id'] = 17;
```

Ali to još nije isto što i:

```php
$currentUser = new User(...);
```

Cilj ove lekcije je da naučimo kako iz session identiteta dobijamo stvarnog, aktuelnog korisnika iz persistence sloja.

Najvažniji mentalni model:

```text
session user_id
↓
UserRepository::findById()
↓
User | null
↓
current authenticated user
```

---

## 1. `user_id` nije isto što i `User`

Session može da kaže:

```php
$_SESSION['user_id'] = 17;
```

To znači samo:

> Ova session tvrdi da predstavlja korisnika sa ID-em 17.

To nije još kompletan `User` objekat.

Da bismo dobili current user-a:

```php
$user = $users->findById(17);
```

Dakle:

```text
Auth state
→ user_id

Persistence
→ User
```

Ovo razdvajanje je veoma zdravo jer session ostaje mali, a baza ostaje source of truth.

---

## 2. Zašto ne čuvamo ceo User u session-u?

Mogli bismo:

```php
$_SESSION['user'] = [
    'id' => 17,
    'email' => 'bojan@example.com',
    'role' => 'admin',
    'status' => 'active'
];
```

Ali podaci mogu da se promene u bazi.

Na primer:

```text
role:
admin → customer

status:
active → disabled
```

Session bi i dalje mogao da sadrži stare vrednosti.

To je stale state.

Bolje:

```php
$_SESSION['user_id'] = 17;
```

pa pri request-u:

```text
user_id
↓
repository
↓
fresh User
```

---

## 3. `AuthService::user()`

Minimalna implementacija:

```php
public function user(): ?User
{
    $id = $this->id();

    if ($id === null) {
        return null;
    }

    return $this->users->findById($id);
}
```

Mentalno:

```text
guest
→ id() vraća null
→ user() vraća null
```

Authenticated session:

```text
id() → 17
↓
findById(17)
↓
User
```

Zato return type ima smisla:

```php
?User
```

odnosno:

```text
User | null
```

---

## 4. Šta ako session ima ID, ali user više ne postoji?

Recimo:

```php
$_SESSION['user_id'] = 17;
```

Ali user #17 je obrisan iz baze.

Repository:

```php
$user = $this->users->findById(17);
```

vrati:

```php
null
```

Session sada sadrži stale authentication state.

Ne želimo:

```text
session kaže authenticated
ali baza kaže da user ne postoji
```

U tom slučaju current auth state treba invalidirati.

---

## 5. Čišćenje stale session state-a

Robusnija verzija:

```php
public function user(): ?User
{
    $id = $this->id();

    if ($id === null) {
        return null;
    }

    $user = $this->users->findById($id);

    if ($user === null) {
        $this->session->forget('user_id');

        return null;
    }

    return $user;
}
```

Dakle:

```text
session user_id
↓
repository lookup
↓
user missing
↓
remove user_id
↓
guest
```

To vraća session u konzistentno stanje.

---

## 6. Šta ako user postoji, ali više nije active?

Drugi slučaj:

```text
session:
user_id = 17
```

Repository vrati:

```text
User #17
status = disabled
```

User postoji, ali više ne bi trebalo da ima pristup authenticated delu aplikacije.

Zato current-user resolution može proveravati:

```php
if (!$user->isActive()) {
    $this->session->forget('user_id');

    return null;
}
```

Mentalno:

```text
identity exists
≠
identity is still eligible for authentication
```

---

## 7. Baza ostaje source of truth

Ovo je centralni princip.

Session kaže:

```text
koji user ID je authenticated
```

Baza kaže:

```text
da li taj user i dalje postoji
koji mu je status
koji su mu aktuelni podaci
```

Zato:

```text
session
→ reference

database
→ truth
```

To je posebno važno kada se tokom aktivne session promene:

```text
email
role
status
account deletion
```

---

## 8. `check()` — samo session ili stvarni User?

Ranije smo imali:

```php
public function check(): bool
{
    return $this->id() !== null;
}
```

To je brzo, ali nije potpuno pouzdano.

Session može imati:

```text
user_id = 17
```

a user možda više ne postoji.

Robusnije:

```php
public function check(): bool
{
    return $this->user() !== null;
}
```

Sada:

```text
check()
→ true samo ako stvarni User može biti resolved
```

Mana:

```text
user()
→ može napraviti DB query
```

Tu dolazimo do sledećeg problema.

---

## 9. Problem ponovljenih query-ja

Zamisli jedan request:

```php
if ($auth->check()) {
    $user = $auth->user();

    echo $auth->user()->email();
}
```

Ako `check()` zove `user()`, a `user()` svaki put radi:

```php
$this->users->findById(...)
```

možemo dobiti:

```text
SELECT user
SELECT user
SELECT user
```

tokom jednog request-a.

To je nepotrebno.

Zato ćemo current user-a **cache-ovati samo tokom trajanja jednog PHP request-a**.

---

## 10. Per-request caching

Želimo da prvi:

```php
$auth->user();
```

uradi repository query.

Ali sledeći:

```php
$auth->user();
```

u istom request-u treba da vrati već učitani objekat.

Mentalno:

```text
prvi poziv
↓
DB lookup
↓
User
↓
sačuvaj u AuthService property

sledeći poziv
↓
vrati isti resolved User
```

Ovo nije session cache.

To je samo memory cache dok traje trenutni PHP request.

Kada request završi, objekat nestaje.

---

## 11. Problem sa običnim `?User $currentUser = null`

Na prvi pogled možemo napisati:

```php
private ?User $currentUser = null;
```

Ali `null` može značiti dve različite stvari:

```text
1. još nismo pokušali da učitamo user-a

2. pokušali smo, ali nema authenticated user-a
```

Ako ne razlikujemo ta dva stanja, možemo iznova praviti DB query iako već znamo da user ne postoji.

Zato nam treba dodatni flag.

---

## 12. `userResolved` flag

Na primer:

```php
private ?User $currentUser = null;

private bool $userResolved = false;
```

Sada imamo tri moguća stanja:

```text
userResolved = false
→ još nismo proverili

userResolved = true
currentUser = null
→ proverili smo, nema user-a

userResolved = true
currentUser = User
→ current user uspešno učitan
```

To je precizan state model.

---

## 13. Implementacija cached `user()`

Na primer:

```php
public function user(): ?User
{
    if ($this->userResolved) {
        return $this->currentUser;
    }

    $this->userResolved = true;

    $id = $this->id();

    if ($id === null) {
        return null;
    }

    $user = $this->users->findById($id);

    if ($user === null) {
        $this->session->forget('user_id');

        return null;
    }

    if (!$user->isActive()) {
        $this->session->forget('user_id');

        return null;
    }

    $this->currentUser = $user;

    return $this->currentUser;
}
```

Prvi poziv radi resolution.

Svaki sledeći samo vraća:

```php
$this->currentUser;
```

---

## 14. `check()` sada postaje jeftin

Možemo:

```php
public function check(): bool
{
    return $this->user() !== null;
}
```

Prvi poziv može napraviti DB query.

Ali nakon toga:

```php
$auth->check();
$auth->user();
$auth->check();
$auth->user();
```

ne mora da pravi četiri query-ja.

Current user je već resolved.

---

## 15. `guest()` ostaje jednostavan

```php
public function guest(): bool
{
    return !$this->check();
}
```

Dakle:

```text
user() !== null
→ check() true
→ guest() false
```

i obrnuto.

Ne treba praviti posebnu logiku za guest-a.

---

## 16. Šta se dešava posle `login()`?

Recimo u istom request-u imamo:

```php
$auth->user();
```

pre login-a.

To vrati:

```text
null
```

i postavi:

```text
userResolved = true
```

Kasnije u istom request-u korisnik bude loginovan.

Ako ništa ne uradimo, cached vrednost ostaje:

```text
null
```

i:

```php
$auth->user();
```

bi pogrešno i dalje vraćao `null`.

Zato login mora da osveži per-request cache.

---

## 17. `login()` treba da postavi current user

Na primer:

```php
public function login(User $user): void
{
    $this->session->regenerate();

    $this->session->put(
        'user_id',
        $user->id()
    );

    $this->currentUser = $user;
    $this->userResolved = true;
}
```

Sada:

```text
login(user)
↓
session user_id
+
current request cache
```

odmah postaju usklađeni.

---

## 18. `logout()` takođe mora da očisti cache

Ako imamo:

```php
$auth->user();
```

pa dobijemo User objekat i zatim:

```php
$auth->logout();
```

ne sme:

```php
$auth->user();
```

i dalje da vraća stari objekat iz memory cache-a.

Zato:

```php
public function logout(): void
{
    $this->session->forget('user_id');

    $this->currentUser = null;
    $this->userResolved = true;
}
```

Kompletan logout lifecycle ćemo dodatno proširiti u Lekciji 11.

Ali current-user cache mora odmah biti invalidiran.

---

## 19. Cache traje samo jedan request

Ovo je važno.

Property:

```php
private ?User $currentUser;
```

ne znači:

> zauvek smo cache-ovali user-a.

U klasičnoj PHP aplikaciji:

```text
Request 1
→ naprave se objekti
→ AuthService učita User
→ request završi
→ objekti nestaju

Request 2
→ novi AuthService lifecycle
→ user se ponovo učitava
```

Dakle database se i dalje proverava po request-u.

To nam daje dobar balans:

```text
fresh state između request-ova
+
bez duplih query-ja unutar jednog request-a
```

## 20. Current user i authorization

Authentication daje:

```php
$user = $auth->user();
```

Authorization onda može koristiti tog user-a:

```php
if (!$policy->update($user, $booking)) {
    // deny
}
```

Dakle:

```text
session
↓
AuthService
↓
current User
↓
Policy / authorization
```

AuthService ne treba sam da odlučuje:

```text
može li ovaj user editovati booking?
```

On samo obezbeđuje identitet.

---

## 21. Current user u Controller-u

Na primer:

```php
final class ProfileController
{
    public function __construct(
        private AuthService $auth
    ) {}

    public function show(): void
    {
        $user = $this->auth->user();

        if ($user === null) {
            // redirect login
            return;
        }

        // render profile
    }
}
```

Ovo radi.

Ali uskoro ćemo videti da je ponavljanje:

```php
if ($user === null)
```

u svakom controller-u loš pattern.

Zato sledeća lekcija uvodi middleware.

---

## 22. Current user u View-u

View može dobiti:

```php
$user
```

iz controller-a.

Na primer:

```php
<h1>
    Welcome,
    <?= htmlspecialchars($user->email()) ?>
</h1>
```

Ali view ne bi trebalo da radi:

```php
$auth->userRepository()->findById(...)
```

Persistence lookup treba da bude rešen pre renderovanja.

View samo prikazuje podatke.

---

## 23. User može biti promenjen tokom request-a

Retko, ali moguće.

Na primer request uradi:

```text
load current User
↓
promeni account status
↓
persist change
```

A AuthService i dalje drži stari User objekat.

To je normalna posledica per-request cache-a.

Ako tvoj use case menja current user podatke i odmah želi novu verziju objekta, imaš opcije:

```text
update cached object
ili
invalidate current-user cache
ili
vrati novi User iz service-a
```

Ne treba komplikovati dok se takva potreba ne pojavi.

---

## 24. `refreshUser()` kao opcionalni helper

Ako zaista ima smisla, možemo imati:

```php
public function refreshUser(): ?User
{
    $this->currentUser = null;
    $this->userResolved = false;

    return $this->user();
}
```

To prisili novi repository lookup.

Ali ovo nije metoda koju mora svaki auth sistem da ima.

Koristi se samo ako application flow stvarno zahteva refresh current user-a tokom istog request-a.

---

## 25. Ne veruj session role-u

Posebno važna security nijansa.

Nemoj:

```php
$_SESSION['role'] = 'admin';
```

pa kasnije:

```php
if ($_SESSION['role'] === 'admin') {
    // allow
}
```

ako role može da se promeni u bazi.

Bolje:

```text
session user_id
↓
fresh User
↓
$user->role()
```

Tada admin kojem je upravo skinuta privilegija neće ostati admin do isteka session-a samo zbog stale podatka.

---

## 26. Deleted / disabled / suspended user

Current-user resolver je dobro centralno mesto da obradi osnovnu auth eligibility.

Na primer:

```php
if ($user === null || !$user->isActive()) {
    $this->session->forget('user_id');

    $this->currentUser = null;

    return null;
}
```

Možemo imati:

```text
deleted
disabled
suspended
```

kao različite business states.

Poenta:

> Session ne sme beskonačno održavati authentication za account koji više ne sme biti authenticated.

---

## 27. Kompletan `AuthService` skeleton posle ove lekcije

```php
final class AuthService
{
    private ?User $currentUser = null;

    private bool $userResolved = false;

    public function __construct(
        private UserRepository $users,
        private Session $session
    ) {}

    public function id(): ?int
    {
        $id = $this->session->get('user_id');

        return $id === null
            ? null
            : (int) $id;
    }

    public function user(): ?User
    {
        if ($this->userResolved) {
            return $this->currentUser;
        }

        $this->userResolved = true;

        $id = $this->id();

        if ($id === null) {
            return null;
        }

        $user = $this->users->findById($id);

        if ($user === null || !$user->isActive()) {
            $this->session->forget('user_id');

            return null;
        }

        $this->currentUser = $user;

        return $this->currentUser;
    }

    public function check(): bool
    {
        return $this->user() !== null;
    }

    public function guest(): bool
    {
        return !$this->check();
    }

    public function login(User $user): void
    {
        $this->session->regenerate();

        $this->session->put(
            'user_id',
            $user->id()
        );

        $this->currentUser = $user;
        $this->userResolved = true;
    }

    public function logout(): void
    {
        $this->session->forget('user_id');

        $this->currentUser = null;
        $this->userResolved = true;
    }
}
```

Ovo je već vrlo pristojan current-user model za Vanilla PHP aplikaciju.

## Najvažnije za zapamtiti

Session ne čuva ceo user state:

```text
$_SESSION['user_id']
→ identity reference
```

Current user:

```text
session user_id
↓
UserRepository::findById()
↓
User | null
```

Baza je source of truth:

```text
session
→ ko je user

database
→ da li postoji
→ da li je active
→ koji su mu aktuelni podaci
```

Ako user više ne postoji ili ne sme da bude authenticated:

```text
stale session
↓
forget user_id
↓
guest
```

`check()` je najrobustnije:

```php
return $this->user() !== null;
```

ali da ne bismo pravili više query-ja:

```text
first user()
→ DB query

next user()
→ per-request cached User
```

Za to razlikujemo:

```text
userResolved = false
→ još nismo proverili

userResolved = true + currentUser = null
→ proverili, nema user-a

userResolved = true + currentUser = User
→ authenticated user resolved
```

`login()` mora da uskladi:

```text
session
+
current request cache
```

`logout()` mora da očisti oba.

I najvažnija granica:

```text
AuthService
→ daje current identity

Authorization / Policy
→ odlučuje šta taj identity sme
```
