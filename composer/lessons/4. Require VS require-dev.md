# 4. Require VS require-dev

## Lekcija 4/15 — require vs require-dev

Najkraće:

```text
require
→ potrebno aplikaciji da radi
```

```text
require-dev
→ potrebno samo tokom development-a, testiranja i analize
```

To deluje jednostavno, ali granica je važna
jer utiče na produkcioni deploy, veličinu vendor/ foldera i attack surface.

1. require
Primer:

```json
{
    "require": {
        "php": "^8.3",
        "monolog/monolog": "^3.0"
    }
}
```

Ovo znači:

Bez ovih dependencies aplikacija ne može normalno da radi u produkciji.

Ako tvoj kod u runtime-u koristi:

```php
use Monolog\Logger;
```

onda monolog/monolog mora biti dostupan i na production serveru.
Tipični runtime dependencies:

```text
PDF generator
HTTP client
image processing library
mailer
logging library
database package
framework
```

Naravno, zavisi kako ih aplikacija koristi.
2. require-dev
Primer:

```json
{
    "require-dev": {
        "phpunit/phpunit": "^12.0"
    }
}
```

PHPUnit ti treba da:

```text
pišeš testove
pokrećeš testove
proveravaš aplikaciju tokom development-a
```

Ali krajnjem HTTP request-u na production serveru uglavnom nije potreban PHPUnit da bi:

```text
kreirao booking
prikazao hotel
ulogovao korisnika
```

Zato ide u:

require-dev

Tipični primeri:

```text
PHPUnit
PHPStan
Psalm
Pest
code style / lint alati
debug paketi
development profilers
```

---

## 3. Kako ih dodajemo?

Runtime dependency:

```bash
composer require monolog/monolog
```

Development dependency:

```bash
composer require --dev phpunit/phpunit
```

Rezultat:

```json
{
    "require": {
        "monolog/monolog": "^3.0"
    },
    "require-dev": {
        "phpunit/phpunit": "^12.0"
    }
}
```

Dakle --dev ne znači:

instaliraj nekakvu dev verziju paketa.

Nego:

zapiši ovaj dependency u require-dev.

To je važna razlika.

---

## 4. Šta se dešava lokalno?

Kada normalno uradiš:

```bash
composer install
```

Composer po defaultu instalira:

```text
require
+
require-dev
```

Dakle u lokalnom development environment-u dobijaš sve.
To ti treba jer želiš i aplikaciju i development tooling.

---

## 5. Produkcija — --no-dev

Na produkciji često koristimo:

```bash
composer install --no-dev
```

Tada Composer instalira:

```php
require ✅
```

require-dev ❌

Na primer:

```json
{
    "require": {
        "monolog/monolog": "^3.0"
    },
    "require-dev": {
        "phpunit/phpunit": "^12.0"
    }
}
```

Production:

```bash
composer install --no-dev
```

dobija:

```text
Monolog ✅
PHPUnit ❌
```

Aplikacija i dalje radi, ali nema development tooling.

---

## 6. Zašto ne bismo sve stavili u require?

Tehnički možeš.
Ali onda produkcija instalira i gomilu nepotrebnih paketa.
To može značiti:

```text
veći vendor/
više fajlova
sporiji deploy
više dependencies za održavanje
veći potencijalni security surface
nepotreban dev tooling na serveru
```

Zato granica ima smisla.
Mentalno:

Da li aplikaciji ovo treba da obradi production request?

```text
DA
→ require
```

```text
NE, treba samo developeru/testovima
→ require-dev
```

---

## 7. Ali postoji jedna važna zamka

Nemoj automatski reći:

"Ovo koristim samo ja kao developer, dakle require-dev."

Pitanje nije ko ga koristi, nego:

Da li ga production runtime zahteva?

Na primer imaš package koji generiše PDF voucher.

Ti si ga instalirao tokom development-a,
ali produkcija mora da generiše voucher kada korisnik rezerviše.

Dakle:

```text
PDF library
→ require
```

Ne require-dev.

## 9. Šta ako pogrešno stavimo runtime dependency u require-dev?

Ovo je mnogo ozbiljnija greška.
Lokalno:

```bash
composer install
```

sve radi.

---

## Zašto?

Jer su instalirani i require i require-dev.
Onda deploy:

```bash
composer install --no-dev
```

i odjednom:

Class "Something\PdfGenerator" not found

---

## Zašto?

Jer si package koji aplikacija stvarno koristi stavio u require-dev.
Dakle možeš dobiti klasičan problem:

works on my machine ✅

production ❌

Zato moraš pravilno klasifikovati dependency.

---

## 10. Šta ako dev dependency stavimo u require?

Aplikacija će verovatno i dalje raditi.
Ali produkcija sada instalira nešto što joj ne treba.
Dakle:

```text
runtime dependency u require-dev
→ može razbiti produkciju
```

```text
dev dependency u require
→ uglavnom nepotrebno opterećenje / lošija higijena
```

Prva greška je obično ozbiljnija.
11. composer.lock prati oba
Važna stvar:

composer.lock sadrži resolved informacije i za:

```text
packages
→ require dependencies
```

```text
packages-dev
→ require-dev dependencies
```

Dakle lock file zna i development dependency graph.
Ali:

```bash
composer install --no-dev
```

kaže Composer-u:

Nemoj instalirati dev deo tog zaključanog graph-a.

Ne znači da Composer ignoriše postojanje composer.lock.

---

## 12. Da li --no-dev menja composer.json?

Ne.
Ako pokreneš:

```bash
composer install --no-dev
```

ovo:

```json
"require-dev": {
    "phpunit/phpunit": "^12.0"
}
```

ostaje u composer.json.
Samo paket neće biti instaliran u trenutnom environment-u.
Dakle:

```text
composer.json
→ dependency deklaracija projekta
```

```text
--no-dev
→ install odluka za konkretan environment
```

13. require-dev dependency ne treba da curi u production code
Ovo je još važniji dizajnerski princip.
Recimo:

```json
"require-dev": {
    "some/debug/package": "^1.0"
}
```

a onda production class radi:

```php
use Some\Debug\Package;

class BookingService
{
    // runtime code zavisi od dev package-a
}
```

To je kontradikcija.
Ako produkcioni kod stvarno zavisi od njega, onda to više nije samo dev dependency.
Moraš ili:

premestiti package u require

ili:

ukloniti dependency iz production code-a

14. autoload vs autoload-dev
Ovo se prirodno povezuje.
Možemo imati:

```json
"autoload": {
    "psr-4": {
        "App\\": "src/"
    }
},
```

```json
"autoload-dev": {
    "psr-4": {
        "Tests\\": "tests/"
    }
}
```

Mentalno:

```text
autoload
→ application/runtime classes
```

```text
autoload-dev
→ development/test classes
```

Ista ideja kao:

```text
require
vs
require-dev
```

Samo sada primenjena na autoloading.

Detaljno ćemo to raditi u Lekciji 14.

## 16. Praktičan composer.json

Naš MiniStay bi kasnije mogao izgledati ovako:

```json
{
    "require": {
        "php": "^8.3",
        "ext-pdo": "*",
        "monolog/monolog": "^3.0"
    },
    "require-dev": {
        "phpunit/phpunit": "^12.0"
    },
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    },
    "autoload-dev": {
        "psr-4": {
            "Tests\\": "tests/"
        }
    }
}
```

Produkcija:

```bash
composer install --no-dev
```

dobija runtime deo.
Development:

```bash
composer install
```

dobija oba.
Mentalna mapa Lekcije 4

```text
require
→ production/runtime dependency
→ instalira se normalno
→ instalira se sa --no-dev
```

```text
require-dev
→ development/testing dependency
→ instalira se normalno
→ NE instalira se sa --no-dev
```

I možda najvažnija rečenica:

```php
require vs require-dev nije pitanje „gde sam instalirao package“,
```

nego da li production runtime zavisi od njega.
