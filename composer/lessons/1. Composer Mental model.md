## Lekcija 1/15 — Composer mental model: šta Composer zapravo radi?

Najkraća definicija:

Composer je dependency manager za PHP koji ujedno generiše autoload sistem za klase.

Ali mnogo je važnije da razumeš šta se zapravo dešava nego da naučiš tu definiciju napamet.

---

## 1. Problem koji Composer rešava

Zamisli Vanilla PHP projekat bez Composer-a.
Želiš neku biblioteku za generisanje PDF-a.
Mogao bi ručno:

1. odeš na GitHub
2. skineš biblioteku
3. kopiraš fajlove u projekat
4. ručno require-uješ fajlove
5. shvatiš da biblioteka zavisi od još 3 biblioteke
6. skineš i njih
7. vodiš računa o verzijama
8. vodiš računa šta je kompatibilno sa čim

Vrlo brzo nastane haos.
Composer kaže:

Ti mi samo reci:

"Mom projektu treba paket X."

Ja ću:

```text
→ pronaći odgovarajuću verziju
→ proveriti njegove dependencies
→ pronaći njihove dependencies
→ instalirati ih
→ zapamtiti verzije
→ napraviti autoload sistem
```

To je osnovni mentalni model.

---

## 2. Dependency

Dependency je jednostavno:

nešto što je tvojoj aplikaciji potrebno da bi radila.

Recimo aplikacija koristi:

```php
use Intervention\Image\ImageManager;
```

Tvoja aplikacija zavisi od Intervention Image biblioteke.
Dakle:

```text
Tvoja aplikacija
       ↓ depends on
Intervention Image
```

Ali Intervention Image možda zavisi od još nekog paketa:

```text
Tvoja aplikacija
       ↓
Package A
       ↓
Package B
       ↓
Package C
```

Composer rešava ceo taj dependency graph.
Ovo je vrlo važan izraz:

Dependency graph

Composer ne instalira samo paket koji si direktno tražio. On rešava ceo graf zavisnosti.

---

## 3. Composer nije isto što i Packagist

Ovo se često meša.

```text
Composer
→ alat koji upravlja dependencies
```

```text
Packagist
→ javni registry/repository PHP paketa
```

Analogija:

```text
npm       ↔ Composer
npmjs.com ↔ Packagist
```

Kada napišeš kasnije:

```bash
composer require monolog/monolog
```

Composer najčešće pronalazi paket preko Packagist-a.
Dakle:

```text
Composer
→ "Koji paket treba?"
```

```text
Packagist
→ "Evo gde postoji i koje verzije postoje."
```

```text
Composer
→ "U redu, rešavam dependencies i instaliram."
```

## 4. Centralna mapa Composer projekta

U praktičnom Composer projektu stalno ćeš vrteti ova četiri elementa:

```text
composer.json
      ↓
composer.lock
      ↓
vendor/
      ↓
vendor/autoload.php
```

Još ih ne učimo detaljno — svako dobija svoju lekciju — ali mentalno odmah treba da znaš šta predstavljaju.
composer.json
Kaže:

Šta moj projekat želi / zahteva?

Na primer konceptualno:

```json
{
    "require": {
        "some/package": "^2.0"
    }
}
```

To nije:

Imam tačno verziju 2.4.7.

nego više:

Moj projekat prihvata paket prema ovom version constraint-u.

composer.lock
Kaže:

Koje su konkretne verzije zaista izabrane za ovaj projekat?

Recimo:

```text
composer.json
→ hoću compatible 2.x verziju
```

Composer rešava dependency graph

```text
composer.lock
→ konkretno smo zaključali 2.4.7
```

Dakle:

```text
composer.json
→ intention / requirements
```

```text
composer.lock
→ resolved snapshot
```

Ovo ćemo mnogo detaljnije raditi.
vendor/
Ovde Composer fizički instalira dependencies.
Na primer:

```text
project/
├── src/
├── public/
├── composer.json
├── composer.lock
└── vendor/
    ├── composer/
    ├── package-a/
    └── package-b/
```

vendor/ je otprilike Composer-ov instalacioni prostor za third-party code.
Zato u Laravel projektu imaš:

vendor/

sa ogromnom količinom framework i dependency koda.
vendor/autoload.php
Ovo je možda najvažniji fajl koji Composer generiše za naš budući Vanilla PHP projekat.
Umesto:

```php
require 'src/Controllers/BookingController.php';
require 'src/Services/BookingService.php';
require 'src/Repositories/BookingRepository.php';
require 'src/DTO/CreateBookingData.php';
require 'src/Enums/BookingStatus.php';
```

na kraju ćeš imati:

```php
require __DIR__ . '/../vendor/autoload.php';
```

i onda:

```php
use App\Services\BookingService;
```

Composer zna gde je ta klasa.
To je autoloading.

## 5. Composer ima dve velike odgovornosti

Ovo bih baš zapamtio.

```text
COMPOSER
│
├── 1. Dependency management
│
│   → instalacija paketa
│   → verzije
│   → dependency graph
│   → lock file
│
└── 2. Autoloading
    → pronalaženje PHP klasa
    → PSR-4
    → vendor/autoload.php
```

Composer nije samo:

„alat kojim instaliram biblioteke“.

Čak i ako ne instaliraš nijedan third-party paket, Composer je veoma koristan samo zbog autoloadinga tvoje aplikacije.
Recimo naš OOP projekat može imati:

```text
src/
├── Controllers/
│   └── BookingController.php
├── DTO/
│   └── CreateBookingData.php
├── Enums/
│   └── BookingStatus.php
├── Repositories/
│   └── BookingRepository.php
└── Services/
    └── BookingService.php
```

Sa Composer PSR-4 autoloadingom:

```php
use App\Controllers\BookingController;
use App\Services\BookingService;
```

bez ručnog require za svaki fajl.
To je ogroman dobitak.

---

## 6. Šta Composer NE radi?

Composer nije framework.
Ne daje ti:

```text
routing
controllers
ORM
authentication
HTTP lifecycle
views
```

To radi Laravel ili kod koji ti napišeš.
Composer samo može da instalira Laravel i njegove dependencies.
Mentalno:

```text
Composer
→ upravlja PHP paketima i autoloadingom
```

```text
Laravel
→ framework koji je instaliran i učitan pomoću Composer-a
```

Zato kada napraviš Laravel projekat, Composer je ispod svega.

---

## 7. Šta se zapravo dešava kada instaliraš Laravel?

Vrlo uprošćeno:

```text
želim Laravel
↓
Composer pročita njegove zahteve
↓
Laravel zavisi od Symfony komponenti
↓
te komponente imaju svoje dependencies
↓
Composer rešava ceo graph
↓
instalira sve u vendor/
↓
generiše autoload
```

Zato Laravel vendor/ ima stotine paketa.
Nisi instalirao svaki ručno.
Composer je rešio graph.

## 8. Composer i PHP verzija

Još jedna važna stvar: dependency ne mora biti samo biblioteka.
Paket može reći:

```text
treba mi PHP >= 8.2
treba mi ext-mbstring
treba mi ext-json
```

Dakle Composer može proveravati i platform requirements.
Konceptualno:

Moj paket zahteva:

```text
├── PHP >= 8.2
├── ext-mbstring
└── package-x ^3.0
```

Ako tvoj environment to ne zadovoljava, Composer može da prijavi konflikt.
Zato ponekad vidiš:

Your PHP version does not satisfy that requirement.

ili:

ext-something is missing

Composer tu ne instalira nužno PHP extension umesto tebe — on ti kaže da dependency graph ne može biti zadovoljen na trenutnoj platformi.

## 9. Dependency resolution — najvažniji deo ispod haube

Recimo tvoj projekat kaže:

Package A ^2.0

ali:

```text
Package A
→ zahteva Package C ^3.0
```

```text
Package B
→ zahteva Package C ^2.0
```

Sada Composer mora da vidi:

Postoji li verzija Package C koja može zadovoljiti oba zahteva?

Ako ne postoji:

dependency conflict

Composer ne može čarobno da instalira bilo šta.
Dakle Composer je između ostalog dependency resolver.
Mentalno:

```text
requirements
↓
constraints
↓
dependency graph
↓
resolution algorithm
↓
compatible concrete versions
```

Ovo je srž Composer-a.

## 10. Direktni i transitive dependencies

Ako ti napišeš:

```bash
composer require package-a
```

package-a je tvoj direct dependency.
Ali ako:

```text
package-a
→ zahteva package-b
```

package-b je transitive dependency.
Mentalno:

```text
Tvoj projekat
│
├── package-a       ← direct
│     └── package-b ← transitive
│
└── package-c       ← direct
```

Ovo je važno jer ćeš u vendor/ često videti gomilu paketa koje nikada nisi direktno instalirao.
Nisu se pojavili slučajno — potrebni su tvojim dependencies.

## 11. Composer workflow u jednoj slici

Ovo je mentalna mapa cele naredne oblasti:

```text
                    composer.json
                         │
                         │ kaže šta želimo
                         ↓
                 Composer resolver
                         │
          ┌──────────────┴──────────────┐
          ↓                             ↓
   dependency graph              version constraints
          │                             │
          └──────────────┬──────────────┘
                         ↓
                  concrete versions
                         │
                         ↓
                   composer.lock
                         │
                         ↓
                       vendor/
                         │
                         ↓
                vendor/autoload.php
                         │
                         ↓
                    tvoja aplikacija
```

Ako ovu sliku razumeš, kasnije će:

```text
require
install
update
lock
PSR-4
autoload
```

samo popuniti detalje.

## 12. Veza sa onim što smo upravo radili u OOP-u

Do sada smo praktično imali sve u jednom fajlu:

enum BookingStatus ...
class Booking ...
interface BookingRepository ...
class BookingService ...
class BookingController ...

To je dobro za učenje OOP-a.
Ali prava aplikacija hoće:

```text
src/
├── Controllers/
├── DTO/
├── Enums/
├── Http/
├── Repositories/
└── Services/
```

I onda nastaje problem:

Kako PHP zna gde je App\Services\BookingService?

Tu se spajaju:

```text
Namespaces
+
PSR-4
+
Composer autoload
```

i zato Composer modul dolazi tačno u pravom trenutku posle OOP-a.

## Šta želim da ti ostane iz Lekcije 1

Ako te sada neko pita:

Šta je Composer?

dobar odgovor bi bio otprilike:

Composer je dependency manager za PHP.
On rešava dependency graph i kompatibilne verzije paketa,
instalira ih uglavnom u vendor/, održava konkretno resolved stanje preko composer.lock,
a takođe generiše autoloading sistem kojim možemo
automatski učitavati third-party i sopstvene PHP klase.

To je već ozbiljniji odgovor od:

„Composer služi da instaliram pakete.“
