Lekcija 3/15 — composer require: šta se tačno dešava kada instaliraš dependency

Najkraće:
composer require dodaje dependency projektu, 
rešava kompatibilne verzije, 
instalira paket i ažurira Composer metadata fajlove.

Na primer:
composer require monolog/monolog

To nije samo:
„Skini Monolog.“

Ispod haube se dešava više koraka.
1. Composer pronalazi paket
Za:
composer require monolog/monolog

Composer traži paket:
vendor:
monolog

package:
monolog

najčešće preko Packagist-a.
Dakle:
monolog/monolog
→ package identifier

To nema veze sa PHP namespace-om koji će biblioteka koristiti.
2. Composer proverava dostupne verzije
Paket može imati verzije poput:
3.7.0
3.8.0
3.9.0
...

Composer zatim mora da izabere verziju koja je kompatibilna sa:
tvojim PHP-om
drugim dependencies
dependency zahtevima samog Monolog-a
postojećim composer.lock stanjem

Dakle opet radi dependency resolution.
3. composer require menja composer.json
Pre:
{
    "require": {
        "php": "^8.3"
    }
}

Pokreneš:
composer require monolog/monolog

Posle možeš dobiti nešto poput:
{
    "require": {
        "php": "^8.3",
        "monolog/monolog": "^3.0"
    }
}

Composer dakle zapisuje:
Ovaj projekat sada direktno zavisi od Monolog-a.

Monolog postaje direct dependency.
4. Composer rešava i transitive dependencies
Pretpostavimo:
monolog/monolog
↓ zavisi od
psr/log

Ti nisi direktno napisao:
composer require psr/log

ali Composer može instalirati i njega.
Mentalno:
tvoj projekat
    ↓
monolog/monolog       ← direct dependency
    ↓
psr/log               ← transitive dependency

Zato se u vendor/ često pojavi više paketa nego što si direktno tražio.
5. Composer ažurira composer.lock
Ovo je veoma važno.
composer.json može reći:
"monolog/monolog": "^3.0"

ali Composer u tom trenutku konkretno odabere recimo:
monolog/monolog 3.9.0
psr/log 3.0.2

Te konkretno resolved verzije idu u:
composer.lock

Dakle posle require često imaš:
composer.json
→ dozvoljeni requirement

composer.lock
→ konkretno izabrane verzije

6. Paketi se instaliraju u vendor/
Posle uspešne instalacije možeš dobiti:
vendor/
├── autoload.php
├── composer/
├── monolog/
│   └── monolog/
└── psr/
    └── log/

Dakle:
vendor/
→ third-party code

Tvoj application code ne treba da ide unutra.
Vrlo važno:
vendor/ nije mesto koje ručno uređuješ.

Ako odeš u:
vendor/monolog/...

i promeniš kod, sledeći Composer install/update može to da pregazi.
7. Composer regeneriše autoload
Na kraju Composer ažurira autoload metadata.
Zato posle:
composer require monolog/monolog

možeš imati:
require __DIR__ . '/vendor/autoload.php';

use Monolog\Logger;

Ne moraš ručno:
require 'vendor/monolog/monolog/src/Monolog/Logger.php';

Composer je već uključio taj package u autoload sistem.
Ceo flow
Dakle:
composer require monolog/monolog

mentalno znači:
1. pronađi paket
↓
2. pročitaj njegove requirements
↓
3. proveri moj projekat i platformu
↓
4. resolve dependency graph
↓
5. izaberi kompatibilne verzije
↓
6. izmeni composer.json
↓
7. izmeni composer.lock
↓
8. instaliraj u vendor/
↓
9. regeneriši autoload

To je mnogo više od „download package“.
Kako zadati verziju?
Možeš eksplicitno:
composer require monolog/monolog:^3.0

Time govoriš:
Želim Monolog koji zadovoljava ovaj constraint.

Možeš i:
composer require monolog/monolog:3.9.0

što je mnogo strože:
tačno 3.9.0

Version constraints ćemo detaljno tek u Lekciji 6, pa za sada samo mentalna razlika:
^3.0
→ dozvoli kompatibilne verzije

3.9.0
→ zahtevaj baš tu verziju

Više paketa odjednom
Composer može:
composer require package-a package-b package-c

i onda rešava njihov zajednički dependency graph.
To je bitno jer dva paketa mogu imati zajednički 
dependency sa različitim version constraints.

Composer mora naći kombinaciju koja zadovoljava sve.
Šta ako ne postoji kompatibilno rešenje?
Recimo:
package A
→ zahteva package C ^2

package B
→ zahteva package C ^3

a ne postoji način da istovremeno instaliraš obe potrebne verzije u tom dependency graph-u.
Composer može prijaviti conflict i odbiti instalaciju.
To je dobra stvar.
Bolje:
installation failed

nego da ti instalira nekonzistentan set dependencies koji će pucati u runtime-u.
require i platform requirements
Recimo paket zahteva:
PHP >= 8.4

a ti imaš:
PHP 8.3

Composer može reći da requirement nije zadovoljen.
Isto za extension:
ext-gd
ext-intl
ext-mbstring

Paket možda može da kaže:
"require": {
    "php": "^8.2",
    "ext-json": "*"
}

Composer proverava environment pre nego što potvrdi da dependency graph može da radi.
composer require bez postojećeg composer.json
Ako si u praznom folderu i uradiš:
composer require monolog/monolog

Composer može napraviti osnovni:
composer.json
composer.lock
vendor/

Dakle require nije rezervisan samo za već potpuno inicijalizovan projekat.

Ipak, u ozbiljnijem projektu često prvo napraviš smislen composer.json, 
pa onda dodaješ dependencies.
composer require vs ručno editovanje

Možeš ručno dodati:
"monolog/monolog": "^3.0"

u composer.json.
Ali onda paket još nije automatski instaliran samo zato što si sačuvao fajl.
composer.json je deklaracija.
Composer komanda je ta koja treba da uradi resolution/install posao.
Zato je praktično:
composer require monolog/monolog

jer Composer u jednom potezu:
upiše requirement
+
resolve
+
instalira
+
lockuje
+
regeneriše autoload

--dev
Ako dependency služi samo development-u:
composer require --dev phpunit/phpunit

onda ne ide u:
"require"

nego u:
"require-dev"

Dakle:
composer require monolog/monolog

→ runtime dependency
composer require --dev phpunit/phpunit

→ development dependency
Sledeća lekcija je upravo tome posvećena.
Praktičan primer sa našim MiniStay projektom
Recimo želimo logging.
Pokrenemo:
composer require monolog/monolog

Posle možemo imati:
MiniStay/
├── composer.json
├── composer.lock
├── src/
├── public/
└── vendor/

I u composer.json:
{
    "require": {
        "php": "^8.3",
        "monolog/monolog": "^3.0"
    }
}

A u PHP-u:
require __DIR__ . '/../vendor/autoload.php';

use Monolog\Logger;

Composer je obezbedio dependency i autoload.
Mentalna mapa Lekcije 3
composer require package/name
↓
package postaje direct dependency
↓
Composer rešava transitive dependencies
↓
proverava compatibility
↓
composer.json se menja
↓
composer.lock se ažurira
↓
paketi idu u vendor/
↓
autoload se regeneriše

I važna rečenica:
composer require ne instalira samo paket — on menja dependency model celog projekta.

Lekcija 3/15 završena.
