# 15. Composer workflow

## Lekcija 15/15 — Praktičan Composer workflow

Cilj ove lekcije je da Composer više ne gledaš kao skup nepovezanih komandi,
nego kao svakodnevni workflow.
Mentalno:

```text
napravi projekat
↓
definiši dependencies
↓
instaliraj ih
↓
proveravaj stanje
↓
bezbedno update-uj
↓
ukloni ono što ne treba
↓
proveri security + platform
↓
deployuj reproducibilno
```

1. composer init
Ako krećeš od praznog Vanilla PHP projekta:

```bash
composer init
```

Composer te interaktivno vodi kroz kreiranje:

composer.json

Pita stvari poput:

```text
package name
description
author
dependencies
autoload
```

Ne moraš koristiti init — možeš ručno napraviti composer.json.
Ali za novi projekat je zgodan bootstrap.
2. composer validate
Jedna od korisnijih komandi:

```bash
composer validate
```

Proverava:

```text
da li je composer.json validan
da li su struktura i constraints smisleni
da li je composer.lock usklađen sa composer.json
```

Composer dokumentacija čak preporučuje validate pre commitovanja
composer.json/lock fajla i pre release-a.

Na primer:

```json
{
    "require": {
        "php": "^8.3",
    }
}
```

ima trailing comma, što nije validan JSON.

```bash
composer validate će pomoći da to uhvatiš.
```

Mentalno:

```text
composer validate
→ da li je Composer konfiguracija zdrava?
```

3. composer show
Ako želiš da vidiš šta je instalirano:

```bash
composer show
```

Dobićeš listu paketa.
Na primer:

monolog/monolog
psr/log
phpunit/phpunit
...

Za konkretan paket:

```bash
composer show monolog/monolog
```

možeš videti podatke poput:

```text
verzija
description
license
requirements
autoload metadata
```

Dakle kada se pitaš:

Koju verziju zapravo trenutno imam?

ne moraš ručno kopati kroz vendor/.

```bash
composer show vendor/package
```

---

## 4. Direct vs transitive dependencies u praksi

Recimo composer.json sadrži:

```json
"require": {
    "monolog/monolog": "^3.0"
}
```

ali:

```bash
composer show
```

prikaže i:

psr/log

---

## Zašto?

Jer:

```text
MiniStay
↓
monolog/monolog
↓
psr/log
```

Monolog je direct dependency.
psr/log može biti transitive dependency.
Ovo je ista dependency graph priča koju smo radili od prve lekcije.
5. composer why
Ovo je odlična debugging komanda.
Pitaš:

composer why psr/log

odnosno:

Zašto je ovaj package uopšte instaliran?

Composer ti pokaže package koji ga zahteva.
Mentalno:

```text
psr/log je u vendor/
↓
zašto?
↓
composer why psr/log
↓
neki drugi package ga zahteva
```

Ovo je posebno korisno kada vendor/ ima 70 paketa, a ti si direktno instalirao samo 10.
6. composer why-not
Suprotna situacija:

Zašto ne mogu da instaliram verziju X?

Možeš koristiti:

composer why-not vendor/package 4.0

ili ekvivalentni prohibits command.
Composer ti može pokazati:

```text
package A zahteva <4.0
package B zahteva ^3.0
```

i odmah vidiš dependency conflict.
Ovo je mnogo bolje od nasumičnog menjanja constraints dok Composer konačno ne prestane da se žali.
7. composer outdated
Ovo ti pokazuje pakete za koje postoje novije verzije:

composer outdated

Na primer:

```text
package/a    2.4.1    2.7.0
package/b    1.3.0    2.0.0
```

Ali pazi:

outdated ne znači automatski „odmah update-uj sve“.

Ako vidiš:

```text
1.3 → 2.0
```

to može biti major upgrade sa breaking promenama.
Za direct dependencies posebno možeš koristiti:

composer outdated --direct

što je zgodno jer prvo vidiš ono što si ti eksplicitno dodao projektu. Composer podržava i filtriranje na minor/patch nivoe. getcomposer.org

---

## 8. Kako bih ja koristio outdated

Periodično:

composer outdated --direct

onda pogledam:

koji package je zastareo?
da li je patch/minor/major?
ima li security problem?
šta kaže changelog?

Tek onda:

```bash
composer update vendor/package
```

Dakle:

```text
outdated
→ informacija
```

```text
update
→ odluka
```

Nemoj ih mentalno spojiti u:

```text
ima novija verzija → odmah update
```

9. composer audit
Ovo je danas vrlo važna komanda:

```bash
composer audit
```

Koristi se za proveru dependency security stanja, uključujući security advisories, a Composer može prijavljivati i abandoned packages u skladu sa konfiguracijom. Aktuelni Composer ima i širi dependency policy sistem za advisories, abandoned packages i druge rizike. getcomposer.org
Mentalno:

```text
composer audit
→ da li moj dependency set ima poznate probleme?
```

Ako dobiješ advisory:

Package X
Affected versions: ...
CVE/GHSA/PKSA...

ne znači automatski:

Aplikacija je ovog trenutka hakovana.

Znači:

Koristiš dependency/version za koji postoji poznat security problem i treba proceniti/update-ovati.

10. audit nije zamena za update strategiju
Nije dovoljno:

```bash
composer audit
```

i ako je danas čist:

Gotovi smo zauvek.

Novi security advisories mogu izaći sutra.
Zato dependency maintenance postoji kao kontinuirana aktivnost:

```text
outdated
+
audit
+
changelog
+
testovi
+
kontrolisani update
```

11. composer remove
Ako package više ne treba:

```bash
composer remove monolog/monolog
```

Composer uklanja requirement iz composer.json, ažurira dependency graph/lock i uklanja packages koji više nisu potrebni. getcomposer.org
Dakle nemoj:

ručno obrisati vendor/monolog

To ne rešava dependency model.
Ispravno:

```bash
composer remove vendor/package
```

Mentalno:

```text
require
→ uvedi dependency u graph
```

```text
remove
→ ukloni dependency iz graph-a
```

---

## 12. A šta sa transitive dependency-jem?

Recimo:

```text
MiniStay
↓
Package A
↓
Package B
```

Ukloniš:

```bash
composer remove package/a
```

Ako više nijedan package ne zahteva B, Composer može ukloniti i B.
Ali ako imaš:

```text
Package C
↓
Package B
```

onda B ostaje.
Composer ne gleda:

Koji folder da obrišem?

nego:

Kakav dependency graph sada treba da postoji?

13. composer check-platform-reqs
Ova komanda je veoma korisna za deployment:

composer check-platform-reqs

Proverava da li stvarna PHP verzija i extensions trenutnog sistema zadovoljavaju platform requirements instaliranih paketa. Za razliku od install/update resolution-a, proverava realnu platformu. getcomposer.org
Na primer projekat zahteva:

```json
"require": {
    "php": "^8.3",
    "ext-pdo": "*",
    "ext-mbstring": "*"
}
```

Server ima:

```text
PHP 8.3 ✅
PDO ✅
mbstring ❌
```

onda:

composer check-platform-reqs

može uhvatiti problem pre nego što aplikacija krene da puca u runtime-u.

---

## 14. Ovo je posebno dobro na produkciji

Deployment može konceptualno imati:

```bash
composer install --no-dev --optimize-autoloader
```

composer check-platform-reqs

Ako platform requirements nisu zadovoljeni:

abort deploy

Mnogo bolje nego:

deploy ✅

```text
prvi korisnik otvori stranicu
↓
```

Call to undefined function ...

Composer dokumentacija upravo navodi check-platform-reqs kao korisnu production/build proveru. getcomposer.org

---

## 15. Oprez sa --ignore-platform-reqs

Sigurno si video:

```bash
composer install --ignore-platform-reqs
```

To praktično kaže Composer-u:

Ignoriši PHP/extension compatibility requirements.

Može biti korisno u vrlo specifičnim situacijama, ali nije „fix“.
Ako package stvarno zahteva:

ext-intl

a ti ga nemaš, ignorisanje Composer provere ne stvara intl extension iz vazduha.
Dakle:

```text
--ignore-platform-reqs
→ preskoči proveru
```

```text
nije
→ popravi platformu
```

To je česta loša navika:

Composer se žali?

```text
→ --ignore-platform-reqs 😄
```

Isto kao što smo rekli za dump-autoload: razumi problem pre komande.
16. composer diagnose
Još jedna zgodna pomoćna komanda:

composer diagnose

Može proveriti Composer environment/config i prijaviti probleme.
Nije nešto što ćeš pokretati svaki dan, ali kada Composer čudno radi, korisno je znati da postoji.
17. composer update — sada sa punim mentalnim modelom
Posle celog modula više ga ne vidiš kao:

update package

nego:

```text
pročitaj composer.json constraints
↓
ponovo resolve dependency graph
↓
izaberi dozvoljene verzije
↓
promeni composer.lock
↓
instaliraj novi dependency state
↓
regeneriši autoload
```

Zato je često pametnije:

```bash
composer update monolog/monolog
```

nego:

```bash
composer update
```

ako želiš da promeniš samo određeni deo dependency seta.

## 18. Praktičan development workflow

Recimo kloniraš projekat:

git clone ...

```bash

```

---

## Zašto install?

Jer želiš:

```text
composer.lock
→ isti dependency state
```

Zatim razvijaš.
Treba ti novi runtime package:

```bash
composer require vendor/package
```

Treba ti test package:

```bash
composer require --dev phpunit/phpunit
```

Proveravaš:

```bash
composer validate
composer audit
```

I commit:

```text
composer.json
composer.lock
source code
```

## 19. Workflow kada želiš update jednog dependency-ja

Recimo:

composer outdated --direct

vidiš:

```text
monolog/monolog 3.8 → 3.9
```

Proveriš release notes.
Onda:

```bash
composer update monolog/monolog
```

Posle:

```text
pokreni testove
↓
composer audit
↓
pregledaj diff composer.lock
↓
commituj promenu
```

Ovo je kontrolisan dependency upgrade.

## 20. Production workflow

Tipično želiš nešto približno:

```bash
composer install --no-dev --optimize-autoloader
```

---

## Zašto?

```text
install
→ koristi lock
```

```text
--no-dev
→ bez dev dependencies
```

```text
--optimize-autoloader
→ production-friendly optimized autoload
```

Composer -o/--optimize-autoloader pretvara PSR-0/4 resolution u optimizovaniju classmap formu i Composer ga posebno preporučuje za production use. getcomposer.org
Zatim možeš:

composer check-platform-reqs

## 23. BookingService.php

Fajl:

src/Services/BookingService.php

```php
<?php

namespace App\Services;

use App\Contracts\BookingRepository;
use App\DTO\CreateBookingData;
use App\Enums\BookingStatus;
use App\Models\Booking;

final class BookingService
{
    public function __construct(
        private BookingRepository $bookings
    ) {}

    public function create(CreateBookingData $data): Booking
    {
        $booking = new Booking(
            1,
            $data->roomId,
            BookingStatus::Pending
        );

        $this->bookings->save($booking);

        return $booking;
    }
}
```

I sada se ceo prethodni OOP modul spojio sa Composer modulom.

## 24. Front Controller

public/index.php:

```php
<?php

require __DIR__ . '/../vendor/autoload.php';

use App\Controllers\BookingController;
use App\Http\CreateBookingRequest;
use App\Http\Request;
use App\Repositories\InMemoryBookingRepository;
use App\Services\BookingService;

$repository = new InMemoryBookingRepository();

$service = new BookingService($repository);

$controller = new BookingController($service);

$request = new Request($_POST);

$formRequest = new CreateBookingRequest($request);

$booking = $controller->store($formRequest);
```

Pogledaj šta više nemamo:

```php
require '../src/DTO/CreateBookingData.php';
require '../src/Models/Booking.php';
require '../src/Services/BookingService.php';
require '../src/Controllers/BookingController.php';
```

...

Samo:

```php
require __DIR__ . '/../vendor/autoload.php';
```

I Composer + namespaces + PSR-4 rešavaju ostalo.
To je ogromna poenta celog modula.
