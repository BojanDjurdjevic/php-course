# 7. Composer install VS update

## Lekcija 7/15 — composer install vs composer update

Najvažnija razlika je:

```text
composer install
→ instalira već resolved verzije iz composer.lock
```

```text
composer update
→ ponovo rešava version constraints iz composer.json
→ bira nove dozvoljene verzije
→ menja composer.lock
```

To je srž cele lekcije.

---

## 1. Situacija: klonirao si projekat

Recimo Git repo sadrži:

```text
composer.json
composer.lock
src/
public/
```

ali nema:

vendor/

što je normalno — vendor/ se najčešće ne commituje.
Ti uradiš:

```bash
composer install
```

Composer vidi:

composer.lock postoji

i kaže:

Odlično. Neko je već rešio dependency graph. Instaliraću baš te konkretne verzije.

Recimo composer.json kaže:

```json
"monolog/monolog": "^3.0"
```

što dozvoljava mnogo 3.x verzija.
Ali composer.lock kaže:

monolog/monolog 3.9.0

```bash
composer install će instalirati:
```

3.9.0

Neće reći:

Hmm, možda je izašao 3.10.0, hajde njega.

To nije njegov posao.

---

## 2. Zašto je ovo toliko važno?

Zamisli nas dvojica radimo isti projekat.
Kod mene:

```text
composer.lock
→ Package A 2.5.4
→ Package B 3.1.7
```

Commitujem:

```text
composer.json
composer.lock
```

Ti kloniraš repo i radiš:

```bash
composer install
```

dobijaš:

```text
Package A 2.5.4
Package B 3.1.7
```

I produkcija kada deployuje:

```bash
composer install --no-dev
```

dobija iste production dependency verzije.
Mentalno:

```text
Developer A
      │
composer.lock
      │
      ├──── Developer B
      │
      ├──── CI
      │
      └──── Production
```

svi koriste isti resolved dependency set

To je reproducible installation.

---

## 3. A šta radi composer update?

Pretpostavimo:

```json
"vendor/package": "^2.4"
```

A composer.lock trenutno ima:

2.5.1

U međuvremenu su izašli:

```text
2.6.0
2.7.3
2.9.0
```

Sve njih ^2.4 dozvoljava.
Ako uradiš:

```bash
composer install
```

dobijaš:

2.5.1

jer je to lockovana verzija.
Ako uradiš:

```bash
composer update
```

Composer kaže:

Hajde da ponovo rešim dependency graph prema composer.json.

Može onda izabrati:

2.9.0

i promeniti:

```text
composer.lock
2.5.1
↓
2.9.0
```

---

## 4. Zato update nije sinonim za install

Ovo je česta greška:

Nemam vendor/, pa ću composer update.

Ne.
Ako projekat već ima validan composer.lock, time si možda promenio dependency set celog projekta bez ikakve potrebe.
Na kloniranom projektu:

```bash
composer install
```

je normalan izbor.
update koristiš kada namerno želiš da promeniš resolved dependency verzije.

---

## 5. Mentalni model

```text
composer.json
→ ŠTA JE DOZVOLJENO
```

```text
composer.lock
→ ŠTA JE IZABRANO
```

Sada:

```text
composer install
→ poštuj IZABRANO
```

```text
composer update
→ ponovo biraj iz DOZVOLJENOG
```

Ako zapamtiš samo ovo, već razumeš razliku.

---

## 6. Šta ako composer.lock ne postoji?

Ako uradiš:

```bash
composer install
```

a nema composer.lock, Composer nema resolved snapshot koji bi mogao da reprodukuje.
Tada mora da pročita constraints iz:

composer.json

resolve-uje dependencies i napravi novi:

composer.lock

Dakle prvi install novog projekta konceptualno mora da uradi resolution.
Ali kada lock postoji:

```text
install
→ lock je autoritet za konkretne verzije
```

---

## 7. Šta se commituje u Git?

Za običnu aplikaciju:

```text
composer.json ✅
composer.lock ✅
```

vendor/ ❌ obično

---

## Zašto composer.lock commitujemo?

Da bi:

```text
lokalni development
CI
staging
production
```

imali iste konkretne dependency verzije.
Ovo je posebno važno za applications.
Kod library package-a priča oko lock fajla ima dodatne nijanse, ali za naše PHP/Laravel aplikacije zapamti:

composer.lock se commituje.

8. Primer
Imamo:

```json
{
    "require": {
        "vendor/package": "^2.4"
    }
}
```

A lock:

vendor/package = 2.6.3

Dostupne verzije:

```text
2.6.3
2.7.0
2.8.4
3.0.0
```

```bash
composer install
```

2.6.3

jer tako kaže lock.

```bash
composer update
```

Composer ponovo proverava constraint:

```text
^2.4
→ >=2.4 <3.0
```

pa može izabrati:

2.8.4

i upisati ga u novi lock.
3.0.0 neće jer ga constraint ne dozvoljava.

---

## 9. Ne moraš update-ovati sve

Ovo je veoma korisno.
Umesto:

```bash
composer update
```

možeš:

```bash
composer update monolog/monolog
```

Tada kažeš:

Želim prvenstveno update ovog dependency-ja, ne kompletnog projekta.

To je često mnogo bezbednije.
Možeš i više:

```bash
composer update package/a package/b
```

10. composer require je povezan sa update
Kada radiš:

```bash
composer require monolog/monolog
```

Composer mora da:

```text
doda requirement
+
resolve dependency graph
+
ažurira lock
+
instalira
```

Zato require nije isto kao običan install.
Menja dependency model projekta.

---

## 11. Tipičan Git workflow

Ti radiš lokalno i želiš novi package:

```bash
composer require some/package
```

Promene:

```text
composer.json
composer.lock
```

Commituješ oba.
Kolega:

```text
git pull
composer install
```

I dobija dependency koji si ti već resolvedovao.
Ne treba da radi:

```bash
composer update
```

jer bi potencijalno dobio nešto drugo od onoga što si ti testirao.

---

## 12. Production workflow

Vrlo čest deployment:

```bash
composer install --no-dev
```

Često uz dodatne production opcije koje ćemo kasnije pomenuti.

---

## Zašto install, a ne update?

Jer ne želiš da deploy kaže:

Baš danas je izašla nova verzija biblioteke — hajde spontano da je ubacimo u produkciju. 😄

Želiš:

deploy exactly what was tested

odnosno lockovane verzije.

---

## 13. Scenario koji treba da izbegneš

Lokalno si testirao:

Package X 4.2.1

Ali na serveru uradiš:

```bash
composer update
```

Server resolve-uje:

Package X 4.5.0

jer ga composer.json dozvoljava.
Ako 4.5.0 ima bug koji pogađa tvoj kod:

```text
local ✅
production ❌
```

I onda se pitaš:

Kako produkcija puca, a isti commit je?

Odgovor:

Nije isti dependency set.

Zato postoji lock.
14. install ne znači "nikad ništa ne proverava"
Composer i dalje proverava da trenutni environment može da zadovolji lockovani paket.
Recimo lock zahteva:

```text
PHP >= 8.3
ext-mbstring
```

a server ima:

PHP 8.2

```bash
composer install može da se pobuni.
```

Lock kaže koje package verzije, ali platforma i dalje mora biti kompatibilna s njima.

---

## 15. Šta ako ručno promenim composer.json, ali ne lock?

Na primer lock je napravljen za:

```json
"package/a": "^2.0"
```

a ti ručno promeniš:

```json
"package/a": "^3.0"
```

i zatim radiš:

```bash
composer install
```

Composer može upozoriti da lock file više nije u skladu sa trenutnim composer.json.
To ima smisla:

```text
composer.json
→ traži jedno
```

```text
composer.lock
→ resolved iz stare konfiguracije
```

Treba ponovo napraviti odgovarajući resolution, obično kroz odgovarajući composer update/require workflow.
Zato je često lepše koristiti Composer komande nego nasumično ručno menjati dependency requirements.

---

## 16. Ovo što ti već radiš posle clone-a

Dakle kada kažeš:

„Kada kloniram projekat često kažem composer install“

to je upravo pravilno.
Flow:

git clone ...
cd project

```bash
composer install
```

mentalno:

```text
repo
↓
composer.json + composer.lock
↓
composer install
↓
rekonstruiši vendor/
↓
koristi iste dependency verzije kao projekat
```

vendor/ praktično možeš gledati kao generisani rezultat Composer dependency metadata-e.
Zato ga ne moraš nositi kroz Git.

---

## Najvažnija tabela

```text
Komanda	Čita composer.lock	Ponovo resolve-uje dozvoljene verzije	Menja lock
composer install	Da, ako postoji	Ne u normalnom locked workflow-u	Ne
composer update	Ne koristi ga kao fiksni snapshot	Da	Da
```

A jedna rečenica za intervju:

```bash
composer install reprodukuje dependency verzije iz composer.lock,
```

dok composer update ponovo rešava constraints iz composer.json i ažurira lock file.

To je odličan odgovor.
