# 12. Brute Force, Enumeration & Abuse Protection — Part 1

## 1. Šta je brute force

Brute force znači:

```text
attacker
↓
mnogo pokušaja
↓
pokušava da pogodi secret
```

Na primer:

```text
password
PIN
reset code
OTP
API key
```

Kod login-a:

```text
email poznat
↓
password1
password2
password3
...
```

Cilj je:

```text
pogoditi credential
```

---

## 2. Brute force nije isto što i credential stuffing

Credential stuffing koristi:

```text
već poznate kombinacije
email + password
```

koje su procurele sa drugih servisa.

Attacker ne pokušava:

```text
milion password-a za jednog user-a
```

nego:

```text
milion već poznatih credential parova
nad velikim brojem account-a
```

Mentalno:

```text
Brute force
→ mnogo password-a
  protiv account-a

Credential stuffing
→ mnogo poznatih credential parova
  protiv mnogo account-a
```

Zato zaštita samo:

```text
5 pokušaja po email-u
```

nije dovoljna za svaki attack pattern.

---

## 3. Password spraying

Treći pattern:

```text
jedan ili mali broj čestih password-a
↓
mnogo account-a
```

Na primer attacker proba:

```text
Winter2026!
```

na velikom broju email adresa.

To je:

```text
password spraying
```

Prednost za attacker-a:

```text
ne pravi mnogo pokušaja
na jednom account-u
```

pa može pokušati da zaobiđe simple per-account lockout.

---

## 4. Rate limiting

Rate limiting znači:

> Ograniči koliko operacija određeni caller ili identifier može izvršiti u određenom vremenskom periodu.

Na primer:

```text
5 login pokušaja
u 1 minutu
po IP adresi
```

ili:

```text
10 pokušaja
u 15 minuta
po account identifier-u
```

Mentalno:

```text
key
+
window
+
limit
```

---

## 5. Jedan rate-limit key nije dovoljan za sve

Ako limitiramo samo:

```text
IP
```

problem:

```text
cela firma
NAT
mobile carrier
shared network
```

može deliti isti IP.

Jedan attacker može napraviti problem svim legitimnim user-ima.

Ako limitiramo samo:

```text
email
```

attacker može pokušavati:

```text
mnogo različitih account-a
```

Zato ozbiljniji sistem može kombinovati:

```text
IP
account/email
device/session signal
global endpoint limit
```

Ne mora svaki projekat imati sve.

Ali mentalni model je:

```text
attack može menjati dimenziju
```

---

## 6. Fixed window primer

Jednostavan model:

```text
key:
login:ip:203.0.113.10

count:
4

window:
60 seconds
```

Ako broj pređe:

```text
5
```

odbijamo request dok window ne istekne.

Konceptualno:

```php
if (
    $limiter->tooManyAttempts(
        $key,
        5
    )
) {
    throw new TooManyRequestsException();
}
```

---

## 7. HTTP 429

Za rate limit failure često koristimo:

```text
429 Too Many Requests
```

Response može sadržati:

```text
Retry-After
```

ili application-specific informaciju o retry periodu.

Bitno:

```text
rate limited
≠ server error 500
```

---

## 8. Throttling vs permanent lockout

Throttling:

```text
previše pokušaja
↓
uspori / privremeno blokiraj
↓
kasnije ponovo dozvoli
```

Permanent lockout:

```text
previše pokušaja
↓
account zaključan
dok admin/user ne interveniše
```

Za običan login permanent lockout je često problematičan.

Zašto?

Attacker može namerno unositi pogrešan password za:

```text
victim@example.com
```

i zaključati žrtvin account.

To postaje:

```text
Denial of Service
```

---

## 9. Progressive throttling

Bolji model može biti:

```text
prvih nekoliko neuspeha
→ normalno

zatim
→ 10 sec delay

zatim
→ 30 sec

zatim
→ 1 min

zatim
→ duži cooldown
```

To je:

```text
progressive throttling
```

Cilj:

```text
attacker-u postaje preskupo
automatizovati pokušaje
```

dok legitiman user i dalje može da se oporavi.

---

## 10. Nemoj koristiti `sleep()` kao glavni rate limiter

Možda deluje lako:

```php
sleep(5);
```

posle failed login-a.

Ali sada svaki attack request može držati PHP worker zauzet.

Attacker može napraviti:

```text
mnogo paralelnih request-a
```

i iscrpeti worker pool.

Dakle:

```text
sleep()
→ može sam postati resource exhaustion problem
```

Bolje:

```text
centralni limiter
Redis/cache/database counter
reject brzo sa 429
```

---

## 11. Distributed rate limiting

Ako aplikacija ima više server instanci:

```text
Server A
Server B
Server C
```

local memory limiter na Server A ne zna šta se dogodilo na Server B.

Zato shared storage poput:

```text
Redis
```

često ima smisla.

Mentalno:

```text
multiple app nodes
↓
shared limiter state
```

Za malu Vanilla PHP aplikaciju ovo možda nije potrebno odmah.

Ali arhitektonski treba razumeti problem.

---

## 12. Login enumeration

Pretpostavimo login response:

Za nepostojeći email:

```text
User not found.
```

Za postojeći email + pogrešan password:

```text
Incorrect password.
```

Attacker sada može testirati:

```text
alice@example.com
bob@example.com
ceo@example.com
```

i saznati:

```text
ko ima account
```

To je:

```text
account enumeration
```

---

## 13. Generic login response

Bolje:

```text
Invalid credentials.
```

za oba slučaja:

```text
user ne postoji
```

i:

```text
password pogrešan
```

Interno sistem zna razliku.

Javni response ne mora.

Mentalno:

```text
internal truth
≠ public information
```

---

## 14. Timing može takođe otkriti informacije

Zamisli:

Ako user ne postoji:

```text
odmah return false
```

Ako postoji:

```text
password_verify()
```

koji je namerno relativno skup.

Napadač može pokušati da meri vreme response-a.

Ako postoji stabilna razlika:

```text
account existence
```

može procuriti i bez različite poruke.

---

## 15. Dummy password hash

Jedan pristup:

Ako user ne postoji, ipak odradimo:

```php
password_verify(
    $password,
    $dummyHash
);
```

gde je `$dummyHash` validan hash koji aplikacija već ima kao konstantu/config vrednost.

Cilj:

```text
postojeći user
i
nepostojeći user
```

imaju približniji computational path.

Ne garantuje savršeno konstantno vreme.

Ali smanjuje očiglednu timing razliku.

---

## 16. Password reset enumeration

Loše:

```text
Email not found.
```

na forgot-password endpoint-u.

Attacker sada može proveravati ko ima account.

Bolje:

```text
If an account exists for that email,
we have sent password reset instructions.
```

bez obzira na to da li account stvarno postoji.

---

## 17. Ali backend ponašanje ipak može biti različito

Ako user postoji:

```text
generate token
store hashed token
send email
```

Ako ne postoji:

```text
ne šalji ništa
```

Public response je isti.

Ali opet treba paziti da:

```text
response time
```

ne bude ekstremno različit.

U praksi može pomoći:

```text
queue email sending
```

jer HTTP response ne mora čekati stvarni SMTP roundtrip.

---

## 18. Registration enumeration

Registration endpoint može reći:

```text
Email already registered.
```

To tehnički otkriva account existence.

Da li je to prihvatljivo?

Zavisi od proizvoda.

Neke aplikacije namerno dozvoljavaju tu informaciju zbog UX-a.

Druge žele da je sakriju.

Security nije:

```text
uvek ista univerzalna odluka
```

nego:

```text
rizik
vs
UX
vs
business requirement
```

Ali odluka mora biti svesna.

---

## 19. Email verification abuse

Endpoint:

```text
POST /resend-verification
```

može biti zloupotrebljen za:

```text
spam
mail cost
harassment
provider reputation damage
```

Zato i njega treba throttlovati.

Na primer:

```text
1 resend / 60 sec
5 / hour
```

uz odgovarajući user/account key.

---

## 20. Password reset spam

Isto:

```text
forgot password
```

nije opasan samo zbog token security-ja.

Attacker može slati:

```text
hiljade reset emailova
```

žrtvi.

Zato reset endpoint treba:

```text
rate limiting
+
generic response
```

---

## 21. Login rate limiting ne treba čekati DB write na svaki pokušaj

Loš dizajn:

```text
svaki failed login
↓
INSERT novi row
↓
DB write storm
```

pod attack load-om može postati problem.

Zato sistemi često koriste:

```text
cache
Redis
efficient counters
```

za high-frequency abuse state.

Database može raditi za male sisteme.

Ali treba razumeti tradeoff.

---

## 22. Rate limit key

Primer:

```php
$key =
    'login:'
    . hash(
        'sha256',
        strtolower($email)
        . '|'
        . $ip
    );
```

Važna stvar:

Ne moraš nužno čuvati raw email u limiter key-u/log-u.

Možeš koristiti:

```text
normalized identifier
+
hash
```

ako ti treba privacy-friendly key.

---

## 23. Normalizuj identifier pre limitiranja

Ako login email tretiraš kao:

```text
case-insensitive
```

onda:

```text
User@Example.com
user@example.com
USER@EXAMPLE.COM
```

ne treba da budu tri odvojena rate-limit bucket-a.

Dakle:

```text
normalize
↓
rate-limit key
```

Isti canonicalization policy kao u auth modulu.

---

## 24. IPv6 i IP key

IP rate limiting ima praktične nijanse.

Nemoj praviti security arhitekturu na pretpostavci:

```text
jedan čovek = jedan IP
```

To nije tačno.

IP je:

```text
signal
```

ne pouzdan identitet.

Zato:

```text
IP limiter
+
account limiter
```

često daje bolji model.

---

## 25. Trusted proxy i real client IP

Ako aplikacija stoji iza:

```text
Cloudflare
Nginx
load balancer
reverse proxy
```

direktni remote IP PHP-a može biti:

```text
IP proxy-ja
```

Ne client-a.

Postoje forwarded headers.

Ali kao u prethodnoj lekciji:

```text
ne veruj forwarded header-u
od arbitrary client-a
```

Samo trusted proxy infrastruktura sme da utiče na real client IP resolution.

# 12. Brute Force, Enumeration & Abuse Protection — Part 2

## 26. Abuse protection nije samo login

Rate limiting ima smisla i za:

```text
registration
password reset
email verification resend
contact form
search
file upload
comments
API calls
expensive reports
export
SMS sending
webhook test endpoint
```

Pitanje:

> Koju operaciju attacker može jeftino da ponovi, a meni je skupa ili štetna?

To je abuse model.

---

## 27. Expensive endpoint

Na primer:

```text
GET /reports/generate
```

pokreće:

```text
velik SQL query
PDF generation
storage write
email
```

Čak i authenticated user može spamovati endpoint.

Zato authorization nije dovoljna.

Možda treba:

```text
rate limit
queue
idempotency
job deduplication
```

---

## 28. Rate limiting i authorization rešavaju različite probleme

Authorization:

```text
Da li user SME?
```

Rate limiting:

```text
Koliko često SME?
```

Primer:

User ima pravo da šalje invitation email.

Ali ne mora imati pravo da šalje:

```text
100000 emailova / minut
```

Dakle:

```text
authorized
≠ unlimited
```

---

## 29. Rate limiting i CSRF rešavaju različite probleme

CSRF:

```text
Da li je request legitimno nastao
u session context-u?
```

Rate limiting:

```text
Koliko puta može biti ponovljen?
```

Attacker sa XSS-om ili compromised account-om može imati potpuno validan:

```text
CSRF token
```

ali abuse limit i dalje može ograničiti štetu.

---

## 30. Rate limiting i idempotency

Payment endpoint:

```text
POST /payments
```

može imati:

```text
rate limiting
```

ali dva request-a unutar dozvoljenog limita i dalje mogu napraviti duplu naplatu.

Zato:

```text
Rate limit
→ frequency control

Idempotency
→ duplicate operation control
```

Različita pravila.

---

## 31. CAPTCHA

CAPTCHA može biti dodatna zaštita nakon suspicious behavior-a.

Na primer:

```text
više neuspelih login pokušaja
↓
CAPTCHA challenge
```

Ali CAPTCHA nije idealna kao:

```text
prva i jedina zaštita
```

zbog:

```text
UX
accessibility
automation bypass
external dependency
```

Bolji mentalni model:

```text
CAPTCHA
→ step-up anti-abuse control
```

---

## 32. Risk-based response

Sistem može povećavati zaštitu kada vidi:

```text
nov IP
mnogo pokušaja
promenu uređaja
neobično ponašanje
```

Na primer:

```text
normal
→ login

suspicious
→ CAPTCHA

više suspicious
→ cooldown

high risk
→ email verification / re-auth
```

To je:

```text
risk-based authentication
```

Za naš Vanilla PHP kurs ne moramo graditi kompleksan risk engine.

Ali treba razumeti koncept.

---

## 33. Account lock notification

Ako postoji mnogo neuspelih pokušaja, možemo user-u poslati:

```text
security notification
```

Ali i tu treba paziti da attacker ne može izazvati:

```text
notification spam
```

Dakle čak i security notification može zahtevati throttling.

---

## 34. Logging failed login-a

Korisno je logovati:

```text
failed login event
request_id
account identifier hash
IP/risk metadata
timestamp
```

Ali ne:

```text
password
password hash
session ID
reset token
remember validator
```

Nikad ne loguj credential koji je user pokušao.

Čak ni pogrešan password.

---

## 35. Ne loguj "password was X"

Ovo:

```php
$logger->warning(
    'Login failed',
    [
        'email' => $email,
        'password' => $password,
    ]
);
```

je ozbiljna greška.

Zašto?

User možda koristi isti password drugde.

Logovi su često dostupni većem broju sistema i ljudi nego production DB.

Security princip:

```text
logs
→ observability

ne:
credential storage
```

---

## 36. Username/email privacy u logovima

Čak i email može biti:

```text
PII
```

Zato sistem može odlučiti da loguje:

```text
user_id
hashed identifier
request_id
```

umesto punog email-a.

Koliko logovati zavisi od:

```text
incident response potreba
privacy zahteva
product architecture
```

---

## 37. Generic public response, detailed internal log

Public:

```text
Invalid credentials.
```

Internal log:

```text
login failed
known account: true
reason: password mismatch
request_id: abc
```

ako business/privacy policy dozvoljava taj nivo detalja.

Opet:

```text
internal truth
≠ public response
```

---

## 38. Reset token attempt limiting

Password reset endpoint:

```text
POST /reset-password
```

prima:

```text
token
new password
```

Attacker možda pokuša da brute-force-uje token ako je token slab.

Zato primarna zaštita mora biti:

```text
cryptographically strong token
```

na primer:

```php
random_bytes(...)
```

Rate limiting je dodatni sloj.

Mentalno:

```text
strong secret
+
expiry
+
single use
+
rate limiting
```

---

## 39. OTP je drugačiji slučaj

Ako koristiš:

```text
6-digit OTP
```

imaš samo:

```text
1,000,000 mogućnosti
```

što nije ogromna entropy.

Zato OTP obavezno zahteva:

```text
short expiration
attempt limit
rate limiting
single-use semantics
```

Ne možeš se osloniti samo na:

```text
random 6 digits
```

---

## 40. Reset link token ima mnogo veću entropy

Ako generišemo:

```php
bin2hex(
    random_bytes(32)
);
```

dobijamo veoma veliki search space.

To znači:

```text
brute-force token
→ praktično neizvodljiv
```

ako je implementation dobar.

Ali i dalje želimo:

```text
expiry
single-use
rate limiting
secure storage
```

Defense in depth.

---

## 41. Token storage

Reset token ne treba nužno čuvati kao raw token u DB.

Bolje:

```text
user dobije raw token
↓
DB čuva hash
```

Kad user vrati token:

```text
hash received token
↓
compare sa stored hash
```

Ako DB procure:

```text
raw active reset token-i
```

nisu odmah dostupni.

---

## 42. Enumeration kroz HTTP status

Nije samo poruka.

Ako:

```text
unknown email
→ 404

known email
→ 200
```

attacker i dalje enumerira account-e.

Ako želiš sakriti existence:

```text
isti status
+
isti public message
```

za oba scenarija.

## 43. Enumeration kroz response body shape

Čak i:

```json
{"success": true}
```

za jedan slučaj i:

```json
{"error": "invalid"}
```

za drugi odaje razliku.

Generic response mora biti konzistentan kroz:

```text
status
body
headers
timing koliko je praktično
```

---

## 44. Enumeration kroz UI

Frontend može slučajno otkriti:

```text
green state → account exists
red state → account missing
```

iako backend message izgleda generički.

Security treba gledati:

```text
ceo observable behavior
```

ne samo jednu string poruku.

---

## 45. DoS kroz account lockout

Primer:

```text
5 failed attempts
↓
account disabled forever
```

Attacker samo uzme email žrtve i pet puta pogreši password.

Rezultat:

```text
legitimate user locked out
```

Zato:

```text
temporary cooldown
```

je često bolji od hard permanent lockout-a.

Permanent security action može imati smisla u specifičnim high-risk situacijama, ali ne kao slepi default.

---

## 46. Global rate limit

Pored per-user/per-IP limita može postojati:

```text
global endpoint protection
```

Na primer:

```text
/login
→ max N requests/sec globally
```

To štiti infrastrukturu od volumetric abuse-a.

Application-level limiter nije zamena za:

```text
reverse proxy
CDN
WAF
network-level protection
```

Ali je deo defense in depth-a.

Različiti slojevi imaju različite odgovornosti.

## 52. Sliding window / token bucket mentalni model

Ne moramo sada implementirati algoritme detaljno.

Ali vredi znati:

### Fixed window

```text
5 / minute
```

counter se resetuje na granici minute.

Jednostavan.

### Sliding window

gleda realni period unazad:

```text
poslednjih 60 sekundi
```

precizniji.

### Token bucket

user ima:

```text
bucket token-a
```

request troši token.

Token-i se vremenom dopunjuju.

Dobar je za:

```text
burst + sustained rate
```

---

## 53. Zašto burst može biti legitiman

User može odjednom napraviti:

```text
5 API request-a
```

zbog page load-a.

Ako limit kaže:

```text
1 request/sec
```

UX može biti loš.

Token bucket omogućava:

```text
mali burst
+
dugoročni limit
```

Zato rate limiting nije samo security broj.

To je i:

```text
traffic policy
```

---

## 54. Retry ponašanje

Ako frontend dobije:

```text
429
```

ne treba da radi:

```text
retry odmah
retry odmah
retry odmah
```

jer samo pogoršava problem.

Treba poštovati:

```text
Retry-After
```

ili koristiti:

```text
backoff
```

Client behavior je deo abuse-resistant sistema.

---

## 55. Exponential backoff

Koncept:

```text
1 sec
2 sec
4 sec
8 sec
16 sec
```

za retry na određenim transient failure-ima.

Ali login password pokušaji nisu samo:

```text
network retry problem
```

Tu application limiter određuje policy.

Backoff je posebno koristan za:

```text
API retries
external service calls
queue jobs
```

da sistem ne napravi retry storm.

---

## 56. Fail open vs fail closed kod rate limiter-a

Ako Redis rate limiter padne, šta radi login?

Opcije:

```text
fail open
→ login nastavlja

fail closed
→ niko ne može login
```

Ne postoji univerzalni odgovor.

Tradeoff:

```text
availability
vs
abuse protection
```

Za high-security endpoint možda biraš strožu politiku.

Za drugi sistem možda availability ima prioritet.

Bitno je:

```text
odluka mora biti namerna
```

## 57. Rate limiting ne sme biti jedina password zaštita

```text
dobro hashovan
```

sa:


Rate limiting smanjuje online guessing.

Password hashing štiti posebno u slučaju:

```text
database compromise
```

Različiti threat modeli.

## 60. Complete abuse mental model

Za svaki sensitive endpoint pitaj:

```text
Ko može da ga pozove?

Koliko često?

Koliko košta jedan request meni?

Može li attacker targetirati drugog user-a?
```

# Laravel paralela

Laravel ima rate limiting infrastrukturu kroz middleware i rate limiter API.

Konceptualno:

```php
RateLimiter::for(
    'login',
    function (Request $request) {
        return Limit::perMinute(5)
            ->by(
                strtolower(
                    $request->input('email')
                )
                . '|'
                . $request->ip()
            );
    }
);
```

Poenta nije da baš ovaj limiter uvek bude idealan.

Poenta je:

```text
key
+
limit
+
time window
```

Laravel može zatim vratiti:

```text
429 Too Many Requests
```

Za login, reset, verification resend i slične endpoint-e throttling treba projektovati prema riziku svakog use case-a.

# Najvažnije za zapamtiti

Razlikuj:

```text
Brute force
→ mnogo password-a protiv account-a

Credential stuffing
→ procureli credential parovi

Password spraying
→ nekoliko čestih password-a
  protiv mnogo account-a
```

Rate limiting znači:

```text
koliko puta
+
ko
+
u kom periodu
```

Nemoj razmišljati samo o:

```text
IP
```

ili samo:

```text
email
```

Napad može promeniti dimenziju.

Permanent account lockout može postati:

```text
DoS protiv žrtve
```

Zato često preferiramo:

```text
temporary throttling
progressive cooldown
```

Enumeration nastaje kada attacker može da razlikuje:

```text
account postoji
vs
account ne postoji
```

preko:

```text
poruke
HTTP status-a
response body-ja
timing-a
UI behavior-a
```

Login često koristi:

```text
Invalid credentials.
```

Password reset često:

```text
If an account exists,
instructions will be sent.
```

Rate limiting treba i za:

```text
login
reset
verification resend
registration
contact
uploads
expensive API actions
```

Ne loguj:

```text
password
session ID
reset token
remember token
```

Authorization:

```text
Da li smeš?
```

Rate limiting:

```text
Koliko često smeš?
```

Idempotency:

```text
Da li isti operation sme
da se izvrši dva puta?
```

Tri različita problema.

Centralni mentalni model:

```text
SENSITIVE ENDPOINT
↓
AUTHENTICATE / IDENTIFY
↓
RATE LIMIT
↓
GENERIC PUBLIC RESPONSE
↓
LOG SAFE SECURITY SIGNALS
↓
STEP-UP PROTECTION
ako rizik raste
```

Ako samo jednu rečenicu zapamtiš:

> **Anti-abuse zaštita ne pokušava samo da blokira pogrešan request — ona kontroliše koliko je skupo attacker-u da ponavlja čak i potpuno validan request.**
