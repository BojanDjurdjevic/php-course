# 1\. Security Mental Model \& Trust Boundaries

## 1\. Security nije jedna funkcija

Security nije:

``` php
htmlspecialchars(...)
```

nije:

``` php
password_hash(...)
```

nije:

``` php
csrf_token()
```

i nije jedan middleware.

Security je način razmišljanja kroz ceo request lifecycle.

Mentalno:

``` text
Request
↓
Input
↓
Validation
↓
Authentication
↓
Authorization
↓
Business logic
↓
Database / Files / External APIs
↓
Output
```

Na svakom koraku postavljamo pitanje:

> Šta ovde može da dođe iz nepouzdanog izvora i šta napadač može da kontroliše?

---

## 2\. Glavno pravilo: input je untrusted dok ne dokažemo suprotno

Sve što dolazi spolja tretiramo kao nepouzdano.

Na primer:

``` text
$_GET
$_POST
$_COOKIE
HTTP headers
JSON body
uploaded files
URL params
query params
external API responses
```

Čak i:

``` text
hidden input
disabled input
select option
JavaScript-generated value
```

nije trusted.

Zašto?

Jer browser nije security boundary.

Napadač ne mora koristiti naš frontend.

Može poslati request direktno:

``` bash
curl
Postman
custom script
modified browser request
```

---

## 3\. Frontend validation nije security

Imamo HTML:

``` html
<input
    type="number"
    min="1"
    max="10"
    name="guests"
>
```

Frontend kaže:

``` text
1–10
```

Ali napadač može poslati:

``` text
guests=999999
```

ili:

``` text
guests=-5
```

ili:

``` text
guests=abc
```

Zato:

``` text
Frontend validation
→ UX

Backend validation
→ security + correctness
```

Frontend pomaže korisniku.

Backend odlučuje šta je stvarno dozvoljeno.

---

## 4\. Trust boundary

**Trust boundary** je mesto gde podatak prelazi iz manje pouzdanog u pouzdaniji deo sistema.

Primer:

``` text
Internet
↓
HTTP Request
────────────── trust boundary
↓
PHP application
```

Ali to nije jedina granica.

Na primer:

``` text
Browser
↓
Backend
↓
Database
↓
External payment API
↓
Filesystem
```

Svaki prelaz je potencijalna trust boundary.

Mentalno:

> Kad podatak prelazi granicu između sistema ili slojeva, proveri šta smeš da pretpostaviš o njemu.

---

## 5\. User input nije jedini untrusted input

Ovo je veoma važno.

Česta početnička greška:

``` text
security = proveri $_POST
```

Ali nepouzdani podaci mogu doći i iz:

``` text
external API-ja
database podataka koje je ranije uneo user
queue payload-a
webhook-a
uploaded file metadata
HTTP header-a
cookie-ja
```

Na primer:

``` php
$name = $user->name;
```

ne znači automatski da je `$name` bezbedan za HTML output.

Možda je originalno unešen kao:

``` html
<script>alert(1)</script>
```

Zato:

``` text
data from DB
≠ automatically safe data
```

---

## 6\. Attack surface

**Attack surface** je sve kroz šta neko može da komunicira sa sistemom ili utiče na njega.

Za web aplikaciju to uključuje:

``` text
routes
forms
API endpoints
login
registration
password reset
file uploads
search/filter params
admin panel
webhooks
cookies
headers
external integrations
```

Što više funkcionalnosti imamo:

``` text
više attack surface-a
```

To ne znači:

``` text
ne dodaj funkcionalnosti
```

nego:

``` text
razumi svaki ulaz u sistem
```

---

## 7\. Security pitanje nije samo "može li user ovo da pošalje?"

Već i:

> Šta se desi ako user pošalje nešto što nismo očekivali?

Na primer:

``` php
$bookingId = $_POST['booking_id'];
```

Pitanja:

``` text
Da li postoji?
Da li je integer?
Da li pripada ovom user-u?
Da li sme da se menja?
Da li je booking u stanju koje dozvoljava operaciju?
```

Security se često krije upravo u ovim pitanjima.

---

## 8\. Authentication nije authorization

Authentication:

``` text
Ko si?
```

Authorization:

``` text
Da li smeš ovo?
```

Primer:

``` php
if (!$auth->check()) {
    throw new AuthenticationException();
}
```

ovo rešava:

``` text
user mora biti ulogovan
```

Ali nije dovoljno.

Ako imamo:

``` text
POST /bookings/123/cancel
```

moramo proveriti:

``` php
if ($booking->userId() !== $auth->id()) {
    throw new AuthorizationException();
}
```

Jer:

``` text
ulogovan user
≠ automatski ovlašćen user
```

Ovo će biti osnova IDOR lekcije kasnije.

---

## 9\. Never trust an ID from the client

Ako frontend pošalje:

``` html
<input
    type="hidden"
    name="user_id"
    value="17"
>
```

nikada ne radimo:

``` php
$userId = $_POST['user_id'];
```

kao dokaz identiteta.

Napadač može promeniti:

``` text
17
→
18
```

Za authenticated user-a uzimamo identitet iz server-side trusted state-a:

``` php
$userId = $auth->id();
```

Mentalno:

``` text
client tells us WHAT
server decides WHO
```

Na primer:

``` text
client:
booking_id = 42

server:
current user = session user 17
```

onda proveravamo:

``` text
da li booking 42 pripada user-u 17?
```

---

## 10\. Defense in depth

Nikad se ne oslanjamo na samo jedan sloj zaštite.

Primer registration email-a:

``` text
Frontend:
<input type="email">

Backend:
validate email

Database:
UNIQUE(email)
```

Tri nivoa.

Ako frontend bude zaobiđen:

``` text
backend i dalje štiti
```

Ako imamo race condition:

``` text
database constraint i dalje štiti
```

To je:

``` text
defense in depth
```

Mentalno:

``` text
više nezavisnih zaštita
→ jedan failure ne ruši ceo sistem
```

---

## 11\. Allowlist je obično bolji od denylist-a

Denylist pita:

``` text
Šta da zabranim?
```

Allowlist pita:

``` text
Šta tačno dozvoljavam?
⁷
```

Primer:

Loše:

``` php
if ($sort !== 'DROP TABLE') {
    ...
}
```

Bolje:

``` php
$allowedSorts = [
    'price',
    'name',
    'created_at',
];

if (!in_array(
    $sort,
    $allowedSorts,
    true
)) {
    $sort = 'created_at';
}
```

Zašto?

Jer je gotovo nemoguće nabrojati:

``` text
sve moguće zlonamerne inpute
```

Mnogo je lakše definisati:

``` text
tri legalne vrednosti
```

---

## 12\. "Never trust user input" ne znači "escape everything immediately"

Ovo je veoma važna nijansa.

Ako dobijemo:

``` php
$name = $_POST['name'];
```

nije nužno dobro odmah:

``` php
$name = htmlspecialchars($name);
```

Zašto?

Jer escaping zavisi od output context-a.

Podatak možemo koristiti u:

``` text
HTML
JSON
SQL
URL
JavaScript
email
log
```

i svaka destinacija ima drugačija pravila.

Bolji mentalni model:

``` text
Input
↓
validate / normalize
↓
store clean semantic value
↓
escape when output context is known
```

Ovo ćemo detaljno raditi kod XSS-a.

---

## 13\. Validation i security nisu isto, ali su povezani

Validation pita:

``` text
Da li je podatak validan za naš use case?
```

Na primer:

``` text
email
→ valid format

guests
→ integer 1–10

status
→ pending|confirmed|cancelled
```

Security koristi validation kao jednu od zaštita.

Ali samo validation nije dovoljna.

Na primer:

``` php
$bookingId = 42;
```

može biti potpuno validan integer.

Ali:

``` text
da li taj booking pripada ovom user-u?
```

je authorization pitanje.

Dakle:

``` text
valid
≠ authorized
```

---

## 14\. Security često štiti invariant

Seti se database invariant-a iz prethodnog modula.

Na primer:

``` text
email mora biti unique
inventory ne sme pasti ispod 0
booking sme menjati samo owner/admin
password reset token sme biti iskorišćen samo jednom
```

Security i correctness se često preklapaju.

Dobar backend čuva invariant čak i ako:

``` text
frontend ima bug
user manipuliše request
dva request-a stignu istovremeno
```

---

## 15\. Least privilege

Princip:

> Svaki korisnik, proces i sistem treba da ima samo minimum prava koja su mu potrebna.

Na primer:

``` text
normal user
→ ne treba admin rights

application DB user
→ ne treba CREATE DATABASE

upload process
→ ne treba write permission nad celim serverom
```

Ako nešto bude kompromitovano, šteta ostaje ograničena.

Mentalno:

``` text
više privileges
→ veći blast radius
```

---

## 16\. Fail closed

Ako sistem nije siguran da je nešto dozvoljeno:

``` text
default treba da bude DENY
```

Loše:

``` php
if ($user !== null) {
    $allowed = true;
}

// neka operacija kasnije možda prođe
```

Bolje:

``` php
if ($user === null) {
    throw new AuthenticationException();
}

if (!$policy->canUpdate($user, $booking)) {
    throw new AuthorizationException();
}
```

Mentalno:

``` text
unknown
→ deny

explicitly allowed
→ allow
```

Ovo je:

``` text
fail closed
```

---

## 17\. Security by obscurity nije zaštita

Na primer:

``` text
/admin-secret-9384
```

nije prava authorization zaštita.

Isto:

``` text
hidden button
```

nije zaštita.

Isto:

``` text
JavaScript ne prikazuje opciju
```

nije zaštita.

Napadač može direktno poslati request.

Prava zaštita mora biti server-side:

``` php
if (!$auth->user()->isAdmin()) {
    throw new AuthorizationException();
}
```

URL može biti dodatno nepredvidiv iz drugih razloga, ali tajnost URL-a nije security model.

---

## 18\. Security i error handling

Security failure ne znači da treba otkriti sve detalje.

Na primer login:

Loše:

``` text
Email exists but password is wrong.
```

ili:

``` text
User account not found.
```

ako želimo da sprečimo account enumeration.

Bolje:

``` text
Invalid credentials.
```

Interno možemo znati pravi razlog.

Public response ne mora.

Mentalno:

``` text
internal truth
≠ public information
```

Ovo će biti veoma važno kod:

``` text
login
forgot password
reset password
```

---

## 19\. Security je pre svega kontrola granica

Ako bismo ceo modul sveli na jednu mapu:

``` text
UNTRUSTED WORLD
↓
trust boundary
↓
validate
normalize
authenticate
authorize
↓
application logic
↓
safe database/files/API usage
↓
context-aware output
```

Na svakom prelazu pitamo:

``` text
Ko kontroliše ovaj podatak?

Šta očekujem?

Šta dozvoljavam?

Šta ako dobijem nešto drugo?

Ko ima pravo da izvrši ovu operaciju?

Kako ovaj podatak bezbedno prosleđujem dalje?
```

---

## 20\. Security mental model za tvoj Vanilla PHP projekat

Za request:

``` text
POST /bookings/42/cancel
```

ne razmišljamo samo:

``` text
"pozovi cancel()"
```

nego:

``` text
1. Da li je HTTP method dozvoljen?

2. Da li je CSRF token validan?

3. Da li je user authenticated?

4. Da li je booking_id validan?

5. Da li booking postoji?

6. Da li booking pripada ovom user-u
   ili user ima admin pravo?

7. Da li booking može biti otkazan
   u trenutnom stanju?

8. Da li DB promena mora biti transactional?

9. Šta user vidi ako operacija ne uspe?

10. Šta logujemo?
```

To je security architecture.

Ne jedna funkcija.

# Laravel paralela

Laravel ima mnogo gotovih slojeva:

``` text
Request validation
Middleware
Authentication
Policies / Gates
CSRF middleware
Eloquent parameter binding
Mass-assignment protection
Escaping u Blade-u
Rate limiting
Secure session handling
```

Ali framework ne može da zna sva pravila tvoje aplikacije.

Na primer Laravel ne zna automatski:

``` text
da booking 42 sme da otkaže samo owner
```

To moraš izraziti kroz:

``` text
Policy
Gate
Service logic
ownership check
```

Framework smanjuje količinu ručnog security koda.

Ne uklanja potrebu za security razmišljanjem.

# Najvažnije za zapamtiti

Security nije:

``` text
jedna helper funkcija
jedan middleware
jedan validator
```

Security je:

``` text
kontrola trust boundaries
kroz ceo request lifecycle
```

Sve što dolazi spolja tretiramo kao:

``` text
untrusted
```

Frontend:

``` text
UX
```

Backend:

``` text
authority
```

Nikada ne verujemo:

``` text
hidden field-u
JavaScript-u
URL ID-u
cookie vrednosti
request user_id-u
```

samo zato što ih je naš frontend poslao.

Authentication:

``` text
Ko si?
```

Authorization:

``` text
Da li smeš ovo?
```

Valid:

``` text
nije isto što i
authorized
```

Preferiramo:

``` text
allowlist
```

nad:

``` text
denylist
```

Koristimo:

``` text
defense in depth
least privilege
fail closed
```

I centralni mentalni model celog Security modula:

``` text
NE VERUJ GRANICI

↓ proveri

NE VERUJ IDENTITETU IZ REQUEST-A

↓ koristi trusted server state

NE VERUJ DA "VALIDNO" ZNAČI "DOZVOLJENO"

↓ authorize

NE VERUJ DA JEDNA ZAŠTITA DOVOLJNA

↓ defense in depth
```

Ako samo jednu rečenicu zapamtiš iz ove lekcije:

> **Security počinje pitanjem: ko kontroliše ovaj podatak i šta sme da uradi sa njim?**
