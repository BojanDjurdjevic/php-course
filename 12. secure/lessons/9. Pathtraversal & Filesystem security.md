# 9. Path Traversal & Filesystem Security — Part 1

## 1. Šta je path traversal

Path traversal nastaje kada attacker uspe da utiče na filesystem putanju tako da izađe iz direktorijuma koji smo nameravali da dozvolimo.

Klasičan payload:

```text
../
```

Primer:

```text
/download?file=invoice.pdf
```

Backend:

```php
$file = $_GET['file'];

$path = __DIR__
    . '/uploads/'
    . $file;

readfile($path);
```

Normalno:

```text
file=invoice.pdf
```

daje:

```text
/uploads/invoice.pdf
```

Ali attacker pošalje:

```text
file=../../.env
```

pa efektivna putanja može postati:

```text
/uploads/../../.env
```

odnosno izaći iz `uploads/` direktorijuma.

---

## 2. Zašto `../` radi

Filesystem interpretira:

```text
.
→ trenutni direktorijum

..
→ parent direktorijum
```

Na primer:

```text
/var/www/app/storage/uploads/../
```

znači:

```text
/var/www/app/storage/
```

A:

```text
../../
```

može ići još više.

Mentalno:

```text
allowed directory
↓
../
↓
parent
↓
../
↓
još jedan parent
```

Ako user kontroliše path segment bez zaštite, može pokušati da "izađe" iz dozvoljene zone.

---

## 3. Šta attacker pokušava da pročita

Tipične mete mogu biti:

```text
.env
config files
source code
private keys
logs
session files
uploaded documents drugih user-a
system files
```

Na primer:

```text
../../.env
```

može sadržati:

```text
DB credentials
API keys
APP secrets
mail credentials
```

Zato path traversal može brzo prerasti u ozbiljan information disclosure incident.

---

## 4. Path traversal nije samo read problem

Može ugroziti i write/delete operacije.

Loše:

```php
unlink(
    $_POST['path']
);
```

ili:

```php
file_put_contents(
    $_POST['path'],
    $content
);
```

Attacker možda pokuša:

```text
../../important-file
```

Dakle path traversal može dovesti do:

```text
arbitrary read
arbitrary write
arbitrary delete
```

zavisno od toga šta aplikacija radi sa putanjom.

---

## 5. Client ne treba da kontroliše filesystem path

Najvažnije pravilo:

> Client treba da referencira resource, ne server filesystem lokaciju.

Loše:

```text
GET /download?path=/var/www/app/storage/user17/file.pdf
```

Bolje:

```text
GET /documents/42/download
```

Server zatim:

```text
document ID
↓
DB lookup
↓
authorization
↓
server-controlled storage key
↓
filesystem path
```

Client nikada ne mora da zna:

```text
/var/www/...
```

---

## 6. Logical ID umesto path-a

Dobar model:

```text
Client:
document_id = 42
```

Database:

```text
id = 42
user_id = 17
storage_key = "ab/cd/9f8e...pdf"
```

Server:

```php
$path =
    $storageRoot
    . '/'
    . $document->storageKey();
```

Ovde client kontroliše samo:

```text
42
```

Server kontroliše:

```text
storage root
storage key
filesystem mapping
```

To je mnogo bezbednije.

---

## 7. Original filename nije storage path

Još jednom:

```text
passport.pdf
```

je user-facing metadata.

Ne treba da bude:

```text
filesystem authority
```

Dakle možemo čuvati:

```text
original_name = passport.pdf
storage_key = 9f8a7b...pdf
```

Za prikaz koristimo:

```text
original_name
```

Za storage:

```text
storage_key
```

Razdvajanje metadata i storage identity je veoma korisno.

---

## 8. `basename()` može pomoći, ali nije kompletan security model

Neko može pokušati:

```php
$file = basename(
    $_GET['file']
);
```

Ako attacker pošalje:

```text
../../.env
```

`basename()` može dati:

```text
.env
```

To uklanja directory traversal deo.

Ali i dalje ostaje pitanje:

```text
da li user uopšte sme da bira arbitrary filename?
```

I:

```text
da li .env postoji unutar allowed folder-a?
```

Zato:

```text
basename()
→ korisna pomoćna funkcija

basename()
≠ kompletna authorization/path security strategija
```

---

## 9. Allowlist filename-a

Ako aplikacija ima mali poznati skup fajlova:

```text
terms.pdf
privacy.pdf
manual.pdf
```

najbezbednije je mapiranje:

```php
$files = [
    'terms' =>
        '/app/static/terms.pdf',

    'privacy' =>
        '/app/static/privacy.pdf',

    'manual' =>
        '/app/static/manual.pdf',
];
```

Request:

```text
?document=terms
```

Backend:

```php
$key = $_GET['document']
    ?? '';

if (!isset($files[$key])) {
    throw new NotFoundException();
}

readfile(
    $files[$key]
);
```

Client bira:

```text
application key
```

ne filesystem path.

---

## 10. Safe storage root

Ako imamo dynamic fajlove, definišemo trusted root:

```php
$storageRoot =
    dirname(__DIR__)
    . '/storage/uploads';
```

Sve dozvoljene datoteke treba da ostanu ispod:

```text
$storageRoot
```

Security pitanje:

> Da li konačna resolved putanja i dalje pripada ovom root direktorijumu?

Tu `realpath()` može pomoći.

---

## 11. `realpath()`

`realpath()` pokušava da vrati canonical absolute path.

Na primer:

```php
$path = realpath(
    $storageRoot
    . '/'
    . $requestedFile
);
```

Ako fajl postoji:

```text
/storage/uploads/docs/../photo.jpg
```

može postati:

```text
/storage/uploads/photo.jpg
```

Dakle:

```text
.
..
symbolic path elements
```

se razrešavaju.

To nam omogućava da proverimo gde je fajl stvarno završio.

---

## 12. `realpath()` može vratiti `false`

Ako putanja ne postoji:

```php
$path = realpath($candidate);

if ($path === false) {
    throw new NotFoundException();
}
```

Važno:

```text
realpath()
→ nije samo string cleaner
```

On tipično zahteva da target može biti razrešen u filesystem-u.

Zato za buduće write destinacije treba drugačije dizajnirati validaciju.

---

## 13. Provera da je path unutar root-a

Primer:

```php
$root = realpath(
    $storageRoot
);

$path = realpath(
    $storageRoot
    . '/'
    . $requestedFile
);

if (
    $root === false
    || $path === false
) {
    throw new NotFoundException();
}
```

Zatim proverimo da path pripada root-u.

Naivno:

```php
if (!str_starts_with(
    $path,
    $root
)) {
    throw new AuthorizationException();
}
```

Ali postoji nijansa.

---

## 14. Prefix check mora uzeti separator u obzir

Ako root glasi:

```text
/storage/uploads
```

onda path:

```text
/storage/uploads_backup/file.txt
```

takođe počinje stringom:

```text
/storage/uploads
```

ali nije unutar istog folder-a.

Bolje:

```php
$root = rtrim(
    $root,
    DIRECTORY_SEPARATOR
) . DIRECTORY_SEPARATOR;

if (!str_starts_with(
    $path,
    $root
)) {
    throw new AuthorizationException();
}
```

Sada dozvoljavamo samo:

```text
/storage/uploads/...
```

ne:

```text
/storage/uploads_backup/...
```

---

## 15. Symlink problem

Symbolic link može pokazivati van dozvoljenog direktorijuma.

Na primer:

```text
storage/uploads/private-link
→ /etc/
```

Ako samo string concatenation kaže:

```text
storage/uploads/private-link/passwd
```

deluje kao da je unutar allowed root-a.

Ali `realpath()` može pokazati:

```text
/etc/passwd
```

Zato canonical path checking ima smisla.

Mentalno:

```text
string path
≠ stvarna filesystem lokacija
```

---

## 16. `include` i `require` su posebno opasni

Nikada:

```php
$page = $_GET['page'];

include $page;
```

ili:

```php
include
    'pages/'
    . $_GET['page']
    . '.php';
```

Attacker može pokušati path traversal ili učitavanje neočekivanog fajla.

Ovo spada u probleme poput:

```text
Local File Inclusion
```

i može biti mnogo ozbiljnije od običnog `readfile()`.

Jer PHP može:

```text
izvršiti PHP kod iz uključenog fajla
```

---

## 17. Bezbedno view mapiranje

Umesto:

```php
include
    $_GET['view']
    . '.php';
```

koristi allowlist:

```php
$views = [
    'home' =>
        __DIR__ . '/views/home.php',

    'contact' =>
        __DIR__ . '/views/contact.php',
];

$key = $_GET['view'] ?? 'home';

if (!isset($views[$key])) {
    throw new NotFoundException();
}

require $views[$key];
```

Client bira:

```text
home
contact
```

Aplikacija bira:

```text
stvarni PHP path
```

---

## 18. Router rešava mnogo ovog problema

U MVC aplikaciji često uopšte nema potrebe da user bira view filename.

Router:

```text
GET /contact
↓
ContactController
↓
render('contact')
```

gde je:

```text
'contact'
```

application-controlled key.

Ne:

```text
?file=contact.php
```

Dobra arhitektura često uklanja čitavu klasu security problema.

---

## 19. Remote file inclusion mental model

Ako bi aplikacija dozvolila user-u da utiče na remote include/resource URL:

```text
https://evil.example/payload
```

rizik postaje još ozbiljniji.

Generalni princip:

```text
user-controlled include path
→ veoma opasan design
```

Views, config i source files treba da dolaze iz:

```text
application-controlled mapping-a
```

ne iz arbitrary URL/path input-a.

---

## 20. `file_get_contents()` nije bezbedan samo zato što "samo čita"

Loše:

```php
$content = file_get_contents(
    $_GET['file']
);
```

User možda može pokušati:

```text
../../.env
```

ili čak drugačiji scheme/URL context ako konfiguracija i funkcija to dozvole.

Dakle svaki filesystem/network sink treba posmatrati kroz pitanje:

```text
ko kontroliše ovu lokaciju?
```

# 9. Path Traversal & Filesystem Security — Part 2

## 21. `unlink()` je security-sensitive sink

Kod:

```php
unlink($path);
```

može trajno obrisati fajl.

Zato `$path` mora biti:

```text
server-controlled
canonicalized
authorized
```

Nikada:

```php
unlink(
    $_POST['filename']
);
```

Pravi tok:

```text
resource ID
↓
DB lookup
↓
authorization
↓
trusted storage key
↓
safe storage root
↓
delete
```

---

## 22. Write operacije su još osetljivije

Na primer:

```php
file_put_contents(
    $path,
    $content
);
```

Ako user kontroliše `$path`, može pokušati da overwrite-uje:

```text
config
template
public file
log
source code
```

Ako application process ima permissions.

Zato:

```text
user controls content
≠ user controls destination
```

Server bira storage destination.

---

## 23. Directory creation

Loše:

```php
mkdir(
    $_POST['folder']
);
```

Bolje:

```text
application-defined root
+
generated / validated logical identifier
```

Na primer:

```php
$folder =
    $storageRoot
    . '/'
    . bin2hex(
        random_bytes(8)
    );
```

Ako user bira kategoriju:

```text
avatar
document
voucher
```

koristi mapping:

```php
$folders = [
    'avatar' => 'avatars',
    'document' => 'documents',
    'voucher' => 'vouchers',
];
```

Ne arbitrary path.

---

## 24. Filesystem allowlist vs denylist

Loše:

```php
if (
    !str_contains(
        $file,
        '../'
    )
) {
    // probably safe
}
```

Zašto?

Jer postoji više mogućih encoding/path representation scenarija i platformskih nijansi.

Bolje:

```text
client bira logical resource
↓
application mapping
↓
trusted canonical path
```

ili canonical root enforcement.

Generalno:

```text
allow known-safe locations
```

je bolji model nego:

```text
traži sve moguće loše stringove
```

---

## 25. URL encoding može sakriti traversal pokušaj

Attacker request može sadržati encoded sekvence.

Na primer konceptualno:

```text
%2e%2e%2f
```

može predstavljati:

```text
../
```

zavisno od toga kada i gde decoding nastaje.

Zato security ne treba da se svodi na:

```php
str_contains(
    $input,
    '../'
);
```

Canonicalization i architecture-based controls su pouzdaniji.

---

## 26. Double decoding problem

Ako različiti slojevi više puta decode-uju input:

```text
encoded value
↓
router decode
↓
application decode opet
```

vrednost može promeniti značenje kasnije.

To je još jedan razlog da:

```text
ne praviš security na string blacklist-u
```

nego na:

```text
trusted mapping-u
canonical path-u
allowed root-u
```

---

## 27. Windows i Unix path razlike

Unix koristi tipično:

```text
/
```

Windows može koristiti:

```text
\
```

i drive paths poput:

```text
C:\
```

Ako ručno pokušavaš da blokiraš samo:

```text
../
```

možeš zaboraviti platform-specific varijante.

Zato koristimo:

```php
DIRECTORY_SEPARATOR
```

gde ima smisla i izbegavamo homemade path parser.

---

## 28. Absolute path injection

Problem nije samo:

```text
../
```

User može pokušati da prosledi absolute path.

Na primer:

```text
/etc/passwd
```

ili:

```text
C:\Windows\...
```

Ako application API uopšte prihvata arbitrary path, architecture je već rizična.

Najbolji odgovor često nije:

```text
više regexa
```

nego:

```text
nemoj prihvatati filesystem path od client-a
```

---

## 29. Path traversal i upload zajedno

Attacker može pokušati upload filename:

```text
../../public/shell.php
```

Ako backend radi:

```php
$destination =
    $uploadRoot
    . '/'
    . $file['name'];
```

može pokušati da izađe iz upload folder-a.

Zato smo u prethodnoj lekciji koristili:

```text
random server filename
```

i trusted storage root.

Dobra upload arhitektura automatski eliminiše veliki deo traversal rizika.

## 30. Download endpoint primer

Loše:

```php
$file = $_GET['file'];

readfile(
    __DIR__
    . '/storage/'
    . $file
);
```

Bolje:

```php
$documentId =
    (int) ($_GET['id'] ?? 0);

$document =
    $documents->findById(
        $documentId
    );

if ($document === null) {
    throw new NotFoundException();
}

if (
    !$policy->view(
        $auth->user(),
        $document
    )
) {
    throw new AuthorizationException();
}

$path =
    $storage->resolve(
        $document->storageKey()
    );

$storage->stream($path);
```

Client nikada ne šalje arbitrary path.

## 31. Storage service

Dobar dizajn:

```php
final class FileStorage
{
    public function __construct(
        private string $root
    ) {}

    public function path(
        string $key
    ): string {
        return $this->root
            . DIRECTORY_SEPARATOR
            . $key;
    }
}
```

Ali još bolje je da `key` sam ima stroga pravila.

Na primer:

```text
random hex filename
```

umesto arbitrary relative path-a.

Tako storage abstraction smanjuje mogućnost greške u Controller-u.

---

## 32. Path validation kao defense in depth

Čak i ako DB čuva trusted generated storage key, možemo imati dodatnu proveru:

```php
$root = realpath(
    $this->root
);

$path = realpath(
    $this->root
    . '/'
    . $key
);

if (
    $root === false
    || $path === false
) {
    throw new RuntimeException();
}

$prefix = rtrim(
    $root,
    DIRECTORY_SEPARATOR
) . DIRECTORY_SEPARATOR;

if (!str_starts_with(
    $path,
    $prefix
)) {
    throw new RuntimeException(
        'Resolved path escaped storage root.'
    );
}
```

To je:

```text
defense in depth
```

## 33. Ne prikazuj absolute server path user-u

Ako error kaže:

```text
Failed opening
/var/www/app/storage/private/users/17/file.pdf
```

user sada dobija informacije o server filesystem-u.

Production response treba da bude generičan.

Log može sadržati:

```text
technical path details
```

ako su potrebni za debugging i ako log access odgovarajuće štitimo.

Opet:

```text
internal truth
≠ public output
```

---

## 34. Logovanje path traversal pokušaja

Može biti korisno logovati:

```text
request_id
user_id
route
resource ID
event = invalid storage path
```

Ali ne treba slepo logovati ogromne/raw attacker payload-e bez kontrole.

Dobar princip:

```text
log enough to investigate
without creating new log injection
or secret exposure problems
```

---

## 35. File permissions kao poslednja granica

Čak i ako path traversal bug postoji, OS permissions mogu ograničiti štetu.

Application user ne treba da može da čita:

```text
arbitrary system secrets
```

ili da piše:

```text
source code
system config
```

ako mu to nije potrebno.

To je opet:

```text
least privilege
```

Filesystem permissions nisu zamena za safe path handling.

Ali smanjuju blast radius.

---

## 36. Chroot/container isolation mental model

U ozbiljnijem deployment-u application process može biti izolovan kroz:

```text
container
restricted filesystem
service user
mount permissions
```

Tako čak i traversal bug može imati manji reach.

Ali security i dalje mora biti ispravan na application nivou.

Defense in depth:

```text
application
+
filesystem permissions
+
runtime/container isolation
```

## 37. Temp files

Temporary files takođe zahtevaju pažnju.

Ne želimo predvidive temp putanje poput:

```text
/tmp/report-user-17.pdf
```

ako mogu izazvati collision ili symlink probleme.

PHP/system alati poput:

```php
tempnam(...)
```

ili sigurni library abstractions su bolji od ručnog predvidivog naming-a.

## 38. Filename i Unicode

Filename može sadržati:

```text
Unicode
control-like characters
visually similar characters
```

To može praviti probleme u:

```text
UI
logs
downloads
operator review-u
```

Još jedan razlog da:

```text
original filename
→ metadata only

storage filename
→ generated by server
```

Kada vidiš:

```php

file_put_contents(...)

```

postavi pitanja:

## 40. Kompletan safe file access flow

Client:

```text
GET /documents/42/download
```

Server:

```text
validate resource ID
↓
authenticate
↓
load document metadata
↓
authorize user
↓
get server-generated storage key
↓
resolve under trusted storage root
↓
verify canonical path remains inside root
↓
stream file
```

Ne:

```text
GET /download?path=../../whatever
```

To je osnovna arhitektonska razlika.

# Laravel paralela

Laravel Storage abstraction radi sa:

```php
Storage::disk('local')
    ->get($path);
```

Ali ovo:

```php
Storage::get(
    $request->input('path')
);
```

i dalje može biti loš security design ako user kontroliše arbitrary storage path.

Bolje:

```text
document ID
↓
model lookup
↓
policy
↓
model.storage_path
↓
Storage
```

Laravel route model binding takođe može pomoći:

```text
/documents/{document}
```

ali i dalje:

```text
route model binding
≠ authorization
```

Policy mora da odluči ko sme da preuzme document.

Isto tako:

```php
return view(
    $request->input('view')
);
```

je loša ideja ako arbitrary view name dolazi direktno od user-a.

Application treba da bira view.

# Najvažnije za zapamtiti

Path traversal znači:

```text
untrusted path input
↓
../ ili druga manipulacija
↓
izlazak iz dozvoljenog direktorijuma
```

Najvažnija zaštita nije:

```text
"blokiraj ../"
```

nego:

```text
client ne kontroliše filesystem path
```

Client treba da šalje:

```text
resource ID
ili
logical application key
```

Server bira:

```text
real storage path
```

Original filename:

```text
metadata
```

ne:

```text
storage authority
```

Za existing paths:

```php
realpath(...)
```

može pomoći da dobiješ canonical path.

Zatim proveri:

```text
resolved path
→ mora ostati unutar trusted root-a
```

Pazi na:

```text
prefix collision
symlinks
absolute paths
encoded traversal
platform differences
```

Nikada nemoj direktno user input stavljati u:

```text
include
require
readfile
unlink
file_put_contents
```

bez vrlo jasne kontrole.

Za views:

```text
application mapping
```

Za downloads:

```text
resource ID
+
authorization
+
server-controlled storage key
```

Za uploads:

```text
server-generated filename
+
trusted storage root
```

Filesystem permissions treba da slede:

```text
least privilege
```

Centralni mentalni model:

```text
CLIENT
→ bira RESOURCE

APPLICATION
→ autorizuje

STORAGE LAYER
→ bira PATH

FILESYSTEM
→ prima samo trusted canonical path
```

Ako samo jednu rečenicu zapamtiš:

> **User može da kaže koji resource želi, ali ne treba da određuje gde se taj resource nalazi na server filesystem-u.**
