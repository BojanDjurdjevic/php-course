# 11. CORS, HTTPS & Security Headers — Part 1: CORS

## 1. Šta je CORS

CORS znači:

```text
Cross-Origin Resource Sharing
```

Da bismo razumeli CORS, prvo moramo razumeti:

```text
Same-Origin Policy
```

Browser po default-u ograničava JavaScript jedne web aplikacije da slobodno čita podatke sa drugog origin-a.

Na primer:

```text
Frontend:
http://localhost:5173

API:
http://127.0.0.1:8000
```

Za browser ovo nisu isti origin-i.

---

## 2. Šta je origin

Origin određuju:

```text
scheme
+
host
+
port
```

Primer:

```text
https://example.com:443
```

Origin uključuje:

```text
scheme = https
host   = example.com
port   = 443
```

Promeni bilo koji od ta tri elementa i dobijaš drugi origin.

---

## 3. Primeri

Ovo:

```text
https://example.com
```

i:

```text
http://example.com
```

nisu isti origin.

Razlikuje se:

```text
scheme
```

Ovo:

```text
https://app.example.com
```

i:

```text
https://api.example.com
```

nisu isti origin.

Razlikuje se:

```text
host
```

Ovo:

```text
http://localhost:5173
```

i:

```text
http://localhost:8000
```

nisu isti origin.

Razlikuje se:

```text
port
```

---

## 4. Primer koji si već video u Automarket projektu

Frontend:

```text
http://localhost:5173
```

API:

```text
http://127.0.0.1:8000
```

Čak i da imaju isti port, ovo:

```text
localhost
```

i:

```text
127.0.0.1
```

browser tretira kao različite hostove.

Zato:

```text
http://localhost:5173
```

i:

```text
http://127.0.0.1:5173
```

nisu isti origin.

To je bio razlog zbog kojeg ti je Sanctum/CORS konfiguracija ranije pravila problem.

---

## 5. Same-Origin Policy

Browser ima security pravilo:

```text
JavaScript sa origin A

ne može automatski da čita
response sa origin B
```

Na primer:

```text
evil.example
↓
JavaScript
↓
bank.example/account
```

Bez browser ograničenja malicious stranica bi mogla pokušavati da čita privatne podatke iz drugih aplikacija koje imaš otvorene.

Zato postoji:

```text
Same-Origin Policy
```

CORS nije ukidanje te zaštite.

CORS je:

> Server-controlled način da browser-u kažemo koje druge origin-e ipak želimo da pustimo.

---

## 6. CORS je browser security mehanizam

Veoma važno:

```text
CORS
→ browser enforcement
```

Ako napraviš request preko:

```text
curl
Postman
backend PHP
server-to-server HTTP client
```

CORS te uglavnom ne interesuje.

Zašto?

Jer:

```text
curl
```

nije browser koji primenjuje Same-Origin Policy.

Zato možeš imati situaciju:

```text
Postman
→ API radi

Browser
→ CORS error
```

API nije nužno pokvaren.

Browser odbija JavaScript-u pristup response-u.

---

## 7. CORS ne znači "da li request može stići do servera"

Ovo je jedna od najvažnijih nijansi.

Ljudi često misle:

```text
CORS blokira request.
```

Preciznije:

```text
CORS kontroliše da li browser
dozvoljava JavaScript-u
cross-origin pristup response-u.
```

Kod nekih request-a browser prvo radi preflight.

Kod drugih request može biti poslat, ali browser kasnije odbije da JavaScript-u izloži response.

Zato smo kod CSRF-a rekli:

```text
CORS
≠ CSRF protection
```

Attacker-u možda nije ni potrebno da pročita response.

Možda mu je dovoljno da izazove state-changing request.

---

## 8. `Origin` header

Browser kod cross-origin request-a može poslati:

```http
Origin: https://app.example.com
```

Server vidi:

```text
Odakle dolazi browser-side caller?
```

i odlučuje:

```text
da li tom origin-u dozvoljavam access?
```

Server zatim može odgovoriti:

```http
Access-Control-Allow-Origin: https://app.example.com
```

Browser poredi request origin sa response politikom.

---

## 9. `Access-Control-Allow-Origin`

Najvažniji CORS response header:

```http
Access-Control-Allow-Origin: https://app.example.com
```

znači:

```text
browser code sa ovog origin-a
sme da pristupi response-u
```

Za javni resource bez credentials možemo videti:

```http
Access-Control-Allow-Origin: *
```

što znači:

```text
bilo koji origin
```

Ali `*` nije univerzalno rešenje.

---

## 10. Zašto ne stavimo jednostavno `*`

Za public API koji ne koristi credentials:

```http
Access-Control-Allow-Origin: *
```

može biti potpuno legitiman.

Na primer javni dataset.

Ali private application API ne treba automatski da kaže:

```text
ceo internet sme da čita moje responses
```

Posebno kada postoje:

```text
session cookies
authenticated user data
private API responses
```

Security politika treba da bude:

```text
minimum required origins
```

ne:

```text
allow everything dok ne proradi
```

---

## 11. Credentialed CORS

Ako frontend koristi cookie/session auth:

```js
fetch(
    'https://api.example.com/user',
    {
        credentials: 'include'
    }
);
```

onda imamo:

```text
credentialed request
```

Credentials mogu uključivati stvari poput:

```text
cookies
HTTP authentication
client certificates
```

Za credentialed CORS server mora eksplicitno dozvoliti credentials.

Na primer:

```http
Access-Control-Allow-Credentials: true
```

I mora dozvoliti konkretan origin.

---

## 12. `*` + credentials ne ide

Ovo je pogrešno:

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

za credentialed browser request.

Ako credentials učestvuju, server mora vratiti konkretan dozvoljeni origin, na primer:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

Browser neće prihvatiti wildcard origin za credentialed CORS response.

Mentalno:

```text
PUBLIC non-credentialed API
→ * može imati smisla

COOKIE / credentialed API
→ explicit trusted origin
```

---

## 13. `withCredentials`

Axios:

```js
axios.get(
    'https://api.example.com/user',
    {
        withCredentials: true
    }
);
```

Fetch:

```js
fetch(
    'https://api.example.com/user',
    {
        credentials: 'include'
    }
);
```

time browser-u govorimo da cross-origin request treba da učestvuje u credential flow-u.

Ali frontend flag sam nije dovoljan.

Backend takođe mora pravilno podesiti CORS.

---

## 14. Cookie pravila i CORS su odvojene stvari

Čak i ako CORS kaže:

```text
origin dozvoljen
```

cookie i dalje mora zadovoljiti svoja pravila:

```text
SameSite
Secure
Domain
Path
```

Dakle:

```text
CORS allowed
≠ cookie će sigurno biti poslat
```

I:

```text
cookie može biti poslat
≠ JavaScript će sigurno dobiti response
```

To su odvojene browser security politike.

---

## 15. Simple request mentalni model

Neki cross-origin request-i mogu biti poslati bez prethodnog preflight-a ako spadaju u ograničen "simple request" skup.

Na primer određene kombinacije:

```text
GET
HEAD
POST
```

sa ograničenim skupom headers/content types.

Browser može:

```text
odmah poslati request
↓
dobiti response
↓
proveriti CORS headers
↓
tek onda odlučiti da li JS sme da vidi response
```

Ovo je jedan od razloga zašto:

```text
CORS
≠ zaštita od CSRF-a
```

---

## 16. Preflight request

Za određene cross-origin request-e browser prvo pita server:

> Da li ćeš dozvoliti request koji želim da pošaljem?

Browser šalje:

```http
OPTIONS /api/bookings/42 HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
```

Može uključiti i:

```http
Access-Control-Request-Headers:
    Content-Type, X-CSRF-TOKEN
```

To je:

```text
preflight
```

MDN opisuje CORS preflight kao `OPTIONS` proveru pre stvarnog request-a za request-e koji ne spadaju u jednostavne CORS slučajeve.

---

## 17. Preflight response

Backend može odgovoriti:

```http
HTTP/1.1 204 No Content

Access-Control-Allow-Origin:
    https://app.example.com

Access-Control-Allow-Methods:
    GET, POST, PUT, PATCH, DELETE

Access-Control-Allow-Headers:
    Content-Type, X-CSRF-TOKEN

Access-Control-Allow-Credentials:
    true
```

Browser vidi:

```text
origin allowed?
method allowed?
headers allowed?
credentials allowed?
```

Ako jeste:

```text
pošalji stvarni request
```

Ako nije:

```text
browser blokira browser-side CORS flow
```

---

## 18. `Access-Control-Allow-Methods`

Primer:

```http
Access-Control-Allow-Methods:
    GET, POST, PUT, PATCH, DELETE
```

Ovaj header govori browser-u koje cross-origin methods server dozvoljava u CORS politici.

To ne znači:

```text
Controller automatski ima authorization
```

Niti:

```text
route postoji
```

Niti:

```text
user sme DELETE
```

To je samo jedan browser access-control sloj.

---

## 19. `Access-Control-Allow-Headers`

Ako frontend šalje:

```http
Content-Type: application/json
X-CSRF-TOKEN: ...
```

preflight može pitati:

```http
Access-Control-Request-Headers:
    content-type, x-csrf-token
```

Backend zatim kaže šta dozvoljava:

```http
Access-Control-Allow-Headers:
    Content-Type, X-CSRF-TOKEN
```

Opet:

```text
CORS allow
≠ header je trusted
```

Attacker-controlled request header i dalje moraš validirati semantički.

---

## 20. `Access-Control-Allow-Credentials`

Za credentialed flow:

```http
Access-Control-Allow-Credentials: true
```

To znači:

```text
server dopušta browser-u
credentialed cross-origin access
```

Jedina stvarna pozitivna vrednost je:

```text
true
```

Ako credentials ne dozvoljavaš:

```text
header se obično jednostavno izostavi
```

---

## 21. Dynamic origin allowlist

Pretpostavimo da podržavamo:

```text
https://app.example.com
https://admin.example.com
```

Možemo imati:

```php
$allowedOrigins = [
    'https://app.example.com',
    'https://admin.example.com',
];

$origin =
    $_SERVER['HTTP_ORIGIN']
    ?? null;

if (
    $origin !== null
    && in_array(
        $origin,
        $allowedOrigins,
        true
    )
) {
    header(
        "Access-Control-Allow-Origin: {$origin}"
    );
}
```

Ovde je veoma važno:

```text
request Origin
↓
allowlist check
↓
tek onda reflection
```

---

## 22. Nemoj slepo reflect-ovati Origin

Loše:

```php
$origin =
    $_SERVER['HTTP_ORIGIN']
    ?? '*';

header(
    "Access-Control-Allow-Origin: {$origin}"
);
```

To praktično može značiti:

```text
ko god pita
→ dobija dozvolu
```

Ako koristimo credentials, to može biti veoma ozbiljna greška.

Pravi model:

```text
Origin
↓
compare against trusted allowlist
↓
allowed?
├── DA → return that origin
└── NE → no CORS permission
```

MDN takođe preporučuje da credentialed pristup bude ograničen na eksplicitno dozvoljene origin-e, a ne slepo reflektovan.

---

## 23. `Vary: Origin`

Ako server dinamički vraća:

```http
Access-Control-Allow-Origin:
    https://app.example.com
```

u zavisnosti od request `Origin` header-a, treba razmišljati i o cache-u.

Response može uključiti:

```http
Vary: Origin
```

Time cache zna:

```text
response može biti različit
za različite Origin vrednosti
```

To sprečava da cache pogrešno ponovo koristi response/CORS header namenjen drugom origin-u.

---

## 24. CORS nije Authentication

Ako dozvolimo:

```text
https://app.example.com
```

to ne znači:

```text
svaki request sa tog origin-a
je authenticated
```

I dalje treba:

```text
session
token
credential
```

CORS odgovara na pitanje:

```text
Da li browser JavaScript sa ovog origin-a
sme cross-origin da radi sa response-om?
```

Auth odgovara:

```text
Ko je caller?
```

---

## 25. CORS nije Authorization

Čak i:

```text
origin allowed
session valid
```

ne znači:

```text
user sme booking 42
```

I dalje:

```text
Policy
ownership
role
permission
```

Dakle:

```text
CORS
≠ Authentication
≠ Authorization
```

---

## 26. CORS nije CSRF

Ovo sada možemo precizno objasniti.

CORS uglavnom štiti:

```text
cross-origin JavaScript
od čitanja response-a
```

CSRF štiti:

```text
state-changing action
od neželjenog cross-site pokretanja
```

Attacker možda ne mora da pročita:

```text
"booking cancelled successfully"
```

ako je njegov cilj samo:

```text
cancel booking
```

Zato:

```text
CORS
+
CSRF
```

rešavaju različite probleme.

---

## 27. CORS nije server-to-server firewall

Ako API kaže:

```http
Access-Control-Allow-Origin:
    https://app.example.com
```

attacker i dalje može poslati HTTP request preko:

```text
curl
PHP
Python
Postman
```

CORS mu ne zabranjuje da razgovara sa serverom.

Samo browser neće njegovom JavaScript origin-u dati CORS privilegije.

Zato security API-ja mora i dalje koristiti:

```text
authentication
authorization
validation
rate limiting
```

---

## 28. Tipičan SPA + Laravel flow

Frontend:

```text
http://127.0.0.1:5173
```

Laravel:

```text
http://127.0.0.1:8000
```

Browser request:

```js
axios.get(
    'http://127.0.0.1:8000/user',
    {
        withCredentials: true
    }
);
```

Backend mora dozvoliti:

```text
Origin:
http://127.0.0.1:5173
```

Ne:

```text
http://localhost:5173
```

ako browser stvarno dolazi sa `127.0.0.1`.

Origin mora odgovarati stvarnom browser origin-u.

---

## 29. Tvoja ranija Sanctum situacija

Imali smo:

```text
frontend:
http://localhost:5173
```

a backend/CORS očekivao:

```text
http://127.0.0.1:5173
```

Browser kaže:

```text
request origin
≠ allowed origin
```

i zato je CORS pukao.

To je odličan realan primer za intervju.

Nije bilo:

```text
Axios problem
Sanctum bug
PHP problem
```

nego:

```text
origin mismatch
```

## 30. CORS mentalni model

```text
Browser JS
↓
želi drugi origin
↓
Same-Origin Policy
↓
da li server daje CORS permission?
↓
NO
→ JS ne dobija cross-origin access

YES
→ browser dozvoljava access
  pod definisanim pravilima
```

CORS je:

```text
server-defined exception
na browser Same-Origin Policy
```

# Najvažnije za zapamtiti

Origin je:

```text
scheme
+
host
+
port
```

Zato:

```text
localhost
≠ 127.0.0.1
```

i:

```text
:5173
≠ :8000
```

CORS postoji zbog:

```text
Same-Origin Policy
```

i prvenstveno kontroliše:

```text
šta browser JavaScript
sme cross-origin da čita/koristi
```

Najvažniji header:

```http
Access-Control-Allow-Origin
```

Za credentialed request:

```http
Access-Control-Allow-Origin:
    https://app.example.com

Access-Control-Allow-Credentials:
    true
```

Ne:

```http
Access-Control-Allow-Origin: *
```

sa credentials.

Preflight:

```text
OPTIONS
↓
Origin
Access-Control-Request-Method
Access-Control-Request-Headers
↓
server CORS response
↓
browser odlučuje
da li šalje actual request
```

Dynamic origin:

```text
request Origin
↓
STRICT ALLOWLIST
↓
return allowed origin
```

Ne:

```text
reflect everything
```

CORS:

```text
≠ Authentication
≠ Authorization
≠ CSRF
≠ server firewall
```

Centralni mentalni model:

```text
CORS
→ "Da li browser code sa origin A
   sme da koristi response origin-a B?"
```

Ako samo jednu rečenicu zapamtiš:

> **CORS nije zaštita API-ja od request-a sa interneta; CORS je pravilo kojim server govori browser-u koji drugi origin-i smeju da zaobiđu deo Same-Origin Policy ograničenja.**

# 11. CORS, HTTPS & Security Headers — Part 2: HTTPS & Security Headers

## 31. HTTP vs HTTPS

HTTP:

```text
client
↓
HTTP
↓
server
```

sam po sebi ne daje odgovarajuću zaštitu transporta.

HTTPS je:

```text
HTTP
+
TLS
```

TLS daje tri ključne stvari:

```text
Confidentiality
Integrity
Authentication
```

---

## 32. Confidentiality

Bez encryption-a neko između client-a i server-a može potencijalno videti podatke.

Na primer:

```text
password
session cookie
CSRF token
personal data
API response
```

HTTPS encryptuje transport.

Mentalno:

```text
Browser
↓
encrypted TLS connection
↓
Server
```

Treća strana na mreži ne bi trebalo jednostavno da može čitati sadržaj request-a i response-a.

---

## 33. Integrity

HTTPS ne rešava samo:

```text
"da niko ne pročita"
```

nego i:

```text
"da niko ne izmeni sadržaj u transportu"
```

Bez odgovarajuće transport protection attacker na mreži bi mogao pokušati da modifikuje:

```text
HTML
JavaScript
forms
responses
downloads
```

TLS omogućava detekciju neautorizovane izmene transportovanih podataka.

---

## 34. Server authentication

TLS certificate pomaže browser-u da proveri:

```text
da stvarno razgovara sa
example.com
```

a ne sa attacker-om koji se samo predstavlja kao taj server.

Zato HTTPS nije samo:

```text
encryption
```

nego i:

```text
authenticated secure channel
```

u okviru PKI/certificate modela.

---

## 35. HTTPS ne rešava application security

Ako aplikacija ima:

```text
SQL injection
XSS
IDOR
broken authorization
```

HTTPS to ne popravlja.

HTTPS može savršeno bezbedno transportovati:

```text
malicious payload
```

do tvog servera.

Mentalno:

```text
HTTPS
→ štiti transport

Validation / Auth / Security
→ štite aplikaciju
```

---

## 36. HTTPS i session cookies

Ako cookie ima:

```text
Secure
```

browser ga šalje samo kroz secure HTTPS context.

Za production session:

```text
HTTPS
+
Secure cookie
```

treba da bude standardni model.

Ne želimo:

```text
session credential
↓
plain HTTP
```

---

## 37. HTTP → HTTPS redirect

Server može da primi:

```text
http://example.com
```

i vrati redirect ka:

```text
https://example.com
```

Na primer:

```text
301 / 308
→ HTTPS
```

To je dobro.

Ali postoji jedna nijansa.

Prvi HTTP request je već krenuo nezaštićenim putem.

Attacker na mreži može pokušati da spreči redirect.

Tu dolazi:

```text
HSTS
```

---

## 38. HSTS

HSTS znači:

```text
HTTP Strict Transport Security
```

Header:

```http
Strict-Transport-Security:
    max-age=31536000
```

govori browser-u:

> Ovaj host koristi HTTPS. U budućnosti nemoj ni pokušavati običan HTTP.

Browser pamti pravilo.

Ako user kasnije otvori:

```text
http://example.com
```

browser može interno prebaciti na:

```text
https://example.com
```

pre običnog HTTP request-a.

MDN trenutno opisuje HSTS upravo kao browser policy koja buduće HTTP pokušaje automatski nadograđuje na HTTPS.

---

## 39. HSTS header se šalje preko HTTPS-a

Važna stvar:

```http
Strict-Transport-Security
```

treba da stigne kroz:

```text
HTTPS response
```

Browser ne treba da veruje HSTS instrukciji dobijenoj preko nebezbednog HTTP kanala.

MDN navodi da browser-i ignorišu HSTS kada je poslat preko običnog HTTP-a.

---

## 40. `max-age`

Primer:

```http
Strict-Transport-Security:
    max-age=31536000
```

znači:

```text
pamti HSTS policy
31536000 sekundi
≈ 1 godina
```

Tokom tog perioda browser tretira host kao HTTPS-only.

---

## 41. `includeSubDomains`

Možemo imati:

```http
Strict-Transport-Security:
    max-age=31536000;
    includeSubDomains
```

što proširuje policy na subdomain-e.

Na primer:

```text
example.com
api.example.com
admin.example.com
```

Ali ovo mora biti namerna deployment odluka.

Ako neki subdomain ne podržava HTTPS:

```text
includeSubDomains
```

može ga praktično učiniti nedostupnim tom browser-u.

---

## 42. HSTS preload

Postoji i:

```text
preload
```

model gde browser može unapred znati da domain zahteva HTTPS.

To rešava deo problema:

```text
"šta je sa prvim obiskom,
pre nego što je browser ikada video HSTS header?"
```

Ali preload je ozbiljna operativna odluka.

Ne uključuje se samo zato što:

```text
"zvuči security"
```

Treba biti siguran da domain i potrebni subdomain-i mogu trajno funkcionisati preko HTTPS-a.

---

## 43. Security headers

Pored HSTS-a, response može nositi druge browser security politike.

Važni primeri:

```text
Content-Security-Policy
X-Content-Type-Options
Referrer-Policy
Permissions-Policy
X-Frame-Options
```

Svaki rešava drugačiji problem.

Ne postoji:

```text
jedan security header
koji rešava sve
```

---

## 44. Content-Security-Policy

CSP omogućava server-u da kaže browser-u:

```text
odakle smeš da učitavaš
scripts
styles
images
frames
fonts
connections
...
```

Na primer veoma pojednostavljeno:

```http
Content-Security-Policy:
    default-src 'self'
```

To znači otprilike:

```text
po default-u dozvoli resources
samo sa mog origin-a
```

---

## 45. CSP i XSS

CSP je veoma koristan kao:

```text
defense in depth protiv XSS-a
```

Na primer možemo ograničiti odakle script sme da se izvršava.

Ali:

```text
CSP
≠ zamena za output escaping
```

Primarna zaštita ostaje:

```text
context-aware escaping
safe DOM APIs
no unsafe raw HTML
```

CSP je dodatna granica.

---

## 46. Zašto inline JavaScript komplikuje CSP

Ako aplikacija ima svuda:

```html
<script>
    ...
</script>
```

i:

```html
<button onclick="...">
```

striktan CSP postaje teže uvesti.

Moderniji pristup može koristiti:

```text
external scripts
nonces
hashes
```

umesto širokog:

```text
'unsafe-inline'
```

Poenta za sada:

```text
dobar frontend architecture
→ olakšava jak CSP
```

---

## 47. `frame-ancestors`

CSP može kontrolisati ko sme da prikazuje našu stranicu u frame-u.

Na primer:

```http
Content-Security-Policy:
    frame-ancestors 'none'
```

znači:

```text
niko ne sme da embed-uje ovu stranicu
u frame
```

To pomaže protiv:

```text
clickjacking-a
```

---

## 48. Clickjacking mentalni model

Attacker prikaže našu aplikaciju u:

```html
<iframe>
```

i preko nje postavi obmanjujući UI.

User misli da klikće:

```text
"Play"
```

a zapravo klikne:

```text
"Delete account"
```

u skrivenom/transparentnom frame-u.

To je:

```text
clickjacking
```

Frame restrictions pomažu protiv ovog napada.

---

## 49. `X-Frame-Options`

Stariji, ali i dalje poznat header:

```http
X-Frame-Options: DENY
```

ili:

```http
X-Frame-Options: SAMEORIGIN
```

`DENY`:

```text
ne dozvoli framing
```

`SAMEORIGIN`:

```text
dozvoli ga samo sa istog origin-a
```

Moderniji CSP:

```text
frame-ancestors
```

daje fleksibilniju kontrolu.

---

## 50. `X-Content-Type-Options`

Header:

```http
X-Content-Type-Options: nosniff
```

govori browser-u:

> Poštuj declared Content-Type i nemoj pokušavati da nagađaš drugi MIME tip.

To smanjuje rizike koji nastaju kroz:

```text
MIME sniffing
```

MDN ga opisuje kao header koji browser-u nalaže da koristi deklarisani `Content-Type` umesto MIME sniffing-a.

---

## 51. Zašto `Content-Type` mora biti tačan

Ako vraćamo JSON:

```http
Content-Type: application/json
```

Ako vraćamo HTML:

```http
Content-Type: text/html; charset=UTF-8
```

Ako vraćamo PDF:

```http
Content-Type: application/pdf
```

Security headers ne zamenjuju:

```text
tačan response metadata
```

`nosniff` zapravo ima više smisla kada server već daje ispravne MIME tipove.

---

## 52. `Referrer-Policy`

Browser može pri odlasku na drugi URL poslati:

```http
Referer: ...
```

što može otkriti informacije o prethodnoj stranici.

`Referrer-Policy` kontroliše koliko tih informacija browser šalje.

Primer:

```http
Referrer-Policy:
    strict-origin-when-cross-origin
```

Ideja:

```text
same-origin
→ može poslati više context-a

cross-origin
→ ograniči informacije
```

Ne treba stavljati secrets u URL ni sa dobrim Referrer policy-jem.

---

## 53. Zašto secrets ne treba da budu u URL-u

Na primer:

```text
/reset-password?token=SECRET
```

nekad je funkcionalno neizbežno za reset link.

Ali secrets generalno mogu procuriti kroz:

```text
browser history
logs
analytics
Referer
screenshots
shared URL
```

Zato security-sensitive URL design zahteva oprez.

`Referrer-Policy` je defense in depth.

Ne zamena za dobar token lifecycle.

---

## 54. `Permissions-Policy`

Header:

```text
Permissions-Policy
```

omogućava da ograničimo browser capabilities kao što mogu biti:

```text
camera
microphone
geolocation
```

zavisno od aplikacije i browser support-a.

Na primer aplikacija kojoj ne treba kamera nema razlog da je arbitrary embedded content koristi.

Princip:

```text
browser capability
→ minimum required permission
```

Opet least privilege.

---

## 55. Security headers nisu "copy-paste magic"

Loš pristup:

```text
kopiram 15 security header-a
sa Stack Overflow-a
```

bez razumevanja.

Na primer previše strog CSP može polomiti aplikaciju.

Loš HSTS `includeSubDomains` može polomiti legacy subdomain.

Pogrešan CORS može otvoriti private API.

Security policy mora pratiti stvarnu arhitekturu.

---

## 56. Primer jednostavnog production response seta

Konceptualno:

```http
Strict-Transport-Security:
    max-age=31536000

X-Content-Type-Options:
    nosniff

Referrer-Policy:
    strict-origin-when-cross-origin

Content-Security-Policy:
    default-src 'self';
    frame-ancestors 'self'
```

Ovo nije univerzalni copy-paste config.

Na primer CSP mora odgovarati tome da li koristiš:

```text
CDN
Google Fonts
analytics
external images
inline scripts
API origin
```

Policy se projektuje za konkretnu aplikaciju.

---

## 57. Security headers middleware

U Vanilla PHP-u možemo centralizovati headers:

```php
final class SecurityHeadersMiddleware
{
    public function handle(
        Request $request,
        callable $next
    ): Response {
        $response = $next($request);

        $response->header(
            'X-Content-Type-Options',
            'nosniff'
        );

        $response->header(
            'Referrer-Policy',
            'strict-origin-when-cross-origin'
        );

        return $response;
    }
}
```

Prednost:

```text
jedna security policy
→ cela aplikacija
```

umesto da svaki Controller ručno dodaje headers.

## 58. HTTPS enforcement pripada infrastrukturi koliko i aplikaciji

HTTPS može biti terminiran na:

```text

Apache
load balancer
reverse proxy
CDN
cloud platform
```

Zato application ponekad ne vidi direktno TLS connection.

U production arhitekturi moraš razumeti:

```text

↓ HTTPS

↓

```

i pravilno podesiti trusted proxy behavior.

Framework može pomoći, ali infrastruktura je deo security modela.

## 59. Proxy i HTTPS detection

Ako reverse proxy završi TLS pa prema PHP-u šalje HTTP, aplikacija može pogrešno misliti:

```text
request nije secure
```

Zato postoje forwarded headers poput:

```text
X-Forwarded-Proto
```

Ali njih takođe ne smeš slepo verovati od svakog client-a.

Veruješ ih samo:

```text
trusted proxy infrastrukturi
```

Ponovo:

```text
trust boundary
```

# Najvažnije za zapamtiti

HTTPS je:

```text
HTTP preko TLS-a
```

i štiti:

```text
confidentiality
integrity
server authentication
```

Ali:

```text
HTTPS
≠ zaštita od XSS
≠ zaštita od SQL injection-a
≠ authorization
```

HSTS:

```text
Strict-Transport-Security
```

govori browser-u:

```text
ovaj host koristi HTTPS
→ buduće HTTP pokušaje prebaci na HTTPS
```

HSTS policy browser prihvata preko secure HTTPS response-a.

CSP:

```text
ograničava browser resource/execution policy
```

i daje snažan:

```text
defense in depth
```

protiv XSS-a.

Ali:

```text
CSP
≠ zamena za escaping
```

`frame-ancestors` / `X-Frame-Options`:

```text
clickjacking protection
```

`X-Content-Type-Options: nosniff`:

```text
sprečava MIME sniffing ponašanje
```

`Referrer-Policy`:

```text
kontroliše Referrer leakage
```

`Permissions-Policy`:

```text
ograničava browser capabilities
```

Ne kopiraj security headers naslepo.

Njihova politika mora odgovarati:

```text
realnoj aplikaciji
realnim origin-ima
realnim external resources
realnoj infrastrukturi
```

Centralna mapa:

```text
HTTPS
→ zaštiti transport

HSTS
→ insistiraj na HTTPS

CORS
→ kontroliši cross-origin browser access

CSP
→ kontroliši browser execution/resources

Security headers
→ dodatno ograniči browser behavior

Application security
→ validation + auth + authorization + CSRF
```

Ako samo jednu rečenicu zapamtiš:

> **HTTPS štiti put između browser-a i server-a, CORS kontroliše koji drugi origin-i smeju da koriste browser access, a security headers dodatno ograničavaju šta browser sme da uradi sa response-om.**
