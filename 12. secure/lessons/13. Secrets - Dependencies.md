# 13. Secrets, Dependencies, Logging & Production Security — Part 1

## 1. Šta je secret

Secret je podatak koji daje neku privilegiju ili pristup i zato ne sme biti javno poznat.

Na primer:

```text
database password
API key
SMTP password
private key
OAuth client secret
payment provider secret
JWT signing key
application encryption key
```

Mentalno:

```text
public configuration
→ može biti poznata

secret
→ poznavanje daje privilege
```

Na primer:

```text
DB_HOST=db.example.com
```

obično nije posebno osetljiv.

Ali:

```text
DB_PASS=super-secret-password
```

jeste.

---

## 2. `.env` rešava jedan problem, ne sve probleme

U PHP aplikaciji često imamo:

```env
DB_HOST=localhost
DB_DATABASE=app
DB_USERNAME=app_user
DB_PASSWORD=secret

MAIL_PASSWORD=secret
API_SECRET=secret
```

Prednost:

```text
code
≠ secrets
```

Repository može sadržati:

```php
$_ENV['DB_PASSWORD']
```

bez stvarne vrednosti password-a.

Ali:

```text
.env
≠ magični security vault
```

Ako attacker može da pročita `.env`, secrets su kompromitovani.

---

## 3. `.env` ne ide u Git

Tipično:

```gitignore
.env
```

a repository može imati:

```text
.env.example
```

sa:

```env
DB_HOST=
DB_DATABASE=
DB_USERNAME=
DB_PASSWORD=
```

bez pravih credentials.

Dobar model:

```text
.env
→ real local/environment secrets

.env.example
→ dokumentacija potrebnih config ključeva
```

---

## 4. `.env.example` ne sme imati stvarne secrets

Loše:

```env
STRIPE_SECRET=sk_live_REAL_SECRET
```

u `.env.example`.

Čak i ako komentar kaže:

```text
# replace this in production
```

secret je već u repository-ju.

Primer treba da bude:

```env
STRIPE_SECRET=
```

ili očigledno fake:

```env
STRIPE_SECRET=your-secret-here
```

---

## 5. "Obrisao sam secret iz poslednjeg commit-a" nije dovoljno

Pretpostavimo:

```text
commit A
→ .env sa production password-om

commit B
→ obrišemo .env
```

Secret i dalje može postojati u:

```text
Git history
forkovima
clone-ovima
CI cache-u
logs
GitHub/GitLab infrastructure
```

Mentalno:

```text
secret committed once
→ smatraj ga compromised
```

Prvi pravi odgovor je:

```text
ROTATE SECRET
```

Ne samo:

```text
delete file
```

---

## 6. Secret rotation

Ako procure database password:

```text
old password
↓
revoke/change
↓
new password
↓
update application config
```

Ako procure API key:

```text
revoke old key
↓
create new
↓
deploy
```

Security princip:

> Ne pokušavaj da utvrdiš da li je neko "verovatno video" javno procureli secret. Ponašaj se kao da jeste.

---

## 7. Git history cleanup ima smisla, ali ne vraća secret u tajnost

Možemo kasnije očistiti history.

To može pomoći da:

```text
secret više nije lako dostupan
novi clone ga ne dobija
```

Ali ne znamo:

```text
ko ga je već kopirao
```

Zato:

```text
history cleanup
+
secret rotation
```

a ne:

```text
history cleanup
umesto rotation-a
```

---

## 8. Secrets ne smeju biti u frontend kodu

Ako Vue aplikacija dobije:

```js
const secret =
    'MY_PRIVATE_API_SECRET';
```

taj secret nije tajan.

Frontend code završava kod user-a.

Sve što browser mora da zna:

```text
attacker takođe može da sazna
```

Zato:

```text
public API identifier
→ može frontend

private secret
→ backend only
```

---

## 9. Build-time environment variable nije automatski secret

Frontend tooling često podržava environment variables.

Ali ako vrednost bude ubačena u JavaScript bundle:

```text
.env
↓
frontend build
↓
bundle.js
↓
browser
```

onda:

```text
više nije secret
```

Naziv:

```text
ENV
```

ne određuje da li je nešto bezbedno.

Važno je:

```text
gde vrednost na kraju završava
```

---

## 10. Secrets ne treba stavljati u URL

Loše:

```text
https://api.example.com/data?api_key=SECRET
```

URL može završiti u:

```text
browser history
proxy logs
server logs
analytics
Referer
monitoring
```

Ako protocol/API podržava, credential obično pripada odgovarajućem:

```text
Authorization header-u
secure request body-ju
server-side configuration-u
```

zavisno od konkretnog protocol-a.

---

## 11. Secrets ne logujemo

Loše:

```php
$logger->debug(
    'Environment',
    $_ENV
);
```

To može logovati:

```text
DB_PASSWORD
MAIL_PASSWORD
API_SECRET
APP_KEY
```

Isto važi za:

```php
$logger->debug(
    'Request',
    $_SERVER
);
```

ako unutra završe:

```text
Authorization headers
cookies
tokens
```

---

## 12. Log redaction

Ako želimo request context, sensitive fields treba ukloniti ili maskirati.

Konceptualno:

```php
$context = [
    'email' => $email,
    'password' => '[REDACTED]',
    'token' => '[REDACTED]',
];
```

Bolje je da logging architecture već zna:

```text
koja polja nikada ne smeju u log
```

nego da svaki developer mora svaki put da se seti.

---

## 13. Šta ne logujemo

Posebno:

```text
plain password
password hash
session ID
Remember Me validator
password reset token
CSRF token
Authorization header
API secret
private key
full payment credentials
```

Neke od ovih vrednosti su hashovane ili privremene.

I dalje ne postoji dobar razlog da ih rutinski logujemo.

---

## 14. Logs su security-sensitive storage

Česta greška:

```text
"To je samo log."
```

Ali log može sadržati:

```text
user IDs
email
IP
request paths
errors
filesystem paths
SQL details
business data
```

Zato logovima treba:

```text
access control
retention policy
rotation
storage protection
```

Log nije javni text file.

---

## 15. Production error output

Iz prethodnog modula:

Development:

```text
display_errors = On
log_errors = On
```

Production:

```text
display_errors = Off
log_errors = On
```

Zašto?

User ne treba da vidi:

```text
stack trace
database credentials
filesystem paths
SQL query internals
class structure
vendor paths
```

Ali developer/operator treba da ima:

```text
server-side log
```

za debugging.

---

## 16. Debug mode u produkciji

Debug page može prikazati:

```text
request
environment
stack trace
SQL
config
paths
```

Zato:

```text
development debug
→ odličan

production debug
→ potencijalni information disclosure
```

Laravel analogija:

```env
APP_ENV=production
APP_DEBUG=false
```

Production mora imati bezbedan public error response.

---

## 17. Generic user response, detailed internal report

User:

```text
Something went wrong.
```

Internal log:

```text
Request ID: abc123
PDOException
file
line
stack trace
previous exception
```

To je isti princip:

```text
internal truth
≠ public output
```

Request ID omogućava support-u:

```text
"Greška reference ABC123"
```

bez prikazivanja stack trace-a user-u.

---

## 18. Secrets u exception porukama

Pazi i na kod poput:

```php
throw new RuntimeException(
    "Connection failed using password {$password}"
);
```

Sada secret može završiti u:

```text
log
error tracker
debug page
exception trace context
```

Exception message treba da objasni problem.

Ne da sadrži credential.

---

## 19. Config object

Umesto da cela aplikacija svuda direktno koristi:

```php
$_ENV
```

možemo centralizovati config.

Na primer:

```php
final readonly class DatabaseConfig
{
    public function __construct(
        public string $host,
        public string $database,
        public string $username,
        public string $password
    ) {}
}
```

Bootstrap jednom čita environment.

Ostatak aplikacije dobija:

```text
explicit config dependency
```

To smanjuje nasumično širenje secrets kroz codebase.

---

## 20. Environment variable nije jedini secret storage

U ozbiljnijoj infrastrukturi secrets mogu dolaziti iz:

```text
deployment platform secret store
Docker/Kubernetes secrets
cloud secret manager
CI/CD protected variables
OS-level environment
```

PHP aplikaciji je najvažnije:

```text
dobije secret kroz controlled deployment boundary
```

a ne:

```text
hard-code u source
```

---

## 21. Least privilege za database user-a

Aplikacija ne treba da se povezuje kao:

```text
root
```

ako joj treba samo:

```text
SELECT
INSERT
UPDATE
DELETE
```

nad svojom bazom.

Ako application credential bude kompromitovan:

```text
manje privileges
→ manji blast radius
```

Ne treba joj automatski:

```text
CREATE USER
GRANT
DROP DATABASE
SUPER/admin permissions
```

---

## 22. Odvojeni credentials po environment-u

Development:

```text
dev database
dev API keys
```

Staging:

```text
staging credentials
```

Production:

```text
production credentials
```

Ne:

```text
isti DB password
svuda
```

Ako development laptop bude kompromitovan, attacker ne treba automatski da dobije production pristup.

---

## 23. Odvojeni credentials po servisu

Ako imamo:

```text
web application
worker
report service
backup process
```

ne mora svaki proces imati isti nivo pristupa.

Princip:

```text
svaki servis
→ minimum permissions koji mu trebaju
```

To je least privilege na infrastructure nivou.

---

## 24. Backup je takođe sensitive

Database backup može sadržati:

```text
user data
password hashes
tokens
business data
```

Ako production DB štitimo dobro, ali ostavimo:

```text
backup.sql
```

javno dostupan, security je izgubljen.

Backup zahteva:

```text
access control
encryption gde je potrebno
retention
secure deletion policy
```

---

## 25. `.env` i web root

Posebno je opasno ako deployment dozvoljava:

```text
https://example.com/.env
```

`.env` ne treba da bude public asset.

Dobar project layout:

```text
project/
├── .env
├── vendor/
├── src/
├── storage/
└── public/
    └── index.php
```

Web server document root:

```text
project/public
```

Ne:

```text
project/
```

Time:

```text
.env
vendor
src
storage
```

nisu direktno web-accessible.

---

## 26. Public directory kao security boundary

Ovo je jedna od velikih prednosti front-controller arhitekture:

```text
Internet
↓
public/
↓
index.php
↓
application
```

Ne želimo:

```text
Internet
↓
arbitrary PHP/source/config files
```

Public directory treba da sadrži samo ono što stvarno sme biti javno.

# Najvažnije za zapamtiti — Part 1

Secret je:

```text
podatak čije poznavanje daje privilege
```

`.env`:

```text
odvaja secret od source code-a
```

ali:

```text
.env
≠ secret vault
```

Nikad:

```text
.env u Git
real secrets u .env.example
private secret u frontend bundle
secret u URL
secret u log
```

Ako secret jednom završi u Git-u:

```text
tretiraj ga kao compromised
↓
ROTATE
```

Brisanje iz poslednjeg commit-a:

```text
ne poništava Git history
```

Production:

```text
display_errors = Off
log_errors = On
```

Public error:

```text
safe
```

Internal log:

```text
detailed
```

ali bez credentials.

Logs su:

```text
security-sensitive storage
```

Database/app credentials treba da prate:

```text
least privilege
```

Development, staging i production treba da imaju:

```text
odvojene credentials
```

I web server root treba da bude:

```text
/public
```

a ne ceo PHP projekat.

Centralna rečenica:

> **Secret nije bezbedan zato što se nalazi u `.env` fajlu; bezbedan je samo dok je njegov ceo lifecycle — storage, deployment, logging, access i rotation — kontrolisan.**

# 13. Secrets, Dependencies, Logging & Production Security — Part 2

## 27. Dependency je deo naše aplikacije

Ako instaliramo:

```bash
composer require vendor/package
```

u naš proces sada ulazi code koji:

```text
nismo sami napisali
```

Ali production server ga izvršava sa privilegijama naše aplikacije.

Zato:

```text
dependency security
=
application security
```

---

## 28. Supply-chain mentalni model

Naša aplikacija:

```text
Our code
↓
Framework
↓
Composer packages
↓
njihove dependencies
↓
njihove dependencies
```

Možemo direktno zahtevati:

```text
10 packages
```

ali imati:

```text
80+ transitive dependencies
```

u `vendor/`.

Security površina nije samo:

```text
composer.json
```

nego ceo dependency tree.

---

## 29. `composer.lock`

Za application project:

```text
composer.json
→ dozvoljeni version constraints

composer.lock
→ konkretne resolved verzije
```

Na production/deployment-u obično želimo:

```bash
composer install
```

sa postojećim `composer.lock`.

Composer tada koristi tačne verzije zaključane u lock fajlu, umesto da ponovo rešava dependency verzije.

Mentalno:

```text
development/update
→ odlučujemo koje verzije koristimo

deployment/install
→ instaliramo ono što smo već zaključali
```

---

## 30. `composer update` nije production deployment command

`composer update` znači:

```text
pogledaj constraints
↓
ponovo resolve dependency tree
↓
promeni composer.lock
```

To je development/dependency-management operacija.

Deployment uglavnom treba:

```text
existing lock
↓
composer install
```

Ne želiš da production server sam odluči:

```text
"koje nove verzije danas postoje?"
```

---

## 31. Commit `composer.lock`

Za application projekat želiš reproducible dependency set.

Dakle:

```text
composer.json
+
composer.lock
```

idu u repository.

`vendor/` se uglavnom ne commit-uje.

Deployment zatim rekonstruiše dependencies iz lock fajla.

Mentalno:

```text
lock file
→ dependency snapshot
```

---

## 32. Dev dependencies

U `composer.json` imamo:

```json
{
    "require": {
        "...": "..."
    },

    "require-dev": {
        "...": "..."
    }
}
```

`require-dev` može sadržati:

```text
testing tools
debugging tools
static analysis
development helpers
```

Production često nema razlog da ih instalira.

Composer podržava:

```bash
composer install --no-dev
```

čime preskače root `require-dev` dependencies i njihove dev autoload rules.

---

## 33. Zašto `--no-dev`

Manje production dependencies znači:

```text
manji attack surface
manje disk prostora
manje nepotrebnog code-a
manje development tooling-a na serveru
```

To ne znači:

```text
svaki dev package je opasan
```

nego:

```text
ako production ne treba capability
→ ne instaliraj je
```

Least privilege važi i za dependencies.

---

## 34. Production autoloader

Composer podržava optimized autoloading:

```bash
composer install \
    --no-dev \
    --optimize-autoloader
```

Composer dokumentacija preporučuje Level 1 classmap optimization za production, dok agresivniji authoritative mode ima dodatne tradeoff-e kod runtime-generated classes.

Security poenta nije sama brzina.

Poenta je:

```text
production deployment
→ determinističan i namenski
```

ne development environment slučajno uploadovan na server.

---

## 35. `composer audit`

Dependency koja je juče bila legitimna može danas imati objavljenu security ranjivost.

Zato postoji:

```bash
composer audit
```

Aktuelni Composer proverava installed/locked dependency set prema security advisories i drugim dependency policies; dokumentacija navodi i detekciju abandoned i malware-flagged paketa u audit procesu.

Mentalno:

```text
dependency installed
≠ dependency zauvek safe
```

---

## 36. Audit treba da bude ponovljiv proces

Nemoj:

```text
pokrenuo sam composer audit
jednom 2026.
→ gotovo
```

Security advisories nastaju kasnije.

Audit ima smisla u:

```text
development workflow
CI/CD
pre-deployment proveri
periodičnom maintenance-u
```

Drugim rečima:

```text
dependency security
→ lifecycle
```

---

## 37. Moderni Composer dependency policy

Aktuelni Composer ima dependency policy sistem koji može da blokira određene insecure package verzije tokom dependency resolution-a; dokumentacija navodi da je stari `config.audit` policy configuration deprecated u korist `config.policy`.

Za intervju nije potrebno memorisati sve config ključeve.

Važnije je razumeti:

```text
Composer
→ ne služi samo da instalira package
→ može biti deo dependency security kontrole
```

---

## 38. Nemoj ignorisati advisory bez razloga

Loš mindset:

```text
audit fail
↓
ignore sve
↓
deploy
```

Nekad advisory nije primenljiv na naš use case.

Ali ignore treba da ima:

```text
poznat razlog
documentation
owner
review
```

Ne:

```text
"smeta CI-u"
```

---

## 39. Abandoned package

Package može biti:

```text
functional
```

ali više nema aktivnog maintainera.

To nije automatski vulnerability.

Ali povećava rizik:

```text
ko će popraviti budući security bug?
da li radi na novim PHP verzijama?
da li postoji maintained replacement?
```

Dependency health je deo engineering odluke.

---

## 40. Update ne znači "uvek latest odmah"

Security ne znači:

```text
svaki dan update sve na newest major
```

Update može doneti:

```text
breaking changes
new bugs
behavior changes
```

Bolji proces:

```text
security advisory
↓
proceni affected version
↓
upgrade ciljano
↓
tests
↓
deploy
```

---

## 41. Testovi su deo dependency security-ja

Ako dependency update popravlja security problem, ali mi nemamo tests:

```text
strah od update-a
↓
ostajemo na ranjivoj verziji
```

Dobar test suite omogućava:

```text
brže i sigurnije patchovanje
```

Security i maintainability su povezani.

---

## 42. Composer plugins zaslužuju dodatni oprez

Composer plugin nije samo obična library koju application kasnije pozove.

Plugin može biti učitan tokom samog Composer procesa.

Composer zato ima `allow-plugins` kontrolu; u non-interactive režimu novi plugin koji nije eksplicitno dozvoljen može izazvati failure umesto tihog izvršavanja.

Mentalno:

```text
dependency code
→ application runtime

Composer plugin
→ može učestvovati i u dependency/install tooling runtime-u
```

Zato plugin treba instalirati namerno.

---

## 43. "Našao sam package na Packagist-u" nije puna procena

Pre dependency-ja razmisli:

```text
Da li ga zaista trebam?

Da li je maintained?

Koliko dependencies uvodi?

Da li postoji security history?

Koliko je komplikovan?

Da li PHP već ima built-in rešenje?
```

Najbezbednija dependency je ponekad:

```text
dependency koju ne moraš dodati
```

Ali ne treba ni reinventovati kompleksne security komponente bez razloga.

---

## 44. Nemoj sam praviti crypto zato što želiš manje dependencies

Ovo je važna kontra-teža.

Ne znači:

```text
dependencies su rizik
→ sve ću sam
```

Za kompleksne security probleme:

```text
cryptography
HTML sanitization
OAuth/OpenID protocol
JWT validation
```

dobar, održavan battle-tested package može biti mnogo sigurniji od homemade implementacije.

Pravo pitanje:

```text
koje rešenje ima manji ukupni rizik?
```

## 45. Package provenance i names

Posebno pazi na:

```text
typosquatting
```

Na primer developer želi:

```text
vendor/security-package
```

ali instalira slično pogrešno ime.

Pre `composer require` proveri:

```text
tačan vendor
tačan package
official documentation
repository
```

Dependency installation je security-sensitive operacija.

## 46. Production filesystem permissions

Web/PHP process treba da može da piše samo tamo gde stvarno mora.

Tipično:

```text
storage/
cache/
uploads/
logs/
```

Ne:

```text
src/
vendor/
config/
public PHP source
```

ako deployment arhitektura to ne zahteva.

Mentalno:

```text
application runtime
→ read code
→ write samo runtime directories
```

---

## 47. Zašto source code ne treba da bude writable

Ako attacker dobije file-write vulnerability i PHP process može menjati:

```text
public/index.php
src/...
vendor/...
```

možda može pretvoriti:

```text
arbitrary write
```

u:

```text
persistent code execution
```

Ako code directories nisu writable application user-u:

```text
blast radius se smanjuje
```

---

## 48. Upload directory ne treba da izvršava PHP

Ako aplikacija mora da piše u:

```text
uploads/
```

taj folder idealno ne treba da bude executable PHP code location.

Mentalno:

```text
writable
+
executable
```

je opasnija kombinacija.

Bolje:

```text
writable data storage
≠ executable source directory
```

---

## 49. Production user

Nemoj pokretati web application kao:

```text
root
```

ako nije apsolutno neophodno.

Process treba da ima:

```text
minimum OS privileges
```

Ako application bude kompromitovana:

```text
attacker dobija privileges process-a
```

Zato process privileges određuju blast radius.

---

## 50. Production dependencies i source nisu public files

Dobar deployment:

```text
/project
    /src
    /vendor
    /storage
    .env

    /public
        index.php
        assets/
```

Web server:

```text
document root = /project/public
```

Ne treba moći preko browser-a tražiti:

```text
/vendor/...
/composer.json
/composer.lock
/.git/...
/.env
```

## 51. `.git` directory na production web root-u

Ako slučajno deploy-ujemo:

```text
.git/
```

u javno dostupan web tree i server ga servira, možemo otkriti:

```text
.git nije deo public deployment artifact-a
```

a document root je svakako samo:

## 53. PHP production error policy

Konceptualno:

```ini
error_reporting = E_ALL
display_errors = Off
log_errors = On
```

Zašto možemo zadržati broad reporting?

Jer želimo da:

```text
PHP primeti probleme
```

ali ne želimo da ih:

```text
prikaže user-u
```

Reporting i displaying nisu ista stvar.

---

## 54. File permissions nisu `777`

Čest shared-hosting "fix":

```bash
chmod -R 777 storage
```

može rešiti permission error.

Ali security model je:

```text
ko tačno mora da čita?
ko mora da piše?
ko mora da izvršava?
```

Ne:

```text
daj svima sve
```

Princip:

```text
minimum required permissions
```

---

## 55. Deployment secrets ne treba printovati u CI

CI/CD može imati secrets.

Ali build script ne treba da radi:

```bash
echo $PRODUCTION_DB_PASSWORD
```

ili da uključi shell tracing koji prikazuje secret u build log-u.

CI logs su isto:

```text
logs
```

i imaju isti redaction problem.

Dobar CI može uraditi:

```text
composer install from lock
↓
tests
↓
static analysis
↓
composer audit

build/deploy
```

Ne mora svaka mala aplikacija imati savršen enterprise pipeline.

Ali mentalni model je:

```text
security checks treba automatizovati
gde god je praktično
```

jer čovek zaboravlja.

## 57. Monitoring posle deployment-a

Security se ne završava sa:

```text
deploy success
```

Treba moći primetiti:

```text
error spike

```

Observability omogućava:

```text

```

## 58. Incident response mentalni model

Ako posumnjamo da je secret kompromitovan:

```text
1. revoke / rotate

2. ograniči incident

3. proveri logove i scope

4. patch root cause

5. deploy

6. proveri da li postoje drugi povezani secrets

7. dokumentuj šta se dogodilo
```

Ne:

```text
promeni string u .env
→ gotovo
```

## 59. Security patch priority

Ako dependency ima ozbiljnu exploitable vulnerability:

```text

```

nije dobar default.

Prioritet zavisi od:

```text

exposure
exploitability
affected feature
available mitigation
```

Security maintenance je deo normalnog software lifecycle-a.

# Laravel paralela

Laravel `.env`:

```env
APP_ENV=production
APP_DEBUG=false
APP_KEY=...
DB_PASSWORD=...
```

ne treba commit-ovati.

Laravel config često čita environment kroz config files:

```php
'env' => env(
    'APP_ENV',
    'production'
),
```

a application code zatim koristi:

```php
config('app.env');
```

U production deployment-u često koristimo:

```bash
composer install \
    --no-dev \
    --optimize-autoloader
```

sa committed `composer.lock`, a dependency security možemo proveravati kroz:

```bash
composer audit
```

Laravel storage/log/cache direktorijumi zahtevaju write permissions.

Ali source code:

```text
app/
vendor/
routes/
config/
```

ne treba nepotrebno da bude writable web process-u.

I naravno:

```env
APP_DEBUG=true
```

na public production server-u može otkriti detalje koje user nikad ne treba da vidi.

# Najvažnije za zapamtiti

Dependency:

```text
tuđi code
koji izvršava tvoja aplikacija
```

zato:

```text
dependency security
=
application security
```

Za application projekat:

```text
composer.json
+
composer.lock
```

pripadaju repository-ju.

Deployment:

```text
composer install
```

koristi locked versions.

Ne želiš production deployment da radi:

```text
composer update
```

i spontano menja dependency tree.

Production često:

```bash
composer install \
    --no-dev \
    --optimize-autoloader
```

`composer audit`:

```text
proverava dependency security/policy stanje
```

i treba ga koristiti periodično/automatizovano, ne samo jednom.

Manje dependencies:

```text
manji attack surface
```

ali:

```text
ne reinventuj complex security
ako postoji dobro održavano,
battle-tested rešenje
```

Filesystem:

```text
code
→ read-only koliko je praktično

storage/log/cache/uploads
→ writable samo gde treba
```

Ne:

```text
chmod 777 everything
```

Web process:

```text
ne root
```

Web root:

```text
/public
```

Ne smeju biti public:

```text
.env
.git
src
vendor
private storage
```

Production:

```text
display_errors = Off
log_errors = On
```

Loguj:

```text
request ID
user ID
event
exception context
```

Ne loguj:

```text
password
session ID
token
private key
API secret
```

Security lifecycle:

```text
PREVENT
↓
least privilege

DETECT
↓
logs + monitoring

RESPOND
↓
revoke / rotate

RECOVER
↓
patch + redeploy
```

Ako samo jednu rečenicu zapamtiš:

> **Production security nije samo bezbedan PHP kod — to je i bezbedan secret lifecycle, dependency supply chain, filesystem, deployment, logging i sposobnost da kompromitovan credential brzo opozoveš i zameniš.**
