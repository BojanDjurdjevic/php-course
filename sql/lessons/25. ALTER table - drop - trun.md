# 25. ALTER table - drop - trun

## Lekcija 25 — ALTER TABLE, DROP i promena schema-e

Do sada smo uglavnom pravili tabelu pomoću:

```sql
CREATE TABLE
```

Ali aplikacija evoluira.
Danas napraviš:

```text
hotels
-------
id
name
```

sutra ti treba:

city

Nećeš obrisati bazu i napraviti sve ponovo. Menjaš postojeću schema-u pomoću:

```sql
ALTER TABLE
```

---

## Dodavanje kolone

```sql
ALTER TABLE hotels
```

ADD COLUMN city `VARCHAR(100)` NOT NULL;

Mentalno:

```text
ALTER TABLE hotels
→ menjam strukturu hotels
```

```text
ADD COLUMN
→ dodajem novu kolonu
```

Može i:

```sql
ALTER TABLE hotels
```

ADD COLUMN description TEXT NULL;

---

## Menjanje postojeće kolone

U MySQL-u možeš koristiti MODIFY COLUMN.
Recimo:

```sql
ALTER TABLE hotels
```

MODIFY COLUMN name `VARCHAR(200)` NOT NULL;

Promenili smo definiciju postojeće kolone.
Na primer sa:

```php
VARCHAR(100)
```

na:

```php
VARCHAR(200)
```

---

## CHANGE COLUMN

MySQL ima i:

```sql
ALTER TABLE hotels
```

CHANGE COLUMN old_name name `VARCHAR(200)` NOT NULL;

Možeš promeniti i ime i definiciju kolone.
Ali u modernom kodu, kada želiš samo rename, jasnije je:

```sql
ALTER TABLE hotels
```

RENAME COLUMN hotel_name TO name;

---

## Brisanje kolone

```sql
ALTER TABLE hotels
```

DROP COLUMN description;

Ovo je već destruktivno.
Podaci iz te kolone nestaju.
Zato:

```text
ADD
→ uglavnom bezbedniji
```

```text
DROP
→ stani i proveri šta brišeš
```

---

## Dodavanje constraint-a kasnije

Recimo napravio si tabelu:

```sql
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) NOT NULL
);
```

Kasnije shvatiš:

email mora biti unique.

Možeš:

```sql
ALTER TABLE users
```

ADD CONSTRAINT uq_users_email UNIQUE (email);

Ali ovde postoji praktičan problem.
Ako baza već sadrži:

```text
a@test.com
b@test.com
a@test.com
```

MySQL ne može samo da kaže:

Od sada UNIQUE.

Postojeći podaci već krše pravilo.
ALTER će pasti dok ne rešiš duplikate.
Ovo je veoma bitna stvar kod migracija:

Nova schema mora biti kompatibilna i sa postojećim podacima.

---

## Dodavanje foreign key-a

```sql
ALTER TABLE hotels
```

---

## ADD CONSTRAINT fk_hotels_owner

---

## FOREIGN KEY (owner_id)

---

## REFERENCES `users(id)`

ON DELETE RESTRICT;

Opet:

Ako već postoji:

hotels.owner_id = 999

a:

users.id = 999

ne postoji, constraint ne može uredno da se uvede dok ne očistiš podatke.

---

## Dodavanje index-a

Već smo videli:

```sql
ALTER TABLE hotels
```

ADD INDEX idx_hotels_city (city);

ili:

```sql
CREATE INDEX idx_hotels_city
ON hotels(city);
```

Oba pristupa se koriste.
Composite:

```sql
ALTER TABLE hotels
```

ADD INDEX idx_city_active_price (
city,
is_active,
base_price
);

---

## Brisanje index-a

```sql
ALTER TABLE hotels
DROP INDEX idx_hotels_city;
```

ili MySQL sintaksa:

```sql
DROP INDEX idx_hotels_city
ON hotels;
```

---

## Brisanje foreign key-a

Tu je jedna česta zamka.
Ako constraint ima ime:

fk_hotels_owner

onda:

```sql
ALTER TABLE hotels
```

DROP FOREIGN KEY fk_hotels_owner;

Ne:

DROP COLUMN owner_id;

To su dve različite stvari.
Constraint je schema pravilo.
Kolona je podatak/atribut.

```sql
DROP TABLE
```

Ovo:

```sql
DROP TABLE hotels;
```

kaže:

Ukloni ceo table object.

Nestaju:

```text
structure
+
rows
+
indexes
+
constraints vezani za tu tabelu
```

Naravno, foreign key relacije iz drugih tabela mogu sprečiti ili zakomplikovati operaciju.

```sql
DROP DATABASE
```

Još destruktivnije:

```sql
DROP DATABASE booking_app;
```

Ovo briše celu bazu.
Dakle:

```text
DROP COLUMN
→ jedna kolona
```

```text
DROP TABLE
→ jedna tabela
```

```text
DROP DATABASE
→ cela baza
```

## DELETE vs TRUNCATE vs DROP

Ovo je čest interview trio.
DELETE

```sql
DELETE FROM hotels;
```

Briše redove.
Tabela ostaje.
Možeš imati:

```sql
DELETE FROM hotels
WHERE is_active = FALSE;
```

Dakle podržava WHERE.
TRUNCATE

```sql
TRUNCATE TABLE hotels;
```

Kaže:

isprazni celu tabelu.

Nema:

```sql
TRUNCATE TABLE hotels WHERE ...
```

TRUNCATE radi nad celom tabelom.
Tipično je efikasniji način da isprazniš celu tabelu nego red-po-red DELETE.
Takođe resetuje AUTO_INCREMENT brojač u tipičnom MySQL slučaju.
DROP

```sql
DROP TABLE hotels;
```

Ne prazni tabelu.
Uklanja samu tabelu.
Mentalno:

```text
DELETE
→ obriši rows
```

```text
TRUNCATE
→ brzo isprazni celu tabelu
```

```text
DROP
→ obriši samu tabelu
```

---

## Važna transaction nijansa za MySQL

Sećaš se:

```sql
START TRANSACTION;

DELETE FROM hotels;

ROLLBACK;
```

Kod transactional engine-a poput InnoDB, običan DELETE može biti deo transaction-a i rollbackovan.
Ali TRUNCATE TABLE u MySQL-u spada u DDL ponašanje i ne treba ga mentalno tretirati kao običan transactional DELETE.
Isto važi za mnoge DDL operacije:

```text
CREATE
ALTER
DROP
TRUNCATE
```

One imaju posebnu transaction semantiku u MySQL-u.
Za naš nivo dovoljno je da ne kažeš:

"TRUNCATE je samo brži DELETE."

Nije. Semantika je drugačija.

## Laravel paralela

Sve ovo si već viđao:

```php
Schema::table('hotels', function (Blueprint $table) {
    $table->string('city');
});
```

ispod toga postoji ideja:

```sql
ALTER TABLE ...
```

A:

```php
Schema::dropIfExists('hotels');
```

je schema-level operacija koja se svodi na koncept:

```sql
DROP TABLE ...
```

Migracije su ti zapravo version-controlled način upravljanja SQL schema promenama.

## Pitanje 25

Objasni razliku između:

```sql
DELETE FROM hotels;

TRUNCATE TABLE hotels;

DROP TABLE hotels;
```

I reci koji bi od ta tri koristio kada želiš da tabela ostane potpuno ista, ali želiš da obrišeš samo neaktivne hotele.

---

Za tvoje potpitanje:

Koristio bih: DELETE from hovtels -> jer podrzava WHERE is_active = FALSE;

Dakle on brise redove i podrzava filtriranje sa WHERE koje odredjuje koje redove obrisati i ne izmenjuje na drugi nacin tabelu.

TRUNCATE -> brzo pražnjenje tabele s tim st se i ID vrati na 0 pa prvi sledeci unos nosice ID 1. Dakle, kao da kaze ajmo ispocetka.

DROP TABLE -> brise celu tablu sa svim unosima, sto je rizicno. Trajno se gube podaci ali i schema

---

Odlično — 9.8/10.
Jedina sitna preciznost je kod TRUNCATE: bolje je reći da u tipičnom MySQL AUTO_INCREMENT slučaju resetuje brojač na početnu vrednost, pa će sledeći ID obično ponovo biti 1. Nije baš konceptualno „ID se postavi na 0“, iako efekat koji si opisao jeste taj koji ćeš najčešće videti.
Tvoja mapa je inače tačna:

```text
DELETE
→ briše redove
→ može WHERE
→ tabela/schema ostaje
```

```text
TRUNCATE
→ prazni celu tabelu
→ nema WHERE
→ tipično resetuje AUTO_INCREMENT
→ nije samo "brži DELETE"
```

```text
DROP TABLE
→ nestaju redovi + sama tabela/schema
```

I za:

```sql
DELETE FROM hotels
WHERE is_active = FALSE;
```

apsolutno pravi izbor.
