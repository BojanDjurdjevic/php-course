# 35. Stored procedures - func and triggers

## Lekcija 35 — Stored Procedures, Functions i Triggers

Ovo nećemo učiti na nivou DBA-a, ali kao PHP/MySQL developer treba da znaš šta su,
kada imaju smisla i zašto ih često ne guramo svuda.

---

## 1. Stored Procedure

Stored procedure je skup SQL instrukcija koji je sačuvan u samoj bazi i možeš ga pozvati po imenu.
Umesto da application svaki put šalje nekoliko SQL naredbi, može postojati:

CALL `some_procedure(...)`;

Najjednostavniji primer:

DELIMITER //

```sql
CREATE PROCEDURE GetActiveHotels()
BEGIN
    SELECT id, name, base_price
    FROM hotels
    WHERE is_active = TRUE;
```

END //

DELIMITER ;

Posle:

CALL `GetActiveHotels()`;

Mentalno:

```text
Stored Procedure
→ funkcionalnost sačuvana unutar DB servera
→ može sadržati više SQL statement-a
```

DELIMITER ovde nije deo stored procedure logike.
MySQL klijentu samo kažemo da privremeno ne tretira svaki ;
kao kraj cele CREATE PROCEDURE komande.

---

## 2. Procedure sa parametrima

Možemo:

DELIMITER //

```sql
CREATE PROCEDURE GetHotelsByCity(
    IN p_city VARCHAR(100)
)
BEGIN
    SELECT id, name, base_price
    FROM hotels
    WHERE city = p_city;
```

END //

DELIMITER ;

Poziv:

CALL `GetHotelsByCity('Novi Sad')`;

Parametar:

p_city

ulazi u procedure.
Postoje:

```text
IN
OUT
INOUT
```

parametri, ali za sada je dovoljno:

```text
IN
→ prosledi vrednost proceduri
```

---

## 3. Stored procedure može imati transaction logiku

Tehnički možeš imati nešto poput:

```sql
START TRANSACTION;
```

INSERT ...

UPDATE ...

```sql
COMMIT;
```

unutar procedure.
Možeš imati i:

```text
IF
LOOP
variables
error handlers
```

Dakle stored procedure može sadržati prilično ozbiljnu proceduralnu logiku.
Ali tu dolazi arhitektonsko pitanje:

Da li booking business logic želimo u MySQL-u ili u PHP/Laravel service layer-u?

U tvom slučaju bih većinu business logike držao u:

Laravel/PHP Services

dok bi baza čuvala:

```text
data
constraints
transactions
indexes
integrity
```

jer application kod:

- lakše testiraš,
- lakše verzionišeš,
- lakše debug-uješ,
- nije vezan toliko čvrsto za jedan DBMS,
- ostatak tima ga lakše vidi uz ostatak aplikacije.
Stored procedures nisu „loše“. Samo ne treba automatski premestiti application layer u bazu.

---

## 4. Stored Function

Stored function je slična, ali je konceptualno više:

dobije input → vrati jednu vrednost.

Na primer:

DELIMITER //

```sql
CREATE FUNCTION CalculateDiscountedPrice(
    p_price DECIMAL(10,2),
    p_discount DECIMAL(10,2)
)
```

---

## RETURNS `DECIMAL(10,2)`

```text
DETERMINISTIC
BEGIN
    RETURN p_price - COALESCE(p_discount, 0);
END //
```

DELIMITER ;

Onda:

```sql
SELECT
    name,
    CalculateDiscountedPrice(base_price, discount)
FROM hotels;
```

Mentalno:

```text
procedure
→ izvrši operaciju / više SQL statement-a
```

```text
function
→ vrati vrednost
→ može se koristiti u izrazima
```

Ne moramo sada da pišemo custom functions u projektima; bitno je da znaš šta su.
5. Trigger
Trigger je drugačiji i veoma važan koncept.
Trigger kaže:

Kada se određeni DB događaj desi, automatski izvrši ovu logiku.

Na primer:

```text
INSERT
UPDATE
DELETE
```

i može biti:

```text
BEFORE
AFTER
```

Primer:

DELIMITER //

```sql
CREATE TRIGGER hotels_before_insert
```

---

## BEFORE INSERT ON hotels

---

## FOR EACH ROW

```text
BEGIN
    SET NEW.created_at = CURRENT_TIMESTAMP;
END //
```

DELIMITER ;

Znači:

```text
pre svakog INSERT-a u hotels
→ uradi nešto
```

---

## OLD i NEW

U trigger-u ćeš često videti:

```text
NEW
OLD
```

Kod INSERT:

```text
NEW
→ novi red
```

Kod DELETE:

```text
OLD
→ red koji se briše
```

Kod UPDATE:

```text
OLD
→ vrednost pre update-a
```

```text
NEW
→ vrednost posle update-a
```

Na primer audit log:

DELIMITER //

```sql
CREATE TRIGGER hotels_after_price_update
```

---

## AFTER UPDATE ON hotels

---

## FOR EACH ROW

BEGIN

---

## IF OLD.base_price <> NEW.base_price THEN

```sql
        INSERT INTO hotel_price_logs (
            hotel_id,
            old_price,
            new_price,
            changed_at
        )
        VALUES (
            NEW.id,
            OLD.base_price,
            NEW.base_price,
            CURRENT_TIMESTAMP
        );
    END IF;
```

END //

DELIMITER ;

Ako cena ode:

```text
100 → 125
```

trigger automatski napravi log.

---

## 6. Zašto su trigger-i moćni?

Zato što rade bez obzira ko menja podatke.
Ako podatak promeni:

```text
Laravel
PHP skripta
admin SQL
druga aplikacija
```

trigger je na nivou baze i i dalje će se izvršiti.
To može biti odlična garancija za određene DB-level potrebe.

---

## 7. A zašto mogu biti problematični?

Jer imaju skrivenu logiku.
Developer vidi:

```text
UPDATE hotels
SET base_price = 150
WHERE id = 42;
```

i misli:

Menjam jednu vrednost.

Ali u pozadini trigger možda:

```text
insertuje audit log
menja drugu tabelu
radi dodatne provere
```

Ako ne znaš da trigger postoji, debugging može biti mnogo teži.
Zato se trigger-i koriste promišljeno.
Mentalno:

```text
prednost
→ DB garantuje ponašanje
```

```text
mana
→ ponašanje nije očigledno iz application koda
```

---

## 8. Trigger nije zamena za constraint

Recimo:

email mora biti unique.

Nemoj praviti trigger koji ručno proverava duplikate ako baza već ima:

```php
UNIQUE(email)
```

Constraint je bolji alat za constraint posao.
Isto:

hotel.owner_id mora postojati

koristi:

FOREIGN KEY

a ne trigger.
Dobar DB design bira najjednostavniji pravi mehanizam:

```text
UNIQUE problem
→ UNIQUE
```

```text
relation integrity
→ FOREIGN KEY
```

```text
valid value range
→ CHECK
```

```text
automatic reaction to event
→ možda TRIGGER
```

---

## 9. Audit log — klasičan trigger use case

Recimo želiš da sačuvaš svaku promenu cene.
Tabela:

```sql
CREATE TABLE hotel_price_logs (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    hotel_id BIGINT UNSIGNED NOT NULL,
    old_price DECIMAL(10,2) NOT NULL,
    new_price DECIMAL(10,2) NOT NULL,
    changed_at DATETIME NOT NULL
);
```

Trigger može garantovati:

```text
kad god se cena promeni
→ napravi istorijski zapis
```

Čak i ako update nije došao iz Laravel-a.
To je jedan od primera gde trigger može biti vrlo smislen.

## 10. Application events vs DB triggers

U Laravel-u možeš imati:

```text
Model Event
Observer
Event/Listener
Service logic
```

pa na primer:

```php
Hotel::updated(...)
```

To je application-level ponašanje.
Trigger je:

database-level ponašanje

Razlika:

```text
Laravel Observer
→ radi samo kada promena prođe kroz odgovarajući Laravel flow
```

```text
DB Trigger
→ radi kad god DB dobije tu operaciju
```

Ali Laravel event je mnogo vidljiviji i lakši za application testing.
Zato nema univerzalnog:

trigger je bolji

ili:

observer je bolji.

Zavisi gde pravilo pripada.

## 11. Šta bih očekivao na junior/junior-mid intervjuu?

Da znaš:

```text
Stored Procedure
→ SQL rutina sačuvana u bazi
```

```text
Stored Function
→ DB funkcija koja vraća vrednost
```

```text
Trigger
→ automatski se izvršava na INSERT/UPDATE/DELETE događaj
```

```text
BEFORE / AFTER
→ vreme izvršavanja trigger-a
```

```text
OLD / NEW
→ stara i nova vrednost reda
```

I još važnije:

Nemoj gurati svu business logiku u stored procedures/triggers samo zato što možeš.

To je mnogo bolji odgovor nego samo znati sintaksu.

## Pitanje 35

Business pravilo kaže:

users.email mora biti jedinstven.

Drugi zahtev kaže:

Svaki put kada se hotels.base_price promeni, želimo automatski istorijski zapis stare i nove cene.

---

## Za prvi problem, da li bi koristio UNIQUE ili trigger?

Za drugi, zašto bi trigger mogao imati smisla, i koja dva pseudo-reda
(OLD / NEW) bi koristio da dođeš do stare i nove cene?

---

Prvo: Uvek bih koristio UNIQUE kada imamo pptrebu za jedinstvenim poljem
jer to mnogo brze i efikasnije resava od trigera.

Drugo: Triger ovde ima smisla jer ce Baza logovayi svaku promenu cene bez obzira na app flow,
dakle i kada bi DB admin rucno updateovao a ovo je veoma korisna situacija.
Ovde bih za dolazak do stare cene koristio OLD a za novu NEW.

---

Tačno — 10/10. Odgovor ti je baš dobro postavljen i arhitektonski i SQL-logički.
Za prvi slučaj:

users.email mora biti jedinstven

UNIQUE je pravi alat jer je to constraint/integrity pravilo. Ne treba praviti trigger da imitira ono što baza već nativno i mnogo čistije garantuje.
Za drugi slučaj si pogodio suštinu trigger-a:

```text
promena može doći iz Laravel-a
iz neke PHP skripte
iz admin SQL konzole
iz druge aplikacije
```

a trigger će se svejedno izvršiti jer pripada bazi, ne application flow-u.
I da, kod UPDATE trigger-a:

```text
OLD.base_price
→ cena pre izmene
```

```text
NEW.base_price
→ cena posle izmene
```

To je upravo intervju odgovor koji bih očekivao.
