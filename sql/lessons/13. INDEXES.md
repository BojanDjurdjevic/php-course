# 13. INDEXES

## Lekcija 13 — Indexes: zašto baza ne želi da pretražuje sve redove

Sad dolazimo do jedne od najvažnijih tema za performance i intervjue: indeksi.

Zamisli tabelu users sa 5 miliona redova i query:

```sql
SELECT id, name, email
FROM users
WHERE email = 'bojan@test.com';
```

Ako nema odgovarajućeg indeksa, MySQL može morati da pregleda ogroman broj redova:

row 1
row 2
row 3
...
row 5,000,000

To je full table scan.

Indeks pravi dodatnu strukturu koja MySQL-u
pomaže da mnogo brže pronađe redove po određenoj koloni.

Na primer:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Mentalno:

```text
bez indexa
→ "pregledaj celu knjigu"
```

```text
sa indexom
→ "pogledaj indeks na kraju knjige
   i idi direktno na odgovarajuće mesto"
```

---

## Primary key već ima indeks

Ako imamo:

id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY

PRIMARY KEY već podrazumeva indeks.
Zato:

```sql
SELECT *
FROM users
WHERE id = 15;
```

može veoma efikasno da pronađe user-a.

Isto važi za UNIQUE constraint — MySQL
tipično koristi unique index da sprovede jedinstvenost.

Dakle ne praviš dodatno:

```sql
CREATE INDEX idx_users_id ON users(id);
```

ako je id već primary key.
To bi bilo redundantno.

---

## Kada indeks ima smisla?

Najčešće na kolonama koje često koristiš u:

```text
WHERE
JOIN / ON
ORDER BY
GROUP BY
```

Recimo:

```sql
SELECT *
FROM hotels
WHERE owner_id = 15;
```

owner_id je dobar kandidat za indeks:

```sql
CREATE INDEX idx_hotels_owner_id
ON hotels(owner_id);
```

Posebno zato što se često koristi i u relaciji:

```sql
ON h.owner_id = u.id
```

Foreign key i indeks su povezani koncepti, ali nisu isto:

```text
FOREIGN KEY
→ integrity / relacija
```

```text
INDEX
→ performance / pronalaženje
```

---

## Ali index nije besplatan

Ovo je intervju-klasik.

---

## Ako su indeksi tako dobri, zašto ne indeksirati svaku kolonu?

Jer indeks troši:

```text
disk prostor
+
memoriju/cache
+
vreme pri INSERT
+
vreme pri UPDATE
+
vreme pri DELETE
```

Kad ubaciš novi red:

```sql
INSERT INTO users ...
```

MySQL ne mora da promeni samo tabelu nego i relevantne indekse.
Dakle:

```text
više indeksa
→ brži određeni SELECT-i
→ skuplji writes
```

To je tradeoff.

---

## Loš kandidat za indeks

Recimo:

is_active

ima samo:

```text
0
1
```

Ako tabela ima:

```text
5 miliona redova
4.9 miliona active
100k inactive
```

query:

```sql
WHERE is_active = 1
```

vraća skoro celu tabelu.
Samostalni indeks na is_active možda nema mnogo koristi,
jer kolona ima veoma malu selectivity.

Selectivity mentalno znači:

koliko dobro kolona sužava skup rezultata?

Email:

bojan@test.com

možda odgovara jednom redu.
Odlična selectivity.
Boolean:

is_active = 1

možda odgovara 95% tabele.
Slaba selectivity.

To ne znači da boolean nikada ne može biti deo korisnog
indeksa — kasnije ćemo videti composite index.

Primer
Query:

```sql
SELECT id, name
FROM hotels
WHERE city = 'Novi Sad';
```

Ako imamo puno hotela i često filtriramo po gradu:

```sql
CREATE INDEX idx_hotels_city
ON hotels(city);
```

može imati smisla.
Ali odluku ne donosimo:

„ova kolona izgleda važno“

nego:

„kakve query-je aplikacija stvarno izvršava?“

To je pravi način razmišljanja o indeksima.

---

## Brisanje indeksa

Možeš:

```sql
DROP INDEX idx_hotels_city
ON hotels;
```

Schema može evoluirati kako se query patterns menjaju.

---

## Za „2 ujutru“

```text
INDEX
→ dodatna struktura za brže pronalaženje
```

```text
PRIMARY KEY
→ već indexed
```

```text
UNIQUE
→ tipično unique index
```

dobri kandidati:

```text
WHERE
JOIN
ORDER BY
GROUP BY
```

tradeoff:

```sql
SELECT brži
```

```text
writes skuplji
storage veći
```

ne indeksiraj sve naslepo

## Pitanje 13

Imamo tabelu:

```text
users
-----
id
email
name
is_active
created_at
```

i aplikacija veoma često radi:

```sql
SELECT id, name
FROM users
WHERE email = 'some@email.com';
```

a takođe često:

```sql
SELECT id, name
FROM users
WHERE is_active = TRUE;
```

Za koju od ove dve kolone bi ti pre napravio indeks:

```text
email
is_active
```

i zašto?
Usput mi reci i zašto ne bismo jednostavno indeksirali svaku kolonu u tabeli.

---

Prvo: pre bih indexirao kolonu email,
jer ona sizava upit i trazi se samo jedan od milion mailova,
dok na is_active mozemo imati 90% aktivnih kotisnika (sto je cesto kod boolean tipa),
tako da nema mnogo smisla.

PS. Imam protivpitanje za tebe:

Rekli smo da primary i unique su vec indexed. Nije li email unique?
Pa onda samim tim, postavimo unique a ne moramo poseban index, zar ne?

Drugo: Iako ubrzavaju pri selektovanju, Indeksi nisu besplatni
jer zauzimaju memoriju + usporavaju writting (update, delete, insert).

---

Tačno — 10/10, i protivpitanje ti je baš na mestu.
Da: ako je email definisan ovako:

email `VARCHAR(255)` NOT NULL UNIQUE

onda MySQL već ima unique index nad tom kolonom da bi mogao
da sprovede UNIQUE constraint. Dakle ovo bi bilo redundantno:

```sql
CREATE INDEX idx_users_email
ON users(email);
```

Jer već imaš indeks preko:

```php
UNIQUE(email)
```

Mentalno razdvoji svrhu:

```text
UNIQUE
→ business/integrity pravilo:
  vrednost se ne sme ponoviti
```

```text
unique index
→ mehanizam kojim MySQL to efikasno sprovodi
  + ubrzava lookup po toj koloni
```

Zato za users tabelu često vidiš:

```sql
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    ...
);
```

i ništa dodatno za email.

---

## Mala MySQL nijansa: UNIQUE može dozvoliti više NULL vrednosti,

zato za email obično ima smisla kombinacija:

email `VARCHAR(255)` NOT NULL UNIQUE

jer tada stvarno kažeš:

svaki user mora imati email i nijedna dva user-a ne smeju imati isti.

I drugi deo tvog odgovora je tačan:

```text
INDEX
→ ubrzava određene reads
```

ali košta:

```text
→ storage
→ memory/cache
→ INSERT
→ UPDATE
→ DELETE
```

Jer svaki write možda mora da ažurira i indeksnu strukturu.
