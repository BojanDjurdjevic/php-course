# 3. Primary key - unique - foreign and constraints

## Lekcija 3 — PRIMARY KEY, UNIQUE, FOREIGN KEY i constraints

Sada prelazimo na ono što zapravo čini relational model ozbiljnim.

---

## PRIMARY KEY

Primarni ključ jednoznačno identifikuje red.

```sql
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

Pravila mentalno:

```text
PRIMARY KEY
→ unique
→ NOT NULL
→ identitet reda
```

Tabela može imati samo jedan primary key, iako on tehnički može biti sastavljen od više kolona.
Najčešće:

id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY

UNIQUE
UNIQUE znači da se vrednost ne sme ponavljati.
Na primer email:

email `VARCHAR(255)` NOT NULL UNIQUE

Ako već postoji:

bojan@test.com

drugi insert sa istim email-om pada.
To je bitno jer application validation:

```php
if ($emailExists) ...
```

nije dovoljna zaštita protiv race condition-a.
Baza treba da bude poslednja linija odbrane:

```text
application validation
+
DB UNIQUE constraint
```

---

## PRIMARY KEY vs UNIQUE

Oba sprečavaju duplikate, ali nisu isto.

```text
PRIMARY KEY
→ glavni identitet reda
→ ne može NULL
```

```text
UNIQUE
→ dodatno pravilo jedinstvenosti
→ možeš imati više UNIQUE constraint-a
```

Na primer:

id BIGINT PRIMARY KEY,
email `VARCHAR(255)` UNIQUE,
slug `VARCHAR(150)` UNIQUE

---

## FOREIGN KEY

Recimo:

```text
users
id = 15
```

i:

```text
hotels
owner_id = 15
```

Želimo da baza garantuje da hotel ne može da pokazuje na user-a koji ne postoji.

```sql
CREATE TABLE hotels (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    owner_id BIGINT UNSIGNED NOT NULL,

    name VARCHAR(150) NOT NULL,

    FOREIGN KEY (owner_id)
        REFERENCES users(id)
);
```

Mentalno:

```text
hotels.owner_id
→ child / foreign key
```

```text
users.id
→ parent / referenced key
```

Ako pokušaš:

```sql
INSERT INTO hotels (owner_id, name)
VALUES (999999, 'Test Hotel');
```

a user 999999 ne postoji, baza može odbiti insert.
To je referential integrity.

---

## Zašto tipovi moraju da se poklapaju

Ako je:

users.id BIGINT UNSIGNED

onda foreign key treba da bude kompatibilan:

hotels.owner_id BIGINT UNSIGNED

Ne želiš:

```text
users.id BIGINT UNSIGNED
hotels.owner_id INT
```

jer model više nije konzistentan, a MySQL može odbiti constraint.

## ON DELETE CASCADE

Ako obrišeš parent, briši i children.
ON DELETE CASCADE

Primer:

```text
hotel
↓
hotel_images
```

Ako obrišeš hotel, možda želiš da se automatski obrišu njegovi image DB redovi.
Ali oprez:

Cascade briše DB redove, ne filesystem fajlove.

Dakle:

```text
DB CASCADE
≠
unlink image files
```

To ti je direktna veza sa prethodnim filesystem modulom.

---

## ON DELETE SET NULL

Ako parent nestane, foreign key postaje NULL.
owner_id BIGINT UNSIGNED NULL

pa:

```text
FOREIGN KEY (owner_id)
REFERENCES users(id)
ON DELETE SET NULL
```

Ako user nestane:

owner_id = NULL

Ovo ima smisla samo ako kolona dozvoljava NULL.

---

## CHECK constraint

Možemo definisati i poslovna ograničenja:

```text
stars TINYINT UNSIGNED
CHECK (stars BETWEEN 1 AND 5)
```

ili:

```text
price DECIMAL(10,2)
CHECK (price >= 0)
```

Tako baza sama brani određene nevalidne vrednosti.
Mentalno:

```text
validation u PHP-u
→ UX + application rules
```

```text
constraint u DB
→ integrity
```

Oba imaju svoje mesto.

## Primer jedne dobre schema relacije

```sql
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE hotels (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    owner_id BIGINT UNSIGNED NOT NULL,

    name VARCHAR(150) NOT NULL,

    FOREIGN KEY (owner_id)
        REFERENCES users(id)
        ON DELETE RESTRICT
);
```

Ovo garantuje:

```text
svaki hotel ima owner-a
owner mora postojati
ne možeš obrisati owner-a dok ima hotel
email user-a je unique
```

To je već ozbiljan relational model.

## Laravel paralela

Laravel migration:

```php
$table->foreignId('owner_id')
    ->constrained('users')
    ->restrictOnDelete();
```

ispod haube generiše upravo SQL foreign key constraint.
Zato kada znaš SQL, migration prestaje da bude magija.

## Pitanje 3

Imamo:

```text
users
hotels
hotel_images
```

Kako bi ti postavio relacije i ON DELETE ponašanje za:

```text
users → hotels
hotels → hotel_images
```

Odnosno, šta bi stavio kao foreign key i da li bi birao:

```text
RESTRICT
CASCADE
SET NULL
```

u svakom slučaju — i zašto?

---

## Hotels bi sadrzao owner_id a referenca bi bila user.id i

ON DELETE bih najverovatnije stavio Restrict dok bi hotel_images sadrzavale hotel_id as foreign
a referenca bi bila hotel.id s tim sto bih ovde radio CASCADE ON DELETE.

Za slucaj iser - hotel nisam siguran, mozda bih razmislio
i o null mada svakako ne bih voleo da imam hotel u bazi bez ownera.

Hotel images, radije bih nakon brisanja hotela pocistio
i njegove slike kako u db tako i naknadno, posebnom logikom nevezanom za db u filesystemu

---

Odlično — 10/10. Ovde si doneo baš zdrave odluke.
Za:

```text
users → hotels
```

tvoj izbor:

```text
hotels.owner_id
→ FOREIGN KEY
→ REFERENCES users(id)
→ ON DELETE RESTRICT
```

ima smisla jer si jasno rekao:

ne želim hotel bez owner-a.

To je upravo razlog da ne biraš SET NULL. Ako je business rule da svaki hotel mora imati owner-a, onda:

owner_id BIGINT UNSIGNED NOT NULL

plus:

ON DELETE RESTRICT

savršeno izražava to pravilo.
Za:

```text
hotels → hotel_images
```

tvoj izbor:

```text
hotel_images.hotel_id
→ REFERENCES hotels(id)
→ ON DELETE CASCADE
```

je takođe prirodan, jer slika bez hotela nema poslovni smisao.
I posebno dobro što si odmah razdvojio:

```text
DB CASCADE
→ briše hotel_images redove
```

```text
filesystem cleanup
→ mora posebna aplikaciona logika
```

To je tačno i lepo povezuje ovaj modul sa prethodnim.
