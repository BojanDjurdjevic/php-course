## A — Atomicity

Sve ili ništa.

Ako transaction ima pet operacija:

```text
A
B
C
D
E
```

ne želimo:

```text
A ✅
B ✅
C ✅
D ❌
E nije izvršeno
```

ali A/B/C ostanu

nego:

```text
sve ✅
ili
ništa
```

To je atomicity.
Za booking:

booking + inventory

posmatramo kao jednu logičku celinu.

---

## C — Consistency

Transaction treba da prevede bazu:

```text
valid state
→
valid state
```

Ne želimo da nakon operacije ostane:

```text
booking postoji
ali inventory nije smanjen
```

ili:

hotel.owner_id = 999999

ako user ne postoji.
Consistency uključuje i pravila kao:

```text
foreign keys
unique constraints
check constraints
application/domain rules
```

Drugim rečima, baza treba da ostane u stanju koje poštuje pravila.

## Šta ako dva korisnika istovremeno rezervišu poslednju sobu?

Početno:

available = 1

Request A pročita:

available = 1

Request B skoro istovremeno pročita:

available = 1

Oba kažu:

Super, ima soba!

A:

```text
booking A ✅
booking B ✅
```

Imamo overbooking.
Isolation govori o tome kako se paralelne transactions međusobno vide i utiču jedna na drugu.
Tu ćemo kasnije uvesti:

```sql
SELECT ... FOR UPDATE
```

i isolation levels.
To će ti biti vrlo bitno baš za BookYourHotel.

## D — Durability

Kada:

```sql
COMMIT;
```

uspešno završi, očekujemo da potvrđene promene ostanu sačuvane čak i ako server posle toga padne.
Mentalno:

```text
COMMIT uspeo
→ promena je durable
```

## ACID mapa

```text
A — Atomicity
→ sve ili ništa
```

```text
C — Consistency
→ valid state → valid state
```

```text
I — Isolation
→ paralelne transactions ne smeju napraviti haos
```

```text
D — Durability
→ committed data ostaje
```

Jedna stvar koju bih posebno naglasio:

transaction ne znači automatski da si rešio sve concurrency probleme.
Možeš imati:

```sql
START TRANSACTION;

SELECT available
FROM room_inventory
WHERE room_id = 15;
```

-- available = 1

UPDATE ...

```sql
COMMIT;
```

i dva request-a ipak mogu napraviti race condition, zavisno od načina na koji čitaš/zaključavaš podatke.
Zato ćemo odvojeno raditi:

```text
transaction
+
locking
+
isolation
```

## Pitanje 16

Imamo booking flow:

1. INSERT booking
2. UPDATE inventory za 1. novembar
3. UPDATE inventory za 2. novembar
4. UPDATE inventory za 3. novembar

Ako korak 4 padne, objasni:

1. šta bi se desilo bez transaction-a,
2. šta želimo da se desi sa transaction-om,
3. i koji deo ACID-a najdirektnije opisuje to „sve ili ništa“ ponašanje.

---

## 1. Bez transakcije bismo imali:

Kreiran booking,
smanjen availability za 1 i 2 novembar ali ne i za 3. Tako bi imali mogucnost overbookinga za 3. novembar.

---

## 2. Sa transaction zelimo da ako bilo koja od operacija ne uspe, da se uradi ROLLBACK

- "odustani i vrati sve na staro". U tvom konkretnom primeru, ne bismo imali kreiran booking
niti smanjen availability za bilo koji datum. Sve bi bilo kao da korisnik ni nije pokusao da napravi booking.

---

## 3. Atomicity ili lakse za zapamtiti "All or nothing".

---

Tačno — 10/10. Ovo je baš čist odgovor.
Najvažnije si pogodio:

```text
bez transaction-a
→ partial success
→ nekonzistentan state
```

dok sa transaction-om želimo:

```text
START TRANSACTION
→ sve operacije uspeju
→ COMMIT
```

ili

```text
→ jedna padne
→ ROLLBACK
→ ništa ne ostaje promenjeno
```

I da:

Atomicity = All or nothing

to ti je najbolji mnemonic.
Jedina nijansa: u tvom primeru za 3. novembar problem nije samo „mogućnost overbookinga“,
nego šire booking i inventory više ne predstavljaju istu realnost.
Booking kaže da je rezervacija za sva tri dana napravljena, dok inventory za treći datum nije promenjen.
