Lekcija 18 — Isolation levels: Dirty Read, Non-repeatable Read, Phantom Read

Sada možemo da objasnimo slovo I iz ACID-a ozbiljnije.

Isolation odgovara na pitanje:
Koliko jedna transaction sme da vidi ono što druge paralelne transaction rade?

Postoje četiri klasična isolation level-a:
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE

Od najslabijeg ka najstrožem:
READ UNCOMMITTED
        ↓
READ COMMITTED
        ↓
REPEATABLE READ
        ↓
SERIALIZABLE

Što ideš naniže:
više izolacije
→ manje concurrency anomalija
→ potencijalno više čekanja / locking overhead-a

1. Dirty Read
Zamisli:
Transaction A:
START TRANSACTION;

UPDATE rooms
SET price = 500
WHERE id = 15;

Ali još nije:
COMMIT;

Transaction B pročita:
SELECT price
FROM rooms
WHERE id = 15;

i vidi:
500

A onda A uradi:
ROLLBACK;

Znači B je pročitao vrednost koja nikada nije postala committed state.
To je:
DIRTY READ

Mentalno:
Pročitao sam tuđu nepotvrđenu promenu.

READ UNCOMMITTED
Najslabiji isolation level.
Može dozvoliti dirty reads.
Konceptualno:
A promenio podatak
ali još nije commitovao

B
→ može ga videti

Za ozbiljne transactional aplikacije ovo uglavnom nije ono što želiš.
2. READ COMMITTED
Ovde transaction može da vidi samo podatke koji su:
COMMITTED

Dakle dirty read se sprečava.
Ali pojavljuje se druga anomalija.
Non-repeatable read
Transaction A:
START TRANSACTION;

SELECT price
FROM rooms
WHERE id = 15;

dobije:
100

U međuvremenu B:
UPDATE rooms
SET price = 150
WHERE id = 15;

COMMIT;

A ponovo radi:
SELECT price
FROM rooms
WHERE id = 15;

i sada dobije:
150

U istoj transaction:
prvi SELECT  → 100
drugi SELECT → 150

To je:
NON-REPEATABLE READ

Isti red pročitaš dva puta, dobiješ različite committed vrednosti.
3. REPEATABLE READ
Ovo pokušava da obezbedi stabilniji pogled.
Mentalno:
Transaction A počne
↓
čita određeni snapshot
↓
ponovljen običan SELECT
→ vidi konzistentan snapshot

Dakle ako A pročita:
price = 100

a B promeni na:
150

i commit-uje, A pri ponovljenom consistent read-u može i dalje videti:
100

dok A ne završi svoju transaction.
Vrlo bitno za MySQL/InnoDB:
default isolation level je tipično REPEATABLE READ.

To je nešto što vredi znati za intervju.
4. Phantom Read
Ovo nije promena postojećeg reda.
Nego promena skupa redova koji odgovaraju query-ju.
A:
SELECT *
FROM bookings
WHERE hotel_id = 42;

dobije:
10 redova

B zatim:
INSERT INTO bookings (...)
VALUES (... hotel_id = 42 ...);

COMMIT;

A ponovo izvrši isti query.
Ako sada dobije:
11 redova

pojavio se „phantom“ red.
Dakle:
non-repeatable read
→ isti RED promenio vrednost

phantom read
→ promenio se SKUP redova

Ovo je jako dobra interview razlika.
MySQL REPEATABLE READ ima dodatne mehanizme
InnoDB koristi MVCC i locking mehanizme, a kod određenih locking/range operacija može koristiti i:
next-key locks
gap locks

što pomaže i oko phantom/concurrency problema.
Nećemo još duboko u internals, ali želim da znaš da MySQL REPEATABLE READ nije samo banalni snapshot.
5. SERIALIZABLE
Najstroži standardni nivo.
Ideja:
Paralelne transaction ponašaju se mnogo bliže tome kao da se izvršavaju jedna po jedna.

Dobijaš jaču izolaciju, ali cena može biti:
više lock-ova
više čekanja
manji concurrency
više šanse za contention

Dakle nije:
SERIALIZABLE je najbolje
→ koristi uvek

nego tradeoff.
Kako podesiti isolation
Na primer:
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

START TRANSACTION;

ili:
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

Postoji i session/global konfiguracija, ali za sada je bitan koncept.
Velika tabela za pamćenje
Isolation level	Dirty read	Non-repeatable read	Phantom risk
READ UNCOMMITTED	moguće	moguće	moguće
READ COMMITTED	sprečeno	moguće	moguće
REPEATABLE READ	sprečeno	sprečeno za consistent reads	jača zaštita; DB-specifične nijanse
SERIALIZABLE	sprečeno	sprečeno	sprečeno / najstrože


Za interview mentalni model ti je dovoljno:
READ UNCOMMITTED
→ mogu videti uncommitted data

READ COMMITTED
→ vidim samo committed,
  ali isti red može promeniti vrednost

REPEATABLE READ
→ stabilniji snapshot u transaction-u

SERIALIZABLE
→ najjača izolacija,
  najmanje concurrency slobode

Kako ovo povezati sa FOR UPDATE
Važna stvar:
Isolation level i:
SELECT ... FOR UPDATE

nisu ista stvar.
Isolation level definiše opšta pravila vidljivosti i izolacije.
FOR UPDATE kaže:
Ovaj konkretan row/range čitam sa namerom da ga menjam; treba mi locking read.

Zato booking sistem često razmišlja:
transaction
+
odgovarajući isolation
+
SELECT ... FOR UPDATE
ili atomic conditional UPDATE

a ne samo:
START TRANSACTION
→ problem rešen

Za „2 ujutru“
Dirty read
→ čitam tuđ UNCOMMITTED podatak

Non-repeatable read
→ isti red, dva čitanja,
  različita committed vrednost

Phantom read
→ isti query,
  drugačiji skup redova

READ UNCOMMITTED
→ najslabiji

READ COMMITTED
→ bez dirty read

REPEATABLE READ
→ stabilniji snapshot
→ MySQL/InnoDB default tipično

SERIALIZABLE
→ najstroži

Pitanje 18
Objasni svojim rečima razliku između ova tri problema:
dirty read
non-repeatable read
phantom read

I reci zašto ne možemo samo reći:
„Stavi SERIALIZABLE svuda i završili smo priču.“

---

Dirty read
→ čitam tuđ UNCOMMITTED podatak

Non-repeatable read
→ isti red, dva čitanja,
  različita committed vrednost

Phantom read
→ isti query,
  drugačiji skup redova


Drugo: 

SERIALIZABLE ipak nije besplatno, nego trade off.

više lock-ova
više čekanja
manji concurrency
više šanse za contention

---

Tačno — 10/10. Ovo je baš intervju-spreman odgovor.
Najbolja kratka razlika je upravo:
dirty read
→ vidim nešto što možda nikad neće biti COMMIT-ovano

non-repeatable read
→ isti postojeći red pročitam dva puta i dobijem različitu vrednost

phantom read
→ isti uslov/query vratim dva puta, ali se promeni skup redova

I za SERIALIZABLE si pogodio suštinu: jača izolacija nije besplatna. 
Ako sve forsiramo na najstroži nivo, možemo dobiti više čekanja, lock contention-a i manji throughput. 
Cilj je dovoljno jaka izolacija za konkretan problem, ne maksimalna izolacija po svaku cenu.
