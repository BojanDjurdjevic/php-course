# 20. EXPLAIN

## Lekcija 20 — EXPLAIN: kako MySQL planira query

Do sada smo govorili:

„Ovaj indeks bi trebalo da pomogne.“

Sada učimo kako da pitamo MySQL:

„Šta ti zapravo planiraš da uradiš sa ovim query-jem?“

Za to postoji:

EXPLAIN

Recimo:

```text
EXPLAIN
SELECT id, name, base_price
FROM hotels
WHERE city = 'Novi Sad'
  AND is_active = TRUE;
```

MySQL ne izvršava query na uobičajen način samo da bi ti dao rezultate, nego ti pokazuje execution plan.
Mentalno:

```text
SQL query
↓
optimizer
↓
koju tabelu prvo?
```

koji indeks?
koliko redova očekujem da pregledam?
kakav access type?

```text
↓
execution plan
```

---

## Najvažnije kolone u EXPLAIN

Nećemo učiti svaku sitnicu napamet. Za početak su ti najvažnije:

```text
table
type
possible_keys
key
rows
Extra
```

possible_keys
Kaže:

Koje indekse bi MySQL potencijalno mogao da koristi?

Na primer:

possible_keys:

idx_hotels_city_active

To ne znači da ga je stvarno izabrao.
key
Ovo kaže:

Koji indeks je optimizer zaista odlučio da koristi?

Ako vidiš:

key = idx_hotels_city_active

super.
Ako vidiš:

key = NULL

nije odabrao indeks.
rows
Procena koliko redova će MySQL morati da razmotri.
Recimo:

rows = 8

nasuprot:

rows = 2,000,000

veoma različita priča.
To je procena, ne mora biti tačan broj.
type
Ovo je veoma korisno.
Ne znači SQL data type, nego access type.
Videćeš vrednosti kao:

```text
ALL
index
range
ref
eq_ref
const
```

Ne moraš sada njihov kompletan ranking napamet, ali nekoliko treba da prepoznaš.
ALL
type = ALL

obično znači:

full table scan.

Recimo:

```sql
SELECT *
FROM hotels
WHERE description LIKE '%spa%';
```

može dovesti do toga da baza pregleda ogromnu količinu tabele.
ALL nije automatski katastrofa.
Ako tabela ima:

20 redova

full scan je sasvim normalan.
Ako ima:

20 miliona

onda počinjemo da postavljamo pitanja.
const
Query:

```sql
SELECT *
FROM users
WHERE id = 15;
```

gde je id PRIMARY KEY, može biti ekstremno efikasan.
Optimizer praktično zna:

ovde može postojati najviše jedan odgovarajući red.

ref
Često ga vidiš kod indexed lookup-a koji može vratiti više redova.
Na primer:

```sql
SELECT *
FROM hotels
WHERE owner_id = 15;
```

sa indeksom:

```php
INDEX(owner_id)
```

Jedan owner može imati više hotela, pa lookup nije unique.
range
Na primer:

```sql
WHERE base_price BETWEEN 80 AND 150
```

ako postoji odgovarajući indeks.
MySQL traži range unutar indeksne strukture umesto da nužno skenira celu tabelu.
Extra
Ovde se mogu pojaviti korisne informacije.
Na primer:

```text
Using where
Using index
Using filesort
Using temporary
```

Nećemo još paničiti kad vidimo Using filesort. Ime zvuči strašnije nego što jeste — ne znači nužno da MySQL piše fajl na disk.
Poenta je:

EXPLAIN se ne čita kao „zelena/crvena lampica“, nego zajedno sa query-jem, brojem redova, indeksima i workload-om.

---

## Primer pre i posle indeksa

Imamo:

```sql
SELECT id, name
FROM users
WHERE email = 'bojan@test.com';
```

Bez indeksa možeš dobiti nešto konceptualno poput:

```text
type: ALL
key: NULL
rows: 1,000,000
```

Dodamo:

```sql
ALTER TABLE users
```

ADD UNIQUE INDEX uq_users_email (email);

pa ponovo:

```text
EXPLAIN
SELECT id, name
FROM users
WHERE email = 'bojan@test.com';
```

plan može sada biti mnogo bliži:

```text
type: const
key: uq_users_email
rows: 1
```

I sad ne nagađamo da je indeks pomogao — proverili smo query plan.

---

## Optimizer može da ignoriše indeks

Ovo je veoma važno.
Čak i ako postoji:

```php
INDEX(is_active)
```

optimizer može reći:

Ne isplati mi se da ga koristim.

Ako:

95% users imaju is_active = 1

query:

```sql
WHERE is_active = 1
```

ionako vraća skoro celu tabelu.
MySQL može zaključiti da je table scan jeftiniji.
Zato:

```text
INDEX postoji
≠
INDEX mora biti korišćen
```

Optimizer bira plan.

```sql
EXPLAIN + composite index
```

Imamo:

```php
INDEX(city, is_active, base_price)
```

i query:

```text
EXPLAIN
SELECT id, name, base_price
FROM hotels
WHERE city = 'Novi Sad'
  AND is_active = TRUE
  AND base_price BETWEEN 80 AND 150;
```

Tu želimo da vidimo da MySQL zaista koristi naš composite indeks i da procenjeni broj pregledanih redova ima smisla.
To je praktični deo performance rada:

1. imamo spor query
2. pogledamo query
3. EXPLAIN
4. pogledamo postojeće indekse
5. eventualno dizajniramo bolji indeks
6. ponovo EXPLAIN
7. merimo

Ne:

```text
query spor
→ napravi 7 indeksa
→ moli se
```

## Pitanje 20

Dobiješ ovaj pojednostavljen EXPLAIN za tabelu sa 3 miliona users:

```text
type: ALL
possible_keys: NULL
key: NULL
rows: 3000000
```

za query:

```sql
SELECT id, name
FROM users
WHERE email = 'bojan@test.com';
```

Šta ti ovaj plan govori i koja bi ti bila prva schema promena ako email treba da bude jedinstven za svakog korisnika?

---

Ovaj plan kaze:

Ne koristim bas nikakve indexe, skeniram bukvalno sve iz tabele i jednog divnog dana... kada pregledam 3M redova... vraticu ti jedan jedinstveni rezultat.

Dakle, najsmisleniji prvi korak je: dodati UNIQUE na email, jer treba naci samo jednog, suzena pretraga.

---

Tačno — 10/10. 😄 I opis EXPLAIN plana ti je odličan:

```text
type: ALL
key: NULL
rows: 3,000,000
```

znači otprilike:

„Nemam koristan indeks, pa ću pregledati praktično celu tabelu da bih našao jedan email.“

A pošto je business rule da email mora biti jedinstven, ne bih pravio samo običan:

```php
INDEX(email)
```

nego upravo:

```sql
ALTER TABLE users
```

ADD CONSTRAINT uq_users_email UNIQUE (email);

Time dobijamo dve stvari odjednom:

```text
integrity
→ dva user-a ne mogu imati isti email
```

```text
performance
→ MySQL dobija unique index za lookup
```

Posle toga EXPLAIN može pokazati drastično bolji plan, sa približno jednim očekivanim redom.
