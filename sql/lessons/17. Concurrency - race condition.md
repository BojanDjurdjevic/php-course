# 17. Concurrency - race condition

## Lekcija 17 — Concurrency, race condition i SELECT ... FOR UPDATE

Sad ulazimo u deo koji je posebno važan za booking sisteme.
Transaction sama po sebi nije dovoljna ako dva request-a rade istovremeno.
Zamisli:

room_inventory

```text
room_id = 15
date = 2026-11-01
available = 1
```

Dva korisnika istovremeno rezervišu poslednju sobu.
Request A:

```sql
SELECT available
FROM room_inventory
WHERE room_id = 15
  AND date = '2026-11-01';
```

dobije:

1

Request B nekoliko milisekundi kasnije uradi isto i takođe dobije:

1

Oba request-a sada misle:

Ima slobodna soba.

Pa oba naprave booking.
To je race condition.

---

## Naivna transaction nije nužno dovoljna

Možeš imati:

```sql
START TRANSACTION;

FROM room_inventory
WHERE room_id = 15
  AND date = '2026-11-01';
```

-- application proveri available > 0

## UPDATE room_inventory

## SET available = available - 1

```sql
WHERE room_id = 15
  AND date = '2026-11-01';

COMMIT;
```

Ako dva request-a paralelno uđu u ovaj flow, moraš da razmišljaš o tome ko sme da čita/menja taj red i kada.
Tu dolazi row-level locking.

```sql
SELECT ... FOR UPDATE
```

Ako unutar transaction-a uradiš:

```sql
START TRANSACTION;

SELECT available
FROM room_inventory
WHERE room_id = 15
  AND date = '2026-11-01'
FOR UPDATE;
```

kažeš MySQL-u otprilike:

Ove redove čitam zato što planiram da ih menjam — zaključaj ih za konkurentne write operacije dok moja transaction ne završi.

Flow:

```text
Request A
↓
START TRANSACTION
↓
SELECT ... FOR UPDATE
↓
lock inventory row
↓
available = 1
```

Request B zatim pokuša:

```sql
SELECT ... FOR UPDATE
```

nad istim redom.
Ne dobija slobodno isti state i nastavlja paralelno, nego tipično mora da čeka da A završi.
A zatim A:

UPDATE room_inventory

## Lock traje do kraja transaction-a

Vrlo važno:

```sql
SELECT ... FOR UPDATE
```

ima smisla u transaction-u.
Lock se tipično drži do:

```sql
COMMIT;
```

ili:

```sql
ROLLBACK;
```

Zato transaction treba da bude:

```text
kratka
precizna
bez nepotrebnog sporog posla
```

Ne želiš:

```text
START TRANSACTION
↓
lock row
↓
pozovi eksterni API 12 sekundi
↓
generiši PDF
↓
pošalji email
↓
COMMIT
```

jer drugim request-ovima držiš resurse zaključane mnogo duže nego što je potrebno.
Bolje:

```text
START TRANSACTION
↓
lock/check/update DB state
↓
COMMIT
↓
tek onda email/PDF/API
```

gde god business flow dozvoljava.

## Lost update

Još jedan concurrency problem:

Početno:

available = 5

A pročita:

5

B pročita:

5

A izračuna u PHP-u:

5 - 1 = 4

B takođe:

5 - 1 = 4

oba urade:

```text
UPDATE room_inventory
SET available = 4
```

Finalno:

4

a trebalo je:

3

Jedan decrement je izgubljen.
To je lost update.
Zato je često bolje raditi atomic DB update:

```text
UPDATE room_inventory
SET available = available - 1
WHERE room_id = 15
  AND date = '2026-11-01';
```

nego:

```text
SELECT 5
↓
PHP izračuna 4
↓
UPDATE SET available = 4
```

Ali i dalje moraš obezbediti da ne ode ispod nule.

---

## Još bolji atomic pattern

Možeš čak:

```text
UPDATE room_inventory
SET available = available - 1
WHERE room_id = 15
  AND date = '2026-11-01'
  AND available > 0;
```

Ako je:

available = 1

jedan request uspešno ga pretvori u:

0

drugi request više ne zadovoljava:

available > 0

pa update utiče na:

0 rows

Application onda proverava broj affected rows.
Ako je:

```text
1 affected row
→ uspešno rezervisano
```

```text
0 affected rows
→ nema availability
```

Ovo je veoma moćan pattern.
U nekim flow-ovima može čak biti jednostavniji od posebnog:

```sql
SELECT ... FOR UPDATE
```

ali zavisi šta sve treba da proveravaš pre booking-a.

## Deadlock — samo uvod

Kad više transaction-a zaključava više redova, može nastati:

```text
A drži row 1
i čeka row 2
```

```text
B drži row 2
i čeka row 1
```

To je deadlock.
MySQL može detektovati takvu situaciju i jednu transaction prekinuti.
Zato se u ozbiljnim sistemima često vodi računa da se resursi zaključavaju doslednim redosledom.
Na primer datume uvek:

```sql
ORDER BY date
FOR UPDATE;
```

O deadlock retry logici ćemo detaljnije kad dođemo do PDO/application transaction-a.

## Pitanje 17

Imamo:

available = 1

i dva korisnika istovremeno pokušavaju da rezervišu poslednju sobu.
Objasni svojim rečima:

1. kako može nastati overbooking bez locking-a,
2. kako SELECT ... FOR UPDATE rešava problem,
3. i zašto je ovaj query zanimljiv kao alternativa:

```text
UPDATE room_inventory
SET available = available - 1
WHERE room_id = 15
  AND date = '2026-11-01'
  AND available > 0;
```

posebno ako posle proverimo broj affected rows.

---

## 1. Transakcija, sama po sebi, ne resava problem overbooking-a jer ne zaključ̣ava redove, pa se dogodi:

Request A ->čita availability i vidi 1 sobu
Request B isto to.
Transakcije provere availability, odrade booking i smanje availability, svaka posebno prođe - overbooking.

---

## 2. Tu dolazi SELECT ... FOR UPDATE; ovo for update kaze: selektuj mi ovo s namerom da kad dobijem rezultate iste izmenim.

Pa onda dok request A čita, B čeka... Transakcija A se zavrsi (sa commiy ili rollback), B pocinje da čita).

---

## 3. Ovaj query je dobra alternativa jer sprečava race condition i lost update jer ovde sql računa i umanjyje availability a ne php.

Php sam po sebi ne zna stanje, uzima ga iz baze a baza ima svoje stanje i kaze
availability = availabiliti - 1 -> trenutni availability -1 i ovo na kraju AND available > 0 osigurava da se nece ići ispod 0.

---

Odlično — 9.7/10. Suštinski si razumeo concurrency problem kako treba.
Samo jedna važna preciznost oko prve rečenice:

„Transakcija sama po sebi ne zaključava redove“

to je malo preširoko rečeno.
Preciznije:

```text
transaction sama po sebi
→ ne znači da će običan SELECT zaključati pročitane redove
```

Ali UPDATE, DELETE i određene locking reads svakako koriste lock-ove.
Dakle problem je više ovo:

```sql
START TRANSACTION;

SELECT available
FROM room_inventory
WHERE ...;
```

Običan SELECT ne znači automatski:

„zaključaj ovaj inventory red za mene dok ne završim.“

Zato oba request-a mogu pročitati availability na način koji vodi ka race condition-u, zavisno od flow-a.
Drugi deo ti je odličan:

```text
A → SELECT ... FOR UPDATE → lock
B → pokušava isti locking read → čeka
```

```text
A → COMMIT / ROLLBACK
→ lock se oslobađa
```

```text
B → nastavlja i vidi novo stanje
```

I treći deo je takođe vrlo dobar. Posebno želim da zapamtiš ovo:

```text
UPDATE room_inventory
SET available = available - 1
WHERE room_id = 15
  AND date = '2026-11-01'
  AND available > 0;
```

ovde:

```text
provera available > 0
+
decrement
```

nisu dve application operacije:

```text
READ
↓
PHP IF
↓
WRITE
```

nego deo jedne SQL write operacije.
To drastično smanjuje prostor za race condition.
A onda je ključ:

```text
affected rows = 1
→ uspeo sam da rezervišem inventory
```

```text
affected rows = 0
→ uslov available > 0 nije zadovoljen
→ nema availability
```

To će ti kasnije kroz PDO biti veoma prirodno:

```php
$stmt->rowCount();
```

Tu ćemo ga konkretno koristiti.
