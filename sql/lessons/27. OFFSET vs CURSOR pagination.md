# 27. OFFSET vs CURSOR pagination

## Lekcija 27 — OFFSET pagination vs cursor/keyset pagination

Sećaš se našeg:

```sql
SELECT *
FROM hotels
ORDER BY id
LIMIT 10 OFFSET 20;
```

To znači:

```text
preskoči 20
vrati sledećih 10
```

i odgovara otprilike:

```text
page 1 → OFFSET 0
page 2 → OFFSET 10
page 3 → OFFSET 20
```

Formula:

offset = (page - 1) * perPage

To je klasična pagination.

---

## Problem velikog OFFSET-a

Recimo:

```sql
SELECT id, name
FROM hotels
ORDER BY id
LIMIT 20 OFFSET 1000000;
```

Na prvi pogled kažeš:

Treba mi samo 20 redova.

Ali baza često mora da prođe kroz ogroman broj prethodnih
redova da bi došla do mesta gde treba da počne.

Mentalno:

```text
pronađi/sortiraj rezultat
↓
preskoči 1,000,000
↓
vrati 20
```

Zato duboke stranice mogu postati skupe.
Dakle:

```text
OFFSET 20
→ nikakav problem
```

```text
OFFSET 1,000,000
→ može postati veoma skup
```

---

## Keyset / cursor pagination

Ako rezultate stabilno sortiramo po id, umesto:

```sql
LIMIT 20 OFFSET 1000000
```

možemo klijentu zapamtiti poslednji ID koji je video.
Recimo poslednji red prethodne strane:

id = 52840

Sledeći query:

```sql
SELECT id, name
FROM hotels
WHERE id > 52840
ORDER BY id ASC
LIMIT 20;
```

Mentalno:

Ne zanima me koja je ovo stranica. Daj mi sledećih 20 posle poslednjeg reda koji sam video.

Ako je id indexed/PK, ovo može biti veoma efikasno.

```text
id > 52840
↓
idi direktno u odgovarajući deo indeksa
↓
uzmi sledećih 20
```

---

## OFFSET vs cursor mentalni model

```text
OFFSET pagination
→ "daj mi stranicu broj 50001"
```

```text
cursor pagination
→ "nastavi posle ovog reda"
```

OFFSET je odličan kada ti treba:

page 1
page 2
page 3
...

i user može da skače:

1 2 3 ... 50

Cursor je odličan za:

```text
Load more
infinite scroll
API feed
velike tabele
```

---

## Stabilnost rezultata

Još jedan problem OFFSET pagination-a je što se podaci mogu promeniti između request-ova.
Recimo imamo:

page 1:

```text
100
99
98
97
```

sortirano:

```sql
ORDER BY id DESC
```

U međuvremenu neko ubaci novi red:

101

Kad user traži page 2 sa OFFSET-om, pomeranje redova može dovesti do:

```text
duplikata
ili
preskočenog reda
```

Cursor pristup:

```sql
WHERE id < 97
ORDER BY id DESC
LIMIT 4;
```

kaže:

Nastavi strogo posle poslednjeg reda koji sam već video.

To je često stabilnije za feed-style rezultate.

---

## Descending cursor

Ako ideš:

```sql
ORDER BY id DESC
```

onda sledeća strana nije:

```sql
WHERE id > last_id
```

nego:

```sql
WHERE id < last_id
```

Primer:

```sql
SELECT id, name
FROM hotels
WHERE id < 52840
ORDER BY id DESC
LIMIT 20;
```

Mentalno:

```text
ASC
→ id > last_id
```

```text
DESC
→ id < last_id
```

---

## A šta ako sortiram po created_at?

Može:

```sql
SELECT id, created_at, name
FROM bookings
WHERE created_at < '2026-10-14 20:00:00'
ORDER BY created_at DESC
LIMIT 20;
```

Ali postoji problem:

više redova može imati isti created_at.
Zato je često bolji deterministic cursor sa:

created_at + id

i odgovarajućim composite index-om.
Na primer:

```sql
ORDER BY created_at DESC, id DESC
```

i cursor čuva obe vrednosti.
To je naprednija verzija, ali ideja je ista:

sorting mora biti determinističan

---

## Laravel paralela

Sada vidiš razliku između koncepata iza:

```php
Model::paginate(20);
```

i:

```php
Model::cursorPaginate(20);
```

`paginate()` tipično razmišlja u smislu:

```text
COUNT
+
LIMIT/OFFSET
+
page number
```

dok `cursorPaginate()` koristi vrednosti sortiranja kao cursor i izbegava duboki OFFSET.
Laravel nije izmislio drugi tip pagination-a — samo ti daje API preko SQL koncepta.

---

## Kada koji koristiti?

Praktično:

Admin tabela sa:

```text
1 2 3 4 5
→ OFFSET pagination je sasvim normalna
```

```text
Infinite scroll / feed
→ cursor vrlo prirodan
```

```text
milioni redova + duboka pagination
→ cursor često mnogo bolji
```

```text
moram direktno na page 742
→ OFFSET je jednostavniji
```

Nije:

cursor je uvek bolji.

Ponovo tradeoff i business requirement.

---

## Za „2 ujutru“

```text
OFFSET
→ preskoči N redova
→ velike vrednosti mogu biti skupe
```

```text
cursor/keyset
→ nastavi posle poslednjeg viđenog reda
```

ASC:

```sql
WHERE id > last_id
```

DESC:

```sql
WHERE id < last_id
```

cursor:

```text
→ brz za velike rezultate
→ odličan za load-more/feed
→ nije prirodan za "idi direktno na page 57"
```

## Pitanje 27

Imamo milion booking-a i API vraća po 20, sortirano:

```sql
ORDER BY id DESC
```

Korisnik je upravo dobio stranicu čiji poslednji booking ima:

id = 845000

Napiši query za sledećih 20 booking-a koristeći cursor/keyset pagination.
I objasni zašto ovde koristiš:

id < 845000

a ne:

id > 845000

---

```sql
SELECT id, hotel_name
FROM bookings
WHERE id < 845000
ORDER BY id DESC
LIMIT 20;
```

Zato sto idemo unazad - DESC i < dakle treba nam manji od poslednjeg pa uzimamo sledecih 20

---

Tačno — 10/10.

```sql
SELECT id, hotel_name
FROM bookings
WHERE id < 845000
ORDER BY id DESC
LIMIT 20;
```

Logika ti je potpuno ispravna:

```text
DESC
→ idemo od većih ka manjim ID-jevima
```

poslednji viđen ID = 845000

```text
sledeća strana
→ mora da nastavi ispod njega
```

```sql
WHERE id < 845000
```

Da je bilo:

```sql
ORDER BY id ASC
```

onda bismo koristili:

```sql
WHERE id > last_id
```

To je cela cursor logika u jednoj slici:

```text
ASC  → >
DESC → <
```
