# 21. SARGable query

## Lekcija 21 — SARGable query: kako da ne „pokvarimo“ dobar indeks

Sad jedna vrlo praktična tema.

Možeš imati savršeno napravljen indeks,
ali napisati query tako da MySQL ne može lako da ga iskoristi.

Pretpostavimo:

```sql
CREATE INDEX idx_users_created_at
ON users(created_at);
```

I hoćemo users kreirane tokom 2026.
Na prvi pogled ovo izgleda lepo:

```sql
SELECT *
FROM users
WHERE YEAR(created_at) = 2026;
```

Ali imamo problem.
Primeniš funkciju:

```php
YEAR(created_at)
```

na indeksiranu kolonu.
Indeks je organizovan po vrednostima:

2025-12-31 10:20:00
2026-01-01 08:00:00
2026-01-02 12:30:00
...

a ne po rezultatu funkcije:

2025
2026
2026
...

Zato optimizer često ne može da iskoristi običan indeks na created_at tako efikasno.
Mnogo bolji query:

```sql
SELECT *
FROM users
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01';
```

Sada kažemo:

Nađi mi range direktno u indeksiranoj vrednosti.

To je SARGable query.
SARGable približno znači:

Search ARGument able — uslov koji baza može efikasno koristiti za index lookup/range scan.

---

## Isto sa datumom

Lošiji pattern:

```sql
WHERE DATE(created_at) = '2026-10-14'
```

Bolji:

```sql
WHERE created_at >= '2026-10-14 00:00:00'
  AND created_at <  '2026-10-15 00:00:00'
```

I primeti da koristim:

< '2026-10-15'

a ne nešto poput:

<= '2026-10-14 23:59:59'

---

## Zašto?

Jer sa fractional seconds možeš imati:

23:59:59.123456

Half-open range:

```text
>= početak
< sledeći početak
```

je mnogo čistiji.
To ti je posebno korisno za booking/date query-je.

---

## LIKE i indeks

Pretpostavimo:

```php
INDEX(name)
```

Ovo:

```sql
WHERE name LIKE 'Danube%'
```

može biti vrlo pogodno za indeks.

---

## Zašto?

Jer zna početak:

Danube...

i može tražiti odgovarajući range.
Ali:

```sql
WHERE name LIKE '%Danube%'
```

je mnogo problematičnije.
Pošto ne zna gde string počinje:

Grand Danube

---

## Hotel Danube

My Danube Resort
...

običan B-tree indeks ne može na isti način da kaže:

Idi direktno na deo indeksa koji počinje sa Danube.

Dakle:

```text
'Danube%'
→ index-friendly mnogo češće
```

```text
'%Danube%'
→ leading wildcard često sprečava efikasan index seek
```

Za ozbiljno full-text search pretraživanje postoje drugi alati/indeksi, ali to je posebna tema.

---

## Izbegavanje računanja nad kolonom

Pretpostavimo indeks:

```php
INDEX(base_price)
```

Lošiji query:

```sql
WHERE base_price * 1.20 < 200
```

Čitljivije za indeks:

```sql
WHERE base_price < 200 / 1.20
```

Ideja je:

Kada možeš, ostavi indeksiranu kolonu „golu“ na jednoj strani poređenja.

Mentalno:

`function(indexed_column)` ❌ često lošije

indexed_column operator constant ✅ često bolje

Naravno, optimizer je pametan i MySQL ima functional/generated-column mogućnosti,
ali kao default mentalni model ovo je veoma dobro pravilo.

---

## Composite index + range — jedna važna nijansa

Imali smo:

```php
INDEX(city, is_active, base_price)
```

i:

```sql
WHERE city = 'Novi Sad'
  AND is_active = TRUE
  AND base_price BETWEEN 80 AND 150
```

Odlično:

```text
city       = equality
is_active  = equality
base_price = range
```

Ali zamisli indeks:

```php
INDEX(city, base_price, is_active)
```

a query isti.
Mentalno dolazimo do:

```text
city       = equality
base_price = range
is_active  = equality
```

Kada dođeš do range dela indeksa, kolone posle range-a često više
ne mogu jednako efikasno da učestvuju u sužavanju index range-a.

Zato smo rekli da je često dobar obrazac:

```text
equality
→ equality
→ range
```

a ne:

```text
equality
→ range
→ equality
```

Nije apsolutni zakon za svaki mogući optimizer plan, ali je veoma dobra polazna tačka.

```sql
ORDER BY i indeks
```

Indeks ponekad može pomoći i pri sortiranju.
Imamo:

```php
INDEX(city, base_price)
```

Query:

```sql
SELECT id, name, base_price
FROM hotels
WHERE city = 'Novi Sad'
ORDER BY base_price ASC;
```

Pošto su unutar indeksa vrednosti organizovane po:

```text
city
→ base_price
```

MySQL potencijalno može efikasno pronaći Novi Sad i dobiti rezultate već u korisnom price redosledu.
To znači da indeks nije samo:

```sql
WHERE optimization
```

nego može uticati i na:

```text
ORDER BY
GROUP BY
JOIN
```

Nemoj:

nego:

```sql

```

i proveri.
Workflow:

```text

↓

↓

↓

```

## Koji query bi pre izabrao i zašto?

```sql
SELECT *
FROM bookings
WHERE DATE(created_at) = '2026-10-14';
```

ili:

```sql
SELECT *
FROM bookings
WHERE created_at >= '2026-10-14 00:00:00'
  AND created_at <  '2026-10-15 00:00:00';
```

I dodatno: zašto je:

```sql
LIKE 'Danube%'
```

obično pogodniji za običan B-tree indeks nego:

```sql
LIKE '%Danube%'
```

?

---

Prvo: Izabrao bih drugi upit jer funkcije kao `DATE()` ili YEAR
ne idu bas uz ondexe i bolje je staviti golu kolonu sa jedne strane poredjenja.

Drugo: 'Danube%' je pogodniji za index jer index onda zna pocetak stringa dok LIKE '%Danube%' - leading wildcard

---

Tačno — 10/10.
Prvi deo si pogodio upravo kako treba:

```php
DATE(created_at)
YEAR(created_at)
```

stavljaju funkciju nad indeksiranu kolonu, pa običan indeks na created_at često ne može da se koristi tako efikasno kao kada ostaviš kolonu „golu“:

```sql
WHERE created_at >= '2026-10-14 00:00:00'
  AND created_at <  '2026-10-15 00:00:00'
```

To je mnogo bolji SARGable obrazac.
I drugi deo je tačan:

```sql
LIKE 'Danube%'
```

zna početak stringa, pa B-tree indeks može mnogo prirodnije da pronađe odgovarajući range.
Dok:

```sql
LIKE '%Danube%'
```

ima leading wildcard — ne znaš gde Danube počinje, pa običan B-tree lookup gubi najveći deo svoje prednosti.
