Filesystem path nije URL
Ovo smo već malo videli kod upload zadatka.
Pretpostavimo projekat:
C:\laragon\www\myapp\

i fajl:
C:\laragon\www\myapp\uploads\15\avatar.webp

To je filesystem path.
PHP-u treba takva putanja da bi uradio:
file_exists(...)
unlink(...)
file_get_contents(...)
move_uploaded_file(...)

Ali browser ne koristi:
C:\laragon\www\myapp\uploads\15\avatar.webp

Browser eventualno koristi nešto poput:
/uploads/15/avatar.webp

ili:
https://example.com/uploads/15/avatar.webp

Dakle:
FILESYSTEM PATH
→ gde se fajl fizički nalazi za PHP/OS

PUBLIC PATH / URL
→ kako mu klijent pristupa preko HTTP-a

To je veoma važna razlika.
__DIR__
U PHP-u:
__DIR__

daje direktorijum trenutnog PHP fajla.
Recimo da je:
C:\laragon\www\myapp\store.php

onda:
echo __DIR__;

može dati:
C:\laragon\www\myapp

Zato je ovo mnogo pouzdanije:
$path = __DIR__ . '/uploads/file.txt';

nego:
$path = 'uploads/file.txt';

Druga varijanta je relative path i može zavisiti od current working directory-ja procesa.
__DIR__ ti daje stabilnu referentnu tačku.
DIRECTORY_SEPARATOR
Možemo:
$path = __DIR__
    . DIRECTORY_SEPARATOR
    . 'uploads'
    . DIRECTORY_SEPARATOR
    . 'avatar.webp';

Na Windows-u je separator tipično:
\

na Linux/macOS:
/

PHP uglavnom sasvim lepo prihvata / čak i na Windows-u, pa je:
__DIR__ . '/uploads/avatar.webp'

često potpuno praktično i čitljivije.
Ali treba da znaš šta DIRECTORY_SEPARATOR predstavlja.
Absolute vs Relative path
Absolute:
C:\laragon\www\myapp\uploads\a.jpg

ili Linux:
/var/www/myapp/uploads/a.jpg

Relative:
uploads/a.jpg

Relative znači:
„u odnosu na trenutno mesto iz kog se putanja razrešava“.

Zato kod backend fajlova često radimo:
$uploadDir = __DIR__ . '/uploads';

umesto da se oslanjamo na:
$uploadDir = 'uploads';

Osnovne filesystem provere
PHP ima nekoliko funkcija koje želim da razlikuješ:
file_exists($path);

pita:
postoji li nešto na ovoj putanji?

Može biti file ili directory.
is_file($path);

pita:
postoji li baš regularan fajl?

is_dir($path);

pita:
postoji li direktorijum?

Na primer:
$path = __DIR__ . '/uploads';

if (!is_dir($path)) {
    mkdir($path, 0755, true);
}

Treći argument:
true

znači recursive creation.
Ako želiš:
uploads/users/15/avatar

a roditeljski direktorijumi još ne postoje, true omogućava PHP-u da napravi celu potrebnu strukturu.
realpath()
realpath($path)

pokušava da vrati canonical absolute path.
Na primer:
$path = __DIR__ . '/uploads/../uploads/avatar.jpg';

$real = realpath($path);

može rezultirati pravom normalizovanom putanjom.
Ali postoji bitna stvar:
realpath() obično zahteva da target već postoji.

Zato nije funkcija koju slepo koristiš kada tek želiš da kreiraš novi fajl.
Kasnije će nam biti veoma korisna kada budemo pričali o path traversal zaštiti.
Prva security tema — nikad slepo user input u putanju
Ovo je veoma loše:
$file = $_GET['file'];

$path = __DIR__ . '/uploads/' . $file;

echo file_get_contents($path);

Korisnik možda pošalje nešto nalik:
?file=../../config.php

i pokušava da izađe iz uploads direktorijuma.
To se zove path traversal / directory traversal.
Zato je mnogo bezbedniji dizajn da aplikacija kontroliše putanje.
Na primer umesto:
GET /download.php?file=../../nešto

korisnik pošalje:
GET /download.php?id=52

pa ti iz baze pronađeš trusted-ish stored path za file ID 52, proveriš authorization i tek onda pristupiš fajlu.
To je isti princip koji već znaš:
user-controlled input
≠
trusted filesystem path

Prvo pitanje Modula 4
Pretpostavimo:
$path = __DIR__ . '/uploads/avatar.jpg';

Objasni mi svojim rečima razliku između:
file_exists($path)
is_file($path)
is_dir($path)

i zašto bi kod direktorijuma za upload radije koristio:
if (!is_dir($uploadDir)) {
    mkdir(...);
}

nego samo:
if (!file_exists($uploadDir)) {
    mkdir(...);
}

file_get_contents()
success → string
failure → false

file_put_contents()
success → int broj bytes
failure → false

Lekcija 3 — fopen(), fread(), fwrite(), fclose()
file_get_contents() i file_put_contents() su odlični kada želiš da odjednom pročitaš ili upišeš sadržaj.
Ali PHP ima i niži nivo rada preko file handle-a.
Na primer:
$handle = fopen($path, 'r');

fopen() otvara fajl i vraća resource/stream handle koji koristiš za dalje operacije.
Ako ne uspe:
false

pa:
$handle = fopen($path, 'r');

if ($handle === false) {
    throw new RuntimeException('Could not open file.');
}

Onda možeš:
$content = fread(
    $handle,
    filesize($path)
);

i na kraju:
fclose($handle);

Mentalno:
fopen
↓
dobiješ handle
↓
read/write
↓
fclose

Modes su veoma važni
Na primer:
fopen($path, 'r');

znači:
read only
file mora postojati

fopen($path, 'w');

znači:
write
ako postoji → truncate na 0 bytes
ako ne postoji → napravi

Ovo je važna zamka: 'w' briše postojeći sadržaj čim otvoriš fajl.
fopen($path, 'a');

znači:
append
piši na kraj
napravi fajl ako ne postoji

fopen($path, 'x');

je zanimljiv:
create for writing
ali FAIL ako fajl već postoji

To može biti korisno kada ne želiš accidental overwrite.
Postoje i + varijante:
r+ → read + write
w+ → read + write, truncate/create
a+ → read + append

Za sada mi je najvažnije da bez gledanja znaš:
r → read
w → write + overwrite/truncate
a → append
x → create only if nonexistent

fwrite()
Primer:
$handle = fopen($path, 'a');

if ($handle === false) {
    throw new RuntimeException('Could not open file.');
}

$bytes = fwrite(
    $handle,
    "New log line\n"
);

if ($bytes === false) {
    fclose($handle);

    throw new RuntimeException('Could not write file.');
}

fclose($handle);

I fwrite() opet vraća:
int broj upisanih bytes
ili false

Kada koristiti shortcut funkcije, a kada handle?
Za običan mali config/text fajl:
file_get_contents()
file_put_contents()

su često najčistije.
Za veliki fajl, streaming, parcijalno čitanje/pisanje, iterativnu obradu ili finiju kontrolu:
fopen()
fread()
fgets()
fwrite()
fclose()

imaju više smisla.
Na primer ogroman log fajl ne želiš nužno ceo da ubaciš u RAM preko:
file_get_contents($hugeFile);

nego možeš da ga čitaš liniju po liniju.
Pitanje
Šta će se desiti ako imamo fajl:
notes.txt

Hello Bojan

i uradimo:
$handle = fopen($path, 'w');

fwrite($handle, 'PHP');

fclose($handle);

A šta bi bilo drugačije da smo koristili:
fopen($path, 'a');

Objasni razliku između w i a svojim rečima.

---

w
→ write
→ create ako ne postoji
→ truncate ako postoji

a
→ append
→ create ako ne postoji
→ ne briše postojeći sadržaj

Lekcija 4 — fgets(), čitanje liniju po liniju i veliki fajlovi
Pretpostavimo log fajl:
2026-10-06 User 15 logged in
2026-10-06 User 21 booked room 8
2026-10-06 User 15 logged out

Možemo ceo fajl učitati:
$content = file_get_contents($path);

Ali ako fajl ima 2 GB, to nije baš dobra ideja jer pokušavaš da ceo sadržaj ubaciš u memoriju.
Zato:
$handle = fopen($path, 'r');

if ($handle === false) {
    throw new RuntimeException('Could not open file.');
}

while (($line = fgets($handle)) !== false) {
    // obradi jednu liniju
}

fclose($handle);

Ovde je opet važan strict comparison:
($line = fgets($handle)) !== false

jer fgets() vraća string za pročitanu liniju, a false kada nema više podataka ili čitanje ne uspe.
Ovo je streaming mentalni model:
otvori fajl
↓
čitaj mali deo
↓
obradi
↓
čitaj sledeći
↓
zatvori fajl

Prednost je što memory usage ostaje mali čak i ako je fajl ogroman.
Možemo i:
while (!feof($handle)) {
    $line = fgets($handle);

    if ($line === false) {
        break;
    }

    // ...
}

ali meni je prvi obrazac često elegantniji.
Još jedna sitnica: fgets() tipično zadržava newline:
"2026-10-06 User logged in\n"

pa ako ga ne želiš:
$line = rtrim($line, "\r\n");

Ne bih radio običan:
trim($line)

bez razloga ako whitespace unutar značenja linije može biti bitan; rtrim($line, "\r\n") precizno uklanja line ending.
Pitanje
Zašto bi za ogroman log fajl radije koristio:
fopen() + fgets()

nego:
file_get_contents()

i šta dobijaš kao return value iz fgets() kada uspešno pročita liniju, a šta kada više nema šta da pročita / čitanje ne uspe?

---

file_get_contents()
→ učitava ceo fajl u memoriju

fopen() + fgets()
→ čita mali deo po mali deo
→ mnogo manji memory footprint

Za male fajlove file_get_contents() može čak biti jednostavniji i sasvim brz. Problem nastaje kada fajl postane velik.
I return vrednosti si dobro rekao:
$line = fgets($handle);

uspeh:
string

failure / EOF:
false

zato:
while (($line = fgets($handle)) !== false) {
    // obrada
}

opet koristimo strict comparison.

Lekcija 5 — File metadata: size, timestamps, permissions
Sada prelazimo na informacije o fajlu, a ne njegov sadržaj.
Pretpostavimo:
$path = __DIR__ . '/storage/report.txt';

filesize()
$size = filesize($path);

vraća veličinu fajla u bytes.
Na primer:
$size = 1048576;

je otprilike:
1 MB

Praktično:
$maxSize = 5 * 1024 * 1024;

if (filesize($path) > $maxSize) {
    // too large
}

Isto smo koristili kod:
$_FILES['photo']['size']

ali ovde proveravamo već postojeći fajl na filesystem-u.
filemtime()
$modifiedAt = filemtime($path);

vraća Unix timestamp poslednje izmene fajla.
Na primer:
echo date('Y-m-d H:i:s', $modifiedAt);

Može biti korisno za:
cache invalidation
last modified prikaz
cleanup starih fajlova

is_readable() i is_writable()
is_readable($path);

pita:
Da li trenutni PHP proces može da čita ovu putanju?

is_writable($path);

pita:
Da li PHP proces može da piše na ovu putanju?

To je bitnije od pitanja:
"Da li fajl samo postoji?"

Jer možeš imati:
file_exists($path) === true

ali PHP nema permission da ga pročita.
Permissions
Na Linux/Unix sistemima često ćeš videti nešto poput:
755
644
775

Za direktorijume je često:
755

a za fajlove:
644

vrlo čest default obrazac.
Neću još da te zatrpavam Unix permission bitovima do detalja, ali osnovno:
r = read
w = write
x = execute

i permissions se odnose na:
owner
group
others

Kod direktorijuma x praktično znači da možeš da „uđeš/traverse-uješ“ direktorijum.
Zato direktorijum često ima:
755

dok običan text/image fajl često nema execute permission.
chmod()
PHP može:
chmod($path, 0644);

ili za direktorijum:
chmod($dir, 0755);

Ali važno:
Ne treba nasumično stavljati 0777 samo zato što nešto „ne radi“.

To je veoma česta loša praksa.
0777 znači veoma široke permissions i često je nepotrebno.
Bolje je razumeti ko je owner, koja grupa koristi fajl i koje minimalne dozvole su stvarno potrebne.
Metadata funkcije mogu vratiti false
Na primer:
$size = filesize($path);

if ($size === false) {
    // could not get size
}

Isto važi za filemtime().
Opet isti PHP pattern:
success → konkretna vrednost
failure → false

Pitanje
Pretpostavimo:
$path = __DIR__ . '/storage/report.txt';

Objasni razliku između:
file_exists($path)
is_readable($path)
is_writable($path)
filesize($path)
filemtime($path)

i posebno: zašto file_exists() sam po sebi nije dovoljan dokaz da PHP stvarno može da pročita ili izmeni fajl?

---

file_exists($path) -> samo proverava da li fajl postoji ali nije dovoljan za čitanje i pisanje jer ne pita ništa o dozvolama za čitanje i pisanje

is_readable($path) -> konkretno pita ima li php dozvolu da čita fajl

is_writable($path) -> konkretno pita da li php ima dozvolu da upisuje u fajl

filesize($path) -> vraća veličinu fajla ili failure

filemtime($path) -> ispisuje unix vreme poslednje izmene fajla ili false
Tačno — 9.5/10. Sve si suštinski pogodio; samo dve male terminološke korekcije.

filesize($path) ne vraća samo „veličinu ili failure“, nego konkretno:

int $bytes

na uspeh, odnosno:

false

na neuspeh.

A filemtime($path) ne „ispisuje“ vreme, nego vraća Unix timestamp poslednje izmene:

$modifiedAt = filemtime($path);

na primer:

1760000000

pa ga tek ti pretvaraš u čitljiv datum:

if ($modifiedAt !== false) {
    echo date('Y-m-d H:i:s', $modifiedAt);
}

Dakle mentalni pregled:

file_exists()
→ postoji li putanja

is_readable()
→ sme li PHP proces da čita

is_writable()
→ sme li PHP proces da piše

filesize()
→ veličina u bytes | false

filemtime()
→ Unix timestamp poslednje izmene | false
I da — ključna stvar je upravo to što si rekao: postojanje nije isto što i dozvola za korišćenje.

Lekcija 6 — copy(), rename(), unlink(), rmdir()
Sada prelazimo na manipulisanje fajlovima.
copy()
Ako želiš kopiju fajla:
$source = __DIR__ . '/storage/report.txt';
$destination = __DIR__ . '/backup/report.txt';

$result = copy($source, $destination);

Na uspeh:
true

na failure:
false

Bitno: ako destination fajl već postoji, copy() ga može pregaziti.
Zato ako overwrite nije dozvoljen:
if (file_exists($destination)) {
    // reject
}

pa tek onda copy().
rename()
rename($oldPath, $newPath);

može služiti i za rename i za move.
Na primer:
rename(
    __DIR__ . '/storage/a.txt',
    __DIR__ . '/storage/b.txt'
);

menja ime.
Ali:
rename(
    __DIR__ . '/storage/a.txt',
    __DIR__ . '/archive/a.txt'
);

praktično pomera fajl u drugi direktorijum.
Na uspeh vraća:
true

inače:
false

unlink()
Za brisanje fajla:
unlink($path);

Važno: unlink() briše fajl, ne direktorijum.
Zato često:
if (is_file($path)) {
    if (!unlink($path)) {
        // delete failed
    }
}

Ne bih slepo radio:
unlink($_GET['file']);

jer smo već rekli da user-controlled path + filesystem operacije mogu biti ozbiljan security problem.
rmdir()
Za direktorijum:
rmdir($dir);

ali postoji važna stvar:
rmdir() po default-u radi samo ako je direktorijum prazan.

Dakle:
uploads/15/
    avatar.webp

ne možeš samo:
rmdir('uploads/15');

dok avatar.webp još postoji.
Moraš prvo:
unlink($avatar);

pa onda:
rmdir($userDir);

To je isti obrazac koji si već praktično koristio kod image cleanup-a u svojim projektima.
Delete file vs delete DB row
Ovo je realna web-app tema.
Recimo DB ima:
users.avatar = uploads/15/avatar.webp

Ako updateuješ avatar, moraš razmišljati o oba sistema:
DATABASE
FILESYSTEM

Ako obrišeš DB path, a ne obrišeš fajl:
orphan file

Ako obrišeš fajl, a DB update padne:
DB pokazuje na nepostojeći fajl

Dakle filesystem operacije i DB transakcije nisu automatski jedna ACID transakcija. To kasnije zahteva pažljiv redosled i cleanup strategiju.
Tipičan avatar replace flow
Recimo user ima:
old avatar
→ uploads/15/old.webp

i uploaduje novi.
Često je sigurnije:
1. validiraj novi upload
2. sačuvaj novi fajl
3. update DB na novi path
4. ako je DB uspeo → obriši stari fajl

nego:
1. obriši stari fajl
2. pokušaj da sačuvaš novi

jer ako korak 2 padne, user ostaje bez starog avatara.
To je važan princip:
Ne uništavaj postojeće validno stanje pre nego što znaš da je zamena uspešna.

Pitanje
Imamo:
$old = __DIR__ . '/uploads/15/avatar.webp';
$new = __DIR__ . '/uploads/15/avatar-new.webp';

Objasni razliku između:
copy($old, $new);
rename($old, $new);
unlink($old);

i šta bi se desilo sa originalnim avatar.webp fajlom nakon svake od te tri operacije.
