# 8.ValidationNotSecuritySanitize

## Validation nije Security sanitizer

Ovo je jedna od najvažnijih lekcija celog modula.
Vrlo često se može čuti nešto poput:

„Validirao sam input, sada je bezbedan.“

To nije nužno tačno.
Ili:

„Sanitizovao sam string, tako da sam rešio SQL injection i XSS.“

Ni to nije tačno.
Različiti sigurnosni problemi rešavaju se na različitim granicama sistema.
Mentalni model:

```text
INPUT VALIDATION
→ da li podatak odgovara našim pravilima?
```

```text
SQL INJECTION
→ prepared statements
```

```text
XSS
→ escaping za output context
```

```text
CSRF
→ CSRF token
```

```text
AUTHORIZATION
→ da li ovaj user sme ovo da uradi?
```

```text
FILE UPLOAD SECURITY
→ MIME/size/storage policy itd.
```

Nema jedne funkcije:

```php
sanitizeEverything($input);
```

koja rešava sve.

---

## 1. Validation ne rešava SQL injection

Pretpostavimo search:

```php
$search = $_GET['search'] ?? '';
```

Čak i da radiš:

```php
$search = trim($search);
```

ili:

```php
$search = htmlspecialchars($search);
```

to nije SQL injection zaštita.
Loš SQL:

```php
$sql = "
    SELECT *
    FROM users
    WHERE name = '$search'
";
```

Problem je što user input ubacuješ direktno u SQL sintaksu.
Pravo rešenje:

```php
$stmt = $pdo->prepare(
    'SELECT * FROM users WHERE name = :name'
);

$stmt->execute([
    'name' => $search,
]);
```

Dakle:

```text
SQL injection prevention
=
odvajanje SQL koda od podataka
```

preko prepared statements.
Ne:

"očisti string dovoljno dobro"

---

## 2. Validation ne rešava XSS

Recimo user legitimno ima business description:

Tom & Jerry `<fan>`

Možda tvoja aplikacija dozvoljava skoro bilo koji tekst.
To može proći validation.
Ali kada ga ubaciš u HTML:

```html
<p><?= $description ?></p>
```

browser može interpretirati HTML koji se nalazi u podatku.
Zato na izlazu:

```html
<p>
    <?= htmlspecialchars(
        $description,
        ENT_QUOTES,
        'UTF-8'
    ) ?>
</p>
```

Poenta je:

XSS zaštitu primenjujemo na output boundary-u.

Zato je naziv output escaping toliko važan.

---

## 3. Zašto ne treba unapred `htmlspecialchars()` pre baze?

Ovo je interesantna zamka.
Neko uradi:

```php
$name = htmlspecialchars(
    $_POST['name'],
    ENT_QUOTES,
    'UTF-8'
);
```

i onda tu vrednost sačuva u DB.
Ako korisnik ima:

Tom & Jerry

možeš završiti sa encoded podatkom u bazi.
Onda imaš problem:

```text
original business data
vs
HTML representation tog podatka
```

Generalno je bolji model:

```text
INPUT
↓
validate / normalize
↓
store meaningful data
↓
escape WHEN rendering to HTML
```

Jer možda isti podatak sutra šalješ kroz:

```text
HTML
JSON
PDF
CSV
email
CLI
```

A svako ima svoj output context.
Ne želiš da HTML escaping bude trajno ugrađen u business podatak.

---

## Context-aware escaping

Još jedna važna ideja:

```php
htmlspecialchars()
```

je za HTML text/attribute context.
Ali escaping zavisi od toga gde podatak ubacuješ.
Ovo:

```html
<p><?= htmlspecialchars($name, ENT_QUOTES, 'UTF-8') ?></p>
```

je jedno.
Ali dinamički JavaScript, URL, CSS itd. imaju druga pravila.
Zato stručnije kažemo:

context-aware output encoding/escaping.

Za većinu naših običnih PHP view-ova sada ćemo koristiti:

```php
htmlspecialchars()
```

ali želim da zapamtiš da nije „univerzalni sanitizer“.
Laravel Blade upravo zato automatski escape-uje:

```blade
{{ $name }}
```

dok:

```blade
{!! $name !!}
```

izbacuje raw HTML i zato je mnogo opasnije ako je sadržaj user-controlled.

---

## 4. Validation nije authorization

Recimo request:

```http
DELETE /posts/15
```

i:

```php
$postId = 15;
```

Možeš savršeno validirati da je:

```text
integer
positive
post exists
```

ali još ne znaš:

Da li trenutni korisnik sme da obriše post 15?

To je authorization.
U Laravelu:

```php
$this->authorize('delete', $post);
```

ili Policy.
U vanilla PHP mentalno:

```php
if (
    $post['user_id'] !== $currentUserId &&
    !$currentUserIsAdmin
) {
    http_response_code(403);
    exit;
}
```

Dakle:

```text
VALIDATION
"Da li request ima pravilan podatak?"
```

```text
AUTHORIZATION
"Da li ovaj user sme ovu akciju?"
```

---

## 5. Validation nije CSRF zaštita

Formu možeš savršeno validirati:

```text
name valid
email valid
age valid
```

ali ako je authenticated user prevaren da njegov browser pošalje neželjeni request, validation ti ne pomaže.
Tu dolazi CSRF token.
To ćemo malo kasnije dublje obraditi kada spojimo forms + sessions.

## Pitanje

Imamo user komentar:

```php
$comment = $_POST['comment'] ?? null;
```

Programer uradi:

```php
$comment = trim($comment);

$comment = htmlspecialchars(
    $comment,
    ENT_QUOTES,
    'UTF-8'
);

$stmt = $pdo->query(
    "INSERT INTO comments (body)
     VALUES ('$comment')"
);
```

i kaže:

„Bezbedno je, sanitizovao sam input sa `htmlspecialchars()`.“

Objasni mi dva problema u ovom kodu:

1. zašto `htmlspecialchars()` ne rešava SQL injection,
2. zašto ga generalno ne bismo koristili ovde pre upisa u bazu, nego kasnije pri HTML outputu.

---

## 1. Zato što `htmlspecialchars()` samo sanitizuje - escapuje html tagove, i onda je to u redu za prikaz na view

ali nikako nije sigurno za sql injection, koji se preventira sa prepared statements.

---

## 2. Takođe, `htmlspecialchars()` nije dobro korisititi pre upisa u bazu jer se tako sudara sa našom biznis politikom,

odnosno rizikujemo da u bazu upišemo podatak koji sadrži escaped karaktere,
a pri tom nije html jedino mesto gde ćemo prikazai taj podatak.
Dakle - u bazu upišemo normalan, validiran i injection odbranjen podatak a za html ga escapujemo radi prevencije XSS-a.
