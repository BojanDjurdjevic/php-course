# 40. Who controlls transaction

## Lekcija 40 — Ko treba da kontroliše transakciju: Repository ili Service?

Ovo je arhitektonski veoma važno, posebno jer već koristiš Service/Repository pattern.

Recimo booking operacija zahteva:

1. proveru inventory-ja
2. smanjenje availability
3. kreiranje booking-a
4. eventualno booking_items

Imamo:

```php
$inventoryRepository
$bookingRepository
```

Loš dizajn bi bio da svaki repository sam radi:

```php
beginTransaction()
```

...

```php
commit()
```

Na primer:

```php
class InventoryRepository
{
    public function decrease(...): void
    {
        $this->pdo->beginTransaction();

        // UPDATE inventory

        $this->pdo->commit();
    }
}
```

pa posle:

```php
class BookingRepository
{
    public function create(...): int
    {
        $this->pdo->beginTransaction();

        // INSERT booking

        $this->pdo->commit();
    }
}
```

Problem je što smo dobili dve odvojene business celine:

```text
inventory transaction
→ COMMIT ✅
```

```text
booking transaction
→ pukne ❌
```

Inventory je već trajno smanjen.
Repository ne zna širu poslovnu operaciju.
Mnogo prirodnije je:

```php
class BookingService
{
    public function book(...): int
    {
        $this->pdo->beginTransaction();

        try {
            $this->inventoryRepository->decrease(...);

            $bookingId = $this->bookingRepository->create(...);

            $this->pdo->commit();

            return $bookingId;
        } catch (Throwable $e) {
            if ($this->pdo->inTransaction()) {
                $this->pdo->rollBack();
            }

            throw $e;
        }
    }
}
```

Repository-ji samo rade svoje DB operacije:

```text
InventoryRepository
→ UPDATE inventory
```

```text
BookingRepository
→ INSERT booking
```

dok Service zna:

Ove operacije zajedno predstavljaju jednu booking operaciju i moraju biti atomic.

Mentalno:

```text
Repository
→ kako da pročitam/upisem podatke?
```

```text
Service
→ koje operacije zajedno čine business use-case?
```

```text
Transaction boundary
→ najčešće oko celog use-case-a
```

Ovo je baš povezano sa onim što si radio u StayCore-u.

## Mini interview pitanje 41

Zašto je često bolje da:

BookingService

otvori i završi transakciju, umesto da:

```text
BookingRepository
InventoryRepository
```

svaki samostalno rade svoj `beginTransaction()` i `commit()`?

---

Zato sto u drugom slucaju bismo imali 2 odvojene transakcije a treba nam 1 jer zelimo sve atomic

---

Tačno — 10/10.
Upravo tako:

```text
Service
→ zna ceo business use-case
→ zato određuje transaction boundary
```

```text
Repository
→ radi pojedinačne DB operacije
```

Ako svaki repository radi svoj `commit()`, možeš završiti sa:

```text
inventory smanjen ✅
booking insert ❌
```

što krši atomicity.
