Lekcija 22 — D: Dependency Inversion Principle

Ovo je poslednje slovo SOLID-a i direktno se nadovezuje na 
DI i interface-e koje smo već radili.

DIP kaže otprilike:
High-level moduli ne treba da zavise 
direktno od low-level konkretnih implementacija. Obe strane treba da zavise od apstrakcije.

Na primer, lošije:
class BookingService
{
    public function __construct(
        private StripeGateway $payment
    ) {}
}

Ovde:
BookingService
→ direktno zavisi od StripeGateway

BookingService je high-level business klasa.
StripeGateway je low-level detalj implementacije.
Ako sutra pređeš na PayPal, Service moraš da menjaš.
Bolje:
interface PaymentGateway
{
    public function charge(int $amount): void;
}

final class StripeGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // Stripe API
    }
}

final class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}

Sada:
BookingService
        ↓
 PaymentGateway
        ↑
 StripeGateway

I high-level i low-level deo zavise od apstrakcije.
BookingService više ne kaže:
Treba mi Stripe.

nego:
Treba mi bilo koji validan PaymentGateway.

To je Dependency Inversion.
DIP nije isto što i DI
Ovo je baš dobro razlikovati na intervjuu.
Dependency Injection je tehnika:
new BookingService($gateway);

Dependency dolazi spolja.
Dependency Inversion Principle je dizajnerski princip:
high-level kod
→ zavisi od abstraction-a

ne od concrete implementation-a

Možeš imati DI bez pravog DIP-a:
class BookingService
{
    public function __construct(
        private StripeGateway $gateway
    ) {}
}

Ovo jeste constructor injection.
Ali Service i dalje zavisi od konkretne klase:
StripeGateway

Dakle:
DI ✅
DIP baš i ne ✅/❌

Bolje:
public function __construct(
    private PaymentGateway $gateway
) {}

Tu imamo i DI i DIP.
Laravel primer
Ovo:
class BookingService
{
    public function __construct(
        private PaymentGateway $gateway
    ) {}
}

zahteva da container zna:
PaymentGateway
→ StripeGateway

U Laravelu bi se ta veza mogla registrovati u container-u.
Mentalno:
Business layer
→ zna samo contract

Infrastructure layer
→ daje konkretnu implementaciju

To je vrlo čista granica.
Zašto DIP pomaže?
Dobijamo:
manji coupling
lakšu zamenu implementacije
lakše testiranje
čistiji business sloj
manje znanja o infrastrukturi

Na primer test:
final class FakePaymentGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // fake
    }
}

BookingService ne zanima da li radi sa:
Stripe
PayPal
Fake

jer svi poštuju isti contract.
SOLID mapa sada
S
→ jedan glavni razlog za promenu

O
→ proširuj novim implementacijama,
  ne menjaj stalno postojeći kod

L
→ subtype mora stvarno moći da zameni base type

I
→ ne teraj klasu da zavisi od metoda koje joj ne trebaju

D
→ zavisi od apstrakcija,
  ne od konkretnih implementation detalja

Mini interview pitanje 22
Da li je ovo Dependency Injection?
class BookingService
{
    public function __construct(
        private StripeGateway $gateway
    ) {}
}

I da li ujedno dobro prati Dependency Inversion Principle?
Objasni mi razliku između ta dva pojma.

---

Ovo jeste DI ali nije i DIP.

DI je prosto tehnika -> klasa prima zavisnost spolja.

DIP je princip koji kao da pita "da li ova klasa cini da Servis (ili druga koja ju prina) zavisi od nje ili ne?".

I to se upravo ovde dogadja, servis zavisi od jednog payment modela (Strip).

Zato je bolje interface PaymentGateway koji je contract, koji posle moze primeniti bilo koja klasa.

---

Tačno — 9.8/10. Suštinu si potpuno pogodio.
Jedino bih DIP formulisao još preciznije ovako:
DI
→ kako dependency ulazi u klasu

DIP
→ od čega klasa treba da zavisi

Dakle:
public function __construct(
    private StripeGateway $gateway
) {}

jeste DI, jer dependency dolazi spolja.
Ali:
BookingService
↓
StripeGateway

i dalje znači da high-level business kod zavisi od konkretnog infrastructure detalja.
Sa:
public function __construct(
    private PaymentGateway $gateway
) {}

dobijamo:
BookingService
        ↓
 PaymentGateway
        ↑
 StripeGateway

To je pravi DIP mentalni model: oba zavise od contract-a.
