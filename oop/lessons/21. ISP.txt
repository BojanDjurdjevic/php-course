Lekcija 21 — I: Interface Segregation Principle

ISP kaže:
Klasa ne treba da bude prisiljena da zavisi od metoda koje joj nisu potrebne.

Odnosno, često je bolje imati više manjih, fokusiranih interface-a nego jedan ogroman.
Zamisli:
interface Worker
{
    public function work(): void;
    public function eat(): void;
    public function sleep(): void;
}

Za čoveka možda:
class Employee implements Worker
{
    public function work(): void {}
    public function eat(): void {}
    public function sleep(): void {}
}

Ali onda imamo:
class Robot implements Worker
{
    public function work(): void {}

    public function eat(): void
    {
        throw new RuntimeException();
    }

    public function sleep(): void
    {
        throw new RuntimeException();
    }
}

To je loš znak.
Robot je primoran da implementira metode koje mu uopšte ne pripadaju.
Bolje:
interface Workable
{
    public function work(): void;
}

interface Eatable
{
    public function eat(): void;
}

interface Sleepable
{
    public function sleep(): void;
}

Sad:
class Employee implements Workable, Eatable, Sleepable
{
    // ...
}

a:
class Robot implements Workable
{
    // ...
}

Mnogo čistije.
Backend primer
Loš interface:
interface UserRepository
{
    public function find(int $id): ?User;

    public function save(User $user): void;

    public function delete(User $user): void;

    public function sendWelcomeEmail(User $user): void;

    public function exportCsv(): string;
}

Ovo već meša:
persistence
email
export

i tera implementacije da podržavaju sve.
Bolje je razdvojiti odgovornosti:
interface UserRepository
{
    public function find(int $id): ?User;

    public function save(User $user): void;

    public function delete(User $user): void;
}

interface UserNotifier
{
    public function sendWelcome(User $user): void;
}

interface UserExporter
{
    public function export(): string;
}

Klasa implementira samo ono što joj stvarno treba.
Zašto je ovo dobro za DI?
Zamisli Service kome treba samo čitanje korisnika:
interface UserReader
{
    public function find(int $id): ?User;
}

pa:
class UserProfileService
{
    public function __construct(
        private UserReader $users
    ) {}
}

Service sada zavisi samo od:
find()

Ne zna ništa o:
save()
delete()
export()
email()

To pravi još manji coupling.
ISP ne znači “jedna metoda po interface-u”
Kao kod SRP-a, ne treba preterivati.
Ovo:
interface BookingReader
{
    public function find(int $id): ?Booking;

    public function findForUser(int $userId): array;
}

je sasvim fokusiran interface.
Poenta nije broj metoda, nego:
Da li svaki consumer stvarno ima smisla da zavisi od svih metoda tog interface-a?

ISP i LSP su povezani
Ako interface ima previše nepovezanih metoda, implementacije često počnu da rade:
throw new RuntimeException('Not supported');

što onda vrlo lako vodi i u LSP problem.
Zato:
predebeo interface
→ implementacija ne podržava sve
→ dummy metode / exceptions
→ moguć LSP problem

ISP sprečava taj dizajn ranije.
Mini interview pitanje 21
Zašto je ovo loš interface?
interface PaymentProvider
{
    public function charge(int $amount): void;
    public function refund(int $amount): void;
    public function generateInvoice(): string;
    public function sendReceiptEmail(): void;
}

Ako neki provider samo može da naplati i refundira, a nema invoice/email 
funkcionalnost — kako bi ISP predložio da ovo redizajniramo?

---

Los je interface jer ne mogu sve 4 metode da se primene u svakoj klasi koja ih implementira.

Zato bi ISP predlozio da zadrzimo prve 2 charge i refund a da ostale 2 izdvojimo u posebne interfaces.

---

Tačno — 10/10.

I odlična ti je logika: problem nije u tome što interface ima „četiri metode“, 
nego što ne važe sve metode za svaku implementaciju.

Možeš recimo razdvojiti ovako:
interface Chargeable
{
    public function charge(int $amount): void;
}

interface Refundable
{
    public function refund(int $amount): void;
}

interface InvoiceGenerator
{
    public function generateInvoice(): string;
}

interface ReceiptSender
{
    public function sendReceiptEmail(): void;
}

I onda konkretna klasa implementira samo ono što stvarno podržava.
