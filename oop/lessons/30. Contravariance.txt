Lekcija 30 — Contravariance

Sad druga polovina iste priče: parametri metoda.

Ovde smer ide obrnuto.
Imamo:
class Animal {}

class Dog extends Animal {}

Parent:
class DogHandler
{
    public function handle(Dog $animal): void
    {
        // ...
    }
}

Child može:
class AnimalHandler extends DogHandler
{
    public function handle(Animal $animal): void
    {
        // ...
    }
}

I ovo je validno.
Zašto?
Parent obećava:
Daj mi Dog i ja mogu da ga obradim.

Child kaže:
Ja mogu da obradim čak i bilo koji Animal.

Dakle naravno da može da primi i Dog.
To je contravariance.
PARAMETER

Dog → Animal
specifičnije → šire

A zašto obrnuto ne bi bilo dobro?
Zamisli parent:
class AnimalHandler
{
    public function handle(Animal $animal): void
    {
    }
}

Njegov contract kaže:
Mogu da primim bilo koji Animal.

A child pokuša:
class DogHandler extends AnimalHandler
{
    public function handle(Dog $animal): void
    {
    }
}

Sad imamo problem.
Kod koji radi sa parent tipom legitimno može da uradi:
$handler->handle(new Cat());

jer parent obećava Animal.
Ali ako smo umesto parent-a dobili DogHandler, on kaže:
Ne, primam samo Dog.

Time je child postao restriktivniji i više nije dobra zamena za parent.
To udara direktno u LSP.
Najlakši način da pamtiš oba
RETURN TYPE
→ može UŽE
→ covariance

PARAMETER TYPE
→ može ŠIRE
→ contravariance

Ili još intuitivnije:
Child sme da kaže:

"Prihvatam VIŠE nego parent." ✅

"Vraćam PRECIZNIJE nego parent." ✅

To je veoma lepa OOP logika.
Mini interview pitanje 30
Zašto je ovo dozvoljeno:
class DogHandler
{
    public function handle(Dog $animal): void {}
}

class AnimalHandler extends DogHandler
{
    public function handle(Animal $animal): void {}
}

i kako se zove ovaj princip?
Posebno objasni zašto child koji prihvata širi tip ne krši contract parent klase.

---

Ovo se zove Contravariance.

I ovo moze, jer child ovde prima širi parametar, 
bilo koji animal a dog jeste animal.
