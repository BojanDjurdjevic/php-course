Lekcija 17 — Controller

Controller je pre svega HTTP/Application boundary.

Najkraći mentalni model:
Request
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
DB

Controller treba da razume stvari poput:
HTTP request
route parametara
input-a
status kodova
redirect-a
JSON response-a

Ali ne bi trebalo da sadrži ceo business workflow.
Na primer:
final class BookingController
{
    public function __construct(
        private BookingService $service
    ) {}

    public function store(Request $request): Response
    {
        // HTTP/input deo

        $data = new CreateBookingData(
            userId: $request->user()->id,
            roomId: $request->integer('room_id'),
            checkIn: new DateTimeImmutable(
                $request->input('check_in')
            ),
            checkOut: new DateTimeImmutable(
                $request->input('check_out')
            ),
        );

        // delegiranje business use-case-a

        $booking = $this->service->create($data);

        // HTTP output

        return response()->json(
            $booking,
            201
        );
    }
}

Ovde Controller radi tri veoma razumljive stvari:
HTTP input
↓
pretvori u application-friendly podatke
↓
pozovi use-case
↓
napravi HTTP response

Šta Controller ne bi trebalo da radi?
Na primer ovo:
public function store(Request $request)
{
    $pdo->beginTransaction();

    $stmt = $pdo->prepare(
        'SELECT available FROM room_inventory ...'
    );

    // 40 linija SQL-a

    // calculate total

    // insert booking

    // decrease inventory

    // call Stripe

    // send email

    $pdo->commit();

    return response(...);
}

To je već:
Controller
→ HTTP
→ SQL
→ business rules
→ transactions
→ payment
→ notifications

Previše odgovornosti.
Dobijamo takozvani:
Fat Controller

Controller vs Service
Ovo vredi baš dobro zapamtiti.
Controller pita:
Kako da prevedem HTTP zahtev u poziv aplikacije?

Service pita:
Kako se ovaj business use-case izvršava?

Na primer:
public function cancel(int $bookingId)

u Controller-u može:
public function cancel(int $id): Response
{
    $this->service->cancel($id);

    return response()->json(
        ['message' => 'Booking cancelled']
    );
}

A Service odlučuje:
public function cancel(int $id): void
{
    $booking = $this->bookings->findById($id);

    if (!$booking) {
        throw new BookingNotFoundException();
    }

    if (!$booking->canBeCancelled()) {
        throw new BookingCannotBeCancelledException();
    }

    $booking->cancel();

    $this->bookings->save($booking);
}

Controller ne treba da zna pravila kao:
da li booking može da se otkaže
koliko dana pre check-in-a
da li treba vratiti inventory
da li ide refund

To je business/application logika.
Controller nije nužno vezan za HTML
Controller može vratiti:
View
JSON
Redirect
File
204 No Content

Na primer API:
return response()->json($booking, 201);

ili klasična web aplikacija:
return redirect('/bookings')
    ->with('success', 'Booking created');

Poenta nije format response-a.
Poenta je njegova pozicija na granici između:
HTTP sveta
i
application sveta

Zašto je tanak Controller lakši za testiranje?
Ako je business logika u Controller-u, za testiranje često moraš da simuliraš:
route
request
session
HTTP
middleware

čak i kada želiš samo da proveriš:
Da li se booking može otkazati?

Ako je logika u Service-u:
$service->cancel($bookingId);

možeš testirati use-case direktno bez HTTP-a.
Zatim odvojeno testiraš Controller:
Da li pravi dobar DTO, poziva servis i vraća pravi response?

To daje mnogo preciznije testove.
A gde ide validation?
Ovde postoji važna nijansa.
Input validation poput:
room_id mora biti integer
check_in mora biti date
email mora imati ispravan format

često je vezana za request boundary.
U Laravelu:
CreateBookingRequest

može odraditi taj deo.
Ali business pravilo:
check-out mora biti posle check-in-a
room mora biti slobodan
booking ne može biti otkazan posle check-in-a

nije samo HTTP validation.
To pripada dubljem sloju aplikacije/domain-a.
Mentalno:
Request validation
→ "da li je input pravilnog oblika?"

Business rule
→ "da li je ova operacija dozvoljena?"

Vrlo važna razlika.
Sada već imamo ozbiljan flow

1. room_id mora biti integer

2. room mora imati availability za sve tražene noći

3. booking se ne sme otkazati nakon check-in datuma

Da li su to Controller/FormRequest validation 
ili business pravila za Service/domain sloj?

----

1. room_id mora biti integer - FormRequest

2. room mora imati availability za sve tražene noći - business pravilo

3. booking se ne sme otkazati nakon check-in datuma - takodje business logic

Tako da bih prvo stavio u Cotroller/Reauest a drugo i treće u Service

---

Tačno — 9.7/10.
Prva dva si smestio baš kako treba. Kod trećeg bih samo dodao jednu važnu nijansu:
booking se ne sme otkazati nakon check-in datuma

jeste business pravilo, ali ne mora nužno da živi baš u Service klasi. Ako pravilo prirodno pripada samom Booking objektu, još lepše može biti:
class Booking
{
    public function canBeCancelled(DateTimeImmutable $now): bool
    {
        return $now < $this->checkIn;
    }

    public function cancel(DateTimeImmutable $now): void
    {
        if (!$this->canBeCancelled($now)) {
            throw new BookingCannotBeCancelledException();
        }

        $this->status = BookingStatus::Cancelled;
    }
}

A Service onda orkestrira:
$booking = $this->bookings->findById($id);

$booking->cancel($now);

$this->bookings->save($booking);

Dakle:
FormRequest
→ oblik/input validacija

Service
→ orkestracija use-case-a

Domain/Entity
→ pravila koja prirodno pripadaju konkretnom business objektu

To će ti postati još jasnije kroz SOLID.
