# 12. Dependency Injection

## Lekcija 12 — Dependency Injection

Sad dolazimo do koncepta koji već praktično koristiš u Laravelu,
ali hoću da ga potpuno ogolimo.

Najkraće:

Dependency Injection znači da objekat ne pravi sam svoje dependencies,
nego ih dobija spolja.

Lošije:

```php
class BookingService
{
    private BookingRepository $repository;

    public function __construct()
    {
        $this->repository = new BookingRepository();
    }
}
```

Ovde BookingService sam odlučuje:

```text
Treba mi repository
↓
sam ću ga napraviti
↓
čvrsto sam vezan za BookingRepository
```

Bolje:

```php
class BookingService
{
    public function __construct(
        private BookingRepository $repository
    ) {}
}
```

Pa spolja:

```php
$repository = new BookingRepository();

$service = new BookingService($repository);
```

Sada:

```text
BookingService
→ zna šta mu treba
```

```text
spoljašnji kod
→ odlučuje šta će mu dati
```

To je Dependency Injection.

---

## Šta je dependency?

Vrlo jednostavno:

Ako klasa ne može da radi svoj posao bez nekog drugog objekta,
taj objekat joj je dependency.

```php
class BookingService
{
    public function __construct(
        private BookingRepository $bookings,
        private PaymentGateway $payment,
        private Mailer $mailer,
    ) {}
}
```

Dependencies su:

```text
BookingRepository
PaymentGateway
Mailer
```

BookingService zavisi od njih.

---

## Constructor Injection

Ovo je najčešći i uglavnom najbolji oblik DI-ja:

```php
public function __construct(
    private PaymentGateway $payment
) {}
```

---

## Zašto?

Jer objekat ne može ni da nastane bez dependency-ja koji mu je potreban.
To se lepo nadovezuje na ono što smo pričali o constructor-u:

```text
constructor
→ garantuje validno početno stanje objekta
```

Ako BookingService bez PaymentGateway ne može da radi:

```php
new BookingService();
```

ne bi ni trebalo da bude dozvoljeno.

---

## DI nije isto što i Service Container

Ovo je veoma važno.
Dependency Injection je princip/tehnika.
Možeš ga raditi ručno:

```php
$payment = new StripeGateway();

$service = new BookingService($payment);
```

To je već DI.
Ne treba ti Laravel.
Service Container samo automatizuje sastavljanje objekata.
Mentalno:

```text
Dependency Injection
→ "daj dependency spolja"
```

```text
Service Container
→ "ja ću automatski pronaći i dati dependency"
```

```text
Bez containera
$repository = new BookingRepository($pdo);
$payment = new StripeGateway();
$mailer = new Mailer();
```

```php
$service = new BookingService(
    $repository,
    $payment,
    $mailer
);
```

Ti ručno sastavljaš object graph.

---

## Sa Laravel containerom

Napišeš:

```php
class BookingController
{
    public function __construct(
        private BookingService $service
    ) {}
}
```

A Laravel kaže otprilike:

```text
BookingController treba BookingService
↓
BookingService treba BookingRepository
↓
```

BookingRepository treba ...

```text
↓
napravi sve
↓
ubaci ih gde treba
```

Zato ti Laravel omogućava da samo type-hintuješ klasu i dependency „magično“ stigne.
Ali ispod te magije je upravo DI.
Još bolje sa interface-om

```php
class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}
```

Ovde PaymentGateway je interface.
Onda spolja možemo dati:

```php
new BookingService(
    new StripeGateway()
);
```

ili:

```php
new BookingService(
    new FakePaymentGateway()
);
```

BookingService ne menjaš.
To daje:

```text
DI
+
interface
+
composition
=
vrlo loose coupling
```

---

## Zašto je new unutar klase često signal za razmišljanje?

Nije svaki new loš.
Ali ako vidiš:

```php
class BookingService
{
    public function create(): void
    {
        $mailer = new Mailer();
        $payment = new StripeGateway();
        $repository = new BookingRepository();
    }
}
```

treba da ti se upali lampica.
Jer servis sada:

```text
koristi dependency
+
zna kako da ga kreira
+
zna njegovu konkretnu implementaciju
```

To su dodatne odgovornosti.
Sa DI:

```php
class BookingService
{
    public function __construct(
        private Mailer $mailer,
        private PaymentGateway $payment,
        private BookingRepository $repository,
    ) {}
}
```

servis samo kaže:

Ovo mi treba.

A neko drugi sastavlja sistem.
Testiranje
Ovo je jedna od najvećih praktičnih koristi.
Produkcija:

```php
$service = new BookingService(
    new StripeGateway()
);
```

Test:

```php
$service = new BookingService(
    new FakePaymentGateway()
);
```

Možeš čak napraviti:

```php
class FakePaymentGateway implements PaymentGateway
{
    public array $charges = [];

    public function charge(int $amount): void
    {
        $this->charges[] = $amount;
    }
}
```

Pa proveriti:

```php
$service->book();

var_dump($fakePayment->charges);
```

bez pravog Stripe API-ja.
To je ogroman dobitak.

---

## Mentalna mapa

```text
DEPENDENCY
→ objekat koji mi je potreban
```

```text
DEPENDENCY INJECTION
→ dependency dobijam spolja
```

```text
CONSTRUCTOR INJECTION
→ dependency dobijam kroz __construct()
```

```text
SERVICE CONTAINER
→ automatizuje pravljenje i injection dependencies
```

```text
INTERFACE
→ omogućava više implementacija istog contract-a
```

I jedna rečenica koju vredi zapamtiti za intervju:

Dependency Injection smanjuje coupling tako što
klasa ne kreira svoje zavisnosti sama, već ih dobija spolja.

---

## Mini interview pitanje 12

Koja je razlika između ova dva pristupa:

```php
class BookingService
{
    public function __construct()
    {
        $this->payment = new StripeGateway();
    }
}
```

i:

```php
class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}
```

Zašto je drugi primer dependency injection i šta konkretno d
obijamo time u testiranju i održavanju?

---

Drugi primer je DI zato sto ovde klasa ne kreira svoje zavisnosti nego ih dobija spolja.

Dobijamo lakocu testiranja i odrzavanja jer ne moramo
da izmenjujemo klasu svaki put kada zelimo odredjeni deo da promenimo.

---

Tačno — 10/10.
U prvom primeru BookingService je čvrsto vezan za konkretni StripeGateway.
Ako sutra želiš PayPalGateway, moraš da menjaš samu klasu.

U drugom:

```php
public function __construct(
    private PaymentGateway $payment
) {}
```

BookingService samo kaže:

Treba mi nešto što ispunjava PaymentGateway contract.

Zato možeš bez menjanja servisa ubaciti:

```php
new StripeGateway()
new PayPalGateway()
new FakePaymentGateway()
```

To je upravo ono što želimo od DI-ja.
