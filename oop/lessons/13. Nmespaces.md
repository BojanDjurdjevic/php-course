# 13. Nmespaces

## Lekcija 13 — Namespaces

---

## Namespaces rešavaju veoma praktičan problem: šta ako dve klase imaju isto ime?

Zamisli veliki projekat:

class User {}

ali neka biblioteka takođe ima:

class User {}

PHP ne može imati dve klase istog potpuno kvalifikovanog imena.
Namespace pravi nešto poput „adrese“ klase.

```php
namespace App\Models;

class User
{
}
```

Sada puno ime klase nije samo:

User

nego:

App\Models\User

Možemo imati i:

```php
namespace Vendor\Package;

class User
{
}
```

To je potpuno druga klasa:

```text
App\Models\User
Vendor\Package\User
```

---

## Namespace nije folder — ali ih obično povezujemo

Ovo je važna nijansa.
Ako napišemo:

```php
namespace App\Services;
```

PHP sam po sebi ne kaže:

ova klasa mora fizički biti u app/Services.

Namespace je jezički koncept.
Ali Composer PSR-4 kasnije može da definiše:

```text
App\
→ app/
```

pa onda:

App\Services\BookingService

prirodno mapiramo na:

app/Services/BookingService.php

Tu će ti sledeći Composer modul spojiti sve kockice.
use
Bez importa mogao bi napisati:

```php
$service = new \App\Services\BookingService();
```

To je fully qualified class name — FQCN.
Ali obično na vrhu fajla napišemo:

```php
use App\Services\BookingService;
```

pa kasnije:

```php
$service = new BookingService();
```

use praktično kaže:

Kada u ovom fajlu kažem BookingService, mislim na App\Services\BookingService.

Na primer:

```php
namespace App\Controllers;

use App\Services\BookingService;

class BookingController
{
    public function __construct(
        private BookingService $service
    ) {}
}
```

Mentalno:

BookingController
namespace:

App\Controllers

BookingService
import:

App\Services\BookingService

---

## Zašto su namespace-i bitni za DI?

Jer kada napišeš:

```php
use App\Contracts\PaymentGateway;

class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}
```

taj type hint zapravo znači:

App\Contracts\PaymentGateway

Laravel container upravo iz tih konkretnih class/interface identiteta zna šta treba da resolve-uje.
Dakle namespace nije samo organizacija foldera. On je deo identiteta klase.
use ... as
Ako baš imamo dve klase istog kratkog imena:

```php
use App\Models\User;
```

use Vendor\Package\User as VendorUser;

onda:

```php
$appUser = new User();
$vendorUser = new VendorUser();
```

Obe klase možemo koristiti u istom fajlu.
namespace vs use
Nemoj ih pomešati.
Ovo:

```php
namespace App\Controllers;
```

znači:

Ovaj fajl / klase koje ovde definišem pripadaju ovom namespace-u.

Dok:

```php
use App\Services\BookingService;
```

znači:

Želim ovde da koristim tu klasu pod kraćim imenom.

Mentalno:

```text
namespace
→ gde JA pripadam
```

```text
use
→ koga JA uvozim
```

Ovo je odlična kratka definicija za intervju.

---

## Primer iz tvoje buduće Vanilla PHP strukture

Možemo imati:

```text
src/
├── Controllers/
│   └── BookingController.php
├── Services/
│   └── BookingService.php
├── Repositories/
│   └── BookingRepository.php
└── Contracts/
    └── PaymentGateway.php
```

BookingController.php:

```php
namespace App\Controllers;

use App\Services\BookingService;

class BookingController
{
    public function __construct(
        private BookingService $service
    ) {}
}
```

BookingService.php:

```php
namespace App\Services;

use App\Contracts\PaymentGateway;
use App\Repositories\BookingRepository;

class BookingService
{
    public function __construct(
        private BookingRepository $bookings,
        private PaymentGateway $payment,
    ) {}
}
```

Već vidiš kako se od običnog OOP-a polako pojavljuje struktura ozbiljne aplikacije.

## Mini interview pitanje 13

Objasni mi razliku između:

```php
namespace App\Services;
```

i:

```php
use App\Repositories\BookingRepository;
```

I još jedno bitno podpitanje: da li namespace sam po sebi znači da klasa fizički mora da bude u folderu App/Services, ili tu vezu kasnije pravi autoloading/PSR-4?

---

Namespace je ono gde kpasa pripada, dok je use ono sto klasa uvozi tj koristi.

U ovom slucaju BookingService koristi BookingRepository.

Namespace samo po sebi ne mora da znaci da klasa mora biti u istoimenom folderu, no tu vezu kasnije pravi autoloading

---

Tačno — 10/10.
Ovo je baš čista formulacija za intervju:

```text
namespace
→ gde moja klasa pripada
```

```text
use
→ koju drugu klasu/interface želim da koristim pod kraćim imenom
```

I potpuno tačno: namespace sam po sebi ne određuje fizički folder. Tu vezu kasnije pravi autoloading, najčešće preko Composer PSR-4 pravila.
