# 11. Composition

## Lekcija 11 — Composition

Ovo je veoma važna OOP tema jer u realnim aplikacijama često koristimo
composition više nego inheritance.

Najkraći mentalni model:

```text
inheritance
→ IS-A
```

```text
composition
→ HAS-A
```

Na primer:

```php
class BookingService
{
    public function __construct(
        private BookingRepository $repository
    ) {}
}
```

Ovde kažemo:

BookingService HAS-A BookingRepository

BookingService nije repository.

On ga samo koristi kao saradnika.

---

## Zašto se zove composition?

Zato što veći objekat sastavljamo od drugih objekata.
Na primer:

```php
class BookingService
{
    public function __construct(
        private BookingRepository $bookings,
        private InventoryService $inventory,
        private PaymentGateway $payment,
        private Mailer $mailer,
    ) {}
}
```

Mentalno:

```text
BookingService
│
├── BookingRepository
├── InventoryService
├── PaymentGateway
└── Mailer
```

BookingService je praktično sastavljen od svojih dependency-ja.
To je composition.

---

## Primer bez composition-a

Mogli bismo napisati katastrofu:

```php
class BookingService
{
    public function create(): void
    {
        $pdo = new PDO(...);

        // proveri inventory

        // napravi booking

        // Stripe API

        // pošalji email
    }
}
```

Sada BookingService sam:

```text
otvara DB
radi SQL
proverava inventory
radi payment
šalje mail
```

Sve je zalepljeno zajedno.
Umesto toga:

```php
class BookingService
{
    public function __construct(
        private BookingRepository $bookings,
        private InventoryService $inventory,
        private PaymentGateway $payment,
        private Mailer $mailer,
    ) {}
}
```

pa:

```php
public function create(BookingData $data): void
{
    $this->inventory->reserve($data);

    $booking = $this->bookings->create($data);

    $this->payment->charge($booking->total());

    $this->mailer->sendBookingConfirmation($booking);
}
```

Sada svaki objekat ima svoju odgovornost.

---

## Zašto composition često pobedi inheritance?

Zamisli da uradimo:

```php
class BookingService extends PaymentService
{
}
```

samo zato što booking treba payment.
To znači:

BookingService IS-A PaymentService

što nema smisla.
Stvarni odnos je:

BookingService HAS-A PaymentGateway

Dakle:

```php
class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}
```

mnogo preciznije modeluje realnost.

---

## Composition daje fleksibilnost

Recimo:

```php
interface PaymentGateway
{
    public function charge(int $amount): void;
}
```

Imamo:

```php
class StripeGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // Stripe
    }
}
```

i:

```php
class PayPalGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // PayPal
    }
}
```

BookingService ostaje isti:

```php
class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}
```

Možemo ga sastaviti sa:

```php
new BookingService(
    new StripeGateway()
);
```

ili:

```php
new BookingService(
    new PayPalGateway()
);
```

To je ogromna prednost composition-a.
Menjamo saradnika, ne inheritance hijerarhiju.

---

## Composition + interface = moćna kombinacija

Ovo je obrazac koji ćeš stalno viđati:

```text
Service
↓ depends on
Interface
↓ implemented by
Concrete class
```

Na primer:

```text
BookingService
↓
PaymentGateway
↓
StripeGateway
```

Service ne zna:

```text
Stripe
PayPal
FakePayment
```

nego samo contract.
To daje:

```text
loose coupling
lakše testiranje
lakšu zamenu implementacije
jasnije dependencies
```

"Favor composition over inheritance"
Ovo je poznato OOP pravilo.
Ne znači:

Nikad ne koristi inheritance.

Nego:

Ako ponašanje možeš modelovati tako da jedan objekat koristi drugi,
često je to fleksibilnije nego da praviš inheritance hijerarhiju.

Inheritance pravi čvršću vezu:

```text
Child
↓
Parent
```

dok composition kaže:

```text
Object A
→ koristi Object B
```

i B može mnogo lakše da se zameni.

---

## Laravel paralela

Laravel ti ovo radi svuda.
Na primer:

```php
class BookingController
{
    public function __construct(
        private BookingService $service
    ) {}
}
```

To nije:

```php
class BookingController extends BookingService
```

jer controller nije service.
Nego:

BookingController HAS-A BookingService

Isto:

```php
class BookingService
{
    public function __construct(
        private BookingRepository $repository
    ) {}
}
```

Service nije repository.
Koristi ga.
To je composition.

---

## Inheritance vs Composition

Najjednostavnije:

```text
Admin extends User
→ Admin IS-A User
```

```text
BookingService has BookingRepository
→ BookingService HAS-A BookingRepository
```

Ako odnos prirodno zvuči kao:

X je Y

inheritance može imati smisla.
Ako zvuči kao:

X koristi / ima Y

composition je verovatno bolji izbor.

## Mini interview pitanje 11

Zašto je ovo:

```php
class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}
}
```

bolji dizajn od:

```php
class BookingService extends StripeGateway
{
}
```

?
Objasni kroz IS-A vs HAS-A odnos i šta composition dobija u pogledu zamene implementacije.

---

Bolji je zato sto ovde umesto BookingService nasledjuje, imamo

BookingServis -> ima / koristi PaymentGateway.

Putem DI jedan Servis moze koristiti vise razlicitih klasa i orkestrirati akcijama. Njega ne zanima kako, on orkestrira, a pri tom ostaje tanak i lak za odrzavanje.

---

Tačno — 10/10.
Posebno si dobro uhvatio servis kao orkestratora:

```text
BookingService
→ ne mora da zna kako Stripe radi
→ ne mora da zna kako repository piše SQL
→ ne mora da zna kako mailer šalje email
```

```text
BookingService
→ orkestrira use-case
```

I ovo je ključ:

BookingService HAS-A PaymentGateway

a ne:

BookingService IS-A StripeGateway

Sitna nijansa: DI sam po sebi ne garantuje da će servis ostati tanak, ali ti mnogo olakšava da odgovornosti razdvojiš i delegiraš pravim objektima.
