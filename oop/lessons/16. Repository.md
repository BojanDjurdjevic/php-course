# 16. Repository

## Lekcija 16 — Repository

Repository je sloj koji odvaja business/service
kod od detalja čuvanja i čitanja podataka.

Najkraće:

Service pita šta mu treba, Repository zna kako
da do toga dođe iz persistence sloja.

Na primer:

```php
final class BookingRepository
{
    public function __construct(
        private PDO $pdo
    ) {}

    public function findById(int $id): ?Booking
    {
        $stmt = $this->pdo->prepare(
            'SELECT * FROM bookings WHERE id = :id'
        );

        $stmt->execute(['id' => $id]);

        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if (!$row) {
            return null;
        }

        return new Booking(
            id: (int) $row['id'],
            userId: (int) $row['user_id'],
            status: $row['status'],
        );
    }
}
```

Service onda ne radi:

```php
$stmt = $pdo->prepare(...);
$stmt->execute(...);
```

nego:

```php
$booking = $this->bookings->findById($id);
```

Mentalno:

```text
BookingService
→ "daj mi booking"
```

```text
BookingRepository
→ "znam kako da ga pročitam iz baze"
```

```text
PDO
→ izvrši SQL
```

---

## Zašto Repository?

Zato što Service ne treba da zna detalje poput:

```text
ime tabele
ime kolone
JOIN
PDO
fetch mode
SQL sintaksa
```

Service treba da govori jezikom use-case-a:

```php
$booking = $this->bookings->findById($id);

$this->bookings->save($booking);

$this->bookings->delete($booking);
```

To je mnogo čitljivije nego da između business odluka imaš 40 linija SQL-a.

---

## Repository nije samo "SQL helper"

Loš repository bi mogao izgledati ovako:

```php
public function query(string $sql): array
{
    // ...
}
```

pa service i dalje sam piše SQL.
Tada nismo mnogo dobili.
Bolje je da repository izrazi nameru:

```php
findById()
findForUser()
save()
delete()
findAvailableRooms()
```

Drugim rečima:

loše:

repository->`runQuery(...)`

bolje:

repository->`findAvailableRooms(...)`

Repository treba da sakrije persistence detalje.

---

## Repository interface

Možemo otići korak dalje:

```php
interface BookingRepository
{
    public function findById(int $id): ?Booking;

    public function save(Booking $booking): void;
}
```

Pa konkretna implementacija:

```php
final class PdoBookingRepository implements BookingRepository
{
    public function __construct(
        private PDO $pdo
    ) {}

    public function findById(int $id): ?Booking
    {
        // PDO
    }

    public function save(Booking $booking): void
    {
        // PDO
    }
}
```

A service:

```php
final class BookingService
{
    public function __construct(
        private BookingRepository $bookings
    ) {}
}
```

Service sada čak ni ne zna da koristiš PDO.
Sutra možeš imati:

```text
PdoBookingRepository
InMemoryBookingRepository
ApiBookingRepository
```

dok BookingService ostaje isti.

## Veza sa testiranjem

U testu možeš napraviti:

```php
final class InMemoryBookingRepository implements BookingRepository
{
    private array $bookings = [];

    public function findById(int $id): ?Booking
    {
        return $this->bookings[$id] ?? null;
    }

    public function save(Booking $booking): void
    {
        $this->bookings[$booking->id()] = $booking;
    }
}
```

i testirati service bez MySQL-a.
To je još jedan primer:

```text
interface
+
DI
+
composition
=
lakše testiranje
```

## Bitna nijansa: Repository nije uvek obavezan

Nemoj da upadneš u zamku:

Svaka aplikacija mora imati repository sloj.

Ne mora.
Za mali CRUD Laravel projekat, ovo:

```php
User::find($id);
```

može biti sasvim dovoljno.
Repository ima više smisla kada želiš:

```text
jasnu persistence granicu
kompleksnije upite
više izvora podataka
lakšu zamenu implementacije
testiranje bez pravog DB-a
čistiji domain/service sloj
```

Dakle Repository je alat, ne religija.

---

## Laravel paralela

Kod Eloquent-a:

```php
Booking::find($id);
```

Model već donekle kombinuje domain objekat i persistence API.
Zato Laravel projekti često funkcionišu bez repository-ja.
Ali ako uvedeš:

```text
BookingService
↓
BookingRepository
↓
Eloquent
```

onda Service više ne mora da zna Eloquent detalje.
To može biti korisno u većim aplikacijama, ali nepotrebno u jednostavnom CRUD-u.

## Mini interview pitanje 16

Zašto bi ovo:

```php
$booking = $this->bookings->findById($id);
```

u BookingService često bilo bolje nego da Service direktno piše PDO/SQL kod?
I drugo: zašto Repository pattern ipak ne treba uvoditi automatski u svaki mali CRUD projekat?

---

Prvo: Zato što servis treba da kaže:

"daj mi booking taj i taj" a Repository je taj koji zna kako da do njega dođe.

Ipak, Repository ima smisla kod velikih aplikacija kada imamo:

```text
jasnu persistence granicu
kompleksnije upite
više izvora podataka
lakšu zamenu implementacije
testiranje bez pravog DB-a
čistiji domain/service sloj
```

Kod malih CRUD operacija nema potrebe za Repository
jer može da se kontroliše sa malo koda.

---

Tačno — 10/10. Posebno je dobra ova formulacija:

Service kaže „daj mi booking“, Repository zna kako da do njega dođe.

To je upravo granica koju želimo.
I dobro si uhvatio da Repository nije nešto što ubacujemo „jer je enterprise“,
nego zato što rešava konkretan problem.
