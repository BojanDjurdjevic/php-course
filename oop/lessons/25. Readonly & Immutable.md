# 25. Readonly & Immutable

## Lekcija 25 — readonly i immutability

readonly smo već dotakli kod DTO-a, ali vredi ga razumeti kao OOP koncept.

Imamo:

```php
final readonly class CreateBookingData
{
    public function __construct(
        public int $userId,
        public int $roomId,
        public DateTimeImmutable $checkIn,
        public DateTimeImmutable $checkOut,
    ) {}
}
```

Kada se objekat napravi:

```php
$data = new CreateBookingData(
    userId: 5,
    roomId: 10,
    checkIn: new DateTimeImmutable('2026-11-10'),
    checkOut: new DateTimeImmutable('2026-11-13'),
);
```

ne možemo posle:

```php
$data->roomId = 20; // ❌
```

Property je inicijalizovan i više ne može biti reassigned.
Mentalno:

```text
mutable object
→ stanje može da se menja
```

```text
readonly / immutable-style object
→ napraviš ga sa stanjem
→ to stanje posle ostaje stabilno
```

---

## Zašto je to korisno?

Zamisli da kroz pet slojeva prosleđujemo DTO:

```text
Controller
↓
Service
↓
PriceCalculator
↓
Repository
```

Ako svako može da uradi:

```php
$data->roomId = 999;
```

teže je znati ko je promenio podatke.
Sa readonly znaš:

Ovo je snapshot input-a. Ne menjaj ga usput.

To smanjuje broj mogućih side effect-a.
readonly nije isto što i const
Ovo je važno.

```php
public const MAX_GUESTS = 4;
```

je vrednost vezana za klasu.
Dok:

```php
public readonly int $roomId;
```

je property konkretne instance.
Dakle:

```text
const
→ class-level constant
```

```text
readonly
→ instance property koji se nakon inicijalizacije ne može reassigned
```

---

## Bitna nijansa: readonly nije nužno "duboka" immutability

Recimo:

```php
readonly class Example
{
    public function __construct(
        public SomeObject $object
    ) {}
}
```

Ne možeš:

```php
$example->object = new SomeObject(); // ❌
```

ali ako SomeObject sam po sebi ima mutable stanje, možeš možda menjati njega:

```php
$example->object->changeSomething();
```

Dakle readonly štiti property reference od reassignment-a; ne pretvara
automatski ceo object graph u duboko immutable strukturu.
Zato smo kod DTO-a koristili:

DateTimeImmutable

umesto:

DateTime

To još bolje podržava ideju nepromenljivih podataka.
DTO je odličan kandidat

```php
final readonly class CreateBookingData
```

ima mnogo smisla jer DTO najčešće predstavlja:

"ovo su podaci koje sam primio za ovaj use-case"

Ne želimo da Service usput uradi:

```php
$data->checkOut = ...
```

Ako treba drugačiji skup podataka, možemo napraviti nov objekat.
To je često čistije nego mutiranje postojećeg.

## Mini interview pitanje 25

Koja je razlika između:

```php
public const MAX_GUESTS = 4;
```

i:

```php
public readonly int $guestCount;
```

?
I zašto je readonly posebno koristan kod DTO objekata koji prolaze
kroz više slojeva aplikacije?

---

Const su konstante vezane za klasu.

Dok su readonly instance properties
koji se ne mogu reasajnovati.

---

## Readonly je posebno koristan kod

DTO podataka kojeli putuju kroz app,
jer ne zelimo
da se njene vrednosti menjaju.

---

Tačno — 10/10. Upravo tako:

```text
const
→ pripada klasi
→ jedna fiksna vrednost
```

```text
readonly property
→ pripada konkretnoj instanci
→ dobija vrednost pri inicijalizaciji
→ posle ne može da se reassigned
```

---

## A kod DTO-a je posebno korisno baš zato što želimo da isti paket podataka

bez neočekivanih mutacija prođe:

```text
Controller
→ DTO
→ Service
→ drugi collaborators
```

Još jednom bitna nijansa: readonly ne garantuje automatski duboku
immutability ako property sadrži neki drugi mutable objekat.
