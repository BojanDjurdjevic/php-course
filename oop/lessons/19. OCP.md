# 19. OCP

## Lekcija 19 — O: Open/Closed Principle

OCP kaže:

Softverske jedinice treba da budu otvorene za proširenje,
a zatvorene za izmenu.

To zvuči apstraktno, pa hajde odmah praktično.
Zamisli:

```php
class PaymentService
{
    public function pay(string $type, int $amount): void
    {
        if ($type === 'stripe') {
            // Stripe logic
        }

        if ($type === 'paypal') {
            // PayPal logic
        }
    }
}
```

Danas imaš:

```text
Stripe
PayPal
```

Sutra želiš:

Adyen

Moraš da otvoriš postojeću klasu i dodaš:

```php
if ($type === 'adyen') {
    // ...
}
```

Prekosutra:

```text
Klarna
Revolut
Bank transfer
```

i PaymentService stalno menjaš.
To je signal da dizajn nije baš OCP-friendly.

## OCP preko interface-a

Napravimo contract:

```php
interface PaymentGateway
{
    public function charge(int $amount): void;
}
```

Implementacije:

```php
final class StripeGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // Stripe
    }
}

final class PayPalGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // PayPal
    }
}
```

Service:

```php
final class BookingService
{
    public function __construct(
        private PaymentGateway $payment
    ) {}

    public function pay(int $amount): void
    {
        $this->payment->charge($amount);
    }
}
```

Sada ako sutra uvedemo:

```php
final class AdyenGateway implements PaymentGateway
{
    public function charge(int $amount): void
    {
        // Adyen
    }
}
```

BookingService ne moramo da menjamo.
Samo mu damo novu implementaciju.
Mentalno:

```text
postojeći kod
→ ostaje zatvoren za izmene
```

```text
nova funkcionalnost
→ dodajemo novu implementaciju
```

To je OCP.
"Closed for modification" ne znači "nikad ne menjaj klasu"
To bi bilo besmisleno.
Ako postoji bug ili se promeni requirement koji pripada toj klasi — naravno da je menjaš.
OCP više govori:

Kada dodaješ novu varijantu istog ponašanja,
pokušaj da sistem može da je prihvati kroz proširenje,
umesto kroz stalno editovanje postojećeg koda.

Na primer loš pattern:

```php
switch ($paymentType) {
    case 'stripe':
        // ...
        break;

    case 'paypal':
        // ...
        break;

    case 'adyen':
        // ...
        break;
}
```

Ako se ovo širi svakog meseca, verovatno traži polymorphism/interface pristup.

---

## Veza sa DI

OCP i DI se lepo slažu:

```php
public function __construct(
    private PaymentGateway $payment
) {}
```

Jer Service ne zna konkretnu implementaciju.
To znači da možemo sistem proširiti:

```text
StripeGateway
PayPalGateway
AdyenGateway
FakePaymentGateway
```

bez promene Service-a.

## Laravel primer

Recimo notification channel.
Lošije:

```php
if ($channel === 'mail') {
    // mail
} elseif ($channel === 'sms') {
    // sms
} elseif ($channel === 'slack') {
    // slack
}
```

Bolje:

```php
interface NotificationChannel
{
    public function send(string $message): void;
}
```

pa:

```text
MailChannel
SmsChannel
SlackChannel
```

i sistem prima bilo koji NotificationChannel.

## Kako prepoznati OCP problem?

Kad vidiš da sa svakom novom varijantom stalno menjaš postojeći:

```text
if/elseif/elseif
switch
match
```

nije automatski bug, ali je znak da pitaš:

Da li ovo ponašanje treba izdvojiti iza interface-a/polymorphism-a?

Nekad je običan match sasvim dovoljan.
Ne treba forsirati pattern-e za dva trivijalna slučaja.

---

## Najkraći intervju odgovor

Open/Closed Principle:

kod treba da bude otvoren za proširenje,
ali zatvoren za nepotrebne izmene postojećeg ponašanja.

Praktično:

```text
novi payment provider
→ nova klasa
```

ne:

```text
→ menjaj BookingService svaki put
```

## Mini interview pitanje 19

Zašto je ovo:

```php
if ($type === 'stripe') {
    // ...
} elseif ($type === 'paypal') {
    // ...
} elseif ($type === 'adyen') {
    // ...
}
```

potencijalno OCP problem ako stalno dodajemo nove payment providere?
I kako bi interface + zasebne implementation klase rešile taj problem?

---

Ovaj primer je OCP problem iz razloga sto stalno moramo da izmenjujemo kod unutar klase ili servisa.

Bolje resenje je koristiti Interface + DI pa onda svaka nova implementacija zasebna klasa.
