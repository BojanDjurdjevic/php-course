# 29. Overriding and variance

## Lekcija 29 — Overriding, method signatures i variance

Method overriding smo već koristili:

```php
class User
{
    public function role(): string
    {
        return 'user';
    }
}

class Admin extends User
{
    public function role(): string
    {
        return 'admin';
    }
}
```

Ali child ne može proizvoljno da promeni contract metode.
Recimo:

```php
class PaymentProcessor
{
    public function process(int $amount): void
    {
    }
}
```

Ne možemo u child-u tek tako napraviti contract restriktivnijim:

```php
class StripeProcessor extends PaymentProcessor
{
    public function process(string $amount): void
    {
    }
}
```

To bi razbilo substitutability.
Jer kod koji zna:

PaymentProcessor

očekuje da može da uradi:

```php
$processor->process(1000);
```

Child mora i dalje da bude validan PaymentProcessor.
To se direktno vezuje za LSP.

---

## Visibility takođe ne smeš suziti

Ako parent ima:

```php
public function process(): void
```

child ne može da kaže:

```php
protected function process(): void
```

jer bi nešto što je bilo dostupno korisnicima parent contract-a odjednom nestalo.
Dakle:

```text
parent public
→ child mora ostati public
```

Možeš ići u širem smeru, recimo:

```text
protected → public
```

ali ne obrnuto.

## Covariance — return type

Ovde PHP dopušta nešto veoma korisno.
Imamo:

```php
class Animal
{
}

class Dog extends Animal
{
}
```

Parent:

```php
class AnimalFactory
{
    public function create(): Animal
    {
        return new Animal();
    }
}
```

Child može vratiti specifičniji tip:

```php
class DogFactory extends AnimalFactory
{
    public function create(): Dog
    {
        return new Dog();
    }
}
```

To se zove covariance.

---

## Zašto je bezbedno?

Ako neko očekuje:

Animal

a dobije:

Dog

nema problema jer:

Dog IS-A Animal

Mentalno:

```text
return type
Animal → Dog
```

```text
šire → specifičnije
```

je dozvoljeno.

---

## Contravariance — parameter type

Kod parametara ide logika u drugom smeru.
Recimo:

```php
class Animal
{
}

class Dog extends Animal
{
}
```

Parent contract:

```php
class DogHandler
{
    public function handle(Dog $animal): void
    {
    }
}
```

Child može prihvatiti širi tip:

```php
class AnimalHandler extends DogHandler
{
    public function handle(Animal $animal): void
    {
    }
}
```

---

## Zašto?

Parent je obećao:

Mogu da obradim Dog.

Child kaže:

Ja mogu čak i bilo koji Animal.

Dakle sigurno može i Dog.
To se zove contravariance.
Mentalno:

```text
parameter type
Dog → Animal
```

```text
specifičnije → šire
```

može biti dozvoljeno.

---

## Najlakši način da zapamtiš

Za overriding:

```text
PARAMETAR
→ child ne sme da bude zahtevniji
```

```text
RETURN
→ child može da bude precizniji
```

I ovo zapravo ima savršenu LSP logiku.
Ako parent obeća:

```php
function process(Dog $dog): Animal
```

child može reći:

Mogu da primim čak i bilo koji Animal, a garantujem da ću vratiti baš Dog.

To je bezbednije, ne restriktivnije.

---

## Interface primer

Isto važi kada implementiraš interface.

```php
interface UserFinder
{
    public function find(int $id): ?User;
}
```

Implementacija mora poštovati taj contract.
Ne može proizvoljno vratiti:

string

jer caller očekuje:

User|null

To je važna stvar: type declarations nisu samo pomoć IDE-u — oni predstavljaju deo OOP contract-a.

Ako sme — zašto je bezbedno da parent obećava Animal,

## Tako da ovde moze child da vrati Dog iz prostog razloga sto

Dog IS - A Animal.
Tako moze da suzi i da vrati specifičniji type
ali samo pod uslovom da vraćeni tip
jeste naslednik, child očekivanog.

---

```text
covariance
→ return type može da ide ka specifičnijem tipu
```

```text
Animal
  ↑
 Dog
```

```text
Animal → Dog ✅
```

Jer ako caller očekuje Animal, a dobije Dog, contract nije prekršen — Dog jeste Animal.
