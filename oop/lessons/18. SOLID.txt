Lekcija 18 — SOLID: šta je to zapravo?
SOLID nije pet pravila koja moraš slepo da primeniš.
To je skup principa koji pokušavaju da postignu:
manji coupling
jasnije odgovornosti
lakše izmene
lakše testiranje

Pet slova:
S → Single Responsibility Principle
O → Open/Closed Principle
L → Liskov Substitution Principle
I → Interface Segregation Principle
D → Dependency Inversion Principle

Ići ćemo jedan po jedan.
S — Single Responsibility Principle
Često se pogrešno objašnjava kao:
Klasa sme da ima samo jednu metodu.

Ne.
Bolja definicija:
Klasa treba da ima jedan glavni razlog za promenu.

Recimo:
class BookingService
{
    public function create(array $data): void
    {
        // validate HTTP input

        // SQL

        // calculate price

        // Stripe

        // generate PDF

        // send email

        // write log
    }
}

Ova klasa može da se promeni ako se promeni:
booking workflow
database
payment provider
email provider
PDF format
validation
logging

To je mnogo razloga za promenu.
SRP predlaže da razdvojimo odgovornosti:
BookingService
→ booking workflow

BookingRepository
→ persistence

PaymentGateway
→ payment

Mailer
→ email

VoucherGenerator
→ PDF

FormRequest
→ request validation

BookingService i dalje može da koristi sve njih:
final class BookingService
{
    public function __construct(
        private BookingRepository $bookings,
        private PaymentGateway $payment,
        private Mailer $mailer,
    ) {}
}

Ali više ne zna kako oni obavljaju svoj posao.
SRP ne znači "što više klasa to bolje"
I ovo je veoma bitno.
Ako za trivijalnu operaciju napraviš:
BookingNameService
BookingEmailService
BookingDateService
BookingStatusService

možeš napraviti još goru arhitekturu.
Cilj nije:
jedna linija = jedna klasa

nego:
grupiši ponašanje koje pripada istoj odgovornosti.

Na primer:
class PriceCalculator
{
    public function subtotal(...): int {}
    public function discount(...): int {}
    public function total(...): int {}
}

ima više metoda, ali sve imaju jednu koherentnu odgovornost:
pricing

To je sasvim u skladu sa SRP.
"One reason to change"
Ovo je najbolji test.
Za BookingRepository:
Zašto bi se ova klasa menjala?
→ promenio se način persistence-a / DB upita

Za BookingService:
Zašto bi se menjala?
→ promenio se booking use-case

Za Mailer:
Zašto bi se menjao?
→ promenio se način slanja maila

Granice nisu matematičke, ali ova pitanja mnogo pomažu.
Laravel paralela
Loš Controller:
public function store(Request $request)
{
    $request->validate(...);

    DB::transaction(...);

    Stripe::charge(...);

    Mail::send(...);

    Storage::put(...);

    return response(...);
}

radi praktično sve.
Čistiji dizajn:
FormRequest
↓
Controller
↓
BookingService
├── Repository
├── PaymentGateway
├── Notification/Mailer
└── InventoryService

To je SRP u praksi.

Mini interview pitanje 18
Zašto ova klasa verovatno krši SRP:
class BookingManager
{
    public function createBooking(): void
    {
        // SQL
        // payment
        // send email
        // generate PDF
    }
}

?
Nemoj mi samo reći „radi previše stvari“ — reci mi kroz SRP terminologiju: 
koliko različitih razloga za promenu ova klasa ima?

---

Zato sto ova klasa ima 4 razloga za promenu, 
dok SRP princip predlaze ne jedna klasa = jedna metoda nego upravo:

1 klasa -> jedan razlog za promenu

---

Tačno — 10/10.
To je najbolja formulacija:
SRP ≠ jedna klasa = jedna metoda

SRP = jedna klasa → jedan glavni razlog za promenu

U tvom primeru imamo više razloga:
SQL promena
payment promena
email promena
PDF promena

zato je klasa previše odgovorna za različite stvari.
